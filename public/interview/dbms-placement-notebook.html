01

Foundations: data, databases and the DBMS

Start here. Every later chapter is a detail of something on this page.

Almost every interview opens with a definition question, and almost every candidate answers it in a way that sounds memorised. The fix is to understand why the DBMS was invented at all, because the reason is the answer to five other questions later.

1.1 Data, information, database

  • Data — raw, unprocessed facts. 1204, 'Alan', 8.7 means nothing by itself.
  • Information — data placed in context so it answers a question. “Student 1204, Alan, has CGPA 8.7.”
  • Database — an organised, self-describing collection of related data that models some slice of the real world (called the mini-world or universe of discourse).
  • Metadata — data about the data: table names, column types, constraints, index definitions. Stored in the data dictionary / system catalog. “Self-describing” means the database carries its own metadata, unlike a plain file.
  • DBMS — the software layer between users and the stored data that lets you define, construct, manipulate and share a database while enforcing correctness and security. MySQL, PostgreSQL, Oracle, SQL Server, SQLite are DBMSs; the data they hold is the database.
  • Database system — the DBMS plus the database itself plus the applications built on it.
One-line definition to memorise

A DBMS is software that stores data in a structured way and provides controlled, concurrent, recoverable and secure access to it through a query language.

1.2 Why not just use files?

Before DBMSs, applications wrote their data into their own files. Every problem the DBMS solves is a problem of that world, so answer this question by naming the disease, not just the cure.

1.3 Advantages and the honest disadvantages

Advantages: controlled redundancy, enforced integrity, restricted access, backup and recovery, multiple user interfaces, ability to represent complex relationships, data independence, and reduced application development time.

Disadvantages (mention these — it shows judgement): licence and hardware cost, the overhead of generality (a hand-written file format can be faster for one fixed job), complexity, and a single point of failure if not replicated. For simple embedded, single-user or read-only workloads a plain file or SQLite-style embedded engine may genuinely be better.

1.4 Who touches the database

  • DBA (Database Administrator) — authorises access, tunes performance, plans storage, schedules backups, defines the schema. The only person with full authority.
  • Database designer — identifies the data to be stored and chooses the structures; produces the ER model and the normalized schema.
  • Application programmer — writes programs that embed SQL calls.
  • End users — naive (use a form or app, e.g. a bank teller), sophisticated (analysts writing their own SQL), casual (occasional ad-hoc queries), specialised (CAD/GIS/ML applications).
  • Behind the scenes — DBMS designers, tool developers, operations staff.

1.6 Two more terms that get confused

  • Schema — the design/structure of the database. Changes rarely. Also called the intension.
  • Instance (or state) — the data present at a given moment. Changes constantly. Also called the extension.

The classic analogy: schema is the class, instance is the object. Or: schema is the variable declaration, instance is its current value.

Interview drill ch. 01

What is a DBMS, and how is it different from a database?

A database is the organised collection of related data itself. A DBMS is the software that manages that data — it lets you define the schema, insert and query data, and it guarantees integrity, concurrency, recovery and security on top. MySQL is a DBMS; the college database inside it is a database.

Give me three concrete problems with using files instead of a database.

One, redundancy and inconsistency — the same customer address lives in two files and only one gets updated. Two, no atomicity — if the machine crashes halfway through a funds transfer, money disappears, because a file has no notion of a transaction. Three, no concurrency control — two users writing the same record can silently lose one update. Files also force you to write a new program for every new question, whereas SQL is declarative.

What is metadata? Where does the DBMS keep it?

Metadata is data describing the data: table and column names, data types, constraints, indexes, views, privileges, statistics. The DBMS stores it in the data dictionary or system catalog — itself a set of tables you can query (information_schema in MySQL/Postgres, USER_TABLES in Oracle). This self-describing property is what a plain file lacks.

Difference between a schema and an instance?

The schema is the structural definition — tables, attributes, types, constraints — and it is largely static. The instance is the actual set of rows stored at a particular moment, and it changes with every INSERT or DELETE. Schema : instance :: class : object.

Classify: TRUNCATE, GRANT, MERGE, SAVEPOINT.

TRUNCATE is DDL (it deallocates the storage structure, so it is not a normal row-by-row delete). GRANT is DCL. MERGE is DML. SAVEPOINT is TCL. The TRUNCATE classification is the trap — many candidates say DML.

When would you deliberately not use a DBMS?

When the data is small, single-user and has a fixed access pattern — configuration files, logs that are only appended and grepped, embedded firmware storing a few calibration constants. Also when the workload is a one-shot batch scan over immutable data, where a columnar file (Parquet) plus a processing framework beats paying for transactional machinery you never use.

Architecture and data independence

Three levels, two mappings, two kinds of independence. Easy marks if you draw it.

2.1 The three-schema (ANSI/SPARC) architecture

The goal of the architecture is a single idea: separate the data as users see it from the data as it is physically stored, so that changing one does not break the other.

        ┌──────────────┐  ┌──────────────┐  ┌──────────────┐
        │  View 1      │  │  View 2      │  │  View 3      │   EXTERNAL LEVEL
        │ (clerk)      │  │ (professor)  │  │ (student)    │   what each user sees
        └──────┬───────┘  └──────┬───────┘  └──────┬───────┘

                    ┌───────────────────────────┐             │  LOGICAL DATA
                    │   CONCEPTUAL SCHEMA       │  ◄──────────┘  INDEPENDENCE
                    │ all tables, attributes,   │
                    │ relationships, constraints│
                    └─────────────┬─────────────┘
                       conceptual/internal mapping
                                  ▼                              PHYSICAL DATA
                    ┌───────────────────────────┐  ◄───────────  INDEPENDENCE
                    │   INTERNAL SCHEMA         │

Draw this on the whiteboard and label the two arrows — that is the whole answer.

  • External / view level — the highest level. Many views, each showing one user group only the part of the data it needs, hiding the rest. Implemented with VIEWs.
  • Conceptual / logical level — one per database. Describes what data is stored and the relationships, without saying how. This is where your normalized tables live.
  • Internal / physical level — one per database. Describes how: file organization, index structures, record placement, compression.

2.2 Data independence

  • Physical data independence — you can change the internal schema (add an index, move a table to another disk, switch from heap to clustered storage) without changing the conceptual schema or any application. Easily achieved.
  • Logical data independence — you can change the conceptual schema (add a column, split a table) without changing the external views or the applications. Harder to achieve, because a view often depends directly on the columns you changed.
Classic trap

“Which is harder to achieve?” — Logical data independence is harder. Candidates guess “physical” because it sounds lower-level and scarier. The reason logical is harder: views and application code name conceptual-level objects directly, so a logical change can break them; nothing above the internal level names a disk block.

2.3 Tiered architectures

2.4 Inside the engine

Know roughly what components exist; it makes chapters 10–13 make sense.

  • Query processor — DDL interpreter, DML compiler, parser (syntax), semantic analyser (does the table exist?), optimizer (choose a plan), execution engine.
  • Storage manager — authorisation & integrity manager, transaction manager, buffer manager (moves pages between disk and RAM), file manager.
  • Disk structures — data files, data dictionary, indexes, statistics, and the write-ahead log.

Interview drill ch. 02

Explain the three-schema architecture and why it exists.

Three levels: external (per-user views), conceptual (the whole logical design — tables, relationships, constraints), and internal (physical storage: files, pages, indexes). Two mappings connect them. It exists to provide data independence: because users never address storage directly, the DBA can reorganise storage or evolve the logical design without rewriting applications. It also supports security, since a view can expose only some columns and rows.

Physical vs logical data independence — with an example each.

Physical: I add a B+ tree index on employee.dept_id or move the table to a faster disk. Query results and application code are unchanged — only speed changes. Logical: I split employee into employee and employee_address. If the applications read a view employee_full that joins them back, they need no change — that is logical data independence, and it is harder because most views depend on the exact conceptual structure.

Why is a 3-tier architecture preferred for web apps?

The middle tier centralises business logic (so rules are not duplicated in every client), acts as a security boundary — the database is never directly reachable from the internet — and enables scaling: you can run many stateless application servers with connection pooling against one database. It also decouples client technology from the database.

What does the buffer manager do, and why does it matter for performance?

It manages the pool of database pages cached in main memory: deciding what to keep, what to evict (LRU/clock-style policies), and coordinating with the log so a dirty page is never written before its log record (the write-ahead rule). It matters because a disk/SSD read is orders of magnitude slower than RAM, so almost all tuning is really about raising the buffer hit ratio.

How many external, conceptual and internal schemas can a database have?

Many external schemas, exactly one conceptual schema, and exactly one internal schema.

Data models

The vocabulary for describing structure. Short chapter, but it frames chapter 14.

A data model is a set of concepts for describing data, relationships, semantics and constraints. Models are usually grouped by how abstract they are:

  • High-level / conceptual — close to how people think. ER and EER models. Entities, attributes, relationships.
  • Representational / implementation — what real DBMSs use. Relational, network, hierarchical, object-relational.
  • Low-level / physical — record formats, orderings, access paths.

3.1 The historical models

Say this and you sound senior

Codd’s breakthrough was not tables — it was replacing pointer navigation with value-based relationships, which is what makes a declarative query language possible. If rows are linked by matching values rather than physical addresses, the optimizer is free to choose how to find them.

3.2 Three-level classification of database systems

Interviewers sometimes ask you to “classify DBMSs”. Use these axes: by data model (relational / document / graph…), by number of users (single vs multi-user), by number of sites (centralised vs distributed), by cost/licensing (open source vs proprietary), and by purpose (general purpose vs special purpose, OLTP vs OLAP).

Interview drill ch. 03

What is a data model? Name the categories.

A collection of concepts used to describe the structure of a database — the data types, relationships, constraints and operations. Categories: conceptual/high-level (ER, EER), representational/implementation (relational, network, hierarchical, object-relational), and physical/low-level (record formats, access paths).

Why did the relational model replace hierarchical and network models?

Because it decoupled the query from the storage. In hierarchical/network systems the programmer navigated physical links, so any change in structure broke the programs, and many-to-many relationships were awkward. The relational model links data by values, gives a formal algebra to reason about queries, and enables a declarative language where the optimizer picks the access path — giving real data independence.

Is the ER model a data model that a DBMS implements?

No. ER is a conceptual design model — a communication and design tool. You then map the ER diagram to a representational model (usually relational tables) that the DBMS actually implements.

ER and EER modelling

How a vague requirement becomes a schema. Expect a live design question.

4.1 The building blocks

  • Entity — a distinguishable real-world object (a student, a course). An entity set/type is the collection of all of them. Drawn as a rectangle.
  • Attribute — a property of an entity. Drawn as an ellipse.
  • Relationship — an association among entities. Drawn as a diamond.
  • Domain — the set of permitted values for an attribute.

4.2 Cardinality and participation

Cardinality ratio answers “how many of B can one A be related to?” — 1:1, 1:N, N:1, M:N. Participation answers “must every A take part?” — total (double line, mandatory) or partial (single line, optional). Together they are the structural constraints; the alternative notation is (min, max), where min = 1 means total participation.

   │ EMPLOYEE │════════║  works_in ║────────│   DEPT   │

                    N                     1

4.3 Weak entity sets

A weak entity has no key of its own; it is identified only in combination with an owner/identifying entity through an identifying relationship. Its own partial key (discriminator, dashed underline) distinguishes it only among the siblings of one owner.

  • Classic example: DEPENDENT of an EMPLOYEE. Two employees can both have a dependent named “Anu”.
  • Notation: double rectangle for the entity, double diamond for the identifying relationship.
  • A weak entity always has total participation in the identifying relationship — it cannot exist without an owner.
  • When mapped to tables, the primary key is (owner PK, discriminator), and the foreign key gets ON DELETE CASCADE.

4.4 EER: the extended features

  • Specialization — top-down: from EMPLOYEE derive ENGINEER, MANAGER.
  • Generalization — bottom-up: from CAR and TRUCK abstract VEHICLE.
  • Inheritance — a subclass inherits all attributes and relationships of its superclass.
  • Constraints on specialization:
    • Disjoint (d) — an entity belongs to at most one subclass. Overlapping (o) — it may belong to several.
    • Total — every superclass entity must be in some subclass (double line). Partial — it need not.
  • Aggregation — treats a whole relationship as one abstract entity so it can participate in another relationship. Needed when a relationship must relate to an entity: e.g. the (employee works-on project) relationship is monitored by a MANAGER.
  • Category / union type — a subclass whose members come from the union of several distinct superclasses (an OWNER is a PERSON or a COMPANY).

4.5 Mapping ER to relational tables — the seven rules

  1. Strong entity → one table; its key attribute becomes the primary key; composite attributes are flattened into their simple parts; derived attributes are dropped.
  2. Weak entity → one table containing the owner’s PK as a foreign key; PK = (owner PK + partial key).
  3. 1:1 relationship → put the foreign key in the table of the side with total participation (fewer NULLs). Optionally merge both entities into one table.
  4. 1:N relationship → put the foreign key on the N side, pointing to the 1 side. No new table needed.
  5. M:N relationship → always a new table (junction/bridge table) whose PK is the pair of foreign keys, plus any relationship attributes.
  6. Multi-valued attribute → a separate table with (entity PK, value), PK = both columns.
  7. N-ary relationship → a new table with a foreign key to each participating entity.
Memory hook

“Many gets the key, many-to-many gets a table.” That single sentence answers most ER-mapping questions.

Specialization mapping options

  • Single table (one big table with a type discriminator) — fast, but many NULLs.
  • Table per subclass with inherited PK — clean, needs joins.
  • Table per concrete subclass only — fine when the specialization is total and disjoint.

Interview drill ch. 04

What is a weak entity? Give an example and its primary key.

A weak entity has no key attribute of its own and depends on an owner entity for identification. Example: DEPENDENT owned by EMPLOYEE. Its partial key (say dep_name) is unique only within one employee’s dependents, so the table’s primary key is the composite (emp_id, dep_name), with emp_id a foreign key declared ON DELETE CASCADE. A weak entity always has total participation in its identifying relationship.

How do you convert an M:N relationship to tables? Why can’t you just use a foreign key?

You create a separate junction table containing one foreign key per participating entity, with the pair as the primary key, plus any relationship attributes such as grade. A single foreign key column cannot work because a foreign key column holds one value per row — it can express “many rows point to one row” (1:N) but not both directions. Trying to store multiple values in one column also violates 1NF.

Where do you place the foreign key in a 1:1 relationship?

On the side with total participation, so the column is never NULL — e.g. in employee manages department with every department having a manager, put manager_id in department. Add a UNIQUE constraint on it to enforce the 1:1. If both sides are total, you can merge the two entities into a single table.

Specialization vs generalization vs aggregation.

Specialization is top-down — splitting a superclass into subclasses based on distinguishing characteristics. Generalization is bottom-up — merging common attributes of several entities into a superclass. Both produce an inheritance hierarchy; they differ in the direction of the design process. Aggregation is different in kind: it treats an entire relationship as a single higher-level entity so that it can participate in another relationship — used when you need a relationship between a relationship and an entity, which plain ER cannot express.

Disjoint vs overlapping specialization?

Disjoint (marked d) means an entity can belong to at most one subclass — a vehicle is either a car or a truck. Overlapping (marked o) means it can belong to several — a person in a university can be both student and employee. Independently, the specialization can be total (every superclass member must be in a subclass) or partial.

Design a schema for a library on the spot.

Talk through it in this order and you will never freeze: (1) entities — BOOK, COPY, MEMBER, AUTHOR, LOAN; (2) note that a physical COPY is distinct from the abstract BOOK (this observation alone impresses); (3) relationships — BOOK M:N AUTHOR → junction book_author; BOOK 1:N COPY; MEMBER 1:N LOAN, COPY 1:N LOAN with issue_date, due_date, return_date; (4) constraints — a copy can have at most one open loan, enforced by a partial unique index on copy_id WHERE return_date IS NULL; (5) keys and indexes — index loan(member_id) and loan(due_date) for overdue reports.

How do you handle a derived attribute like age?

Do not store it. Store dob and compute age in the query or in a view, otherwise the value silently goes stale and you get an update anomaly. Store a derived value only as a deliberate denormalization for performance, and then keep it correct with a trigger or a scheduled refresh.

The relationship in one line

Every candidate key is a super key; the primary key is one chosen candidate key; the rest are alternate keys. So: super key ⊇ candidate key ⊇ primary key.

Counting super keys — a common written-test question

If a relation has n attributes and {A} is the only candidate key, then any subset containing A is a super key, so the count is 2n−1. With two disjoint single-attribute candidate keys A and B in n attributes, use inclusion–exclusion: 2n−1 + 2n−1 − 2n−2 = 3 · 2n−2.

5.3 Integrity constraints

  • Domain constraint — every value must belong to the attribute’s domain (type, CHECK, enumerations).
  • Entity integrity — no part of a primary key may be NULL. Reason: a NULL cannot identify anything.
  • Referential integrity — a foreign key must either be NULL or match an existing primary key value in the referenced relation.
  • Key constraint — no two tuples may share the same candidate-key value.
  • Semantic / business constraints — application rules such as “an account balance may not go below zero”, enforced by CHECK, triggers or assertions.

Referential actions

When a referenced row is deleted or updated, the FK declares what happens:

RESTRICT checks immediately; NO ACTION defers the check to the end of the statement. In practice they behave the same in most cases.

5.4 NULL — the value that is not a value

NULL means unknown, not applicable or withheld — never “zero” and never “empty string”. Consequences worth stating:

  • Comparisons return UNKNOWN: NULL = NULL is not true. Use IS NULL.
  • SQL uses three-valued logic: TRUE, FALSE, UNKNOWN. A WHERE clause keeps only TRUE rows.
  • Aggregates ignore NULLs — COUNT(col) skips them while COUNT(*) does not; AVG divides by the non-NULL count.
  • GROUP BY, DISTINCT and UNION treat all NULLs as one group (they use “not distinct”, not equality).
  • Any arithmetic with NULL is NULL. Use COALESCE(x, 0).

Interview drill ch. 05

Super key vs candidate key vs primary key.

A super key is any set of attributes that uniquely identifies a row; it may carry redundant attributes. A candidate key is a minimal super key — no proper subset of it is still unique. The primary key is the one candidate key the designer picks; it must be non-NULL and should be small and stable. The remaining candidate keys are alternate keys and are usually enforced with UNIQUE constraints.

Can a primary key be NULL? Can a foreign key? Can a unique key?

Primary key: no — entity integrity forbids it, and in a composite PK no component may be NULL. Foreign key: yes — a NULL FK simply means “not related to anything yet”, and referential integrity is satisfied vacuously. Unique key: yes — the SQL standard and most engines allow NULLs, and MySQL/Postgres allow multiple NULLs in a UNIQUE column because NULLs are not equal to each other.

Can a table have two primary keys?

No. It can have exactly one primary key, but that key may be composite — made of several columns. Multiple candidate keys can exist; the extras are enforced with UNIQUE. This wording trap is deliberate: “composite key” ≠ “two primary keys”.

Surrogate key or natural key — which do you choose and why?

I default to a surrogate key (auto-increment or UUID) as the primary key and enforce the natural key with a UNIQUE constraint. Reasons: natural keys change (people change email, phone, even government IDs get reissued), they are often wide, which bloats every secondary index and foreign key, and they leak business meaning into every child table. The trade-off is one extra join to look up a row by its business identifier, and the loss of a naturally meaningful key. For a small static lookup table, a natural key like a country code is fine.

What is referential integrity, and what happens when you delete a parent row?

Referential integrity says every non-NULL foreign key value must match an existing primary key value in the referenced table, so there are no orphan rows. On deleting a parent, the behaviour follows the declared action: RESTRICT/NO ACTION rejects it, CASCADE deletes the children, SET NULL nulls the child’s FK, SET DEFAULT points it at a default row. I choose CASCADE only when the child cannot meaningfully exist without the parent, like order line items.

How many super keys does R(A,B,C,D) have if A is the only candidate key?

Every super key must contain A, and the other three attributes are freely present or absent: 2³ = 8. In general 2n−1 for a single-attribute candidate key in an n-attribute relation.

Why is WHERE salary <> NULL wrong?

Because comparing anything to NULL yields UNKNOWN, not TRUE, and WHERE only keeps TRUE rows — so the query returns nothing at all, silently. The correct form is WHERE salary IS NOT NULL. This is three-valued logic, and it is also why NOT IN with a NULL in the subquery returns no rows.

Difference between COUNT(*), COUNT(1) and COUNT(col).

COUNT(*) counts rows. COUNT(1) is identical in every modern optimizer — the constant is never evaluated per row, so the folklore that it is faster is false. COUNT(col) counts rows where col IS NOT NULL, so it can be smaller. COUNT(DISTINCT col) counts distinct non-NULL values.

Can a foreign key reference the same table?

Yes — a self-referencing or recursive foreign key, used for hierarchies: employee.manager_id referencing employee.emp_id. The root row has a NULL manager. You traverse it with a recursive CTE. It can also reference a UNIQUE column rather than the primary key.

Relational algebra and calculus

The maths behind SQL. Asked in written tests and by product companies.

Relational algebra is procedural — it says how to get the answer as a sequence of operations. Relational calculus is non-procedural/declarative — it describes what the answer looks like. SQL is closer to calculus in style; the engine converts it into an algebra tree to execute. Closure means every operation takes relations and returns a relation, so operations compose.

6.2 Joins

  • Theta join R ⋈θ S — product followed by a selection on any condition θ.
  • Equi join — a theta join where θ uses only =. The common column appears twice.
  • Natural join R ⋈ S — equi join on all same-named attributes, keeping only one copy of each. If there are no common attributes it degenerates into a Cartesian product.
  • Outer joins — left ⟕, right ⟖, full ⟗: keep unmatched tuples and pad with NULLs.
  • Semi join R ⋉ S — tuples of R that have some match in S, returning only R’s columns (SQL: EXISTS). Anti join — those with no match (NOT EXISTS).

6.3 Division — the “for all” operator

R ÷ S returns the values in R that are associated with every tuple of S. Use it for questions phrased “find students who have taken all courses offered by the CS department”.

6.4 Extended operations

Real systems add: generalized projection (computed columns), aggregate functions with grouping (G𝓕agg), assignment (←) for temporary results, and outer joins.

6.5 Relational calculus

  • Tuple relational calculus (TRC) — variables range over tuples: { t | t ∈ STUDENT ∧ t.cgpa > 8 }.
  • Domain relational calculus (DRC) — variables range over attribute values: { ⟨n⟩ | ∃c (⟨n,c⟩ ∈ STUDENT ∧ c > 8) }.
  • An expression must be safe — it must produce a finite result. {t | ¬(t ∈ R)} is unsafe: infinitely many tuples are not in R.
  • Relational completeness — a language is relationally complete if it can express everything relational algebra can. Algebra, safe TRC and safe DRC are all equivalent in expressive power; SQL is relationally complete and then some (it adds aggregation, ordering and recursion).

Interview drill ch. 06

Difference between relational algebra and relational calculus.

Algebra is procedural: you specify the sequence of operations, so you are effectively giving a query plan. Calculus is declarative: you describe the properties of the tuples you want and leave the evaluation strategy open. They have equal expressive power for safe expressions. SQL looks like calculus but is compiled into an algebra tree that the optimizer rewrites.

Why is projection said to reduce cardinality?

Because relational algebra works on sets: after dropping columns, previously distinct tuples may become identical and duplicates are eliminated, so the row count can shrink. SQL differs — plain SELECT col keeps duplicates because SQL tables are multisets; you need DISTINCT to match the algebra.

Natural join vs equi join vs theta join.

Theta join allows any comparison operator in the condition. Equi join restricts theta to equality, and both copies of the compared columns survive in the result. Natural join is an equi join on all commonly named attributes with the duplicate column removed automatically. Natural join is convenient but risky in production: adding a column with a coincidentally matching name silently changes the join condition, which is why explicit ON clauses are preferred.

How do you express “find suppliers who supply every part”?

That is relational division: SUPPLY(sid, pid) ÷ PART(pid). In SQL, either a double NOT EXISTS — “no part exists that this supplier does not supply” — or a counting form comparing COUNT(DISTINCT pid) per supplier against the total number of parts. The counting form is usually clearer and often faster; the NOT EXISTS form is the direct translation of the universal quantifier.

What is a safe expression in relational calculus?

One whose result is guaranteed finite, i.e. every tuple in the result is built from values appearing in the database or in the query itself (the domain of the expression). Negation alone, like “all tuples not in R”, is unsafe because the universe of possible tuples is infinite. Restricting to safe expressions is what makes calculus equivalent to algebra.

If R has 5 tuples with 3 attributes and S has 4 tuples with 2 attributes, what is R × S?

Degree (columns) = 3 + 2 = 5; cardinality (rows) = 5 × 4 = 20. Degrees add, cardinalities multiply.

7.5 Aggregates and grouping

SELECT d.dept_name,
       COUNT(*)        AS headcount,
       AVG(e.salary)   AS avg_salary,
       MAX(e.salary)   AS top_salary
FROM   employee e
JOIN   department d ON d.dept_id = e.dept_id
WHERE  e.hire_date >= '2020-01-01'      -- filters rows   (before grouping)
GROUP BY d.dept_name
HAVING COUNT(*) > 5                     -- filters groups (after grouping)
ORDER BY avg_salary DESC;

Rule: every non-aggregated column in the SELECT list must appear in GROUP BY (PostgreSQL and standard SQL enforce this strictly; MySQL only with ONLY_FULL_GROUP_BY, which is on by default in modern versions).

7.6 Subqueries

  • Scalar subquery — returns one row, one column; usable anywhere a value is.
  • Row / table subquery — used with IN, ANY, ALL, or in the FROM clause (a derived table, which must be aliased).
  • Correlated subquery — references a column from the outer query, so conceptually it re-runs per outer row. Recognise it by the outer alias inside.
-- non-correlated: employees earning more than the company average
SELECT name FROM employee
WHERE salary > (SELECT AVG(salary) FROM employee);

-- correlated: employees earning more than their own department's average
SELECT e.name FROM employee e
WHERE e.salary > (SELECT AVG(x.salary) FROM employee x
                  WHERE x.dept_id = e.dept_id);

-- EXISTS: departments that have at least one project
SELECT d.dept_name FROM department d
WHERE EXISTS (SELECT 1 FROM project p WHERE p.dept_id = d.dept_id);
IN vs EXISTS vs JOIN

Semantically IN and EXISTS agree except for NULLs: if the subquery of a NOT IN returns even one NULL, the whole predicate becomes UNKNOWN and you get zero rows. NOT EXISTS is NULL-safe, so prefer it. Performance-wise, modern optimizers usually rewrite all three into the same semi-join, so “EXISTS is always faster” is outdated folklore — but EXISTS can short-circuit on the first match, which helps when the inner set is large.

7.7 Set operators

UNION (removes duplicates, so it sorts or hashes — costly), UNION ALL (keeps everything, cheap — use it whenever duplicates are impossible), INTERSECT, EXCEPT (MINUS in Oracle). All require the same number of columns with compatible types.

7.8 Views

  • A view is a stored query — a virtual table. It stores no data; it is expanded at query time.
  • Benefits: security (expose some columns/rows only), simplification of complex joins, logical data independence, and a stable interface over a changing schema.
  • A view is updatable only if the DBMS can map a modified row back to exactly one base row: typically one base table, no DISTINCT, no aggregation, no GROUP BY, no set operators, no window functions, and the base table’s required columns present.
  • WITH CHECK OPTION prevents inserting a row through the view that the view itself could not see afterwards.
  • A materialized view physically stores the result and must be refreshed (on commit, on demand, or on a schedule). It trades staleness for speed and is a staple of reporting/OLAP.
CREATE VIEW high_earners AS
SELECT emp_id, name, dept_id, salary FROM employee WHERE salary > 100000
WITH CHECK OPTION;

CREATE MATERIALIZED VIEW dept_summary AS
SELECT dept_id, COUNT(*) AS headcount, AVG(salary) AS avg_sal
FROM employee GROUP BY dept_id;

Interview drill ch. 07

What is the logical order of execution of a SELECT statement?

FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT. This explains why a column alias defined in SELECT is unusable in WHERE but usable in ORDER BY, and why aggregates belong in HAVING rather than WHERE.

WHERE vs HAVING.

WHERE filters individual rows before grouping and cannot contain aggregate functions. HAVING filters groups after GROUP BY and normally does contain aggregates. When a condition can go in either place, put it in WHERE — filtering earlier means fewer rows to group, so it is cheaper.

DELETE vs TRUNCATE vs DROP.

DELETE — DML, row-by-row, supports WHERE, fires triggers, fully logged, rollback-able, keeps identity counters. TRUNCATE — DDL, deallocates pages, no WHERE, no row triggers, minimal logging, far faster, typically resets identity, auto-commits in MySQL and Oracle. DROP — DDL, removes the table itself with its indexes, constraints, triggers and privileges.

Explain all the join types with an example.

INNER returns only matched pairs. LEFT OUTER returns all left rows, padding unmatched right columns with NULL — “all employees including those without a department”. RIGHT OUTER is the mirror. FULL OUTER keeps unmatched rows from both sides. CROSS is the Cartesian product. SELF joins a table to itself with two aliases, used for employee–manager. A LEFT JOIN plus WHERE right.pk IS NULL is the standard anti-join pattern for finding rows with no match.

Why did my LEFT JOIN behave like an INNER JOIN?

Because a predicate on the right-hand table was placed in WHERE instead of ON. After the join, unmatched left rows carry NULLs on the right, and NULL = 'Chennai' is UNKNOWN, so those rows are discarded and the outer join collapses to an inner join. Move the condition into the ON clause, or allow NULLs explicitly with OR d.location IS NULL.

UNION vs UNION ALL — which is faster and why?

UNION ALL is faster: it simply concatenates. UNION additionally removes duplicates, which requires a sort or a hash over the whole result. Use UNION ALL whenever duplicates are impossible or acceptable — for example when combining strictly disjoint partitions.

Correlated vs non-correlated subquery.

A non-correlated subquery is independent — it can be run once on its own, and the optimizer usually caches its result. A correlated subquery references a column of the outer query, so logically it is evaluated once per outer row, which is why it can be slow; optimizers often rewrite it into a join or semi-join. Example of correlated: employees earning above their own department’s average.

Why can NOT IN return zero rows unexpectedly?

If the subquery result contains a NULL, then for every candidate row the comparison x <> NULL evaluates to UNKNOWN, so the whole NOT IN is never TRUE and no rows survive. Fix it by filtering NULLs in the subquery or, better, by using NOT EXISTS, which is NULL-safe.

Write a query for the Nth highest salary.

The version I would give, because it handles ties correctly:

SELECT DISTINCT salary FROM (
  SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS r
  FROM employee) t
WHERE r = :n;

If window functions are banned, use the correlated-count form: SELECT DISTINCT salary FROM employee e WHERE :n-1 = (SELECT COUNT(DISTINCT salary) FROM employee x WHERE x.salary > e.salary). The LIMIT 1 OFFSET n-1 form is simplest but reports the Nth row, not the Nth distinct salary, unless you add DISTINCT.

RANK vs DENSE_RANK vs ROW_NUMBER.

ROW_NUMBER always gives a distinct sequential number, breaking ties arbitrarily. RANK gives tied rows the same rank and then skips numbers (1,2,2,4). DENSE_RANK gives tied rows the same rank with no gaps (1,2,2,3). Use ROW_NUMBER for pagination and de-duplication, DENSE_RANK for “Nth distinct value” questions.

What is a view? Can you update through one?

A view is a named stored query that behaves like a virtual table; it holds no data of its own. You can update through it only when each result row maps unambiguously to one base-table row — so no aggregation, no DISTINCT, no GROUP BY, no set operators, generally a single base table, and all NOT NULL columns without defaults must be exposed. Otherwise the update is rejected, or you provide an INSTEAD OF trigger to define the semantics yourself.

View vs materialized view.

A plain view is re-executed on every reference, so it is always current and costs nothing to store. A materialized view stores the computed result on disk and therefore returns instantly, at the cost of staleness and refresh work. Materialized views suit expensive aggregations in reporting workloads where data a few minutes old is acceptable; they can also carry their own indexes.

Stored procedure vs function.

A procedure is invoked with CALL as a standalone statement, can return multiple values via OUT parameters or result sets, and may contain DML and transaction control. A function returns a single value and is invoked inside an expression, so it can appear in SELECT, WHERE or a CHECK constraint; it is usually restricted from side effects. Procedures suit multi-step business operations; functions suit reusable computations.

What is a trigger, and when would you avoid it?

A trigger is procedural code that fires automatically on INSERT/UPDATE/DELETE, either BEFORE or AFTER, at row or statement level. It is ideal for audit trails and invariants that must hold no matter which application writes. I avoid triggers for business logic that changes often, for anything doing heavy work in the write path, and where cascading triggers make behaviour hard to reason about or debug — the logic becomes invisible to the developer reading the application code.

What is a cursor and why is it usually a bad idea?

A cursor lets you fetch and process a result set row by row. It is usually a bad idea because SQL is set-based: a cursor loop performs one round trip and one execution step per row, so it scales linearly where a single set-based statement lets the optimizer choose a bulk strategy. Use one only when the operation genuinely depends on sequential state that cannot be expressed with window functions or recursive CTEs.

CHAR vs VARCHAR.

CHAR(n) is fixed length and pads with spaces, so it wastes space for variable data but avoids row growth on update and is marginally faster for fixed-width codes like country codes. VARCHAR(n) stores only the characters used plus a length prefix. Trailing-space comparison semantics also differ between the two in some engines, which occasionally surprises people.

What does COALESCE do, and how is it different from NVL/ISNULL?

COALESCE(a,b,c) returns the first non-NULL argument and is standard SQL, accepting any number of arguments. NVL (Oracle) and ISNULL (SQL Server) are vendor-specific two-argument equivalents. NULLIF(a,b) is the inverse idea: it returns NULL when the two arguments are equal — handy for avoiding division by zero.

Normalization

Second only to SQL in frequency. Learn the procedure, not just the definitions.

8.1 Why: the three anomalies

Consider one badly designed table:

STUDENT_COURSE(sid, sname, dept, dept_hod, cid, cname, grade)
  • Insertion anomaly — you cannot record a new department until some student joins it, because sid and cid are part of the key and cannot be NULL.
  • Update anomaly — the HOD’s name is repeated in every row of that department; changing it means updating hundreds of rows, and missing one leaves the database inconsistent.
  • Deletion anomaly — deleting the last student of a department erases the department’s existence entirely.

Normalization is the process of decomposing relations to remove redundancy and these anomalies, guided by functional dependencies, while preserving information.

8.2 Functional dependency

X → Y means: whenever two tuples agree on X, they must agree on Y. “X determines Y.” It is a statement about the semantics of the data, not about one instance — you cannot prove an FD from sample data, you can only disprove it.

  • Trivial FD — Y ⊆ X, e.g. {A,B} → A. Always holds.
  • Non-trivial FD — Y ⊄ X.
  • Full functional dependency — Y depends on the whole of X and not on any proper subset.
  • Partial dependency — a non-prime attribute depends on part of a composite candidate key. (Kills 2NF.)
  • Transitive dependency — X → Y and Y → Z, so X → Z where Y is not a candidate key. (Kills 3NF.)
  • Prime attribute — one that is a member of some candidate key. Everything else is non-prime.

Fast way to find candidate keys

Split the attributes into three groups. Attributes that appear only on the right of every FD can never be in a key. Attributes that appear only on the left (or in no FD at all) must be in every key — start your closure with them. Then add attributes from the “both sides” group one at a time and test the closure. This turns an exponential search into a few checks.

3NF vs BCNF — the difference that decides the question

3NF has an escape clause: a dependency X→Y is allowed if Y is prime, even when X is not a super key. BCNF has no escape clause. So every BCNF relation is in 3NF, but not conversely.

R(student, subject, teacher)
  FDs:  (student, subject) → teacher     each student takes a subject from one teacher
        teacher → subject                each teacher teaches exactly one subject
  Candidate keys: (student,subject) and (student,teacher)
  → 3NF?  yes: in "teacher → subject", subject is a prime attribute.
  → BCNF? no:  "teacher" is not a super key.
  Decomposing to BCNF gives  (teacher, subject) and (student, teacher),
  which loses the FD (student,subject) → teacher.
The line that wins marks

A lossless-join, dependency-preserving decomposition into 3NF is always possible. Into BCNF, a lossless decomposition is always possible but dependency preservation is not guaranteed. That is exactly why 3NF still gets used in practice.

8.4 Decomposition properties

Lossless join (non-additive)

A decomposition of R into R1 and R2 is lossless if R1 ∩ R2 → R1 or R1 ∩ R2 → R2, i.e. the common attributes form a super key of at least one of the pieces. Otherwise the natural join of the pieces produces spurious tuples that were never in R.

R(A,B,C)  F = {A→B, B→C}
  D1 = AB, BC → common = B, and B→C so B is a key of BC   ⇒ LOSSLESS ✓
  D2 = AB, AC → common = A, and A→B so A is a key of AB   ⇒ LOSSLESS ✓
  D3 = AC, BC → common = C, and C determines nothing      ⇒ LOSSY ✗ (spurious tuples)

Dependency preservation

The decomposition preserves dependencies if (F1 ∪ F2 ∪ …)+ = F+, meaning every original FD can be checked on a single relation without a join. If it is not preserved, enforcing that constraint needs a join on every update — expensive and often skipped, which lets bad data in.

8.5 Canonical (minimal) cover

The smallest equivalent FD set. Three steps:

  1. Split right sides so every FD has a single attribute on the right (decomposition rule).
  2. Remove extraneous left attributes: for AB → C, if {A}+ already contains C, drop B.
  3. Remove redundant FDs: temporarily delete X→Y and, using the remaining set, compute X+; if it still contains Y, the FD was redundant.
F = { A→BC, B→C, A→B, AB→C }
1. split:      A→B, A→C, B→C, A→B, AB→C
2. left-reduce AB→C: {A}+ = ABC contains C  ⇒ becomes A→C
3. dedupe:     A→B, A→C, B→C
   remove A→C: with {A→B, B→C}, {A}+ = ABC still contains C ⇒ A→C is redundant
Minimal cover: { A→B, B→C }

8.6 4NF, 5NF and denormalization

A multi-valued dependency X ↠ Y exists when, for each X value, the set of Y values is independent of the remaining attributes. Storing two independent multi-valued facts in one table forces a Cartesian product of rows:

EMP(ename, skill, language)   -- skills and languages are independent
 Ravi, Java,   English        4 rows are needed to state 2 skills + 2 languages
 Ravi, Java,   Tamil          Fix: split into EMP_SKILL(ename,skill)
 Ravi, Python, English                     and EMP_LANG(ename,language)  ⇒ 4NF
 Ravi, Python, Tamil

5NF deals with join dependencies: a relation that cannot be losslessly split in two, but can be split in three (a classic supplier–part–project case). It is rare in practice and rarer in interviews — knowing the definition is enough.

Denormalization is the deliberate reintroduction of redundancy for read performance: storing a precomputed order_total, duplicating dept_name into a reporting table, or maintaining a summary table. State the cost honestly — extra write cost and a real risk of inconsistency, which must be managed with triggers, materialized views or scheduled jobs. Denormalize after measuring, never by default.

Interview drill ch. 08

What is normalization and why do we do it?

It is the process of structuring relations to minimise redundancy by decomposing them according to their functional dependencies. The purpose is to eliminate insertion, update and deletion anomalies — for instance, being unable to record a department with no students, or having to update a manager’s name in a thousand rows. The decomposition must be lossless so no information is destroyed.

Explain 1NF, 2NF, 3NF and BCNF with an example.

1NF: atomic values only — a phone_numbers column holding “9xx, 8xx” violates it, so it moves to its own table. 2NF: no partial dependency on a composite key — in ENROL(sid, cid, grade, sname), sname depends only on sid, so it moves to STUDENT. 3NF: no transitive dependency — in STUDENT(sid, dept, hod), sid → dept → hod, so DEPT(dept, hod) is split out. BCNF: every determinant must be a super key, which is stricter than 3NF and matters when candidate keys overlap.

Difference between 3NF and BCNF. Is BCNF always achievable?

3NF permits a dependency X→Y where X is not a super key provided Y is a prime attribute; BCNF removes that exemption entirely. Every BCNF relation is in 3NF but not the reverse. A lossless BCNF decomposition always exists, but it may not preserve all functional dependencies — the (student, subject, teacher) example is the standard counterexample. 3NF, in contrast, can always be achieved losslessly and dependency-preservingly, which is why many production schemas stop at 3NF.

What is a partial dependency? A transitive dependency?

A partial dependency is when a non-prime attribute depends on only part of a composite candidate key — it can only occur when the key has more than one attribute. A transitive dependency is when a non-prime attribute depends on the key only through another non-key attribute: sid → dept and dept → hod, therefore sid → hod indirectly.

Find the candidate keys of R(A,B,C,D) with F = {AB→C, C→D, D→A}.

B appears on no right-hand side, so B is in every candidate key. Test closures: {AB}+ = ABCD ✓, {BC}+ = BC → BCD → ABCD ✓, {BD}+ = BD → BDA → ABCD ✓. So the candidate keys are AB, BC and BD. Prime attributes: A, B, C, D — all of them; non-prime: none. Note this means the relation is automatically in 3NF, though not in BCNF since C and D are not super keys.

How do you check whether a decomposition is lossless?

For a two-way split, compute the intersection of the two attribute sets and check whether it functionally determines all attributes of at least one of the two relations — i.e. the common attributes form a super key of one piece. For an n-way decomposition, use the tableau (chase) method: build a matrix of rows per sub-relation, mark matching symbols, apply the FDs repeatedly, and the decomposition is lossless if some row becomes entirely distinguished symbols.

What is a minimal/canonical cover and why does it matter?

It is the smallest FD set equivalent to the original: single attribute on each right side, no extraneous attributes on the left, and no redundant FDs. It matters because the standard 3NF synthesis algorithm builds one relation per FD in the minimal cover, so a smaller cover yields a cleaner schema, and because it makes constraint checking cheaper.

When would you deliberately denormalize?

When measurement shows a read-heavy query is dominated by joins or repeated aggregation — for example a dashboard recomputing order totals over millions of rows, or a reporting table that must serve a fixed query in milliseconds. I would first try an index or a materialized view, since those keep one source of truth. If I do denormalize, I keep the normalized tables authoritative and maintain the redundant copy through a trigger or a scheduled refresh, and I document that the column is derived.

Can a relation be in 3NF but have redundancy?

Yes. 3NF’s prime-attribute exemption allows a non-super-key determinant to remain, so teacher → subject can repeat the subject on every row for that teacher. That is exactly the redundancy BCNF removes — and the reason the trade-off between BCNF and dependency preservation exists.

Is a relation with only two attributes always in BCNF?

Yes. With attributes A and B, the only possible non-trivial FDs are A→B and B→A, and in either case the determinant is a key of the relation. This is a handy shortcut when checking a decomposition.

9.1 What a transaction is

A transaction is a single logical unit of work — a sequence of read and write operations that must take the database from one consistent state to another. The canonical example is a funds transfer: debit A, credit B. Half of it is worse than none of it.

9.3 Schedules

  • Serial schedule — transactions run one after another with no interleaving. Always correct, but no concurrency, so throughput is poor.
  • Serializable schedule — interleaved, but equivalent to some serial schedule. This is the correctness criterion.
  • Conflicting operations — two operations conflict if they belong to different transactions, access the same data item, and at least one is a write. So: R–W, W–R, W–W conflict; R–R never does.

Conflict serializability and the precedence graph

Build a directed graph with one node per transaction. Draw an edge Ti → Tj whenever an operation of Ti conflicts with a later operation of Tj on the same item. The schedule is conflict serializable if and only if the graph is acyclic; a topological sort then gives an equivalent serial order.

S: R1(A) W2(A) R3(A) W1(B) R2(B)
   R1(A) before W2(A)  ⇒ T1 → T2
   W2(A) before R3(A)  ⇒ T2 → T3
   W1(B) before R2(B)  ⇒ T1 → T2   (already present)
   Graph: T1 → T2 → T3, no cycle ⇒ conflict serializable, order T1, T2, T3

View serializability is weaker and larger: schedules that produce the same reads-from relationships and the same final writes. Every conflict-serializable schedule is view serializable; the converse fails for schedules containing blind writes (a write with no prior read of that item). Testing view serializability is NP-complete, which is why real systems enforce conflict serializability.

Interview drill ch. 09

Explain ACID with a bank transfer example.

Transferring ₹1000 from A to B is one transaction with a debit and a credit. Atomicity means a crash between the two cannot leave money destroyed — the undo log rolls the debit back. Consistency means the invariant “total money is unchanged, no balance goes negative” holds before and after. Isolation means a concurrent balance report never sees the intermediate state where the money has left A but not reached B. Durability means once the commit returns, a power failure cannot undo it, because the log record was forced to stable storage first.

What is a schedule, and what makes one serializable?

A schedule is the chronological interleaving of the operations of several transactions. It is conflict serializable if you can transform it into some serial schedule by swapping only non-conflicting adjacent operations — equivalently, if its precedence graph is acyclic. Two operations conflict when they touch the same item, belong to different transactions, and at least one is a write.

How do you test conflict serializability?

Draw the precedence (serialization) graph: a node per transaction, and an edge Ti→Tj for every conflicting pair where Ti’s operation comes first. If the graph has no cycle, the schedule is conflict serializable and any topological order is an equivalent serial schedule; if there is a cycle, it is not.

Conflict serializable vs view serializable.

View serializability is the broader class: it requires only that each transaction reads the same values, the reads-from relationships match, and the final write on each item is by the same transaction as in some serial schedule. Every conflict-serializable schedule is view serializable; the extra schedules that are view- but not conflict-serializable always contain a blind write. Since checking view serializability is NP-complete, practical systems enforce the conflict version.

What is a dirty read? A phantom read?

A dirty read is reading data written by a transaction that has not committed — if that transaction aborts, you acted on a value that never officially existed. A phantom read is when a transaction re-executes a range query and finds rows that were inserted (or removed) by another committed transaction in the meantime. The distinction that matters: non-repeatable reads concern existing rows changing, phantoms concern the set of qualifying rows changing, so preventing them needs range or predicate locks rather than row locks.

Which isolation level would you choose for a payments system?

For the money-moving path I would use SERIALIZABLE, or READ COMMITTED with explicit SELECT ... FOR UPDATE on the accounts involved, so balance checks and updates are atomic and lost updates are impossible. For reporting and dashboards on the same database, READ COMMITTED or a read replica is fine, since a slightly stale aggregate is harmless. The general principle is to raise isolation only on the code paths whose invariants are actually at risk, because higher isolation costs concurrency.

Recoverable vs cascadeless vs strict schedule.

Recoverable: a transaction commits only after every transaction it read from has committed — so you never have to undo a committed transaction. Cascadeless: transactions read only committed data, so one abort never forces a chain of other rollbacks. Strict: no other transaction may read or write an item until the writer commits or aborts, which makes recovery simple because undo is just restoring the before-image. Strict ⊂ cascadeless ⊂ recoverable.

Can a committed transaction be rolled back?

No — durability forbids it. The only correct remedy is a compensating transaction that performs the logical inverse, for example a refund entry rather than an erasure. Point-in-time recovery from backups can restore the whole database to an earlier state, but that is a database-level operation, not a rollback of one transaction.

Concurrency control

Locks, 2PL, deadlocks, timestamps, MVCC.

10.1 Lock-based protocols

Two lock modes: shared (S) for reading and exclusive (X) for writing.

Requested ↓ / Held →SX
SCompatibleConflict
XConflictConflict

Locking alone is not enough — you must also constrain when locks are released.

Two-phase locking (2PL)

Every transaction has a growing phase (acquires locks, releases none) followed by a shrinking phase (releases locks, acquires none). The point between them is the lock point. 2PL guarantees conflict serializability — but it does not prevent deadlock or cascading rollback.

  • Conservative (static) 2PL — acquire all locks before starting. Deadlock-free, but requires knowing the whole read/write set in advance and reduces concurrency badly.
  • Strict 2PL — hold all exclusive locks until commit/abort. Prevents cascading rollback. This is what most real systems use.
  • Rigorous 2PL — hold all locks (shared and exclusive) until commit. Simplest to reason about; serialization order equals commit order.
Frequently confused

Conservative 2PL is deadlock-free but not cascadeless; strict 2PL is cascadeless but not deadlock-free. Only conservative-strict 2PL is both.

Lock granularity and intention locks

Locks can be taken on a database, file, table, page, row or field. Fine granularity means more concurrency but far more locks to manage (memory and CPU overhead), which can trigger lock escalation to a coarser level. Intention locks (IS, IX, SIX) are placed on ancestors in the hierarchy so that a transaction wanting a table-level X lock can tell instantly that someone holds a row lock underneath, without scanning every row.

10.2 Deadlocks

A deadlock is a cycle of transactions each waiting for a lock held by the next. Four necessary conditions (Coffman): mutual exclusion, hold and wait, no preemption, circular wait.

Prevention using timestamps

SchemeTi requests a lock held by TjCharacter
Wait–Die (non-preemptive)If Ti is older it waits; if younger it dies (aborts and restarts with the same timestamp)Older waits, younger dies
Wound–Wait (preemptive)If Ti is older it wounds Tj (forces Tj to abort); if younger, Ti waitsOlder wounds, younger waits

Both are deadlock-free and starvation-free because the timestamp is retained on restart, so a transaction eventually becomes the oldest. Wound–wait causes fewer rollbacks overall.

Detection and recovery

Maintain a wait-for graph (an edge Ti → Tj means Ti waits for Tj) and run cycle detection periodically. On a cycle, choose a victim to abort, based on how much work it has done, how many items it holds, how many more it needs, and how many times it has already been rolled back — the last factor guards against starvation. Rollback can be total or partial (to a savepoint).

Practical prevention worth mentioning: acquire locks in a consistent global order across all code paths, keep transactions short, and use a lock timeout.

10.3 Timestamp ordering

Every transaction gets a timestamp TS(T) at start; every item X keeps read_TS(X) and write_TS(X). The protocol enforces the serial order of the timestamps:

  • T reads X: if TS(T) < write_TS(X), T is trying to read a value written by a “future” transaction → abort T. Otherwise read and set read_TS(X) = max(read_TS(X), TS(T)).
  • T writes X: if TS(T) < read_TS(X) or TS(T) < write_TS(X) → abort T. Otherwise write and set write_TS(X) = TS(T).
  • Thomas’s write rule: an outdated write (TS(T) < write_TS(X)) that no one has read can simply be ignored rather than causing an abort, since it would be immediately overwritten. This allows some view-serializable but not conflict-serializable schedules.

Timestamp ordering is deadlock-free (nobody ever waits) but can cause many restarts, and basic TO is not recoverable without extra rules.

10.4 Optimistic (validation) concurrency control

Three phases: read (work on a private copy, note read-set and write-set), validate (check for conflicts against transactions that committed meanwhile), write (make changes public). Great when conflicts are rare — read-mostly workloads — and poor when contention is high, because work is discarded late.

10.5 MVCC — how real databases actually do it

Multi-Version Concurrency Control keeps multiple versions of each row. A writer creates a new version instead of overwriting; each reader sees the version consistent with its own snapshot. The headline property: readers never block writers and writers never block readers. Only writer–writer conflicts on the same row need locking.

  • PostgreSQL stores versions in the table itself with xmin/xmax transaction IDs; dead versions are reclaimed by VACUUM.
  • Oracle and MySQL/InnoDB keep old versions in undo/rollback segments and reconstruct them on demand.
  • Cost: version storage, garbage collection, and possible “snapshot too old” errors for very long-running queries.

Interview drill ch. 10

What is two-phase locking? Does it guarantee serializability?

2PL requires each transaction to acquire all its locks in a growing phase and release them in a shrinking phase, never acquiring after the first release. It does guarantee conflict serializability. However, it does not prevent deadlock, and plain 2PL can still cause cascading rollbacks — which is why production systems use strict 2PL, holding exclusive locks until commit.

Strict vs rigorous vs conservative 2PL.

Strict holds exclusive locks until commit, giving cascadeless recovery. Rigorous holds all locks — shared and exclusive — until commit, making the serialization order equal to the commit order. Conservative acquires every lock up front, which is the only variant that is deadlock-free, but it needs the full lock set known in advance and hurts concurrency.

What is a deadlock and how do databases handle it?

A deadlock is a cyclic wait: T1 holds A and wants B while T2 holds B and wants A. Databases handle it in one of three ways. Detection — build a wait-for graph, look for a cycle, and abort a chosen victim; this is what most engines do, since deadlocks are rare. Prevention — timestamp schemes like wait–die and wound–wait, or acquiring locks in a fixed global order. Avoidance by timeout — abort any transaction that waits too long, which is cheap but can kill innocent transactions.

Explain wait–die and wound–wait.

Both compare timestamps, where a smaller timestamp means an older transaction. In wait–die (non-preemptive), if the requester is older it waits, and if younger it aborts itself. In wound–wait (preemptive), if the requester is older it forces the holder to abort, and if younger it waits. Both avoid cycles because waiting is always in one direction of age, and since an aborted transaction keeps its original timestamp on restart, it eventually becomes old enough to proceed — so no starvation.

What is MVCC and why is it popular?

MVCC gives each transaction a consistent snapshot by keeping multiple versions of each row rather than overwriting in place. Readers therefore never block writers and writers never block readers, which massively improves throughput for the read-heavy workloads most applications have, and it gives consistent reads without long read locks. The costs are storage for old versions, background cleanup (VACUUM in PostgreSQL or undo segments elsewhere), and write–write conflicts that must still be resolved by aborting or waiting.

What are intention locks for?

They make multi-granularity locking efficient. Before locking a row, a transaction places an IS or IX lock on the table and database above it. Then a transaction wanting a full-table S or X lock only has to inspect the table-level lock to know whether any incompatible row lock exists, instead of scanning every row. SIX means “shared on the whole table plus intention-exclusive on some rows”.

What is Thomas’s write rule?

In timestamp ordering, if a transaction tries to write an item whose write_TS is already larger — meaning a newer transaction has written it — the write is obsolete. Instead of aborting, the system simply ignores the write, because that value would have been overwritten anyway and no one has read it. This increases concurrency and admits some schedules that are view serializable but not conflict serializable.

Optimistic vs pessimistic concurrency control — when do you pick each?

Pessimistic (locking) assumes conflicts are likely and blocks up front — right for high-contention workloads such as inventory decrements on a popular item. Optimistic assumes conflicts are rare, does the work on a private copy and validates at commit — right for read-mostly workloads and for stateless web applications, where it often appears as a version-number check on update. The trade-off is blocking cost versus wasted work on retry.

Recovery and logging

How the D in ACID is actually delivered.

11.1 Failure types

  • Transaction failure — logical error (constraint violation, bad input) or system-enforced abort (deadlock victim).
  • System crash — power loss or OS crash. Volatile memory is lost, disk survives. This is the case recovery algorithms mainly target.
  • Media failure — the disk itself fails. Needs backups plus archived logs, or replication.

Storage classes: volatile (RAM, lost on crash), non-volatile (disk/SSD, survives crashes but not media failure), stable (an abstraction approximated by replicating across independent devices and sites).

11.2 The log and the write-ahead rule

The log is an append-only sequence of records on stable storage:

<T1, START>
<T1, A, 1000, 900>      -- transaction, item, old value, new value
<T1, B,  500, 600>
<T1, COMMIT>
<CHECKPOINT (T2, T3)>   -- list of transactions active at checkpoint time
Write-Ahead Logging (WAL)

Two rules. (1) The undo (old value) log record must reach stable storage before the corresponding data page is written to disk. (2) All log records of a transaction, including its commit record, must be on stable storage before the transaction is reported committed. Rule 1 makes atomicity possible; rule 2 makes durability possible.

11.4 Checkpoints

Without checkpoints, recovery would have to scan the log from the beginning of time. At a checkpoint the system flushes log records and dirty buffer pages to disk and writes a checkpoint record listing the currently active transactions. On restart, recovery only needs to go back to the last checkpoint. A fuzzy checkpoint avoids freezing the whole system by allowing transactions to continue while pages are flushed in the background.

Log:  ...  <CKPT (T2)>  <T2,COMMIT>  <T3,START> ... <T3,W> ... CRASH
Recovery:  REDO list  = {T2}   (committed after the checkpoint)
           UNDO list  = {T3}   (started but never committed)

11.5 ARIES, in outline

The industry-standard algorithm, built on three principles: write-ahead logging, repeating history during redo, and logging changes made during undo (using compensation log records, so undo work is never repeated after a crash during recovery). Three passes:

  1. Analysis — scan forward from the last checkpoint to rebuild the transaction table and the dirty page table, identifying losers (uncommitted) and winners.
  2. Redo — replay all logged updates from the earliest dirty page LSN, including those of losers, to restore the exact pre-crash state.
  3. Undo — roll back the losers in reverse order, writing CLRs as it goes.

Each page stores the LSN (log sequence number) of the last change applied to it, which makes redo idempotent: if the page LSN is already ≥ the record’s LSN, skip it.

11.6 Shadow paging

An alternative with no log: keep a shadow page table pointing to the old versions; updates write to new pages and modify only the current page table. Commit atomically swaps the pointer to the page table. Advantage: no undo/redo needed. Disadvantages: data fragmentation, expensive garbage collection, and it is hard to make work with concurrent transactions — which is why WAL won.

Interview drill ch. 11

What is write-ahead logging and why is it necessary?

WAL requires that a change be recorded in the log on stable storage before the modified data page is written to disk, and that all log records including the commit record are flushed before a commit is acknowledged. It is necessary because the buffer manager may write a dirty page at any time: without the undo record on disk first, a crash could leave uncommitted changes in the data file with no way to reverse them, breaking atomicity. The second rule is what makes durability true even though the data pages themselves may still be in memory at commit time.

What happens during crash recovery?

The system reads the log backwards to the last checkpoint and classifies transactions: those with both START and COMMIT go on the redo list; those with START but no COMMIT go on the undo list. It then redoes the committed transactions’ writes to restore their effects, and undoes the uncommitted ones by restoring before-images. In ARIES the redo pass deliberately repeats history for all transactions first, and undo happens afterwards with compensation log records so that a second crash during recovery is safe.

Why do we need checkpoints?

To bound recovery time. Without them, restart would require scanning the entire log from the beginning. A checkpoint flushes dirty pages and records which transactions were active, so recovery can start there instead. The trade-off is that frequent checkpoints cost I/O during normal operation, so systems use fuzzy checkpoints that do not stall running transactions.

Deferred vs immediate database modification.

Deferred update writes changes to disk only after commit, so recovery needs redo only and the log can store just new values. Immediate update allows dirty pages to reach disk before commit, so the log must store old values too and recovery needs both undo and redo. Immediate update is what real systems do, because deferring everything would require the buffer pool to hold an entire transaction’s changes.

What is shadow paging and why is it rarely used?

Shadow paging keeps two page tables — current and shadow — and commits by atomically switching the pointer, so no log is needed. It is rarely used because it fragments data badly as pages are relocated on every write, it needs garbage collection of old pages, and it does not adapt well to many concurrent transactions, which each would need their own consistent page-table view.

Where “why is my query slow?” gets answered. B+ trees are near-certain to come up.

12.1 The memory hierarchy, and why it decides everything

Registers → cache → RAM → SSD → disk → tape. Each step down is roughly 10–100× slower and larger. A single random disk seek costs about as much as executing millions of CPU instructions, so database performance analysis counts disk block accesses, not CPU operations. Everything in this chapter follows from that one fact.

Data is transferred in fixed-size blocks/pages (typically 4–16 KB). The blocking factor is how many records fit in a block; the cost of a full scan is (number of records ÷ blocking factor) block reads.

Both are self-balancing, always height-balanced, and grow upward from the leaves by splitting a full node and pushing the middle key up. Deletion may borrow from a sibling or merge. 12.5 Hash indexes

  • Static hashing — fixed number of buckets. Simple, but overflow chains degrade performance as the file grows.
  • Extendible hashing — a directory of 2d pointers using the first d bits of the hash. On overflow, only the affected bucket splits and, if needed, the directory doubles. No full rehash.
  • Linear hashing — buckets split in a fixed round-robin order when a load threshold is crossed; no directory needed.

Hash indexes serve equality in O(1) but cannot do range queries, ordering, or leftmost-prefix matching — which is why B+ trees remain the default.

12.6 Other index types worth naming

  • Bitmap index — one bit vector per distinct value. Superb for low-cardinality columns (gender, status) in read-heavy warehouses, and combines with AND/OR at bit speed. Terrible for OLTP because a single row update locks a whole vector.
  • Full-text / inverted index — maps each term to the documents containing it.
  • Spatial (R-tree) — bounding-box hierarchy for geographic queries.
  • Partial / filtered index — indexes only rows matching a predicate: CREATE INDEX ... WHERE status = 'ACTIVE'. Small and highly effective.
  • Function-based index — indexes LOWER(email) so that a case-insensitive lookup can still use an index.
  • LSM tree — write-optimised structure (buffer in memory, flush sorted runs, compact in background) used by Cassandra, RocksDB and friends: faster writes, higher read amplification.

12.7 When an index will not be used

Being able to list these is the difference between memorising and understanding.

  • The column is wrapped in a function or arithmetic: WHERE YEAR(hire_date) = 2024 — rewrite as a range on hire_date.
  • A leading wildcard: LIKE '%son'. LIKE 'son%' can use the index.
  • Implicit type conversion between the column and the literal.
  • Low selectivity — if a predicate matches a large fraction of the table, a sequential scan is genuinely cheaper than random lookups, and the optimizer knows it.
  • A composite index used without its leftmost prefix: an index on (a, b, c) helps queries filtering on a, or a,b, or a,b,c, but not on b alone.
  • OR across columns that lack a common index, and IS NULL in engines that do not index NULLs.
  • Stale statistics, which make the optimizer misjudge cardinality.

Interview drill ch. 12

What is an index? What are its costs?

An index is a separate data structure of search-key values and pointers that lets the engine locate rows without scanning the whole table, turning O(n) into roughly O(log n). The costs are real: additional disk space, slower INSERT/UPDATE/DELETE because every index must be maintained, more memory pressure in the buffer pool, and longer maintenance operations. So you index the columns that actually appear in WHERE, JOIN and ORDER BY clauses of frequent queries, and you drop indexes nothing uses.

Why do databases use B+ trees rather than binary search trees or hash tables?

Because the unit of I/O is a disk page, not a value. A binary tree has fan-out 2, so it needs about log₂(n) reads — around 30 for a billion rows. A B+ tree node fills an entire page, giving a fan-out of hundreds, so the same billion rows are 3–4 levels deep and the upper levels stay cached, meaning one or two physical reads. Hash tables give O(1) equality but cannot serve range scans, ORDER BY, or prefix matching, and they degrade with collisions. B+ trees also keep the leaves in a linked list, which makes range queries a sequential walk.

B tree vs B+ tree.

In a B tree, data pointers can be in internal nodes as well as leaves; in a B+ tree, all data pointers are in the leaves and internal nodes hold only keys, which raises the fan-out and lowers the height. B+ tree leaves are chained, so range queries need one descent and then a sequential scan, whereas a B tree must traverse repeatedly. B+ tree search cost is uniform — always the height — which makes performance predictable. Practically every relational engine uses B+ trees.

Clustered vs non-clustered index.

A clustered index determines the physical ordering of rows, so the leaf level is the table; you get at most one per table and range scans on it are sequential. A non-clustered index is a separate structure pointing at rows, so you can have many, but retrieving columns not in the index costs an extra lookup per row. In InnoDB the primary key is the clustered index and secondary indexes store the primary key value as the pointer — which is a good argument for keeping the primary key narrow.

Dense vs sparse index.

A dense index has an entry for every search-key value in the file; a sparse index has one entry per block. Sparse indexes are smaller and therefore faster to search at the top level, but they require the data file to be sorted on that key, so a secondary index must be dense. Multi-level indexes typically make the lowest level dense and the levels above sparse.

My query is slow. Walk me through what you would do.

First, look at the actual plan with EXPLAIN ANALYZE and find where the time and the row estimates go wrong. Typical findings and fixes: a sequential scan on a selective predicate → add or fix an index; a huge mismatch between estimated and actual rows → refresh statistics; a nested loop over a large outer input → often a missing index on the join column; a sort or hash spilling to disk → raise work memory or add a supporting index. Then check for anti-patterns in the SQL itself — a function wrapped around an indexed column, a leading-wildcard LIKE, SELECT * pulling columns that prevent an index-only scan, or an OR that could be a UNION ALL. Only after that would I consider denormalization, caching or a materialized view.

You have an index on (a, b, c). Which queries can use it?

The leftmost-prefix rule applies. It helps WHERE a=?, WHERE a=? AND b=?, and WHERE a=? AND b=? AND c=?, and it can also serve a=? AND b>? — though once a range is used on b, the c part can only be a filter, not a seek. It does not serve WHERE b=? or WHERE c=? alone, because the index is sorted by a first. It can also satisfy ORDER BY a, b without a sort.

When is a bitmap index better than a B+ tree?

On low-cardinality columns in a read-mostly analytical workload — status flags, gender, region — where multiple such predicates get combined. Bitmaps compress extremely well and can AND/OR several conditions with bitwise operations before touching any row. They are a poor choice for OLTP because updating a single row means rewriting a bit vector that covers many rows, causing severe contention.

Does an index always speed up a query?

No. If the predicate matches a large share of the table, using the index means many random accesses plus reading the index itself, which is slower than one sequential scan — so the optimizer will correctly ignore it. Indexes also slow down every write, and an unusable index (function-wrapped column, leading wildcard, type mismatch, wrong prefix) costs storage and maintenance for no benefit.

13.2 Heuristic (rule-based) optimization

Transformations that are almost always good, applied to the algebra tree:

  1. Push selections down — filter as early as possible, so later operators see fewer tuples. The single biggest win.
  2. Push projections down — drop unneeded columns early to shrink each tuple.
  3. Convert Cartesian product + selection into a join.
  4. Perform the most restrictive selections and joins first, so intermediate results stay small.
  5. Combine sequences of selections and projections; eliminate duplicate computation and common sub-expressions.

13.3 Cost-based optimization

The optimizer enumerates candidate plans and estimates each one’s cost from statistics kept in the catalog: number of rows, number of blocks, distinct values per column, histograms of value distribution, index heights and clustering factors. The dominant cost term is disk I/O. Selectivity — the fraction of rows a predicate keeps — drives everything; an equality predicate on a column with V distinct values is estimated at 1/V under a uniformity assumption, which is exactly why histograms matter for skewed data.

Join-order search is the expensive part: n tables have a factorial number of orderings, so optimizers use dynamic programming (System-R style, considering left-deep trees) or, above a threshold, genetic/heuristic search.

Interview drill ch. 13

What are the steps in processing a query?

Parsing and syntax checking, semantic validation against the catalog, translation into relational algebra, optimization — both heuristic rewriting and cost-based plan selection using statistics — code generation into physical operators, and finally execution, which pulls pages through the buffer manager and returns rows.

Rule-based vs cost-based optimization.

Rule-based applies fixed transformations and a static ranking of access paths without looking at the data — cheap, predictable, but blind to data distribution. Cost-based estimates the I/O and CPU cost of many candidate plans using catalog statistics such as row counts, distinct values and histograms, and picks the cheapest. Modern optimizers do both: heuristics first to prune obviously bad forms, then cost-based search over the rest.

Why push selections down the query tree?

Because every operator above it then processes fewer tuples, and intermediate results are what cost memory and I/O. Filtering before a join can turn a million-row intermediate result into a few thousand, which changes the join algorithm the optimizer picks as well. It is the highest-value algebraic transformation.

Explain hash join vs sort-merge join vs nested loop join.

Nested loop compares every pair, so it is only viable when one side is small or, in its index variant, when the inner side has an index on the join column — that is the standard OLTP plan for a selective lookup. Sort-merge sorts both inputs and merges them once, so it is attractive when the inputs are already sorted or the query needs sorted output, and it handles inequality joins. Hash join builds a hash table on the smaller input and probes with the larger; it is usually the fastest for large unsorted equi-joins, which is why analytics workloads lean on it, but it needs memory and only works for equality.

What are database statistics and why do they go stale?

They are catalog-stored summaries — row counts, block counts, distinct-value counts, histograms, index clustering — used to estimate selectivity and cardinality. They go stale after bulk loads or heavy modification, because they are refreshed by an explicit or background ANALYZE rather than on every write. Stale statistics are one of the most common causes of a plan that was fast yesterday and slow today.

14.2 CAP theorem

In a distributed data store you can guarantee at most two of: Consistency (every read sees the latest write), Availability (every request gets a non-error response), Partition tolerance (the system keeps working despite dropped messages between nodes).

The nuance that impresses

Network partitions are not optional in a real distributed system — they will happen — so P is mandatory and the actual choice is C or A during a partition. That is why “CP vs AP” is the real classification and “CA” systems are essentially single-node. The refinement is PACELC: if there is a Partition, choose A or C; Else (normal operation), choose Latency or Consistency.

14.3 ACID vs BASE

BASE = Basically Available, Soft state, Eventually consistent. It accepts temporary inconsistency in exchange for availability and horizontal scale. Eventual consistency means that if writes stop, all replicas converge — useful for a “likes” counter, unacceptable for an account balance.

14.5 Scaling techniques

  • Vertical scaling — a bigger machine. Simple, no code change, but bounded and expensive at the top end.
  • Replication — copies of the data on several nodes. Primary–replica for read scale-out and failover, multi-primary for write availability at the price of conflict resolution. Replication is synchronous (safe, slower commits) or asynchronous (fast, risks losing the tail on failover, and replicas serve stale reads).
  • Partitioning within one server — horizontal splits rows (by range, list or hash), vertical splits columns into separate tables. Improves manageability and lets the optimizer prune whole partitions.
  • Sharding — horizontal partitioning across independent machines, each holding a disjoint subset. Gives write scale-out, but cross-shard joins and transactions become hard, and a bad shard key creates hotspots. Choosing the shard key is the entire design decision.
  • Caching — Redis/Memcached in front of the database; the hard part is invalidation.
  • Two-phase commit (2PC) — a coordinator asks all participants to prepare, and commits only if all vote yes. It gives atomicity across nodes but blocks if the coordinator fails after the prepare phase, which is why distributed systems often prefer sagas (a sequence of local transactions with compensating actions).

Interview drill ch. 14

Explain the CAP theorem.

In a distributed store you cannot simultaneously guarantee consistency, availability and partition tolerance. Since partitions are a fact of networks, the real decision is what to do during a partition: a CP system such as HBase refuses requests to stay consistent; an AP system such as Cassandra keeps answering and reconciles later. PACELC extends this: even without a partition, you still trade latency against consistency, which is why many systems offer tunable consistency per query.

SQL or NoSQL — how would you choose for a new product?

I would start from the access patterns and the invariants. If the data has rich relationships, the queries are ad-hoc, and correctness matters — payments, inventory, bookings — I would choose a relational database, because joins and multi-row ACID transactions are exactly what it is for. I would choose NoSQL when the access pattern is known and narrow and the volume is very large: a key–value store for sessions, a wide-column store for time-series telemetry, a graph database when traversals dominate. In practice the default is PostgreSQL — it also handles JSON documents well — and I would introduce a specialised store only for a component that demonstrably needs it.

Sharding vs partitioning vs replication.

Partitioning splits one table into pieces, usually within one server, for manageability and partition pruning. Sharding is partitioning across separate machines, so it adds write throughput and capacity but makes cross-shard joins and transactions expensive. Replication copies the same data to multiple nodes for read scale-out and high availability, not for write capacity. They are complementary: production systems typically shard for capacity and replicate each shard for availability.

What is eventual consistency and when is it acceptable?

It means replicas may temporarily disagree, but converge once writes stop. It is acceptable when a slightly stale read causes no harm — view counts, recommendations, social feeds, search indexes. It is not acceptable where a read drives a decision that must be correct at that instant: account balance checks, seat or stock reservations, authorisation. A common design is strong consistency on the write path and eventual consistency for derived read models.

Star schema vs snowflake schema.

Both organise a warehouse around a fact table of measures with dimension tables around it. In a star, dimensions are denormalized into single flat tables — fewer joins, simpler and faster queries, at the cost of redundancy. In a snowflake, dimensions are normalized into hierarchies, saving space and easing dimension updates but requiring more joins. Star is the usual default for query performance.

What is two-phase commit?

A protocol for atomic commit across several nodes. In the prepare phase the coordinator asks every participant whether it can commit and each durably logs its vote; in the commit phase, if all voted yes the coordinator tells everyone to commit, otherwise to abort. Its weakness is blocking: if the coordinator fails after participants have voted yes, they hold locks until it recovers. Three-phase commit reduces that risk, and many modern systems avoid distributed transactions altogether using sagas with compensating actions.

Security and practical database work

Short, but SQL injection is a near-guaranteed question.

15.1 Privileges

Follow least privilege: the application account should not own the schema and should not have DDL rights. Use views to expose subsets, and row-level security policies where the engine supports them.

15.2 SQL injection

-- vulnerable: the input becomes part of the statement text
query = "SELECT * FROM users WHERE name = '" + input + "'"
input =  ' OR '1'='1        →  always true, dumps the table
input =  '; DROP TABLE users; --   →  statement stacking
-- safe: the driver sends SQL and data separately, so input can never become code
PREPARE stmt FROM 'SELECT * FROM users WHERE name = ?';
-- application side (Python)

Defence in depth: parameterised queries first, then least-privilege accounts, input validation and allow-lists for identifiers you cannot parameterise (table and column names), stored procedures where appropriate, WAF and monitoring, and generic error messages so the schema is not leaked.

15.3 Backups, keys and the rest

  • Backup types — full, incremental (changes since the last backup of any type), differential (changes since the last full). Physical copies files; logical exports statements (mysqldump, pg_dump). Point-in-time recovery = last full backup + archived WAL replayed to a chosen instant.
  • RPO / RTO — how much data you can afford to lose, and how long you can afford to be down. These two numbers dictate the backup and replication design.
  • Encryption — in transit (TLS) and at rest (transparent data encryption or filesystem-level), plus column-level encryption or hashing for secrets. Passwords are never encrypted — they are hashed with a slow salted algorithm such as bcrypt or Argon2.
  • Auditing — who read or changed what, usually via triggers or the engine’s audit log.
  • Connection pooling — reusing a fixed set of connections, since each one costs memory and setup time on the server.

Interview drill ch. 15

What is SQL injection and how do you prevent it?

It is an attack where user input is concatenated into a SQL statement, so the input is interpreted as code — allowing an attacker to bypass authentication, read arbitrary tables or destroy data. The real fix is parameterised queries / prepared statements, because they send the statement and the parameter values over separate channels, so a value can never change the parsed structure. Escaping is fragile by comparison. I would add least-privilege database accounts, validation and allow-lists for identifiers that cannot be bound, and generic error messages so failures do not leak schema details.

How should passwords be stored in a database?

Never in plaintext and never with reversible encryption. Store a salted hash from a deliberately slow, memory-hard algorithm such as bcrypt, scrypt or Argon2, with a unique random salt per user so identical passwords produce different hashes and rainbow tables are useless. Plain SHA-256 is unsuitable precisely because it is fast. Verification hashes the supplied password with the stored salt and compares in constant time.

Difference between GRANT and REVOKE, and what does WITH GRANT OPTION do?

GRANT gives a privilege to a user or role; REVOKE takes it away. WITH GRANT OPTION additionally lets the recipient pass that privilege on to others, which means revoking it can cascade to everyone who received it downstream. Because of that cascade, production systems usually grant privileges to roles rather than individuals and avoid the grant option.

Full, incremental and differential backups.

A full backup copies everything. An incremental copies only what changed since the previous backup of any kind — smallest to take, but restore needs the full plus every increment in order. A differential copies everything changed since the last full backup — larger each day, but restore needs only the full plus the latest differential. The choice is a trade between backup window and restore time, driven by your RTO.

Say what you do know, name the concept it is nearest to, and reason out loud towards the answer. “I have not used partitioned tables directly, but the idea is the same as sharding within one server — the optimizer prunes partitions that cannot match the predicate, so the win depends on the partition key matching the query filter.” That answer scores far better than silence, and far better than a confident wrong one.

Interview drill mixed & behavioural

You are designing the database for a ride-hailing app. Walk me through it.

Core entities: RIDER, DRIVER, VEHICLE, TRIP, PAYMENT, LOCATION_PING, RATING. TRIP references rider, driver and vehicle with a status enum, timestamps and pickup/drop coordinates. Design points I would raise: trips are append-heavy and queried by rider, by driver and by time, so I would index (rider_id, requested_at) and (driver_id, requested_at), and partition trips by month. Location pings are extremely high volume and low value individually — they do not belong in the transactional store; I would stream them to a time-series or wide-column store. Money movement stays in a relational database with a serializable path so a trip is never double-charged. Driver availability and matching is a hot-key problem best served by an in-memory geospatial index rather than a table scan.

What happens, step by step, when you run a SELECT?

The client sends the text over a connection; the parser checks syntax and builds a tree; the semantic analyser resolves table and column names against the catalog and checks privileges; the query is translated into relational algebra; the optimizer rewrites it heuristically and then chooses a physical plan by cost, using statistics; the executor runs the plan’s operators, requesting pages from the buffer manager, which reads from disk on a miss; concurrency control provides a consistent view through locks or a snapshot; and rows are streamed back to the client.

How would you find and fix a table that has grown too large?

First measure: row count, size on disk, index sizes, and which queries actually touch it. Then in order of cheapness — archive or delete data nobody queries; add or correct indexes so the hot queries stop scanning; partition by time so old partitions are pruned or detached; move cold data to a separate archive table or store; and only then consider sharding. I would also check for data-model issues that inflate size, like storing large blobs in the row instead of object storage, or storing derived data that can be recomputed.

Where do you see the limits of relational databases?

Three places. Write throughput beyond a single primary, which is where sharding or a distributed SQL engine becomes necessary. Deeply recursive graph traversal, where each hop is a join and a native graph store wins. And genuinely schemaless or rapidly changing document shapes, though JSONB columns cover much of that case now. I would also note that the relational model is a poor fit for very high-volume append-only telemetry, where a time-series or columnar store is designed for exactly that pattern.
