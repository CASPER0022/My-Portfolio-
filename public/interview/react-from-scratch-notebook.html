§00 The JavaScript you must know first

90% of "I don't understand React" is actually "I don't understand modern JavaScript".

React is not a language. It is a JavaScript library, and every confusing line of React code is really a piece of ordinary JavaScript wearing a costume. This section is short, but skipping it is the single most common reason people stay stuck.

Arrow functions

Three ways to write the same function. React code uses the third form constantly.

Destructuring

Pulling values out of objects and arrays by name or position. This is how props and hooks are read.

The one to memorise

const [count, setCount] = useState(0) is not special syntax. useState returns a two-element array, and you are destructuring it. You could write const state = useState(0); const count = state[0]; and it would work identically.

Spread and rest

The ... operator. It copies things (spread) or collects things (rest). React state updates depend on this because you must never mutate state directly.

Shallow copy warning

Spread copies one level deep. {...user} gives you a new outer object, but user.address inside it is still the same object reference. Nested updates need nested spreads — this bites people constantly in section 07.

Array methods that render UI

map is the single most used method in React. It turns an array of data into an array of elements.

Ternary and short-circuit

You cannot write if statements inside JSX. These two operators are how conditions get expressed instead.

Modules, promises, async/await

Interview questions — JavaScript foundations

What is the difference between == and ===?

== compares after type coercion, so "1" == 1 is true. === compares value and type with no coercion, so "1" === 1 is false. Always use === unless you are deliberately checking for "null or undefined", where x == null is a known idiom.

Explain shallow vs deep copy.

A shallow copy duplicates the top level only; nested objects are shared references between the original and the copy. {...obj} and Object.assign({}, obj) are shallow. A deep copy duplicates every level, so nothing is shared — structuredClone(obj) does this natively in modern browsers. React only needs a new reference at the levels you actually changed, so targeted shallow copies are the normal approach and deep cloning is usually wasteful.

What does Array.prototype.map return, and how is it different from forEach?

map returns a new array of the same length containing the return value of the callback for each element. forEach returns undefined and exists only for side effects. React needs a returned array of elements, so map is used and forEach would render nothing.

Why does || sometimes cause bugs where ?? does not?

|| falls back on any falsy value, which includes 0, "", false and NaN. So count || 10 turns a legitimate 0 into 10. ?? only falls back on null and undefined, so count ?? 10 preserves 0. Use ?? for defaults on numbers, booleans and strings.

What is a closure, and where does React use it?

A closure is a function that keeps access to the variables of the scope it was created in, even after that scope has finished executing. In React, every render creates fresh variables, and any event handler or effect callback defined in that render closes over that render's values. This is why a setTimeout inside a component can log a stale count — it captured the count from the render in which it was created. The fix is the functional updater form, covered in section 07.

What is the difference between let, const and var?

var is function-scoped and hoisted as undefined, which causes surprising bugs in loops. let and const are block-scoped and sit in a temporal dead zone until declared, so using them early throws instead of silently returning undefined. const prevents reassignment of the binding, but does not freeze the object — you can still push to a const array. Default to const, use let when you must reassign, never use var.

§01 What React actually is

A rendering engine that runs a pure function every time your data changes.

Before React, updating a page meant reaching into the document and editing it by hand: find the element, change its text, add a class, remove a row. That is imperative — you describe the steps.

React is declarative — you describe the result. You write a function that takes data and returns "what the screen should look like right now". React figures out the steps.

Imperative — you patch the DOM
Declarative — you describe the output

Notice what disappeared on the right: there is no code that removes the class. You never describe transitions, only states. That is the whole philosophy, and it is why React scales to large UIs where the number of possible transitions explodes.

If you think in hardware

The mapping is surprisingly clean and it is worth holding onto:

  • A component is a module. It has a name, an interface, and an implementation.
  • Props are input ports. Driven from outside, read-only inside — exactly like an input in Verilog. Writing to a prop is as illegal as driving an input port from inside a module.
  • State is a register. It holds a value across renders, and it only changes when you clock it (call the setter).
  • A re-render is a clock edge. React re-evaluates the combinational logic (your component function) with the new register values.
  • The virtual DOM diff is the synthesis step that works out the minimal set of physical changes to apply.

The core loop

Everything React does is this cycle, repeated:

Render trace — one click on "+1"
  1. Initial render. React calls Counter(). count = 0. Returns a description of a div containing a button and "0".
  2. React commits that description to the real DOM. The browser paints.
  3. User clicks. Your onClick runs setCount(1).
  4. React marks the component dirty and schedules a re-render. Nothing is on screen yet.
  5. React calls Counter() again, from the top. count = 1 this time. New description returned.
  6. React diffs new description against old. Only the text node changed.
  7. React updates exactly that one text node. Button untouched, div untouched.
The mental model that unlocks everything

Your component function runs many times — once per render. It is not a constructor that runs once and sets up listeners. Every render creates brand new variables, brand new functions, brand new JSX. The only things that survive between renders are the things React stores for you: state and refs.

Library, not framework

React handles one job: turning state into UI. It does not ship a router, a data-fetching layer, a form library or a build tool. You assemble those. That is why "learning React" in practice means React plus Vite plus React Router plus whatever else the job needs.

Exercise 01 — no code, just thinking

A component shows a list of 200 rows. You change the text of row 57 in state. How many DOM elements does React update, and why does that matter for performance compared to re-rendering the HTML string for the whole table?

Show answer

React re-runs your component function and produces a new description of all 200 rows — that part is cheap, because elements are just objects. Diffing then finds that 199 rows are identical and only one text node differs, so it touches one DOM node.

This matters because DOM writes are expensive: they trigger style recalculation, layout and paint. Regenerating the table's innerHTML would destroy and rebuild 200 rows, losing focus, scroll position and any input state along the way. React's diff is the reason a declarative API does not cost you performance.

Interview questions — fundamentals

Is React a library or a framework, and why does the distinction matter?

React is a library focused on the view layer. A framework like Angular prescribes routing, HTTP, forms and dependency injection; React deliberately does not, so teams pick their own router, state manager and data layer. The trade-off is flexibility versus decision fatigue — it is why two React codebases can look completely different, and why job descriptions list React plus four other tools.

What is the virtual DOM and is it faster than the real DOM?

The virtual DOM is a lightweight JavaScript representation of the UI tree. React builds a new one each render and diffs it against the previous one to compute the minimum set of real DOM mutations.

It is not inherently faster than hand-written DOM code — a perfectly targeted textContent assignment always beats a diff. What it buys you is that you get near-optimal updates automatically, from declarative code, without tracking transitions yourself. The honest framing in an interview: the virtual DOM optimises for developer predictability, and its performance is good enough that hand-optimising is rarely worth it.

Explain reconciliation and the two assumptions React's diffing algorithm makes.

Reconciliation is the process of comparing the new element tree with the previous one to decide what to create, update or remove. A fully general tree-diff is O(n³), so React uses heuristics that get it to O(n) based on two assumptions:

  1. Two elements of different types produce different trees — so if a <div> becomes a <span>, React tears down the whole subtree and rebuilds rather than trying to match children.
  2. The developer can hint which children are stable across renders using the key prop — which is why keys matter so much in lists.
What is the difference between an element and a component?

A component is a function (a blueprint). An element is the object that function returns (an instance of a description). Button is a component; <Button color="red" /> evaluates to an element, roughly { type: Button, props: { color: "red" } }. Elements are immutable and disposable — React creates a whole new set every render.

What does "declarative UI" mean in practice?

You write a pure mapping from state to markup, and never write the transition between two UI states. Instead of "when the error clears, remove the red border and delete the message node", you write "if there is an error, render a red border and a message". The number of states you must handle grows linearly, whereas the number of transitions in imperative code grows quadratically — that is the actual engineering argument for it.

Why is React said to have "one-way data flow"?

Data moves from parent to child through props, and only downward. A child cannot write to a prop. If a child needs to change something, the parent passes down a callback function and the child calls it, so the write still happens where the state lives. This makes it possible to answer "who changed this value?" by reading upward from the component, which is the main maintainability win over two-way binding.

Interview questions — tooling

Why Vite instead of Create React App?

CRA is deprecated and no longer recommended. Vite serves source over native ES modules in development, so there is no bundling step on startup and cold start is near-instant regardless of project size, with dependency pre-bundling handled by esbuild. For production it bundles with Rollup. CRA rebuilt the whole bundle with Webpack on every change, which got painfully slow past a few hundred modules.

What is the difference between react and react-dom?

react is the renderer-agnostic core: it defines components, elements, hooks and the reconciler's public API. react-dom is the browser renderer that turns reconciler output into DOM operations. Splitting them lets the same component code run under react-native, react-three-fiber or a test renderer.

What does StrictMode do, and would you keep it on in production?

It is a development-only wrapper that double-invokes render functions, state initialisers and effects to surface impure components and missing effect cleanups, and warns about deprecated APIs. It renders no DOM of its own. In a production build the double invocation is stripped entirely, so the question of "keeping it on" is really about development — and you should, because the bugs it surfaces are real bugs that show up later under concurrent rendering.

Why is there only one HTML file?

Because this is a single-page application. The server returns one shell document, and JavaScript swaps the content for every "page". Navigation is handled client-side by a router updating the URL through the History API, with no full document reload. The trade-off is a heavier initial JavaScript payload and worse crawlability, which is what server-side rendering and Next.js exist to solve.

Interview questions — JSX

What is JSX and does the browser understand it?

JSX is an XML-like syntax extension to JavaScript. Browsers do not understand it. A compiler — Babel, or esbuild/SWC inside Vite — transforms each element into a call to the JSX runtime, which returns a plain object describing the element. Since React 17 the compiler imports jsx from react/jsx-runtime automatically, which is why modern files no longer need import React from "react".

Why must a component return a single root element?

Because the JSX compiles to a function call, and a JavaScript function returns exactly one value. Two sibling roots would be two return values, which is not expressible. Fragments solve it by providing a wrapper element type that React renders as nothing, so you get one return value without an extra DOM node breaking your flex or grid layout.

What is the difference between <></> and <React.Fragment>?

They are the same thing, but the short syntax cannot take props. Since key is a prop, any fragment produced inside a map must use the long form: <Fragment key={id}>.

Why does {items.length && <List />} sometimes print a zero?

&& returns its left operand when that operand is falsy. If items.length is 0, the expression evaluates to the number 0, and React renders numbers as text — unlike false, null and undefined, which render nothing. Fix by coercing to a boolean: items.length > 0 && ... or Boolean(items.length) && ....

Is JSX mandatory?

No. You can call createElement directly, and a few codebases do for dynamic tag generation. JSX is preferred because nested createElement calls become unreadable past two levels, and because tooling — formatters, linters, editor autocomplete — understands the tag form far better.

How do you render raw HTML from a string, and what is the risk?

Using dangerouslySetInnerHTML={{ __html: str }}. The verbose, deliberately ugly name is a warning: it bypasses React's automatic escaping and opens a cross-site scripting hole if the string contains anything user-supplied. Sanitise with something like DOMPurify first, or avoid it entirely.

§04 Components and props

Input ports, read-only, driven from outside.

A component is a function whose name starts with a capital letter and which returns JSX. That is the entire definition.

Passing every kind of value

The most common props bug

onClick={handleSave} passes the function. onClick={handleSave()} calls it during render and passes the return value — usually undefined. If you need to pass an argument, wrap it: onClick={() => handleSave(id)}.

children — the special prop

Anything you put between a component's opening and closing tags arrives as props.children. This is how you build layout components that do not know what they wrap.

Hardware analogy

children is a generic port: the parent decides what gets wired in, and the wrapper does not need to know the type. It is how you write a Modal once and reuse it for a login form, a confirm dialog and an image viewer, without if statements inside the modal.

Props are read-only. Non-negotiable.

React's contract is that a component is a pure function of its props and state. Same inputs, same output, no side effects during render. Break that and you get bugs that only appear under StrictMode, concurrent rendering or memoisation — the hardest category to debug.

Spreading props

Use this deliberately. Blindly spreading {...props} onto a DOM node makes it impossible to see what the element receives and can leak invalid attributes into the HTML.

Interview questions — components and props

What are props and why are they immutable?

Props are the arguments passed into a component by its parent, delivered as a single object. They are immutable because React's model depends on components being pure functions of their inputs — if a child could rewrite its props, the parent's state and the rendered output would silently diverge, and React's ability to skip or replay renders would break. Changes flow back up through callbacks instead.

What is props.children and when would you reach for it?

It is whatever sits between a component's tags, passed automatically as a prop. You reach for it whenever a component provides structure or behaviour but should not dictate content — layouts, cards, modals, providers, error boundaries. It is the primary tool for composition, and it is often the correct answer to "how do I avoid prop drilling?" because passing a subtree down as children means the intermediate component never needs to know about the data at all.

Class components vs function components — what should you use in 2026?

Function components with hooks, always, for new code. Class components are still supported but receive no new features; hooks cannot be used in them, and lifecycle methods split related logic across componentDidMount, componentDidUpdate and componentWillUnmount, which hooks keep together. The one thing classes could still do that hooks could not was error boundaries — and React 19 added onCaughtError / onUncaughtError root options, though the class boundary remains the common pattern. Know classes well enough to read legacy code and to answer this question.

How do you give a prop a default value?

Destructuring defaults in the parameter list: function X({ size = "md" }). The old Component.defaultProps API is removed for function components in React 19. Note the default fires on undefined only, not on null.

What is prop drilling and what are the ways out?

Prop drilling is passing a value through components that do not use it, only to reach a deep descendant. Three escapes, in the order you should consider them: restructure with children so the data-owning parent renders the consumer directly; use Context for genuinely global, rarely-changing values like theme or auth; use an external store like Zustand or Redux Toolkit for large, frequently-updating shared state. Reaching for Context first is a common mistake — composition solves more cases than people expect.

§05 Conditions, lists, keys

Rendering the variable parts of a UI — and the one prop everyone gets wrong.

Four ways to render conditionally

Rendering lists

Note the shape: { opens JavaScript, tasks.map(...) produces an array of elements, React renders arrays by rendering each item. There is no special loop syntax to learn.

Keys — read this part twice

A key is React's identity tag for an item in a list. Without it, React matches children by position. With it, React matches by identity. That difference decides whether DOM state — input values, focus, scroll, CSS animations, component state — follows the right item.

Why index-as-key breaks — deleting the first of three items
  1. List renders [A, B, C] with keys 0, 1, 2. Each row has a checkbox. You tick the box on A.
  2. You delete A. New array is [B, C] with keys 0, 1.
  3. React compares by key. Key 0 existed before and still exists, so it reuses that DOM node and just changes the text from A to B.
  4. Result: the row now says B, but the ticked checkbox — which lives in the DOM node, not in your array — is still ticked. The tick jumped from A to B.
  5. With key={item.id}, React sees key a is gone, unmounts that row entirely, and B keeps its own untouched node.
When index-as-key is actually fine

All three must hold: the list never reorders, items are never inserted or deleted except at the end, and the items have no internal state or form inputs. A static footer nav qualifies. A to-do list does not. When in doubt, use a real id.

Keys are scoped and invisible

Keys only need to be unique among siblings, not globally. And key is consumed by React — a component cannot read props.key. If a child needs the id, pass it separately: <Row key={id} id={id} />.

The key trick nobody teaches you

Changing a component's key forces React to unmount it and mount a fresh one, resetting all its internal state. This is the idiomatic way to reset a form when the selected record changes.

Interview questions — lists and keys

Why does React need keys?

To identify which items in a list are the same item across renders. Reconciliation compares children pairwise; keys let React match by identity instead of position, so it can move, insert and delete nodes instead of overwriting them in place. That preserves DOM state and component state attached to each item, and it avoids unnecessary DOM work when a list reorders.

What goes wrong when you use the array index as a key?

Indices are positional, so after an insert, delete or reorder the same key points at different data. React reuses the DOM node and component instance for that position, so anything not driven by props — uncontrolled input values, focus, scroll position, internal useState, CSS transition state — stays behind while the content shifts. The symptom is usually "the checkbox ticked the wrong row" or "my input text jumped". It is safe only for static, append-only, stateless lists.

Why is key={Math.random()} worse than an index?

Because a fresh random key every render means no key ever matches, so React unmounts and remounts every single item on every render. You lose all state, lose focus on every keystroke, and turn an O(changes) update into an O(n) full teardown. It is the worst possible option.

Can two elements in different lists have the same key?

Yes. Keys only need to be unique among siblings within the same parent, because reconciliation compares children of one parent at a time. Global uniqueness is not required and does no harm either.

How would you force a child component to reset its internal state?

Change its key. React treats an element with a new key as a different element, unmounts the old instance and mounts a fresh one with initial state. This is preferred over an effect that watches a prop and calls setters, which double-renders and is easy to get wrong.

How do you render a list of 10,000 rows without freezing the browser?

Virtualisation: render only the rows in the viewport plus a small overscan buffer, and translate a spacer to fake the full scroll height. Libraries: @tanstack/react-virtual or react-window. Pagination or infinite scroll are the product-level alternatives. Memoising rows helps, but memoising 10,000 rows still costs 10,000 diffs — the only real fix is to not render them.

§06 Events and forms

Controlled inputs are the single most asked-about React topic in interviews.

Event handlers

React's synthetic events

React wraps native events in a SyntheticEvent object with a consistent cross-browser API. Since React 17, listeners are attached to the root container rather than document, and since React 17 the event pooling that used to require e.persist() is gone — you can safely use the event object asynchronously.

Controlled inputs

A controlled input is one whose displayed value comes from React state, and whose changes go back into React state. React is the single source of truth; the DOM just displays.

Typing one character into a controlled input
  1. State is "". React renders <input value="">.
  2. You press R. The browser fires a change event.
  3. onChange runs setText(e.target.value) — that is "R".
  4. State becomes "R". React re-renders the component.
  5. React renders <input value="R">. The character appears.
  6. If step 3 is missing, the value never changes and the input appears frozen — the classic beginner bug.
Read this line carefully

[name]: value is a computed property name. The square brackets mean "use the value of the variable name as the key". That one line replaces a separate handler for every field.

Interview questions — events and forms

What is a controlled component?

An input whose value is driven by React state and updated through onChange. React holds the source of truth and the DOM element only reflects it. The benefit is that the value is available anywhere in your render logic, so validation, conditional disabling, formatting and dependent fields all become trivial. The cost is a re-render per keystroke, which matters only in very large forms.

Why would you ever choose an uncontrolled input?

When you only need the value at submit time and want to avoid per-keystroke renders — large forms, or performance-sensitive pages. Also mandatory for file inputs, whose value cannot be set programmatically for security reasons. Read them with a ref, and set initial content with defaultValue / defaultChecked.

What is a synthetic event?

React's cross-browser wrapper around the native event, exposing a normalised API such as preventDefault, stopPropagation and target. React attaches a small number of listeners at the root container and dispatches from there rather than binding a listener to each node, which keeps memory use low on large trees. The native event is still available at e.nativeEvent.

Why does my form reload the page on submit?

Because the browser's default form submission is still happening. Call e.preventDefault() in the onSubmit handler. Attach the handler to the <form> rather than the button so keyboard Enter also works — that is an accessibility point worth mentioning.

Should validation errors be stored in state?

No, when they are purely a function of the current values — derive them during render so they cannot go stale. Store only what cannot be derived: which fields have been touched, whether a submit is in flight, and errors that come back from the server. Storing derived data is one of the most common causes of "the UI shows the old error" bugs.

How do you handle a form with 40 fields without 40 handlers?

One state object plus one handler using a computed property name from the input's name attribute: setForm(p => ({ ...p, [e.target.name]: e.target.value })). Branch on e.target.type for checkboxes and multi-selects. Beyond that scale, use React Hook Form, which keeps fields uncontrolled internally so typing does not re-render the whole form.

§07 State with useState

The register that survives re-renders. Get this section right and React stops feeling magical.

Why a plain variable does not work

State solves both: React stores the value outside your function, and calling the setter is what tells React to re-render.

Hardware analogy

A local let is a wire — it holds a value only while the combinational logic is evaluating, and it is gone afterwards. useState is a flip-flop: it holds across clock edges, and the setter is the clock enable. You cannot "just assign" to a register from combinational logic; you drive its input and wait for the edge. Same with state — you call the setter and read the new value on the next render.

State updates are asynchronous

count is a const captured by this render's closure. It can never change. The setter schedules a re-render in which a new count variable will exist with the new value. The current render keeps seeing the old one, and that is a feature — it guarantees everything in one render is consistent.

Batching, and the updater function

Render trace — three setters in one handler
  1. Render #1. count = 0. Handler is created, closing over count = 0.
  2. Click. All three setCount calls run. React batches them into one update queue.
  3. Direct form: queue is [set 1, set 1, set 1] → final value 1.
  4. Updater form: queue is [+1, +1, +1], applied in order to 0 → final value 3.
  5. React re-renders once, not three times. Batching is why.
Rule

If the new value depends on the old value, use the updater function form: setX(prev => ...). If it does not, the direct form is fine. Since React 18, batching applies everywhere — including inside promises, setTimeout and native event handlers — not just React event handlers.

Never mutate state

Mutation — React sees no change
New reference every time

React compares the old and new state with Object.is. Mutating gives back the same reference, so React concludes nothing changed and skips the re-render. The value did change; React just cannot see it.

push/pop/shift/unshift → spread. splice → slice + spread. sort/reverse → copy first, or use toSorted()/toReversed(). If nesting gets deep, reach for Immer (useImmer) rather than writing four levels of spread.

Lazy initialisation

Choosing what to put in state

Four questions before adding state
  1. Can I compute it from existing state or props? → derive it, do not store it.
  2. Does it stay the same across renders and never affect output? → use a ref (§11), not state.
  3. Does it need to be shared with a sibling? → lift it to the parent (§08).
  4. Is it server data? → it probably belongs in a data-fetching library's cache, not useState.

State is per-instance

Interview questions — state

Why is setState asynchronous?

So React can batch multiple updates from one event into a single re-render, and so it can prioritise work under concurrent rendering. Practically, the state variable in the current render is a const from a closure and never changes — you read the new value on the next render. If you must react to the new value, use the updater form, or compute the value into a local variable and use that.

What is the difference between setCount(count + 1) and setCount(c => c + 1)?

The first uses the value captured by the current render's closure. Called three times in one handler it schedules the same value three times, so the count goes up by one. The updater form receives the latest queued value, so three calls compose to plus three. Use the updater form whenever the new value derives from the old one, and always inside effects, timers and async callbacks where the closed-over value may be stale.

What is batching, and what changed in React 18?

Batching means grouping several state updates into a single re-render. Before React 18 it only applied inside React event handlers; updates inside promises, setTimeout or native listeners each caused their own render. React 18's automatic batching extends it to all of them. You can opt out for a specific update with flushSync from react-dom, which is occasionally needed when you must read the DOM immediately after an update.

Why must state be updated immutably?

React decides whether to re-render by comparing the previous and next state with Object.is. Mutating an object or array keeps the same reference, so the comparison says "unchanged" and the render is skipped. Immutability also makes React.memo, useMemo and dependency arrays work, since they all rely on reference equality, and it keeps features like time-travel debugging and concurrent rendering coherent.

When should you use lazy initialisation?

When the initial value is expensive to compute — parsing JSON, reading localStorage, building a large structure. useState(expensive()) evaluates on every render and throws the result away after the first; useState(() => expensive()) passes a function React calls only on mount.

What is "derived state" and why is storing it a bug?

Derived state is any value computable from existing state or props — a filtered list, a total, a validity flag. Storing it duplicates the source of truth, so the two can drift whenever one is updated and the other is not. Compute it during render instead; if the computation is genuinely expensive, wrap it in useMemo, which is a performance optimisation rather than a second copy of the data.

Two components render <Counter />. Do they share state?

No. State is stored per component instance, keyed by position in the render tree. Each <Counter /> gets its own independent slot. To share, the state must be lifted to a common ancestor and passed down, or placed in a Context or external store.

How does React know which state belongs to which useState call?

By call order. React keeps a list of state slots per component instance and advances an internal cursor with each hook call, so the first useState in the function always maps to the first slot. This is precisely why hooks cannot be called inside conditions or loops — a skipped call shifts every later hook onto the wrong slot.

§08 Lifting state and composition

Where should this piece of state live? There is a mechanical answer.

The rule

State belongs in the closest common ancestor of every component that needs to read or write it. Not higher (that causes needless re-renders and prop drilling), not lower (siblings cannot see it).

Notice the shape: the parent owns the value and passes down both the value and a way to change it. The child becomes controlled — it has no state of its own and is trivially reusable and testable. This is the same relationship as value/onChange on a DOM input, applied to your own components.

Hardware analogy

You have two modules that need the same register value. You do not duplicate the register in both — you instantiate it once in the parent module and route it to both as a port. Duplicating state in React has the same failure mode as duplicating a register: the two copies drift out of sync and you spend an afternoon working out which one is authoritative.

Prop drilling and the composition escape hatch

Order of escalation

1. Restructure with children. 2. If genuinely global and rarely changing — theme, locale, logged-in user — use Context (§12). 3. If large and frequently updating, use a store like Zustand or Redux Toolkit. 4. If it is server data, use TanStack Query and stop treating it as client state at all. Most people jump straight to step 2 or 3 and end up with an unnecessarily complicated app.

Interview questions — state architecture

What does "lifting state up" mean?

Moving a piece of state from a child into the closest common ancestor of all components that need it, then passing the value down as a prop and a setter down as a callback. It gives you a single source of truth so siblings cannot disagree, and it turns the children into controlled, reusable components.

How do you decide where a piece of state should live?

Find every component that reads it and every component that writes it, then put it in their lowest common ancestor. Keep it as low as possible — state high in the tree re-renders more of the app than necessary. If the only consumer is one component, it should stay local; global stores for local state is a common over-engineering smell.

Can a child update the parent's state?

Not directly. The parent passes a callback down as a prop; the child invokes it with the new value. The write still happens in the parent's scope, which preserves one-way data flow and keeps the update traceable to a single owner.

Is Context a replacement for Redux?

Not really. Context is a transport mechanism for passing a value down the tree without prop drilling; it has no reducers, no middleware, no devtools, and no selector-level subscription — every consumer re-renders when the provider's value changes. It fits low-frequency global values like theme or auth. For high-frequency or large shared state, a store with fine-grained subscriptions such as Zustand or Redux Toolkit is the appropriate tool, and for server data, TanStack Query.

What is the difference between local, lifted, and global state?

Local state lives in one component and nothing else can see it. Lifted state lives in a shared ancestor and reaches consumers by props. Global state lives outside the tree entirely and can be read from anywhere. The engineering trade-off is blast radius: local state cannot cause a bug elsewhere, global state can cause one anywhere, so you push state as low as the requirements allow.

Interview questions — effects

What is useEffect for?

Synchronising a component with an external system — the DOM outside React, network, timers, subscriptions, browser APIs. It runs after render is committed and the browser has painted, so it never blocks the visual update. It is not a lifecycle hook and thinking of it as componentDidMount leads people to write effects that should be plain calculations or event handlers.

Map useEffect to the class lifecycle methods.
  • useEffect(fn, []) ≈ componentDidMount
  • useEffect(fn, [a]) ≈ componentDidUpdate guarded on a
  • the returned function ≈ componentWillUnmount
  • useEffect(fn) ≈ mount plus every update

Worth adding: the mapping is a teaching aid, not the model. Effects are about synchronisation with a dependency, not about points in a lifecycle.

Why does my effect run twice on mount?

Because StrictMode in development mounts, unmounts and remounts each component to verify that effects are resilient to being re-run. It does not happen in production. The correct response is to add proper cleanup — abort the request, clear the timer, close the socket — because an effect that breaks when run twice will also break under fast refresh, offscreen rendering and future concurrent features.

What is a stale closure?

A callback that captured variables from an old render and keeps using those values after state has changed. It typically appears when an effect or timer has an empty dependency array but reads state inside. Fixes: include the dependency, use the functional updater form setX(prev => ...) so you never read the stale value, or store the latest value in a ref.

When does the cleanup function run?

Before the effect runs again due to a dependency change, and once more when the component unmounts. That ordering is what lets an effect cleanly hand off from one dependency value to the next — old subscription torn down before the new one is created.

What happens if you omit the dependency array entirely?

The effect runs after every render. If the effect sets state, that render triggers another effect run, which sets state again — an infinite loop. This is the most common cause of a frozen dev server for beginners.

Difference between useEffect and useLayoutEffect?

useEffect fires asynchronously after the browser paints; useLayoutEffect fires synchronously after DOM mutations but before paint, so it blocks painting. Use useLayoutEffect only when you must measure the DOM and immediately adjust it — positioning a tooltip against a trigger, for example — because otherwise the user sees a flash at the wrong position. It also does not run during server rendering, which produces a warning in SSR apps.

Name three things people wrongly use effects for.

Computing derived values from props or state; running logic that should live in an event handler; and resetting child state on a prop change, which should be a key change instead. A fourth: chaining effects where one sets state that triggers another — that is a state machine wearing a disguise, and useReducer is the right tool.

§10 Fetching data and custom hooks

Every real app does this. Doing it correctly means handling four states, not one.

The four states of any request

Idle, loading, success, error. Beginners handle only success, which is why their apps show blank screens and crash on a flaky connection. Interviewers check for exactly this.

Two things almost everyone gets wrong
  1. fetch only rejects on network failure. A 404 or 500 resolves normally with res.ok === false. Always check it.
  2. Without AbortController, a fast typing user fires five requests and the slowest one may resolve last, overwriting the correct result. That is the race condition interviewers ask about.
The race condition, and why abort fixes it
  1. User types "a". Request A starts.
  2. User types "ab". Effect cleanup aborts A. Request B starts.
  3. Without abort: A is slow, B is fast. B resolves, results for "ab" render.
  4. Without abort: A finally resolves and calls setResults. The screen now shows results for "a" while the box says "ab".
  5. With abort: A was cancelled at step 2 and its catch sees AbortError, which we deliberately ignore. Never happens.

Custom hooks

A custom hook is just a function whose name starts with use and which calls other hooks. It is not a React feature so much as a naming convention that lets you extract stateful logic and reuse it. No new syntax to learn.

Three custom hooks you should be able to write from memory

Rules of hooks — and why they exist
  1. Only call hooks at the top level — never inside conditions, loops, nested functions or after an early return.
  2. Only call hooks from React function components or other custom hooks.

The reason is mechanical: React identifies each hook by its call order, not by name. Skip a useState inside an if and every subsequent hook reads the wrong slot — your effect gets someone else's state.

What custom hooks share and do not share

Custom hooks share logic, not state. Every component calling useCounter gets its own independent state. To share actual state you need Context or a store.

When to stop hand-rolling this

In production, server data is usually handled by TanStack Query (React Query) or SWR. They give you caching, deduplication, background refetching, retries, pagination and stale-while-revalidate for free — all things you would otherwise reimplement badly. Write useFetch by hand to understand it, then use the library.

Interview questions — data fetching and custom hooks

How do you fetch data in React?

In a useEffect with a dependency array containing whatever the request depends on, handling loading, error and empty states explicitly, checking res.ok, and aborting on cleanup with AbortController. In production, delegate to TanStack Query or SWR for caching and deduplication, or fetch on the server with a framework and pass data down. React 19's use() with Suspense is the newer in-render approach — covered in §15.

What race condition can data fetching cause and how do you fix it?

If a dependency changes quickly, multiple requests are in flight and they can resolve out of order, so an older response overwrites a newer one. Fixes: abort the previous request in the effect cleanup with AbortController, or set a boolean flag in the cleanup and ignore results when the effect has been superseded. Query libraries handle this for you by keying results.

What is a custom hook?

A function starting with use that composes built-in hooks to package reusable stateful logic. It removes duplication without the wrapper-component nesting that HOCs and render props caused. It shares logic only — each caller gets its own independent state.

What are the rules of hooks and why do they exist?

Call hooks only at the top level of a component or another hook, never conditionally, and never from ordinary functions or class components. React associates hook calls with internal state slots by call order on each render, so a conditional call shifts the indices and every later hook reads the wrong slot. The ESLint plugin enforces both rules.

Why can't you call a hook inside an if, and what do you do when you need conditional logic?

Because the call order must be identical on every render. Put the condition inside the hook instead: call useFetch(shouldLoad ? url : null) and have the hook return early inside its effect. Same for early returns — all hooks must come before any return in the component.

Do two components using the same custom hook share state?

No. Each call creates a fresh set of state slots in that component's instance. If shared state is the goal, the hook must read from a Context or an external store — which is exactly how libraries like Zustand let a hook look local while being global.

Why debounce a search input?

To avoid one request per keystroke — that is server load, rate limiting, wasted bandwidth and a UI that flickers between partial results. Debouncing waits for a pause in typing before firing. Throttling is the related tool: debounce fires once after activity stops, throttle fires at most once per interval, so scroll and resize handlers use throttling while search boxes use debouncing.

Why re-renders happen, and when they matter

A component re-renders when its state changes, when its parent re-renders, or when a context it consumes changes. A parent re-rendering re-renders all its children by default, even if their props are identical.

React.memo — skip a re-render when props are unchanged

useMemo and useCallback

When these are actually worth it
  1. The computation is genuinely expensive — sorting thousands of rows, heavy parsing. Measure first.
  2. The value is a dependency of an effect and you need reference stability to stop the effect looping.
  3. The value is a prop passed to a memo-wrapped child, and stability is what makes the memo work.

Outside these three, memoisation adds code, adds a dependency array to keep correct, and costs a comparison on every render for no benefit.

The React Compiler changes this

Interview questions — refs and performance

What is useRef and how does it differ from useState?

useRef returns a mutable object with a current property that persists across renders. Mutating current does not trigger a re-render, whereas a state setter does. Use refs for values the UI does not display — DOM handles, interval ids, previous values, "has this already run" flags — and state for anything rendered.

When does a React component re-render?

When its own state changes, when its parent re-renders, or when a context value it consumes changes. Notably, a parent re-render propagates to all children regardless of whether their props changed — unless the child is wrapped in memo and its props are shallow-equal.

What does React.memo do and when does it fail?

It memoises a component so React skips re-rendering when the new props are shallow-equal to the previous ones. It fails whenever a prop is a newly created object, array or function — inline arrow handlers and object literals defeat it every render. That is the pairing with useCallback and useMemo: they exist to make memo viable. It also does nothing for state or context changes inside the component itself.

useMemo vs useCallback?

useMemo caches the result of calling a function; useCallback caches the function itself. useCallback(fn, deps) is defined as useMemo(() => fn, deps). Both take a dependency array and recompute only when a dependency changes by reference or value.

Is memoising everything a good idea?

No. Every memo has a cost — the dependency comparison, the retained memory, and the maintenance burden of keeping the dependency array correct. Applied indiscriminately it can be net slower and definitely makes code harder to read. The correct approach is to profile, find the actual hot path, and memoise there. And with React Compiler 1.0 handling this automatically at build time, hand-memoisation is becoming a legacy concern.

How do you access a DOM node in React, and why is it discouraged?

With a ref attached to the element, read as ref.current after mount. It is an escape hatch because it steps outside the declarative model — React no longer knows about changes you make imperatively, so they can be clobbered on the next render. Legitimate uses are the ones the declarative API does not cover: focus, text selection, scroll position, measuring, and media playback.

What replaced forwardRef in React 19?

Nothing replaced it — ref simply became a regular prop that function components can accept and destructure directly. forwardRef still works and is everywhere in existing code, but new components do not need the wrapper. This also removed a layer of indirection that used to confuse stack traces and devtools names.

What is useReducer and when do you prefer it over useState?

useReducer takes a pure reducer and an initial state and returns the current state plus a dispatch function. Prefer it when several state values change together, when transitions have branching rules, or when the same logic is triggered from many components. It centralises transitions so you can read all of them in one place, and because the reducer is pure and lives outside the component, it is directly unit-testable.

Must a reducer be pure?

Yes. No mutation of the incoming state, no fetch calls, no randomness, no reading of the clock. React may call it more than once for the same action in development to check this. Side effects belong in event handlers or effects; the reducer only computes the next state.

What is Context and what problem does it solve?

Context lets a provider make a value available to any descendant without passing it through intermediate props. It solves prop drilling for values that are genuinely tree-wide: theme, locale, authenticated user, feature flags. It is a transport mechanism, not a state container — the state usually still lives in a useState or useReducer inside the provider.

Why can Context hurt performance, and how do you mitigate it?

Every consumer re-renders whenever the provider's value changes by reference, and an inline object literal creates a new reference on every provider render — so unrelated components re-render constantly. Mitigations: memoise the value with useMemo; split state and dispatch into two contexts so action-only components never re-render on data changes; split by domain rather than one giant app context; or move to a store with selector-level subscriptions.

How do you avoid the "used outside provider" class of bug?

Wrap useContext in a custom hook that throws a descriptive error when the value is null. It converts a confusing downstream crash into an immediate, precise message, and it gives you one place to change the context implementation later without touching consumers.

Context + useReducer vs Redux Toolkit — how do you choose?

Context plus reducer is enough for most apps: no dependency, no boilerplate, and the pattern is identical in shape. Reach for Redux Toolkit when you need devtools time-travel, middleware for complex async flows, normalised entity caches, or when a large team benefits from strict conventions. If the pain is really about server data, neither is the answer — TanStack Query is.

§13 Routing with React Router

Multiple "pages" in a single-page app, without a full page reload.

The minimum you need

Never use an anchor tag for internal links

<a href="/products"> triggers a full document reload: the whole JavaScript bundle re-downloads, React remounts, and all in-memory state is destroyed. <Link> intercepts the click, pushes to the History API and lets React swap the component. Use <a> only for external URLs.

Reading the URL

Underrated point

Filters, sort order, pagination and search queries should live in the URL via useSearchParams, not in useState. That makes the view shareable, bookmarkable and survivable across refreshes — and it removes a piece of state you would otherwise have to manage.

Nested routes and layouts

The layout stays mounted while children swap — so the sidebar does not flicker, and its scroll position is preserved.

Protected routes

Say this in an interview

A protected route is a user-experience control, not a security control. Anyone can read your bundle and call the API directly. Real authorisation happens on the server on every request; the client route guard only stops honest users from seeing an empty page.

Lazy loading routes

Each lazy import becomes its own chunk, downloaded on first visit to that route. On a large app this is the difference between a 900 KB initial bundle and a 120 KB one.

Interview questions — routing

How does client-side routing work?

The router intercepts link clicks, calls history.pushState to change the URL without a request, and renders the component that matches the new path. It also listens for popstate so the browser's back and forward buttons work. No document is fetched, so state and the loaded bundle survive navigation.

Difference between Link and <a>?

<a> performs a full page load — the bundle re-downloads and all React state is lost. <Link> renders an anchor but calls preventDefault and navigates through the History API instead. Rendering a real anchor matters for accessibility and for middle-click / open-in-new-tab, which is why Link does not use a div.

NavLink vs Link?

NavLink is a Link that knows whether it is active for the current URL, exposing isActive to its className and style callbacks. Use it for navigation menus so the current section is highlighted without you tracking the pathname yourself.

How do you protect a route?

Render a guard component that checks auth state and either renders <Outlet /> or <Navigate to="/login" replace />. Use replace so the protected URL does not enter the history stack and trap the user in a redirect loop on back. Pass the attempted location in navigation state so login can return them there. And state clearly that the real enforcement is server-side.

What is Outlet?

A placeholder in a parent route's element where the matched child route renders. It is what makes nested layouts possible: the shell — header, sidebar, breadcrumbs — stays mounted while only the inner content changes.

Why put filters and pagination in the URL?

Because the URL is shared, bookmarked, refreshed and navigated back to. Keeping that view state in useSearchParams makes those cases work for free, removes duplicated state, and is what users expect from a real product. It also makes bug reports reproducible — someone can paste the URL.

Why does refreshing /products/42 give a 404 on deployment?

Because the static host looks for a file at that path and does not find one — client-side routing only exists after the JavaScript loads. The fix is a server rewrite that returns index.html for any unmatched path: a _redirects file on Netlify, a rewrite rule on Vercel, or try_files $uri /index.html in nginx. This is a very common practical interview question.

§14 Boundaries, portals, Suspense

Three tools for problems that are awkward without them.

Error boundaries

A JavaScript error thrown during render unmounts the entire React tree and leaves a white screen. An error boundary catches errors from its subtree and renders a fallback instead.

What boundaries do not catch

Errors in event handlers, in setTimeout or other async code, during server rendering, and errors thrown by the boundary itself. Handle those with ordinary try/catch. In practice most teams use react-error-boundary, which provides a hook-friendly API and a reset mechanism.

Portals

A portal renders children into a DOM node outside the parent's hierarchy, while keeping them in the React tree — so props, context and event bubbling all still work normally.

Why it exists: a modal nested inside a card with overflow: hidden or a transform gets clipped or trapped in a stacking context. Portalling to document.body escapes that without breaking your component structure.

lazy and Suspense

lazy splits the component into a separate bundle chunk fetched on first render. Suspense declares what to show while any component below it is not ready. Split at route level first, then at heavy-widget level — charts, editors, maps, PDF viewers.

Interview questions — boundaries, portals, Suspense

What is an error boundary and what does it not catch?

A component that catches JavaScript errors thrown during rendering, in lifecycle methods and in constructors of its subtree, and renders a fallback UI instead of unmounting the whole tree. It does not catch errors in event handlers, in asynchronous code, during server rendering, or thrown by itself. Traditionally it must be a class component implementing getDerivedStateFromError and/or componentDidCatch; React 19 added root-level onCaughtError and onUncaughtError options for reporting.

Where should you place error boundaries?

Around independent subtrees whose failure should not take down the page — a chart widget, a comments panel, each route. One boundary at the root is better than none, but it turns any failure into a whole-app fallback. Granular boundaries let the rest of the page keep working, which is the actual point.

What is a portal and does event bubbling still work?

A portal renders children into a different DOM container while keeping them at their original position in the React tree. Because React's event system follows the React tree rather than the DOM tree, events bubble to the React parent even though the node is elsewhere in the document — a click inside a modal portalled to body still reaches an onClick on the component that rendered the modal. Context also flows through normally.

What is code splitting and how do you do it in React?

Breaking the bundle into chunks loaded on demand instead of shipping everything upfront. In React it is React.lazy(() => import("./X")) wrapped in <Suspense>; the bundler turns each dynamic import into its own chunk. Route-level splitting gives the biggest win, followed by heavy third-party widgets. The trade-off is a loading state on first navigation, which you mitigate with skeletons and prefetching on hover.

What is Suspense actually for?

It declares a loading fallback for a subtree that is not ready yet, so components below it do not each need their own loading flag. Originally it worked only with lazy; it now also handles data with use() and with Server Components, and pairs with useTransition so navigations do not blank out already-visible content.

§15 React 19: use, Actions, Optimistic UI

The current APIs. Learn them after the fundamentals, because they only make sense as replacements.

React 19 shipped in December 2024 and is the baseline for new work in 2026. The theme across all of it is removing boilerplate you used to write by hand: pending flags, error state, optimistic updates, form resets.

use — read a promise or context during render

Unlike every other hook, use may be called conditionally and inside loops. It also reads context: const theme = use(ThemeContext). Note that the promise must be created outside the component or cached — creating it inline on each render restarts the request forever.

Actions and useActionState

An "Action" is an async function passed to a form or transition. React tracks pending state, errors and sequencing for you.

Compare with what this replaces: a useState for pending, another for error, a try/catch/finally, and manual form reset. React also resets uncontrolled form fields automatically after a successful action.

useOptimistic — show the result before the server confirms

The value automatically reverts to the real state when the action finishes or fails. That revert-on-failure is the part that was tedious and bug-prone to write by hand.

useTransition — keep the UI responsive during heavy updates

Related: useDeferredValue(value) returns a lagging copy of a value so an expensive list can render at lower priority while the input stays responsive.

Smaller changes worth knowing

  • ref is a plain prop. forwardRef is no longer needed for new components.
  • Document metadata — <title>, <meta> and <link> rendered anywhere get hoisted into <head> automatically, so react-helmet is no longer required.
  • <Context> as provider — no more .Provider.
  • Ref cleanup functions — a ref callback may return a cleanup function.
  • Better hydration errors — a single diff instead of a wall of mismatched-text warnings.
  • Removed — propTypes and defaultProps on function components, legacy context, string refs, ReactDOM.render.
  • React Compiler 1.0 — an opt-in build plugin that inserts memoisation automatically for code that follows the rules of React.
  • Server Components are stable, though the bundler-facing APIs do not follow semver between 19.x minors, so pin versions if you maintain that layer.
What to say when asked "do you know React 19?"

Name three things and what they replace: useActionState replaces hand-rolled pending/error state around form submits; useOptimistic replaces manual optimistic update and rollback; ref as a prop removes forwardRef. Then mention the Compiler making manual useMemo/useCallback largely unnecessary. That is a far better answer than reciting a changelog.

Interview questions — React 19

What is the use API and how does it break the rules of hooks?

use reads a resource — a promise or a context — during render. If given an unresolved promise it suspends the component until it settles, integrating with the nearest Suspense boundary. Unlike other hooks it can be called conditionally and inside loops, because it is not tied to a positional state slot. The promise must be created outside render or cached, otherwise a new one starts on every render.

What problem does useActionState solve?

It removes the boilerplate around async submissions: it manages the pending flag, holds the value returned by the action as state, and sequences submissions so a slow one cannot overwrite a newer one. Combined with <form action={fn}>, React also resets uncontrolled fields after success. Previously you wrote two or three useState calls and a try/catch/finally for every form.

What is optimistic UI and what does useOptimistic add?

Optimistic UI shows the expected result immediately rather than waiting for the server, which makes an app feel instant. The hard part was reverting cleanly on failure and reconciling with the eventual server state. useOptimistic gives you a temporary derived value that automatically falls back to the real state once the action completes or throws.

What is useTransition for?

It marks a state update as non-urgent so React can interrupt it to handle urgent work like typing or clicking. You get an isPending flag to show feedback. It is the fix for "the input lags while a big list re-renders" — the input update is urgent, the list update is a transition. useDeferredValue does the same thing from the consuming side when you cannot wrap the setter.

What is the React Compiler and does it change how you write code?

It is a build-time optimising compiler that analyses components and inserts memoisation automatically, so manual useMemo, useCallback and React.memo become largely unnecessary. It reached 1.0. It does change how you write code in one respect: it relies on components following the rules of React — pure render, no mutation of props or state — so code that quietly breaks those rules can behave differently once compiled. That is another reason StrictMode warnings matter.

What are Server Components, in one paragraph?

Components that render on the server and send a serialised description of the result to the client, never shipping their own JavaScript in the bundle. They can read a database or filesystem directly and are ideal for static, data-heavy parts of a page; they cannot use state, effects or event handlers, so interactive leaves stay as client components marked with "use client". They are stable in React 19 but require a framework such as Next.js or a bundler integration to use.

Interview questions — practices

How do you structure a React project?

By type for small apps — components, pages, hooks, services — and by feature once the app grows, so each domain owns its components, hooks and API calls in one folder. The deciding question is "if I delete this feature, how many folders do I touch?" One is the right answer. Shared, generic UI stays in a top-level components folder.

CSS Modules vs Tailwind vs styled-components?

CSS Modules give local scoping with zero runtime and plain CSS — a safe default. Tailwind trades verbose markup for speed, consistency and no naming decisions, and is the most common choice in industry now. styled-components allow styles derived from props but add runtime cost and do not sit well with Server Components. There is no universally right answer; what matters is picking one and applying it consistently.

How do you handle environment variables in a React app?

In Vite, variables prefixed VITE_ are exposed as import.meta.env.VITE_X and inlined at build time. Because they are inlined into the client bundle, they are readable by anyone — API secrets must live on a server, never in a frontend env file. Use them for public config: API base URLs, feature flags, analytics ids.

What do you test in a React component?

Behaviour visible to a user: does clicking the button show the new value, does an invalid form show the error, does the empty state appear with no data. Not implementation details like internal state variables or CSS classes, because those change during refactors that do not change behaviour. Query by role and accessible name, which also nudges you toward accessible markup.

Name three accessibility mistakes common in React apps.

Using div with onClick instead of button, so the control is unreachable by keyboard and invisible to screen readers. Inputs with placeholder text but no label. Modals that do not trap or restore focus, leaving keyboard users stranded behind the overlay. A fourth: removing the focus outline in CSS for aesthetics.

§19 Rapid-fire interview sheet

Short answers you should be able to give in under 30 seconds each.

Core

What are the main features of React?

Component-based architecture, declarative rendering, one-way data flow, a virtual DOM with reconciliation, JSX, hooks for stateful logic in functions, and renderer independence so the same components can target DOM, native or test environments.

What is a pure component?

One that returns the same output for the same props and state, and causes no side effects during render — no mutating props, no writing to variables outside itself, no fetching. React relies on purity to skip, restart and reorder renders safely. React.memo is the function-component equivalent of the old PureComponent class.

Why can't you mutate props or state during render?

Because React may call your component more than once for the same update, may abandon a render, and may reuse the previous result. Any mutation during render makes the output depend on how many times it ran, which is non-deterministic. StrictMode's double render exists to expose exactly this.

What is a higher-order component?

A function that takes a component and returns an enhanced one — withAuth(Dashboard). It was the pre-hooks pattern for sharing logic. Custom hooks superseded it because HOCs caused deep wrapper nesting in devtools, prop-name collisions and awkward ref forwarding. Know it for reading older codebases.

What are render props?

Passing a function as a prop that returns JSX, so a component can supply data while the caller decides the markup: <Mouse render={pos => <Dot at={pos} />} />. Same purpose as HOCs, same replacement by hooks — though the pattern survives in libraries for headless UI components.

Controlled vs uncontrolled — one line each.

Controlled: React state is the source of truth, driven by value + onChange. Uncontrolled: the DOM holds the value, seeded by defaultValue and read via a ref.

What is the children prop?

Whatever sits between a component's tags, delivered automatically as props.children. The foundation of composition and the simplest cure for prop drilling.

How do you pass data from child to parent?

The parent passes a callback down as a prop; the child calls it with the data. The state update still executes in the parent, preserving one-way data flow.

What happens if you call a setter with the same value?

React compares with Object.is and bails out — no re-render. It may still render once more before bailing out, but it will not go deeper into the tree. This is why mutating an object and passing the same reference results in no update at all.

What is flushSync?

A react-dom escape hatch that forces a state update to be applied synchronously instead of being batched, so the DOM is updated before the next line runs. Needed rarely — for example measuring an element immediately after inserting it. It hurts performance and defeats concurrent features, so treat it as a last resort.

Hooks

List the built-in hooks you have used.

useState, useEffect, useRef, useContext, useReducer, useMemo, useCallback, useLayoutEffect, useId, useTransition, useDeferredValue, and from React 19 use, useActionState, useOptimistic, plus useFormStatus from react-dom.

Why were hooks introduced?

To let function components hold state and side effects, so stateful logic could be extracted and reused without HOC or render-prop nesting, and so related logic could live together instead of being split across three lifecycle methods. They also removed the confusion around this binding in classes.

What is useId for?

Generating a stable unique id that matches between server and client render, for accessibility attributes like htmlFor and aria-describedby. It is not for list keys — those must come from your data.

What is useDeferredValue?

It returns a copy of a value that lags behind during urgent updates, so an expensive subtree can render at lower priority while the input stays responsive. Use it when you cannot wrap the state setter in startTransition — for instance when the value arrives as a prop.

Can you call a hook inside a loop or condition?

No, except use. React tracks hooks by call order, so a varying number of calls misaligns the state slots. Move the condition inside the hook, or extract a child component.

Performance

How do you find a performance problem in React?

React DevTools Profiler: record an interaction, look at the flame graph for components that render often or take long, and use "highlight updates" to spot unnecessary re-renders. Then decide whether the fix is fewer renders (memoisation, moving state down, splitting context) or less DOM (virtualisation, pagination). Measure before and after.

Name five ways to reduce unnecessary re-renders.

Move state down to the smallest component that needs it; pass subtrees as children so they are not recreated by the parent's render; React.memo on expensive leaves with stable props; useMemo/useCallback for reference stability where a memo depends on it; split large contexts. And virtualise long lists, which is usually a bigger win than all of the above.

What is code splitting and why does it matter?

Splitting the bundle so users download only what a route or feature needs. It reduces time-to-interactive on the first load, which is the metric users actually feel. Route-level lazy + Suspense gives most of the benefit for very little code.

What is lazy loading images and how is it done?

Deferring off-screen images until they are near the viewport. Native loading="lazy" on <img> covers most cases; IntersectionObserver gives more control for placeholders and blur-up effects. Always set explicit width and height to avoid layout shift.

Practical and behavioural

How do you debug a React app?

React DevTools components tab to inspect props, state and hooks and confirm the value is what you think it is; the Profiler for render cost; the browser Network tab for request problems; and a console.log at the top of the component body to see how many times it renders and with what. For state bugs, the first question is always "is this value derived or stored?" — most of them come from stored derived state.

A component re-renders too often. Walk me through your diagnosis.

First, confirm it with the Profiler rather than guessing. Then check the three causes in order: its own state changing more than expected, a parent re-rendering and passing new object or function props, or a context value being recreated each render. The fix follows from which one it is — move state down, memoise the prop, or split the context. Only after that would I reach for React.memo.

What would you do differently if you rebuilt your project?

Have a real answer ready and make it about architecture, not features. For example: keeping filter state in the URL from the start instead of retrofitting it; splitting a single app-wide context that was re-rendering everything; or adding loading and error states in the first pass rather than bolting them on. Naming a genuine mistake and its fix reads as experience.

How do you keep up with React?

The official blog and docs at react.dev, the release notes for each minor, and reading the source of a library you use. Naming one recent change and what it replaces — the Compiler, or Actions removing manual pending state — is worth more than listing newsletters.

What is server-side rendering and when would you use it?

Rendering the component tree to HTML on the server so the browser receives content immediately, then hydrating it with JavaScript to make it interactive. Use it when SEO or first-contentful-paint matters — marketing pages, e-commerce, content sites. Skip it for authenticated dashboards where neither applies and it only adds infrastructure complexity.

What is hydration and what is a hydration mismatch?

Hydration is attaching React's event listeners and state to server-rendered HTML instead of recreating the DOM. A mismatch happens when the client's first render produces different markup than the server sent — typically from using Date.now(), Math.random(), window, or locale-dependent formatting during render. React 19 reports these as a single readable diff rather than a stream of warnings.

React vs Next.js — when do you choose which?

React with Vite for client-rendered apps: dashboards, internal tools, anything behind a login. Next.js when you need server rendering, static generation, file-based routing, API routes or Server Components — public-facing sites where SEO and first paint matter. Next is React plus a framework, so the component knowledge transfers entirely.

§20 Study plan and habits to unlearn

The specific fix for "I shipped projects but cannot read my own code".

Why the gap exists

Generated code gives you a working result without the intermediate step where you form a model of why it works. You end up able to recognise correct code but not produce it — which is exactly the skill an interviewer tests, because a whiteboard has no autocomplete. The gap closes surprisingly fast, because you already have the vocabulary; what is missing is retrieval practice.

Five habits to drop immediately
  1. Copy-pasting a block you cannot explain line by line.
  2. Asking for the whole component instead of the one concept you are stuck on.
  3. Adding useEffect whenever something feels out of sync — usually the value should be derived.
  4. Reaching for a library before you have written the twenty-line version once.
  5. Reading tutorials instead of building. Reading feels like progress and is not.

The daily loop that actually works

  1. Read one concept — 15 minutes maximum.
  2. Type the example without looking, then compare. The gap between what you wrote and what is here is your real syllabus.
  3. Break it on purpose. Remove the key. Mutate the state. Omit the dependency array. Watch what happens. Deliberate breakage teaches more than working code.
  4. Explain it out loud in two sentences, as if to another student. If you cannot, you have not learned it — go back to step 2.
The self-test that predicts your interview result

Close everything. On a blank file, write from memory: a controlled form with one shared change handler; a to-do list with immutable add/toggle/delete; a useFetch hook with loading, error and abort; and a debounced search input.

If you can write all four without help, you will pass a frontend machine-coding round. If you cannot, you know exactly which section to reopen — and that is worth more than another tutorial.

Where to go next

  • TypeScript with React. Almost every job listing asks for it now, and typing props is a small step from what you already know.
  • TanStack Query. Once you have hand-written useFetch, this will feel obvious and will save you writing it again.
  • Next.js. Only after plain React is comfortable — otherwise you will not be able to tell which behaviour is React and which is the framework.
  • Testing with Vitest and React Testing Library. A single well-written test in a portfolio project is a strong signal.
  • Read source code. Pick a small library — clsx, zustand, react-error-boundary — and read it end to end. Zustand is under 200 lines and will teach you more about React internals than most articles.
One last thing

Your hardware background is an advantage in frontend interviews, not a detour. You already think about state machines, timing, purity of combinational logic and separating interface from implementation. React is the same discipline applied to a screen. Say that in an interview and it will land.
