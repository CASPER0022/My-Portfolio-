Foundations · 00

What "backend" actually means

Before any framework, understand the shape of the problem. A backend is a program that sits on a machine you control, waits for messages from machines you do not control, and answers them correctly, quickly and safely.

The one-sentence definition

A backend is a long-running program that accepts requests over a network, applies business rules, reads and writes durable data, and returns a response — while remaining correct when thousands of users do this at the same time.

Everything else in this notebook is a consequence of that sentence:

  • "over a network" → HTTP, TCP, latency, timeouts, retries (Part A, D4)
  • "applies business rules" → architecture, layering, validation (A6, D3)
  • "durable data" → databases, transactions, indexes (Part B)
  • "quickly" → caching, indexing, async work (B3, C3, C4)
  • "safely" → authentication, authorization, OWASP (C1, C2)
  • "at the same time" → concurrency, scaling, replication (C5, D1, D2)

The single most important backend rule

Never trust the client. Anything the browser sends — form fields, headers, cookies, hidden inputs, prices, user IDs, "isAdmin" flags — can be forged with a single curl command. Frontend validation is a courtesy to honest users. Backend validation is the actual security boundary. Interviewers slip this into questions constantly: if a question mentions the client sending a price, quantity or role, the expected answer includes "I re-derive or re-verify that on the server."

The layers of a typical backend

Almost every production backend, in any language, decomposes into the same layers. Being able to name them is often the first question in an interview.

1 · Edge / CDNServes static assets from the location nearest the user, absorbs traffic spikes, terminates TLS, blocks obvious abuse.
2 · Load balancerSpreads incoming connections across many identical app servers, removes unhealthy ones, keeps the system alive when a machine dies.
3 · Web / API layerParses HTTP, routes to a handler, runs middleware (auth, logging, rate limiting), validates input, serialises output. Holds no business rules.
4 · Service / business layerThe actual rules: "an order can only be cancelled before it ships", "a wallet cannot go negative". Framework-agnostic, testable without a network.
5 · Data access layerRepositories, ORM models, raw SQL. The only place that knows table names, so storage can change without rewriting the rules.
6 · DatastoresRelational database (source of truth), cache (Redis), object storage (S3), search index (Elasticsearch).
7 · Async workersConsume from a queue and do the slow things — emails, PDFs, image resizing, report generation — so the request can return in milliseconds.
Why layering is a real answer, not jargon

Layering exists so that a change has one place to happen. If the tax rule lives in the service layer, changing it means editing one function. If it is scattered across three controllers, a template and a SQL query, changing it means finding all four and missing one. When an interviewer asks "why not put the SQL directly in the route handler?", that is the answer: not purity, but blast radius and testability.

Interview questions · Foundations
What does a backend developer actually do all day?

Design and expose APIs, model and query data, enforce business rules and permissions, make slow things fast (indexes, caching, async jobs), and keep the system correct under concurrency and failure. In practice, a large share of the work is data modelling and failure handling, not writing new endpoints.

Why can't we just validate on the frontend?

Because the frontend is code running on a machine the attacker controls. Anyone can bypass it with curl, Postman, or by editing JavaScript in DevTools. Frontend validation improves UX (instant feedback, fewer round trips); backend validation is the enforcement point. You need both, for different reasons.

What is the difference between stateless and stateful servers?

A stateless server keeps no per-user memory between requests — everything needed is in the request itself (a token) or in shared storage (a database, Redis). A stateful server remembers, for example, session data in local RAM. Stateless is preferred because any instance can serve any request, so you can add and remove servers freely and a crash loses nothing. "Stateless" does not mean "no state anywhere" — the state simply lives in a shared store rather than in one process's memory.

Where should business logic live, and why not in the controller?

In a service layer that does not import the web framework. Then the same rule can be invoked from an HTTP endpoint, a background job, a CLI script and a unit test without spinning up a server. Controllers should do four things only: parse, validate shape, call a service, format the response.

What usually becomes the bottleneck first in a web application?

The database — through unindexed queries, N+1 query patterns, lock contention, or exhausted connection pools. App servers are cheap to clone; a single primary database is not. That is why the standard optimisation order is: fix the query → add an index → add a cache → offload work to a queue → only then add read replicas or shard.

Explain latency vs throughput with an example.

Latency is how long one request takes; throughput is how many complete per second. A single-lane road with a 200 km/h speed limit has low latency and low throughput; an eight-lane road at 60 km/h has higher latency and much higher throughput. Adding servers usually raises throughput without improving latency, whereas adding an index or a cache improves both.

Why do we report p95 and p99 latency instead of the average?

Averages hide the tail. If 95 requests take 50 ms and 5 take 4 seconds, the mean looks like 250 ms and seems fine — but one user in twenty had a terrible experience. Percentiles describe the worst experiences that are still common, which is what users actually complain about. On a page that makes 20 API calls, a p99 of 4 s means most page loads contain at least one slow call.

The life of a single request

"What happens when you type a URL and press Enter?" is the most-asked backend interview question in existence. Here is the full path, in order, with what can go wrong at every hop.

The twelve steps

  1. URL parsing. The browser splits https://api.shop.com:443/orders?page=2#top into scheme, host, port, path, query string and fragment. The fragment after # is never sent to the server — a favourite trick question.
  2. DNS resolution. The name api.shop.com is turned into an IP address. The browser cache is checked, then the OS cache, then the configured resolver, which walks root → .com → authoritative nameserver. Results are cached for the record's TTL, which is why DNS changes take time to propagate.
  3. TCP connection. A three-way handshake — SYN, SYN-ACK, ACK — establishes a reliable, ordered byte stream. One round trip.
  4. TLS handshake. For HTTPS, client and server agree on a cipher, the server presents a certificate signed by a trusted CA, and they derive a shared symmetric key. One or two more round trips (TLS 1.3 needs only one).
  5. Request sent. A request line, headers and an optional body travel over the encrypted connection.
  6. Edge/CDN. If the resource is cacheable and already stored nearby, the CDN answers immediately and the origin never hears about it.
  7. Load balancer. Picks a healthy application server, usually round-robin or least-connections, and forwards the request.
  8. Application server. The framework routes the path to a handler and runs the middleware chain: logging → CORS → authentication → rate limiting → body parsing → validation.
  9. Business logic. The service layer applies rules and asks for data.
  10. Cache, then database. Redis is checked first; on a miss, a connection is borrowed from the pool, SQL runs (hopefully hitting an index), and the result is written back to the cache.
  11. Response built. The object is serialised to JSON, a status code and headers are set, and the bytes travel back down the same chain.
  12. Cleanup. Metrics and logs are emitted, the database connection returns to the pool, and slow follow-up work (email, analytics) is pushed to a queue rather than done inline.

Step through it yourself

Each stage below is one hop in the path. Watch where the time goes — and notice that a cache hit short-circuits everything after it.

Where each hop can fail

DNS — stale cache after a migration. TCP — connection refused, or exhausted ports. TLS — expired certificate (a real, common outage cause). Load balancer — all backends marked unhealthy. App — unhandled exception → 500. Database — pool exhausted, so requests queue and time out even though the database itself is idle. Client — timeout fires while the server is still working, so the work happens but nobody receives the answer. That last case is exactly why idempotency matters.

Interview questions · Request lifecycle
What happens when you type a URL and press Enter? (the classic)

Answer it in layers rather than as a flat list: resolve (DNS name → IP), connect (TCP handshake, then TLS handshake for HTTPS), request (HTTP request line + headers + body), route (CDN → load balancer → app server → middleware → handler), fetch (cache, then database), respond (serialise, status code, headers, bytes back), render (browser parses HTML, requests sub-resources, runs JS). Mentioning caching at each level — DNS TTL, CDN, HTTP cache headers, Redis — is what separates a strong answer from a memorised one.

How many round trips before the first byte of a fresh HTTPS request?

Roughly: 1 for DNS if uncached, 1 for the TCP handshake, 1 for TLS 1.3 (2 for TLS 1.2), then 1 for the request/response itself — about 3–4 round trips. On a 100 ms link that is 300–400 ms before any application work happens, which is why connection reuse (keep-alive), HTTP/2 multiplexing and CDNs matter so much.

Is the URL fragment sent to the server?

No. Everything after # is processed entirely by the browser and never appears in the HTTP request. That is why fragments cannot be logged server-side and why single-page apps historically used them for routing.

Difference between TCP and UDP, and where each is used?

TCP is connection-oriented: it handshakes, guarantees ordered delivery, retransmits lost packets and applies congestion control — at the cost of latency and head-of-line blocking. UDP just fires datagrams with no guarantees, so it is faster and has no ordering constraint. HTTP/1.1 and HTTP/2 run over TCP; DNS queries, video calls, game traffic and QUIC (which underlies HTTP/3) run over UDP, adding their own reliability where needed.

What does TLS actually give you?

Three things: confidentiality (traffic is encrypted so intermediaries cannot read it), integrity (tampering is detected), and authentication (the certificate proves you are talking to the real host, not an impostor). It uses asymmetric cryptography only to agree on a key, then switches to fast symmetric encryption for the actual data.

Why is DNS cached, and what problem does that cause?

Caching avoids a network round trip on every request. The cost is propagation delay: after you point a domain at a new server, clients holding a cached record keep using the old IP until the TTL expires. The standard mitigation is to lower the TTL well before a planned migration.

The database is idle but requests are timing out. What is happening?

Almost certainly connection-pool exhaustion. Requests are waiting to borrow a connection, not waiting on SQL. Common causes: a leaked connection that is never returned, a long-running transaction holding one open, or a pool sized far below concurrency. Check pool wait time as a metric separately from query time.

HTTP in depth

asked in ~every interview methods status codes headers idempotency

HTTP is a text-based request/response protocol. The client opens a connection, sends a request, receives one response, and that exchange is complete. The server remembers nothing afterwards — HTTP is stateless by design, and every session and token mechanism exists to work around that.

Anatomy of a request

POST /api/v1/orders HTTP/1.1 ← method, path, version Host: api.shop.com ← headers begin Content-Type: application/json Authorization: Bearer eyJhbGciOi... Idempotency-Key: 4f9a-11ee-8c2b Content-Length: 48 ← blank line separates headers from body {"productId": 42, "quantity": 2} ← body

Methods, and the two properties that define them

Two ideas explain the whole method table. Safe means the request does not change server state — it is read-only, so it can be prefetched or retried freely. Idempotent means sending it N times has the same effect as sending it once — so a client that times out can retry without fear.

Why PUT is idempotent but POST is not

PUT /users/7 with a full body says "make user 7 look exactly like this". Run it five times and user 7 still looks exactly like that. POST /users says "create a new user" — run it five times and you have five users. This is not a naming convention; it is a promise the client relies on when deciding whether a timed-out request is safe to retry.

PATCH is idempotent only if the patch is absolute ({"status":"paid"}) and not relative ({"increment_views": 1}) — which is why the spec refuses to guarantee it.

The status-code mistakes that get candidates marked down

Returning 200 with {"error": "..."} inside. Clients, proxies and monitoring all read the status line; hiding failures in a 200 body breaks retries and alerting.
Confusing 401 and 403. 401 = "I don't know who you are." 403 = "I know exactly who you are, and no."
Using 500 for user mistakes. A 5xx means you broke; it should page an engineer. Invalid input is 4xx.
Using 404 for an empty list. GET /orders with no orders is 200 [] — the collection exists, it is simply empty.

Interview questions · HTTP
What does it mean that HTTP is stateless?

Each request is interpreted independently; the protocol carries no memory of previous requests. The server cannot tell request #2 came from the same user as request #1 unless the client re-proves it — with a cookie, a token, or an API key. Statelessness is what allows any server behind a load balancer to answer any request, which is the foundation of horizontal scaling.

Difference between PUT and PATCH?

PUT replaces the whole resource: fields you omit are treated as removed or reset. PATCH applies a partial change: only the fields you send are touched. So PUT /users/7 {"name":"Sam"} may wipe the email, while PATCH /users/7 {"name":"Sam"} changes only the name. PUT is idempotent; PATCH is idempotent only if the operations are absolute rather than relative.

Is POST ever idempotent? How do you make it safe to retry?

Not by default, but you can make it effectively idempotent with an idempotency key: the client generates a UUID and sends it in a header. The server stores (key → result); if the same key arrives again it returns the stored result instead of performing the action twice. This is exactly how Stripe prevents double charges when a network call times out.

401 vs 403 — give a concrete example of each.

401: you call /api/orders with no token, or with an expired one — the server does not know who you are, so re-authenticating could fix it. 403: you are logged in as a regular user and call /api/admin/users — the server knows exactly who you are and re-authenticating will not help. A useful nuance: for sensitive resources many APIs return 404 instead of 403, so attackers cannot learn which IDs exist.

What status code for a successful DELETE? For a slow job?

DELETE: 204 No Content if nothing is returned, or 200 with a body if you return the deleted object. Deleting something already gone can return 204 as well, which keeps DELETE idempotent. A slow job: return 202 Accepted immediately with a job id and a status URL the client can poll.

What is an ETag and what two problems does it solve?

An ETag is a fingerprint of a resource version (a hash, or a timestamp). First, caching: the client sends it back in If-None-Match and the server can answer 304 Not Modified with no body. Second, optimistic concurrency: the client sends it in If-Match on an update, and the server rejects with 412 Precondition Failed if someone else changed the resource meanwhile — preventing lost updates.

Why does HTTP/2 make the "sprite sheet" and "concatenate all JS" tricks obsolete?

Those tricks existed because HTTP/1.1 allowed only one in-flight request per connection and browsers capped connections at about six, making many small files expensive. HTTP/2 multiplexes many streams over a single connection, so small files cost far less — and bundling actually hurts caching, because changing one line invalidates the whole bundle.

Why is HTTP/3 built on UDP?

To escape TCP head-of-line blocking. In HTTP/2 all streams share one TCP connection, so a single lost packet stalls every stream until it is retransmitted. QUIC implements reliability per-stream on top of UDP, so a loss on one stream does not block the others. It also merges the transport and TLS handshakes, cutting a round trip.

Can GET have a body?

Technically the spec no longer forbids it, but in practice it is unusable: proxies, CDNs and many server libraries strip or ignore it, and caching keys are built from the URL. If a read genuinely needs a large complex filter, either encode it in the query string or use POST to a /search endpoint and accept the loss of cacheability.

What is keep-alive and why does it matter?

Persistent connections: instead of tearing down the TCP (and TLS) connection after each response, it is reused for subsequent requests. This removes the handshake cost — often 100–300 ms — from every request after the first. It is the default in HTTP/1.1 and inherent to HTTP/2. Server-side, this is also why connection limits and timeouts must be tuned.

REST API design

design round favourite resources versioning pagination consistency > cleverness

REST (Representational State Transfer) is an architectural style, not a protocol. Its core idea: model your system as resources identified by URLs, and use HTTP's existing verbs and status codes to act on them, instead of inventing your own vocabulary.

The six REST constraints

  1. Client–server. Separate concerns; each can evolve independently.
  2. Stateless. Every request carries everything needed to understand it. No server-side session affinity.
  3. Cacheable. Responses declare whether and for how long they can be reused.
  4. Uniform interface. The same small set of verbs and conventions everywhere — the constraint that makes REST learnable.
  5. Layered system. A client cannot tell whether it is talking to the origin, a proxy or a CDN.
  6. Code on demand (optional). The server may ship executable code to the client.

Interview questions · REST
What makes an API RESTful?

Resource-oriented URLs, correct use of HTTP verbs and status codes, statelessness, cacheable responses, and a uniform interface across the whole API. Most production APIs are Richardson level 2 — which is fine, and saying so shows judgement rather than dogma.

Design endpoints for a blog with posts and comments.

GET /posts (paginated, filterable), POST /posts, GET /posts/{id}, PATCH /posts/{id}, DELETE /posts/{id}, GET /posts/{id}/comments, POST /posts/{id}/comments, and DELETE /comments/{id} — comments get a top-level path for deletion because the id is globally unique and the parent is redundant. Add POST /posts/{id}/publish for the state transition rather than expecting clients to PATCH a status field, so the server owns the rules.

How do you handle an action that isn't CRUD, like "cancel order"?

Two acceptable answers. Model it as a sub-resource action: POST /orders/7/cancel — explicit, and the server enforces which transitions are legal. Or model the state as a field and use PATCH /orders/7 {"status":"cancelled"} — more purist but lets clients attempt illegal transitions, so you validate anyway. Most teams pick the first for anything with side effects such as refunds.

Why is cursor pagination better for a social feed?

Because the underlying data changes constantly. With offset pagination, ten new posts arriving between page 1 and page 2 push everything down, so the user sees repeats. A cursor anchors to a specific row ("give me what comes after post 118"), which is both stable and fast — OFFSET 100000 forces the database to walk and discard 100,000 rows, while a cursor seeks straight into the index.

How do you version an API without breaking existing clients?

Only version on breaking changes; make additive changes instead where possible. When you must break, run /v1 and /v2 side by side, announce a deprecation window, send a Deprecation/Sunset header, monitor per-version traffic, and switch off only when usage approaches zero. Internally, both versions usually call the same service layer with a thin translation at the edge.

Should the API return database IDs?

Sequential integer IDs leak information — competitors can estimate your order volume, and they make enumeration attacks trivial. Prefer UUIDs or opaque public IDs in the API while keeping integer primary keys internally for index efficiency. If you do expose sequential IDs, authorization must be checked on every single object access.

What is HATEOAS and why is it rarely used?

Responses embed links to the next available actions, so the client discovers the API rather than hardcoding URLs. In theory the server can restructure freely. In practice clients hardcode paths anyway, it adds payload size and complexity, and most teams get more value from good documentation (OpenAPI) — so level 2 is the pragmatic stopping point.

How do you keep a list endpoint from becoming a performance problem?

Enforce a default and maximum page size; require an indexed sort key; reject arbitrary ORDER BY from user input; avoid SELECT *; eager-load relations to avoid N+1 queries; and avoid computing an exact COUNT(*) on huge tables — either omit the total, cap it ("1000+"), or use an estimate.

Where do you document an API?

OpenAPI (Swagger) generated from the code so it cannot drift from reality — FastAPI produces it automatically from type hints, and Express can via decorators or JSDoc plugins. The specification also drives client SDK generation and contract tests.

GraphQL, gRPC, WebSockets & SSE

alternatives to REST real-time "why not just REST?"

REST is the default, not the only option. Interviewers ask about these to see whether you choose tools for reasons rather than fashion.

GraphQL

A query language where the client specifies exactly which fields it wants, usually through a single POST /graphql endpoint against a typed schema.

query { user(id: 7) { name orders(last: 3) { total items { productName } } } } # → returns exactly this shape, nothing more, in one round trip
Solves
  • Over-fetching — mobile clients no longer download 40 fields to show 3
  • Under-fetching — no more three sequential REST calls to build one screen
  • A strongly typed, self-documenting, introspectable schema
  • Frontend teams iterate without waiting for new backend endpoints
Costs
  • HTTP caching largely stops working — everything is one POST URL
  • The N+1 problem is severe; you need DataLoader-style batching
  • A malicious deeply nested query can DoS you → need depth/complexity limits
  • Rate limiting and monitoring per-endpoint no longer apply
  • File uploads and error semantics are awkward (errors arrive with HTTP 200)

gRPC

Remote procedure calls over HTTP/2 using Protocol Buffers — a binary, schema-first format. You define a .proto file and both client and server code are generated from it.

service OrderService { rpc GetOrder (GetOrderRequest) returns (Order); rpc StreamUpdates (OrderFilter) returns (stream OrderEvent); } message Order { int64 id = 1; string status = 2; double total = 3; }

Strengths: compact binary payloads (often 5–10× smaller than JSON), fast serialisation, generated clients in many languages, built-in streaming in both directions, and a schema that makes breaking changes visible. Weaknesses: not human-readable, poor browser support without a proxy (grpc-web), harder to debug with curl, and it needs the schema shared between teams. The usual verdict: gRPC for service-to-service traffic inside your system; REST or GraphQL at the public edge.

Interview questions · Alternatives to REST
When would you choose GraphQL over REST?

When many different clients need different shapes of the same data (web, iOS, Android, partners), when screens require data from several resources at once, or when the frontend iterates much faster than the backend can ship endpoints. I would stay with REST when the API is public and needs HTTP caching and CDN support, when the data model is simple, or when the team is small — GraphQL moves complexity from the client to the server rather than removing it.

What is the N+1 problem in GraphQL and how is it fixed?

A query for 50 posts, each with an author, naively runs 1 query for posts plus 50 for authors. The fix is DataLoader batching: resolvers register the ids they need during a tick, and the loader issues a single WHERE id IN (...) query, then distributes the results — and caches within the request. The same problem exists in REST via ORM lazy loading, where the fix is eager loading / a join.

How do you stop a malicious GraphQL query from taking down your server?

Limit query depth, assign a complexity score per field and cap the total, disable introspection in production, use persisted queries so only approved queries are executable, enforce pagination limits on list fields, and apply timeouts. Without these, a recursive query like user { friends { friends { friends ... } } } can explode combinatorially.

Why is gRPC faster than REST+JSON?

Protobuf is binary and schema-driven, so field names are not transmitted and parsing is far cheaper than JSON text parsing. It runs over HTTP/2 with multiplexing and header compression, and connections are long-lived. For chatty internal service-to-service calls the difference is substantial; for a single user-facing request it is usually dwarfed by database time.

WebSocket vs SSE — pick one for a notification feed.

SSE. Notifications flow server → client only, so full duplex is unnecessary. SSE is plain HTTP, so it passes through proxies and load balancers unchanged, supports automatic reconnection with Last-Event-ID resumption for free, and needs no separate protocol handling. WebSockets would add operational complexity for no benefit here.

How do WebSockets complicate horizontal scaling?

Connections are stateful and pinned to one server, so a message for a user connected to server B cannot be delivered by server A. The standard fix is a shared pub/sub backplane — typically Redis pub/sub or a message broker — where every server subscribes and forwards to its own connected sockets. You also need sticky sessions or a connection-aware load balancer, and a plan for redistributing connections during deploys.

How does a WebSocket connection start?

As an ordinary HTTP GET carrying Upgrade: websocket and Connection: Upgrade plus a key. The server replies 101 Switching Protocols, and from that point the same TCP connection carries WebSocket frames instead of HTTP. Because it begins as HTTP, it can share port 443 and pass through most firewalls — and, importantly, you can authenticate during the handshake.

Web servers, threads & the event loop

separates strong candidates event loop reverse proxy blocking = disaster

A "web server" is really two things stacked: a process that accepts TCP connections and parses HTTP, and your application code that decides what to answer. How those two handle many requests at once is the whole story.

Three concurrency models

ModelHowCost per connectionExamples
Process per requestFork a process for each requestMegabytes; very slowClassic CGI (historical)
Thread per requestA pool of OS threads, one blocks per request~1 MB stack + context switchingJava servlets, Django+Gunicorn (sync), Rails
Event loop / asyncOne thread juggles thousands of sockets; waiting tasks are parkedKilobytesNode.js, FastAPI+Uvicorn, nginx, Go (goroutines are similar in spirit)
The key insight

A typical web request spends most of its time waiting — for the database, for another API, for disk. A blocking thread model dedicates an entire OS thread to that waiting, so 200 threads means 200 concurrent requests maximum, most of them idle. An event loop instead registers a callback and moves on, so one thread can hold tens of thousands of waiting connections. Async wins on I/O-bound work; it gives you nothing on CPU-bound work, because there is no waiting to overlap.

How the event loop actually runs

  1. The loop takes the next ready task from the queue and runs it to completion, without interruption.
  2. When that task hits an I/O call, it registers interest with the OS (epoll/kqueue) and returns control immediately.
  3. The loop picks up the next ready task. Nothing waits idly.
  4. When the OS reports the I/O is complete, the continuation is queued and runs on a later turn.
  5. True CPU work — hashing, image processing, large JSON — has no waiting to yield on, so it blocks every other request for its whole duration.
Blocking the loop — the classic production incident

A synchronous bcrypt.hashSync, a 200 ms JSON parse, a tight loop over 10 million records, or a synchronous file read inside a request handler will freeze every concurrent request on that process. The fixes: use the async variant, offload to a worker thread or worker pool, push the job to a queue (C4), or run multiple processes so one stuck loop does not take down the box. In Python the equivalent sin is calling a blocking library inside an async def — use run_in_executor or an async driver.

Why nginx sits in front of your app

A reverse proxy receives client traffic and forwards it to your application. It exists so your app can stay focused on business logic.

  • TLS termination — certificates and encryption handled once, in optimised C.
  • Static files — served from disk without touching your process.
  • Load balancing across several app processes or machines.
  • Buffering slow clients — nginx absorbs a slow upload so your worker is not tied up (this alone defeats Slowloris attacks).
  • Compression, rate limiting, request size limits, header hygiene.
  • Graceful deploys — drain connections from an old instance while a new one warms up.
Middleware — the mental model

Middleware is an onion around your handler. A request passes inward through each layer and the response passes back outward through them in reverse. Order matters enormously: request-id and logging first (so everything downstream is traceable), then CORS, then body parsing and size limits, then authentication, then rate limiting per user, then authorization, then the handler — with the error handler registered last so it catches everything. Putting authentication after an expensive body parse means unauthenticated requests still consume the parse.

Interview questions · Servers & concurrency model
Node.js is single-threaded — how does it serve thousands of users?

Your JavaScript runs on one thread, but I/O does not happen on that thread. Node registers the operation with the OS via libuv and continues; when the OS signals completion, the callback is queued. Because requests spend most of their life waiting on I/O, one thread can interleave thousands. Note that some operations (file I/O, DNS, crypto, compression) do use libuv's internal threadpool of four threads by default.

What exactly happens if you block the event loop?

Every other request on that process stops — not slows, stops — until the blocking work finishes. Health checks fail, latency spikes across the board, and the load balancer may mark the instance unhealthy. The observable symptom is that p99 latency for unrelated fast endpoints explodes.

Async vs multithreading — when does each win?

Async wins for I/O-bound workloads: thousands of concurrent connections mostly waiting, with low memory per connection and no lock contention. Threads (or processes) win for CPU-bound work, since only true parallelism helps there. Real systems combine them: an async server for request handling plus a process pool or job queue for heavy computation.

What is the GIL and how does it affect Python backends?

CPython's Global Interpreter Lock allows only one thread to execute Python bytecode at a time, so threads do not give CPU parallelism — although they still help for I/O, because the GIL is released during blocking calls. The consequence for backends: scale with multiple processes (Gunicorn/Uvicorn workers), use multiprocessing or a task queue for CPU work, and rely on async for I/O concurrency.

Why put nginx in front of Node or Gunicorn?

TLS termination, static asset serving, load balancing across worker processes, buffering slow clients so application workers are not held hostage, compression, connection limits and basic rate limiting — all handled by battle-tested C rather than your application. It also lets you restart the app without dropping connections.

How many worker processes should you run?

A common starting point is one per CPU core for async workers, or (2 × cores) + 1 for synchronous, thread-blocking workers. Then measure: too few leaves CPU idle, too many causes context-switch overhead and, more importantly, multiplies database connections — with 8 workers × 20 pool connections you have 160 connections against a database that may allow 100.

What is middleware and what order should it run in?

Functions that wrap the request/response cycle. Sensible order: request-id → logging → CORS → body parsing with a size limit → authentication → rate limiting → authorization → route handler, with the error handler last. The principle is to reject cheaply and early: check size and identity before doing expensive work.

CORS — what it is and what it is not

Browsers enforce the Same-Origin Policy: JavaScript on https://app.shop.com may not read a response from https://api.other.com. An origin is the triple scheme + host + port, so http://x.com and https://x.com are different origins, as are ports 3000 and 8080.

CORS is the mechanism by which a server opts in to being read across origins, by returning specific headers.

The two misconceptions interviewers probe

1. CORS does not protect your server. It is enforced by browsers only. Curl, Postman, a mobile app and any script ignore it completely. It protects users from a malicious page reading their data from another site — it is not an authorization mechanism. Your API still needs authentication.
2. The request often still reaches your server. For a simple request the browser sends it and then blocks the response from JavaScript. So a cross-origin POST can already have created a row before the error appears in the console — which is exactly why CSRF protection is separate from CORS.

Simple requests vs preflight

Interview questions · Cookies & CORS
What is CORS and why does it exist?

Cross-Origin Resource Sharing is a browser mechanism that lets a server declare which other origins may read its responses, relaxing the Same-Origin Policy. It exists because the browser sends your cookies automatically: without SOP, any site you visit could silently read your bank's API using your logged-in session. CORS is the controlled opt-out.

Does CORS secure my API?

No. Only browsers enforce it. curl, Postman, mobile apps, servers and scripts ignore CORS entirely. It protects the user's browser session from malicious web pages; it does nothing against a direct attacker. Authentication and authorization are what secure the API.

What triggers a preflight request?

Any request that is not "simple": a method other than GET/HEAD/POST, a Content-Type of application/json, or a custom header such as Authorization or X-Request-Id. Since almost every real JSON API request qualifies, preflights are common — which is why setting Access-Control-Max-Age matters for performance.

Why can't you use Access-Control-Allow-Origin: * with credentials?

Because it would let any website make authenticated requests with the user's cookies and read the response — a universal CSRF-plus-data-exfiltration hole. The browser therefore refuses the combination: with Allow-Credentials: true you must echo one specific origin, validated against an allowlist. Reflecting the Origin header blindly is equivalent to * and is a real vulnerability.

Explain HttpOnly, Secure and SameSite.

HttpOnly hides the cookie from JavaScript, so an XSS payload cannot steal the session. Secure restricts it to HTTPS so it never crosses the network in plaintext. SameSite controls whether it accompanies cross-site requests: Strict never, Lax only on top-level GET navigations (the modern default), None always but requiring Secure. Together they neutralise the most common session attacks.

Where should a JWT be stored in a browser?

localStorage is convenient but readable by any script, so a single XSS vulnerability leaks the token. An HttpOnly cookie cannot be read by scripts but is sent automatically, so it needs SameSite and/or CSRF tokens. The common production pattern is a short-lived access token held in memory plus a refresh token in an HttpOnly; Secure; SameSite=Strict cookie scoped to the refresh endpoint.

Are subdomains the same origin?

No — app.shop.com and api.shop.com are different origins and require CORS, even though they are the same site. Cookies follow different rules: a cookie with Domain=.shop.com is shared across subdomains, which is convenient but means a compromised subdomain can read the session cookie. Scope cookies as narrowly as you can.

Interview questions · API design in practice
Where do you validate, and how many times?

Three layers, each for a different reason. Shape validation at the edge (types, required fields, ranges) via zod or Pydantic → 400/422. Business validation in the service (does this product exist, is there stock, is this transition legal) → 404/409. Integrity constraints in the database (NOT NULL, UNIQUE, CHECK, foreign keys) as the last line of defence, because bugs and other services will eventually bypass the application.

A user changes the price in the request body. What happens?

Nothing, because the server never reads a price from the request. It looks up the current price from the database, computes the total itself, and stores that. The general rule: the client may send what it wants (product ids, quantities) but never the values that determine money or permissions.

Two users buy the last item at the same moment. What do you do?

Do the check and the decrement inside one transaction with a row lock — SELECT ... FOR UPDATE — so the second transaction waits and then sees stock 0 and gets a 409. Alternatives: a conditional update (UPDATE products SET stock = stock - 1 WHERE id = ? AND stock >= 1) and check the affected row count, or optimistic locking with a version column. What is not acceptable is a read, an if, and a separate write.

How do you make order creation safe to retry?

An idempotency key: the client sends a UUID header, and the server stores it with a unique constraint alongside the created order. A retry with the same key returns the original order instead of creating a second one. This matters because a timeout tells the client nothing about whether the server succeeded.

Should GET /orders/{id} return 403 or 404 for someone else's order?

404 is usually better: 403 confirms the order exists, which leaks information and enables enumeration. Return 403 only when the user is entitled to know the resource exists but not to act on it. Either way, the ownership filter belongs in the query itself (WHERE id = ? AND user_id = ?), not in an if after fetching.

How would you test this API?

Unit tests on the service layer with the repository mocked — that is where the rules are, and they run in milliseconds. Integration tests against a real database in a container for the repository and transaction behaviour, including the concurrency case. A handful of end-to-end tests over HTTP for auth, the happy path and the main error codes. The layering is what makes the fast tests possible.

The one-line summary examiners want

When to deliberately denormalize

Normalization optimises for write correctness; it costs joins on read. Denormalize consciously, when you can name the query you are speeding up and you have a plan for keeping the copy correct.

  • Historical snapshots — order_items.unit_price, the invoice address at time of purchase. This is not really denormalization: the past is genuinely a different fact from the present.
  • Counters — posts.comment_count instead of COUNT(*) on every page load, updated by a trigger or in the same transaction.
  • Read-model duplication — storing author_name beside author_id for a feed that would otherwise join five tables per row.
  • Reporting tables — a nightly rollup so dashboards never touch the transactional tables.
Schema decisions that come back to bite

Storing money as FLOAT (use DECIMAL or integer cents). Storing timestamps without a timezone (store UTC, convert at the edge). Using VARCHAR for enums with no CHECK constraint. Nullable foreign keys "just in case". Comma-separated lists in a column. No created_at/updated_at. Hard-deleting rows that reports later need — prefer a deleted_at soft delete for user-facing entities.

Interview questions · Data modelling
What is normalization and why do it?

Organising columns and tables so each fact is stored exactly once. The purpose is to eliminate insertion, update and deletion anomalies: when a fact lives in one place, it cannot be updated inconsistently. The cost is more joins on read, which is a fair trade for transactional systems.

Explain 1NF, 2NF and 3NF with one example each.

1NF: a phones column containing "9876,9123" violates atomicity → separate rows in a phones table. 2NF: with key (order_id, product_id), a product_name column depends only on product_id — half the key — so it belongs in products. 3NF: with key employee_id, storing dept_id and dept_name makes dept_name depend on dept_id, a non-key column → move it to departments.

Difference between 3NF and BCNF?

3NF allows a non-key attribute to determine part of a candidate key in some overlapping-key situations; BCNF forbids any determinant that is not itself a candidate key, so it is strictly stronger. It matters only when a table has multiple overlapping candidate keys — rare in practice, common in exams.

Is normalization always right?

No. It optimises writes and correctness; read-heavy systems often denormalize deliberately — cached counters, duplicated display names, materialised rollups. The right answer is that you normalize by default and denormalize with a specific measured query in mind plus a defined strategy for keeping the duplicate in sync.

Primary key vs unique key?

A table has exactly one primary key; it cannot be NULL and it is the default clustering/identity of the row. A table can have many unique keys, and depending on the database they may permit NULLs (Postgres allows multiple NULLs in a unique column, since NULL is not equal to anything). Both create an index and both enforce uniqueness.

How do you model many-to-many? What goes in the junction table?

A separate table holding both foreign keys, with a composite primary key on the pair to prevent duplicates. Crucially, any attribute of the relationship itself lives there too — enrolments(student_id, course_id, enrolled_at, grade). Grade belongs to the pairing, not to the student or the course.

UUID or auto-increment integer for a primary key?

Integers are compact, ordered and index-friendly, but they leak volume and are enumerable. UUIDs can be generated client-side, are safe to expose and merge cleanly across shards, but they are 16 bytes and random v4 values cause index fragmentation on insert. A common compromise: an internal BIGSERIAL primary key plus an external UUID column, or a time-ordered UUID (v7/ULID) to keep inserts sequential.

What does ON DELETE CASCADE do, and when is it dangerous?

Deleting a parent automatically deletes children. Useful for truly owned data such as order items. Dangerous when the child has independent value — deleting a user should probably not silently erase their invoices, which finance and law may require you to keep. Safer options are ON DELETE RESTRICT, SET NULL, or a soft delete.

SQL traps interviewers love

COUNT(*) vs COUNT(col) — the second skips NULLs. NOT IN with NULLs returns nothing; use NOT EXISTS. A WHERE filter on the right table of a LEFT JOIN silently turns it into an inner join — put that condition in the ON clause instead. Aggregates ignore NULLs, so AVG over a column with NULLs divides by the non-null count. NULL = NULL is not true; use IS NULL. And DISTINCT is usually a symptom of an accidental row multiplication from a join, not a fix.

Interview questions · SQL
WHERE vs HAVING?

WHERE filters individual rows before grouping and cannot contain aggregate functions. HAVING filters groups after aggregation and is where aggregate conditions belong. For performance, filter as much as possible in WHERE so fewer rows ever reach the grouping step.

Find the second-highest salary. Now the Nth.

Second: SELECT MAX(salary) FROM employees WHERE salary < (SELECT MAX(salary) FROM employees) — this correctly returns NULL when there is no second value. Nth: SELECT DISTINCT salary FROM employees ORDER BY salary DESC OFFSET N-1 LIMIT 1, or use DENSE_RANK() OVER (ORDER BY salary DESC) and filter on the rank, which also handles ties the way most interviewers intend.

RANK vs DENSE_RANK vs ROW_NUMBER?

For salaries 100, 90, 90, 80: ROW_NUMBER gives 1,2,3,4 (arbitrary among ties); RANK gives 1,2,2,4 (leaves a gap); DENSE_RANK gives 1,2,2,3 (no gap). Choose by whether ties should share a position and whether the next value should skip.

Why is my LEFT JOIN behaving like an INNER JOIN?

Because you filtered the right table in WHERE. Unmatched rows have NULL in every right-hand column, and NULL = 'paid' is not true, so they are discarded. Move the condition into the ON clause: LEFT JOIN orders o ON o.customer_id = c.id AND o.status = 'paid'.

What is a CTE and when do you prefer it to a subquery?

A WITH clause naming an intermediate result. Prefer it when a query has several logical steps, when the same intermediate set is referenced more than once, or for recursive queries such as walking an org chart with WITH RECURSIVE. It is mainly a readability tool; in modern Postgres CTEs are inlined and optimised like subqueries.

DELETE vs TRUNCATE vs DROP?

DELETE removes rows one at a time, can have a WHERE, fires triggers, is logged and is rollback-able. TRUNCATE deallocates whole pages: much faster, no WHERE, usually resets identity sequences, and generally does not fire row triggers. DROP removes the table definition itself.

UNION vs UNION ALL?

UNION removes duplicates, which requires a sort or hash and therefore costs time. UNION ALL just concatenates. If you know the sets are disjoint — and you usually do — use UNION ALL.

How would you find and remove duplicate rows keeping the oldest?

Find them with GROUP BY email HAVING COUNT(*) > 1. Remove with a window function: DELETE FROM users WHERE id IN (SELECT id FROM (SELECT id, ROW_NUMBER() OVER (PARTITION BY email ORDER BY created_at) rn FROM users) t WHERE rn > 1). Then add a UNIQUE constraint so the problem cannot recur — cleaning without constraining is treating the symptom.

Indexing & query performance

the "make it faster" question B-tree EXPLAIN N+1

An index is a sorted, secondary data structure that lets the database find rows without reading the whole table. It is the single highest-leverage backend optimisation, and also the one most often applied blindly.

How a B-tree index works, in three sentences

Keys are stored sorted in a balanced tree whose leaves point at rows. Finding a value walks from root to leaf — about 3–4 disk reads for millions of rows, versus scanning every page. Because the leaves are linked and sorted, the same index also serves ORDER BY, range scans (BETWEEN, >, <) and prefix matches (LIKE 'abc%').

The leftmost-prefix rule — the most-asked index question

An index on (user_id, status, created_at) can serve queries filtering on user_id, on user_id + status, or on all three. It cannot serve a query filtering on status alone, because the index is sorted by user_id first — like a phone book sorted by surname is useless for finding everyone named "Asha". Order the columns by equality filters first, then range filters, then sort columns.

Why an index gets ignored

  • A function wraps the column: WHERE LOWER(email) = 'a@b.com' cannot use an index on email — create an expression index on LOWER(email) instead, or store the value normalised.
  • Leading wildcard: LIKE '%son' has no prefix to seek on. Use full-text search or a trigram index.
  • Type mismatch: comparing a VARCHAR column to a number forces a cast on every row.
  • Low selectivity: an index on a boolean where 90% of rows are true is worse than a scan — reading index then jumping to random table rows costs more than reading sequentially.
  • Stale statistics: the planner estimates using statistics; after a bulk load, run ANALYZE.

Indexes are not free

Every index must be updated on every INSERT, UPDATE and DELETE, and it consumes storage and memory. A table with twelve indexes has slow writes. Remove unused ones (Postgres exposes usage counts in pg_stat_user_indexes), and remember that an index on (a, b) already covers queries on a, so a separate index on a alone is redundant.

Interview questions · Performance
What is an index and what does it cost?

A sorted secondary structure — usually a B-tree — mapping column values to row locations, so lookups become O(log n) tree descents instead of a full scan. The cost is slower writes (every index is maintained on every change), extra storage, and more memory pressure. So index the columns you filter, join and sort on, and no more.

A query got slow in production. Walk me through your process.

Reproduce and measure with EXPLAIN ANALYZE rather than guessing. Look for sequential scans on large tables, estimates far off from actuals, and nested loops with high loop counts. Then in order: can I filter earlier or select fewer columns; is there a missing or wrong-ordered index; is this actually N+1 from the application; would a cache be appropriate; do I need pagination limits. Only after that consider read replicas or denormalization.

Why did the database ignore my index?

Common causes: a function or cast applied to the column, a leading wildcard in LIKE, a mismatched data type, low selectivity so a scan is genuinely cheaper, stale statistics, or a composite index whose leading column is not in the predicate. The planner is usually right — check whether a scan is truly the cheaper plan before assuming a bug.

Explain the leftmost-prefix rule.

A composite index on (a, b, c) is sorted by a, then b within equal a, then c. So it serves predicates on a, a+b and a+b+c, but not b alone or c alone. A range condition also "stops" the usefulness of later columns: with a = 1 AND b > 5 AND c = 3, the index can seek on a and b, but c only filters.

What is a covering index?

An index that contains every column the query needs, so the database answers entirely from the index without visiting the table — an "index-only scan". It can be dramatically faster because it avoids random heap lookups. In Postgres you add non-key columns with INCLUDE; in MySQL/InnoDB you simply put them in the index.

Clustered vs non-clustered index?

A clustered index defines the physical order of the rows themselves, so there is only one per table — in InnoDB it is the primary key, and every secondary index stores the primary key as its pointer. A non-clustered index is a separate structure pointing back at rows. Postgres has no clustered index in this sense; its tables are heaps, with an optional one-off CLUSTER command.

What is the N+1 problem and how do you detect it?

Fetching a list with one query and then issuing one additional query per item, usually via ORM lazy loading. Detect it by logging query counts per request, or by watching a plan full of tiny repeated queries. Fix with eager loading (select_related/selectinload/include) or by batching ids into a single WHERE id IN (...). A good habit is a test that asserts an endpoint issues a bounded number of queries.

Why is OFFSET 100000 slow?

The database still has to produce and discard the first 100,000 rows before returning the next page — the work grows linearly with the page number. Cursor (keyset) pagination replaces it with WHERE id < :last_seen ORDER BY id DESC LIMIT 20, which seeks directly into the index and is constant time regardless of depth.

How do you add an index to a huge live table safely?

A plain CREATE INDEX takes a write lock for the duration, which on a large table means an outage. Use CREATE INDEX CONCURRENTLY in Postgres, or an online DDL tool (gh-ost, pt-online-schema-change) in MySQL. Build during low traffic, monitor replication lag, and be ready to drop and retry, since concurrent builds can fail and leave an invalid index.

The race condition every interviewer uses

Stock = 1. Two users check out simultaneously. T1: SELECT stock FROM products WHERE id=5 → 1 T2: SELECT stock FROM products WHERE id=5 → 1 ← both saw 1 T1: if (1 >= 1) UPDATE ... four correct fixes — know at least three
-- FIX 1: pessimistic lock. The second transaction BLOCKS until the first commits.
BEGIN;
  SELECT stock FROM products WHERE id = 5 FOR UPDATE;   -- row is now locked
  -- application checks stock >= qty
  UPDATE products SET stock = stock - 1 WHERE id = 5;
  INSERT INTO orders (...) VALUES (...);
COMMIT;                                                  -- lock released

-- FIX 2: conditional update. No explicit lock; let the DB decide atomically.
UPDATE products SET stock = stock - 1
WHERE id = 5 AND stock >= 1;
-- rows affected = 0  ->  someone beat us  ->  return 409
-- This is often the best answer: one statement, no lock held across app logic.

-- FIX 3: optimistic locking with a version column. Great for low contention
-- and for long "think time" like an edit form.
UPDATE products SET stock = stock - 1, version = version + 1
WHERE id = 5 AND version = 7;
-- rows affected = 0  ->  somebody changed it  ->  reload and retry

-- FIX 4: SERIALIZABLE isolation. The DB detects the conflict and aborts one
-- transaction with a serialization failure, which you MUST catch and retry.
BEGIN ISOLATION LEVEL SERIALIZABLE;
  ...
COMMIT;
Pessimistic vs optimistic — the deciding question

How likely is a conflict? High contention (flash-sale stock, seat booking) → pessimistic: take the lock, since retrying constantly is worse than waiting briefly. Low contention (a user editing their own profile) → optimistic: no lock, detect the rare clash with a version check and ask the user to refresh. Also note that a pessimistic lock must be held for as short a time as possible — never across a network call to a payment provider.

Transaction anti-patterns

Long transactions. Holding one open while calling an external API means locks are held for the duration of someone else's outage. Do external work outside the transaction, or use the outbox pattern (C4).
Inconsistent lock order. T1 locks A then B while T2 locks B then A → guaranteed deadlock. Always acquire in a deterministic order.
Doing business logic between the read and the write without a lock — that gap is the race.
Assuming a rollback undoes side effects. The database rolls back; the email you already sent does not.

Interview questions · Transactions
Explain ACID with an example.

Bank transfer of ₹100. Atomicity: debit and credit both happen or neither does — a crash in between cannot lose the money. Consistency: the constraint that balances cannot go negative holds before and after. Isolation: a concurrent balance check never sees the money missing from both accounts. Durability: once the commit is acknowledged, a power cut cannot undo it, because the write-ahead log was flushed first.

What are the isolation levels and which is the default?

READ UNCOMMITTED, READ COMMITTED, REPEATABLE READ, SERIALIZABLE, in increasing strictness and cost. PostgreSQL and Oracle default to READ COMMITTED; MySQL/InnoDB defaults to REPEATABLE READ; SQL Server defaults to READ COMMITTED. Higher levels prevent more anomalies but increase blocking and the chance of aborted transactions you must retry.

Dirty read vs non-repeatable read vs phantom read?

Dirty read: you see uncommitted data that may be rolled back. Non-repeatable read: the same row read twice gives different values because another transaction committed an update. Phantom read: the same query run twice returns a different set of rows because new rows were inserted. The progression is row-level then set-level.

Two users book the last seat simultaneously. Prevent it.

Make the check and the write one atomic operation. Simplest: a conditional update — UPDATE seats SET booked = true WHERE id = ? AND booked = false — and treat zero affected rows as "taken", returning 409. Alternatively SELECT ... FOR UPDATE inside a transaction, or a unique constraint on (show_id, seat_no) in the bookings table so the database rejects the duplicate outright. A database constraint is the most robust because it holds even if a future code path forgets the check.

What is a deadlock and how do you handle it?

Two transactions each hold a lock the other needs, so neither can proceed. The database detects the cycle and kills one, returning an error. Prevention: acquire locks in a consistent global order, keep transactions short, touch as few rows as possible, and use lower isolation where safe. Handling: catch the deadlock error and retry with exponential backoff and jitter — deadlocks are expected occurrences under load, not necessarily bugs.

What is MVCC?

Multi-Version Concurrency Control: instead of blocking readers, the database keeps multiple versions of each row and shows each transaction a consistent snapshot as of its start. The huge practical benefit is that readers never block writers and writers never block readers. The cost is storage for old versions and the need to reclaim them — Postgres's VACUUM, and the bloat problems that follow long-running transactions holding old snapshots open.

Optimistic vs pessimistic locking — pick one for an editing form.

Optimistic. A user may keep a form open for minutes, and holding a database lock that long would block everyone. Attach a version number or ETag to the form; on submit, update WHERE version = :loaded_version. If zero rows change, someone else saved first — show a conflict message rather than silently overwriting their work.

Can you use a transaction across two different services or databases?

Not with ordinary ACID guarantees. Two-phase commit exists but is fragile and blocking. The practical approach is the saga pattern: a sequence of local transactions where each step has a compensating action to undo it, combined with the outbox pattern so that publishing an event and committing the data happen in a single local transaction. This is the standard microservices answer (D3, D4).

CAP, stated correctly

In a distributed system you may guarantee at most two of Consistency (every read sees the latest write), Availability (every request gets a non-error response), and Partition tolerance (the system keeps working when the network splits).

The nuance that separates a real answer from a memorised one

Partitions are not optional. Networks fail; if you run more than one machine you must tolerate partitions. So CAP is not "pick two" — it is: when a partition happens, do you choose consistency or availability? CP systems (HBase, MongoDB with majority writes, etcd, ZooKeeper) refuse to answer rather than answer wrongly. AP systems (Cassandra, DynamoDB in default mode, Riak) answer with possibly stale data and reconcile afterwards.

PACELC extends it usefully: if there is a Partition, choose A or C; Else — in normal operation — choose between Latency and Consistency. That "else" branch is where most real systems actually live, because partitions are rare but latency is constant.

Interview questions · NoSQL & CAP
Explain the CAP theorem.

Under a network partition, a distributed system cannot be both consistent and available — it must either refuse requests to avoid serving stale data (CP) or serve possibly stale data to remain up (AP). Since partitions cannot be avoided, the practical framing is that CAP describes your behaviour during a partition, not a menu of three from which you pick two.

What does "eventually consistent" mean, and give an example where it is acceptable.

If writes stop, all replicas converge to the same value after some time — but a read immediately after a write may return an older value. Acceptable for a like count, a view counter, a follower list or a search index, where being a second behind is invisible. Unacceptable for account balances, seat inventory or anything where a stale read lets a user do something illegal.

Is MongoDB ACID?

Single-document operations have always been atomic. Since version 4.0 it also supports multi-document transactions across replica sets and, since 4.2, sharded clusters. But they are more expensive than in a relational engine and are meant to be an exception rather than the normal access pattern — the idiomatic approach is to design documents so that things which change together live together.

Would you use NoSQL for a banking system?

Not for the ledger. Money requires multi-row atomic transactions, strong consistency and strict constraints — exactly what relational engines provide. NoSQL fits the surrounding workloads: Redis for sessions and rate limiting, Cassandra or a time-series store for transaction event streams and audit logs, Elasticsearch for search. Core correctness stays in SQL.

How does Cassandra scale writes so well?

It is masterless: every node can accept writes, and data is distributed by a partition key using consistent hashing. Writes go to an append-only commit log and an in-memory memtable, later flushed as immutable SSTables — sequential I/O, no read-before-write. The trade-offs are tunable consistency per query, no joins, and the requirement to model tables around the queries you will run rather than around entities.

What is a partition key and why does choosing it matter?

It determines which node stores the data. A poor choice creates hot partitions — for example partitioning by date puts all of today's traffic on one node, and partitioning by country puts most traffic on one. Good keys are high-cardinality and evenly distributed, and they align with your most common query so it can be answered from a single partition.

Redis is called a database and a cache. Which is it?

An in-memory data-structure store that can be either. As a cache you set TTLs and accept loss. As a database you enable persistence — RDB snapshots, AOF append-only logging, or both — and replication. Even then, its durability is weaker than a disk-first database, so it is normally used for data you can rebuild: sessions, rate-limit counters, leaderboards, queues, and cached query results.

ORMs: what they buy and what they cost

An Object–Relational Mapper maps tables to classes so you write user.orders instead of SQL. Two common designs: Active Record (the model knows how to save itself — Django ORM, Sequelize, Rails) and Data Mapper (a separate layer moves data between objects and tables — SQLAlchemy, TypeORM, Hibernate).

Worth it for
  • CRUD boilerplate and result mapping
  • Automatic parameterisation → SQL injection largely gone
  • Migrations and schema versioning
  • Portability across databases
  • Relationships and transaction helpers
Costs you must name
  • N+1 queries from lazy loading (B3)
  • Generated SQL can be badly shaped for complex reports
  • A leaky abstraction — you still must understand the SQL underneath
  • Hidden cost: one innocent attribute access can hit the database

The professional position: use the ORM for the 90% that is CRUD, and drop to raw SQL for reports, bulk operations and anything performance-critical — every serious ORM supports it.

Connection pooling — why it exists

Opening a database connection costs a TCP handshake, authentication and server-side memory: tens of milliseconds and megabytes each. Databases also cap total connections (Postgres commonly around 100). A pool keeps a fixed set of connections open and lends them out for the duration of a query.

Without a pool: 1000 req/s × 30 ms setup = the DB spends its life authenticating With a pool: 20 connections serve 1000 req/s because each query holds one for ~5 ms Sizing trap: 8 app instances × pool of 25 = 200 connections against a DB that allows 100 → half your app cannot connect Rule of thumb: total pool size across ALL instances < max_connections, with headroom. For very high instance counts, put PgBouncer in front and pool the poolers.

Migrations: changing a schema without downtime

A migration is a versioned, ordered, reviewable script that changes the schema — alembic, knex, prisma migrate, Django migrations. Never edit a production schema by hand: migrations must be in version control alongside the code that depends on them.

The expand–contract pattern (a strong answer to "how do you rename a column with zero downtime?")

You cannot rename in one step, because old and new code run simultaneously during a rolling deploy. Instead:

  1. Expand — add the new column, nullable. Old code is unaffected.
  2. Dual-write — deploy code that writes both columns and reads the old one.
  3. Backfill — copy existing data in batches, so you do not lock the table for minutes.
  4. Switch reads — deploy code that reads the new column.
  5. Contract — after a safe period, stop writing and drop the old column.

The same pattern applies to splitting tables, changing types and moving data between services. Every step is independently reversible, which is the real point.

Migrations that cause outages

ADD COLUMN ... NOT NULL DEFAULT on an old database version rewrites the whole table under a lock. Adding an index without CONCURRENTLY blocks writes for the duration. A backfill in a single statement holds one enormous transaction. Adding a foreign key validates every existing row while holding a lock — add it NOT VALID first, then validate separately. Always ask: what does this lock, and for how long?

Interview questions · ORMs & operations
Why use an ORM, and when would you not?

Use it to remove CRUD boilerplate, get safe parameterisation, and manage migrations. Skip it for complex analytical queries, bulk operations, and hot paths where the generated SQL is inefficient — write raw SQL there. The failure mode is not using an ORM but using it without knowing what SQL it produces.

What is a connection pool and how do you size it?

A reusable set of open database connections, so requests borrow rather than reconnect. Size it by the concurrency you actually need, remembering it multiplies by instance count: total connections across all app processes must stay under the database's limit with headroom for admin access and replicas. A pool that is too large simply moves queueing from your app into the database, where it is more damaging.

The app hangs but the database looks idle. What is wrong?

Pool exhaustion. Requests are blocked waiting to borrow a connection. Usual causes: a connection leaked because it was never released on an error path, a transaction left open, a long-running query holding one hostage, or a pool sized far below concurrency. Fix by using context managers or finally blocks, setting statement timeouts, and monitoring pool wait time as a first-class metric.

How do you rename a column with no downtime?

Expand–contract: add the new column, deploy code that writes both, backfill in batches, deploy code that reads the new one, then drop the old column in a later release. A direct rename breaks whichever version of the application is not yet deployed, and during a rolling deploy both versions are running.

How do you roll back a bad migration?

Additive changes are easy to reverse. Destructive ones often are not — dropping a column loses data permanently, so the real strategy is to make migrations backwards-compatible so a code rollback alone is enough, and to defer destructive steps until the new code has been stable for a while. Always take a backup before a destructive migration, and test it against a production-sized copy.

Lazy loading vs eager loading?

Lazy loading fetches a relation when you first touch it — convenient, and the direct cause of N+1 queries. Eager loading fetches it up front with a join or a batched IN query. Use eager loading whenever you know you will need the relation, especially inside a loop or a serializer.

Salt, pepper and work factor

A salt is a unique random value per password, stored alongside the hash. Anatomy of a JWT

header.payload.signature ← three base64url parts joined by dots header {"alg":"HS256","typ":"JWT"} payload {"sub":"1234","role":"admin","iat":1712,"exp":1715} signature HMAC-SHA256(base64(header) + "." + base64(payload), SECRET) CRITICAL: the payload is base64-ENCODED, not encrypted. Anyone can read it. Never put a password, card number or PII in it. The signature proves it was not TAMPERED with — not that it is secret.
JWT mistakes that fail interviews (and audits)

Accepting alg: none or letting the token choose the algorithm — always pin the expected algorithm server-side. A weak secret — HS256 with "secret123" is brute-forceable offline. Long expiry — a 30-day access token cannot be revoked when a laptop is stolen. Storing tokens in localStorage — readable by any XSS payload. Trusting a role claim forever — if you demote a user, their existing token still says admin until it expires. Decoding without verifying — jwt.decode is not jwt.verify.

Access token + refresh token: the standard pattern

  1. Access token: JWT, short-lived (5–15 minutes), sent on every request. If stolen, its usefulness expires quickly.
  2. Refresh token: long-lived (days/weeks), opaque and random, stored server-side so it can be revoked, and kept in an HttpOnly; Secure; SameSite=Strict cookie scoped to the refresh endpoint only.
  3. When the access token expires, the client calls POST /auth/refresh and receives a new pair.
  4. Rotate refresh tokens on each use, and invalidate the old one. If an already-used refresh token appears again, it was stolen — revoke the entire family and force re-login.
  5. Logout deletes the refresh token server-side; the access token dies naturally within minutes.

Interview questions · Auth
Authentication vs authorization?

Authentication verifies identity (a token, a password, a biometric) and maps to 401 when it fails. Authorization verifies permission for a specific action on a specific resource, and maps to 403. Authentication happens once per request in middleware; authorization must be re-checked at every resource access, because a valid token says nothing about whether this user may touch this row.

How do you store passwords?

With a slow, salted, memory-hard hash — bcrypt at cost 12+, or argon2id. Never plain text, never reversible encryption, and never a fast general-purpose hash like SHA-256, because GPUs test billions of those per second. The salt must be unique per user so identical passwords produce different hashes.

Why not just increase SHA-256 rounds instead of using bcrypt?

You can (that is essentially PBKDF2), but bcrypt and especially argon2 are also memory-hard, which specifically defeats GPU and ASIC parallelism — thousands of cores cannot each hold a large memory buffer. They also have a tunable cost factor stored in the hash itself, so you can raise it over time and upgrade hashes transparently at the user's next login.

Explain JWT structure and what the signature guarantees.

Header, payload and signature, base64url-encoded and dot-separated. The signature is an HMAC (or an RSA/ECDSA signature) over the first two parts, so anyone can read the payload but nobody without the key can change it and still produce a valid signature. It guarantees integrity and authenticity, not confidentiality — which is why secrets must never go in the payload.

How do you log out or revoke a JWT?

You cannot un-sign a token, so you need a strategy: keep access tokens very short-lived and revoke the long-lived refresh token server-side; or maintain a denylist of revoked token ids (jti) in Redis with a TTL equal to the remaining lifetime; or store a tokenVersion per user in the token and bump it on logout so all outstanding tokens fail validation. The first is the usual choice, because it keeps the common path stateless.

Sessions or JWT — which would you choose for a web app?

For a single-domain browser app I would choose server-side sessions in Redis with an HttpOnly cookie: instant revocation, tiny requests, and no token-storage dilemma. JWTs earn their complexity when you have multiple services or mobile clients that must validate identity without a shared session store, or when a third party must verify tokens using a public key.

Why does the login response say "invalid credentials" instead of "wrong password"?

To prevent user enumeration. A distinct "no such account" message tells an attacker which emails are registered, which is valuable for credential stuffing and phishing. For the same reason you should compare against a dummy hash when the user does not exist, so response timing does not leak the answer either.

What is OAuth and what does it actually solve?

Delegated authorization: an application obtains limited, scoped, revocable access to a user's data at another service without handling their password. The Authorization Code flow with PKCE is the correct one for web and mobile; the implicit flow is deprecated because it exposed tokens in the URL. Adding OpenID Connect turns it into authentication as well, via the id_token.

What is the state parameter for in OAuth?

It is an unguessable value your app generates before the redirect and verifies when the provider redirects back. It proves the callback corresponds to a flow this browser started, defeating CSRF attacks where a victim is tricked into completing an attacker-initiated login and ends up with the attacker's account linked to their session.

How do you implement "user can only see their own orders"?

Put the ownership condition in the query — SELECT ... WHERE id = :id AND user_id = :me — rather than fetching and checking afterwards. It cannot be forgotten on one code path, it avoids a needless read, and returning 404 for a non-matching row also avoids confirming that the order exists. Centralise it in the repository layer so every query for that resource is scoped by default.

Rate limiting algorithms — a common follow-up

Fixed window: count per minute; simple, but allows a double burst at the boundary. Sliding window log: store timestamps and count those inside the window; exact, but memory-heavy. Sliding window counter: weighted blend of the current and previous window; the usual production compromise. Token bucket: tokens refill at a fixed rate and each request consumes one — allows controlled bursts, and is what most APIs and Redis implementations use. Leaky bucket: a fixed drain rate, smoothing traffic completely. Whichever you pick, the counters must live in Redis rather than process memory, or each instance enforces its own separate limit.

Interview questions · Security
What is SQL injection and how do you prevent it?

Untrusted input concatenated into a query so it is parsed as SQL rather than data, allowing authentication bypass, data theft or destruction. The fix is parameterised queries or an ORM that parameterises for you: the statement is compiled before the values are bound, so input can never change the structure. Additional layers: least-privilege database accounts, input validation, and allowlists for any identifier you must interpolate.

XSS vs CSRF — the difference in one line each?

XSS: the attacker gets their code running on your page, so they can read anything the user can see. CSRF: the attacker gets the user's browser to make a request they did not intend, without ever reading the response. XSS is defeated by output escaping and CSP; CSRF by SameSite cookies and CSRF tokens. Note that XSS defeats CSRF tokens, so XSS is the more severe of the two.

Is a token-based API vulnerable to CSRF?

Not if the token is sent in an Authorization header, because browsers do not attach headers automatically to cross-site requests — the attacker's page would have to read the token, which the same-origin policy prevents. But if you store the JWT in a cookie that is sent automatically, you are back to being CSRF-vulnerable and need SameSite or CSRF tokens.

What is IDOR and how do you systematically prevent it?

Insecure Direct Object Reference: the server uses a client-supplied identifier without verifying the requester may access that object, so changing /orders/1001 to /orders/1002 reveals someone else's data. Prevent it structurally: scope every query by the authenticated user in the repository layer, so it is the default rather than a check someone might forget; use unguessable identifiers as defence in depth; and add tests that assert cross-user access returns 404.

What is mass assignment?

Binding the entire request body onto a model, so a user can set fields you never intended to expose — role, is_verified, balance. The fix is an explicit allowlist or a dedicated input DTO containing only the updatable fields, with unknown fields rejected rather than silently ignored.

How do you store API keys and secrets?

Never in source control. Use environment variables injected at deploy time, or a secret manager (AWS Secrets Manager, Vault) with rotation and audit logging. Validate that all required secrets exist at startup so misconfiguration fails immediately rather than at 3 a.m. For keys you issue to your users, store only a hash — you should be unable to recover the key, exactly as with passwords.

How do you rate limit across many servers?

Keep counters in a shared store — typically Redis with an atomic INCR plus EXPIRE, or a Lua script for a token bucket so the read-modify-write is atomic. In-process counters would give each instance its own budget, so ten instances means ten times the intended limit. Key by user id where authenticated and by IP otherwise, and return 429 with Retry-After.

What is SSRF and why is it dangerous in the cloud?

Server-Side Request Forgery: you accept a URL and fetch it, and an attacker points it at internal infrastructure. In cloud environments the classic target is the instance metadata endpoint at 169.254.169.254, which can return temporary IAM credentials — turning a "fetch this image" feature into full account compromise. Defend with a destination allowlist, blocking private and link-local IP ranges after DNS resolution, disabling redirects, and using IMDSv2.

Why should error responses be generic?

Stack traces, SQL fragments, framework versions and file paths hand attackers a map of your system and often reveal exactly which injection to try next. Return a generic message plus a request id to the client, and put the full detail in your logs where only you can see it.

Caching

"make it faster" cache-aside TTL invalidation

Caching trades freshness for speed. Every cache decision is really a decision about how stale you can afford to be — so the first question is never "should I cache?" but "how wrong may this be, and for how long?".

Where caches live

BrowserGoverned by Cache-Control, ETag. Free, but you cannot invalidate it — which is why asset filenames contain content hashes.
CDN / edgeStatic assets and cacheable API GETs served from a nearby PoP. Purgeable, absorbs enormous read traffic.
Application memoryFastest possible, but per-process — so it is inconsistent across instances and lost on restart. Good for config and reference data.
Distributed cache (Redis / Memcached)Shared across all instances, survives deploys, supports TTLs and rich structures. The default meaning of "add a cache".
DatabaseBuffer pool, query plan cache, materialised views. Mostly automatic, but worth knowing it exists.

Invalidation — the genuinely hard part

The three classic cache failures

Cache stampede (thundering herd). A popular key expires and 5,000 concurrent requests all miss and all hit the database at once — often taking it down. Fixes: a short-lived lock so only one request recomputes while the rest wait or serve stale; probabilistic early expiry; or refreshing hot keys in the background before they expire.
Cache penetration. Requests for keys that do not exist anywhere always miss and always reach the database — trivially weaponised. Fix: cache the negative result with a short TTL, or use a Bloom filter.
Cache avalanche. Many keys were populated together and therefore expire together. Fix: add random jitter to every TTL.

  const key = `product:${id}`;

  const cached = await redis.get(key);
  if (cached !== null) {
    return cached === "__MISSING__" ? null : JSON.parse(cached);  // negative cache
  }

  const lockKey = `lock:${key}`;
  const gotLock = await redis.set(lockKey, "1", { NX: true, EX: 10 });
  if (!gotLock) {
    await sleep(50);
    return getProduct(id);                    // others retry, cache is warm by then

    const product = await db.products.findById(id);

      return null;
    }
    await redis.set(key, JSON.stringify(product), { EX: ttl });
    return product;

    await redis.del(lockKey);

Interview questions · Caching
What would you cache, and what would you never cache?

Cache expensive, frequently read, rarely changing data: product details, user profiles, computed aggregates, rendered fragments, reference lists. Never cache anything where a stale read is a correctness bug — account balances, stock counts at checkout, permission decisions — and never cache per-user data under a shared key, which is how one user ends up seeing another's dashboard.

Explain cache-aside.

On read: check the cache; on a hit, return; on a miss, read the database, write it into the cache with a TTL, and return. On write: update the database and delete the key. The application owns the logic, only requested data occupies memory, and a cache outage degrades performance rather than causing an outage.

Why delete the cache key on update instead of updating it?

Because updating races. A concurrent read that missed just before your write can complete afterwards and put the old value back, leaving a stale entry with a full TTL. Deleting means the next read recomputes from the source of truth. For extra safety under heavy write load you can delete, write to the database, then delete again after a short delay.

What is a cache stampede and how do you prevent it?

A hot key expires and every concurrent request misses simultaneously, sending a flood of identical queries to the database. Prevent it with a mutex so only one request recomputes while others wait or serve the stale value, with probabilistic early recomputation so expiry is staggered, or by refreshing hot keys in the background before they expire.

How do you choose a TTL?

From the business tolerance for staleness, not from a habit. A trending feed can be 30 seconds; a product page a few minutes; a list of countries a day. Then add jitter so keys created together do not expire together. If nothing can be stale, do not use a TTL — use explicit invalidation on write, and accept the extra coupling.

Your cache hit rate is 40%. Is that a problem?

It depends what is missing. A low hit rate with a long tail of rarely repeated keys is normal and caching may simply be the wrong tool. But if hot keys are missing, the likely causes are a TTL that is too short, memory pressure causing eviction, keys that are too specific (including a timestamp or a request id), or over-eager invalidation. Measure hit rate per key prefix, not globally.

Redis vs Memcached?

Memcached is a simple, multithreaded string cache — excellent at exactly that. Redis adds data structures (lists, sets, sorted sets, hashes, streams), persistence, replication, pub/sub, Lua scripting and atomic operations, which lets it serve as a rate limiter, leaderboard, queue and lock manager as well as a cache. Redis is the default choice today; Memcached still wins on raw simplicity for a pure key–value cache.

What happens if Redis goes down?

With cache-aside, every request falls through to the database — so the question is whether the database can survive the full load. Mitigate with a short in-process fallback cache, circuit breaking so a dead Redis fails fast instead of adding latency to every request, and load shedding. If losing the cache means an outage, then it is not a cache, it is a database, and it needs replication and persistence accordingly.

Delivery guarantees — the exam question

At-most-once: acknowledge before processing. Fast, but a crash loses the message. At-least-once: acknowledge after processing. Nothing is lost, but a crash between the work and the ack causes a redelivery — this is what almost every system uses. Exactly-once is not achievable end-to-end in a distributed system in the general case; what you actually build is at-least-once delivery plus an idempotent consumer, which is indistinguishable from exactly-once in its effects. Saying it that way is the answer interviewers are listening for.

The outbox pattern

A subtle and impressive answer to "how do you make sure the database write and the queue publish both happen?"

The problem — two systems, no shared transaction: 1. INSERT order ✔ committed 2. publish "order.created" ✘ broker unreachable → the order exists but nothing downstream ever hears about it. (Reversing the order is no better: you may publish an event for an order whose transaction then rolls back.) The fix — make the publish part of the SAME database transaction: BEGIN INSERT INTO orders ... INSERT INTO outbox (topic, payload, created_at) VALUES ('order.created', ...) COMMIT ← atomic: both rows, or neither A separate poller (or change-data-capture, e.g. Debezium) reads the outbox, publishes to the broker, and marks rows as sent. Publishing may happen twice, so consumers must be idempotent — which they already had to be.
Interview questions · Async work
Why use a message queue at all?

To decouple producers from consumers in time and in availability. The request returns immediately, slow work happens elsewhere, traffic spikes are absorbed by the queue instead of overwhelming a downstream service, failures are retried automatically, and workers scale independently of web servers. The costs are eventual consistency and more moving parts to operate.

What happens if a worker crashes mid-job?

With late acknowledgement, the broker never received an ack, so after a visibility timeout the message is redelivered to another worker. That is why jobs must be idempotent — the crash may have occurred after the side effect but before the ack, so the work may be repeated. With early acknowledgement the message would simply be lost.

How do you make a consumer idempotent?

Give every message a stable key and record processed keys in a table with a unique constraint, returning early if the insert conflicts. Alternatively make the operation naturally idempotent — UPDATE ... SET status='paid' rather than balance = balance + 100 — or use conditional updates that only apply if the current state matches what you expect.

What is a dead-letter queue?

A separate queue for messages that failed every retry. It stops one poisonous message from blocking the pipeline forever while preserving it for investigation. Operationally you alert on DLQ depth, inspect the payload and error, fix the cause, then replay the messages back onto the main queue.

Kafka or RabbitMQ for order processing?

If one service consumes each order to do a task, RabbitMQ or SQS is simpler and gives per-message acknowledgement and easy DLQs. If several services must independently react to "order placed" — inventory, billing, analytics, notifications — and you may want to replay history or add a new consumer that reprocesses the past, Kafka's retained log is the better fit. The deciding question is whether events have one consumer or many.

How do you guarantee ordering?

Only within a partition or a single-consumer queue. In Kafka, messages with the same key go to the same partition and are ordered there — so keying by order_id keeps that order's events sequential while allowing parallelism across orders. With multiple concurrent consumers on one queue, ordering is lost, so design handlers to be order-independent or use a version number and discard stale updates.

Explain the outbox pattern and the problem it solves.

You cannot atomically commit a database write and publish to a broker, so a crash between them leaves the two systems inconsistent. The outbox pattern writes the event into an outbox table inside the same transaction as the data change, making them atomic. A poller or change-data-capture process then publishes those rows and marks them sent. It converts a distributed-transaction problem into a local one, at the cost of possible duplicate publishes.

How do you schedule recurring work?

A scheduler enqueues jobs on a cron expression — Celery Beat, BullMQ repeatable jobs, or a Kubernetes CronJob. The important detail is that with multiple instances you need a distributed lock or a leader election, or every instance fires the same job. Also make scheduled jobs idempotent and give them a maximum runtime, so an overrun does not overlap with the next tick.

Race conditions

A race condition exists whenever the result depends on timing between concurrent operations. The classic form is a read-modify-write that is not atomic.

Two requests increment a view counter that is currently 100: A: read 100 B: read 100 ← both read the same value A: compute 101 B: compute 101 A: write 101 B: write 101 ← one increment lost The critical section is the whole read-modify-write, not just the write. Fixes, in order of preference: 1. Make it atomic in the store: UPDATE posts SET views = views + 1 WHERE id=7 or Redis INCR 2. Lock the row: SELECT ... FOR UPDATE inside a transaction 3. Optimistic version check: UPDATE ... WHERE version = 7 4. Application-level mutex ← only works within ONE process. Rarely enough.
The mistake candidates make

Reaching for an in-process mutex to fix a race in a web application. With four instances behind a load balancer you have four independent mutexes and no mutual exclusion at all. In a distributed system, correctness must be enforced where the shared state lives — in the database, or in Redis with an atomic operation — not in application memory.

async function withLock(key, ttlMs, fn) {

Interview questions · Concurrency
Concurrency vs parallelism?

Concurrency is structuring a program so multiple tasks are in progress at once, interleaving on one core if necessary; parallelism is genuinely executing them simultaneously on multiple cores. A single-threaded async server is highly concurrent but not parallel. Web workloads need concurrency because they are dominated by waiting; parallelism only helps when the CPU is the bottleneck.

What is a race condition? Give a backend example.

When the outcome depends on the timing of concurrent operations. Example: two requests both read a stock count of 1, both conclude it is available, and both decrement — selling two of one item. The critical section is the entire read-modify-write, so the fix must make that whole sequence atomic, using a row lock, a conditional update, or an atomic operation in the store.

Mutex vs semaphore?

A mutex enforces mutual exclusion for one holder at a time and has an owner, so only the holder should release it. A semaphore is a counter permitting N concurrent holders, so it is used for limiting resource usage — for example allowing at most ten concurrent outbound API calls. A binary semaphore resembles a mutex but lacks ownership semantics.

What causes a deadlock and how do you avoid it?

All four Coffman conditions holding together: mutual exclusion, hold-and-wait, no preemption, and circular wait. The practical fix is to break the circular wait by acquiring locks in a consistent global order, and to break hold-and-wait with timeouts so a stuck acquirer gives up and retries. In databases, keep transactions short and touch rows in a deterministic order.

Why can't you just use a mutex in your Node or Python app to fix a race?

Because production runs many processes on many machines and each has its own mutex, so nothing is actually excluded. Synchronisation must happen at the shared state: an atomic database statement, SELECT ... FOR UPDATE, a unique constraint, or a distributed lock in Redis with a TTL and a fencing token.

What can go wrong with a Redis-based distributed lock?

Several things. If your work outlives the TTL, the lock expires and someone else acquires it while you are still running — so releasing must be a compare-and-delete against your own token, and ideally the protected resource checks a monotonically increasing fencing token. If Redis fails over, an unreplicated lock can be granted twice. And a lock is not a substitute for correctness at the data layer: prefer a database constraint when one exists.

How does the GIL change how you scale a Python backend?

Threads cannot execute Python bytecode in parallel, so CPU-bound work does not speed up with threads — although I/O still benefits, because the GIL is released during blocking calls. Therefore: use async or threads for I/O concurrency, use multiple worker processes to use all cores, and push heavy computation to a process pool or a task queue. Note that the GIL is a CPython implementation detail, not a language rule.

How do you call an API for 10,000 records without falling over?

Bound the concurrency with a semaphore or a worker pool — ten to fifty in flight rather than all at once — because unbounded fan-out exhausts sockets, file descriptors and the connection pool, and often trips the other side's rate limit. Add per-call timeouts, retries with exponential backoff and jitter, and process in batches so partial progress is preserved. Better still, move the whole thing to a queue where each record is its own retryable job.

What to actually alert on — the four golden signals

Latency (p95/p99, split by success and failure), Traffic (requests per second), Errors (5xx rate, and 4xx spikes which often indicate a broken client release), Saturation (CPU, memory, connection pool usage, queue depth). Alert on symptoms users feel, not on causes: "error rate above 1% for five minutes" is actionable; "CPU at 80%" may be perfectly healthy. Every alert should have a human action attached — an alert nobody acts on trains everyone to ignore alerts.

Logging mistakes

Logging passwords, tokens, card numbers or full request bodies — configure redaction and treat it as a security control. Logging inside a tight loop, which floods storage and slows the request. Using console.log/print with no level, so you cannot filter. Logging an error and then re-throwing it, producing three copies of the same stack trace. Interview questions · Observability
A user says "the site is slow". How do you investigate?

Start from data, not guesses. Check whether latency is up globally or for one endpoint, and whether p50 or only p99 moved — a p99-only change suggests a subset of requests such as a large tenant. Look at error rate and traffic to see if this is a load problem. Use a trace to find which span consumed the time: database, cache, an external call, or queueing. Correlate with recent deploys and infrastructure events. Ask the user for the request id if they saw an error, which takes you straight to the log line.

Logs vs metrics vs traces — when do you reach for each?

Metrics to detect and to answer "how bad, and since when" — they are cheap and aggregated, so you alert on them. Traces to localise a latency problem across services and see the breakdown of one slow request. Logs for the detail of a specific event once you know where to look. Metrics point, traces narrow, logs explain.

What is a correlation id and why does it matter?

A unique identifier generated at the entry point and propagated through every downstream call and log line. Without it, logs from a dozen services are unrelated noise; with it, one id reconstructs the complete path of a single request. Returning it to the client in error responses means a user's screenshot is enough to find the exact failure.

Liveness vs readiness probes?

Liveness asks "is this process functional, or should it be restarted?" — it must not depend on external systems, or a database blip would trigger a restart storm. Readiness asks "should traffic be routed here right now?" and does check dependencies, so an instance with a broken database connection is removed from the load balancer without being killed. Conflating them is a common and damaging mistake.

What are SLI, SLO and SLA?

An SLI is the measurement (99.2% of requests succeeded under 300 ms). An SLO is your internal target (99.5%). An SLA is the external contractual promise with penalties, usually set looser than the SLO to leave room. The useful derived concept is the error budget: at a 99.9% SLO you may fail 0.1% of requests, and when the budget is exhausted the team prioritises reliability over new features.

What should never appear in logs?

Passwords, tokens, API keys, session ids, full card numbers, and personal data beyond what you have a lawful reason to retain. Logs are widely readable within a company, are shipped to third-party services, and are retained for a long time. Configure redaction at the logger level rather than relying on every developer to remember.

  5. Scale up the database and app servers.
  6. Scale out the app tier — easy once stateless.

Autoscaling in one paragraph

Scale on a metric that reflects real load — CPU, request rate, or queue depth for workers. Set a cooldown so instances are not added and removed in an oscillating loop, keep warm capacity because new instances take time to boot and warm their caches, and remember that scaling the app tier increases pressure on the database, so the database must be able to absorb it. Also make sure instances drain connections gracefully before termination.

Interview questions · Scaling
Horizontal or vertical scaling — which and why?

Vertical first, because it needs no code changes and modern servers are very large; horizontal when you need fault tolerance, exceed a single machine, or want elasticity for spiky traffic. Horizontal scaling is not really about capacity alone — a single machine is a single point of failure, so two smaller machines can be preferable to one bigger one even at the same total capacity.

What must be true before you can add a second app server?

The app must be stateless: sessions in a shared store, uploads in object storage, caches shared or accepted as per-instance, and scheduled jobs coordinated so they do not run N times. Configuration must come from the environment, and logs must go to a central place rather than local files. Instances should be disposable — killable at any moment without data loss.

How does a load balancer know a server is unhealthy?

Active health checks — it periodically calls a readiness endpoint and removes the instance after a threshold of failures, restoring it after a threshold of successes. Passive checks also matter: a burst of connection errors or 5xxs can eject an instance immediately. The health endpoint should reflect readiness to serve, including critical dependencies, but must not be so strict that a transient blip ejects the entire fleet at once.

What does a CDN actually do for a backend?

It serves cacheable content from a location near the user, which cuts latency and removes most read traffic from your origin. It also terminates TLS at the edge, absorbs traffic spikes and DDoS volume, and can compress and optimise assets. For APIs it can cache public GETs; for private data it can still help through connection reuse and edge routing.

Traffic just went up 10×. What do you check first?

Whether it is real traffic or an incident — a retry storm, a bot, or a broken client looping. Then the saturation signals: database CPU and connections, cache hit rate, queue depth, error rate. Short-term levers are raising cache TTLs, shedding non-critical load, disabling expensive features, and scaling the app tier; the database usually cannot be scaled instantly, which is why caching and queueing are the emergency tools.

What is the difference between an L4 and an L7 load balancer?

L4 operates on TCP/UDP — it forwards packets by IP and port without inspecting content, so it is fast and works for any protocol. L7 understands HTTP, enabling path- and header-based routing, TLS termination, retries, sticky cookies, compression and request rewriting. The trade-off is throughput and cost versus flexibility.

Replication — copies of the same data

One primary accepts writes and streams its changes to replicas, which serve reads. This buys read scaling, redundancy for failover, and a place to run analytics without disturbing production.

Replication lag — the bug that confuses everyone

A user updates their profile (write → primary), the page reloads (read → replica), and the old name appears. The write was not lost; the replica has not caught up. Fixes: read-your-own-writes — route a user's reads to the primary for a few seconds after they write, or until the replica's position passes the write's position; pin session-critical reads to the primary; or return the updated object from the write response so the UI does not need to re-read at all. Also monitor lag and stop routing reads to a replica that falls too far behind.

Sharding — splitting data across independent databases

Replication copies all data everywhere, so it scales reads but not writes or storage. Sharding splits the data itself, so each shard holds a subset and handles its own writes.

Choosing a shard key — the question behind the question

A good shard key is high cardinality, evenly distributed, and present in your most common queries so they can be answered by a single shard. Sharding a social app by user_id means a user's timeline lives on one shard; sharding by post_id means assembling a timeline requires scattering to every shard. Bad keys: timestamps (all of today's writes hit one shard), country (one dominates), boolean flags (cardinality of two). Once chosen, changing the shard key is one of the most expensive operations in engineering — which is why it belongs last in the scaling order.

What you lose when you shard

  • Cross-shard joins — you join in the application, or denormalize so you do not have to.
  • Cross-shard transactions — no single ACID transaction; you need sagas (D4).
  • Global uniqueness and auto-increment — use UUIDs or a Snowflake-style id generator.
  • Simple aggregations — COUNT(*) across all users now means fan-out and merge.
  • Rebalancing — moving data between shards while serving traffic is genuinely hard.
Vertical partitioning — split by COLUMN: hot columns in one table, large rarely-read blobs in another. Same database. Horizontal partitioning — split by ROW within one database (e.g. Postgres native partitioning of orders by month). Queries stay simple, old partitions can be dropped instantly. Sharding — horizontal partitioning across SEPARATE databases on separate machines. This is the one with the distributed-systems cost.
Interview questions · Replication & sharding
Replication vs sharding?

Replication copies the same data to multiple nodes — it scales reads and provides redundancy, but every node still holds everything, so writes and storage do not scale. Sharding splits the data so each node holds a subset — it scales writes and storage, but adds routing, forfeits cross-shard joins and transactions, and complicates every operational task. Most systems use replication first and shard only when forced.

A user updates their profile and immediately sees the old value. Why?

Replication lag: the write went to the primary and the subsequent read went to a replica that had not applied it yet. Fix with read-your-own-writes — route that user's reads to the primary briefly after a write, or track the replication position — or avoid the re-read entirely by returning the updated resource in the write response.

What is consistent hashing and what problem does it solve?

With hash(key) % N, changing N remaps almost every key, so adding one cache node invalidates nearly the whole cache. Consistent hashing places nodes and keys on a ring; each key belongs to the next node clockwise, so adding or removing a node moves only about 1/N of keys. Virtual nodes are added so each physical node occupies many ring positions, which evens out the distribution.

How would you shard a chat application?

By conversation_id, so all messages in a conversation live together and loading a chat hits one shard. Sharding by user_id would split a two-person conversation across two shards, forcing every read to fan out. The trade-off is that a user's list of conversations must then be assembled from several shards, which you solve with a separate index table or a denormalized per-user conversation list.

What is a hot partition and how do you fix one?

A shard receiving far more traffic than the others — a celebrity account, or a key that includes today's date. Fixes: add a salt or suffix to spread a hot key across several partitions and merge on read; give the hot entity its own dedicated shard; or cache aggressively in front of it so most reads never reach the store. Prevention starts with picking a high-cardinality, evenly distributed key.

How does failover work, and what can go wrong?

A monitor detects the primary is unreachable, promotes a replica, and redirects traffic — often via a virtual IP or a proxy such as PgBouncer or Orchestrator. Risks: with asynchronous replication the promoted replica may be missing the most recent writes; and split brain, where the old primary returns and both accept writes. Quorum-based election and fencing the old primary are the standard defences.

Can you avoid sharding entirely?

Very often, yes, and saying so is a mark of judgement. Before sharding: fix queries and indexes, cache aggressively, move writes off the hot path with queues, archive cold data into separate tables or storage, use table partitioning within one database, and scale the machine up. A single modern PostgreSQL instance handles a great deal of traffic. Shard when one machine genuinely cannot hold the writes or the data.

Interview questions · Architecture
Monolith or microservices for a new product?

A modular monolith. Early on you do not yet know the correct boundaries, and getting them wrong in a distributed system is far more expensive than getting them wrong in one codebase. Keep modules cleanly separated with their own data access so extraction later is mechanical, and split when a specific pressure appears — independent scaling, team autonomy, or isolation.

How do you decide service boundaries?

By business capability and by what changes together — orders, payments, inventory, notifications — not by technical layer. A useful test: if a typical feature requires changing three services at once, the boundary is wrong. Domain-driven design's bounded contexts formalise this, and Conway's law warns that your architecture will end up mirroring your team structure whether you plan it or not.

Why is a shared database between microservices an anti-pattern?

Because it destroys independence: a schema change breaks other services, nobody can migrate freely, and you cannot reason about who writes what. It also means the services are only independently deployable in theory. Each service should own its schema and expose data through an API or events; others must not read its tables directly.

What is an API gateway?

A single entry point in front of many services that handles cross-cutting concerns once: routing, authentication, rate limiting, TLS termination, request aggregation and protocol translation. It stops each service reimplementing them and gives clients one stable surface. The risk is that it becomes a bottleneck or a place where business logic accumulates.

How do you handle a transaction across services?

You cannot use a single ACID transaction, so use a saga: a sequence of local transactions where each step publishes an event and each has a compensating action. If payment succeeds but shipping fails, you issue a refund rather than rolling back. Combine with the outbox pattern for reliable event publishing and idempotent handlers for safe retries, and accept that the system is eventually consistent.

Explain dependency injection and why it matters.

Passing dependencies into a component instead of letting it construct them. It makes code testable — you inject fakes rather than needing a live database or payment gateway — and it makes implementations swappable, so switching a provider is a wiring change rather than an edit across the codebase. It is the practical expression of the dependency inversion principle.

What is the layered/clean architecture idea in one sentence?

Dependencies point inward: the domain and business rules at the centre know nothing about HTTP, the database or the framework, while the outer layers (controllers, repositories, adapters) depend on the inner ones. The payoff is that you can change the delivery mechanism or the datastore without touching the rules.

D4

Reliability patterns

"what if X is down?" timeouts circuit breaker graceful degradation

The first law of distributed systems: everything fails eventually. Reliability is not preventing failure but containing it, so one broken dependency does not become an outage.

Timeouts — the most under-used tool

A call with no timeout is a call that can hang forever, holding a thread, a connection and a pool slot. When a dependency slows down, requests pile up until you run out of resources and the whole service dies — a healthy service killed by a slow neighbour.

Set a timeout on EVERY boundary: HTTP client calls, database queries, cache reads, queue publishes, DNS. Budget them so they compose. If your API promises a 3 s response: total 3000ms → auth check 200ms + DB 500ms + payment API 1500ms + serialisation, leaving headroom. A downstream timeout LONGER than your own is always a bug.

Retries — and how they cause outages

Retry storms

A service slows down. Every caller retries three times. The service now receives four times the traffic while already struggling, so it fails completely. Three rules make retries safe: only retry idempotent operations; use exponential backoff with jitter so retries spread out instead of synchronising into waves; and cap total attempts, ideally with a retry budget so retries can never exceed a small fraction of normal traffic. Never retry a 4xx — the request is wrong and will stay wrong.

Circuit breaker

CLOSED — calls pass through; failures are counted │ failure rate crosses the threshold ▼ OPEN — calls fail INSTANTLY without touching the dependency │ after a cool-down period ▼ HALF-OPEN — allow a few trial calls ├── they succeed → CLOSED (recovered) └── they fail → OPEN (wait again) Why: when a dependency is down, waiting for 30 timeouts is worse than failing in 1ms. It protects YOU from tying up resources, and protects THEM from a stampede while they are trying to recover.
timeout, retry with jitter, circuit breaker, graceful shutdown
// --- timeout + retry with exponential backoff and FULL JITTER ---
async function callWithRetry(fn, { attempts = 3, timeoutMs = 2000 } = {}) {
  for (let i = 0; i < attempts; i++) {
    const ac = new AbortController();
    const t = setTimeout(() => ac.abort(), timeoutMs);
    try {
      return await fn(ac.signal);
    } catch (e) {
      if (!isRetryable(e) || i === attempts - 1) throw e;
      // full jitter: random between 0 and the backoff ceiling.
      // Without jitter, every client retries at the SAME instant.
      const ceiling = Math.min(200 * 2 ** i, 5000);
      await sleep(Math.random() * ceiling);
    } finally {
      clearTimeout(t);
    }
  }
}
const isRetryable = (e) =>
  e.name === "AbortError" || e.code === "ECONNRESET" ||
  (e.status >= 500) || e.status === 429;      // never retry other 4xx

// --- circuit breaker ---
class CircuitBreaker {
  constructor({ threshold = 5, cooldownMs = 30000 } = {}) {
    Object.assign(this, { threshold, cooldownMs, failures: 0,
                          state: "CLOSED", openedAt: 0 });
  }
  async call(fn, fallback) {
    if (this.state === "OPEN") {
      if (Date.now() - this.openedAt < this.cooldownMs) {
        if (fallback) return fallback();       // fail fast, degrade gracefully
        throw new Error("circuit_open");
      }
      this.state = "HALF_OPEN";
    }
    try {
      const out = await fn();
      this.failures = 0; this.state = "CLOSED";
      return out;
    } catch (e) {
      if (++this.failures >= this.threshold) {
        this.state = "OPEN"; this.openedAt = Date.now();
      }
      if (fallback) return fallback();
      throw e;
    }
  }
}

Interview questions · Reliability
The payment service is down. What does your checkout do?

It should fail fast rather than hanging: a timeout on the call, a circuit breaker so we stop hammering a dead service, and a clear 503 with Retry-After to the user. If the business allows, accept the order in a pending_payment state and queue the charge for retry, so the customer's intent is not lost. What must not happen is that unrelated endpoints slow down because checkout requests are holding every connection.

Why can retries make an outage worse?

Because they multiply load on a service that is already failing, and because unsynchronised clients tend to retry in synchronised waves. The result is a retry storm that prevents recovery. Safe retrying means idempotent operations only, exponential backoff with jitter, a hard attempt cap, a retry budget, and a circuit breaker to stop entirely when the dependency is clearly down.

Explain the circuit breaker states.

CLOSED: traffic flows and failures are counted. When the failure rate crosses a threshold it trips to OPEN, where calls fail immediately without touching the dependency, protecting both sides. After a cool-down it becomes HALF-OPEN and allows a few probe calls; success returns it to CLOSED, failure sends it back to OPEN. The value is failing in a millisecond instead of waiting for thousands of timeouts.

How do you set timeouts across a call chain?

Work backwards from the deadline you promise your caller and give each downstream a slice, always shorter than your own remaining budget. Propagate the remaining deadline downstream where the protocol allows it, so a service does not start work that can no longer be used. A downstream timeout longer than your own guarantees you abandon work that is still running.

What is graceful shutdown and why does it matter?

On SIGTERM, stop accepting new requests, finish in-flight ones, let running jobs complete or return them to the queue, close database and broker connections, then exit. Without it, every deploy drops live requests and may leave jobs half-finished. It also requires deregistering from the load balancer first and allowing a short delay, because routing tables take a moment to converge.

What is the bulkhead pattern?

Isolating resources so a failure in one area cannot exhaust everything — separate connection pools, thread pools or concurrency limits per dependency. Named after ship compartments: one flooded section does not sink the vessel. In practice it prevents a single slow third-party API from consuming every worker and taking down endpoints that never call it.

What is the saga pattern?

A way to keep multiple services consistent without a distributed transaction. The business process becomes a sequence of local transactions, each publishing an event, and each with a compensating action that semantically undoes it — refund a payment, restock an item. Coordination is either orchestrated by a central workflow or choreographed through events. The system is eventually consistent, and every handler must be idempotent.

Containers vs virtual machines

A VM virtualises hardware and runs a full guest OS — gigabytes, tens of seconds to boot, strong isolation. A container virtualises the operating system: it is an isolated process on the host kernel using namespaces (what it can see) and cgroups (what it can use) — megabytes, milliseconds to start, weaker isolation. Containers solve "it works on my machine" by shipping the application together with its dependencies.

To keep compilers, dev dependencies and build artefacts out of the final image. The result is much smaller — faster to pull and deploy — and has a far smaller attack surface, since a shipped compiler is a tool for an attacker. It also lets you order layers so dependency installation is cached separately from source changes.

How do you handle secrets in containers?

Never bake them into the image — anyone who pulls it can read every layer. Inject them at runtime as environment variables or mounted files from a secret manager (Kubernetes Secrets backed by Vault or a cloud provider), keep them out of source control, rotate them, and scan images and repositories for accidentally committed credentials.

Blue-green or canary — which and why?

Canary when you have good metrics and want to limit blast radius: a small percentage of users sees the new version and you compare error rate and latency before proceeding. Blue-green when you need an instant, complete rollback and can afford duplicate infrastructure. Canary is usually preferable for high-traffic services; blue-green suits big, risky cutovers.

How do you run database migrations during a deploy?

Run them before the new code rolls out, and make them backwards compatible so the old version still works — because both versions run simultaneously during a rolling deploy. Additive changes only in the same release; destructive steps come in a later one after the new code is stable. Long backfills run in batches outside the deploy path, and index creation uses the concurrent variant.

What do you do when a deploy breaks production?

Roll back first and investigate afterwards — restoring service beats diagnosing. That is only possible if deploys are reversible, which means immutable images tagged by commit, backwards-compatible schemas, and feature flags for anything that cannot be rolled back cleanly. Afterwards, a blameless postmortem focused on why the pipeline let it through.

Numbers worth memorising for estimation

1 million requests/day ≈ 12 per second. 1 million/hour ≈ 280/s. Peak traffic is typically 2–3× the average. Memory reference ≈ 100 ns; SSD random read ≈ 100 µs; network round trip within a datacentre ≈ 0.5 ms; across a continent ≈ 50–150 ms. One modern database instance handles roughly 5,000–20,000 simple queries/second. A UUID is 16 bytes; a typical JSON row is a few hundred bytes. Round aggressively — interviewers want the reasoning, not arithmetic.

Design 1 · URL shortener

Requirements: shorten a URL, redirect, optional custom alias, click analytics. Scale: 100M new URLs/month, 10:1 read:write → ~4,000 redirects/s peak. This is an overwhelmingly READ-heavy system. That single fact drives everything. API POST /urls {"url": "...", "alias": "..."} → {"short": "sho.rt/aB3x9Z"} GET /{code} → 301/302 redirect Key generation — three options, know the trade-offs: a) hash(url) truncated to 7 chars → deterministic, but collisions need handling b) random 7 chars from [A-Za-z0-9] → 62^7 ≈ 3.5 trillion; check for collision c) counter → base62 → no collisions, but sequential = guessable, and the counter is a bottleneck unless you hand out ranges per server (ticket server) Data urls(code PK, long_url, user_id, created_at, expires_at) clicks — do NOT write a row synchronously on redirect at 4,000/s. Emit an event to Kafka; workers aggregate into daily counters. Read path (the important one) GET /{code} → CDN/edge cache → Redis (code → long_url, hit rate ~95%) → DB only on a miss → 301 redirect Codes are immutable, so caching is trivially safe and TTLs can be long. 301 vs 302: 301 is cached by the browser, so subsequent clicks never reach you — cheapest, but you lose analytics. 302 keeps every click visible. Choose 302 if analytics is a requirement, and say so out loud. Scaling: the app tier is stateless and trivially horizontal; the read path is almost entirely cache; shard the urls table by code hash when it outgrows one node.

Design 2 · Distributed rate limiter

Requirements: limit each user to N requests per window, across many servers, with minimal added latency, failing open if the limiter itself is down. Why not in-process: 10 instances × 100/min = an effective limit of 1,000/min. State must be shared → Redis. Token bucket in Redis, atomic via Lua (read-modify-write MUST be atomic): key = ratelimit:{userId} value = {tokens, lastRefillTimestamp} on request: refill = (now - lastRefill) * rate tokens = min(capacity, tokens + refill) if tokens >= 1: tokens -= 1 → ALLOW else → DENY, return 429 + Retry-After Why token bucket: it permits short bursts (good UX) while enforcing an average rate, and it needs only two numbers per key instead of a list of timestamps. Layers: edge/CDN → crude per-IP limits, absorbs volumetric abuse API gateway → per-API-key quotas application → per-user, per-endpoint business limits Response: 429 with Retry-After, plus X-RateLimit-Limit / -Remaining / -Reset. Failure mode: if Redis is unavailable, FAIL OPEN for normal endpoints (allow traffic) but FAIL CLOSED for login and payment, where abuse is the real risk.

Design 3 · News feed

Requirements: users follow others; the home feed shows recent posts from people they follow, ordered by time. 10M daily users, 500M follows. The central decision: FAN-OUT ON WRITE vs FAN-OUT ON READ. Fan-out on WRITE (push) On post: append the post id to every follower's precomputed feed list (Redis). Read = O(1) — just read the list. Excellent for the common case. Problem: a celebrity with 50M followers triggers 50M writes for one post. Fan-out on READ (pull) On read: query recent posts from everyone this user follows and merge. Write = O(1). Read is expensive, and gets worse the more people you follow. The real answer is HYBRID, and saying so is the point of the question: • Normal users → fan-out on write (fast reads for everyone) • Celebrity accounts → NOT fanned out; their posts are pulled at read time • Feed = merge(precomputed list, recent posts from followed celebrities) • Cap stored feed length (~500–1000 ids); older pages fall back to a query • Inactive users are skipped during fan-out and rebuilt lazily on login Storage posts(id, author_id, body, created_at) — sharded by author_id follows(follower_id, followee_id) — indexed BOTH ways feed:{user_id} — Redis sorted set, score = timestamp Consistency: a feed that is a few seconds stale is completely acceptable, so fan-out runs asynchronously through a queue — the post request returns immediately.
What actually gets you through a design round

Ask clarifying questions before designing. State assumptions out loud and write them down. Start simple and scale when the interviewer pushes — do not open with sharding. Name trade-offs explicitly ("this gives faster reads at the cost of stale data for a few seconds"). Draw the data flow, not a box collection. And when you do not know something, say so and reason from principles instead of bluffing — interviewers are evaluating how you think under uncertainty, which is precisely the job.

Interview questions · System design
How do you start a system design question?

With requirements, never with architecture. Functional: what must it do? Non-functional: how many users, what read:write ratio, what latency target, how consistent must it be, how available? Then scope: what is explicitly out. Estimating traffic and storage next tells you whether this is a caching problem, a write-throughput problem, or a storage problem — and that determines the shape of the whole design.

Design a URL shortener — what is the core challenge?

It is a read-dominated system with immutable data, so the real work is the read path: cache aggressively at the edge and in Redis, keep the redirect handler tiny, and make the app tier stateless. The interesting decisions are key generation (random with collision check, or a counter in base62 with ranges handed out per server) and whether to write click analytics synchronously — you should not, at thousands per second; emit events and aggregate asynchronously.

Design a rate limiter for a distributed API.

Shared counters in Redis, because in-process state multiplies the limit by the instance count. Token bucket implemented as an atomic Lua script gives burst tolerance with only two stored numbers. Key by user id where authenticated and by IP otherwise, return 429 with Retry-After and rate-limit headers, and decide the failure mode deliberately — fail open for ordinary endpoints, fail closed for login and payment.

Fan-out on write or on read for a feed?

Hybrid. Fan-out on write gives O(1) reads and suits the vast majority of users, but a celebrity post would trigger tens of millions of writes. So exclude high-follower accounts from fan-out and pull their recent posts at read time, merging the two sources. Also cap the stored feed length and skip inactive users during fan-out, rebuilding their feed lazily.

How do you estimate storage for a system?

Rows per day × bytes per row × retention, then add indexes (often 20–50% more) and replication factor. For example 100M URLs/month at ~500 bytes is 50 GB/month, so 600 GB/year before indexes and replicas — comfortably one machine, which tells you sharding is not the first problem. Doing this arithmetic prevents over-engineering, and interviewers notice when it changes your design.

How would you add search to a system like this?

Keep the relational database as the source of truth and maintain a separate search index (Elasticsearch or OpenSearch) updated asynchronously — through the outbox pattern or change data capture, so the write path is not coupled to the index's availability. The index is eventually consistent, which is acceptable for search, and you rebuild it from the source of truth when the mapping changes.

Rapid-fire viva questions

Thirty questions that recur across almost every backend interview. Answer out loud before opening each one.

What happens when you type a URL and press Enter?

DNS resolution → TCP handshake → TLS handshake → HTTP request → CDN/load balancer → app server middleware → cache then database → response serialised and returned → browser renders and fetches sub-resources. Mention caching at every level and you have given the full answer.

Why is HTTP called stateless?

The protocol carries no memory between requests; each is interpreted alone. Cookies, tokens and sessions exist to re-establish identity on every request. Statelessness is what lets any server behind a load balancer handle any request.

Idempotent vs safe?

Safe means no state change (GET, HEAD). Idempotent means repeating it has the same effect as doing it once (GET, PUT, DELETE). All safe methods are idempotent; the reverse is not true — DELETE changes state but repeating it does not change it further.

PUT vs PATCH vs POST?

POST creates or triggers, and is not idempotent. PUT replaces a whole resource, and is idempotent. PATCH partially updates, and is idempotent only if the operations are absolute rather than relative.

401 vs 403?

401 means not authenticated — re-authenticating might help. 403 means authenticated but not permitted — it will not.

What is CORS, in one sentence?

A browser-enforced mechanism by which a server declares which other origins may read its responses; it protects users from malicious pages, not your API from attackers.

Where should you store a JWT?

Access token in memory, refresh token in an HttpOnly; Secure; SameSite=Strict cookie scoped to the refresh endpoint. localStorage is readable by any XSS payload.

How do you revoke a JWT?

You cannot un-sign it. Keep access tokens short-lived and revoke the server-side refresh token, or maintain a denylist keyed by token id with a TTL matching the remaining lifetime.

How do you store passwords?

bcrypt (cost 12+) or argon2id — slow, salted per user, memory-hard. Never plaintext, reversible encryption, or a fast hash like SHA-256.

SQL injection — cause and cure?

Cause: user input concatenated into a query so it is parsed as SQL. Cure: parameterised queries, so the statement is compiled before the values are bound. Allowlist any identifier you must interpolate.

XSS vs CSRF?

XSS runs the attacker's script on your page. CSRF makes the victim's browser send a request they did not intend. Escape output and set a CSP for XSS; use SameSite cookies and CSRF tokens for CSRF.

What is IDOR?

Using a client-supplied id without checking that the requester may access that object. Fix by scoping every query with the authenticated user id, in the repository layer so it cannot be forgotten.

Explain ACID.

Atomicity: all or nothing. Consistency: constraints hold. Isolation: concurrent transactions do not corrupt each other. Durability: a commit survives a crash.

Name the isolation levels and the anomalies each prevents.

READ UNCOMMITTED allows everything. READ COMMITTED prevents dirty reads. REPEATABLE READ also prevents non-repeatable reads. SERIALIZABLE also prevents phantoms.

What is a deadlock and how do you prevent one?

Two transactions each waiting on a lock the other holds. Prevent by acquiring locks in a consistent order and keeping transactions short; handle by catching the error and retrying with backoff.

What is an index and when does it hurt?

A sorted structure enabling fast lookup. It hurts write throughput, consumes storage, and is useless on low-selectivity columns or when a function wraps the indexed column.

Explain the leftmost-prefix rule.

An index on (a, b, c) serves predicates on a, a+b, or all three — never on b or c alone, because the sort order starts with a.

What is the N+1 problem?

One query for a list plus one per item, usually from ORM lazy loading. Fix with eager loading or by batching ids into a single IN query.

Normalization in one line, and when to break it?

Store each fact once so the data cannot contradict itself. Break it deliberately for historical snapshots, counters and read models — with a plan for keeping the copy correct.

SQL or NoSQL — how do you choose?

Relational by default: joins, transactions, ad-hoc queries. NoSQL when access is key-based at very high volume, documents vary in shape, or you need multi-region availability more than strict consistency.

State the CAP theorem correctly.

During a network partition you must choose between consistency and availability. Partition tolerance is not optional in a distributed system, so it is not a free choice of two out of three.

What is eventual consistency?

If writes stop, all replicas converge. A read immediately after a write may be stale. Fine for counters, feeds and search indexes; unacceptable for balances and inventory at checkout.

Explain cache-aside and why you delete rather than update.

Read: check cache, on a miss read the database and populate. Write: update the database and delete the key. Updating races with an in-flight read that could write the old value back.

What is a cache stampede?

A hot key expires and every concurrent request misses at once, flooding the database. Prevent with a lock so only one request recomputes, probabilistic early expiry, or background refresh.

Why can't you achieve exactly-once delivery?

Because acknowledgements can be lost, so you must choose between possibly losing a message and possibly redelivering it. In practice you use at-least-once delivery plus idempotent consumers, which produces exactly-once effects.

What is the outbox pattern?

Write the event to an outbox table inside the same transaction as the data change, then publish it asynchronously from there — so the database write and the event publish cannot diverge.

Concurrency vs parallelism?

Concurrency is dealing with many tasks in overlapping time; parallelism is executing them simultaneously on multiple cores. Web servers need concurrency; only CPU-bound work needs parallelism.

Why does blocking the event loop matter?

Because one thread serves every request, a synchronous CPU-heavy operation halts all concurrent requests for its full duration. Offload to a worker thread, a process pool, or a queue.

What breaks when you add a second app server?

In-memory sessions, local file uploads, per-process caches and in-process scheduled jobs. All of them must move to shared infrastructure — that is what "stateless" means in practice.

Explain the circuit breaker.

Count failures; when they cross a threshold, open the circuit and fail instantly instead of waiting for timeouts; after a cool-down, allow probe calls and close again if they succeed.

Why do retries need jitter?

Without it, every client retries at the same instant, producing synchronised waves that prevent a struggling service from recovering. Randomising the delay spreads the load.

How do you deploy without downtime?

Rolling or canary deployment with graceful shutdown, health checks, and backwards-compatible schema and API changes — because two versions run simultaneously during the rollout.

A five-step script for any design question

  1. Repeat the problem back and confirm scope. "So we need X for Y users, and Z is out of scope — correct?"
  2. State your assumptions aloud and write them down. Wrong assumptions are fine; silent ones are not.
  3. Start with the simplest thing that works, then scale it only when pushed. Opening with sharding signals inexperience.
  4. Name every trade-off. "This makes reads O(1) but costs us a few seconds of staleness — acceptable here because…"
  5. Close with what breaks first and what you would monitor. That is the sentence that sounds like someone who has run a system in production.
