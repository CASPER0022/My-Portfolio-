Section 01 · Foundations

What Machine Learning Is

The one-sentence definition, the three (really four) types of learning, and the vocabulary every later section assumes.

The definition, and why it matters

In traditional programming you write the rules, feed in data, and get answers. In machine learning you feed in the data and the answers, and the computer works out the rules.

Tom Mitchell's formal definition — quotable in an interview

“A computer program is said to learn from experience E with respect to some task T and performance measure P, if its performance at T, as measured by P, improves with experience E.”

For spam filtering: T = classify emails as spam or not; E = a labelled corpus of past emails; P = the fraction correctly classified. Being able to decompose any problem into T, E and P is genuinely useful — it forces you to name your metric before you build anything.

When should you not use ML?

A surprisingly common interview question, and a strong differentiator. Do not use ML when:

  • A simple rule works. If “flag transactions over ₹10 lakh” catches the fraud, ship the if statement. It is faster, free, and explainable in court.
  • You have no data, or no labels, and no cheap way to get them.
  • Errors are catastrophic and unexplainable errors are unacceptable — some medical and legal contexts.
  • The pattern does not exist. No model predicts a fair coin flip; the Bayes error rate is 50%.
  • The cost of being wrong exceeds the value of being right. Compute the expected value before the model.

The fourth type you should mention

Semi-supervised learning uses a small labelled set plus a large unlabelled one — which is the realistic situation in industry, because labelling is expensive and raw data is nearly free. Self-supervised learning goes further: it manufactures labels from the data itself (predict the next word; predict a masked patch of an image). Self-supervision is the reason modern LLMs and vision models exist at all — it converts the entire internet into a labelled dataset without a single human annotator.

Classification vs regression

Classification

Output is a discrete category. Binary (spam / not spam), multi-class (digit 0–9, exactly one), or multi-label (an image tagged both “beach” and “sunset”). Loss: cross-entropy. Metrics: accuracy, precision, recall, AUC.

Regression

Output is a continuous number — price, temperature, time-to-failure. Loss: MSE or MAE. Metrics: RMSE, MAE, R².

Watch the trap: predicting a probability is regression-flavoured but the task is classification. And an ordinal target — a 1–5 star rating — is genuinely ambiguous; treating it as regression respects the ordering, treating it as classification does not, and saying that out loud scores well.

Parametric vs non-parametric

A parametric model commits to a fixed number of parameters regardless of dataset size — linear regression has one weight per feature whether you have 100 rows or 100 million. It is fast, needs less data, and is strongly biased toward its assumed form. A non-parametric model lets complexity grow with the data — KNN literally stores the entire training set; a decision tree grows more nodes with more data. It is flexible and data-hungry, and it overfits readily.

Discriminative vs generative

A distinction interviewers love

A discriminative model learns P(y | X) — the decision boundary directly. Logistic regression, SVM, random forests, most neural networks. It answers “which class is this?”

A generative model learns P(X, y) — or P(X | y) and P(y) — the full joint distribution, then applies Bayes’ rule to classify. Naive Bayes, GMMs, and every modern generative model (VAEs, diffusion, LLMs).

Trade-off: discriminative models usually classify better with enough data because they solve the easier problem directly. Generative models need less data, handle missing features gracefully, and can synthesise new samples — which is the entire basis of generative AI.

Interview questions · Section 01
What is machine learning, and how is it different from traditional programming?

In traditional programming, a human writes explicit rules; the program takes data plus those rules and produces answers. In machine learning, you supply data and the answers, and the algorithm infers the rules — the model — which you then apply to new data.

The formal definition I'd give is Mitchell's: a program learns from experience E with respect to task T and performance measure P if its performance at T, measured by P, improves with E. For a spam filter, T is classifying emails, E is a labelled corpus, P is accuracy or precision at a fixed recall.

The reason the distinction matters practically: ML earns its complexity only when the rules are too numerous, too subtle, or too fast-changing to write by hand. Recognising a cat in an image has no writable rule set. Flagging transactions above a threshold does — and there I'd write the if statement, because it's faster, free and explainable.

Explain supervised, unsupervised and reinforcement learning with examples.

Supervised learning trains on labelled data — every input has a known correct output — and learns a mapping from features to that output. Classification when the output is a category (spam detection, digit recognition) and regression when it's continuous (house prices). Feedback is direct, so evaluation is straightforward.

Unsupervised learning has no labels; the goal is to find structure. Clustering groups similar customers for segmentation; PCA reduces dimensionality; anomaly detection flags unusual transactions. The hard part is evaluation — with no ground truth, you're relying on internal measures like silhouette score plus domain judgement, and that's the point I'd emphasise.

Reinforcement learning has an agent taking actions in an environment and receiving rewards, learning a policy that maximises cumulative reward. Game playing like AlphaGo, robotic control, ad bidding. What makes it distinct is that feedback is delayed and evaluative — you're told the score, not the correct action, and the reward may arrive a hundred steps after the decision that caused it. That credit-assignment problem is what makes RL hard.

I'd add a fourth that matters commercially: self-supervised learning, which generates labels from the data itself — predicting the next word or a masked image patch. It's how LLMs and modern vision models are pretrained, because it turns unlabelled data into supervision at internet scale.

What is the difference between a parameter and a hyperparameter?

Parameters are learned from the training data by the optimisation process — the weights and bias in linear regression, the split thresholds in a decision tree, the millions of weights in a neural network. You never set them by hand; they're the output of training.

Hyperparameters are set before training and control how learning happens — learning rate, number of trees, maximum tree depth, k in KNN, regularization strength λ, batch size. They aren't learned from the training data because optimising them on training data would just pick whatever overfits hardest.

That's the key consequence: hyperparameters must be tuned on a validation set or by cross-validation, never on the training set and never on the test set. Tuning on the test set contaminates your final estimate — you've effectively fitted to it, and your reported performance becomes optimistic.

Discriminative vs generative models?

A discriminative model learns the conditional P(y|X) — it models the decision boundary directly, answering "given these features, which class?" Logistic regression, SVMs, random forests and most neural network classifiers are discriminative.

A generative model learns the joint distribution P(X,y), typically by modelling P(X|y) and the prior P(y), then classifying via Bayes' rule. Naive Bayes, Gaussian mixture models, and modern generative models like VAEs, diffusion models and LLMs.

The trade-off: discriminative models generally achieve better classification accuracy when data is plentiful, because they solve the narrower problem and don't waste capacity modelling the input distribution. Generative models need less labelled data, handle missing features naturally by marginalising, and — uniquely — can sample new data, which is the whole basis of generative AI. Naive Bayes versus logistic regression is the classic paired example: Naive Bayes converges faster with little data, logistic regression wins asymptotically.

When would you NOT use machine learning?

Several cases, and I'd treat this as a genuine engineering question rather than a trick.

  • When a rule works. If a threshold or a lookup table solves it, that's cheaper, faster, deterministic and explainable. ML adds data pipelines, monitoring, retraining and drift — real permanent cost.
  • When there's no data, or labels are unaffordable and can't be bootstrapped.
  • When the pattern doesn't exist. No model beats chance on a fair coin. If the irreducible error is high, more modelling won't help and the honest answer is to say so.
  • When errors are catastrophic and explanations are legally required — some clinical and credit decisions, where a regulator needs a reason, not a probability.
  • When the expected value is negative — if a false positive costs more than a true positive saves, the model has to be very good before it's worth deploying, and that calculation should happen before any code.

Saying this shows judgement. Interviewers see plenty of candidates who reach for a neural network before asking whether the problem needs one.

What is the difference between AI, ML and deep learning?

They're nested. Artificial intelligence is the broadest — any technique making machines behave intelligently, including hand-written expert systems and search algorithms that involve no learning at all.

Machine learning is the subset of AI where behaviour is learned from data rather than programmed. Linear regression, decision trees, SVMs and neural networks all sit here.

Deep learning is the subset of ML using neural networks with many layers. Its defining property is automatic feature learning — classical ML needs a human to engineer features, whereas a deep network learns a hierarchy of representations from raw input, which is why it dominates on images, audio and text.

The practical corollary worth adding: deep learning is not strictly better. On small or medium tabular datasets — which is most business data — gradient-boosted trees typically beat neural networks, train in seconds and are easier to explain. Deep learning wins where data is abundant and the input is unstructured.

The Maths You Actually Need

Only the parts that appear in interviews: vectors and matrices, derivatives and the chain rule, probability, and the statistics behind every metric.

Scope

You do not need a maths degree. You need to be able to write a loss function, take its derivative, explain what a probability distribution is, and reason about sampling. This section is exactly that and nothing more.

Calculus — you need one rule

Training a model means minimising a loss. Minimising means following the slope downhill. The slope is the derivative.

The gradient ∇L is the vector of partial derivatives — one per parameter. It points in the direction of steepest increase, so we step in the opposite direction. That is the whole of gradient descent (Section 10).

The medical-test problem — asked verbatim in interviews

A disease affects 1 in 1 000. A test is 99% accurate both ways. You test positive. What is the probability you have the disease?

Take 100 000 people. 100 have the disease; 99 of them test positive. 99 900 are healthy; 1% of them — 999 — test positive anyway.

So of 99 + 999 = 1 098 positive tests, only 99 are real: ≈ 9%. The intuition to state: when the base rate is tiny, false positives from the huge healthy majority swamp true positives. This is the same reason accuracy is a useless metric on imbalanced data (Section 07).

Central Limit Theorem — the reason the normal distribution is everywhere

The distribution of the sample mean approaches a normal distribution as sample size grows, regardless of the shape of the underlying population. Roughly n ≥ 30 is the usual rule of thumb.

Why it matters: it is what licenses confidence intervals and hypothesis tests on data that is not itself normal — which is nearly all real data. It is also why measurement noise, being the sum of many small independent effects, tends to be Gaussian.

Statistics behind every metric

  • Mean, median, mode. The median is robust to outliers, the mean is not — which is exactly why MAE is robust and MSE is not (Section 07).
  • Variance and standard deviation. Spread. σ² = E[(X − μ)²].
  • Covariance measures joint variability but its scale is arbitrary; correlation normalises it to [−1, 1] so it is comparable.
  • Correlation is not causation — and the mechanism to name is a confounder: ice-cream sales and drownings correlate because temperature drives both.
  • Skew (asymmetry) and kurtosis (tail heaviness) tell you whether to log-transform a feature.
  • p-value: the probability of observing data at least this extreme if the null hypothesis were true. It is not the probability the null is true — that misstatement is a common interview trap.
  • Type I error = false positive (rejecting a true null). Type II error = false negative (failing to reject a false null). These map exactly onto FP and FN in a confusion matrix.
Interview questions · Section 02
Explain Bayes' theorem and give an ML application.

Bayes' theorem lets you invert a conditional probability: P(A|B) = P(B|A)P(A) / P(B). In words: the posterior equals the likelihood times the prior, normalised by the evidence. It's how you update a belief when new data arrives.

The ML application is Naive Bayes classification. To classify an email, I want P(spam | words), which I can't estimate directly. Bayes flips it into P(words | spam) × P(spam), both of which I can count from training data. The "naive" part is assuming the words are conditionally independent given the class, which lets me multiply individual word probabilities instead of modelling their joint distribution.

The intuition I'd add is the base rate effect. With a disease affecting 1 in 1 000 and a 99%-accurate test, testing positive still means only about a 9% chance of having it — because 1% of the enormous healthy population produces far more false positives than the tiny sick population produces true ones. That's the same arithmetic that makes accuracy meaningless on imbalanced datasets.

What is the Central Limit Theorem and why does it matter?

The CLT says that the sampling distribution of the mean tends toward a normal distribution as sample size increases, whatever the shape of the underlying population — skewed, bimodal, discrete, it doesn't matter. Conventionally n ≥ 30 is treated as sufficient, though heavily skewed populations need more.

It matters for two reasons. First, it's what justifies constructing confidence intervals and running t-tests on real data, which is almost never normally distributed. When I A/B test a conversion rate, the individual outcomes are Bernoulli, but the mean conversion rate across thousands of users is approximately normal, so standard inference applies.

Second, it explains why the Gaussian shows up so persistently in nature and in ML — measurement noise is typically the sum of many small independent effects, and sums of independent random variables tend to normality. That's why we model errors as Gaussian and why Gaussian assumptions in things like linear regression's error term are often reasonable.

What is the difference between covariance and correlation?

Both measure how two variables move together. Covariance is the expected product of their deviations from their means — positive if they move together, negative if oppositely. Its problem is that its magnitude depends on the units: the covariance between height in centimetres and weight in kilograms is a different number from the same relationship in inches and pounds, so you can't compare covariances across variable pairs or judge strength from the value.

Correlation fixes this by dividing by the product of the standard deviations, giving a unitless value in [−1, 1]. Now −1 is perfect inverse, 0 is no linear relationship, +1 is perfect direct, and values are comparable across any pair of variables.

Two caveats worth adding: Pearson correlation only captures linear relationships — a perfect parabola can have correlation near zero, so I'd plot the data rather than trust the number alone. And correlation isn't causation; the usual mechanism is a confounder driving both variables.

What is a p-value? What does p = 0.03 mean?

A p-value is the probability of observing a result at least as extreme as the one you got, assuming the null hypothesis is true. So p = 0.03 means: if there were genuinely no effect, there'd be a 3% chance of seeing data this extreme by random variation alone. At a conventional threshold of 0.05, you'd reject the null.

The critical thing it is not: it is not the probability that the null hypothesis is true, and not the probability your result is a fluke. Getting that backwards is the most common statistics error in interviews. To get the probability of a hypothesis given the data you'd need a Bayesian approach with a prior.

I'd also flag the practical problems: a p-value says nothing about effect size, so with a huge sample a trivially small difference can be highly significant and commercially worthless. And running many tests inflates false positives — twenty independent tests at α = 0.05 will produce roughly one "significant" result from pure noise, which is why multiple-comparison corrections exist.

What is the chain rule and where does it appear in ML?

The chain rule differentiates composed functions: if y = f(g(x)), then dy/dx = (dy/du)(du/dx). You multiply the local derivatives along the path.

It appears in ML as backpropagation, which is nothing more than the chain rule applied systematically through a network. A neural network is a composition of functions — each layer transforms the previous layer's output — so the derivative of the loss with respect to an early weight is the product of all the local derivatives on the path from that weight to the loss. Backprop computes these efficiently by working backwards from the loss and reusing shared sub-results, which is why it's linear in the number of parameters rather than quadratic.

It also explains two of deep learning's characteristic failures. Because gradients are multiplied along the path, if the local derivatives are consistently below 1 the product shrinks toward zero over many layers — vanishing gradients, which is what killed sigmoid-based deep networks and motivated ReLU and residual connections. If they're consistently above 1, the product explodes, which is why we clip gradients in RNNs.

What is cosine similarity and when would you use it over Euclidean distance?

Cosine similarity is the cosine of the angle between two vectors — their dot product divided by the product of their magnitudes — giving a value in [−1, 1] that measures direction while ignoring magnitude.

I'd use it whenever magnitude is an artefact rather than signal. The canonical case is text: two documents about the same topic, one 200 words and one 2 000, have very different vector magnitudes under a bag-of-words or TF-IDF representation, so Euclidean distance would call them dissimilar purely because of length. Cosine similarity correctly identifies them as pointing the same direction in term space. Same logic for embeddings in semantic search and recommendation systems.

I'd use Euclidean distance when magnitude genuinely matters — physical measurements, coordinates, or any case where "how much" is part of the meaning. Worth noting: for L2-normalised vectors the two are monotonically related, so on normalised embeddings the ranking they produce is identical and the choice is just convention.

The End-to-End ML Workflow

The pipeline a real project follows — and the three splitting mistakes that silently invalidate results.

  1. Frame the problem What is being predicted, and what decision does the prediction drive? Is it classification or regression? What metric reflects business value? Decide this first — a model optimising the wrong metric is worse than no model.
  2. Collect & understand the data Exploratory data analysis: distributions, missing values, outliers, class balance, correlations, leakage suspects. Plot before you model.
  3. Split the data Train / validation / test — before any preprocessing decisions are made from it. Typically 60/20/20, or 80/20 with cross-validation on the 80.
  4. Preprocess & engineer features Impute, encode, scale, transform, create features. Fit every transformer on the training set only (Section 04).
  5. Choose a baseline Predict the mean, or the majority class, or use logistic regression. If your deep model can’t beat the baseline, something is wrong.
  6. Train candidate models Start simple. Complexity is something you earn by demonstrating the simple model is insufficient.
  7. Evaluate & tune Use cross-validation on the training data to select hyperparameters. The test set stays sealed.
  8. Interpret Feature importance, SHAP values, partial dependence. A model you cannot explain is a model you cannot debug — or defend.
  9. Final evaluation Touch the test set once. This number is your honest estimate; do not go back and tune after seeing it.
  10. Deploy & monitor Serve it, then watch for data drift, concept drift, latency and business KPIs. Plan retraining before you launch (Section 24).

Train / validation / test — what each is for

The three splitting mistakes
  1. Preprocessing before splitting. If you compute the mean for imputation, or fit a scaler, on the whole dataset, information from the test set has leaked into training. Your test score is now optimistic. Fit transformers on train, apply to validation and test.
  2. Tuning on the test set. Every time you look at test performance and change something, you fit a little more to it. After twenty iterations the test set is a second validation set and you have no honest estimate left.
  3. Random splitting when the data isn’t i.i.d. For time series you must split chronologically — a random split lets the model see the future. For grouped data (multiple rows per patient), split by group, or the same patient appears in train and test.

Data leakage — the silent killer

Leakage is when information unavailable at prediction time gets into training. It produces spectacular validation scores and a model that collapses in production. It is the single most common cause of “it worked in the notebook”.

The detection heuristic to state

“If a model performs suspiciously well — 99% on a hard problem — assume leakage before assuming genius.” Then check feature importance: leakage usually shows up as one feature dominating implausibly. That sentence is a very strong signal of practical experience.

Always build a baseline first

Classification baseline

Predict the majority class. On a 95/5 imbalance this scores 95% accuracy — instantly showing why accuracy is the wrong metric, and setting the bar your model must clear.

Regression baseline

Predict the training mean (or the previous value for time series). Gives you the R² = 0 reference point.

Interview questions · Section 03
Walk me through an end-to-end machine learning project.

I'd start by framing the problem: what exactly is predicted, what decision does the prediction drive, and what metric reflects business value. That last part is critical — for fraud detection, optimising accuracy is meaningless; I need recall at a precision the review team can actually handle.

Then EDA: distributions, missing values, outliers, class balance, and a hard look for leakage candidates. Then split the data — before any preprocessing decision, and chronologically if it's time-series or by group if rows share an entity.

Preprocess and engineer features inside a pipeline, so every transformer is fitted on training folds only. Establish a baseline — majority class or the mean — because if the sophisticated model can't beat that, something is wrong. Then train candidates starting simple, tune hyperparameters via cross-validation on the training data, and interpret the model with feature importance or SHAP to sanity-check that it's using sensible signal.

Finally, evaluate on the test set once, and deploy with monitoring for data drift, concept drift and the business KPI — planning the retraining cadence before launch, not after the first incident. And I'd emphasise the loop: most of the gain in a real project comes from better data and features, not a better algorithm.

What is data leakage? Give an example and say how you'd detect it.

Leakage is when information that wouldn't be available at prediction time makes it into training. The result is excellent validation performance and a model that fails in production, because the signal it learned doesn't exist when it matters.

The classic target leakage example: predicting whether a customer will churn, with a feature like cancellation_reason that is only populated for customers who already churned. The model achieves 99% accuracy by reading the answer. Another: predicting loan default using a recovery_amount field that only exists post-default.

Train–test contamination is subtler: fitting a scaler or imputer on the full dataset before splitting means test-set statistics influenced the training transform. Temporal leakage comes from randomly splitting time-series data so the model trains on the future. Group leakage is the same patient or user appearing in both splits.

Detection: the first heuristic is that suspiciously good results mean leakage until proven otherwise. Then I'd check feature importance for one feature dominating implausibly, ask of every top feature "would I really have this value at prediction time?", and confirm the pipeline fits transformers only on training folds. Prevention beats detection — using a proper Pipeline object makes contamination structurally hard.

Why do you need a validation set if you already have a test set?

Because they answer different questions, and using one set for both destroys the answer to the second.

The validation set is for making decisions during development — which model family, which hyperparameters, when to stop training, which feature set. You look at it many times, and each look adapts your choices to it. That means validation performance is optimistically biased: you've effectively fitted to it through your own decisions.

The test set exists to give one unbiased estimate of generalisation. It works only if it's untouched during development. The moment you tune based on test performance, it stops being a test set and becomes a second validation set — and you're left with no honest estimate of real-world performance at all.

In practice, with limited data I'd use k-fold cross-validation on the training portion instead of a fixed validation split, which uses the data more efficiently and gives a variance estimate too — but I'd still hold out a genuine test set, sealed until the end.

How would you split time-series data?

Chronologically, never randomly. A random split lets the model train on data from after the validation period, so it's effectively seeing the future — a form of leakage that produces wildly optimistic scores and a model that fails the moment it's deployed.

The basic approach is a forward split: train on everything up to a cutoff date, validate on the next window, test on the final window. For cross-validation, use rolling or expanding-window validation — train on months 1–6 and validate on 7, then train on 1–7 and validate on 8, and so on. That mirrors how the model will actually be used and gives several estimates rather than one.

Two additional details I'd raise. A gap between train and validation is often necessary: if you're predicting 7 days ahead, the last week before the validation window shouldn't be in training, or you leak information the model wouldn't have. And any feature engineering involving windows — rolling means, lag features — must use only past data at each point, which is easy to get wrong when computing features on the full series before splitting.

Why start with a simple baseline model?

Four reasons. It sets the bar: on a 95/5 imbalanced problem, predicting the majority class scores 95% accuracy, which immediately tells you both that accuracy is the wrong metric and what your model actually has to beat. Without it, "our model gets 94%" sounds good and is in fact worse than doing nothing.

It validates the pipeline end to end — data loading, splitting, encoding, evaluation — while the model is trivial enough that any bug is obviously in the plumbing rather than the algorithm.

It quantifies the value of complexity. If logistic regression gets 0.82 AUC and a tuned gradient-boosted ensemble gets 0.84, you now have an explicit conversation about whether two points is worth the training cost, latency, and loss of interpretability.

And it surfaces problems early — if a simple model does implausibly well, that's a leakage signal; if nothing beats the baseline, the features probably lack signal and the fix is better data, not a bigger model.

Fit every transformer on the training set only, then apply it to validation and test. Which algorithms need scaling? — a guaranteed question

Need it: anything using distances (KNN, K-means, SVM with RBF), anything using gradient descent (linear/logistic regression, neural nets — unscaled features make the loss surface elongated and convergence slow), and anything using variance (PCA, LDA).

Don’t need it: tree-based models — decision trees, random forests, gradient boosting. A tree splits on “is x > threshold”, and that ordering is unchanged by any monotonic rescaling. Saying why — not just that — is what scores.

Outliers

Detect: Z-score (|z| > 3), IQR rule (outside Q1 − 1.5·IQR or Q3 + 1.5·IQR), Isolation Forest, DBSCAN noise points, or simply a box plot.

Then decide, don’t reflexively delete. An outlier can be a data-entry error (fix or drop), a genuine rare event (keep it — in fraud detection the outliers are the entire point), or a heavy-tailed distribution (transform rather than remove). Options: cap/winsorize at a percentile, log-transform, use robust models (trees, MAE loss), or model them separately.

Feature engineering — where the real gains are

  • Domain features: from a timestamp derive hour, day-of-week, is-weekend, is-holiday, days-since-last-purchase. From latitude/longitude derive distance-to-city-centre. This is usually the single highest-value activity in a project.
  • Interactions: products or ratios of features — BMI from height and weight; price-per-square-foot. Linear models can’t discover these themselves, so you must supply them.
  • Binning: convert a continuous feature into ranges to capture non-linearity in a linear model.
  • Aggregations: per-user mean, count, max over a window — the backbone of most tabular competition solutions.
  • Text: TF-IDF, n-grams, embeddings (Section 23). Cyclical features: encode hour-of-day as sin/cos so 23:00 and 00:00 are adjacent rather than maximally distant.

Feature selection

Filter

Score features independently of any model — correlation with target, chi-square, mutual information, variance threshold. Fast and model-agnostic; ignores feature interactions.

Wrapper

Train a model on subsets — forward selection, backward elimination, RFE. Finds interactions; computationally expensive and can overfit the selection process.

Embedded

Selection happens during training — Lasso drives coefficients to exactly zero; trees give importances. Best balance, and usually what I'd reach for first.

Why bother

Less overfitting, faster training and inference, better interpretability, and mitigation of the curse of dimensionality. Sometimes required for latency or cost reasons.

The curse of dimensionality

As dimensions grow, the volume of the space grows exponentially, so any fixed number of samples becomes exponentially sparse. Two consequences that matter: distances lose meaning — the ratio between the nearest and farthest neighbour approaches 1, which breaks KNN, K-means and RBF-SVM — and the number of samples needed to cover the space grows exponentially, so models overfit. Mitigations: feature selection, dimensionality reduction (Section 18), regularization, and more data.

Interview questions · Section 04
How do you handle missing data?

First I'd ask why it's missing, because the mechanism determines the correct fix. If it's MCAR — unrelated to anything — dropping or simple imputation is safe. If it's MAR, explained by other observed features, I'd impute using those features via KNN or iterative imputation. If it's MNAR, where missingness depends on the hidden value itself — high earners declining to state income — then any imputation introduces bias, and the honest move is to add a missingness indicator and treat absence as signal.

Practically: drop rows only if under ~5% and MCAR; drop a column if it's mostly empty and low value; use median rather than mean for skewed numerics; and for categoricals, treat "Unknown" as its own level rather than filling with the mode, since that preserves information.

Two things I'd always do. Add a binary was_missing flag — it costs nothing and often turns out predictive. And fit the imputer on training data only, applying it to validation and test, because computing the imputation mean on the full dataset is leakage.

For tabular problems I'd also note that XGBoost, LightGBM and CatBoost handle missing values natively by learning a default branch direction at each split, which frequently beats any explicit imputation.

Which algorithms require feature scaling, and why?

Three families need it, for three distinct reasons.

Distance-based algorithms — KNN, K-means, SVM with an RBF kernel — because they compute distances, and a feature measured in rupees (range 0–10⁶) will completely dominate one measured in years (range 0–80). The unscaled feature effectively becomes the only feature.

Gradient-descent-based algorithms — linear and logistic regression, neural networks — because wildly different feature scales create an elongated, ravine-shaped loss surface. Gradient descent then oscillates across the narrow direction and crawls along the long one, so convergence is far slower. Scaling makes the contours more circular and descent direct.

Variance-based methods — PCA and LDA — because they maximise variance, and variance is scale-dependent, so an unscaled large-range feature is chosen as the first principal component regardless of its actual importance.

Tree-based models don't need it. A tree splits on "is x > threshold", and any monotonic rescaling preserves the ordering of values and therefore produces identical splits. That's the reasoning I'd give — it shows I understand the mechanism rather than having memorised a list.

One caveat: regularization is scale-sensitive even for linear models, because the penalty applies uniformly to coefficients, so a feature on a large scale gets an artificially small coefficient and is under-penalised. So scale before Ridge or Lasso.

One-hot vs label encoding — when do you use each?

Label encoding maps categories to integers. It's correct only when the categories have a genuine order — low/medium/high, or education level. For nominal categories it invents a false ordering: encoding cities as Delhi = 0, Mumbai = 1, Chennai = 2 tells a linear model that Chennai is "twice" Mumbai and that Mumbai lies between the other two, which is nonsense and will corrupt the fit.

One-hot encoding creates a binary column per category, imposing no ordering. It's the right default for nominal features with low cardinality — say under 15 levels — in linear models and neural networks.

The nuance that matters: tree models are different. Trees can split on an integer-encoded category directly and don't interpret it as a magnitude, so label encoding is fine. And one-hot actively hurts trees at high cardinality, because 50 sparse binary columns each carry little information, so the tree rarely selects any of them and the feature effectively vanishes. For trees I'd use ordinal, frequency, or a native categorical implementation like LightGBM's.

For very high cardinality — pin codes, product IDs — I'd use target encoding computed out-of-fold with smoothing, or hashing, or learned embeddings in a neural network. And with one-hot in a linear model, drop one column to avoid perfect multicollinearity.

What is the curse of dimensionality?

As the number of features grows, the volume of the feature space grows exponentially, so a fixed dataset becomes exponentially sparser. Ten points cover a line reasonably; the same ten points in 10 dimensions are isolated specks in a mostly-empty space.

Two concrete consequences. First, distance becomes meaningless: in high dimensions the ratio of the farthest to the nearest neighbour distance converges toward 1, so "nearest" stops being distinctive. That directly breaks KNN, K-means and RBF kernels, which are all built on distance.

Second, data requirements explode: to maintain the same density you'd need exponentially more samples, so with realistic data the model has many more parameters than it can support and overfits — it can always find some hyperplane separating the training points, which won't generalise.

Mitigations: feature selection to drop uninformative dimensions; dimensionality reduction like PCA to project onto a lower-dimensional manifold; regularization to constrain the effective capacity; and using models less sensitive to it, such as tree ensembles. The saving grace in practice is that real high-dimensional data usually lies near a much lower-dimensional manifold — which is exactly what makes embeddings and PCA work.

How would you handle outliers?

Detect first, then decide — I wouldn't delete reflexively. For detection: the IQR rule (outside Q1 − 1.5·IQR or Q3 + 1.5·IQR), Z-score beyond ±3 for roughly normal data, or model-based methods like Isolation Forest for multivariate outliers that look normal in each dimension individually.

Then I'd classify what I found. If it's a data error — an age of 300, a negative price — fix it or drop it. If it's a genuine rare event, keep it: in fraud detection, network intrusion or equipment failure, the outliers are the target, and removing them removes the problem. If it reflects a heavy-tailed distribution, like income, the values aren't errors at all and the right response is a log transform, not deletion.

Treatment options short of removal: winsorizing (cap at the 1st and 99th percentiles), log or Box-Cox transformation, robust scaling using median and IQR, or switching to models that tolerate outliers — trees are naturally robust, and MAE loss is far less sensitive than MSE because it doesn't square the error.

And I'd note that outliers should be assessed on the training set only, so the decision doesn't leak test-set information.

What is feature engineering and why does it matter more than the algorithm?

Feature engineering is creating input representations that expose the underlying signal to the model — deriving day-of-week and is-holiday from a timestamp, price-per-square-foot from price and area, days-since-last-purchase from a transaction history.

It matters more than algorithm choice because most models can only learn relationships expressible in the representation they're given. A linear model cannot discover that the ratio of two features is what matters — but hand it that ratio and it succeeds immediately. Between a well-tuned gradient-boosting model and a random forest, the gap is usually a percentage point; between good and poor features, the gap can be enormous.

Techniques worth naming: domain-derived features, interactions and ratios, binning to let linear models capture non-linearity, per-entity aggregations over time windows, and cyclical encoding — representing hour-of-day as sine and cosine so 23:00 and 00:00 are adjacent rather than maximally far apart, which a raw integer encoding gets badly wrong.

The caveat: deep learning inverts this. On images, audio and text, learned representations beat hand-engineered ones decisively, which is exactly why CNNs displaced SIFT and HOG features. So the honest statement is that feature engineering dominates for tabular data, and representation learning dominates for unstructured data.

Bias, Variance, Overfitting & Underfitting

The single most-asked concept in ML interviews. Learn the decomposition, not just the slogan.

The two errors

Bias
Error from wrong assumptions — the model is too simple to represent the true relationship. Fitting a straight line to a curve. High bias → underfitting: poor on training data and poor on test data.
Variance
Error from excessive sensitivity to the training sample — the model memorises noise. Change the training set slightly and the model changes a lot. High variance → overfitting: excellent on training data, poor on test data.
E[(y − f̂(x))2] = Bias[f̂]2 + Var[f̂] + σ2 Expected error = bias² + variance + irreducible noise

The third term, irreducible error, is noise inherent in the problem — measurement error, or genuine randomness. No model can reduce it. Naming it matters: it is why 100% accuracy is often impossible in principle, and it sets the ceiling you are working toward.

How to fix each

Reduce bias (underfitting)
  • Use a more expressive model — polynomial terms, deeper tree, more layers
  • Add or engineer better features
  • Decrease regularization strength
  • Train longer / more boosting rounds
  • Remove restrictive constraints (max_depth, min_samples_leaf)

  • More training data — the most reliable fix
  • Regularization: L1, L2, dropout, weight decay

  • Early stopping on a validation set
  • Ensembling — bagging averages away variance
  • Data augmentation (images, text)
  • Cross-validation for honest model selection
Where common models sit

High bias / low variance: linear regression, logistic regression, Naive Bayes, KNN with large k, shallow trees.
Low bias / high variance: deep unpruned decision trees, KNN with k = 1, high-degree polynomial regression, large neural networks without regularization.

The two ensemble families map exactly onto this: bagging (random forest) takes high-variance models and averages the variance down; boosting takes high-bias weak learners and sequentially reduces bias. That connection is worth stating in both Section 05 and Section 16 answers.

The “double descent” caveat — a strong bonus point

The classical U-shaped curve isn’t the whole story for very large models. As capacity grows past the interpolation threshold — where the model can exactly fit the training data — test error often decreases again. This “double descent” is why massively over-parameterised deep networks and LLMs generalise well despite having far more parameters than samples, which the classical theory says should be catastrophic. Mentioning this signals genuinely current knowledge.

Interview questions · Section 05
Explain the bias–variance tradeoff.

Bias is error from wrong assumptions — the model is too simple to capture the real relationship, like fitting a line to curved data. It shows up as poor performance on training and test data: underfitting.

Variance is error from sensitivity to the particular training sample — the model fits noise as if it were signal. Retrain on a slightly different sample and you get a very different model. It shows up as excellent training performance and poor test performance: overfitting.

Formally, expected squared error decomposes into bias² + variance + irreducible error. The trade-off is that increasing model complexity reduces bias but increases variance, so total error is U-shaped in complexity and the goal is the minimum of the sum — not zero of either. The irreducible term is noise inherent in the problem and sets a ceiling no model can pass.

Concretely: KNN with k = 1 has near-zero bias and huge variance; with k = n it predicts the global mean, so maximum bias and zero variance. A shallow tree is high bias; a fully grown tree is high variance.

And the ensemble connection: bagging reduces variance by averaging many high-variance models, which is what random forests do; boosting reduces bias by sequentially correcting high-bias weak learners.

How do you detect and fix overfitting?

Detection: the signature is a large gap between training and validation performance — say 99% training accuracy and 72% validation. I'd confirm with cross-validation rather than a single split, since one unlucky split can mislead, and by plotting learning curves, where overfitting shows as a persistent gap that's still narrowing as data increases.

Fixes, roughly in order of reliability:

  • More training data — the most dependable cure, since it becomes harder to memorise. For images or text, data augmentation is a cheap synthetic substitute.
  • Regularization — L2 to shrink coefficients, L1 to zero them out entirely, dropout in neural networks, weight decay.
  • Reduce complexity — shallower trees, fewer layers or units, lower polynomial degree, fewer features.
  • Early stopping — halt training when validation loss stops improving, which is effectively free regularization.
  • Ensembling — bagging averages out the variance component.
  • Feature selection — fewer, better features means less opportunity to fit noise.

One thing I'd check first though: if performance is implausibly good on training data, I'd look for data leakage before assuming ordinary overfitting, because the fixes are completely different.

Your model has 99% training accuracy and 65% test accuracy. What's wrong and what do you do?

That 34-point gap is textbook overfitting — high variance. The model has memorised the training set, including its noise, rather than learning generalisable patterns.

Before fixing, I'd rule out two other explanations. First, a distribution shift between train and test — if they were split non-randomly, or the test set comes from a different time period or population, the model may be fine and the split wrong. Second, a bug in the evaluation — different preprocessing applied to test, or label misalignment.

Assuming genuine overfitting, I'd work through: gather more data or augment; add regularization and tune its strength by cross-validation; simplify the model — reduce depth, units, or polynomial degree; apply early stopping; reduce the feature count, especially if I have many features relative to samples; and try a bagged ensemble to average the variance down.

I'd also plot learning curves to confirm more data would actually help, and check that the test set is large enough that 65% isn't just noise — with 100 test samples the confidence interval is roughly ±10 points.

What are learning curves and what do they tell you?

A learning curve plots training and validation error as a function of training-set size. It's the most useful single diagnostic in ML because it tells you whether more data will help — which is expensive to find out empirically.

High bias signature: both curves rise/converge quickly to a high error and sit close together, with the gap already tiny. The model has hit its capacity ceiling. Crucially, more data will not help — the curves have already flattened. The fix is a more expressive model or better features. This is the insight people miss, because "get more data" is the reflexive answer to any poor result.

High variance signature: training error is low, validation error is much higher, and the gap is still closing as data grows. Here more data will help, and so will regularization.

A related curve — error against training epochs rather than data size — diagnoses when to early-stop: the point where validation loss bottoms out and starts rising while training loss keeps falling.

Can a model have both high bias and high variance?

Yes, and it's more common than people expect. The tradeoff describes what happens as you move along a complexity axis for a well-chosen model family — it doesn't guarantee that every model sits on the efficient frontier.

Concrete example: a model with a badly mis-specified functional form and too many parameters relative to the data. A high-degree polynomial fitted to data that's actually exponential is wrong in shape (bias) while also swinging wildly between training points (variance). Similarly, a deep network trained on a tiny dataset with a poorly chosen architecture can underfit the true structure while overfitting the noise.

The practical signature is high training error and an even higher validation error — bad at both. The fix isn't to move along the complexity dial; it's to change the model family, fix the features, or get more data. That distinction is the point of the question: the tradeoff is a curve, and a bad model can sit well above it.

What is irreducible error?

It's the noise inherent in the problem itself — the σ² term in the bias–variance decomposition. It comes from genuine randomness in the process, measurement error, or missing features that were never recorded. No model, however good, can reduce it.

It matters for two practical reasons. It sets the ceiling on achievable performance, sometimes called the Bayes error rate, so if the irreducible error corresponds to 8% misclassification, a model at 9% is nearly optimal and further effort is wasted. Knowing that stops you burning weeks chasing an impossible target.

And it's a useful reality check in interviews: if someone reports 100% accuracy on a genuinely hard real-world problem, the likeliest explanation is data leakage, because most real problems have non-zero irreducible error.

Estimating it is hard, but human-level performance is often a reasonable proxy for tasks humans do well — which is exactly how error analysis in vision and speech is usually framed.

Regularization

L1 vs L2 — the difference, the geometry of why Lasso zeroes coefficients, and everything else that counts as regularization.

Regularization is any technique that adds a constraint or penalty to discourage the model from fitting noise. It deliberately increases bias in exchange for a larger reduction in variance — the trade is worth it whenever the model is overfitting.

The mechanism

Instead of minimising just the loss, minimise the loss plus a penalty on the size of the weights:

J(w) = Loss(w) + λ · Penalty(w) λ = 0 → no regularization · λ → ∞ → all weights driven to zero (maximum bias)

Large weights mean the model is making confident, high-leverage use of particular features, which is exactly what memorising noise looks like. Penalising weight magnitude pushes toward smoother, simpler functions.

Penalty = λ₁ Σ|w| + λ₂ Σw². Combines both: it does feature selection like Lasso while handling correlated features like Ridge. It's the safe default when you have many correlated predictors and want sparsity.

Interview questions · Section 06
What is L1 vs L2 regularization? Why does L1 produce sparsity?

Both add a penalty on weight magnitude to the loss, trading a little bias for a larger reduction in variance. L2 (Ridge) penalises the sum of squared weights; L1 (Lasso) penalises the sum of absolute weights.

The consequence is that L2 shrinks all coefficients smoothly toward zero but never reaches it, while L1 drives some coefficients to exactly zero — so Lasso performs feature selection as part of fitting.

The geometric explanation for why: adding a penalty is equivalent to constraining the weights inside a region. For L2 that region is a circle (a hypersphere); for L1 it's a diamond (an L1 ball). The solution sits where the elliptical loss contours first touch the constraint region. A circle is smooth, so contact occurs at an arbitrary point with both coefficients non-zero. A diamond has corners, and those corners lie on the axes, so contact is disproportionately likely at a corner — where one coefficient is exactly zero.

An equivalent calculus argument: the L1 gradient is a constant ±λ regardless of how small the weight is, so it keeps pushing all the way to zero. The L2 gradient is 2λw, which shrinks as w shrinks, so it asymptotes toward zero without arriving.

Practically: L2 when most features carry some signal and especially when features are correlated, since it distributes weight across a correlated group. L1 when I expect most features to be irrelevant and want a sparse interpretable model. Elastic Net combines both and fixes Lasso's tendency to pick one member of a correlated group arbitrarily.

What is dropout and why does it work?

Dropout randomly sets a fraction of neuron activations to zero during each training step — typically 20–50%. At test time nothing is dropped, and activations are scaled (or equivalently, scaled up during training) so the expected magnitude matches.

Two explanations for why it works. The first is preventing co-adaptation: if any neuron might vanish on any step, no neuron can rely on a specific partner being present, so the network is forced to learn redundant, distributed representations rather than fragile chains that depend on exact combinations — which is what memorising noise looks like.

The second is that dropout approximates an ensemble. Each training step samples a different sub-network, so training with dropout is roughly training exponentially many networks with shared weights, and inference approximates averaging their predictions. Since averaging reduces variance, that's regularization.

Practical notes: it must be disabled at inference (frameworks handle this via train/eval mode, and forgetting it is a classic bug); it's applied to fully-connected layers more than convolutional ones, since convolutions already share weights heavily; and it's used far less in modern transformer architectures, where batch/layer normalization, weight decay and sheer data volume do most of the regularizing.

How do you choose the regularization strength λ?

By cross-validation — never by looking at training error, since training error decreases monotonically as λ decreases and would always select λ = 0.

Concretely: define a grid of λ values on a logarithmic scale, because the useful range spans orders of magnitude — something like 10⁻⁴ to 10². For each value, run k-fold cross-validation on the training data and record the mean validation error. Pick the λ minimising it, then refit on the full training set with that value.

Two refinements worth mentioning. Plotting validation error against λ gives the characteristic U-shape, and if the minimum sits at the edge of my grid, the grid was too narrow and I should extend it. And the one-standard-error rule is a good default: rather than the exact minimum, choose the largest λ whose error is within one standard error of the best. That picks a simpler, more strongly regularized model at negligible cost in accuracy, and it generalises more reliably.

For Elastic Net there are two hyperparameters — overall strength and the L1/L2 mix — so I'd search both, and for efficiency use the fact that coordinate descent can compute the whole regularization path cheaply.

Why does regularization reduce overfitting?

Because it restricts the effective capacity of the model. Overfitting happens when a model has enough freedom to fit the noise in the training sample; regularization removes some of that freedom.

Mechanically, large weights are what let a model produce sharp, high-leverage responses to small feature changes — which is exactly the shape of a function that has memorised individual training points. Penalising weight magnitude biases the optimiser toward smoother functions that can't swing wildly between data points.

In bias–variance terms, regularization deliberately increases bias to decrease variance. That's a good trade whenever variance is the dominant error term — which is the case whenever you're overfitting. If the model is already underfitting, adding regularization makes things strictly worse, which is why λ has to be tuned rather than set on principle.

There's also a Bayesian reading worth mentioning: L2 regularization is exactly equivalent to placing a Gaussian prior on the weights and finding the maximum a posteriori estimate, and L1 corresponds to a Laplace prior. So regularization is formally the same thing as encoding a prior belief that weights should be small.

Is early stopping a form of regularization?

Yes. You monitor validation loss during training and stop when it stops improving — even though training loss is still falling — then keep the weights from the best validation epoch.

It's regularization because it limits how far the optimiser can travel from its initialisation, which limits how large the weights can grow. For linear models trained with gradient descent, early stopping can be shown to be approximately equivalent to L2 regularization, with the number of epochs playing the role of 1/λ.

The practical appeal is that it's essentially free — no extra hyperparameter to search, no extra compute, and it doubles as a way to avoid wasting time on epochs that don't help. In practice you use a patience parameter, waiting some number of epochs before concluding validation loss has genuinely plateaued, because validation curves are noisy and stopping at the first uptick is premature.

One caveat: it entangles optimisation and regularization, so you can't tune them independently. If I want both a well-converged model and strong regularization, explicit weight decay plus early stopping is more controllable than early stopping alone.

Why accuracy is usually the wrong metric

A cancer screening dataset is 99% healthy. A model that predicts “healthy” for everyone scores 99% accuracy and detects zero cancers. Accuracy is only meaningful when classes are balanced and both error types cost the same — which is almost never true.

Why F1 uses the harmonic mean

Because the harmonic mean punishes imbalance. Precision 1.0 and recall 0.0 gives an arithmetic mean of 0.5 — which flatters a useless model — but a harmonic mean of 0. F1 is high only when both are high, which is the entire point of having it.

A worked example — do this by hand once

The precision–recall tradeoff

Every classifier outputs a probability; the threshold turns it into a label. Lowering the threshold flags more items — recall rises, precision falls. Raising it does the reverse. You do not have to accept 0.5. Choosing the threshold from the business cost of each error type is a mark of practical experience.

ROC-AUC vs PR-AUC — the distinction that scores

ROC plots TPR against FPR = FP / (FP + TN). On a 1%-positive dataset, TN is enormous, so even a large number of false positives barely moves FPR — the curve looks great while precision is terrible. PR-AUC uses precision, which has no TN term at all, so it cannot be flattered by the abundant negative class.

Rule: use ROC-AUC for roughly balanced problems and for comparing rankers; use PR-AUC when the positive class is rare and is the class you care about.

Interview questions · Section 07
Explain precision and recall. When would you optimise each?

Precision = TP / (TP + FP) — of everything I predicted positive, what fraction actually was. It answers "when I raise an alarm, can it be trusted?"

Recall = TP / (TP + FN) — of everything that actually was positive, what fraction did I find. It answers "am I missing cases?"

The memory device: precision reads down the predicted-positive column of the confusion matrix; recall reads across the actual-positive row.

Optimise precision when false positives are expensive. A spam filter sending a real job offer to the spam folder is far worse than letting one spam email through, so I'd want high precision. Same for recommendation systems and ad targeting, where irrelevant suggestions erode trust and waste budget.

Optimise recall when false negatives are expensive. Cancer screening: missing a real case can be fatal, while a false positive costs a follow-up test. Same for fraud detection and security threat detection — you accept extra review workload to avoid misses.

The two trade off through the decision threshold, so in practice I'd frame it as a business question: fix the acceptable level of one and maximise the other. "Maximise recall subject to precision ≥ 0.6, because the review team can only handle so many alerts" is a much better answer than "optimise F1", because it reflects an actual operational constraint.

Your dataset is 99% negative and your model has 99% accuracy. Is it good?

Almost certainly not — that's exactly what a model predicting "negative" for every input would score. Accuracy is dominated by the majority class, so on severe imbalance it's uninformative by construction.

I'd immediately look at the confusion matrix to see whether the model ever predicts the positive class at all, and then at precision, recall and F1 for the positive class specifically, since that's the class anyone cares about. If recall is near zero, the model has learned nothing useful regardless of its accuracy.

For threshold-independent assessment I'd use PR-AUC rather than ROC-AUC. ROC-AUC can look strong here because its false-positive rate has an enormous true-negative denominator, so even many false positives barely move it. Precision has no TN term, so PR-AUC can't be flattered the same way.

Then I'd fix the underlying setup: adjust the decision threshold rather than accepting 0.5, apply class weighting or resampling, and pick the operating point from the relative cost of a false negative versus a false positive.

Explain ROC-AUC. What does AUC = 0.8 mean?

The ROC curve plots the true positive rate against the false positive rate as you sweep the decision threshold from 1 to 0. AUC is the area beneath it, summarising performance across all thresholds in one number, so it measures ranking quality independent of any particular operating point.

AUC = 0.8 has a precise probabilistic interpretation: if you draw one random positive and one random negative example, there's an 80% chance the model assigns the positive a higher score. That's the cleanest way to state it, and it's what makes AUC meaningful rather than arbitrary.

Reference points: 0.5 is random guessing (the diagonal), 1.0 is perfect separation, and below 0.5 means the model is anti-correlated — you could invert its predictions and do better, which usually signals a label bug.

Two limitations I'd raise unprompted. On heavily imbalanced data AUC is over-optimistic, because the FPR denominator is dominated by abundant true negatives, so PR-AUC is more informative. And AUC measures only ranking, not calibration — a model can have perfect AUC while its predicted probabilities are systematically wrong, which matters whenever the probability itself feeds a decision.

MSE or MAE — which would you use?

It depends on how I want large errors treated, and that's a domain question rather than a statistical one.

MSE squares the errors, so a single error of 10 contributes as much as a hundred errors of 1. Use it when large errors are disproportionately bad — being 50°C wrong in a temperature control system is far worse than being 5°C wrong ten times. It's also differentiable everywhere and has a convenient gradient, which is why it's the default training loss, and it corresponds to maximum likelihood under Gaussian noise.

MAE weights every error equally and is therefore robust to outliers. Use it when the data has genuine anomalies you don't want dominating the fit — a few extreme house prices shouldn't drag the whole model. It's also more interpretable: "average error of ₹40 000" is directly meaningful, while MSE's units are squared.

A useful statistical framing: minimising MSE predicts the conditional mean, minimising MAE predicts the conditional median. So if the target is skewed and you want a typical-case prediction, MAE is the better target.

In practice I'd often use Huber loss, which is quadratic near zero and linear in the tails — outlier-robust like MAE but differentiable everywhere like MSE. And I'd report RMSE rather than MSE, since it's back in the target's units.

What is R² and can it be negative?

R² is the fraction of variance in the target explained by the model: 1 − (residual sum of squares / total sum of squares). R² = 0.75 means the model explains 75% of the variability, with the remainder unexplained.

The reference points matter: R² = 0 means the model does exactly as well as predicting the mean for every input, and R² = 1 is a perfect fit.

Yes, it can be negative — and that's a genuinely useful diagnostic. It happens when the residual sum of squares exceeds the total, meaning the model is worse than just predicting the mean. On training data with an intercept-fitted linear model that's impossible, but on a test set it happens regularly, and it usually indicates severe overfitting, a distribution shift between train and test, or a model that was fitted without an intercept.

One caveat I'd add: plain R² never decreases when you add a feature, even a random one, so it can't be used to compare models with different numbers of predictors. Adjusted R² penalises extra parameters and is the correct choice there.

How would you choose the classification threshold?

Not by defaulting to 0.5 — that's an arbitrary convention with no claim to optimality. I'd derive it from the relative cost of the two error types.

The most rigorous approach is cost-sensitive: assign a cost to a false positive and a false negative, then pick the threshold minimising expected total cost across the validation set. If missing a fraudulent transaction costs ₹5 000 and reviewing a false alarm costs ₹50, the maths pushes the threshold much lower than 0.5.

When costs aren't quantifiable, I'd use an operational constraint: "the review team can process 200 alerts a day, so set the threshold that produces 200 alerts and report the resulting recall." That's usually how it works in practice and it's a very credible answer.

Other approaches: maximise F1 if both errors genuinely matter equally; use Youden's J (TPR − FPR) to pick the point furthest from the ROC diagonal; or choose from the PR curve to hit a target precision.

Two important details: tune the threshold on the validation set, not the test set, and check the model is reasonably calibrated first — if the probabilities are systematically wrong, threshold choice is built on sand and calibration should come first.

What is model calibration and why does it matter?

A model is calibrated when its predicted probabilities match observed frequencies — among all cases it scores at 0.7, roughly 70% should genuinely be positive. It's a different property from discrimination: a model can rank perfectly (AUC = 1) while every probability it emits is badly wrong.

It matters whenever the probability itself drives a decision rather than just the ranking. In expected-value calculations — insurance pricing, credit risk, bidding, medical decision support — you multiply the probability by a cost, so an uncalibrated 0.9 that really means 0.6 produces systematically wrong decisions. If you only need to rank and pick a top-k, calibration doesn't matter.

I'd check it with a reliability diagram: bin predictions by predicted probability and plot the observed positive rate per bin against the bin's midpoint. Perfect calibration is the diagonal; a curve below it means overconfidence. Expected Calibration Error summarises this in a number.

Fixes are post-hoc and fitted on held-out data: Platt scaling fits a logistic function to the model's scores, and isotonic regression fits a non-parametric monotonic mapping — more flexible but needs more data. Worth knowing which models need it: SVMs and boosted trees are typically poorly calibrated, deep networks tend to be overconfident, and logistic regression is naturally well calibrated because it optimises log loss directly.

Interview questions · Section 08
What is k-fold cross-validation and why use it?

You split the training data into k equal folds. For each of k rounds, one fold is held out for validation and the model trains on the other k−1. You then average the k validation scores, and report the standard deviation alongside.

The reason to use it over a single train/validation split is that one split gives one estimate, and that estimate is noisy — an unlucky split can make a good model look poor. With a small dataset the variance is severe. Cross-validation uses every point for validation exactly once, so it makes far better use of limited data and gives a more stable estimate.

The standard deviation across folds is as informative as the mean: a model scoring 0.85 ± 0.02 is far more trustworthy than one scoring 0.86 ± 0.15, where performance depends heavily on which data it saw.

k = 5 or 10 is standard. Smaller k trains on less data so estimates are pessimistic; k = n is leave-one-out, which is nearly unbiased but has high variance because the training sets overlap almost completely, and costs n model fits.

For classification I'd always use stratified k-fold to preserve class proportions in each fold, and for time series I'd use a forward-chaining split instead, since random folds would train on the future.

Grid search vs random search — which is better?

For a fixed compute budget, random search is usually better, and the reason is a genuinely interesting result from Bergstra and Bengio.

In most problems only a small number of hyperparameters materially affect performance. Suppose you have three hyperparameters and can afford 27 runs. A 3×3×3 grid tests only three distinct values of the one parameter that actually matters — the other 24 runs are repeats of those three values with different settings of parameters that don't matter. Random search with the same 27 runs tests 27 distinct values of every parameter, so it explores the important dimension nine times more finely.

Random search also handles continuous ranges naturally, lets you sample from sensible distributions (log-uniform for learning rates), and can be stopped at any point since every sample is independent.

Grid search still has its place: with one or two hyperparameters over a small discrete set it's exhaustive and reproducible.

But for anything expensive I'd go further and use Bayesian optimisation via Optuna or Hyperopt, which builds a surrogate model of the objective and samples where improvement is most likely — reaching good configurations in far fewer trials. Or Hyperband, which starts many configurations with a small budget and progressively kills the weak ones.

How do you handle imbalanced datasets?

First, I'd fix the evaluation, because that's where imbalance does most damage. Drop accuracy; use precision, recall and F1 on the minority class, and PR-AUC rather than ROC-AUC. Without this, everything downstream is measured wrongly.

Then, in rough order of what I'd try:

  • Threshold tuning — often the whole solution. The model may already rank well; 0.5 is just the wrong operating point. Costs nothing and invents no data.
  • Class weights — penalise minority errors more heavily in the loss, via class_weight='balanced' or scale_pos_weight in XGBoost. Nothing is discarded or fabricated.
  • Resampling — undersampling the majority (viable only with plenty of data, since it throws information away) or oversampling the minority. SMOTE synthesises new minority points by interpolating between neighbours rather than duplicating, which reduces overfitting to repeated points.
  • Specialised ensembles like BalancedRandomForest.
  • If the positive class is extremely rare — well under 1% — I'd consider reframing it as anomaly detection rather than classification.

The critical implementation detail: resampling must happen inside each CV fold, on the training portion only. Applying SMOTE before splitting means synthetic points derived from training examples leak into validation, which inflates scores dramatically and is one of the most common bugs in ML code.

What is nested cross-validation and when do you need it?

Nested CV uses two loops. The inner loop performs cross-validation on the training folds to select hyperparameters. The outer loop takes the model tuned by the inner loop and evaluates it on data the inner loop never saw. Averaging the outer scores gives an unbiased estimate.

You need it because of a subtle bias: if you use 5-fold CV to choose hyperparameters and then report that same CV score, the estimate is optimistic. You selected the configuration that happened to perform best on those particular folds, so some of that performance is fitting to fold noise rather than genuine skill. With a large hyperparameter search the inflation can be substantial.

Nested CV separates the two jobs: the inner loop does selection, the outer loop measures how well the entire tuning procedure generalises — which is the honest quantity, since the procedure is what you'd rerun on new data.

The cost is multiplicative: 5 outer × 5 inner folds × the size of the hyperparameter grid. So in practice I'd use it when the dataset is small (where the bias is worst and compute is cheap) or when reporting results that need to be defensible, such as in research. For a large dataset, a simple held-out test set achieves the same thing far more cheaply.

Why can't you use random k-fold on time-series data?

Because it lets the model train on the future and predict the past, which is impossible at deployment time. A random fold puts data from March in training and data from February in validation, so the model has effectively seen what it's meant to forecast — leakage that produces excellent validation scores and a model that fails immediately in production.

There's a second, subtler problem: time series are autocorrelated. Adjacent points are highly similar, so a randomly held-out point almost certainly has its immediate neighbours in the training set — the model can nearly interpolate rather than genuinely forecast.

The correct approach is forward-chaining: train on months 1–6, validate on 7; train on 1–7, validate on 8; and so on, either with an expanding window or a fixed-size rolling one. This mirrors real usage and gives several estimates across different periods, which also reveals whether performance is degrading over time.

Two further details: leave a gap between train and validation matching the forecast horizon, so a 7-day-ahead model doesn't train on the six days immediately preceding the target. And any window-based features — rolling means, lags — must be computed using only past data at each point, which is easy to get wrong if you engineer features on the full series before splitting.

Interview questions · Section 09
Explain linear regression and its cost function.

Linear regression models the target as a weighted sum of the features plus an intercept: ŷ = w₀ + w₁x₁ + … + wdxd. Each weight is the expected change in the target per unit change in that feature, holding the others constant.

The cost function is mean squared error — the average of the squared vertical distances between predictions and actual values. We square rather than take absolutes for three reasons: it's differentiable everywhere, so gradient methods work cleanly; it penalises large errors disproportionately; and it has a closed-form solution.

There are two ways to minimise it. The normal equation, w = (XᵀX)⁻¹Xᵀy, gives the exact answer in one step with no hyperparameters — but inverting a d×d matrix costs O(d³), so it's impractical beyond roughly ten thousand features, and it fails outright if XᵀX is singular, which happens with perfectly correlated features or when features outnumber samples. Gradient descent iterates toward the minimum at O(nd) per step, scales to large problems and supports streaming, but needs a learning rate and feature scaling.

A nice property worth adding: MSE is convex for linear regression, so there's a single global minimum and no risk of getting stuck in a local one — which is not true for neural networks.

What are the assumptions of linear regression?

Five, and I use the mnemonic LINE-M.

  • Linearity — the relationship between features and target is actually linear. I'd check with a residuals-versus-fitted plot; any curve or pattern means it's violated. Fix with polynomial terms, splines, a log transform, or a non-linear model.
  • Independence of errors — one observation's error tells you nothing about another's. Commonly violated by time-series data through autocorrelation; the Durbin–Watson statistic tests it.
  • Normality of residuals — needed for valid confidence intervals and p-values, but not for the coefficient estimates themselves, which are unbiased regardless. Check with a Q–Q plot.
  • Equal variance (homoscedasticity) — residual spread is constant across the range of predictions. A funnel shape means heteroscedasticity, which makes standard errors wrong. Fix by log-transforming the target or using weighted least squares.
  • No multicollinearity — features aren't strongly correlated with each other. Check with VIF; above 5–10 is concerning.

The nuance I'd add: these assumptions matter mainly for inference — trusting the coefficients and their p-values. If you only care about prediction, mild violations often don't hurt much, and you'd be better served by cross-validated predictive performance than by assumption tests.

What is multicollinearity and does it hurt predictions?

Multicollinearity is when two or more features are highly correlated with each other — height in centimetres and height in inches, or total price and unit price times quantity.

The honest answer to whether it hurts predictions is not much. The model can still fit the data well and predict accurately on similar data, because the redundant information is still all there.

What it destroys is interpretability and stability. If two features are nearly identical, many different weight combinations produce nearly identical predictions — the optimisation problem becomes ill-conditioned. Coefficients then become large, unstable, and can flip sign entirely with a small change in the data, so you can't say "a one-unit increase in this feature causes that change" with any confidence. Standard errors inflate and p-values become unreliable, so features that genuinely matter may appear insignificant.

Detection: a correlation matrix catches pairwise cases, but Variance Inflation Factor is better because it catches multi-way relationships — VIF above 5 or 10 is a flag.

Fixes: drop one of the pair, combine them into a single feature, apply PCA, or use Ridge regression, which handles it elegantly by shrinking correlated coefficients toward each other rather than letting them explode in opposite directions.

When would you use the normal equation vs gradient descent?

Normal equation when the number of features is modest — up to roughly ten thousand. It gives the exact optimum in one step, requires no learning rate, no iteration count and no feature scaling, so there's nothing to tune and nothing to converge. For a typical tabular problem with a few dozen features it's simply the right answer.

Gradient descent when the feature count is large, because the normal equation requires inverting a d×d matrix at O(d³) cost — at 100 000 features that's completely infeasible, whereas gradient descent is O(nd) per iteration. It's also the only option when data arrives as a stream and you want online updates, and it's what generalises to models with no closed form — logistic regression, neural networks — so it's the more broadly useful tool to understand.

One more consideration: the normal equation breaks when XᵀX is singular, which happens with perfectly correlated features or when features outnumber samples. Gradient descent still runs, and adding L2 regularization fixes the singularity in the closed form too, since (XᵀX + λI) is always invertible for λ > 0.

Why use squared error rather than absolute error?

Three reasons, and the honest answer is that it's a default rather than always the right choice.

Mathematical convenience: the squared error is differentiable everywhere, including at zero, so gradient-based optimisation works cleanly. Absolute error has a kink at zero where the derivative is undefined, requiring subgradient methods. Squared error also yields a closed-form solution; absolute error does not.

Penalty structure: squaring makes large errors count disproportionately, so the model works hard to avoid big misses. That's appropriate when large errors are genuinely much worse than small ones.

Statistical justification: minimising squared error is exactly maximum likelihood estimation under the assumption of Gaussian errors — so if the noise is normally distributed, least squares is the principled choice, not just a convenient one.

The trade-off is that squaring makes it very sensitive to outliers — a single extreme point can dominate the fit. So with outlier-prone data I'd use MAE, which is robust and predicts the conditional median rather than the mean, or Huber loss, which is quadratic near zero and linear in the tails and gets both robustness and differentiability.

Interview questions · Section 10
Explain gradient descent.

It's an iterative optimisation algorithm for finding parameters that minimise a loss function. The intuition is descending a foggy hillside: you can't see the bottom, but you can feel the slope, so you step downhill and repeat.

Concretely, you compute the gradient of the loss with respect to the parameters — the vector of partial derivatives, which points in the direction of steepest increase — then move in the opposite direction, scaled by the learning rate: w := w − α∇J(w). Repeat until the gradient is near zero or improvement stalls.

The learning rate is the critical hyperparameter. Too large and the updates overshoot the minimum and can diverge with the loss going to NaN; too small and training takes forever or stalls on a plateau.

Why it's used at all: for linear regression there's a closed-form solution, so gradient descent isn't necessary — but for logistic regression, neural networks and most modern models no closed form exists, and gradient descent scales to millions of parameters where matrix inversion cannot. It's the workhorse behind essentially all of deep learning.

One important detail: for convex losses like linear or logistic regression there's a single global minimum, so gradient descent is guaranteed to find it. Neural network losses are non-convex, so you're finding a good local solution, not a provably optimal one.

Batch vs stochastic vs mini-batch gradient descent?

They differ in how many samples are used to compute each update.

Batch uses the entire dataset per update. The gradient is exact so the path to the minimum is smooth and direct, but each step is expensive, the whole dataset must fit in memory, and being deterministic it can't escape a poor region.

Stochastic uses one sample per update. Updates are extremely fast and the noise can help jump out of sharp minima, but the path is erratic, it never quite settles without decaying the learning rate, and — crucially — it can't exploit a GPU, which is designed for massively parallel identical operations.

Mini-batch uses a small batch, typically 32 to 512. This is what's used in practice, and not just as a compromise: the batch is large enough to saturate GPU parallelism and give a reasonably stable gradient estimate, while small enough to make frequent updates. The residual noise also acts as a mild regularizer.

On batch size specifically: larger batches give more stable gradients and better hardware utilisation but tend to converge to sharper minima that generalise slightly worse, and each epoch requires fewer updates. Smaller batches generalise a little better but are noisier. There's also a scaling relationship worth knowing — if you increase the batch size, you generally need to increase the learning rate proportionally.

What happens if the learning rate is too high or too low?

Too high: each step overshoots the minimum. In the mild case the loss oscillates and never settles; in the severe case it grows each step and diverges to infinity or NaN. Seeing NaN loss within a few iterations is almost always a learning rate problem — the standard first response is to divide it by ten.

Too low: training converges, but extremely slowly, so you may run out of time or patience before reaching a good solution. Worse, a small learning rate makes it easy to stall on a plateau or in a shallow local region, because there's not enough momentum to escape, and the model appears converged when it's merely stuck.

How I'd find a good value: a learning-rate range test — train for a few hundred iterations while exponentially increasing α, and plot loss against α. The loss falls, reaches a minimum, then explodes; pick a value slightly below where it starts rising. That's far more efficient than grid searching.

In practice I'd also use a schedule rather than a fixed rate — starting higher for fast early progress and decaying it so the model can settle precisely, with cosine annealing being a common modern default. And adaptive optimisers like Adam reduce the sensitivity considerably, which is why they're the usual starting point.

How does gradient descent get stuck, and how do you avoid it?

The textbook answer is local minima, but for high-dimensional models that's misleading and worth correcting.

In deep networks, true local minima are rare. For a point to be a local minimum, the loss must curve upward in every one of millions of parameter directions — statistically very unlikely. What you actually encounter are saddle points, where the surface curves up in some directions and down in others, and long flat plateaus where the gradient is nearly zero so progress crawls.

The fixes: momentum accumulates a velocity term so the optimiser carries through flat regions rather than stalling. Adaptive optimisers like Adam and RMSprop scale the step size per parameter, taking larger steps where gradients have been persistently small. Mini-batch noise itself helps, since the stochastic gradient rarely sits exactly at a saddle. And good initialization — He or Xavier — starts you in a region with healthy gradient magnitudes.

Two other causes of apparent stalling worth naming: vanishing gradients in deep networks, addressed with ReLU activations, batch normalization and residual connections; and unscaled features, which create an elongated ravine-shaped loss surface where descent zig-zags — fixed simply by standardizing.

Why do you need feature scaling for gradient descent?

Because unscaled features distort the shape of the loss surface. If one feature ranges 0–1 and another ranges 0–100 000, the loss contours become extremely elongated ellipses — a narrow ravine rather than a bowl.

Gradient descent always steps perpendicular to the contours, so in a ravine it bounces back and forth across the narrow direction while creeping slowly along the long axis. You're forced to use a small learning rate to avoid diverging in the steep direction, which makes progress along the shallow direction glacial. Convergence can take orders of magnitude longer than necessary.

After standardizing to mean 0 and standard deviation 1, the contours become roughly circular, so the negative gradient points more or less straight at the minimum and a single learning rate is appropriate for all parameters.

Two related points: the same reasoning is why adaptive optimisers like Adam help — they effectively give each parameter its own learning rate, partially compensating for scale differences. And batch normalization in deep networks applies the same idea to internal activations, keeping every layer's inputs well-conditioned rather than just the first one.

Logistic Regression

A classifier despite the name — and the model whose loss function every neural network classifier reuses.

Why not just use linear regression for classification?

Three reasons, worth knowing as a set: linear regression outputs values below 0 and above 1, which cannot be probabilities; it is extremely sensitive to outliers, since one distant point drags the whole line and shifts the decision boundary; and squared error on a classification target is non-convex when passed through a sigmoid, so optimisation is unreliable.

The sigmoid

Logistic regression computes a linear score, then squashes it into (0, 1) with the sigmoid function:

z = wTx + b ,   σ(z) = 11 + e−z σ(0) = 0.5 · σ(∞) → 1 · σ(−∞) → 0 · the curve is S-shaped and always between 0 and 1

The loss: binary cross-entropy (log loss)

J = − 1n Σ [ y log(p) + (1−y) log(1−p) ] If y = 1, only the first term survives → −log(p). If y = 0, only the second → −log(1−p).
Read the loss out loud — it explains itself

Suppose the true label is 1. The loss is −log(p). If the model predicts p = 0.99, loss ≈ 0.01 — almost free. If it predicts p = 0.5, loss ≈ 0.69. If it confidently predicts p = 0.01, loss ≈ 4.6 — enormous. As p → 0 the loss → ∞. Cross-entropy punishes confident wrongness savagely, which is exactly the behaviour you want from a probabilistic classifier.

This loss comes from maximum likelihood estimation: maximising the probability of observing the training labels under the model is mathematically identical to minimising the negative log-likelihood, which is this expression. And critically, it is convex in the weights, so gradient descent finds the global optimum — which squared error would not guarantee.

Odds and interpretability

Rearranging the sigmoid gives the logit: log(p / (1 − p)) = wTx + b. So logistic regression is linear in the log-odds.

That gives coefficients a clean meaning: a one-unit increase in xj multiplies the odds by ewj. If wj = 0.7, then e0.7 ≈ 2, so the odds double. This interpretability is why logistic regression is still standard in credit scoring and medicine, where a regulator may require an explanation.

Multi-class extension

  • Softmax (multinomial): one weight vector per class; softmax normalises the scores into probabilities summing to 1. This is the standard, and it's exactly the output layer of a neural network classifier.
  • One-vs-Rest: train K binary classifiers, each "class k vs everything else"; pick the highest score. Simple, but the probabilities aren't calibrated against each other.
  • One-vs-One: train K(K−1)/2 pairwise classifiers and vote. More models but each trains on less data — used by SVMs.
Strengths and limits

Strengths: fast to train and predict, outputs well-calibrated probabilities, highly interpretable coefficients, works well on high-dimensional sparse data (text), extends naturally with L1/L2 regularization, and is an excellent baseline.

Limits: the decision boundary is linear, so it cannot solve XOR-like problems without engineered interaction or polynomial features; it assumes independent observations; it's sensitive to strongly correlated features; and it can fail to converge under perfect separation, where the classes are exactly separable and the weights would grow to infinity to make the sigmoid maximally steep — which is another reason regularization is applied by default.

Interview questions · Section 11
Explain logistic regression. Why is it called regression if it does classification?

Logistic regression computes a linear combination of features, z = wᵀx + b, then passes it through the sigmoid function 1/(1+e⁻ᶻ), which maps any real number into (0, 1) so it can be read as a probability. You then threshold that probability to get a class label.

It's called "regression" because it is genuinely performing a linear regression — just not on the target directly. Rearranging the sigmoid shows the model is linear in the log-odds: log(p/(1−p)) = wᵀx + b. So it regresses the logit, and the sigmoid is simply the inverse transform back to probability space.

The loss is binary cross-entropy, derived from maximum likelihood — maximising the probability of the observed labels is equivalent to minimising the negative log-likelihood. Squared error isn't used because it's non-convex when composed with the sigmoid, so optimisation could get stuck, whereas cross-entropy is convex and gradient descent finds the global optimum.

The practical appeal is interpretability: a coefficient of 0.7 means a one-unit increase in that feature multiplies the odds by e⁰·⁷ ≈ 2. That's why it remains standard in credit scoring and clinical settings where decisions must be explainable.

Why not use MSE as the loss for logistic regression?

Two reasons, and the first is the important one.

Non-convexity. When you compose squared error with the sigmoid, the resulting loss surface is non-convex — it has multiple local minima. Gradient descent could converge to a poor solution depending on initialization, and you'd have no guarantee of optimality. Cross-entropy composed with the sigmoid is convex, so there's a single global minimum and gradient descent is guaranteed to find it.

Vanishing gradients. With MSE, the gradient includes the derivative of the sigmoid, σ'(z) = σ(z)(1−σ(z)), which approaches zero when the model is confidently wrong — say predicting 0.001 when the true label is 1. So exactly when the model is most wrong, it learns most slowly. With cross-entropy, the sigmoid derivative cancels algebraically and the gradient reduces to simply (p − y) times the input, so the update is proportional to the error. Confidently wrong means a large gradient and fast correction, which is the behaviour you want.

There's also a principled justification: cross-entropy is the maximum-likelihood loss for a Bernoulli target, whereas MSE is the maximum-likelihood loss under Gaussian noise — which isn't the right noise model for binary outcomes.

How do you extend logistic regression to multi-class problems?

Three approaches.

Softmax regression (multinomial logistic regression) is the standard. You learn one weight vector per class, compute a score for each, then apply softmax — exponentiate each score and divide by the sum — so the outputs are positive and sum to 1, forming a proper probability distribution. It's trained with categorical cross-entropy. This is exactly the output layer of a neural network classifier, which is worth pointing out.

One-vs-Rest trains K binary classifiers, each distinguishing one class from all others, and predicts the class with the highest score. It's simple and only needs K models, but the classifiers are trained independently so their probabilities aren't calibrated against one another, and each one faces an artificially imbalanced problem.

One-vs-One trains K(K−1)/2 classifiers, one per pair of classes, and takes a majority vote. That's many more models, but each trains on only the two relevant classes so training is fast and each sub-problem is easier. It's the approach SVMs typically use, since SVM training scales poorly with dataset size.

I'd default to softmax because it directly models the joint distribution over classes and gives coherent probabilities, unless I had a specific reason such as needing multi-label outputs — where classes aren't mutually exclusive — in which case I'd use independent sigmoids rather than softmax.

Can logistic regression solve a non-linear problem like XOR?

Not in its raw form. Logistic regression produces a linear decision boundary — the sigmoid squashes the output but is monotonic, so it can't bend the boundary. XOR isn't linearly separable: no single straight line separates the (0,0),(1,1) class from the (0,1),(1,0) class, so logistic regression on the raw features cannot exceed chance.

But it can be made to work by changing the representation. If I add the interaction feature x₁·x₂, the problem becomes linearly separable in the expanded three-dimensional space, and logistic regression solves it exactly. The same trick generalises: polynomial features, basis expansions, or any engineered non-linear transform.

That's the key insight — logistic regression is linear in the features it is given, so its power depends entirely on the feature representation. It's also precisely why neural networks exist: rather than a human hand-crafting the transformation, hidden layers learn a representation in which the final linear layer can separate the classes. A neural network's output layer is literally logistic or softmax regression on learned features.

The alternatives if I didn't want to engineer features: an SVM with an RBF kernel, a decision tree, or a neural network — all of which produce non-linear boundaries natively.

What is the difference between linear and logistic regression?

Output: linear regression predicts an unbounded continuous value; logistic regression predicts a probability in (0, 1) which is then thresholded into a class.

Function: linear regression is just wᵀx + b; logistic regression passes that through the sigmoid.

Loss: linear uses mean squared error, derived from maximum likelihood under Gaussian noise; logistic uses cross-entropy, derived from maximum likelihood under a Bernoulli distribution.

Solution method: linear regression has a closed-form solution via the normal equation; logistic regression does not, so it must be fitted iteratively with gradient descent or Newton-based methods.

Interpretation of coefficients: in linear regression a coefficient is the change in the target per unit change in the feature; in logistic regression it's the change in log-odds, so exponentiating it gives a multiplicative effect on the odds.

What they share is more interesting: both are generalized linear models with a linear predictor wᵀx + b at their core, differing only in the link function and the assumed noise distribution. Understanding them as one family rather than two unrelated algorithms is the framing that generalises.

K-Nearest Neighbours

The algorithm with no training phase — and the clearest illustration of the bias–variance tradeoff you will find.

The idea

To classify a new point, find the k closest points in the training set and take a majority vote. For regression, average their values. That is the entire algorithm.

Lazy learning

KNN is the archetypal lazy learner — it does no work at training time, simply storing the dataset. All computation is deferred to prediction. This inverts the usual cost profile: training is O(1), prediction is O(n · d) per query, and memory is O(n · d) forever. It's also non-parametric and instance-based — it makes no assumption about the shape of the decision boundary, which is its main strength.

Interview questions · Section 12
How does KNN work, and how do you choose k?

To predict for a new point, compute its distance to every training point, take the k nearest, and either majority-vote their labels for classification or average their values for regression. There's no training phase — the model just stores the data, which is why it's called a lazy learner.

Choosing k is a direct bias–variance decision. With k = 1, the boundary wraps tightly around every training point, so bias is near zero and variance is enormous — a single mislabelled neighbour flips the prediction, and the model memorises noise. With k = n, every prediction is the global majority class, so variance is zero and bias is maximal.

In practice I'd tune k by cross-validation over a range, plotting validation error against k, which typically gives a U-shape whose minimum is the right value. √n is a reasonable starting point. For binary classification I'd use an odd k so votes can't tie.

A refinement worth mentioning: distance-weighted voting, where each neighbour's vote is weighted by 1/distance, so closer points count more. It makes the result much less sensitive to the exact choice of k and generally improves accuracy.

Why must you scale features before using KNN?

Because KNN's entire decision rests on distance, and distance is computed by summing contributions from every feature. If one feature is measured in rupees with a range of 0 to 1 000 000 and another is age with a range of 0 to 80, the squared differences in the income term are astronomically larger — so the distance is effectively determined by income alone, and age contributes nothing regardless of how predictive it is.

This isn't a subtle degradation; it can reduce a multi-feature model to a single-feature one. Standardizing to mean 0 and standard deviation 1, or min-max scaling to [0, 1], puts every feature on comparable footing so each contributes according to its actual informativeness.

The same argument applies to every distance-based method — K-means, SVMs with RBF kernels, hierarchical clustering, PCA. And the contrast is instructive: tree models don't need scaling at all, because they split on "is x above a threshold", and any monotonic rescaling preserves that ordering.

One practical caution: fit the scaler on the training set and apply it to test data. Fitting on the full dataset leaks test-set statistics into training.

What are the disadvantages of KNN?
  • Slow at prediction time. Every query compares against the whole training set — O(nd) per prediction. That's backwards from what production usually needs, where training can be slow but inference must be fast. Mitigated with KD-trees, ball trees or approximate methods like HNSW.
  • High memory. The entire training set must be retained forever; there's no compact learned model.
  • Curse of dimensionality. In high dimensions distances concentrate — the nearest and farthest neighbours become nearly equidistant — so "nearest" loses meaning. KNN degrades badly beyond a few dozen features unless you reduce dimensionality first.
  • Requires feature scaling, or large-scale features dominate the metric.
  • Sensitive to irrelevant features, because every feature contributes to the distance whether or not it carries signal. Feature selection matters more here than for most models.
  • Sensitive to class imbalance — the majority class dominates neighbourhoods by density alone.
  • No interpretable model — no coefficients or feature importances, though you can at least show which neighbours drove a prediction, which is a form of example-based explanation.

Its strengths are real though: no training cost, no assumptions about the boundary shape, naturally handles multi-class, and it's genuinely strong on low-dimensional problems with plenty of data.

Is KNN a parametric or non-parametric model? What does that mean?

KNN is non-parametric. That means it doesn't assume a fixed functional form for the decision boundary and doesn't summarise the data into a fixed number of parameters. Its "model" is the training set itself, so complexity grows with the data — more samples means a more detailed boundary.

Contrast with a parametric model like logistic regression, which commits to a fixed number of parameters — one weight per feature — regardless of whether you have a hundred rows or a hundred million. It assumes the boundary is linear, and no amount of extra data changes that assumption.

The trade-off: non-parametric models are flexible and can represent arbitrarily complex boundaries, which is powerful when the true relationship is unknown and irregular. But they need much more data to work well, they're prone to overfitting, they're expensive at inference, and they don't extrapolate beyond the range of the training data.

Parametric models need less data, train and predict fast, and are interpretable — but they're wrong whenever the assumed form is wrong, which shows up as irreducible bias no amount of data can fix. Other non-parametric examples: decision trees, kernel SVMs and Gaussian processes.

Naive Bayes

A probabilistic classifier built on an assumption that is obviously false — and works remarkably well anyway.

The derivation

We want P(class | features), which we can't estimate directly. Bayes' theorem flips it into quantities we can count:

P(C | x1…xd) ∝ P(C) · Π P(xj | C) posterior ∝ prior × product of per-feature likelihoods. The denominator P(x) is constant across classes, so we drop it and just pick the largest.

The step from the true joint likelihood to that product is the "naive" assumption: all features are conditionally independent given the class. That lets us estimate d simple one-dimensional distributions instead of one impossible d-dimensional joint distribution.

Why an obviously false assumption still works

In spam detection, "free" and "money" are clearly not independent. So why does it work? Because classification only needs the correct ranking of classes, not correct probabilities. The independence assumption distorts the magnitudes — Naive Bayes is famously overconfident, pushing probabilities toward 0 and 1 — but it usually preserves which class scores highest. That's the answer interviewers are looking for, and it also explains why you shouldn't use Naive Bayes' probabilities for anything requiring calibration.

Laplace smoothing — the detail that gets asked

The zero-frequency problem

If a word never appeared in the spam training set, then P(word | spam) = 0. Since the classifier multiplies probabilities, that single zero annihilates the entire product — the email cannot be classified as spam no matter how many other spam indicators it contains.

Fix — Laplace (add-one) smoothing: add α (usually 1) to every count. P = (count + α) / (total + α·V), where V is the vocabulary size. No probability is ever exactly zero, so no single unseen feature can veto a class. α is a hyperparameter — larger values smooth more aggressively.

A related implementation detail worth naming: multiplying thousands of small probabilities causes numeric underflow, so real implementations sum log probabilities instead of multiplying raw ones. Same ranking, no underflow.

Strengths and limits

Strengths: extremely fast to train — a single pass counting frequencies, with no iterative optimisation; works well with very little training data; scales effortlessly to enormous feature spaces, which is why it remains a strong text-classification baseline; naturally handles multi-class; and it's easy to update incrementally with new data.

Limits: the independence assumption is violated whenever features are correlated, which degrades accuracy; probabilities are poorly calibrated and overconfident; it can't learn feature interactions by construction; Gaussian NB additionally assumes normality within each class; and it's typically beaten by logistic regression or gradient boosting once you have enough data.

Interview questions · Section 13
Explain Naive Bayes. Why is it called "naive"?

Naive Bayes is a probabilistic classifier that applies Bayes' theorem to compute P(class | features) and picks the class with the highest posterior. Bayes lets you rewrite that as proportional to P(class) × P(features | class), and both of those can be estimated by counting from training data.

The problem is P(features | class) — the full joint distribution over all features — which is impossible to estimate, since with d binary features there are 2ᵈ combinations and you'd never observe most of them.

It's called "naive" because it sidesteps this with a strong assumption: features are conditionally independent given the class. That turns the joint likelihood into a simple product of per-feature likelihoods, so instead of one d-dimensional distribution you estimate d one-dimensional ones — a massive reduction that makes the method trivially fast and workable with very little data.

The assumption is almost always false — in spam detection "free" and "money" clearly co-occur. It still works because classification only requires the right ranking of classes, not accurate probabilities. The independence assumption distorts the magnitudes, making Naive Bayes notoriously overconfident, but it usually preserves which class scores highest. The practical corollary is that you shouldn't trust its probabilities for anything requiring calibration.

What is Laplace smoothing and why is it needed?

It addresses the zero-frequency problem. If a feature value never appeared with a particular class in training — say the word "cryptocurrency" never occurred in any spam email in the training set — then P(cryptocurrency | spam) is estimated as exactly zero.

Because Naive Bayes multiplies the per-feature probabilities, a single zero drives the entire product to zero. So an email containing that one word can never be classified as spam, no matter how many other strong spam signals it contains. One unseen feature vetoes the whole class, which is clearly wrong — absence from a finite training sample isn't evidence of impossibility.

Laplace or add-one smoothing fixes it by adding a constant α to every count: P = (count + α) / (total + α·V), where V is the number of possible feature values. Every probability becomes small but non-zero, so no single feature can veto a class, while the estimates for well-observed features are barely affected.

α is a hyperparameter — α = 1 is standard Laplace, smaller values like 0.1 give lighter smoothing (Lidstone smoothing), and it's worth tuning by cross-validation. I'd also mention the related implementation detail: real implementations sum log probabilities rather than multiplying raw ones, because multiplying thousands of small numbers causes floating-point underflow.

When would you use Naive Bayes over logistic regression?

When training data is scarce. This is the strongest case. Naive Bayes is a generative model with a strong bias, so it converges to its asymptotic performance very quickly — with a few hundred examples it can outperform logistic regression, which needs more data to estimate its parameters reliably. There's a well-known result by Ng and Jordan formalising exactly this: Naive Bayes has higher asymptotic error but reaches it much faster.

When speed matters and features are numerous. Training is a single counting pass with no iterative optimisation, so it handles enormous sparse feature spaces — text with a 100 000-word vocabulary — in seconds. It's still a very respectable spam-filtering and text-classification baseline for that reason.

When you need incremental updates, since counts can be updated online without retraining.

I'd use logistic regression when there's enough data, because it makes no independence assumption, learns feature weights that account for correlation, gives well-calibrated probabilities, and generally wins asymptotically. And for tabular problems with meaningful feature interactions, gradient boosting would beat both.

In practice I'd use Naive Bayes as a fast baseline — it takes a minute to fit and tells you immediately whether the problem has signal.

What's the difference between Gaussian, Multinomial and Bernoulli Naive Bayes?

They differ in the distribution assumed for P(feature | class), which is what you need to match to your data type.

Gaussian NB assumes each continuous feature is normally distributed within each class, so it estimates a mean and variance per feature per class. Use it for numeric features — measurements, sensor readings. Its weakness is that real features are often skewed rather than Gaussian, in which case a log transform first helps.

Multinomial NB models feature counts — how many times each word appears. It's the standard for text classification with bag-of-words or TF-IDF representations, and it accounts for repetition, so a document mentioning "sale" ten times is treated differently from one mentioning it once.

Bernoulli NB models binary presence or absence, and importantly it explicitly penalises the absence of a feature, which Multinomial does not. That makes it better for short documents — tweets, subject lines — where whether a word appears matters more than how often, and where the absence of typical spam words is itself informative.

The practical rule: continuous features → Gaussian; word counts or TF-IDF → Multinomial; binary indicators or short texts → Bernoulli. And with mixed feature types you'd either discretise, or model the groups separately and combine.

Support Vector Machines

Maximum-margin classification, and the kernel trick — one of the most elegant ideas in machine learning.

The idea: the widest street

Many lines separate two classes. SVM picks the one with the largest margin — the greatest distance to the nearest point of either class. The intuition: a boundary far from all training points is more robust to new data, so it generalises better.

The training points sitting exactly on the margin edges are the support vectors. They alone define the boundary — delete every other training point and the model is unchanged. That property is worth stating; it explains SVM's memory efficiency at prediction time and its robustness to points far from the boundary.

Hard vs soft margin, and C

A hard margin demands perfect separation — impossible with overlapping classes and hopelessly overfitting with noise. A soft margin allows some points to violate the margin, penalised by a slack term. The hyperparameter C controls the trade:

Large CHigh — classify training points correctly at all costsNarrowLow bias, high variance → overfits
Small CLow — tolerate misclassification for a wider marginWideHigh bias, low variance → underfits

C is effectively an inverse regularization strength — larger C means less regularization. That framing makes it easy to remember.

The kernel trick

The elegant part

SVM's optimisation depends on the data only through dot products between pairs of points. So if you want to work in a higher-dimensional space where the data is separable, you don't need the coordinates in that space — you only need the dot products there.

A kernel function computes exactly that: K(a, b) = φ(a)·φ(b), without ever computing φ. The RBF kernel corresponds to an infinite-dimensional space, which you obviously could never construct explicitly — yet the kernel evaluates in O(d). That is the trick.

Strengths and limits

Strengths: effective in high dimensions, including d > n; memory-efficient at prediction since only support vectors are kept; the maximum-margin objective gives good generalisation; kernels handle non-linearity elegantly; the optimisation is convex so there's a unique global optimum.

Limits: training scales roughly O(n²)–O(n³), so it becomes impractical beyond ~100 000 samples; no native probability output (Platt scaling is bolted on and requires extra cross-validation); very sensitive to C and γ, so tuning is mandatory; feature scaling is required; and it's poorly interpretable with a non-linear kernel. For large tabular datasets, gradient boosting has largely displaced it.

Interview questions · Section 14
Explain SVM and the concept of margin.

An SVM finds the hyperplane that separates two classes with the maximum margin — the largest possible distance between the boundary and the nearest points of either class. Many hyperplanes may separate the data; SVM picks the one sitting in the middle of the widest possible "street".

The reasoning is generalisation: a boundary that barely squeezes past training points will misclassify new points that fall slightly differently, whereas one maximally far from all training data has the most room for error. There's formal backing for this in statistical learning theory — the margin bounds the generalisation error.

The points lying exactly on the margin edges are the support vectors, and they alone determine the boundary. You could delete every other training point and retrain, and get the identical model. That's why SVM prediction is memory-efficient and why it's robust to points far from the boundary — unlike, say, logistic regression, where every point contributes to the loss.

In practice you use a soft margin, allowing some violations penalised by the hyperparameter C, because real classes overlap and demanding perfect separation would overfit noise badly.

What is the kernel trick and why is it clever?

The starting problem is that many datasets aren't linearly separable in their original feature space. The standard fix is to map them into a higher-dimensional space where they become separable — data inseparable on a line often becomes separable once you add x², for instance.

The difficulty is that useful mappings blow up in dimension, and computing the transformed coordinates becomes expensive or literally impossible.

The kernel trick exploits the fact that the SVM optimisation depends on the data only through dot products between pairs of points — never on the individual coordinates. So if you can compute the dot product in the target space directly, you never need the coordinates at all.

A kernel function does exactly that: K(a,b) = φ(a)·φ(b), evaluated without ever applying φ. The cleanest illustration is the RBF kernel, which corresponds to an infinite-dimensional feature space — something you could never construct explicitly — yet the kernel itself is just exp(−γ‖a−b‖²), computable in O(d).

That's what makes it clever: you get the expressive power of an enormous feature space at the computational cost of the original one. The same idea generalises beyond SVMs, to kernel PCA and Gaussian processes.

What do C and gamma control in an SVM?

C controls the trade-off between margin width and training errors — it's effectively an inverse regularization strength. A large C heavily penalises misclassified points, so the optimiser narrows the margin to classify training data correctly: low bias, high variance, and it overfits. A small C tolerates violations in exchange for a wider margin: high bias, low variance, and it can underfit. So larger C means less regularization.

Gamma applies to the RBF kernel and controls how far a single training example's influence extends. A large gamma means influence is tightly local, so the decision boundary becomes wiggly and wraps around individual points — overfitting, in the limit approaching a nearest-neighbour classifier. A small gamma means broad influence, giving a smooth boundary that approaches linear — underfitting.

The key practical point is that they interact, so they can't be tuned independently. A high gamma with a high C overfits severely, while a low gamma can be partly compensated by a higher C. I'd tune them jointly with a grid or random search on a logarithmic scale — something like C from 10⁻² to 10³ and gamma from 10⁻⁴ to 10¹ — evaluated by cross-validation. And I'd standardize features first, since both parameters are scale-sensitive.

When would you not use an SVM?

On large datasets. Training complexity is roughly O(n²) to O(n³), so beyond about 100 000 samples it becomes impractically slow. Gradient boosting or a linear model with SGD would be far more sensible.

When you need probabilities. SVM outputs a signed distance from the boundary, not a probability. Probability estimates require Platt scaling bolted on afterwards, which needs an internal cross-validation and can be inconsistent with the decision function. Logistic regression gives calibrated probabilities natively.

When interpretability matters. With a non-linear kernel there are no coefficients to read — you can't tell a regulator why a loan was declined. Logistic regression or a shallow tree would be required.

When there's a lot of label noise, since heavily overlapping classes force many support vectors and the model becomes both slow and poor.

For multi-class problems with many classes, since SVM is intrinsically binary and needs one-vs-one or one-vs-rest, meaning many models.

Where SVMs still shine: high-dimensional problems, especially with more features than samples — text classification and some bioinformatics — where the margin objective handles the dimensionality well and a linear kernel is fast.

Decision Trees

Entropy, information gain and Gini — with the arithmetic worked out, because interviewers ask you to compute it.

The idea

Repeatedly split the data on the feature and threshold that best separates the classes, producing a tree of yes/no questions. To predict, walk from root to leaf and return the majority class (or mean value) there.

The core question is which split is best, and the answer is: the one that most reduces impurity.

Entropy and information gain

H(S) = − Σ pi log2 pi Entropy = disorder. 0 when a node is pure; 1 (for binary) when perfectly mixed 50/50.
Worked example — compute this by hand once

A node has 14 samples: 9 yes, 5 no.

H = −(9/14)log₂(9/14) − (5/14)log₂(5/14) = −(0.643)(−0.637) − (0.357)(−1.485) = 0.410 + 0.530 = 0.940

Split on a feature giving two children: [6 yes, 2 no] (8 samples) and [3 yes, 3 no] (6 samples).

H(left) = −(0.75)log₂(0.75) − (0.25)log₂(0.25) = 0.311 + 0.5 = 0.811
H(right) = 50/50 = 1.0

Weighted child entropy = (8/14)(0.811) + (6/14)(1.0) = 0.464 + 0.429 = 0.892

Information Gain = 0.940 − 0.892 = 0.048. The tree evaluates this for every feature and threshold and picks the largest.

Gini impurity

Gini(S) = 1 − Σ pi2 Probability that a randomly labelled sample (by the node's class distribution) is wrong. 0 = pure, 0.5 = maximally mixed (binary).

For the 9/5 node above: Gini = 1 − (0.643² + 0.357²) = 1 − (0.413 + 0.127) = 0.459.

Gini vs Entropy — the honest answer

They almost always choose the same splits and produce near-identical trees. Gini is the default in scikit-learn because it is computationally cheaper — no logarithm to evaluate. Entropy has a cleaner information-theoretic interpretation and is very slightly more sensitive to changes in class probabilities. Practically the choice does not matter; say so, rather than inventing a distinction.

Splitting criteria for regression trees

For continuous targets, impurity is variance (or MSE). The best split is the one minimising the weighted sum of the children's variances. The leaf prediction is the mean of its samples.

Why trees overfit, and how to stop them

An unconstrained tree keeps splitting until every leaf is pure — typically one sample per leaf. That achieves 100% training accuracy and memorises noise perfectly. Trees are high-variance, low-bias models by nature.

Pre-pruning (early stopping)
  • max_depth — the single most effective control
  • min_samples_split — don't split a small node
  • min_samples_leaf — every leaf must have ≥ N samples
  • max_features — consider only a subset per split
  • min_impurity_decrease — require a minimum gain
Post-pruning

Grow the full tree, then remove branches that don't improve validation performance — cost-complexity pruning with parameter ccp_alpha. Generally better than pre-pruning, because a split that looks useless may enable a very useful split beneath it — which pre-pruning would never discover.

Strengths and limits

Strengths: highly interpretable — you can print the rules and show a non-technical stakeholder; no feature scaling required; handles numeric and categorical features together; captures non-linear relationships and interactions automatically; robust to outliers in the features; and gives feature importances directly.

Limits: overfits readily without constraints; unstable — a small change in data can produce a completely different tree, which is precisely the high variance that bagging exists to fix; biased toward features with many distinct values when using information gain (use gain ratio or Gini to mitigate); can only create axis-parallel splits, so a diagonal boundary requires a staircase of many splits; and it cannot extrapolate beyond the range of the training data.

Interview questions · Section 15
How does a decision tree decide where to split?

It evaluates every candidate split — every feature, and for numeric features every threshold between observed values — and picks whichever most reduces impurity in the resulting children.

For classification, impurity is measured by entropy or Gini. Entropy is −Σp log₂p, which is 0 when a node is pure and 1 for a 50/50 binary split. Information gain is the parent's entropy minus the weighted average entropy of the children — the split with the highest gain wins. Gini impurity is 1 − Σp², interpreted as the probability of misclassifying a randomly labelled sample.

Concretely, for a node with 9 yes and 5 no, entropy is −(9/14)log₂(9/14) − (5/14)log₂(5/14) ≈ 0.94. If a split produces children of [6 yes, 2 no] and [3 yes, 3 no], their weighted entropy is (8/14)(0.811) + (6/14)(1.0) ≈ 0.892, so the information gain is about 0.048.

For regression trees, impurity is variance or MSE, and the best split minimises the weighted variance of the children.

The process is greedy and recursive — it picks the locally best split at each node without looking ahead, which means the tree isn't globally optimal. Finding the optimal tree is NP-hard, so greediness is a practical necessity, and it's part of why ensembles help.

Gini or entropy — which is better?

In practice it makes almost no difference — they select the same split the large majority of the time and produce trees of very similar accuracy. I'd say that directly rather than manufacture a distinction, because a candidate claiming a large practical gap is signalling they've memorised rather than used these.

The real differences are minor. Gini is computationally cheaper because it involves only squares, whereas entropy requires logarithms — which is why Gini is scikit-learn's default and matters slightly when training thousands of trees in an ensemble. Entropy has a cleaner information-theoretic grounding, measuring bits of information gained, and is marginally more sensitive to changes in class probabilities, so it can very occasionally produce more balanced trees.

Both peak at maximum mixing and reach zero at purity; their curves are nearly the same shape, with entropy's slightly steeper.

What actually matters far more is the pruning strategy and depth constraints. I'd spend tuning effort on max_depth, min_samples_leaf and ccp_alpha rather than on the impurity criterion.

Why do decision trees overfit, and how do you prevent it?

They overfit because, left unconstrained, a tree keeps splitting until every leaf is pure — often one sample per leaf. At that point it has perfectly memorised the training data including its noise, achieving 100% training accuracy and poor test accuracy. Trees are inherently low-bias, high-variance models.

There's a second aggravating factor: with many features and thresholds, the tree evaluates a huge number of candidate splits, so by chance some will look good on the training sample without reflecting any real pattern.

Pre-pruning constrains growth: max_depth is the most effective single lever; min_samples_split prevents splitting nodes that are already small; min_samples_leaf guarantees each leaf represents enough data to be meaningful; and min_impurity_decrease requires a split to earn its place.

Post-pruning grows the full tree then removes branches that don't improve validation performance — cost-complexity pruning via ccp_alpha. It's generally superior, because a split that appears worthless on its own may enable a very valuable split beneath it, which pre-pruning would cut off before discovering.

The most effective fix in practice, though, is ensembling. Random forests average many deliberately deep, high-variance trees, and the averaging cancels the variance — which is why a single tuned tree is rarely the final model.

Do decision trees require feature scaling? Why or why not?

No, and the reason is instructive. A tree makes decisions of the form "is feature x greater than threshold t". Any monotonic transformation of x — standardizing, min-max scaling, taking logs — preserves the ordering of values, so the same partition of the data is still achievable, just at a rescaled threshold. The tree finds an equivalent split and produces an identical model.

Contrast with distance-based methods like KNN, K-means or RBF-SVM, where features are summed into a single distance, so a large-scale feature dominates. Or gradient-descent methods, where mismatched scales produce an elongated loss surface and slow convergence. Trees have neither problem because they treat each feature independently and only use rank information.

The same reasoning means trees are robust to outliers in the features — an extreme x value just ends up on one side of a threshold and doesn't distort anything, unlike in linear regression where it drags the whole fit. Note that outliers in the target still matter for regression trees, since leaf predictions are means.

This extends to all tree-based ensembles — random forests, gradient boosting, XGBoost — which is one reason they're so convenient for tabular data with little preprocessing.

What are the limitations of a single decision tree?
  • High variance / instability. Changing a few training points can produce an entirely different tree structure, because a different split at the root cascades through everything below. That makes single trees unreliable and is the main motivation for bagging.
  • Overfits without careful constraint, as it will happily grow until every leaf is pure.
  • Greedy, so not globally optimal. It picks the locally best split at each node without lookahead, and can miss a combination of splits that would work better together. Finding the optimal tree is NP-hard.
  • Axis-parallel splits only. A diagonal decision boundary must be approximated with a staircase of many splits, which is inefficient and generalises poorly. Linear models or SVMs handle that natively.
  • Cannot extrapolate. Predictions are leaf averages, so for a regression target trending upward, a tree predicts a flat value beyond the training range — a real problem for time-series or forecasting.
  • Biased toward high-cardinality features when using information gain, since a feature with many distinct values can split the data finely and appear informative by chance. Gain ratio or Gini reduces this.
  • Struggles with imbalanced classes, tending toward the majority unless class weights are applied.

Nearly all of these — especially variance and greediness — are substantially fixed by ensembling, which is why random forests and gradient boosting dominate tabular ML while single trees survive mainly where interpretability is the priority.

Ensembles: Bagging, Random Forest & Boosting

Why many weak models beat one strong one — and the single most important distinction in this section: bagging fights variance, boosting fights bias.

The sentence to memorise

Bagging trains models in parallel on different data samples and averages them → reduces variance. Boosting trains models sequentially, each correcting the previous one's errors → reduces bias. Nearly every ensemble question is answered from this one line.

Bagging (Bootstrap Aggregating)

  1. Bootstrap Draw N samples with replacement from the training set, N times. Each sample set is a slightly different view of the data.
  2. Train independently Fit one model per bootstrap sample — in parallel, since they don't interact.
  3. Aggregate Majority vote for classification, mean for regression.

Why it reduces variance: averaging M independent estimates each with variance σ² gives variance σ²/M. The models aren't fully independent — they share most of the data — so the reduction is less than the ideal, but still substantial. Crucially, averaging does not reduce bias, which is why bagging is applied to low-bias, high-variance base models like deep unpruned trees.

Out-of-bag (OOB) error — a free validation set

Each bootstrap sample omits about 37% of the original data (the limit of (1 − 1/n)ⁿ = 1/e ≈ 0.368). Those omitted points are "out of bag" for that tree, so each point can be predicted using only the trees that never saw it. Averaging over all points gives an unbiased generalisation estimate without any separate validation set or cross-validation. The 37% figure is a favourite interview question.

Random Forest = Bagging + feature randomness

Bagged trees are still correlated: if one feature is dominant, nearly every tree splits on it at the root, so the trees look alike and averaging helps less. Random Forest adds a second source of randomness — at each split, only a random subset of features is considered (typically √d for classification, d/3 for regression).

This forces different trees to use different features, decorrelating them, and less correlated models average to lower variance. That is the entire innovation over plain bagging, and stating it precisely scores well.

Interview questions · Section 16
What is the difference between bagging and boosting?

The core distinction: bagging reduces variance, boosting reduces bias.

Bagging trains many models in parallel and independently, each on a different bootstrap sample drawn with replacement, then averages or votes. Because the models are independent, averaging cancels their individual errors — averaging M estimates with variance σ² gives variance roughly σ²/M. It doesn't touch bias, so it's applied to low-bias, high-variance base learners like deep unpruned trees. Random forest is the canonical example.

Boosting trains models sequentially, each one focused on the errors of the ensemble so far — AdaBoost by re-weighting misclassified samples, gradient boosting by fitting the residuals. Each model is deliberately weak and high-bias, typically a shallow tree, and the sequence progressively reduces bias. XGBoost, LightGBM and CatBoost are the modern implementations.

Practical consequences worth stating: bagging parallelises across cores while boosting can't; adding more trees to a random forest never hurts, whereas adding more boosting rounds can overfit; random forests are forgiving to tune while boosting is sensitive and needs a small learning rate plus early stopping; and boosting is more affected by noisy labels, since it keeps chasing points it can't fit.

When tuned properly, boosting usually wins on accuracy for tabular data — which is why it dominates competitions — but random forest is a stronger default when you have limited tuning time.

How does a Random Forest differ from plain bagging?

Random forest adds a second source of randomness: at every split, the tree considers only a random subset of features rather than all of them — typically √d features for classification and d/3 for regression.

The reason is that plain bagged trees remain correlated. If one feature is strongly predictive, nearly every tree will choose it at the root and produce similar structure below. Averaging highly correlated models doesn't reduce variance much — the variance reduction from averaging depends on the models being genuinely different.

By restricting the feature choice at each split, random forest forces trees to use different features and find alternative patterns, decorrelating them. Less correlated trees average to lower variance, so the ensemble generalises better even though each individual tree is slightly worse than it would have been with full feature access.

That's a neat illustration of a general principle: deliberately weakening individual models can strengthen the ensemble, because diversity matters more than individual accuracy.

The main hyperparameter is max_features — smaller values mean more decorrelation and more bias, larger values mean the opposite, converging to plain bagging when it equals d.

What is out-of-bag error?

When you draw a bootstrap sample of size n with replacement, each individual point has a (1 − 1/n)ⁿ chance of never being selected — which converges to 1/e, about 37%. So roughly a third of the training data is left out of each tree's bootstrap sample; those are its "out-of-bag" points.

That gives a free validation mechanism. For any training point, you can predict it using only the subset of trees whose bootstrap sample excluded it — trees that genuinely never saw it. Aggregating those predictions across all points gives the out-of-bag error, an essentially unbiased estimate of generalisation performance.

The appeal is that you get this without a separate validation set and without cross-validation. All the data is used for training, and the estimate comes for free during fitting — no extra model fits, unlike k-fold which costs k times the training.

Caveats: it only applies to bagging methods, so it's available for random forests but not for boosting. And it's slightly pessimistic, because each point is evaluated by only about a third of the trees rather than the full ensemble. In practice OOB error and 5-fold CV usually agree closely, and OOB is a good way to tune the number of trees cheaply.

Why is XGBoost so effective?

It's gradient boosting with a set of well-chosen engineering and algorithmic improvements, each addressing a real weakness.

Regularization in the objective. Unlike classic gradient boosting, XGBoost's loss explicitly includes L1 and L2 penalties on leaf weights plus a penalty on the number of leaves. That directly controls overfitting rather than relying only on tree depth.

Second-order optimisation. It uses both the gradient and the Hessian of the loss — a Newton step rather than a plain gradient step — which converges in fewer boosting rounds and finds better splits.

Native missing-value handling. At each split it learns a default direction for missing values from the data itself, so no imputation is needed and the missingness pattern becomes usable signal.

Speed. Split-finding is parallelised across features, it uses cache-aware access patterns and a compressed column format, and it supports out-of-core training on data larger than memory.

Built-in tools — early stopping on a validation set, cross-validation, and column and row subsampling, which add randomness in the manner of random forests.

The deeper reason it dominates tabular problems is that boosted trees naturally capture non-linearities and feature interactions, need no scaling, handle mixed types, and are robust to irrelevant features — which is exactly the shape of real business data. Neural networks generally beat it only on unstructured data.

Can adding more trees to a boosting model hurt performance?

Yes — and this is a real difference from random forests, where more trees never hurt and simply plateau.

The reason is that each boosting round is explicitly fitted to the residual errors of the current ensemble. Once the genuine signal is captured, the remaining residuals are mostly noise — and boosting will keep dutifully fitting that noise. Training loss continues falling while validation loss bottoms out and then rises, the classic overfitting curve.

Random forests don't have this problem because each tree is fitted independently to the data rather than to the ensemble's errors, so adding trees only refines the average.

The controls: early stopping is the direct fix — monitor validation loss and stop when it stops improving, with a patience of some rounds. A small learning rate (0.01–0.1) means each tree contributes only a little, so overfitting arrives more slowly and the optimum is broader; the trade-off is needing more rounds. Shallow trees (depth 3–8), row and column subsampling, and explicit L1/L2 regularization all help.

The standard practice is to set the number of estimators generously high and let early stopping choose the actual value, rather than trying to tune it directly.

What is stacking?

Stacking trains several different base models — say a random forest, an SVM, a neural network and logistic regression — then trains a meta-model that takes their predictions as input and learns how to combine them optimally.

It differs from bagging and boosting in that those use many instances of the same algorithm, whereas stacking deliberately combines different algorithm families. The idea is that different models make different kinds of errors, so a meta-learner can learn which model to trust in which region of the feature space — a more sophisticated combination than simple averaging.

The critical implementation detail: base-model predictions fed to the meta-model must be generated out-of-fold. If you train a base model on the full training set and then use its predictions on that same data, those predictions are overfitted and unrealistically good, so the meta-model learns to over-trust that base model and fails at inference. The correct approach is k-fold: for each fold, train the base models on the other folds and predict the held-out one, assembling a full set of honest out-of-fold predictions.

The meta-model is usually kept simple — logistic regression or ridge — since a complex one on top of already-strong predictions overfits easily. Stacking reliably wins competitions, but the accuracy gain is often small relative to the added complexity and inference cost, so in production I'd want a clear justification.

Clustering

K-means, hierarchical and DBSCAN — plus the honest answer to “how do you evaluate clustering?”

K-means

  1. Initialise Choose k centroids — with k-means++, which spreads initial centroids apart rather than picking purely at random, dramatically improving results.
  2. Assign Assign each point to its nearest centroid.
  3. Update Move each centroid to the mean of its assigned points.
  4. Repeat Steps 2–3 until assignments stop changing.

The objective it minimises is within-cluster sum of squares (WCSS), also called inertia — the total squared distance from each point to its centroid. K-means is guaranteed to converge, but only to a local optimum, which is why it's run multiple times with different initialisations (n_init) and the best result kept.

K-means' assumptions — the reason it fails

It implicitly assumes clusters are spherical, similarly sized, and of similar density, because it assigns by Euclidean distance to a centre. So it fails on elongated, crescent-shaped, or nested-ring clusters, and it will split one genuinely large cluster while merging two small ones. It's also sensitive to outliers, since a single distant point drags its centroid. And k must be chosen in advance.

Choosing k

Elbow method

Plot WCSS against k. It always decreases, but the rate of improvement drops sharply at the "elbow" — the point of diminishing returns. Simple, but the elbow is often ambiguous.

Silhouette score

For each point: (b − a) / max(a, b), where a is mean distance to its own cluster and b to the nearest other cluster. Ranges −1 to 1; higher is better. Pick the k maximising the average. More objective than the elbow.

Gap statistic

Compare WCSS against what you'd expect from uniformly random data. More principled, more computation.

Domain knowledge

Often the real answer — "marketing wants four segments" is a legitimate and frequently correct constraint. Say this; it shows practical sense.

Hierarchical clustering

Agglomerative (bottom-up) starts with every point as its own cluster and repeatedly merges the two closest, producing a dendrogram — a tree you can cut at any height to get any number of clusters. Divisive (top-down) does the reverse and is rarer.

Linkage determines "closest": single (nearest pair — produces long chains), complete (farthest pair — compact clusters), average, and Ward (minimises the increase in within-cluster variance — usually the best default).

Advantages: no need to pre-specify k, and the dendrogram is genuinely informative. Cost: O(n³) time and O(n²) memory in the naive form, so it doesn't scale past tens of thousands of points, and merges are irreversible.

DBSCAN

Density-based: a cluster is a dense region separated by sparse regions. Two parameters — eps (neighbourhood radius) and min_samples (points required to be a core point).

Explain K-means and how you choose k.

K-means partitions data into k clusters by iterating two steps: assign each point to the nearest centroid, then move each centroid to the mean of its assigned points. Repeat until assignments stabilise. It minimises the within-cluster sum of squares — total squared distance from points to their centroids.

Initialization matters a lot: random starting centroids can produce poor local optima, so k-means++ is standard, choosing initial centroids spread far apart. And since convergence is only to a local optimum, you run it several times with different seeds and keep the best.

Choosing k: the elbow method plots WCSS against k and looks for the point where improvement sharply slows — though the elbow is often ambiguous in practice. The silhouette score is more objective: for each point it compares mean distance to its own cluster against the nearest other cluster, giving a value in [−1, 1], and you pick the k maximising the average. The gap statistic compares WCSS to what random data would produce.

But the answer I'd emphasise is that domain knowledge often decides it. If the marketing team can only run four campaigns, k = 4 is the right answer regardless of what the silhouette curve says. Clustering is a means to a decision, not an end in itself.

When does K-means fail?

Its failures all trace back to one thing: it assigns points by Euclidean distance to a centre, which implicitly assumes spherical, equally-sized, equally-dense clusters.

  • Non-spherical shapes. Elongated, crescent or concentric-ring clusters get cut straight through, because a centroid can't represent a curved region. DBSCAN or spectral clustering handle these.
  • Different sizes or densities. K-means tends to split one large cluster and merge two small ones, since it's minimising total squared distance rather than respecting structure.
  • Outliers. A single distant point pulls its centroid substantially, distorting the cluster. K-medoids is more robust since it uses actual data points as centres.
  • You must know k in advance, which is often the very thing you're trying to discover.
  • Sensitivity to initialization — mitigated by k-means++ and multiple restarts, but not eliminated.
  • High dimensions, where the curse of dimensionality makes Euclidean distance uninformative. Reduce with PCA first.
  • Unscaled features, where a large-range feature dominates the distance entirely.
  • Categorical data, since means aren't defined — use k-modes or a different distance.
How does DBSCAN differ from K-means?

DBSCAN is density-based rather than centroid-based: it defines a cluster as a dense region of points separated by sparser regions. It takes two parameters — eps, the neighbourhood radius, and min_samples, the number of neighbours required for a point to be a "core point" — and grows clusters by chaining together core points and their neighbours.

Three advantages follow. It doesn't require k in advance, discovering the number of clusters from the data. It finds arbitrarily shaped clusters — crescents, rings, elongated shapes — because it follows density rather than fitting to a centre. And it has an explicit notion of noise: points in no dense region are labelled as outliers rather than forced into a cluster, which makes it directly useful for anomaly detection.

Its weaknesses: it struggles when clusters have varying density, since a single eps can't suit both a dense and a sparse cluster — HDBSCAN addresses this. Choosing eps is difficult, though a k-distance plot helps by showing where distances jump. And in high dimensions the density notion degrades along with distance generally.

So I'd pick K-means for large, roughly spherical, well-separated data where speed matters, and DBSCAN when cluster shapes are irregular, the count is unknown, or outliers must be identified rather than absorbed.

How do you evaluate a clustering result when there are no labels?

With internal validation measures that assess the geometry of the clustering itself.

The silhouette score is the most common: for each point, compare its mean distance to points in its own cluster against its mean distance to the nearest other cluster. Values near 1 mean well-separated, near 0 mean on a boundary, negative means probably misassigned. The average over all points summarises the clustering, and it's useful for comparing different values of k.

The Davies–Bouldin index measures average similarity between each cluster and its most similar one — lower is better. The Calinski–Harabasz index is a ratio of between-cluster to within-cluster dispersion — higher is better. Comparing several measures is safer than trusting one, since each has its own biases (silhouette, for instance, favours convex clusters and so flatters K-means).

If labels happen to exist for a subset, external measures like Adjusted Rand Index or Normalised Mutual Information compare the clustering to the known grouping.

But the answer I'd finish on is that internal metrics measure geometry, not usefulness. The real test is whether a domain expert finds the clusters meaningful and actionable — I'd profile each cluster on interpretable features and check they tell a coherent story. A clustering with a great silhouette score that no one can act on has failed.

Dimensionality Reduction

PCA derived properly, plus t-SNE, UMAP and LDA — and the one thing you must never do with t-SNE.

PCA — the idea

Find a new set of axes (principal components) such that the first captures the most variance in the data, the second captures the most of what remains while being orthogonal to the first, and so on. Keep the top few and discard the rest.

The reasoning: directions with high variance carry most of the information; directions with near-zero variance are close to constant and carry almost none.

  1. Standardize PCA maximises variance, and variance is scale-dependent — without scaling, whichever feature has the largest units becomes the first component regardless of importance. This step is mandatory.
  2. Compute the covariance matrix A d×d matrix of how each pair of features co-varies.
  3. Eigendecomposition Find its eigenvectors and eigenvalues. Eigenvectors are the principal component directions; eigenvalues are the variance captured along each.
  4. Sort and select Order by descending eigenvalue and keep the top k — chosen so that, say, 95% of total variance is retained.
  5. Project Transform the data onto those k axes.
What PCA costs you

Interpretability. A principal component is a linear combination of all original features — "0.3 × income + 0.5 × age − 0.2 × tenure + …" — which usually means nothing to a domain expert. You have traded explainability for compactness, and you should say so.

Also: PCA is unsupervised, so it ignores the target entirely. A direction of low variance may be exactly the direction that separates your classes, and PCA will happily discard it. And it only captures linear structure — use kernel PCA or an autoencoder for non-linear manifolds.

t-SNE and UMAP

Non-linear techniques designed for visualisation. They convert distances into probabilities and find a 2-D or 3-D layout preserving local neighbourhood structure — points close in high dimensions stay close.

The t-SNE rules people break
  1. Never use t-SNE output as features for a model. It has no consistent transform for new data — you cannot project a new point into an existing embedding, so it can't be part of a pipeline. It is a visualisation tool.
  2. Cluster sizes in a t-SNE plot are meaningless. The algorithm expands dense regions and contracts sparse ones.
  3. Distances between clusters are meaningless too — only local neighbourhoods are preserved, so "these two clusters are far apart" is not a valid reading.
  4. Perplexity matters enormously — different values produce visibly different plots, so examine several before drawing conclusions.

UMAP is usually preferred now: it's much faster, preserves more global structure, and — unlike t-SNE — supports transforming new data, so it can be used in a pipeline.

LDA — the supervised alternative

Linear Discriminant Analysis finds the projection that maximises separation between classes rather than overall variance. Since it uses labels, it often preserves discriminative information that PCA would discard. Its limit: it can produce at most C − 1 components for C classes, so for binary classification you get exactly one dimension.

Explain PCA. How does it work?

PCA finds a new coordinate system for the data in which the first axis captures the maximum possible variance, the second captures the maximum remaining variance while being orthogonal to the first, and so on. You then keep the top few axes and discard the rest, reducing dimensionality while losing as little information as possible.

Mechanically: standardize the features — mandatory, because variance is scale-dependent and otherwise whichever feature has the largest units becomes PC1 regardless of importance. Compute the covariance matrix, then take its eigendecomposition. The eigenvectors are the principal component directions and the corresponding eigenvalues are the variance captured along each. Sort by eigenvalue descending, keep the top k, and project the data onto them.

Choosing k: plot cumulative explained variance and keep enough components to retain, say, 95%, or use the elbow of the scree plot.

Why it works: directions with high variance carry most of the information, while directions with near-zero variance are essentially constant and carry almost none. As a bonus, the components are orthogonal by construction, so PCA also removes multicollinearity.

The cost worth stating: components are linear combinations of all original features, so interpretability is lost. And it's unsupervised — a low-variance direction might be exactly what separates your classes, and PCA will discard it without knowing.

Why must you scale data before PCA?

Because PCA maximises variance, and variance depends entirely on units. Consider a dataset with salary in rupees, ranging over hundreds of thousands, and age in years, ranging over decades. The variance of salary is many orders of magnitude larger purely because of the unit, so the first principal component will align almost perfectly with salary — not because salary is more informative, but because its numbers are bigger.

Change salary to lakhs and the entire result changes. That's the tell that the unscaled analysis is meaningless: a legitimate method shouldn't give different answers based on an arbitrary choice of units.

Standardizing to mean 0 and standard deviation 1 puts every feature on equal footing, so components reflect genuine shared structure rather than measurement scale. Technically, this means running PCA on the correlation matrix rather than the covariance matrix.

The one exception: if all features are already in the same units and their relative magnitudes are meaningful — say pixel intensities, or repeated measurements of the same quantity — then running on the covariance matrix without standardizing can be the right choice, because the scale differences are real information rather than an artefact.

PCA vs LDA — what's the difference?

The core difference is that PCA is unsupervised and LDA is supervised.

PCA finds directions of maximum variance in the data, ignoring labels entirely. LDA finds directions that maximise separation between classes — specifically the ratio of between-class scatter to within-class scatter.

That difference has real consequences. PCA can discard exactly the direction you need: if two classes differ along a low-variance axis, PCA sees an unimportant direction and drops it, destroying the signal. LDA, knowing the labels, keeps it. So for dimensionality reduction as preprocessing for classification, LDA is often the better choice.

LDA's main limitation is that it produces at most C − 1 components for C classes — so binary classification gives you exactly one dimension, which is very restrictive. PCA can produce up to d. LDA also assumes classes are Gaussian with equal covariance, and needs enough samples per class to estimate those covariances.

So: PCA for unsupervised compression, denoising, visualisation, or when labels are unavailable. LDA when you have labels, a reasonable number of classes, and dimensionality reduction is serving a classification task. They're also complementary — PCA first to reduce noise, then LDA — which is a common pipeline in face recognition.

Can you use t-SNE output as input features to a model?

No, and this is the most common misuse of t-SNE.

The fundamental problem is that t-SNE has no consistent transform for new data. It optimises the positions of a fixed set of points to preserve their pairwise neighbourhood probabilities — it doesn't learn a mapping function. There's no way to project a new point into an existing embedding, so you cannot apply it to test data or to production inputs. It can't be part of a pipeline at all.

Beyond that, running t-SNE twice on the same data with different random seeds produces different layouts, so the "features" aren't even stable.

There are also interpretation traps worth naming: cluster sizes in a t-SNE plot are meaningless, since the algorithm expands dense regions and contracts sparse ones; and distances between clusters are meaningless, because only local neighbourhoods are preserved. So you can't conclude "these two groups are more similar than those two". Perplexity also changes the picture substantially, so I'd view several settings before concluding anything.

t-SNE is a visualisation and exploration tool. If I needed a learned low-dimensional representation for downstream modelling, I'd use PCA, an autoencoder, or UMAP — which is faster, preserves more global structure, and unlike t-SNE does support transforming new data.

How do you decide how many principal components to keep?

Several complementary approaches, and I'd use more than one.

Cumulative explained variance is the most common: plot the running total of variance explained and keep enough components to reach a threshold — 95% is typical, 99% if information loss is costly, 80–90% if compression matters more. This directly quantifies what you're giving up.

Scree plot elbow: plot each component's explained variance and look for where the curve flattens. Components after the elbow contribute little individually.

Kaiser criterion: keep components with eigenvalue greater than 1 when working on standardized data, on the reasoning that such a component explains more variance than a single original feature. It's a rough heuristic and tends to over-retain.

But the most defensible approach when PCA feeds a supervised model is to treat k as a hyperparameter and cross-validate it. Optimise for downstream task performance rather than for variance retained — those aren't the same objective, since PCA doesn't know which directions are predictive. Sometimes a small number of components performs better than a large number, because the discarded ones were mostly noise.

And if the purpose is visualisation, the answer is simply 2 or 3, with the explained variance reported so the reader knows how much of the structure they're actually seeing.

Neural Networks & Backpropagation

A neuron is logistic regression. A network is many of them stacked. Backprop is the chain rule. That's the whole thing.

The neuron

One neuron takes inputs, computes a weighted sum plus a bias, and applies a non-linear activation function:

a = g(wTx + b) If g is the sigmoid, this is exactly logistic regression. A network is a stack of these.

Why activation functions must be non-linear

The single most important fact about neural networks

Without a non-linear activation, stacking layers is pointless. A composition of linear functions is itself a linear function: W₂(W₁x) = (W₂W₁)x = W′x. A hundred-layer network with no activations collapses to a single matrix multiply — i.e. plain linear regression. Non-linearity is what makes depth meaningful.

Backpropagation, step by step

  1. Forward pass Feed the input through every layer, storing each layer's intermediate activations — they're needed for the backward pass.
  2. Compute loss Compare the output to the target (cross-entropy for classification, MSE for regression).
  3. Backward pass Starting at the loss, compute ∂Loss/∂w for every weight by applying the chain rule layer by layer, moving backwards. Each layer's gradient is computed from the layer above it — which is what makes this efficient rather than quadratic.
  4. Update Apply the optimiser: w := w − α · ∂Loss/∂w.
  5. Repeat Over mini-batches, for many epochs.
What backprop actually is

It is not a learning algorithm — gradient descent is. Backprop is an efficient method for computing gradients in a composed function, by reusing shared intermediate results instead of recomputing them for each parameter. That reuse is why training a network with a million parameters costs roughly the same as one forward pass, rather than a million forward passes. Saying this precisely is a strong differentiator.

Vanishing and exploding gradients

Because the chain rule multiplies derivatives along the path from loss to weight, a deep network multiplies many terms together.

Vanishing

If each derivative is < 1 (sigmoid's max is 0.25), the product shrinks exponentially with depth. Early layers receive almost no gradient and stop learning. Fixes: ReLU, careful initialization (He/Xavier), batch normalization, residual connections, and LSTM/GRU gates for sequences.

Exploding

If derivatives are > 1, the product grows exponentially — weights blow up, loss becomes NaN. Most common in RNNs. Fixes: gradient clipping (cap the norm), lower learning rate, better initialization, weight regularization.

The Universal Approximation Theorem

A feedforward network with a single hidden layer and enough neurons can approximate any continuous function to arbitrary accuracy. So why go deep? Because "enough neurons" may mean exponentially many. Depth buys efficiency: deep networks build hierarchical representations — edges → textures → parts → objects — expressing complex functions with far fewer parameters than a shallow network would need. And the theorem says nothing about whether gradient descent can find those weights.

Interview questions · Section 19
Explain backpropagation.

Backpropagation is the algorithm for computing the gradient of the loss with respect to every weight in a network, so that gradient descent can update them.

It works in two passes. The forward pass feeds the input through each layer to produce a prediction, storing the intermediate activations along the way. The loss is then computed against the target. The backward pass starts at the loss and works backwards through the layers, applying the chain rule to compute how much each weight contributed to the error. Each layer's gradient is derived from the gradient of the layer above it, so the results are reused rather than recomputed.

That reuse is the whole point of the algorithm. Naively computing the derivative separately for each of a million parameters would require a million passes. Backprop computes all of them in a single backward sweep costing roughly the same as one forward pass — which is what makes training large networks feasible at all.

A precise framing worth stating: backprop is not a learning algorithm. It's an efficient method for computing gradients; gradient descent is what does the learning. Modern frameworks generalise it as reverse-mode automatic differentiation.

The consequence to raise: because the chain rule multiplies derivatives along the path, deep networks suffer vanishing gradients when those derivatives are consistently below 1, and exploding gradients when above — which is why ReLU, careful initialization and residual connections exist.

Why do we need non-linear activation functions?

Because without them, depth is worthless. A linear layer computes Wx + b, and composing two of them gives W₂(W₁x + b₁) + b₂, which simplifies to (W₂W₁)x + (W₂b₁ + b₂) — just another linear function with a single effective weight matrix.

So a hundred-layer network with no activations is mathematically identical to a one-layer network, which is plain linear regression. It could never learn XOR, let alone recognise an image.

Non-linearity is what makes depth meaningful. Inserting a non-linear function between layers means the composition cannot be collapsed, so each layer genuinely adds representational capacity. That's what lets a network build hierarchical features — early layers detecting edges, later ones combining them into shapes and objects.

It's also the condition for the Universal Approximation Theorem, which says a network with one hidden layer and a non-linear activation can approximate any continuous function given enough neurons. Remove the non-linearity and that guarantee vanishes entirely.

In practice the choice is usually ReLU for hidden layers — cheap, non-saturating for positive inputs, and it avoids the vanishing-gradient problem that made sigmoid-based deep networks untrainable. GELU has become standard in transformers.

What is the vanishing gradient problem and how do you fix it?

Because backpropagation applies the chain rule, the gradient reaching an early layer is the product of all the local derivatives on the path from the loss back to it. If those derivatives are consistently less than 1, the product shrinks exponentially with depth.

Sigmoid is the classic culprit: its derivative peaks at 0.25 and approaches zero when saturated. Across twenty layers, 0.25²⁰ is around 10⁻¹². The early layers receive essentially no gradient, so they stop learning entirely — the network trains only its last few layers. This is why deep networks were considered untrainable before roughly 2010.

The fixes, roughly in order of impact:

  • ReLU activations — the derivative is exactly 1 for positive inputs, so no shrinkage occurs along active paths. This was the single biggest breakthrough.
  • Residual connections — skip connections give the gradient a direct path back, bypassing many layers. This is what made networks of 100+ layers trainable and is why ResNet mattered.
  • Careful initialization — He initialization for ReLU, Xavier for tanh, scaled so activation variance stays stable across layers.
  • Batch normalization — keeps each layer's inputs in a well-conditioned range so activations don't drift into saturation.
  • LSTM/GRU gates for sequences, which give gradients an additive path through time rather than a multiplicative one.

The mirror problem is exploding gradients, where derivatives above 1 compound — most common in RNNs, and fixed by gradient clipping.

What is the dying ReLU problem?

ReLU outputs zero for any negative input, and its derivative there is also zero. So if a neuron's weights drift such that its pre-activation is negative for every training example, it outputs zero always, receives zero gradient always, and can never update. It's permanently dead — and any capacity it represented is lost.

It usually happens after a large gradient update pushes the weights or bias strongly negative, which is why an excessive learning rate is the most common cause. In a badly configured network a substantial fraction of neurons can die.

Fixes: Leaky ReLU, which uses a small negative slope like 0.01x so the gradient is never exactly zero; Parametric ReLU, which learns that slope; ELU or GELU, which are smooth and non-zero for negative inputs — GELU being the standard in transformers. Beyond activation choice, a lower learning rate prevents the destructive updates in the first place, proper He initialization starts neurons in a healthy regime, and batch normalization keeps pre-activations centred so they don't drift entirely negative.

In practice, plain ReLU with sensible initialization and learning rate is usually fine, and I'd only switch if I diagnosed a genuinely high fraction of dead units.

How do you choose the number of layers and neurons?

There's no formula, so I'd treat it empirically and start from what's known to work.

My approach: begin with an established architecture for the problem type rather than designing from scratch — a known CNN for vision, a transformer for text — and fine-tune it. Most practical problems don't need a novel architecture.

If building from scratch, I'd start small and grow. Begin with one or two hidden layers and a modest width, establish a baseline, then increase capacity while watching the training-versus-validation gap. If both errors are high, the model is underfitting and needs more capacity. If training error is low and validation error is much higher, it's overfitting and I need regularization or more data, not more layers.

Rough heuristics: hidden layer widths in powers of two (64, 128, 256) for hardware efficiency; often a funnel shape narrowing toward the output; the input layer sized by feature count and the output by class count.

The point I'd emphasise is that architecture size is usually not the highest-leverage decision. Learning rate, data quantity and quality, and regularization matter more. Modern practice also leans toward building a deliberately over-parameterised network and controlling it with dropout, weight decay and early stopping, rather than hunting for a minimal architecture — partly because of the double-descent phenomenon, where very large models generalise better than classical theory predicts.

Weight initialization

Never initialise all weights to zero. Every neuron in a layer would then compute the same output, receive the same gradient, and update identically — they'd remain permanently identical, so the layer would have the capacity of a single neuron. This is the symmetry-breaking problem, and it's a common interview question.

  • He — variance scaled by 2/fan_in. For ReLU, since ReLU zeroes half the activations and the factor of 2 compensates.
  • The goal in both cases is to keep activation variance roughly constant across layers, so signals neither vanish nor explode as they propagate.

Transfer learning

Take a model pretrained on a large dataset and adapt it to your smaller task. Early layers have learned generic features (edges, textures, general language structure) that transfer broadly; only the later, task-specific layers need to change.

  • Feature extraction: freeze the pretrained backbone, replace and train only the final head. Best with very little data.

Why transfer learning matters commercially

It is usually the difference between "we need a million labelled images" and "we need two thousand". For almost any vision or NLP problem in industry, starting from a pretrained model is not merely an optimisation — it is the only viable approach given realistic data budgets.

Interview questions · Section 20
What is Adam and how does it differ from SGD?

Adam — Adaptive Moment Estimation — combines two ideas. From momentum it keeps an exponentially decaying average of past gradients (the first moment), which smooths the update direction and carries the optimiser through noise and plateaus. From RMSprop it keeps a decaying average of squared gradients (the second moment) and divides the step by its square root, giving each parameter its own effective learning rate — large steps where gradients have been small, small steps where they've been large. It also applies bias correction, since both averages start at zero and would otherwise be biased early in training.

Compared with plain SGD, which uses a single global learning rate and the raw mini-batch gradient, Adam converges much faster, handles sparse gradients and badly-scaled features far better, and is much less sensitive to the learning-rate choice — which is why it's the default starting point.

The honest caveat: well-tuned SGD with momentum often generalises slightly better than Adam, particularly in computer vision, and many state-of-the-art image models still use it with a cosine schedule. The rough intuition is that Adam's adaptivity can steer toward sharper minima.

For transformers, AdamW is the correct variant: it decouples weight decay from the gradient update, because plain Adam's L2 penalty gets scaled by the adaptive term and stops behaving like proper regularization.

Why can't you initialise all weights to zero?

Because of symmetry. If every weight in a layer starts at zero — or at any identical value — then every neuron in that layer computes exactly the same output for a given input. During backpropagation they all receive exactly the same gradient, so they all update identically, and they remain identical forever.

The result is that a layer with 512 neurons has the representational capacity of one neuron, no matter how long you train. The network can never learn diverse features because there's no mechanism to differentiate the units.

The fix is random initialization to break symmetry. But the scale matters as much as the randomness: too small and activations shrink layer by layer until the signal vanishes; too large and they explode into saturation. So we use principled schemes that keep activation variance roughly constant across layers — Xavier/Glorot for tanh and sigmoid, scaling variance by 1/(fan_in + fan_out), and He initialization for ReLU, scaling by 2/fan_in, where the factor of 2 compensates for ReLU zeroing roughly half the activations.

One exception worth noting: biases can safely be initialised to zero, because the randomness in the weights is already enough to break symmetry.

What is batch normalization and why does it help?

Batch normalization normalises each layer's inputs across the mini-batch — subtracting the batch mean and dividing by the batch standard deviation per feature — then applies a learnable scale and shift so the network can undo the normalization if that's optimal.

The original motivation was reducing "internal covariate shift" — the idea that as earlier layers update, the distribution of inputs to later layers keeps changing, forcing them to constantly re-adapt. That explanation is now disputed; the better-supported account is that BatchNorm smooths the loss landscape, making gradients more predictable and allowing larger stable steps.

Whatever the mechanism, the practical benefits are clear: training converges substantially faster, much higher learning rates become usable, sensitivity to weight initialization drops, and the noise from batch statistics provides mild regularization.

Two implementation details that matter. At inference there's no batch, so it uses running averages accumulated during training — which is why forgetting to switch the model to eval mode is a classic bug producing wrong predictions. And it's unreliable with small batch sizes, since the statistics become noisy — which is exactly why transformers use layer normalization instead, normalising across features within each sample so it's independent of batch size and of variable sequence lengths.

Explain transfer learning. When would you fine-tune vs freeze?

Transfer learning takes a model pretrained on a large dataset and adapts it to a related task with much less data. It works because early layers learn generic features — edges and textures in vision, syntax and general semantics in language — that are useful far beyond the original task, while only the later layers are task-specific.

The decision depends mostly on how much data you have:

  • Very little data (hundreds of examples): freeze the entire backbone and train only a new classification head. With so little data, fine-tuning would overfit and destroy the pretrained representations.
  • Moderate data (thousands): freeze the early layers and fine-tune the later ones, which are the most task-specific.
  • Plenty of data: fine-tune everything, but with a small learning rate — often with discriminative rates, lower for early layers — so you refine rather than overwrite the pretrained weights.

Domain similarity also matters: if the target domain is very different from the pretraining data — medical scans versus natural photographs — more fine-tuning is needed even with limited data.

For LLMs, full fine-tuning is usually prohibitive, so the standard is parameter-efficient fine-tuning like LoRA, which freezes the base model and trains small injected low-rank matrices — a fraction of a percent of the parameters, with most of the benefit.

CNNs & Computer Vision

Why a fully-connected network fails on images, and the three ideas that fix it.

Why not just flatten the image?

A 224×224 RGB image flattened is 150 528 inputs. A single fully-connected hidden layer of 1 000 units needs 150 million parameters — for one layer. Worse, flattening destroys spatial structure: pixels that are neighbours become arbitrary distant entries, so the network must relearn adjacency from scratch. And it has no translation invariance — a cat in the top-left and the same cat in the bottom-right activate completely different weights, so each position must be learned independently.

The three ideas behind convolution

  1. Local receptive fields A neuron looks at a small patch (say 3×3), not the whole image. Local structure — edges, corners — is what matters at low level.
  2. Parameter sharing The same filter slides across the entire image. An edge detector is useful everywhere, so learn it once. This is what collapses 150 million parameters into a few thousand and delivers translation invariance.
  3. Hierarchical composition Stacking layers builds complexity: edges → textures → parts → objects. Each layer's receptive field covers more of the original image than the last.

Why use a CNN instead of a fully-connected network for images?

Three reasons, and they're all about exploiting structure a fully-connected network ignores.

Parameter count. A 224×224 RGB image has 150 528 values. One fully-connected hidden layer of 1 000 units would need 150 million parameters — for a single layer. That's computationally absurd and would overfit catastrophically. A convolutional layer with 64 filters of 3×3 needs under 2 000 parameters, because the same filter is reused at every position.

Spatial structure. Flattening an image destroys the information that adjacent pixels are related — neighbouring pixels become arbitrary distant entries in a vector, and the network must relearn adjacency from data. Convolutions operate on local patches, so spatial locality is built in.

Translation invariance. In a fully-connected network, a cat in the top-left activates entirely different weights from the same cat in the bottom-right, so the network must learn "cat" separately at every position. Because a convolutional filter slides across the whole image, a feature learned anywhere is detected everywhere.

Underneath all three is the same idea: CNNs encode a prior about images — that local patterns matter and are position-independent. That prior is why CNNs need far less data than a fully-connected network to reach the same accuracy, and it's also why Vision Transformers, which lack it, need much larger datasets to compete.

What is pooling and why is it used?

Pooling downsamples a feature map by summarising each small window into a single value — max pooling takes the maximum, average pooling the mean. A 2×2 max pool with stride 2 halves both spatial dimensions, cutting the data by four.

Three purposes. It reduces computation and memory in every subsequent layer. It widens the receptive field, so deeper neurons see a larger portion of the original image, which is how the hierarchy from edges to objects is built. And it provides local translation invariance — if a feature shifts by one pixel, the max over the window is often unchanged, so the representation is stable to small movements.

Max pooling is preferred over average for feature detection because it keeps the strongest activation — the presence of a feature matters more than its average intensity across a region.

The modern caveat worth adding: pooling is used less than it once was. Many architectures now use strided convolutions instead, which downsample while learning how to do so rather than applying a fixed operation. And global average pooling has largely replaced the big fully-connected layers at the end of a CNN, drastically reducing parameters. Pooling also discards precise spatial information, which is why segmentation architectures either avoid it or use skip connections to recover the detail.

What is a residual connection and why does it matter?

A residual or skip connection adds a layer's input directly to its output: instead of computing H(x), the block computes F(x) + x, so the layers only need to learn the residual F(x) = H(x) − x.

It matters because it solved the degradation problem. Before ResNet, adding layers beyond a certain depth made networks worse — and not from overfitting, since training error rose too. They were simply too hard to optimise, largely because gradients vanished before reaching early layers.

Skip connections fix this in two ways. First, they give gradients a direct path backwards — the derivative of x with respect to x is 1, so gradient flows through the skip unattenuated no matter how many blocks it passes. Second, they make identity mappings easy to learn: if a layer isn't useful, the network can push F(x) toward zero and pass the input through unchanged, so adding depth can never hurt by construction.

The result was that networks jumped from around 20 usable layers to over 100, with ResNet-152 winning ImageNet in 2015. The idea proved so general that it now appears almost everywhere — every transformer block has residual connections around both its attention and feedforward sub-layers. It's arguably the most broadly important architectural idea in deep learning.

Calculate the output size: 32×32 input, 5×5 filter, stride 1, padding 2.

The formula is Output = ⌊(W − F + 2P)/S⌋ + 1, where W is input size, F is filter size, P is padding and S is stride.

Substituting: (32 − 5 + 2×2)/1 + 1 = (32 − 5 + 4)/1 + 1 = 31 + 1 = 32×32.

So the spatial dimensions are preserved — this is "same" padding. The general rule is that padding of (F−1)/2 with stride 1 preserves size, which is why 3×3 filters with padding 1 and 5×5 filters with padding 2 are so common: you can stack many layers without the feature map shrinking away.

The depth of the output is separate — it equals the number of filters, not the input depth. So with 64 filters the output is 32×32×64 regardless of whether the input had 3 channels or 128.

And the parameter count for that layer would be (5 × 5 × input_channels + 1) × 64, the +1 being the bias per filter — worth being able to compute, since it's a common follow-up.

RNNs, LSTMs & Sequence Models

Memory across time, why plain RNNs forget, and the gating mechanism that fixed it.

Why sequences need a different architecture

A feedforward network takes a fixed-size input and treats each input independently. Sequences break both assumptions: sentences vary in length, and order carries meaning — "the dog bit the man" and "the man bit the dog" contain identical words.

An RNN processes one element at a time while maintaining a hidden state that carries information forward:

ht = tanh(Whhht−1 + Wxhxt + b) The same weights are reused at every timestep — parameter sharing across time, mirroring the CNN's sharing across space.
Why plain RNNs fail on long sequences

Backpropagation through time multiplies the same weight matrix once per timestep. Over 100 steps that's a 100-fold product — so gradients either vanish toward zero (the common case) or explode. Vanishing gradients mean the network cannot learn dependencies more than about 10 steps apart: in "I grew up in France … I speak fluent ___", the signal from "France" never survives the journey. This is the long-term dependency problem.

LSTM — gates that control memory

An LSTM adds a separate cell state that runs through the sequence with only minor linear interactions, plus three learned gates that decide what happens to it:

Forget gateWhat should I discard from memory?Outputs 0–1 per cell dimension; multiplies the cell state

Why gating solves the gradient problem

The cell state is updated additively — Ct = ft ⊙ Ct−1 + it ⊙ C̃t — rather than being repeatedly multiplied by a weight matrix. When the forget gate stays near 1, gradients flow backwards through many timesteps almost unchanged. It is the same insight as ResNet's skip connection: give the gradient an additive highway instead of a multiplicative gauntlet.

GRU is a simplified variant with two gates (update and reset) and no separate cell state. Fewer parameters, faster to train, and typically comparable in performance — try GRU first if data or compute is limited.

Architectural variants

  • Bidirectional RNN — runs one pass forward and one backward, concatenating both. Uses future as well as past context, which helps for classification and tagging. Not usable for real-time generation, since the future isn't available.
  • Encoder–decoder (seq2seq) — an encoder compresses the input into a context vector, a decoder generates the output. Used for translation and summarisation.
  • Attention — added to seq2seq because a single fixed-size context vector is a bottleneck for long inputs. Instead the decoder looks back at all encoder states and learns which to focus on at each step. This mechanism is what the transformer took and built an entire architecture from (Section 23).
Why transformers replaced RNNs

RNNs are inherently sequential — timestep t cannot be computed before t−1, so training cannot be parallelised across the sequence, which caps how large a model you can afford to train. Transformers process all positions simultaneously, making full use of GPUs, and their attention gives every position direct access to every other — a path length of 1 rather than n. That combination of parallelism and short gradient paths is why transformers displaced RNNs for essentially all serious NLP.

Interview questions · Section 22
What problem do RNNs solve that feedforward networks can't?

Feedforward networks take a fixed-size input and process each input independently. Sequential data violates both assumptions: sentences, time series and audio have variable length, and order carries meaning — "the dog bit the man" and "the man bit the dog" have identical word sets but opposite meanings.

An RNN handles this by processing elements one at a time while maintaining a hidden state that carries information forward — a form of memory. At each step it combines the current input with the previous hidden state, so the output at any point depends on everything seen so far.

Critically, the same weights are reused at every timestep. That means the network can handle sequences of any length with a fixed parameter count, and a pattern learned at position 3 transfers to position 300. It's the temporal analogue of a CNN sharing filters across space.

The limitation, which I'd raise unprompted, is that plain RNNs can't learn long-range dependencies because of vanishing gradients — which is what motivated LSTMs and ultimately transformers.

How does an LSTM solve the vanishing gradient problem?

In a plain RNN, backpropagating through time repeatedly multiplies by the same weight matrix — once per timestep. Over 100 steps that's a 100-fold product, so gradients shrink exponentially toward zero and the network can't learn dependencies more than roughly ten steps apart.

An LSTM introduces a separate cell state that flows along the sequence with only minor linear interactions, plus three gates that control it. The forget gate decides what to discard, the input gate decides what new information to write, and the output gate decides what to expose as the hidden state.

The crucial point is the form of the update: Ct = ft ⊙ Ct−1 + it ⊙ C̃t. The cell state is updated additively rather than by repeated matrix multiplication. When the forget gate is near 1, the gradient flows backwards through many timesteps essentially unchanged — an uninterrupted highway rather than a multiplicative gauntlet.

It's the same insight as ResNet's skip connection, arrived at years earlier: give gradients an additive path. And because the gates are learned, the network decides for itself what to remember and for how long, rather than having a fixed decay.

It mitigates rather than eliminates the problem — very long sequences still degrade, which is part of why attention and transformers took over.

LSTM or GRU — which would you use?

I'd try GRU first in most cases. It has two gates instead of three — an update gate merging LSTM's forget and input gates, and a reset gate — and no separate cell state. That's roughly 25% fewer parameters, so it trains faster, needs less data, and is less prone to overfitting on small datasets.

Empirically they perform comparably on most tasks; there's no consistent winner across benchmarks. The general pattern is that LSTM tends to edge ahead on very long sequences or large datasets, where its separate cell state and finer-grained control over memory pay off, while GRU matches it elsewhere at lower cost.

So my practical approach: start with GRU as a baseline, and try LSTM if sequences are long or if I have plenty of data and compute. Treating the choice as a hyperparameter and testing both is cheap and more defensible than arguing from first principles.

The bigger point I'd make is that for most modern NLP, neither is the right default any more — transformers dominate. RNNs remain relevant for genuinely streaming applications where you must process input as it arrives with bounded memory, for very long sequences where attention's quadratic cost is prohibitive, and on small edge devices.

Why did transformers replace RNNs?

Two reasons, and the first is about hardware economics as much as modelling.

Parallelism. An RNN is inherently sequential — the hidden state at step t requires step t−1, so a sequence of length 1 000 needs 1 000 sequential operations that cannot be parallelised. That leaves GPUs, which are built for massive parallel computation, largely idle, and it caps how large a model you can afford to train. Transformers process every position simultaneously, so training time depends on sequence length far less. This is what made models with hundreds of billions of parameters economically possible.

Path length. In an RNN, information from position 1 reaching position 500 must pass through 499 intermediate states, degrading along the way — which is the long-range dependency problem LSTMs mitigate but don't eliminate. In a transformer, self-attention gives every position direct access to every other position in a single step. The path length is constant, so a word at the start of a document influences one at the end just as easily as its neighbour.

The cost is that attention is quadratic in sequence length — every position attends to every other — so very long contexts are expensive, which is an active research area (sparse attention, linear attention, state-space models like Mamba). And transformers lack the RNN's built-in notion of order, so they need explicit positional encodings.

Explain the attention mechanism.

Attention lets each position in a sequence look at every other position and decide how much to draw from each, producing a context-aware representation.

Each token is projected into three vectors: a query ("what am I looking for?"), a key ("what do I contain?") and a value ("what do I contribute?"). You compute the dot product of a token's query with every key to get relevance scores, scale by √dk, apply softmax to turn them into weights summing to 1, and take the weighted sum of the values.

The library analogy: your query is what you want, each book's key is its title, you score your query against all titles, and then you take a weighted blend of the books' actual contents.

The √dk scaling matters and is worth explaining: dot products of high-dimensional vectors grow large in magnitude, which pushes softmax into a saturated region where one weight approaches 1 and gradients vanish. Dividing by √dk keeps the scores in a workable range.

Why it beats recurrence: every position reaches every other in a single step rather than passing through hundreds of intermediate states, so long-range dependencies are learned directly. And all positions compute simultaneously, so it parallelises on GPUs where RNNs cannot.

Multi-head attention runs several of these in parallel with different projections, so different heads can specialise in different relationships — syntax, coreference, local context.

What is the difference between BERT and GPT?

The core difference is the direction of attention, which determines what each is good for.

BERT is encoder-only with bidirectional attention — every token sees the entire sentence, both left and right. It's pretrained with masked language modelling: random tokens are hidden and the model predicts them from surrounding context on both sides. That produces rich representations for understanding, so BERT excels at classification, named entity recognition, extractive question answering and generating embeddings for search. What it cannot do is generate text naturally, because it was never trained to produce tokens sequentially.

GPT is decoder-only with causal attention — each token attends only to previous tokens, enforced by masking future positions. It's pretrained on next-token prediction. That makes it a natural generator: chat, completion, summarisation, code. The trade-off is that its representation of a token can't use anything to its right, which is theoretically weaker for pure understanding tasks.

The historical point worth adding: BERT-style models were expected to dominate, but the field moved decisively toward decoder-only models because next-token prediction scales better and turns out to be a general enough objective that a sufficiently large generative model handles understanding tasks well too — via prompting rather than task-specific fine-tuning.

What is RAG and when would you use it over fine-tuning?

RAG — Retrieval-Augmented Generation — combines a retrieval system with a generative model. You chunk a document corpus, embed each chunk into a vector database, and at query time embed the user's question, retrieve the most similar chunks by nearest-neighbour search, and insert them into the prompt as context. The LLM then answers grounded in that retrieved material.

I'd use RAG for knowledge — facts that are private, large, or change frequently. Company documentation, product catalogues, legal or medical corpora. Its advantages: knowledge updates instantly by re-indexing, with no retraining; answers can cite sources, which matters enormously for trust and auditability; hallucination drops because the model is grounded; and access control can be applied at the retrieval layer so users only see permitted documents.

I'd use fine-tuning for behaviour — response format, tone, domain-specific style, or a specialised task where you want consistent structured output. Fine-tuning changes how the model responds; it's a poor and expensive way to inject facts, since the knowledge is baked in and stale the moment anything changes.

They compose well: fine-tune for the format and voice, use RAG for the facts. In practice most of the engineering effort in a RAG system goes into retrieval quality — chunking strategy, hybrid keyword-plus-vector search, and re-ranking the top results — because if retrieval returns the wrong context, no amount of model quality saves the answer.

Why do LLMs hallucinate, and how do you reduce it?

Because of what they're trained to do. An LLM is optimised to predict the most probable next token given the context — it models the statistical structure of plausible text, not truth. There's no internal database being consulted and no verification step, so when the model lacks reliable knowledge it produces text that reads like a correct answer, because fluent-and-wrong and fluent-and-right look similar from the objective's point of view.

Contributing factors: training data contains errors and contradictions; the model has no calibrated sense of its own uncertainty; RLHF can reward confident, helpful-sounding answers over honest refusals; and asking about anything after the training cutoff or outside the training distribution forces extrapolation.

Mitigations, roughly in order of effectiveness:

  • RAG — ground answers in retrieved documents and require citations, so claims are checkable and the model isn't relying on parametric memory.
  • Lower temperature for factual tasks, reducing sampling of low-probability tokens.
  • Prompt design — explicitly permit "I don't know", and ask the model to answer only from provided context.
  • Verification layers — check generated claims against a source, or use a second model to critique the first.
  • Structured outputs and tool use — for arithmetic, dates or lookups, call a real tool rather than letting the model generate the answer.

The honest caveat: hallucination can be reduced substantially but not eliminated, so any high-stakes application needs a human in the loop or a verifiable source.

What is the difference between Word2Vec embeddings and BERT embeddings?

The difference is context. Word2Vec produces a static embedding — one fixed vector per word, regardless of usage. BERT produces contextual embeddings — the vector for a word depends on the sentence it appears in.

The classic illustration is polysemy. In Word2Vec, "bank" has a single vector that awkwardly averages the financial and river senses, so it's a poor representation of either. In BERT, "bank" in "I deposited money at the bank" and "we sat on the river bank" produce genuinely different vectors, because the surrounding tokens shape the representation through attention.

Word2Vec's strengths are real though: it's cheap to train, fast at inference, and produces the well-known geometric structure where king − man + woman ≈ queen, making semantic relationships into directions. For simple similarity tasks it's often sufficient and enormously cheaper.

BERT's cost is computational — you must run the full model over the sentence rather than looking up a table. And for sentence-level similarity, raw BERT embeddings are actually poor without further training, which is why Sentence-BERT exists, fine-tuned with a siamese objective so cosine similarity between sentence vectors is meaningful. That's what modern semantic search and RAG systems actually use.

What does temperature do in an LLM?

Temperature scales the logits before the softmax that converts them into a probability distribution over the next token. Dividing logits by a temperature T reshapes that distribution.

Low temperature (approaching 0) sharpens the distribution — the highest-probability token dominates, so output becomes deterministic and repetitive. At T = 0 it's pure greedy decoding, always picking the single most likely token. Use it for factual answers, extraction, classification and code, where you want consistency and correctness.

High temperature (above 1) flattens the distribution, giving unlikely tokens more chance. Output becomes more varied and creative, and also more error-prone and eventually incoherent. Use it for brainstorming or creative writing.

T = 1 leaves the distribution as the model produced it.

Two related controls worth mentioning: top-k sampling restricts choices to the k most likely tokens, and top-p or nucleus sampling restricts to the smallest set whose cumulative probability exceeds p. Top-p is generally preferred because it adapts — when the model is confident it considers few tokens, and when uncertain it considers more. In practice these are combined with temperature rather than used alone.

An important clarification: low temperature reduces randomness, not hallucination. A confidently wrong model will state its wrong answer very consistently at T = 0.

Drift — why models decay

Data drift (covariate shift)

The input distribution changes: P(X) shifts while P(y|X) stays the same. A new customer demographic starts using the product. Detect: compare feature distributions over time — KS test, PSI, or simply monitor the means.

Concept drift

The relationship changes: P(y|X) shifts. What signalled fraud last year no longer does, because fraudsters adapted. Detect: monitor prediction quality against actual outcomes as labels arrive. More dangerous, because feature distributions can look completely normal.

Also worth naming: label drift (the target's base rate changes), upstream data changes (a team renames a column or changes a unit — the most common real cause of silent breakage), and training–serving skew, where the preprocessing applied at inference differs from training.

Monitoring a deployed model

  • Data quality: nulls, ranges, schema changes, unexpected categories. Catch these before they reach the model.
  • Input distributions: per-feature statistics compared to a training baseline.
  • Prediction distribution: if a fraud model's positive rate suddenly triples, something changed.
  • Performance: accuracy, AUC and business metrics — but only once ground-truth labels arrive, which may be days or months later. Design for that delay.
  • Operational: latency, throughput, error rates, cost per prediction.
  • Business KPI: the metric that actually justified the project. A model with great AUC that doesn't move revenue has failed.
Online vs offline evaluation

Offline metrics — accuracy, AUC on a held-out set — measure whether the model predicts well. They do not tell you whether it helps. Only an A/B test does, because deploying a model changes user behaviour, which offline data cannot capture. The standard practice is: gate on offline metrics, then decide with an online test. Saying this shows you understand the difference between a model and a product.

MLOps essentials

  • Versioning everything — code, data, model artefacts and hyperparameters. A result you cannot reproduce is not a result. (DVC, MLflow.)
  • Experiment tracking — log every run's parameters, metrics and artefacts, or you will lose the configuration that worked.
  • Feature store — a shared, versioned home for features so training and serving compute them identically. This is the standard defence against training–serving skew.
  • Automated retraining — triggered on a schedule or by a drift alert, with automatic validation gates before promotion.
  • Model registry — staged promotion (dev → staging → production) with the ability to roll back instantly.
  • Reproducibility — pinned dependencies, fixed random seeds, containerised environments.
Ethics & fairness — increasingly asked directly

Models learn the biases present in their training data. A hiring model trained on historical decisions will reproduce historical discrimination, and removing the protected attribute does not fix it, because proxies remain — postcode correlates with ethnicity, and a career gap with parenthood.

Fairness metrics to name: demographic parity (equal positive rates across groups), equal opportunity (equal true positive rates), equalised odds (equal TPR and FPR). These are mathematically incompatible in general — you cannot satisfy all of them simultaneously except in degenerate cases, so the choice is a value judgement that must be made explicitly with stakeholders, not quietly by an engineer.

Scenario questions · Section 24
Your model performed well in testing but poorly in production. Why?

I'd work through the likely causes in order of frequency.

Data leakage in training is the most common. If a feature encoded information unavailable at prediction time, offline scores were inflated and production reveals the truth. I'd re-audit every top feature: "would I genuinely have this value at inference?"

Training–serving skew — the preprocessing at inference differs from training. A different imputation value, a scaler refitted on production data, a category encoded in a different order. Extremely common and completely silent. A feature store or a shared pipeline artefact prevents it.

Distribution shift — production data simply differs from the training set. Maybe the training data was old, or sampled from a different population, or the test split wasn't representative. I'd compare feature distributions between training and live traffic directly.

Temporal leakage — if the data was split randomly when it should have been split chronologically, the offline score was measuring interpolation, not forecasting.

Feedback loops — the model's own predictions change user behaviour, so the environment it operates in is no longer the one it was trained on.

Diagnostically I'd start by scoring the production data offline: if the model scores well on logged production inputs, the problem is in the serving path; if it scores badly, the problem is the data distribution or the original evaluation.

How do you detect and handle model drift?

I'd distinguish two kinds, because they need different detection.

Data drift is a change in the input distribution — P(X) shifts while the relationship P(y|X) holds. It's detectable without labels by comparing live feature distributions against a training baseline, using a KS test for continuous features, chi-square for categorical, or Population Stability Index, which is the standard in credit risk. This is cheap and gives early warning.

Concept drift is a change in the relationship itself — what predicted fraud last year no longer does, because fraudsters adapted. It's more dangerous because feature distributions can look entirely normal. Detecting it requires ground-truth labels, so you monitor rolling performance as outcomes arrive — which may lag by days or months.

As a proxy while waiting for labels, I'd monitor the prediction distribution: if a fraud model's positive rate triples overnight, something has changed even if I can't yet say what.

Handling it: scheduled retraining on recent data as a baseline defence; drift-triggered retraining for faster response; a rolling training window or sample weighting that favours recent data in fast-moving domains; and online learning where the environment changes continuously. Every retrain should pass automated validation gates and go out via canary or shadow deployment, with instant rollback — because an automatically retrained model on corrupted data is its own failure mode.

You have 1000 labelled and 100,000 unlabelled examples. What do you do?

I'd use several approaches, probably in combination.

Transfer learning first. If the data is images or text, start from a pretrained model and fine-tune on the 1 000 labels. This is by far the highest-leverage move — a pretrained backbone has already learned generic representations from millions of examples, so 1 000 labels can be enough. For text I'd fine-tune a pretrained language model; for images, a pretrained CNN or ViT.

Self-supervised pretraining on the 100 000 unlabelled examples — contrastive learning like SimCLR for images, or continued masked-language-model pretraining on the domain text. This adapts the representation to my specific domain before fine-tuning on the labels.

Active learning to spend the labelling budget well. Rather than labelling randomly, use the current model to find the examples it's most uncertain about and label those — they're the most informative per label. This typically reaches a target accuracy with a fraction of the labels.

Semi-supervised methods — pseudo-labelling, where confident predictions on unlabelled data are added as training targets, or consistency regularization, which requires the model to give stable predictions under input perturbations. Pseudo-labelling needs a high confidence threshold, or errors compound.

And practically: heavy data augmentation, a simpler model with strong regularization to avoid overfitting 1 000 examples, and cross-validation rather than a single split, since a held-out set of 200 gives a very noisy estimate.

How would you explain a model's prediction to a non-technical stakeholder?

I'd use SHAP, because it gives per-prediction attributions that decompose the output into feature contributions — with a game-theoretic guarantee that the contributions sum correctly to the prediction.

Concretely, for a declined loan application I'd show a waterfall: "the baseline approval probability is 40%; a credit score of 580 pushed it down 18 points; a debt-to-income ratio of 55% pushed it down 12 more; six years of employment pushed it up 5; final probability 15%." That's a specific, checkable, human-readable explanation.

For a global view — how the model behaves overall — I'd use a SHAP summary plot showing which features matter most and in which direction, plus partial dependence plots for how a single feature's effect varies across its range.

Two things I'd be careful about. Correlation, not causation: SHAP explains what the model used, not what causes the outcome, and stakeholders routinely conflate the two — I'd say that explicitly. And I'd avoid default tree feature importances for this purpose, since they're biased toward high-cardinality features and can be actively misleading.

The broader point: if explainability is a hard requirement — regulated lending or clinical decisions — I'd consider choosing an inherently interpretable model like logistic regression or a shallow tree from the start, rather than explaining a black box after the fact. A small accuracy cost is often worth a defensible decision.

How do you decide if a model is good enough to deploy?

Not by looking at accuracy alone. I'd check several things in sequence.

Does it beat the baseline meaningfully? Compare against the current system, or against a trivial baseline like majority class or a simple rule. A statistically significant improvement that doesn't change any decision isn't worth deploying.

Does it clear the business threshold? Translate model metrics into business terms: at this operating point, we catch X% of fraud while sending Y alerts a day — is that within the review team's capacity, and is the net value positive? That's the actual decision criterion.

Is the evaluation trustworthy? Was it measured on a properly held-out set, split correctly for time or groups, with no leakage? Is the test set large enough that the estimate isn't noise?

Does it fail acceptably? Check performance on important slices — different regions, customer segments, devices — not just the aggregate. A model that's excellent overall but poor for one group is a real risk. Also check fairness across protected attributes where relevant.

Does it meet operational requirements? Latency, throughput, memory, cost per prediction, and whether all its features are actually available at serving time.

And then the honest final answer: offline metrics only gate the decision. The real test is an A/B test in production, because deploying changes user behaviour in ways offline data can't capture. I'd ship to a small percentage behind a shadow or canary deployment, with monitoring and a rollback path ready.

Your model is biased against a demographic group. What do you do?

First, define what "biased" means here, because the fairness definitions are mathematically incompatible. Demographic parity requires equal positive rates across groups; equal opportunity requires equal true positive rates; equalised odds requires both TPR and FPR to match. You generally cannot satisfy all of these at once, so which one applies is a value and policy judgement that must be made explicitly with stakeholders and legal — not silently by an engineer.

Then find the source. Usually it's the data: historical decisions encode historical discrimination, or a group is under-represented so the model fits it poorly, or the label itself is biased — arrest records are not the same thing as crime rates. Sometimes it's the features, via proxies: removing the protected attribute doesn't help when postcode correlates with ethnicity or a career gap with parenthood.

Mitigations at three stages. Pre-processing: rebalance or reweight the training data, collect more data for under-represented groups, remove proxy features where legally appropriate. In-processing: add a fairness constraint or penalty to the training objective. Post-processing: use group-specific decision thresholds to equalise the chosen metric — simple and effective, though it may itself raise legal questions.

And throughout: measure performance per group rather than in aggregate, document the tradeoff made and why, and keep a human in the loop for high-stakes decisions. I'd also raise that a fairness gap sometimes means the model shouldn't ship at all — that's a legitimate outcome and worth saying plainly.

How would you build a recommendation system?

I'd start by clarifying the objective, because "recommend" is ambiguous — optimising for clicks, watch time, purchases or long-term retention produces very different systems, and clicks in particular reward clickbait.

Then the standard two-stage architecture. Candidate generation narrows millions of items to a few hundred cheaply, then ranking scores those precisely with a heavier model.

For candidate generation:

  • Collaborative filtering — recommend based on behaviour of similar users. Matrix factorisation or two-tower embedding models, retrieved by approximate nearest neighbour. Strong signal, but suffers the cold start problem for new users and items.
  • Content-based — recommend items similar to what the user liked, using item features or embeddings. Handles cold-start items and is more explainable, but tends toward a filter bubble.
  • Hybrid is what real systems use, combining both plus popularity and recency heuristics.

For ranking, gradient-boosted trees or a neural ranker over user features, item features and interaction history, trained on logged engagement.

Issues I'd raise unprompted: cold start, handled with popularity fallbacks and onboarding preferences; popularity bias, where popular items get recommended, become more popular, and crowd out the tail — needing explicit exploration or diversity terms; feedback loops, since you only observe outcomes for items you showed; and evaluation, where offline metrics like NDCG are weak proxies and A/B testing is the real measure.

50 rapid-fire questions · answer each in under 30 seconds
1 · Supervised vs unsupervised in one line each?

Supervised: learn a mapping from features to known labels. Unsupervised: find structure in data with no labels.

2 · What is overfitting?

The model fits noise in the training data as if it were signal — excellent training performance, poor test performance. It's the high-variance failure mode.

3 · Bias vs variance?

Bias is error from wrong assumptions (too simple → underfits). Variance is error from sensitivity to the training sample (too complex → overfits). Total error is their sum plus irreducible noise.

4 · Name three ways to prevent overfitting.

More data, regularization (L1/L2/dropout), and a simpler model. Also early stopping, cross-validation and ensembling.

5 · L1 vs L2 in one line?

L1 (Lasso) drives coefficients to exactly zero, so it selects features. L2 (Ridge) shrinks all coefficients smoothly toward zero without eliminating any.

6 · Why does L1 give sparsity?

Its constraint region is a diamond whose corners lie on the axes, so the loss contours are likely to touch it at a corner — where a coefficient is exactly zero. L2's circular region has no corners.

7 · What is regularization doing, conceptually?

Deliberately increasing bias to reduce variance, by restricting the model's effective capacity so it cannot fit noise.

8 · Precision vs recall?

Precision: of what I flagged, how much was right (TP/(TP+FP)). Recall: of what existed, how much I caught (TP/(TP+FN)).

9 · When is accuracy a bad metric?

When classes are imbalanced or error costs differ. On 99% negatives, predicting "negative" always scores 99% and is useless.

10 · Why is F1 a harmonic mean?

Because it punishes imbalance. Precision 1.0 with recall 0 gives an arithmetic mean of 0.5 but a harmonic mean of 0 — F1 is high only if both are.

11 · ROC-AUC vs PR-AUC?

ROC uses FPR, whose denominator includes abundant true negatives, so it flatters imbalanced problems. Precision has no TN term, so PR-AUC is the honest choice when positives are rare.

12 · What does AUC = 0.8 mean?

Given a random positive and a random negative, there's an 80% chance the model scores the positive higher. It measures ranking, not calibration.

13 · MSE vs MAE?

MSE squares errors, so it punishes large ones and is outlier-sensitive; it predicts the conditional mean. MAE weights all errors equally, is robust, and predicts the median.

14 · Can R² be negative?

Yes — on a test set. It means the model is worse than simply predicting the training mean, usually indicating severe overfitting or distribution shift.

15 · What is cross-validation for?

Getting a stable, low-variance performance estimate from limited data by using every point for validation exactly once, and for choosing hyperparameters honestly.

16 · Why stratified k-fold?

It preserves the class ratio in every fold. Without it, an imbalanced dataset can produce folds with almost none of the minority class, making estimates wildly noisy.

17 · What is data leakage?

Information unavailable at prediction time getting into training — producing excellent validation scores and a model that fails in production.

18 · Which algorithms need feature scaling?

Distance-based (KNN, K-means, RBF-SVM), gradient-descent-based (linear/logistic regression, neural nets) and variance-based (PCA, LDA). Tree models do not.

19 · Why don't trees need scaling?

They split on "is x > threshold", and any monotonic rescaling preserves the ordering, so the same partitions remain available.

20 · One-hot or label encoding for a tree?

Label/ordinal or native categorical handling. Trees don't read integers as magnitudes, and one-hot at high cardinality creates sparse columns the tree rarely selects.

21 · What is the curse of dimensionality?

As dimensions grow, data becomes exponentially sparse and distances concentrate, so "nearest neighbour" loses meaning and models overfit.

22 · What is the normal equation?

w = (XᵀX)⁻¹Xᵀy — the closed-form solution to linear regression. O(d³), so impractical for very high dimensions, and it fails when XᵀX is singular.

23 · Assumptions of linear regression?

Linearity, independence of errors, normality of residuals, equal variance (homoscedasticity), no multicollinearity — LINE-M.

24 · Does multicollinearity hurt prediction?

Not much. It destroys coefficient interpretability and stability — coefficients become large and can flip sign — but predictive accuracy is largely unaffected.

25 · Why is it called logistic regression?

Because it performs linear regression on the log-odds: log(p/(1−p)) = wᵀx + b. The sigmoid just maps that back to a probability.

26 · Why not MSE for logistic regression?

It's non-convex when composed with the sigmoid, so optimisation can stall in local minima, and its gradient vanishes exactly when the model is confidently wrong. Cross-entropy is convex and its gradient is proportional to the error.

27 · Can logistic regression learn XOR?

Not on raw features — its boundary is linear. Add the interaction term x₁x₂ and it can. That's exactly why hidden layers exist.

28 · What does k control in KNN?

The bias–variance tradeoff. k = 1 overfits with a jagged boundary; k = n underfits by predicting the majority class always.

29 · Why is Naive Bayes "naive"?

It assumes all features are conditionally independent given the class — usually false, but it makes estimation tractable and still gives the right class ranking.

30 · What is Laplace smoothing?

Adding a constant to every count so no probability is zero — otherwise one unseen feature multiplies the whole posterior to zero and vetoes a class.

31 · What is a support vector?

A training point lying on the margin boundary. Only these define the hyperplane — delete everything else and the model is unchanged.

32 · What is the kernel trick?

Computing dot products in a high-dimensional space without ever computing the coordinates there. The RBF kernel corresponds to an infinite-dimensional space at O(d) cost.

33 · What does C do in an SVM?

Controls the margin/error tradeoff — it's inverse regularization strength. Large C means narrow margin and overfitting; small C means wide margin and underfitting.

34 · Entropy vs Gini?

They pick almost identical splits. Gini is scikit-learn's default because it avoids computing logarithms. The practical difference is negligible.

35 · Compute the entropy of a 50/50 split.

−0.5log₂0.5 − 0.5log₂0.5 = 0.5 + 0.5 = 1.0 — maximum disorder for a binary node.

36 · Bagging vs boosting in one line?

Bagging trains models in parallel on bootstrap samples and averages — reduces variance. Boosting trains sequentially, each correcting the last — reduces bias.

37 · How does Random Forest differ from bagging?

It also samples a random subset of features at each split, which decorrelates the trees so averaging reduces variance more effectively.

38 · What is out-of-bag error?

A free validation estimate using, for each point, only the trees whose bootstrap sample excluded it. About 37% of data is out-of-bag per tree.

39 · Can more trees hurt a boosting model?

Yes — each round fits the previous residuals, so eventually it fits noise. Use early stopping. More trees never hurt a random forest.

40 · How do you pick k in K-means?

Elbow method on WCSS, silhouette score, or gap statistic — and very often domain constraints, which are a legitimate answer.

41 · When does K-means fail?

Non-spherical clusters, clusters of very different size or density, outliers, unscaled features, and high dimensions. It assumes spherical, equally-sized groups.

42 · Why standardize before PCA?

PCA maximises variance, and variance depends on units — otherwise the feature with the largest scale becomes PC1 regardless of importance.

43 · PCA vs LDA?

PCA is unsupervised and maximises variance. LDA is supervised and maximises class separation, but yields at most C−1 components.

44 · Can you use t-SNE output as model features?

No. It has no transform for new data, so it can't be part of a pipeline. It's a visualisation tool. Use UMAP or PCA instead.

45 · Why do we need non-linear activations?

Without them, stacked linear layers collapse into a single linear function, so depth adds nothing at all.

46 · What is the vanishing gradient problem?

The chain rule multiplies derivatives, so with values below 1 the gradient shrinks exponentially with depth and early layers stop learning. Fixed with ReLU, residual connections and normalization.

47 · Why can't you initialise weights to zero?

Every neuron in a layer would compute the same output and receive the same gradient, so they'd stay identical forever — the layer would have the capacity of one neuron.

48 · Batch norm vs layer norm?

Batch norm normalises across the batch per feature (used in CNNs, needs adequate batch size). Layer norm normalises across features per sample (used in transformers, batch-independent).

49 · Why did transformers replace RNNs?

They parallelise across the sequence, where RNNs are inherently sequential, and attention gives every position direct access to every other rather than a long chain.

50 · RAG or fine-tuning?

RAG for knowledge that changes and needs citation. Fine-tuning for behaviour, format and style. They compose — fine-tune the voice, retrieve the facts.

They are checking four things: that you interrogate the problem before reaching for a model, that you know what each choice costs, that you can spot when a result is too good to be true, and that you can explain a technical idea clearly to someone who does not already know it.
