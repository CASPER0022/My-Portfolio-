Chapter 01

Foundations: what an operating system actually is

Before processes and page tables, get clear on the one idea everything else hangs from — the OS is a manager of hardware and a provider of abstractions.

1.1 The problem the OS solves

A bare computer is hostile. The CPU executes one instruction stream. Memory is a flat array of bytes with no notion of ownership. A disk understands "read sector 91,204", not "open resume.pdf". If every program had to talk to hardware directly, every program would have to be rewritten for every disk controller, and any program could scribble over any other program's memory.

The operating system sits between hardware and applications and solves this in two ways.

Operating System

A system software layer that acts as an intermediary between the user/applications and the computer hardware. It performs two roles: as a resource manager it allocates CPU time, memory, disk and I/O devices among competing programs; as an extended (virtual) machine it hides messy hardware behind clean abstractions — files instead of sectors, processes instead of CPU registers, virtual memory instead of physical RAM.

1.2 Goals of an operating system

  • Convenience — make the machine easy to use (dominant goal on desktops/phones).
  • Efficiency — maximise CPU utilisation and throughput (dominant goal on servers/mainframes).
  • Isolation & protection — one buggy or malicious process must not corrupt another.
  • Fairness — no process is starved of resources indefinitely.
  • Ability to evolve — new hardware and services can be added without rewriting everything.

Convenience and efficiency pull in opposite directions; almost every OS design decision is a trade-off between them. Saying that sentence in an interview shows maturity.

1.3 Types of operating systems

These evolved historically, each fixing a flaw in the one before. Learn the progression, not the list — it makes the answer memorable.

1. Batch OS

Similar jobs are batched by an operator and run one after another with no user interaction. Job Control Language describes each job.

Problem: CPU sits idle during I/O; no priority; a long job blocks everyone.

2. Multiprogramming OS

Keep several jobs in memory. When the running job starts I/O, the CPU switches to another. Goal: maximise CPU utilisation.

Problem: a CPU-bound job can hog the CPU for minutes — no interactivity.

3. Multitasking / Time-sharing OS

Multiprogramming plus a timer interrupt: each process gets a small time slice (quantum). Goal: minimise response time. Unix, Linux, Windows.

Cost: context-switch overhead.

4. Multiprocessing OS

Two or more CPUs/cores under one OS. Symmetric (SMP): all CPUs peer, share memory — Linux, Windows. Asymmetric: a master CPU assigns work to slaves.

Gives true parallelism, higher throughput, graceful degradation.

5. Real-Time OS (RTOS)

Correctness depends on meeting deadlines, not just producing right answers. Hard RTOS: missing a deadline is a system failure (airbag, pacemaker, avionics). Soft RTOS: a miss degrades quality (video streaming, VoIP).

Uses priority-based preemptive scheduling; predictability beats throughput.

6. Distributed / Network OS

Distributed: many independent machines appear to the user as one system (transparency); resource sharing, no single point of failure, but complex. Network OS: machines stay visibly separate and share via the network (servers, NFS).

7. Mobile / Embedded OS

Android, iOS, FreeRTOS. Optimised for power, limited memory, and app sandboxing.

8. Clustered OS

Multiple independent systems tied together by a fast network to act as one, giving high availability and load balancing.

Privileged instructions include: setting the timer, changing the mode bit, loading the page table base register, direct device I/O, halting the CPU. If a user program attempts one, the hardware raises a trap and the kernel usually terminates it. This hardware support is exactly what makes protection possible — an OS cannot enforce isolation by software alone.

1.5 System calls — the only legal door into the kernel

System Call

A programmatic request from a user-mode process asking the kernel to perform a privileged service on its behalf. It is the only controlled entry point from user mode into kernel mode, implemented by a software-interrupt / trap instruction (syscall on x86-64, svc on ARM).

What happens on a system call, step by step

  1. The program calls a library wrapper, e.g. read(fd, buf, n) in libc.
  2. The wrapper places the system call number in a register and arguments in registers (or a block whose address is in a register).
  3. It executes the trap instruction. Hardware switches the mode bit to kernel and jumps to a fixed trap handler address from the interrupt vector table.
  4. The handler saves user context, validates arguments, and dispatches through the system-call table to the real kernel function.
  5. The kernel does the work (possibly blocking the process meanwhile).
  6. The return value is placed in a register, user context is restored, mode bit flips back, and execution resumes at the instruction after the trap.

1.6 Kernel architectures

Monolithic kernel

The entire OS — scheduler, memory manager, file systems, device drivers, network stack — runs as one program in kernel space, in one address space.

+ Very fast: services call each other as ordinary function calls.
− Huge; one driver bug can crash the machine; hard to maintain.

Examples: Linux, traditional Unix, MS-DOS.

Microkernel

Kernel keeps only the bare minimum — address spaces, threads, IPC. File systems, drivers and protocol stacks run as ordinary user-space servers.

+ Reliable and secure (a driver crash kills one server, restartable); portable; easily extended.
− Slower: every service call becomes message passing plus mode switches.

Examples: MINIX 3, QNX, L4, Mach.

Hybrid kernel

Microkernel-style structure but performance-critical servers are pulled back into kernel space. The pragmatic middle.

Examples: Windows NT family, macOS (XNU = Mach + BSD).

Others worth naming

Layered: strictly ordered levels, each using only the level below (THE OS).
Exokernel: exposes hardware almost raw and lets library OSes manage it.
Modular / loadable: Linux's real design — monolithic core plus dynamically loadable modules (insmod, rmmod).

1.7 The boot process

A frequently asked "explain end to end" question. Learn the six beats.

  1. Power on → CPU reset. The program counter is set to a fixed address in ROM.
  2. BIOS / UEFI firmware runs POST (Power-On Self-Test), initialises hardware and finds a bootable device.
  3. Bootloader stage 1 — the Master Boot Record (first 512 bytes, MBR) or the EFI System Partition loader is read into memory.
  4. Bootloader stage 2 — GRUB / Windows Boot Manager presents a menu, then loads the kernel image and the initial RAM disk (initrd/initramfs) into memory.
  5. Kernel initialisation — sets up memory management, interrupt tables, mounts the root filesystem, starts drivers.
  6. First user process — the kernel starts PID 1 (systemd or init), which starts all services and finally the login/GUI.
Why a bootloader at all?

Firmware is too small and too dumb to understand file systems, kernel image formats or multiple installed OSes. The bootloader is a tiny purpose-built program whose only job is "find the kernel, load it, jump to it" — this is called bootstrapping, from "pulling yourself up by your bootstraps".

Chapter 01 — Interview questions

What is an operating system and why do we need one?

An OS is system software that sits between hardware and applications. It plays two roles: resource manager (allocates CPU, memory, disk, devices among competing programs fairly and efficiently) and extended machine (hides hardware behind clean abstractions — files, processes, virtual memory, sockets).

We need it because without it every application would have to contain its own device drivers, there would be no protection between programs, and only one program could realistically run at a time.

Follow-up they may ask: name an environment with no OS → simple embedded microcontrollers running bare-metal firmware.
What is a kernel? How is it different from an operating system?

The kernel is the core component of the OS — the part that is always resident in memory, runs in privileged mode, and directly manages CPU scheduling, memory, processes, device drivers and system calls.

The operating system is broader: kernel + user-space utilities, shells, libraries, GUI, package manager. "Linux" is strictly a kernel; "Ubuntu" is an operating system built around it.

Explain user mode vs kernel mode. Why does the hardware need to support this?

The CPU has a mode bit. In kernel mode all instructions are legal, including privileged ones (I/O, changing page tables, setting the timer, halting). In user mode those instructions trap.

Hardware support is essential because protection must not be bypassable by software. If mode were enforced only in software, a malicious program could simply not call the checking code. Since the CPU itself refuses a privileged instruction in user mode, isolation is guaranteed.

A mode switch (user↔kernel) is not a context switch: no process changes, only the privilege level.

Very common follow-up: "Is a mode switch the same as a context switch?" — No, and saying so scores points.
What is a system call? Walk me through what happens during one.

A system call is the controlled interface by which a user process requests a privileged service from the kernel.

Sequence: library wrapper loads the syscall number and arguments into registers → executes a trap instruction → CPU switches to kernel mode and jumps to the trap handler via the interrupt vector → handler saves user context, validates arguments, dispatches via the syscall table → kernel executes the service → result placed in a register → context restored, mode bit cleared, execution resumes after the trap.

Categories: process control, file management, device management, information maintenance, communication.

Monolithic vs microkernel — which is better?

Neither is universally better; it is a performance-versus-reliability trade-off.

Monolithic puts all services in one kernel address space, so a service call is a function call — fast. But the kernel is large and a single driver bug can panic the system.

Microkernel keeps only IPC, scheduling and basic memory management in the kernel, pushing drivers and file systems to user space. That gives fault isolation (a crashed driver can be restarted), better security and portability, at the price of message-passing overhead on every service request.

Practical answer: general-purpose systems chose monolithic/hybrid (Linux, Windows NT, macOS) for speed; safety-critical and real-time systems chose microkernel (QNX in cars, L4 in secure enclaves).

Difference between multiprogramming, multitasking and multiprocessing?

Multiprogramming: multiple programs held in memory on a single CPU; the CPU switches when the running program blocks on I/O. Goal — CPU utilisation.

Multitasking (time-sharing): adds a timer so the CPU switches on a fixed quantum even if nobody blocks. Goal — response time; gives the illusion of simultaneity.

Multiprocessing: more than one physical CPU/core, so instructions genuinely execute in parallel. Goal — throughput and reliability.

What is a real-time operating system? Hard vs soft?

An RTOS guarantees that a task completes within a specified deadline; correctness depends on timing as well as on output. It uses priority-based preemptive scheduling, has bounded interrupt latency, and avoids unpredictable features like demand paging.

Hard real-time: a missed deadline is a total failure — airbag deployment, nuclear plant control, flight control.

Soft real-time: a missed deadline degrades quality but the system still works — video playback, online gaming, VoIP.

Interrupt vs trap vs exception?

Interrupt — asynchronous, raised by hardware external to the CPU (timer, disk, keyboard). Unrelated to the currently executing instruction.

Trap — synchronous and deliberate, raised by a program instruction; the mechanism behind system calls and debugger breakpoints.

Exception/fault — synchronous and accidental, caused by an error condition in the current instruction: divide by zero, page fault, illegal memory access.

All are dispatched through the interrupt vector table to a handler.

Explain the boot process from power-on to login screen.

Power on → CPU jumps to a fixed ROM address → BIOS/UEFI runs POST and locates a boot device → bootloader stage 1 (MBR/EFI loader) loads stage 2 (GRUB or Windows Boot Manager) → bootloader loads the kernel image plus initramfs into RAM and transfers control → kernel initialises memory management, interrupts and drivers, mounts the root filesystem → kernel starts PID 1 (systemd/init), which brings up services and the login manager.

What is a device driver? Why does it live in the kernel?

A device driver is kernel-level software that translates generic OS requests ("write these bytes") into the specific register-level commands a particular hardware controller understands. It presents a uniform interface so the rest of the kernel does not need per-device knowledge.

It typically runs in kernel space because it must execute privileged I/O instructions, handle device interrupts, and access DMA-capable memory — though microkernels and Linux's FUSE/UIO deliberately move some drivers to user space for safety.

What is the difference between a program and a process? (asked here as a warm-up)

A program is a passive entity: an executable file of instructions sitting on disk. A process is an active entity: a program in execution, with a program counter, registers, stack, heap, data section and an entry in the kernel's process table.

One program can produce many processes (open three tabs of the same browser binary). A program has no lifetime; a process is born, runs, and dies. Full detail in Chapter 02.

Chapter 02

Processes and inter-process communication

The process is the OS's unit of ownership and protection. Master its memory layout, its state machine and its control block, and half of the syllabus falls into place.

2.1 Process vs program

Process

A program in execution — an active entity comprising the program code (text section), the current activity represented by the program counter and CPU registers, a stack for temporary data, a data section for global variables, and a heap for dynamically allocated memory.

 ProgramProcess
NaturePassiveActive
Lives inSecondary storage (disk)Main memory
LifetimePermanent until deletedLimited — created and terminated
ResourcesHolds noneHolds CPU, memory, files, devices
RelationshipOne program …… may become many processes

2.2 Memory layout of a process

  • Text — compiled machine code; read-only and shareable between processes running the same binary.
  • Data — initialised global and static variables.
  • BSS — uninitialised globals/statics, zero-filled at load time (costs no space in the executable file).
  • Heap — runtime dynamic allocation (malloc, new); grows upward; the programmer's responsibility.
  • Stack — one frame per function call holding parameters, locals and the return address; grows downward; automatically managed.

2.3 Process states

  • New — being created; PCB allocated but not yet admitted to the ready queue.
  • Ready — has everything it needs except the CPU; waiting in the ready queue.
  • Running — instructions are executing on a CPU. At most one process per core.
  • Waiting / Blocked — cannot proceed until an event occurs (I/O completion, signal, semaphore).
  • Terminated — finished execution; resources being reclaimed.
Common trap

There is no transition from Waiting directly to Running. A process that finishes I/O goes back to Ready and must be scheduled again. Interviewers ask this deliberately.

Two extra states exist in systems with swapping: Suspended-Ready and Suspended-Blocked, where the process has been swapped out of main memory to disk by the medium-term scheduler.

2.4 Process Control Block (PCB)

Process Control Block

The kernel data structure that represents a process — its "identity card". One PCB per process; the collection of PCBs forms the process table. In Linux this is struct task_struct.

Contents, grouped the way you should recite them:

  1. Identification — process ID (PID), parent PID, user ID.
  2. State — new / ready / running / waiting / terminated.
  3. CPU context — program counter, stack pointer, all general-purpose registers, status flags. This is what gets saved and restored on a context switch.
  4. Scheduling information — priority, pointers to scheduling queues, time slice remaining, CPU time used.
  5. Memory management information — base and limit registers, page table pointer or segment table.
  6. Accounting — CPU time consumed, real time elapsed, job/process numbers.
  7. I/O status — list of open files (file descriptor table), allocated devices, pending I/O requests.

2.5 Context switching

Context Switch

The mechanism of saving the state of the currently running process into its PCB and loading the saved state of another process from its PCB, so the CPU can switch execution from one process to another.

Triggered by: a timer interrupt (quantum expiry), a higher-priority process becoming ready, an I/O request that blocks the running process, or process termination.

Context switching is pure overhead

During a switch the CPU does no useful work for the user. The direct cost is saving/restoring registers (~1–10 µs); the indirect and larger cost is cache and TLB pollution — the new process finds a cold cache and stalls on memory. This is exactly why a very small time quantum in Round Robin destroys performance (Chapter 04), and why threads are cheaper to switch than processes (Chapter 03).

The dispatcher is not a scheduler — it is the module that actually carries out the short-term scheduler's decision: context switch, switch to user mode, jump to the right instruction. The time it takes is dispatch latency.

2.7 Creating processes: fork and exec

// classic Unix process creation
pid_t pid = fork();          // duplicate the calling process

if (pid < 0)  { /* fork failed */ }
else if (pid == 0) {
    // CHILD: fork returns 0 here
    execlp("/bin/ls", "ls", NULL);   // replace image with a new program
} else {
    // PARENT: fork returns the child's PID here
    wait(NULL);              // block until child terminates, reap it
}
  • fork() creates a near-identical copy of the parent — same code, data, heap and open file descriptors. It is called once and returns twice: 0 in the child, the child's PID in the parent. Modern kernels use copy-on-write so pages are shared until one side writes.
  • exec() family replaces the current process image with a new program. It does not create a process, and on success it never returns.
  • wait() blocks the parent until a child terminates and collects its exit status.
  • exit() terminates a process and returns a status to the parent.
Classic puzzle: how many processes does this create?

2³ = 8 processes total (1 original + 7 new). In general n consecutive fork() calls yield 2n processes, of which 2n−1 are children. If the question says "how many child processes are created", the answer is 2n−1.

Zombie and orphan processes

Zombie (defunct)

The child has terminated but the parent has not yet called wait(). The PCB is kept alive only to hold the exit status.

Harm: consumes a PID entry; many zombies exhaust the process table.
Fix: parent must wait() / handle SIGCHLD. Killing a zombie does nothing — it is already dead; kill the parent instead, and init reaps it.

Orphan

The parent terminated first while the child is still running.

Handled by: the child is immediately re-parented to init/systemd (PID 1), which will wait() on it. Orphans are harmless.

A daemon is a deliberately created orphan that runs in the background.

Message passing variants

  • Direct naming — send(P, msg) names the process explicitly. Indirect — messages go to a mailbox/port that both share.

Chapter 02 — Interview questions

What is a PCB and what does it contain?

The Process Control Block is the kernel's data structure representing one process — the record used to save and restore it.

Contents: PID and parent PID; process state; CPU context (program counter, stack pointer, registers); scheduling info (priority, queue pointers, quantum left); memory management info (page table base / base & limit registers); accounting info (CPU time used); I/O status (open file table, allocated devices).

All PCBs together form the process table. In Linux it is struct task_struct.

Explain the process state diagram. Can a process go from Waiting to Running?

Five states: New → Ready → Running → Terminated, with Running ↔ Waiting for I/O.

No — a process cannot go directly from Waiting to Running. When the event it was waiting for completes, it moves to Ready and must be selected by the short-term scheduler before it runs again. Only the scheduler can put a process into Running.

Systems with swapping add Suspended-Ready and Suspended-Blocked states, entered when the medium-term scheduler swaps a process out to disk.

What is a context switch and why is it expensive?

Saving the running process's CPU state into its PCB and loading another process's state so it can run.

It is expensive because (a) it is pure overhead — no user work happens during it, and (b) the indirect cost dominates: the new process starts with a cold CPU cache, and on many architectures the TLB must be flushed, so it stalls on memory for thousands of cycles afterwards. Direct cost is a few microseconds; the cache effect can be much larger.

Switching between threads of the same process is cheaper because the address space, page table and TLB entries stay valid.

Difference between long-term, short-term and medium-term scheduler?

Long-term (job scheduler) — selects which jobs are admitted from the job pool into the ready queue. Runs rarely; controls the degree of multiprogramming. It should maintain a good mix of CPU-bound and I/O-bound processes.

Short-term (CPU scheduler) — selects which ready process runs next. Runs every few milliseconds, so it must be fast.

Medium-term — performs swapping: removes processes from memory to disk to reduce the degree of multiprogramming when memory is over-committed, and brings them back later.

What is a zombie process? How do you get rid of one?

A zombie is a child process that has terminated but whose parent has not yet called wait() to read its exit status. The kernel keeps a minimal PCB entry so that status is available — the process holds no memory or CPU, only a PID slot.

You cannot kill a zombie (it is already dead). Fixes: the parent should call wait()/waitpid() or install a SIGCHLD handler; or send SIGCHLD to the parent; or kill the parent, after which the zombie is re-parented to init (PID 1), which reaps it automatically.

Zombie vs orphan process?

Zombie: child is dead, parent is alive but hasn't reaped it. Wastes a process table entry — a real leak if it accumulates.

Orphan: parent is dead, child is still running. Immediately adopted by PID 1, which reaps it on exit. Harmless — daemons are created this way deliberately.

What does fork() return, and how many processes does fork(); fork(); create?

fork() is called once and returns twice: 0 in the child and the child's PID in the parent (−1 on failure). That return value is how the two identical copies tell themselves apart.

Two consecutive forks give 2² = 4 processes (3 children). n forks give 2n processes / 2n−1 children.

Note that modern kernels implement fork with copy-on-write: the child shares the parent's physical pages read-only, and a private copy is made only when either writes.

Difference between fork() and exec()?

fork() creates a new process that is a duplicate of the caller; after it there are two processes running the same code.

exec() replaces the calling process's memory image with a new program; no new process is created, the PID stays the same, and on success it never returns.

They are used together: shell forks, and the child execs the command — which is why the shell survives the command.

What are the IPC mechanisms? Which is fastest and why?

Pipes, named pipes (FIFOs), shared memory, message queues, sockets, signals and memory-mapped files. They fall into two models: shared memory and message passing.

Shared memory is fastest. After the kernel maps one physical region into both address spaces, communication is plain memory read/write at user speed — no system calls, no copying data through the kernel. Message passing copies every message through the kernel, costing two mode switches per exchange.

The catch: shared memory gives you no synchronisation, so you must add semaphores or mutexes yourself to avoid race conditions. Message passing is inherently synchronised and is the only option across machines (sockets).

What is a daemon process?

A background process that runs without a controlling terminal and usually for the lifetime of the system, providing a service — sshd, crond, httpd. Conventionally named with a trailing "d".

Created by forking, letting the parent exit (so the child is orphaned and adopted by PID 1), calling setsid() to detach from the terminal and start a new session, then redirecting standard streams to /dev/null.

What is the difference between a pipe and a message queue?

A pipe is a byte stream with no message boundaries, unidirectional, and (for anonymous pipes) only usable between related processes. Data is consumed in strict FIFO order and disappears when both ends close.

A message queue stores discrete typed messages, preserves boundaries, allows a reader to select messages by type/priority rather than strictly first-in-first-out, works between unrelated processes, and persists in the kernel until explicitly removed.

What is copy-on-write and why is it useful?

An optimisation where a copy operation is deferred: the parent and child initially share the same physical pages, marked read-only in both page tables. The first write by either side triggers a protection fault; the kernel then allocates a fresh frame, copies the page, and marks it writable for that process only.

It makes fork() almost free, which matters because the very common pattern fork() then exec() would otherwise copy an entire address space just to throw it away a microsecond later.

Threads and concurrency

A thread is the unit the CPU actually schedules. Understanding what threads share and what they don't explains every concurrency bug you will ever be asked about.

3.1 What a thread is

Thread

The smallest unit of execution that can be scheduled by the OS — a lightweight process. A thread has its own program counter, register set and stack, but shares the code section, data section, heap and open files with all other threads of the same process.

3.3 Benefits of multithreading

  1. Responsiveness — a UI thread stays interactive while a worker thread does a long download. This is the single best example to give.
  2. Resource sharing — threads share memory by default, so no IPC setup is required.
  3. Economy — creating and switching threads is an order of magnitude cheaper than processes.
  4. Scalability — a multithreaded process can run truly in parallel across cores; a single-threaded one cannot, no matter how many cores you buy.

Multithreading models (how ULTs map to KLTs)

Many-to-one

Many user threads → one kernel thread. Fast switching, but one blocking syscall stops everything and no multicore use. Rare today.

Each user thread has its own kernel thread. True concurrency and blocking is isolated; cost is one kernel structure per thread, so systems cap thread counts. Linux and Windows use this.

Many-to-many

Many user threads multiplexed onto a smaller-or-equal set of kernel threads. Best of both, hardest to implement. Two-level is the same plus the option to bind a thread one-to-one.

3.5 Concurrency vs parallelism

Say it this way

Concurrency is dealing with many things at once — tasks make progress in overlapping time periods; achievable on a single core by interleaving.

Parallelism is doing many things at once — tasks execute literally simultaneously, which requires multiple cores.

Concurrency is a program-structure property; parallelism is a hardware-execution property. Every parallel program is concurrent; not every concurrent program is parallel.

3.6 Thread pools

Creating a thread per request is wasteful and unbounded — a burst of requests can exhaust memory. A thread pool creates a fixed number of worker threads at startup; requests go into a queue and idle workers pick them up.

  • Servicing a request costs no thread creation — faster.
  • The pool size bounds concurrency, protecting the system from overload.
  • Separating task submission from execution lets you schedule and prioritise work.

Rule of thumb for size: CPU-bound work → about the number of cores; I/O-bound work → many more, since threads spend most of their time blocked.

3.7 Other terms interviewers drop in

  • Thread Control Block (TCB) — per-thread structure holding thread ID, program counter, register set, stack pointer, state and a pointer to its PCB.
  • Thread safety — code is thread-safe if it behaves correctly when called simultaneously by multiple threads, typically achieved by avoiding shared mutable state or by protecting it with locks.
  • Reentrant — a function that can be safely interrupted and called again before the first call completes; it uses no static/global mutable state. Reentrant ⇒ thread-safe, but not the reverse (a function can be made thread-safe with a lock while remaining non-reentrant).
  • Race condition — outcome depends on the unpredictable relative timing of threads. Detailed in Chapter 05.
  • Thread cancellation — asynchronous (kill immediately; may leave resources in a bad state) vs deferred (target checks a cancellation point and exits cleanly). Deferred is preferred.
  • Signal handling with threads — a synchronous signal (e.g. divide by zero) goes to the thread that caused it; an asynchronous signal (e.g. Ctrl-C) goes to a thread that isn't blocking it.

Chapter 03 — Interview questions

Click to reveal
What is a thread? What do threads share and not share?

A thread is the basic unit of CPU scheduling — a single flow of execution within a process.

Shared between threads of one process: code/text section, global and static data, heap, open file descriptors, signal handlers, the process ID and current working directory.

Private to each thread: program counter, CPU register set, stack (so local variables are private), thread ID, and per-thread errno.

That split is exactly why threads communicate easily and also why they need synchronisation.

Process vs thread — give the key differences.

A process is an independent program with its own address space; a thread is a lightweight execution unit inside a process sharing that address space.

Processes are expensive to create and switch (address space, page tables, TLB flush); threads are cheap. Processes need IPC to communicate; threads just read shared memory. Processes are isolated — one crashing doesn't affect others; threads are not — one segfault takes down the whole process. Threads require explicit synchronisation, processes usually don't.

User-level threads vs kernel-level threads. What is the biggest drawback of ULTs?

ULTs are managed entirely by a user-space library and the kernel is unaware of them, so switching is very fast (no mode switch) and they are portable. KLTs are created and scheduled by the kernel itself.

Biggest drawback of ULTs: if one user thread makes a blocking system call, the kernel blocks the entire process, since it only sees one schedulable entity — so all other user threads stall. ULTs also cannot exploit multiple cores.

Mitigations historically: non-blocking I/O with an event loop, or "scheduler activations" where the kernel upcalls the library when a thread blocks.

Concurrency vs parallelism?

Concurrency — multiple tasks are in progress over overlapping periods; the CPU may interleave them on one core. It is about program structure and dealing with many things.

Parallelism — multiple tasks execute at the exact same instant on different cores. It is about hardware and doing many things.

Example: a single-core machine running a browser with 10 tabs is concurrent, not parallel. A matrix multiplication split across 8 cores is parallel.

Why is a thread called a lightweight process?

Because it has far less state to create and switch. A process needs a full address space, page tables and a copy of resource tables; a thread needs only a stack, a register set and a small TCB, reusing the parent process's address space and open files. Consequently thread creation and context switching cost roughly an order of magnitude less, and switching between threads of the same process does not invalidate the TLB.

What is a thread pool and why use one?

A fixed set of pre-created worker threads that pull tasks from a shared queue.

Reasons: (1) avoids the per-request cost of thread creation; (2) bounds the number of concurrent threads so a traffic spike can't exhaust memory or thrash the scheduler; (3) decouples task submission from execution, allowing queuing policies and back-pressure.

Sizing: roughly N cores for CPU-bound tasks; substantially more for I/O-bound tasks since workers idle while blocked.

If one thread crashes, what happens to the process? And if it's a process?

If a thread causes a fatal fault (e.g. dereferences a null pointer), the signal is delivered to the process and by default the entire process — all its threads — terminates, because they share one address space and the memory may now be corrupt.

If a process crashes, other processes are unaffected; the OS reclaims its resources and the parent is notified via wait(). This isolation is exactly why browsers run each tab in a separate process rather than a thread.

What is thread safety? Is a thread-safe function always reentrant?

Thread-safe code produces correct results when executed simultaneously by multiple threads, usually by not sharing mutable state or by guarding it with locks.

No. A function made thread-safe by taking a mutex is not reentrant — if a signal handler interrupts it and calls it again, the second call deadlocks on the lock the first call already holds. Reentrancy requires using no shared state at all, which is the stronger property: reentrant ⇒ thread-safe, but not the converse.

Which multithreading model do Linux and Windows use?

One-to-one. Each user thread maps to a distinct kernel thread, giving true parallelism across cores and ensuring a blocking call blocks only that thread. Linux implements it via clone() with shared flags plus the NPTL library; Windows via native kernel thread objects.

The trade-off is one kernel structure per thread, so creating tens of thousands of threads is expensive — which is why modern runtimes layer green threads / goroutines / virtual threads (a many-to-many scheme) on top.

CPU scheduling

The most reliably examined chapter in the whole subject. You will be asked to define the algorithms and to draw a Gantt chart and compute averages by hand — so work every example below with a pen.

4.1 Why schedule at all

Processes alternate between CPU bursts and I/O bursts. An I/O-bound process has many short CPU bursts; a CPU-bound process has few long ones. Whenever the running process blocks or is preempted, the short-term scheduler must pick the next process from the ready queue, and the dispatcher performs the switch. Good scheduling keeps the CPU busy while keeping interactive users happy — those two goals conflict.

4.4 The algorithms

FCFS — First Come First Served

Non-preemptive. Processes run in arrival order; the ready queue is a simple FIFO. Trivial to implement and provably fair in the "no favouritism" sense.

Weakness: the convoy effect. One long CPU-bound process at the head makes every short process behind it wait, wrecking average waiting time and leaving I/O devices idle. Average waiting time under FCFS is generally the worst of all algorithms and varies wildly with arrival order.

SJF — Shortest Job First (non-preemptive)

Among processes that have arrived, pick the one with the smallest CPU burst.

SJF is provably optimal — it gives the minimum possible average waiting time for a given set of processes. Two problems: it needs the burst length in advance (impossible in general — it is predicted using exponential averaging of past bursts, τn+1 = α·tn + (1−α)·τn), and long processes can starve if short ones keep arriving.

SRTF — Shortest Remaining Time First (preemptive SJF)

At every arrival, compare the new process's burst with the running process's remaining time and preempt if it is smaller. Gives an even lower average waiting time than SJF, at the cost of more context switches and worse starvation for long jobs.

Round Robin

FCFS plus preemption on a fixed time quantum (typically 10–100 ms). A preempted process goes to the tail of the ready queue. Designed for time-sharing: it guarantees every process gets the CPU within (n−1)×q time, so response time is bounded and no process starves.

The quantum trade-off — a guaranteed follow-up question

q too large → nobody is preempted before finishing → Round Robin degenerates into FCFS, and response time collapses.

q too small → excellent response time but the CPU spends a large fraction of its time context switching instead of working — this is called processor sharing in the limit, and in practice it thrashes.

Rule of thumb: choose q so that roughly 80% of CPU bursts are shorter than the quantum. Also: q should be large compared to context-switch time (if q = 10 ms and a switch is 0.1 ms, overhead is ~1%).

Priority scheduling

Each process gets a priority number; the CPU goes to the highest priority (conventionally the lowest number). Comes in preemptive and non-preemptive flavours. SJF is simply priority scheduling where priority = 1/burst-length.

Problem: starvation / indefinite blocking — a low-priority process may never run. Solution: aging — gradually increase the priority of a process the longer it waits, so every process eventually reaches the top. (Famously, a low-priority job submitted to MIT's IBM 7094 in 1967 was found still unrun when the machine was shut down in 1973.)

Multilevel Queue (MLQ)

The ready queue is split permanently into several queues — e.g. system processes, interactive processes, batch processes — each with its own scheduling algorithm (RR for interactive, FCFS for batch). Scheduling between queues is usually fixed-priority preemptive, or time-sliced (e.g. 80% of CPU to foreground, 20% to background). A process cannot move between queues, which is inflexible and can starve the lowest queue.

Multilevel Feedback Queue (MLFQ)

The practical descendant, and the model behind real schedulers. Same multiple queues, but a process can move between them:

  • A new process enters the highest-priority queue, which has the smallest quantum.
  • If it uses its whole quantum (it is CPU-bound) it is demoted to a lower queue with a larger quantum.
  • If it blocks for I/O before the quantum expires (it is interactive) it stays or is promoted.
  • Aging promotes long-waiting processes to prevent starvation.

The effect: MLFQ learns the nature of each process without being told burst times, giving short/interactive jobs great response time while long jobs still make progress. It is the most general CPU-scheduling algorithm and also the most complex to tune.

Others worth naming in one line

  • HRRN (Highest Response Ratio Next) — non-preemptive; picks the largest (waiting time + burst)/burst. It favours short jobs but the ratio grows with waiting, so it eliminates starvation. A great answer to "how do you fix SJF's starvation?"
  • LJF / LRTF — longest job/remaining time first; theoretical, poor in practice.
  • Linux CFS (Completely Fair Scheduler) — no fixed quantum; tracks each task's virtual runtime in a red-black tree and always runs the task with the smallest vruntime, approximating perfectly fair CPU sharing.

4.6 Starvation, aging and the convoy effect

  • Starvation (indefinite blocking) — a ready process never gets the CPU because higher-priority or shorter processes keep arriving. Affects SJF, SRTF and Priority.
  • Aging — the standard cure: increase a waiting process's priority over time, so it eventually becomes the highest-priority process and runs.
  • Convoy effect — under FCFS, many short (often I/O-bound) processes are stuck behind one long CPU-bound process. The CPU is busy but the I/O devices sit idle, so overall utilisation is poor. Fixed by preemption or by SJF-like policies.
  • Priority inversion — a high-priority task is blocked waiting for a lock held by a low-priority task, which itself is preempted by a medium-priority task. Cured by priority inheritance (the lock holder temporarily inherits the waiter's priority). This is a genuinely famous bug — it nearly killed the 1997 Mars Pathfinder mission.

Chapter 04 — Interview questions

Click to reveal
What are the goals/criteria of CPU scheduling?

Maximise: CPU utilisation (keep the CPU as busy as possible) and throughput (processes completed per unit time).

Minimise: turnaround time (total time in system), waiting time (time in the ready queue) and response time (arrival to first execution).

Plus fairness — every process should get a reasonable share and none should starve. These conflict: minimising average waiting time favours short jobs, which starves long ones.

Preemptive vs non-preemptive scheduling?

Non-preemptive: once a process gets the CPU it keeps it until it terminates or blocks voluntarily. Simple, low overhead, but a long job destroys response time for everyone (convoy effect). Examples: FCFS, SJF, non-preemptive Priority.

Preemptive: the OS can forcibly take the CPU away, on a timer tick or when a higher-priority process arrives. Gives good response time and is required for time-sharing and real-time systems, but costs more context switches and creates the possibility of race conditions on shared kernel data. Examples: SRTF, Round Robin, preemptive Priority, MLFQ.

Which scheduling algorithm gives the minimum average waiting time, and why can't we just use it?

SJF (and its preemptive form SRTF) is provably optimal for average waiting time — putting shorter jobs first always reduces the sum of waiting times.

We can't use it directly because the CPU burst length of the next burst is not known in advance. In practice it is estimated by exponential averaging of previous bursts: τn+1 = α·tn + (1−α)·τn, typically with α = 0.5.

The second problem is starvation of long processes when short ones keep arriving — which HRRN or aging fixes.

What is the convoy effect?

A performance problem in FCFS where several short processes are queued behind one long CPU-bound process. They all wait a long time, average waiting time balloons, and because the short processes are typically I/O-bound, the I/O devices sit idle the whole time — so overall system utilisation drops even though the CPU is 100% busy.

Fixes: preemption (Round Robin), or shortest-job-first policies.

What happens if the Round Robin time quantum is too large or too small?

Too large: most processes finish within one quantum, so no preemption occurs and RR degenerates into FCFS — losing the responsiveness that was the entire point.

Too small: response time is excellent, but the CPU spends a large fraction of its time context switching rather than executing user code, so throughput collapses.

Practical guidance: the quantum should be large relative to context-switch time (so overhead stays around 1%), and chosen so roughly 80% of CPU bursts complete within one quantum — typically 10–100 ms.

What is starvation and how do you prevent it?

Starvation (indefinite blocking) is when a runnable process never gets the resource it needs — under priority scheduling, a low-priority process may wait forever if higher-priority processes keep arriving.

Prevention: aging — periodically increase the priority of processes that have been waiting a long time, guaranteeing that every process eventually reaches the highest priority. Alternatives: HRRN scheduling (the response ratio grows with waiting time), or reserving a share of CPU time for lower-priority queues.

Deadlock vs starvation — what's the difference?

Deadlock: a set of processes are each waiting for a resource held by another in the set, so none of them can ever proceed. It is a circular, permanent condition, and no process in the set makes progress.

Starvation: a process is able to proceed but is repeatedly passed over by the scheduler while other processes keep making progress. It is not circular and, unlike deadlock, may resolve on its own or with aging.

Deadlock ⇒ starvation for those processes; starvation does not imply deadlock.

Explain Multilevel Feedback Queue scheduling.

The ready queue is divided into several queues of different priority, each with its own quantum (small at the top, large at the bottom), and processes move between queues based on observed behaviour.

A new process starts in the top queue. If it consumes its entire quantum it is judged CPU-bound and demoted to a lower-priority queue with a longer quantum. If it blocks for I/O before the quantum expires it is judged interactive and stays high. Aging promotes processes that have waited too long, preventing starvation.

The value: the scheduler infers whether a job is interactive or batch without being told burst times, giving short jobs SJF-like response while long jobs still progress. It is the most general algorithm — and the hardest to tune, needing the number of queues, each queue's algorithm, and the promotion/demotion rules.

Multilevel Queue vs Multilevel Feedback Queue?

In MLQ a process is permanently assigned to one queue based on a static property (system / interactive / batch) and can never move. It is rigid and can starve the lowest queue entirely.

In MLFQ processes migrate between queues dynamically according to their CPU-burst behaviour, with aging as a safety net. MLFQ is flexible and adaptive; MLQ has lower scheduling overhead.

What is priority inversion? How is it solved?

A high-priority task H needs a lock currently held by a low-priority task L. H blocks. A medium-priority task M, which needs no lock, preempts L — so L never finishes, never releases the lock, and H (the highest priority task in the system) is effectively blocked by M. The priorities are inverted.

Solution: priority inheritance — while L holds a lock wanted by H, L temporarily inherits H's priority, so M cannot preempt it; L finishes quickly, releases the lock, and reverts. An alternative is the priority ceiling protocol.

Famous real case: the Mars Pathfinder rover kept resetting in 1997 due to exactly this bug; it was fixed by enabling priority inheritance remotely.

Turnaround time vs waiting time vs response time?

Turnaround time = Completion − Arrival. Total time the process spent in the system, including running, waiting and doing I/O.

Waiting time = Turnaround − Burst. Total time spent sitting in the ready queue, summed over all the times it waited.

Response time = First time on CPU − Arrival. Only the initial wait; it is the metric interactive users actually feel. Round Robin optimises this at the expense of the other two.

What scheduler does Linux use?

For normal tasks, the Completely Fair Scheduler (CFS). Instead of fixed time slices it tracks each task's virtual runtime (actual runtime weighted by the task's nice value) in a red-black tree, and always dispatches the task with the smallest vruntime. The effect approximates giving every runnable task an exactly equal share of the CPU, with O(log n) selection. (Recent kernels ship EEVDF, a refinement with better latency guarantees.)

Real-time tasks use separate policies — SCHED_FIFO and SCHED_RR — which always outrank normal tasks.

Chapter 05

Process synchronization

Where concurrency stops being an optimisation and starts being a hazard. Every question here reduces to one thing: shared mutable state accessed without coordination.

5.1 The race condition

Race Condition

A situation where the final result depends on the unpredictable relative ordering of operations performed by multiple processes or threads on shared data. The same program with the same input can produce different answers on different runs.

The canonical example: two threads each execute counter++ on a shared counter starting at 5. That one line is really three machine instructions:

T1: load  R1 ← counter      // R1 = 5
T2: load  R2 ← counter      // R2 = 5   <-- context switch happened here
T2: add   R2 ← R2 + 1       // R2 = 6
T2: store counter ← R2      // counter = 6
T1: add   R1 ← R1 + 1       // R1 = 6   (stale!)
T1: store counter ← R1      // counter = 6

Expected 7, got 6. One increment was silently lost.

The bug exists because the read-modify-write sequence is not atomic. The fix is to make it atomic — which is what every mechanism in this chapter does.

5.2 The critical section problem

Critical Section

The segment of code in which a process accesses shared resources (variables, files, tables). The problem is to design a protocol so that no two processes are in their critical sections at the same time.

do {
    entry section      // request permission to enter
        critical section
    exit section       // signal that you have left
        remainder section
} while (true);

The three requirements — memorise these exactly

  1. Mutual Exclusion — if a process is executing in its critical section, no other process may be executing in its own critical section.
  2. Progress — if no process is in its critical section and some processes wish to enter, only those not in their remainder sections may participate in the decision, and the decision cannot be postponed indefinitely. (Plain English: if the room is empty, someone who wants in must be let in.)
  3. Bounded Waiting — there is a limit on how many times other processes may enter their critical sections after a process has made a request and before that request is granted. (Plain English: no starvation — you can't be skipped forever.)

5.3 Software solution: Peterson's algorithm

A two-process solution using only shared memory — no special hardware instruction.

// shared
bool flag[2] = {false, false};   // "I want to enter"
int  turn;                       // "whose turn it is"

// process i (the other is j)
flag[i] = true;        // I want in
turn    = j;           // but you go first
while (flag[j] && turn == j)
      ; // busy-wait

critical section

flag[i] = false;       // I'm done

The trick is turn = j: each process politely defers, so if both arrive simultaneously the last write to turn decides, and exactly one proceeds. Peterson's satisfies all three requirements.

Why isn't Peterson's used in real systems?

Three reasons: (1) it only handles two processes in this form; (2) it busy-waits, burning CPU; (3) modern CPUs and compilers reorder memory operations, which breaks the algorithm unless you insert memory barriers. Real systems use hardware atomic instructions instead.

5.4 Hardware support

  • Disabling interrupts — works on a uniprocessor (no timer tick ⇒ no preemption), but is unacceptable on multiprocessors (other cores keep running) and is far too dangerous to give to user code.
  • Test-and-Set — an atomic instruction that reads a boolean and sets it to true in one indivisible step. A lock is acquired by spinning until Test-and-Set returns false.
  • Compare-and-Swap (CAS) — atomically compares a memory word with an expected value and, only if they match, writes a new value. CAS is the foundation of all modern lock-free data structures and of every atomic type in Java/C++/Go.
  • Atomic variables — std::atomic, AtomicInteger — built on the above.

5.5 Mutex locks and semaphores

Mutex (Mutual Exclusion Lock)

A binary locking mechanism with ownership: the thread that locks it is the only thread permitted to unlock it. Operations: acquire() / release().

Semaphore

An integer variable accessed only through two atomic operations, used for signalling and for controlling access to a pool of resources.

wait(S) / P(S) / down: while (S <= 0) block; S--;
signal(S) / V(S) / up: S++; wake one waiter;

Busy waiting vs blocking

A naive semaphore spins (spinlock): the waiting process loops on the CPU doing nothing. That wastes cycles — but avoids a context switch, so it is actually the right choice on a multiprocessor when the wait is expected to be shorter than a context switch (a few hundred nanoseconds). The alternative is a blocking implementation: the process is put on the semaphore's waiting queue and moved to the Waiting state; signal() wakes it. Better for long waits, and the standard choice for user-level code.

5.6 The three classical problems

Producer–Consumer (bounded buffer)

A producer fills a buffer of size N; a consumer empties it. The producer must block when the buffer is full, and the consumer must block when it is empty.

semaphore mutex = 1;    // mutual exclusion on the buffer
semaphore empty = N;    // number of free slots
semaphore full  = 0;    // number of filled slots

   add item to buffer;          remove item from buffer;

The order of the two waits matters — and this is the trap

If you swap the producer's first two lines to wait(mutex); wait(empty); you get a deadlock: the producer holds the mutex while sleeping on a full buffer, so the consumer can never acquire the mutex to make space. Always acquire the counting semaphore before the mutex, and release in the reverse order.

Readers–Writers

Many readers may read simultaneously (reading doesn't change data), but a writer needs exclusive access.

  • First readers–writers problem — readers have priority; no reader waits unless a writer already has permission. Writers can starve.
  • Second readers–writers problem — writers have priority; once a writer is waiting, no new reader may start. Readers can starve.
  • Fair/third variant — a queue-based solution where neither starves.
  • Real implementation: a reader-writer lock (pthread_rwlock, ReadWriteLock), which is a big performance win for read-heavy workloads.

Dining Philosophers

Five philosophers sit around a table with five chopsticks between them; each needs both neighbours' chopsticks to eat. The naive solution — "pick up left, then pick up right" — deadlocks the instant all five pick up their left chopstick simultaneously: circular wait.

Standard fixes — each breaks one deadlock condition:

  • Allow at most four philosophers at the table (breaks circular wait).
  • Asymmetric solution: odd-numbered philosophers pick up left first, even-numbered pick up right first (breaks circular wait). This is the most elegant answer.
  • Pick up both chopsticks only if both are available, in one atomic step, else pick up neither (breaks hold-and-wait).
  • Impose a global ordering on chopsticks and always acquire the lower-numbered one first (breaks circular wait) — this generalises to real lock-ordering discipline in code.

5.7 Monitors

Monitor

A high-level synchronisation construct — an abstract data type in which shared variables are private and only one process can be active inside the monitor at a time, enforced automatically by the compiler/runtime. Condition variables (wait / signal) allow a process to sleep inside the monitor and release the monitor lock while it sleeps.

Why monitors exist: semaphores are error-prone — one forgotten signal(), or two wait()s in the wrong order, and you get a deadlock that appears once a week in production. A monitor moves mutual exclusion out of the programmer's hands and into the language. Java's synchronized keyword with wait()/notify() is a monitor.

Condition variable vs semaphore

A semaphore remembers: a signal() with no waiter still increments the count, so a later wait() succeeds immediately. A condition variable is stateless: a signal() with no waiter is lost forever. That is exactly why condition-variable waits must always sit inside a while loop re-checking the predicate, never an if.

What is a race condition? Give an example.

A race condition occurs when two or more threads access shared data concurrently and the final result depends on the unpredictable order in which they are scheduled.

Example: two threads each run counter++ on a shared counter of 5. That statement compiles to load, add, store. If both load 5 before either stores, both compute 6 and both store 6 — the result is 6 instead of 7, and one update is lost.

The root cause is that read-modify-write is not atomic; the fix is mutual exclusion (mutex, semaphore) or an atomic instruction (compare-and-swap).

What is a critical section, and what three conditions must a solution satisfy?

The critical section is the part of a program that accesses shared resources and must not be executed by more than one process at a time.

1. Mutual exclusion — at most one process in its critical section at any time.
2. Progress — if no one is inside and processes want to enter, the selection cannot be postponed indefinitely, and only contending processes take part in the decision.
3. Bounded waiting — there is a bound on how many times others can enter after a process has requested entry, so no process starves.

Mutex vs semaphore — the difference?

A mutex is a locking mechanism with ownership: only the thread that acquired it may release it. It is strictly for mutual exclusion, and typically supports priority inheritance.

A semaphore is a signalling mechanism — an atomic counter with wait/signal operations and no ownership, so any thread may signal it. A binary semaphore (0/1) can provide mutual exclusion; a counting semaphore (0…N) manages N interchangeable resources such as a pool of database connections.

Key consequence of ownership: a semaphore can signal between threads ("thread A finished, thread B may proceed") — a mutex cannot express that.

Binary semaphore vs mutex — aren't they the same?

They look identical (both take values 0/1) but differ in two ways that matter.

Ownership: a mutex must be released by its locker; a binary semaphore may be signalled by any thread. So a binary semaphore can be used for signalling and a mutex cannot, and a mutex can detect programming errors that a semaphore cannot.

Priority inheritance: because a mutex knows its owner, the OS can boost that owner's priority to solve priority inversion. A semaphore has no owner, so it cannot.

What is a spinlock? When would you use one?

A spinlock is a lock where a thread that fails to acquire it busy-waits in a tight loop rather than being put to sleep.

It is wasteful on a uniprocessor (the spinner prevents the lock holder from running). But on a multiprocessor it is faster than blocking when the expected wait is shorter than the cost of two context switches — a few hundred nanoseconds. Kernels use them extensively for very short critical sections, especially in interrupt handlers where sleeping is forbidden.

Explain the producer–consumer problem and its solution.

A producer adds items to a shared bounded buffer of size N and a consumer removes them. The producer must not write to a full buffer, the consumer must not read from an empty one, and neither may access the buffer while the other is mid-operation.

Solution with three semaphores: mutex = 1 for exclusive buffer access, empty = N counting free slots, and full = 0 counting filled slots. The producer does wait(empty); wait(mutex); …insert…; signal(mutex); signal(full); and the consumer mirrors it.

Critical detail: the counting semaphore must be acquired before the mutex. Reversing them deadlocks — a producer would fall asleep on a full buffer while still holding the mutex the consumer needs to drain it.

Explain the readers–writers problem.

A shared object is accessed by readers, who only read, and writers, who modify. Any number of readers may proceed concurrently, but a writer needs exclusive access — no other reader or writer.

Reader-priority (first) variant: a reader never waits unless a writer is already writing — maximises concurrency but writers may starve under continuous reads. Writer-priority (second) variant: once a writer is waiting, no new reader may begin — readers may starve. A fair variant queues all requests in arrival order.

In practice this is a reader–writer lock, which is a large win for read-heavy structures like caches and routing tables.

Explain the dining philosophers problem and one correct solution.

Five philosophers alternate between thinking and eating; each needs the two chopsticks adjacent to them. If every philosopher picks up their left chopstick at the same moment, all five hold one and wait forever for the other — a deadlock caused by circular wait.

Correct solutions, each breaking a deadlock condition: allow only four philosophers at the table at once; make odd philosophers take left-then-right and even ones right-then-left (asymmetry breaks the cycle); require both chopsticks be acquired atomically or neither (breaks hold-and-wait); or number the chopsticks and always acquire the lower number first.

The last one is the real-world lesson: a consistent global lock ordering is how production code avoids deadlock.

What is a monitor and why is it preferred over semaphores?

A monitor is a high-level construct bundling shared data with the procedures that operate on it, where the runtime guarantees that only one process executes inside the monitor at a time. Condition variables let a process wait inside the monitor while releasing the monitor lock.

It is preferred because semaphores are unstructured and easy to misuse — omit a signal(), or order two wait()s wrongly, and you get a deadlock that surfaces intermittently. A monitor makes the mutual exclusion automatic and compiler-enforced, so those errors become impossible. Java's synchronized is a monitor.

What is Peterson's algorithm? Why don't real systems use it?

A pure-software solution to the two-process critical section problem using a shared flag[2] array ("I want to enter") and a shared turn variable ("you go first"). Each process sets its flag, then politely sets turn to the other, then waits while the other both wants to enter and holds the turn. It satisfies mutual exclusion, progress and bounded waiting.

Not used in practice because it busy-waits, only handles two processes in this form, and — most importantly — modern CPUs and compilers reorder memory operations, which breaks the algorithm's assumptions unless explicit memory barriers are added. Hardware atomics (test-and-set, compare-and-swap) are simpler and faster.

What is compare-and-swap and why does it matter?

An atomic CPU instruction: "compare the value at address X with an expected value E; if they are equal, replace it with a new value N; report whether the swap happened" — all indivisibly.

It matters because it lets you build lock-free algorithms: read the current value, compute the new one, and CAS it in; if another thread interfered, the CAS fails and you retry. No thread can be blocked by another holding a lock, so there is no deadlock and no priority inversion. Every atomic type in Java, C++ and Go, and most modern concurrent queues and counters, are built on CAS.

What is a deadlock in the context of locks, and how do you avoid it in your code?

Two threads each hold a lock the other needs, so both wait forever — e.g. thread A locks mutex 1 then mutex 2, thread B locks mutex 2 then mutex 1.

Practical avoidance: (1) impose a global lock ordering and always acquire in that order; (2) use try_lock with timeout and back off on failure; (3) hold as few locks as possible and never call unknown code while holding one; (4) prefer lock-free structures or a single coarse lock where contention allows. Full theory in Chapter 06.

Chapter 06

Deadlocks

Four conditions, four strategies, one algorithm you will be asked to run by hand. This chapter is high-yield and almost entirely mechanical once you learn the structure.

6.1 Definition

Deadlock

A situation in which every process in a set is waiting for an event that can only be caused by another process in the same set. Since all are waiting, none can trigger the event, and none will ever proceed.

The everyday analogy: two cars meeting on a single-lane bridge from opposite ends, each refusing to reverse.

6.2 The four necessary conditions (Coffman conditions)

All four must hold simultaneously for deadlock to be possible. Break any one and deadlock cannot occur — that is the entire basis of prevention.

6.3 Resource Allocation Graph (RAG)

A directed graph with processes (circles) and resources (rectangles, with a dot per instance).

  • Request edge P → R : process P has requested resource R.
  • Assignment edge R → P : an instance of R has been allocated to P.

6.4 The four strategies

1. Prevention

Design the system so that one of the four conditions can never hold. Applied statically, before anything runs.

+ Deadlock is structurally impossible.
− Low device utilisation, reduced throughput, possible starvation.

2. Avoidance

Allow the conditions, but use advance knowledge of maximum needs to grant a request only if the system stays in a safe state. This is the Banker's algorithm.

+ Better utilisation than prevention.
− Requires each process to declare maximum resource needs up front — usually unrealistic — and runs an O(m·n²) check on every request.

3. Detection & Recovery

Let deadlocks happen, run a detection algorithm periodically, then recover by killing processes or preempting resources.

+ Full utilisation while things are healthy.
− Detection is expensive; recovery loses work.

4. Ignore it — the Ostrich Algorithm

Pretend deadlocks never happen; if the system hangs, reboot. Used by Linux, Windows and most Unixes, because deadlock is rare and the cost of prevention is paid constantly while the cost of a reboot is paid almost never.

6.5 Safe state and the Banker's Algorithm

Safe State

A state is safe if there exists a sequence of all processes <P₁, P₂, …, Pₙ> — a safe sequence — such that for each Pᵢ, the resources it may still request can be satisfied by the currently available resources plus those held by all Pj with j < i.

The relationship to remember

Safe state ⇒ no deadlock.
Unsafe state ⇒ possibility of deadlock (not certainty).
Deadlock ⇒ unsafe state.

So avoidance works by simply never leaving the safe region.

Data structures

  • Available[m] — instances of each resource type currently free.
  • Max[n][m] — maximum demand of each process.
  • Allocation[n][m] — currently held by each process.
  • Need[n][m] = Max − Allocation — what each process may still ask for.

Safety algorithm

  1. Work = Available; Finish[i] = false for all i.
  2. Find an i with Finish[i] = false and Need[i] ≤ Work.
  3. If found: Work = Work + Allocation[i]; Finish[i] = true; go to 2.
  4. If no such i exists: the state is safe iff Finish[i] = true for all i.

Resource-Request algorithm

When process Pᵢ requests Requesti:

  1. If Requesti > Needi → error, the process exceeded its declared maximum.
  2. If Requesti > Available → Pᵢ must wait (resources not there right now).
  3. Otherwise pretend to allocate: Available −= Request; Allocationi += Request; Needi −= Request.
  4. Run the safety algorithm on this hypothetical state. Safe → grant. Unsafe → roll back and make Pᵢ wait, even though the resources are physically available.
Limitations of Banker's — always mention these

It requires every process to declare its maximum resource needs in advance, which real programs cannot do. It assumes a fixed number of processes and resources, which breaks when processes come and go. And it is expensive — O(m×n²) per request. That is why no general-purpose OS actually uses it.

6.6 Detection and recovery

  • Single instance per resource type — maintain a wait-for graph (the RAG with resource nodes collapsed out) and periodically search for a cycle. A cycle ⇔ deadlock. Cost O(n²).
  • Multiple instances — run an algorithm very like the safety algorithm, but using current requests instead of maximum need. Any process left unfinished is deadlocked.
  • How often to run it? Every request (expensive, but identifies the exact culprit) or periodically / when CPU utilisation drops below a threshold (cheap, but harder to attribute).

Recovery options

  • Process termination — abort all deadlocked processes (expensive, guaranteed), or abort one at a time until the cycle breaks (needs re-running detection each time). Victim selection considers priority, CPU time consumed so far, resources held, and how many more it needs.
  • Resource preemption — take a resource from a victim and give it to another. Requires rollback to a safe checkpoint, and raises the risk of starvation if the same process is always chosen — so include the number of past rollbacks in the cost function.

Click to reveal
What is a deadlock and what are the four necessary conditions?

A deadlock is a state where every process in a set waits for an event that only another process in the same set can cause, so none can ever proceed.

The four Coffman conditions, all of which must hold simultaneously:

1. Mutual exclusion — at least one resource is non-sharable.
2. Hold and wait — a process holds resources while requesting more.
3. No preemption — resources can only be released voluntarily.
4. Circular wait — a closed chain of processes each waiting on the next.

Breaking any single one makes deadlock impossible.

How do you prevent deadlock? Which condition is most practical to break?

Mutual exclusion: make resources sharable — rarely possible, since some devices are inherently exclusive.

Hold and wait: require a process to request all resources at once before starting, or to release everything before requesting more. Causes poor utilisation and starvation.

No preemption: forcibly reclaim resources from waiting processes. Only works where state can be saved and restored — fine for CPU and memory, impossible for a printer mid-page.

Circular wait: impose a total ordering on all resource types and require processes to request them in increasing order. This is the practical one, and it is exactly the "consistent lock ordering" rule real codebases enforce.

Deadlock prevention vs deadlock avoidance?

Prevention is static: the system is designed so that one of the four conditions can never hold. It needs no runtime information about future requests, but it constrains how resources are requested and therefore wastes capacity.

Avoidance is dynamic: all four conditions are allowed, but before granting any request the OS checks — using each process's declared maximum need — whether the resulting state is still safe. If not, the request waits even though resources are free. It gives better utilisation but requires knowledge no real program has.

What is a safe state? Does an unsafe state mean deadlock?

A state is safe if there is at least one ordering of all processes — a safe sequence — in which each process's remaining maximum need can be met from the currently available resources plus those released by the processes before it. Then every process can finish.

No. Unsafe means only that deadlock is possible, not certain: the processes might never actually request their declared maximums. But since the OS cannot know, avoidance conservatively refuses to enter unsafe states. Formally: safe ⇒ no deadlock; deadlock ⇒ unsafe; unsafe ⇏ deadlock.

Explain the Banker's algorithm.

A deadlock-avoidance algorithm, named after how a banker never lends so much that they cannot satisfy every customer's credit line.

It maintains Available, Max, Allocation and Need = Max − Allocation. On each request it checks (a) the request doesn't exceed the declared Need, (b) the resources are available, then it tentatively grants them and runs the safety algorithm: repeatedly find a process whose Need fits in the current Work vector, "finish" it, and add its Allocation back to Work. If every process can be finished this way the state is safe and the request is granted; otherwise the tentative allocation is rolled back and the process waits.

Limitations: needs maximum demands in advance, assumes a fixed process/resource count, and costs O(m·n²) per request — which is why real operating systems don't use it.

What is a resource allocation graph? When does a cycle mean deadlock?

A directed graph with processes as circles and resource types as rectangles containing one dot per instance. A request edge goes P → R; an assignment edge goes R → P.

No cycle ⇒ no deadlock, always.

If a cycle exists and every resource type has exactly one instance, deadlock is certain. If some resource types have multiple instances, a cycle is only a necessary condition — another process holding an instance may finish and release it, breaking the cycle.

What is the ostrich algorithm? Why do real operating systems use it?

Deliberately ignoring the deadlock problem — "bury your head in the sand" — and relying on the user or administrator to reboot or kill processes if the system hangs.

Linux, Windows and most Unix systems take this approach because deadlocks are rare in practice, while prevention and avoidance impose a cost on every single resource request. The engineering trade-off favours paying nothing most of the time and accepting a rare manual recovery. Systems where deadlock is unacceptable — databases, real-time control — do implement detection with rollback.

How would you detect and recover from a deadlock?

Detection: with one instance per resource type, build a wait-for graph (processes only) and search for a cycle — a cycle means deadlock, cost O(n²). With multiple instances, run a variant of the safety algorithm using current requests rather than maximum needs; processes that cannot be marked finished are deadlocked. Run it periodically or when CPU utilisation drops suspiciously low.

Recovery: either terminate processes (all deadlocked ones at once, or one at a time re-checking after each) or preempt resources and roll the victim back to a checkpoint. Victim selection weighs priority, CPU time already invested, resources held and needed, and — importantly — how many times the process has already been rolled back, to avoid starving it.

Can deadlock occur with a single resource type? With a single process?

With a single resource type having one instance: no, because circular wait needs at least two resources. With a single resource type having multiple instances and processes each needing several, yes — e.g. 2 instances and two processes each eventually needing 2.

With a single process: classic deadlock (which is defined over a set of processes) cannot occur, but a process can deadlock against itself by trying to acquire a non-recursive mutex it already holds — this is called self-deadlock, and it is a real bug pattern.

A system has 3 processes each needing 2 units of a resource. What is the minimum number of units that guarantees no deadlock?

4 units.

General formula: with n processes each needing a maximum of m units, deadlock is impossible if the total number of units R satisfies

R ≥ n × (m − 1) + 1

Reasoning: the worst case is every process holding m−1 units and waiting. That uses n×(m−1) units. One extra unit lets some process reach its maximum, finish, and release everything — breaking the chain. Here 3 × (2−1) + 1 = 4.

This exact formula appears constantly in aptitude and GATE-style rounds.
Chapter 07

Memory management

How the OS gives every process the illusion of owning a large, private, contiguous memory — and the two kinds of fragmentation that illusion creates.

7.1 Logical vs physical address

Logical (virtual) address

The address generated by the CPU as a program executes. The set of all such addresses is the process's logical address space. It always starts at 0 from the program's point of view.

Physical address

The address actually seen by the memory unit — an index into real RAM. The set of them is the physical address space.

The Memory Management Unit (MMU) is the hardware that translates one to the other at every memory reference. In compile-time and load-time binding the two are identical; in execution-time binding — what all modern systems use — they differ, and that is what allows a process to be moved in memory while it runs.

Address binding — when a symbolic name becomes an address

  • Compile time — absolute code is generated. If the start location changes, you must recompile. (Old MS-DOS .COM programs.)
  • Load time — the compiler emits relocatable code; final binding happens when the program is loaded. Moving the process requires reloading.
  • Execution time — binding is deferred to every memory access, done by the MMU. The process can be moved at any moment. Requires hardware support (base/limit or page tables).

7.2 Contiguous memory allocation

The simplest scheme: each process gets one contiguous block of RAM. Protection uses two registers — a base (relocation) register holding the smallest legal physical address and a limit register holding the size. Every logical address is checked against the limit and then added to the base; a violation traps to the OS.

7.4 Paging

Paging

A memory management scheme that permits a process's physical address space to be non-contiguous. Physical memory is divided into fixed-size frames; logical memory is divided into blocks of the same size called pages. To run a process of n pages, find any n free frames — they need not be adjacent.

Paging eliminates external fragmentation completely, because any free frame fits any page. It introduces internal fragmentation instead, but only in the last page of each process — on average half a page, which is tiny.

Address translation

A logical address is split by hardware into two parts. If the page size is 2n bytes, the low n bits are the offset (d) and the remaining high bits are the page number (p). No division is needed — it is just wire splitting.

Worked example

Page size = 4 KB = 4096 B = 212. Logical address = 8203. Page 2 is stored in frame 5. Find the physical address.

Page number p = ⌊8203 / 4096⌋ = 2. Offset d = 8203 − (2 × 4096) = 8203 − 8192 = 11. Frame f = 5. Physical address = (5 × 4096) + 11 = 20480 + 11 = 20491.

Number of pages = logical address space size / page size
Page table size = number of pages × size of one page table entry
Bits: 32-bit logical address, 4 KB pages → 12 offset bits, 20 page-number bits → 220 = 1M entries

7.5 The TLB — Translation Lookaside Buffer

The page table lives in main memory, so a naive design needs two memory accesses per instruction: one to read the page table entry, one to read the actual data. That halves performance. The fix is the TLB — a small, fast, fully-associative hardware cache (typically 64–1024 entries) of recently used page→frame mappings.

EAT (with TLB) = hit-ratio × (TLB time + memory time) + (1 − hit-ratio) × (TLB time + 2 × memory time)
Worked EAT example

TLB access = 20 ns, memory access = 100 ns, hit ratio = 80%.

EAT = 0.8 × (20 + 100) + 0.2 × (20 + 100 + 100) = 0.8 × 120 + 0.2 × 220 = 96 + 44 = 140 ns.
Compared to a raw 100 ns access, that is a 40% slowdown — and with a 98% hit ratio it drops to 122 ns. This is why hit ratio matters so much.

On a context switch the TLB entries of the old process are invalid. Flushing the whole TLB is correct but costly, so modern CPUs tag each entry with an ASID (address-space identifier) so entries from several processes can coexist.

7.6 Page table structures

Single-level

One flat array indexed by page number. With 32-bit addresses, 4 KB pages and 4-byte entries you need 220 × 4 B = 4 MB of contiguous memory per process — far too much. Unusable at scale.

Hierarchical (multi-level)

Page the page table itself. A 32-bit address becomes p1 (10 bits) | p2 (10 bits) | d (12 bits). Only the inner tables that are actually used need to exist, so a sparse address space costs almost nothing. x86-64 uses four levels.

Cost: one extra memory access per level on a TLB miss.

Hashed page table

Hash the virtual page number into a table of chains. Common on 64-bit architectures where the address space is far too sparse for hierarchical tables.

Inverted page table

One entry per physical frame, not per virtual page — so there is exactly one table for the whole system. Each entry stores <PID, page number>.

+ Huge memory saving.
− Translation requires searching the table (mitigated by hashing), and shared memory is hard to represent.

Segmentation

Click to reveal
Logical address vs physical address? Who translates between them?

A logical (virtual) address is generated by the CPU during program execution; every process believes its address space starts at 0. A physical address is the actual location in RAM.

Translation is done in hardware by the MMU on every memory reference, using the base/limit registers or the page table. The separation is what allows the OS to move a process in memory, to give each process an isolated address space, and to make memory look larger than it is.

Internal vs external fragmentation?

Internal fragmentation is unused space inside an allocated block, because memory is handed out in fixed-size units. A process needing 4.1 KB gets two 4 KB pages and wastes 3.9 KB. Occurs in paging and fixed partitioning.

External fragmentation is unused space between allocated blocks: enough total free memory exists but it is scattered in pieces too small to satisfy a request. Occurs in segmentation and variable partitioning.

External fragmentation is cured by compaction (relocating blocks to coalesce holes) or, better, by paging, which eliminates it entirely. Internal fragmentation is reduced by smaller pages — at the cost of larger page tables.

What is paging and what problem does it solve?

Paging divides physical memory into fixed-size frames and logical memory into equal-sized pages, allowing a process's pages to be scattered across any free frames.

It solves external fragmentation: since every frame is identical in size, any free frame can hold any page, so free memory is never unusable due to being split up. It also makes it easy to load only part of a process (demand paging) and to share pages between processes.

The price is internal fragmentation in the last page (about half a page per process on average) and the memory and time cost of page tables.

How does address translation work in paging?

The CPU-generated logical address is split by hardware into a page number p (high bits) and an offset d (low bits). With a page size of 2n bytes, the low n bits are the offset.

p indexes the page table to get the frame number f; the physical address is then f × page-size + d — in practice just concatenating f with d. The offset passes through unchanged.

Example: page size 4 KB, logical address 8203 → p = 2, d = 11. If page 2 maps to frame 5, physical address = 5 × 4096 + 11 = 20491.

What is a TLB? Compute the effective access time.

The Translation Lookaside Buffer is a small, fast, fully-associative hardware cache holding recently used page-number → frame-number mappings. Without it, every memory reference would need two memory accesses — one for the page table and one for the data — halving performance.

EAT = h × (tTLB + tmem) + (1−h) × (tTLB + 2tmem)

With TLB = 20 ns, memory = 100 ns, hit ratio 80%: EAT = 0.8(120) + 0.2(220) = 96 + 44 = 140 ns.

On a context switch the TLB must be flushed or entries tagged with an address-space identifier (ASID) so different processes' entries can coexist.

Why do we need multi-level page tables?

Because a single-level table is too big. With a 32-bit address space, 4 KB pages and 4-byte entries, each process needs 220 entries = 4 MB of contiguous physical memory, and 64-bit address spaces make this absurd.

Multi-level paging pages the page table itself: the page number is split into several indices, and only the inner tables that are actually used need to exist. Since real address spaces are extremely sparse, this saves almost all of that memory. x86-64 uses four levels.

The cost is one extra memory access per level on a TLB miss — which is exactly why the TLB hit ratio matters so much.

What is an inverted page table?

A single system-wide table with one entry per physical frame rather than one per virtual page. Each entry records which <process, virtual page> currently occupies that frame.

Advantage: memory used is proportional to physical RAM, not to the number and size of address spaces — a huge saving on 64-bit systems.

Disadvantage: translation requires searching the table rather than indexing it (mitigated with a hash table), and shared pages are difficult because a frame can only have one owner entry.

Paging vs segmentation — which is better?

Paging uses fixed-size blocks decided by hardware, is invisible to the programmer, and suffers only internal fragmentation. Segmentation uses variable-size blocks that correspond to logical program units (code, stack, a specific array), is visible to the programmer, and suffers external fragmentation.

Paging wins on memory utilisation and simplicity of allocation. Segmentation wins on protection and sharing, because a whole logical unit — like a code segment — can be marked read-only and shared naturally.

Modern systems use paging, sometimes with a thin segmentation layer on top (segmented paging), getting logical structure without external fragmentation.

First fit vs best fit vs worst fit — which performs best?

First fit takes the first hole large enough — fastest, since it stops searching early. Best fit takes the smallest sufficient hole — must scan the entire list and tends to leave many tiny unusable fragments. Worst fit takes the largest hole, intending to leave a usable remainder.

Simulation studies consistently show first fit and best fit are both better than worst fit in storage utilisation, and first fit is generally faster. Worst fit performs poorly because it quickly destroys the large holes needed for large processes.

What is swapping, and how is it different from paging?

Swapping moves an entire process out of main memory to a backing store and back later, managed by the medium-term scheduler. It raises the degree of multiprogramming beyond physical RAM but is slow — transferring a whole address space takes seconds.

Paging (with demand paging) moves individual pages, so only the small parts actually needed are transferred. Modern systems therefore do demand paging rather than whole- process swapping; the "swap partition" name survives but it stores pages.

Chapter 08

Virtual memory

The single most-asked topic after scheduling. Page faults, replacement algorithms, Belady's anomaly and thrashing — learn to work the reference strings by hand.

8.1 The idea

Virtual Memory

A technique that allows the execution of processes not completely in main memory. It separates the logical address space (which can be far larger than RAM) from physical memory, keeping only the currently needed pages resident and the rest on disk.

Why it works: the principle of locality. Programs do not touch their memory uniformly; at any moment they reference a small subset. Temporal locality — a location referenced now is likely to be referenced again soon (loops, counters). Spatial locality — nearby locations are likely to be referenced soon (arrays, sequential code).

Benefits

  • A program can be larger than physical memory.
  • More processes fit in memory → higher degree of multiprogramming and CPU utilisation.
  • Less I/O is needed to load or swap a program, so it starts faster.
  • Enables efficient process creation via copy-on-write, and shared libraries mapped once into many address spaces.

8.2 Demand paging and the page fault

Pages are loaded only when referenced — a "lazy swapper". Each page table entry carries a valid/invalid bit: valid means the page is in memory, invalid means it is either illegal or on disk.

EAT = (1 − p) × memory-access-time + p × page-fault-service-time    where p = page fault rate
Worked example — why page faults must be rare

Memory access = 200 ns, page fault service = 8 ms = 8,000,000 ns.

EAT = (1−p)(200) + p(8,000,000) = 200 + 7,999,800p ns.

With p = 0.001 (one fault per 1000 accesses): EAT = 200 + 7999.8 ≈ 8200 ns — a 40× slowdown.

To keep degradation under 10% we need 220 > 200 + 7,999,800p, i.e. p < 0.0000025 — fewer than one fault per 400,000 accesses. This calculation is a favourite in interviews because the answer is so counter-intuitive.

8.3 Page replacement algorithms

LRU implementation — the two classic methods

  • Counters — every page table entry has a time-of-use field, updated from a logical clock on every reference. Replacement scans for the smallest. Requires a memory write on every memory reference — very expensive.
  • Stack — keep page numbers in a doubly-linked list; on reference, move that page to the top. The bottom is always the LRU victim. No search needed, but six pointer updates per reference.
  • Because both are too slow in hardware, real systems use reference-bit approximations: the additional-reference-bits algorithm (shift an 8-bit history register right on each timer interrupt) or the enhanced second-chance algorithm using the (reference, dirty) pair, which prefers evicting clean unreferenced pages.

8.4 Belady's anomaly

Belady's Anomaly

The counter-intuitive phenomenon where increasing the number of frames increases the number of page faults for certain reference strings, under FIFO replacement.

The standard demonstration

Reference string: 1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5 under FIFO.

With 3 frames → 9 page faults. With 4 frames → 10 page faults. More memory, worse performance.

Why it happens: FIFO does not have the stack property — the set of pages resident with n frames is not guaranteed to be a subset of the set resident with n+1 frames, so a larger memory can hold a genuinely worse selection of pages.

Which algorithms are immune? Stack algorithms — LRU and Optimal — never suffer Belady's anomaly. FIFO and Second Chance can.

8.5 Frame allocation

  • Equal allocation — m frames split evenly among n processes. Simple, wasteful for small processes.
  • Proportional allocation — frames given in proportion to process size (or to priority). Fairer in practice.
  • Global replacement — a faulting process may take a frame from any process. Better throughput, but a process's fault rate now depends on other processes' behaviour, making performance unpredictable.
  • Local replacement — a process may only replace its own frames. Predictable per-process performance, but a process cannot use free memory that others aren't using.
  • Every process needs a minimum number of frames — enough to hold all pages that a single instruction can reference, otherwise the instruction can never complete.

8.6 Thrashing

Thrashing

A state in which a process (or the whole system) spends more time paging than executing. It occurs when processes do not have enough frames to hold their active pages, so every eviction is immediately followed by a fault for the evicted page.

The vicious cycle to describe:

  1. Processes lack frames → page fault rate rises.
  2. Processes block waiting on disk → CPU utilisation drops.
  3. The OS's long-term scheduler sees low CPU utilisation and concludes it should increase the degree of multiprogramming.
  4. New processes take frames from existing ones → fault rate rises further. Go to 1.

Throughput collapses almost vertically past a threshold. The fix is to reduce the degree of multiprogramming — the opposite of what the naive scheduler does.

Two solutions

Working set model

The working set WS(t, Δ) is the set of pages referenced in the most recent Δ references — an approximation of locality.

The OS computes D = Σ WSSi, the total demand. If D > m (total frames), thrashing is imminent and a process is suspended. If D is comfortably below m, another process can be admitted.

Page-Fault Frequency (PFF)

Measure each process's fault rate directly and define an acceptable band.

Rate too high → the process needs more frames; give it some. Rate too low → it has more than it needs; take some away. If no frames are available to give, suspend a process.

More direct and cheaper than tracking working sets.

8.7 Related mechanisms

  • Copy-on-write — parent and child share pages read-only after fork(); a private copy is made on the first write. Makes process creation nearly free.
  • Memory-mapped files (mmap) — a file is mapped into the address space so file I/O becomes ordinary memory access, handled by demand paging. Also the mechanism behind shared libraries.
  • Pre-paging — bring in a group of pages before they fault, betting on spatial locality. Wins only if most pre-paged pages are actually used.
  • Page buffering — keep a pool of free frames so a fault can be served immediately, writing the evicted page out later in the background.
  • Page size trade-off — larger pages mean smaller page tables, better disk transfer efficiency and better TLB reach, but more internal fragmentation and more wasted I/O. Trend has been toward larger pages (4 KB standard, 2 MB / 1 GB "huge pages" for databases).

What is virtual memory and how does it work?

Virtual memory lets a process execute while only part of it is in physical RAM, by separating the logical address space from physical memory. Pages not currently in RAM live on disk in swap space.

Mechanism: each page table entry has a valid/invalid bit. When the CPU references a page marked invalid, the hardware raises a page fault; the OS finds the page on disk, loads it into a free (or newly freed) frame, updates the page table, and restarts the faulting instruction.

It works because of locality of reference — a process only touches a small subset of its pages at any moment. The benefits are: programs larger than RAM, more processes resident at once, faster startup, and cheap process creation via copy-on-write.

What is demand paging? What is a page fault?

Demand paging loads a page into memory only when it is actually referenced — a "lazy swapper" — rather than loading the whole process up front.

A page fault is the trap raised when a process references a page that is not currently in physical memory. Handling: trap to the OS → check the reference is legal → find a free frame (evicting a victim if necessary) → schedule a disk read → update the page table and set the valid bit → restart the faulting instruction.

Note a page fault is not an error — it is a normal, expected event. An invalid reference to an address outside the address space is the error case, and results in a segmentation fault.

Compute the effective access time with a page fault rate of 0.001.

EAT = (1 − p) × memory access + p × page fault service time.

With memory access 200 ns and fault service 8 ms:
EAT = 0.999 × 200 + 0.001 × 8,000,000 = 199.8 + 8000 = ≈ 8200 ns.

That is a 40× slowdown from one fault in a thousand accesses — because a disk access is roughly 100,000 times slower than a memory access. To keep the slowdown under 10%, the fault rate must be below about 0.0000025.

The takeaway to state out loud: virtual memory only works because locality keeps p astronomically small.
Compare FIFO, LRU and Optimal page replacement.

FIFO evicts the oldest resident page. Trivial to implement with a queue, but it ignores usage — it will happily evict a hot page just because it was loaded first — and it suffers Belady's anomaly.

Optimal (OPT) evicts the page that will not be needed for the longest time in the future. It gives the provably minimum number of faults but requires knowledge of the future, so it is used only as a benchmark to judge other algorithms.

LRU evicts the page unused for the longest time, using the past as a proxy for the future. It is the best practical approximation to OPT and is immune to Belady's anomaly, but exact implementation needs a counter update or list splice on every memory reference, which is too slow — so real systems approximate it with reference bits (the clock algorithm).

On the standard reference string with 3 frames: FIFO 15 faults, LRU 12, OPT 9.

What is Belady's anomaly? Which algorithms suffer from it?

Belady's anomaly is when increasing the number of page frames increases the number of page faults — the opposite of what you'd expect.

Classic demonstration with FIFO and reference string 1,2,3,4,1,2,5,1,2,3,4,5: 3 frames give 9 faults, 4 frames give 10 faults.

FIFO and second-chance suffer from it. LRU and Optimal do not, because they are stack algorithms: the set of pages resident with n frames is always a subset of the set resident with n+1 frames, so more memory can never hurt.

What is thrashing? What causes it and how do you fix it?

Thrashing is when the system spends more time swapping pages in and out than executing instructions, so useful throughput collapses.

Cause: processes have fewer frames than their active working set, so each fault evicts a page that is needed almost immediately. It is made much worse by a feedback loop — high paging means processes block on disk, so CPU utilisation drops, so the long-term scheduler admits more processes, taking away even more frames.

Fixes: reduce the degree of multiprogramming by suspending processes; use the working set model (only admit a process if the total working-set demand D ≤ available frames m); or use page-fault frequency control, giving frames to processes whose fault rate exceeds an upper bound and reclaiming from those below a lower bound. Ultimately, add RAM or use local rather than global replacement.

What is the working set model?

The working set WS(t, Δ) is the set of distinct pages a process referenced in its most recent Δ memory references — a practical approximation of its current locality.

The OS sums the working set sizes of all processes to get total demand D. If D > m (total available frames), thrashing will occur, so a process is suspended and its frames redistributed. If D is well below m, another process can be admitted.

Choosing Δ matters: too small and it misses the locality; too large and it spans several localities and overestimates. It is approximated in practice using a timer interrupt plus reference bits.

Difference between a page fault and a segmentation fault?

A page fault is a normal, expected event: the referenced address is valid but the page is currently on disk. The OS transparently loads it and re-runs the instruction; the program never notices except as a delay.

A segmentation fault is an error: the process referenced an address that is not part of its address space at all, or violated permissions (writing to read-only memory). The OS sends SIGSEGV and the process usually dies.

Both start as an MMU trap — the difference is what the OS finds when it checks the address against the process's valid regions.

What is the dirty bit and why does it matter?

The dirty (modify) bit in a page table entry is set by hardware whenever the page is written to.

It matters at replacement time: if the victim page is clean, its copy on disk is still accurate, so the frame can simply be reused — no disk write needed. If it is dirty, it must first be written back, doubling the cost of that fault.

Replacement algorithms therefore prefer clean victims — this is exactly what the enhanced second-chance algorithm does using the (reference, dirty) pair.

How do you choose the page size? What are the trade-offs?

Larger pages: fewer page table entries (smaller tables), better TLB reach (each entry covers more memory, so fewer TLB misses), and more efficient disk transfers since seek time is amortised over more data.

Smaller pages: less internal fragmentation, and finer-grained resolution of locality — you don't waste I/O bandwidth transferring parts of a page you never touch.

The historical trend is toward larger pages because memory is cheap and TLB misses are expensive; 4 KB is the standard, with 2 MB and 1 GB "huge pages" used by databases and VMs to cut TLB pressure.

Global vs local page replacement?

Global replacement lets a faulting process take a frame from any process, including others. It generally gives better overall throughput because frames flow to whoever needs them, but a process's page-fault rate now depends on other processes' behaviour, so its performance becomes unpredictable and it can be victimised.

Local replacement restricts a process to replacing only its own frames. Performance is consistent and isolated, but a process cannot benefit from memory that other processes are not using, so utilisation is lower.

File systems

The abstraction users actually see. Allocation methods and the inode are the two things you must be able to draw.

9.1 Files and their attributes

File

A named collection of related information recorded on secondary storage — the smallest logical unit of storage from the user's perspective. It is an abstraction: the OS maps it onto physical blocks.

Attributes: name, unique identifier (inode number), type, location (pointer to blocks), size, protection bits (owner/group/others × read/write/execute), and timestamps (created, modified, accessed) plus owner IDs.

Operations: create, write, read, reposition (seek), delete, truncate, open, close. open() moves the directory entry's metadata into an in-memory open-file table, so subsequent operations avoid re-searching the directory. Each open file has a file pointer, an open count, its disk location, and access rights.

9.2 Access methods

  • Sequential access — read/write in order from the start; a pointer advances automatically. Matches tape and most real file usage (compilers, editors).
  • Direct / random access — the file is a numbered sequence of fixed-length records; you can jump to record n immediately. Essential for databases.
  • Indexed access — an index file maps a key to a block; look up the index, then go directly to the data. For very large files the index itself is indexed.

9.5 The inode

inode (index node)

The Unix data structure that stores all metadata about a file except its name: type, permissions, owner and group IDs, size, timestamps, link count, and the pointers to the data blocks. The name lives in the directory entry, which maps name → inode number.

The classic inode uses a multi-level index: typically 12 direct block pointers, then one single-indirect, one double-indirect and one triple-indirect pointer. Small files are reached in one access via the direct pointers; enormous files are still addressable through the indirect levels. It is a deliberate optimisation for the fact that most files are small.

Why the name is not in the inode

Because separating them is exactly what makes hard links possible: several directory entries, with different names and in different directories, can point to the same inode number. The inode keeps a link count and the file's data is freed only when that count reaches zero and no process has it open.

9.6 Free-space management

  • Bit vector / bitmap — one bit per block, 1 = free. Simple, and finding the first free block is a fast word-scan. The bitmap itself must be kept in memory to be efficient, which costs memory on huge volumes.
  • Linked list — each free block points to the next. No wasted space, but traversing to find n contiguous blocks requires reading each block from disk.
  • Grouping — the first free block stores the addresses of n other free blocks, so a batch of free blocks is found in one read.
  • Counting — store <first free block, count of contiguous free blocks>. Compact, because free space tends to come in runs.

9.7 Journaling and consistency

If the machine loses power midway through an update, the file system can be left inconsistent — a block marked allocated but belonging to no file, or a directory entry pointing at a freed inode. Checking the whole disk afterwards (fsck) takes hours on large volumes.

Journaling

Before performing a metadata update, the file system writes a description of the intended change to a sequential log (journal). Only after the log record is safely on disk is the real update applied; the log entry is then discarded. After a crash, the OS simply replays the journal, making recovery a matter of seconds.

Modes: writeback (metadata only), ordered (metadata journaled, data written first — the ext4 default), journal (both data and metadata journaled — safest, slowest).

Common file systems: ext4 (Linux, journaling, extents), NTFS (Windows, journaling, ACLs), FAT32/exFAT (portable, no journaling), APFS (macOS, copy-on-write, snapshots), ZFS/Btrfs (copy-on-write, checksums, snapshots).

What is a file system? What does it do?

A file system is the OS component that controls how data is stored on and retrieved from secondary storage. It provides the file and directory abstractions, maps logical files onto physical disk blocks, manages free space, enforces access permissions, and maintains metadata (size, timestamps, ownership).

Without one, a disk is just a numbered sequence of blocks with no way to know where one piece of data ends and another begins.

Compare contiguous, linked and indexed file allocation.

Contiguous: the file occupies consecutive blocks; the directory stores start block and length. Excellent sequential and random access (block i = start + i). But it suffers external fragmentation and files cannot easily grow — you must know the final size in advance. Used on CD-ROMs.

Linked: each block contains a pointer to the next; the directory stores only the first block. No external fragmentation and files grow freely, but random access is O(n) — you must walk the chain from the start — and one corrupted pointer loses the rest of the file. Pointers also consume space in each block.

Indexed: all block pointers are gathered into a dedicated index block. Gives efficient random access with no external fragmentation; the cost is an entire index block per file, wasteful for tiny files. Unix inodes use this with multiple levels of indirection.

What is an inode?

An inode is the Unix structure holding all metadata for a file except its name: file type, permissions, owner and group, size, link count, timestamps, and pointers to the data blocks.

Block pointers are organised as roughly 12 direct pointers plus single, double and triple indirect pointers — so small files (the vast majority) are reached in one access, while very large files remain addressable.

The filename lives in the directory entry, which is just a mapping of name → inode number. That separation is what makes hard links possible.

Hard link vs soft link?

A hard link is an additional directory entry pointing to the same inode. All links are equal — there is no "original". Deleting one just decrements the inode's link count; the data survives until the count hits zero. Hard links cannot cross file system boundaries and cannot point to directories (that would create cycles).

A soft/symbolic link is a small separate file whose contents are a pathname. It can cross file systems and can point to directories, but if the target is deleted or moved the link becomes dangling and breaks.

How does the OS manage free disk space?

Bit vector: one bit per block (1 = free). Simple and fast to scan for the first free block using word-level operations; requires keeping the whole bitmap in memory to be efficient.

Linked list: free blocks chained together. Wastes no extra space but is slow to traverse, since each step requires a disk read.

Grouping: the first free block holds the addresses of n other free blocks, so one read yields many free blocks.

Counting: store pairs of (first free block, run length), which is compact because free space naturally occurs in contiguous runs.

What is journaling and why is it needed?

A crash partway through a multi-step metadata update leaves the file system inconsistent — for example a block marked in-use that belongs to no file. Scanning an entire large volume to repair this (fsck) can take hours.

A journaling file system first writes the intended change to a sequential log, then applies it, then clears the log entry. After a crash the OS just replays or discards incomplete log entries, so recovery takes seconds and the file system is always returned to a consistent state.

ext4, NTFS and XFS are journaling; FAT32 is not, which is why an unclean unplug of a USB stick can corrupt it.

What happens when you open and then read a file?

open(): the OS resolves the pathname component by component, reading each directory to find the next inode number. It checks permissions, then copies the inode into the in-memory open-file table, creates a per-process entry with a file pointer starting at 0, and returns a file descriptor — an index into the process's descriptor table.

read(): the descriptor indexes to the open-file entry; the current file offset is converted to a logical block number, the inode's pointers give the physical block, the buffer cache is checked, and on a miss the block is read from disk. Data is copied to the user buffer and the file pointer advances.

The point of open() is that the expensive directory search happens once, not on every read.

What is a file descriptor?

A small non-negative integer that a process uses to refer to an open file. It is an index into the per-process file descriptor table, which points into the system-wide open-file table, which points to the inode.

By convention 0 is standard input, 1 standard output and 2 standard error — which is what makes shell redirection and piping work: the shell simply reassigns those descriptors in the child before calling exec.

What is a directory, physically?

A directory is just a file whose contents are a table of entries mapping filenames to inode numbers. It is stored in data blocks like any other file and has its own inode.

That is why directory operations are file operations — reading a directory is reading a file — and why permissions on a directory mean something slightly different: execute on a directory means "may traverse into it", while read means "may list its entries".

SSTF or LOOK are reasonable defaults; LOOK/C-LOOK are what real drivers implement. Under light load FCFS is fine since the queue is usually length 1. 10.5 Buffering, caching, spooling

  • Buffering — a memory area holding data while it is transferred, to cope with speed mismatch between producer and consumer, differing transfer sizes, and to support copy semantics.
  • Caching — keeping a copy of data in faster storage. Unlike a buffer, a cache holds a copy of something that also exists elsewhere; the buffer holds the only copy in flight.
  • Spooling — a buffer that holds output for a device that cannot accept interleaved streams. The printer is the classic example: each job is spooled to disk in full and printed one at a time.

What is DMA and why is it important?

Direct Memory Access lets a dedicated controller transfer a whole block of data directly between a device and main memory without the CPU copying each word. The CPU sets up the source, destination and byte count, then continues with other work; the controller raises a single interrupt when the whole block is done.

It matters because interrupt-driven I/O costs one interrupt per word — transferring a 4 KB block would cost thousands of interrupts and consume the CPU entirely. DMA reduces that to one. The trade-off is cycle stealing: the DMA controller competes with the CPU for memory bus cycles.

Compare polling and interrupts.

Polling has the CPU repeatedly read a device status register until it signals ready. It is simple and has low latency for very fast devices, but it wastes the CPU entirely while waiting.

Interrupts let the CPU do other work; the device signals when it is ready. Far more efficient for slow or sporadic devices, at the cost of interrupt-handling overhead (context save, handler dispatch) per event.

The crossover: polling wins when the device is faster than the interrupt overhead — which is why high-speed network drivers actually switch back to polling under heavy load (Linux NAPI).

What are the components of disk access time?

Seek time — moving the arm to the target cylinder. Largest and most variable; this is what disk scheduling minimises.

Rotational latency — waiting for the target sector to rotate under the head, on average half a revolution. At 7200 RPM one revolution is 8.33 ms, so average latency ≈ 4.17 ms.

Transfer time — the time to actually read or write the bytes, determined by rotation speed and data density.

Total = seek + rotational latency + transfer, plus queuing delay and controller overhead.

Explain SCAN, C-SCAN, LOOK and C-LOOK.

SCAN (elevator): the head sweeps from one end of the disk to the other, servicing every request it passes, then reverses. Bounded waiting, but requests just behind the head must wait nearly two full sweeps.

C-SCAN (circular SCAN): services requests in one direction only; on reaching the end it jumps straight back to the start without servicing anything on the way. This treats the disk as circular and gives much more uniform waiting time.

LOOK / C-LOOK: identical to SCAN / C-SCAN except the head reverses (or jumps back) at the last actual request rather than travelling all the way to cylinder 0 or 199. They are strictly better and are what real drivers implement.

On the standard queue (98,183,37,122,14,124,65,67 with head at 53): FCFS 640, SSTF 236, SCAN 236, C-SCAN 382, LOOK 208, C-LOOK 322 cylinders.

Why not always use SSTF, since it minimises head movement?

Two reasons. First, starvation: if requests keep arriving near the head's current position, a request at the far edge of the disk may never be serviced. Second, SSTF is greedy, not optimal — choosing the nearest request each time does not necessarily yield the globally shortest total path.

SCAN and its variants trade a little extra movement for a hard guarantee that every request is served within one sweep, which matters much more on a loaded system.

Does disk scheduling matter on an SSD?

Barely. Disk scheduling exists to minimise seek time, and an SSD has no moving parts — random and sequential access cost roughly the same. Reordering requests by "cylinder" is meaningless.

Linux therefore offers a none (noop) scheduler for NVMe devices, and modern schedulers like mq-deadline or kyber focus on fairness and latency rather than seeks. What does matter on SSDs is write amplification, wear levelling and the TRIM command telling the drive which blocks are no longer in use.

Explain RAID levels 0, 1, 5 and 10.

RAID 0 — striping across disks with no redundancy. Maximum speed and 100% capacity but zero fault tolerance: losing any disk loses all data.

RAID 1 — mirroring: every block written to two disks. Survives one disk failure per pair and reads are fast (either copy can serve), but usable capacity is only 50%.

RAID 5 — striping with parity distributed across all disks. Survives one failure, usable capacity (n−1)/n, needs at least 3 disks. Writes are slower due to the read-modify-write parity update.

RAID 10 — mirrored pairs, then striped across them. Combines RAID 1's redundancy with RAID 0's speed and has fast rebuilds, at 50% capacity. The usual choice for databases.

Always add: RAID is not a backup — it protects against hardware failure, not against deletion or corruption, which are replicated faithfully.

Difference between buffering, caching and spooling?

Buffering temporarily holds data in transit between two devices operating at different speeds or in different chunk sizes. The buffer holds the only copy currently in flight.

Caching keeps a duplicate of data in faster storage so future accesses are quicker. The authoritative copy exists elsewhere.

Spooling holds an entire output job for a device that cannot handle interleaved streams, releasing them one complete job at a time — printing is the canonical example.

11.3 Principles of protection

  • Principle of least privilege — every program and user should operate with the minimum set of privileges necessary to complete the job, for the minimum time. This is the single most important idea in the chapter.
  • Separation of privilege — require more than one condition to grant access.
  • Fail-safe defaults — deny by default; grant explicitly.
  • Defence in depth — multiple independent layers, so one failure is not total.

11.4 The access matrix

A conceptual model: rows are domains (who), columns are objects (what), and each cell lists permitted operations. Storing it as a full matrix is wasteful because it is mostly empty, so it is implemented in one of two ways:

Access Control List (ACL)

Store the matrix by column: each object carries a list of (user, rights) pairs.

+ Easy to answer "who can access this file?" and to revoke access to an object.
− Hard to answer "what can this user access?"

Unix permissions are a compressed ACL: owner/group/others × rwx.

Capability list

Store the matrix by row: each domain holds a list of objects it may access, with rights — an unforgeable ticket.

+ Easy to answer "what can this process access?"; fast checks.
− Revocation is hard — you must hunt down every copy of the capability.

Unix file permissions: rwxr-xr-- = owner rwx (7), group r-x (5), others r-- (4) = chmod 754. On a directory, x means "may traverse into", r means "may list".

11.6 Defences

  • Authentication — something you know (password), have (token, phone), or are (biometric). Multi-factor combines categories.
  • Password storage — never store plaintext. Store a salted hash using a slow KDF (bcrypt, scrypt, Argon2). The salt defeats rainbow tables; slowness defeats brute force.

  • Encryption — symmetric (one shared key, fast — AES) for bulk data; asymmetric (public/private key pair — RSA, ECC) for key exchange and digital signatures. TLS uses asymmetric crypto to agree on a symmetric key, then switches.
  • Sandboxing / isolation — chroot, containers (namespaces + cgroups), VMs, seccomp filters restricting which syscalls a process may make.
  • Auditing and logging — you cannot respond to what you cannot see.

Chapter 11 — Interview questions

Click to reveal
Difference between protection and security?

Protection controls access by processes and users already inside the system to its resources — an internal problem, solved with access matrices, ACLs, capabilities, memory protection and user/kernel mode.

Security defends the system against external threats — ensuring only legitimate entities get in at all — using authentication, encryption, firewalls and auditing.

Protection mechanisms assume security has already established who a principal is; if an attacker can impersonate a legitimate user, protection will faithfully grant them that user's rights.

What is the principle of least privilege?

Every user, process and program should be granted only the privileges strictly necessary to complete its task, and only for as long as it needs them.

It limits the blast radius of both bugs and compromises: a web server running as an unprivileged user that gets exploited cannot read /etc/shadow. Concrete applications: not running services as root, dropping privileges after binding a port, using separate service accounts, and seccomp/capability restrictions on syscalls.

Access control list vs capability list?

Both are ways of storing the sparse access matrix. An ACL stores it by column: each object carries the list of principals allowed to use it and how. A capability list stores it by row: each subject holds unforgeable tickets naming the objects it may access.

ACLs make it easy to see and revoke all access to a given object; capabilities make it easy to enumerate what a process can do and are faster to check, but revocation is hard because capabilities may have been copied. Unix permissions are a compressed ACL; file descriptors are effectively capabilities.

Virus vs worm vs trojan?

Virus — attaches itself to a host program or file and requires that host to be executed (usually by a user) in order to spread.

Worm — a standalone program that replicates and spreads across networks by itself, exploiting vulnerabilities. No host and no user action required, which is why worms spread orders of magnitude faster.

Trojan horse — does not self-replicate at all; it masquerades as legitimate software and relies purely on the user choosing to install and run it.

What is a buffer overflow attack and how do you prevent it?

A program writes more data into a fixed-size buffer than it can hold. In C, with a stack buffer, the overflow spills into adjacent stack memory and can overwrite the saved return address. When the function returns, execution jumps to an address of the attacker's choosing — typically injected shellcode.

Prevention: bounds-checked functions (strncpy over strcpy) or memory-safe languages; stack canaries — a random value placed before the return address and checked on return; ASLR, randomising segment base addresses so the attacker cannot predict where to jump; and DEP/NX, marking the stack non-executable.

How should passwords be stored?

Never in plaintext, and never with a fast general-purpose hash like MD5 or SHA-256 alone.

Store a salted hash produced by a deliberately slow key-derivation function — bcrypt, scrypt or Argon2. The salt is a unique random value per user, stored alongside the hash; it ensures two users with the same password get different hashes and defeats precomputed rainbow tables. The slowness (configurable work factor) makes brute-force guessing economically infeasible even if the database leaks.

What is the CIA triad?

The three core security goals. Confidentiality — data is disclosed only to authorised parties (protected by encryption and access control). Integrity — data is not altered without authorisation (protected by hashes, checksums, digital signatures). Availability — authorised users can access the system when needed (threatened by DoS attacks, protected by redundancy and rate limiting).

12.5 Two things Linux does that surprise people

The OOM killer

Linux overcommits memory — malloc succeeds even when the total promised exceeds RAM plus swap, because most programs never touch everything they allocate. When memory genuinely runs out, the Out-Of-Memory killer picks a victim (scored by memory footprint and an adjustable oom_score_adj) and kills it. Check dmesg when a process vanishes with no explanation.

"Free" memory looks tiny

free -h often shows almost no free memory — because Linux uses all spare RAM as page cache for files. That memory is instantly reclaimable, so the column to read is "available", not "free". Unused RAM is wasted RAM.

A process is consuming 100% CPU. How do you debug it?

1. top or htop to confirm which process and whether it's user time or system time. High system time points at syscalls or I/O; high user time points at a compute loop.

2. top -H -p <pid> to find which thread is hot.

3. strace -p <pid> — if it's spinning on syscalls you'll see them immediately; silence means it's in a pure userspace loop.

4. perf top -p <pid> or a stack sample (gdb, jstack) to find the exact function.

5. Check /proc/<pid>/status for context-switch counts — a very high voluntary switch count suggests lock contention rather than real work.

Why can't you kill a process with kill -9?

Because SIGKILL is delivered to the process only when it is scheduled, and a process in uninterruptible sleep (state D) is blocked inside the kernel waiting on I/O and will not return to a point where signals are checked. Typically it's waiting on a hung disk or an unresponsive NFS mount.

The other case is a zombie (state Z) — it is already dead, so there is nothing to kill; only the parent reaping it (or the parent dying, re-parenting it to init) removes it.

What is the difference between kill -9 and kill -15?

kill -15 sends SIGTERM, a polite request to shut down. The process can catch it, flush buffers, close files, finish in-flight requests and exit cleanly. This is the default of kill and what you should always try first.

kill -9 sends SIGKILL, which cannot be caught, blocked or ignored. The kernel destroys the process immediately, with no chance to clean up — so temp files, locks and partially-written data are left behind.

What is /proc?

A virtual (pseudo) filesystem that presents kernel and process data as files. Nothing is stored on disk — reading a file causes the kernel to generate the contents on demand.

It gives userspace a uniform, permission-checked window into the kernel: /proc/<pid>/status for process state, /proc/<pid>/maps for the virtual memory layout, /proc/<pid>/fd/ for open descriptors, /proc/meminfo and /proc/cpuinfo for system facts. Tools like ps, top and free are just readers of /proc.

The server is slow. Walk me through diagnosing whether it's CPU, memory or I/O bound.

Start with top / vmstat 1 and read three things:

CPU-bound: high us (user) time, load average near or above the core count, low wa. Drill into the hot process with perf.

Memory-bound / thrashing: si/so (swap in/out) consistently non-zero in vmstat, low available memory, rising page-fault rate. This is textbook thrashing — reduce the workload or add RAM.

I/O-bound: high wa (iowait), many processes in state D, and iostat -x showing device utilisation near 100% with high await times.

Then confirm with dmesg (OOM kills, disk errors) and strace on the specific slow process.

This is the "systems thinking" question — the structure of your answer matters more than the exact flags.
What does chmod 755 mean?

Each digit is an octal bit-field of read (4), write (2), execute (1), given for owner, group, others in that order.

755 = owner 7 (4+2+1 = rwx), group 5 (4+1 = r-x), others 5 (r-x) — i.e. rwxr-xr-x. The owner can read, write and run it; everyone else can read and run but not modify. This is the standard permission for executables and directories.

On a directory, execute means "may enter/traverse" and read means "may list contents" — so 711 lets people access a known file inside without listing the directory.

What is the OOM killer?

Linux overcommits: it allows the sum of all allocations to exceed RAM plus swap, because programs typically reserve far more memory than they touch. When physical memory is genuinely exhausted and nothing can be reclaimed, the kernel invokes the Out-Of-Memory killer, which scores each process (mainly by memory footprint, adjusted by oom_score_adj) and kills the highest scorer to free memory.

Symptom: a process disappears with no error in its own logs — the evidence is in dmesg. It is a last-resort mechanism, not something to rely on.

13.4 Rapid-fire round

Answer each in one or two sentences before expanding.

Can a process run without a thread?

No. A process always has at least one thread of execution — the main thread. The process is the container for resources; the thread is what actually executes. A process with zero threads has nothing running and would be terminated.

What is the degree of multiprogramming?

The number of processes held in main memory at once. The long-term scheduler controls it by admitting processes; the medium-term scheduler reduces it by swapping processes out. Too low wastes the CPU; too high causes thrashing.

Is a mode switch a context switch?

No. A mode switch only changes the CPU privilege level (user ↔ kernel) while the same process continues. A context switch replaces the running process entirely, saving and restoring PCBs. Every context switch involves mode switches, but not vice versa — and a mode switch is far cheaper.

Why is the page size a power of two?

So that splitting a logical address into page number and offset requires no arithmetic — the hardware just takes the low n bits as the offset and the rest as the page number. Division and modulo would otherwise be needed on every memory reference.

What happens if the TLB hit ratio is 100%?

Every translation is served from the TLB, so EAT = TLB access + memory access. There is still overhead — the TLB lookup itself — but no second memory access for the page table. In practice hit ratios of 98–99% are typical, which is why paging is viable at all.

Which is faster: reading 1 MB sequentially from disk or from memory?

Memory, by roughly 4–5 orders of magnitude for the access itself. A memory access is ~100 ns; a disk seek is ~10 ms — about 100,000× slower. Even ignoring the seek, disk streaming bandwidth is far below memory bandwidth. This gap is the entire reason caches, buffer pools and virtual memory exist.

Can two processes share the same physical memory page?

Yes — their page tables simply map different virtual page numbers to the same frame number. This is how shared memory IPC, shared libraries and copy-on-write after fork() all work.

What is a reentrant kernel?

A kernel that can have several processes executing kernel code simultaneously (on different CPUs) or interleaved. It requires kernel data structures to be protected with locks. All modern SMP kernels are reentrant; the alternative — a "big kernel lock" — serialises everything and does not scale.

Why doesn't the OS just give every process all the memory it asks for?

Because physical memory is finite and shared. It uses virtual memory to give each process the illusion of a large private space, backing only the actively used pages with real frames. Linux additionally overcommits — allowing more total allocation than exists — because programs reserve far more than they touch, with the OOM killer as the backstop.

What is the difference between a trap and an interrupt, one more time?

A trap is synchronous and generated by software (a system call or an error) — it is caused by the currently executing instruction. An interrupt is asynchronous and generated by hardware, unrelated to what the CPU happens to be executing.

If a system has 4 GB RAM, can a process use 8 GB of memory?

Yes, on a 64-bit system with sufficient swap space. Virtual memory means the process's address space is limited by the architecture and swap, not by RAM. Only the actively used pages need to be resident. Performance depends entirely on whether the working set fits in RAM — if it doesn't, the system thrashes.

Why do we need both a long-term and a short-term scheduler?

They solve different problems at different timescales. The long-term scheduler decides how many processes are in memory (degree of multiprogramming) and runs rarely, so it can afford to be clever about job mix. The short-term scheduler decides which ready process runs next and executes every few milliseconds, so it must be extremely fast.

What is a virtual machine, and how is it different from a container?

A virtual machine virtualises the hardware: a hypervisor presents virtual CPU, memory and devices, and each VM runs its own complete guest kernel. Strong isolation, heavier — gigabytes and seconds to boot.

A container virtualises the operating system: processes share the host kernel but get isolated views via namespaces (PID, network, mount, user) and resource limits via cgroups. Much lighter — megabytes and milliseconds — but isolation is weaker because a kernel vulnerability is shared.

What is the difference between cooperative and preemptive multitasking?

Under cooperative multitasking, a process keeps the CPU until it voluntarily yields — so one buggy program that never yields freezes the entire machine (classic Mac OS, Windows 3.x). Under preemptive multitasking, a timer interrupt lets the OS take the CPU back regardless, so a single misbehaving process cannot hang the system. All modern OSes are preemptive.

What is cache coherence and why is it an OS/hardware concern?

On a multiprocessor each core has private caches, so the same memory location can be cached in several places. Cache coherence protocols (MESI and relatives) ensure that a write by one core is made visible to the others, so no core reads a stale value.

It matters to the OS because coherence traffic is a real performance cost — two threads writing to adjacent variables in the same cache line ("false sharing") can be slower than a single thread — and because it underpins the correctness of every lock and atomic operation.
