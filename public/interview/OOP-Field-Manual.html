§01

Programming paradigms and why OOP exists

OOP is not "the good way to program". It is one answer to one specific problem: how do you stop a large program from becoming impossible to change?

The paradigms you should be able to name

The problem procedural code hits

In procedural code, data structures and the functions that operate on them are separate. Any function may touch any field. Fine for 500 lines, fatal at 50,000:

  • No enforced invariants. If a BankAccount must never go negative, nothing stops any of 200 functions writing acc.balance = -5.
  • Change ripples. Rename or retype a field and every function touching it breaks.
  • No natural extension point. Adding a new "kind" of thing means editing every switch in the codebase.
C · procedural
/* Data and behaviour are separate. Nothing protects the invariant. */
struct Account { int id; double balance; };

void withdraw(struct Account *a, double amt) {
    a->balance -= amt;              /* no check anywhere */
}

int main(void) {
    struct Account a = {1, 100.0};
    a.balance = -9999;              /* legal. The struct cannot defend itself. */
    return 0;
}
Java · object-oriented
public class Account {
    private final int id;
    private double balance;                 // only this class can touch it

    public Account(int id, double opening) {
        if (opening < 0) throw new IllegalArgumentException("negative opening");
        this.id = id;
        this.balance = opening;
    }

    public void withdraw(double amt) {      // the ONLY legal way to reduce it
        if (amt <= 0)      throw new IllegalArgumentException("amount must be > 0");
        if (amt > balance) throw new IllegalStateException("insufficient funds");
        balance -= amt;
    }

    public double getBalance() { return balance; }
}
// balance < 0 is now UNREPRESENTABLE, not merely discouraged.

What OOP actually buys you

  • Invariant enforcement — the class is the only code that can break itself, so bugs stay local.
  • Modularity — change internals freely as long as the public contract holds.
  • Extension without editing — add a subclass instead of a case in every switch (Open/Closed, §16).
  • Reuse — via composition and inheritance.
  • Shared vocabulary — Order, Invoice, Customer map to domain nouns, so code reads like the problem.
Honest counterpoint — say this and you sound senior

OOP costs indirection. Deep hierarchies make it hard to answer "what actually runs when I call this?" Functional and data-oriented styles push back for exactly that reason, and real codebases mix paradigms. The right framing: OOP is a tool for managing change in stateful domain models, not a universal good.

Interview Q&A · §01

very commonWhat is object-oriented programming, in one paragraph?

OOP structures a program as a collection of objects — self-contained units bundling state with the operations permitted on that state. Instead of functions reaching into shared data, each object owns its data and exposes a contract. The four pillars support that: encapsulation protects invariants, abstraction hides implementation, inheritance shares behaviour, polymorphism lets one call site work with many concrete types. The payoff is that large systems stay changeable.

Difference between procedural programming and OOP?

Is Java a pure object-oriented language? Is C++? Is Python?

No mainstream language is fully pure. Purity would require that everything is an object, no primitives, no free functions, all interaction by message passing.

  • Java — not pure: 8 primitive types (int, char, …) are not objects, and static members are not tied to instances.
  • C++ — definitely not: multi-paradigm, fully supports free functions and C-style procedural code.
  • Python — closest of the three: everything is an object, including classes, functions and integers. Still multi-paradigm because module-level functions are idiomatic.
  • Smalltalk / Ruby — usually cited as (near-)pure OO.
Where does OOP hurt?
  • Performance-critical code — virtual dispatch blocks inlining, and object graphs scattered on the heap wreck cache locality. Data-oriented design (struct-of-arrays) wins in game engines and DSP loops.
  • Small scripts — wrapping 40 lines in three classes is ceremony.
  • Concurrency — shared mutable state is the enemy; immutable/functional styles are safer.
  • Over-abstraction — deep hierarchies obscure control flow.
Name the four pillars, one line each.
  • Encapsulation — bind state to the methods allowed to modify it, so the class enforces its own invariants.
  • Abstraction — expose what an object does, hide how.
  • Inheritance — derive a new type from an existing one to reuse and specialise (IS-A).
  • Polymorphism — one interface, many implementations; the concrete method is chosen by the actual object type.

Some texts add a fifth, message passing. Noting that abstraction and encapsulation are commonly confused (§04) earns credit.

§02

Classes and objects

A class is a type. An object is a value of that type sitting in memory. Being able to say where it sits is what makes this answer good.

Anatomy of a class

Java
public class Rectangle {                    // 1. class declaration
    private double width, height;           // 2. instance fields  (state)
    private static int count = 0;           // 3. static field     (per class)

    public Rectangle(double w, double h) {  // 4. constructor
        this.width = w; this.height = h;
        count++;
    }

    public double area() {                  // 5. instance method  (behaviour)
        return width * height;
    }

    public static int getCount() {          // 6. static method
        return count;                       //    cannot touch width/height
    }

    @Override public String toString() {    // 7. overridden Object method
        return "Rectangle(" + width + "x" + height + ")";
    }
}
C++
class Rectangle {
private:
    double width, height;
    static int count;                       // declaration only
public:
    Rectangle(double w, double h) : width(w), height(h) { ++count; }  // init list
    ~Rectangle() { --count; }               // destructor — no Java equivalent
    double area() const { return width * height; }   // const = does not mutate
    static int getCount() { return count; }
};
int Rectangle::count = 0;                   // definition, outside the class
Python
class Rectangle:
    count = 0                               # class attribute

    def __init__(self, w, h):               # initialiser
        self.width = w                      # instance attributes created here
        self.height = h
        Rectangle.count += 1

    def area(self):                         # self is explicit in Python
        return self.width * self.height

    @staticmethod
    def get_count():
        return Rectangle.count

    def __repr__(self):
        return f"Rectangle({self.width}x{self.height})"

Where objects live: stack vs heap

The single most useful mental model to have ready — half the trick questions in §19 depend on it.

Java · memory layout
Rectangle r = new Rectangle(3, 4);

   STACK (per thread)                HEAP (shared, GC-managed)
   +--------------+                  +------------------------+
   | r  ----------+----------------->| Rectangle object       |
   +--------------+   reference      |  width  = 3.0          |
                                     |  height = 4.0          |
   The local variable holds a        |  header / class ptr ---+--> class metadata
   REFERENCE, never the object.      +------------------------+
  • Java — all objects on the heap; variables hold references. Primitives live on the stack or inline inside an object.
  • C++ — you choose. Rectangle r(3,4); puts the object on the stack, destroyed automatically at scope exit. Rectangle* p = new Rectangle(3,4); puts it on the heap and you must delete it.
  • Python — everything is a heap object; names are references; reference counting plus a cycle collector.
Classic trap

"Java is pass-by-reference." False. Java is strictly pass-by-value — but for object types the value copied is the reference. So you can mutate the pointed-to object inside a method, while reassigning the parameter does nothing to the caller. Worked example in §19.

Object lifecycle

  1. Allocation — memory reserved (heap in Java/Python; stack or heap in C++).
  2. Initialisation — fields defaulted, then instance initialisers, then constructor body (exact order in §08).
  3. Use — methods invoked, state mutates.
  4. Unreachable — no live reference remains.
  5. Destruction — C++: destructor runs deterministically at scope exit or delete. Java: GC reclaims later, at an unspecified time; no destructors. Python: refcount hits zero → __del__, usually promptly.

Interview Q&A · §02

very commonDifference between a class and an object?

A class is a blueprint / user-defined type: compile-time, declares what state and behaviour instances will have, costs no per-instance memory. An object is a runtime instance with its own copy of the instance fields and its own identity. One class, many objects.

Better analogy than "blueprint and house": a class is the design of an IC; objects are the physical chips fabricated from it.

Can a class exist without objects? Can an object exist without a class?

Yes to the first — utility classes like java.lang.Math are never instantiated (private constructor, all static members), and abstract classes/interfaces can't be instantiated directly at all.

No to the second in class-based languages: every object has a type. In prototype-based languages (JavaScript before ES6 classes) objects derive from other objects rather than classes, so there objects genuinely exist without classes. Mentioning that nuance is a plus.

How much memory does an object take?

A class itself costs only metadata plus its static fields (Java: Metaspace since JDK 8, PermGen before). Each object costs: header + fields + padding to an 8-byte boundary. In 64-bit HotSpot with compressed oops the header is typically 12 bytes (mark word + class pointer).

So a Java object with one int ≈ 12 + 4 = 16 bytes. With one long: 12 + 8 = 20 → padded to 24.

In C++ there is no header unless the class has virtual functions, which add a vptr (8 bytes on 64-bit). sizeof an empty C++ class is 1, not 0, so distinct objects get distinct addresses.

What is this? Can it be null?

An implicit reference to the object the instance method was invoked on. Uses: disambiguating a field from a same-named parameter, constructor chaining (this(...)), passing the current object elsewhere, and returning this for fluent/builder chaining.

In Java it can never be null — a null receiver throws NullPointerException before the method is entered. It doesn't exist in a static context. In C++ this is a pointer, and calling a member function through a null pointer is undefined behaviour (it may appear to "work" for non-virtual functions that touch no members — never rely on it).

Stack vs heap — and why does it matter for OOP?
StackHeap
AllocationPointer bump; very fastAllocator work; slower

It explains object lifetime, why C++ has destructors and Java doesn't, why shallow copy is a real bug source, and the difference between StackOverflowError (deep recursion) and OutOfMemoryError (heap exhausted).

What is escape analysis?

A JIT optimisation: if the JVM proves an object never escapes the method that created it (never stored in a field, returned, or passed to unknown code) it can stack-allocate it, or eliminate it entirely by scalar replacement — splitting it into plain locals. So "all Java objects live on the heap" is true at the language level but not always at the machine level.

§03

Encapsulation and access control

Encapsulation is not "make fields private and add getters". That's the mechanism. The purpose is that a class becomes the sole guardian of its own correctness.

Definition worth memorising

Encapsulation is the bundling of data with the methods that operate on that data, together with restriction of direct access to the data, so that the class can guarantee its invariants at all times.

Two halves, and interviewers want both:

  • Bundling — state and the behaviour over that state live in one unit.
  • Information hiding — the representation is not part of the public contract, so it can change freely.

The protected subtlety they love

A subclass in a different package can access a protected member only through a reference of its own type (or a subtype) — not through a reference of the parent type. parentRef.protectedField fails to compile from another package; this.protectedField compiles.

C++ and Python differences

  • C++ has private, protected, public — but no package concept. It adds friend, which grants another class or function full access, deliberately breaking encapsulation where needed (e.g. operator<<). Default access is private for class, public for struct — that single sentence is the entire class-vs-struct answer.
  • Python has no enforcement. Convention only: _name means "internal, don't touch", and __name triggers name mangling to _ClassName__name, which prevents accidental collision in subclasses but does not prevent access.
Python · name mangling
class A:
    def __init__(self):
        self._soft   = 1     # convention: private-ish
        self.__hard  = 2     # mangled to _A__hard

a = A()
print(a._soft)               # 1  — works, just impolite
# print(a.__hard)            # AttributeError
print(a._A__hard)            # 2  — mangling is not security

Encapsulation done properly

Java · a class that defends itself
public final class TemperatureSensor {
    private static final double MIN = -273.15;   // absolute zero
    private double celsius;
    private final List<Double> history = new ArrayList<>();

    public TemperatureSensor(double initial) { set(initial); }

    public void set(double c) {
        if (c < MIN) throw new IllegalArgumentException("below absolute zero: " + c);
        this.celsius = c;
        history.add(c);
    }

    public double getCelsius()    { return celsius; }
    public double getFahrenheit() { return celsius * 9 / 5 + 32; }   // derived, not stored

    // Defensive copy: returning `history` directly would let callers mutate our state
    public List<Double> getHistory() { return List.copyOf(history); }
}

Three things this demonstrates that a plain getter/setter example does not: an enforced invariant, a derived value that isn't a field at all (so the representation is genuinely hidden), and a defensive copy that stops a caller from mutating internal state through a leaked reference.

The getter/setter trap

If every private field has a public getter and a public setter that does nothing but assign, you have not encapsulated anything — you have written a struct with more typing. Real encapsulation means some fields have no setter, some have validation, and some are not exposed at all.

Interview Q&A · §03

very commonWhat is encapsulation and how is it achieved in Java?

Encapsulation binds data with the methods permitted to operate on it and hides the internal representation behind a public contract, so the class alone is responsible for keeping its state valid.

Achieved by: declaring fields private; exposing controlled access through methods that validate; omitting setters for fields that shouldn't change; returning defensive copies of mutable internals; and marking a class final if subclasses could break the invariants.

Benefit line: it localises change and localises bugs — if balance is wrong, only Account could have done it.

One-liner: abstraction hides complexity; encapsulation hides data. They usually appear together: an interface abstracts, and the implementing class encapsulates.

Can a class be private in Java?

A top-level class may only be public or package-private (no modifier) — private and protected are illegal there, because there is no enclosing scope for them to mean anything. A nested class can be private, protected, package-private or public, since it has an enclosing class.

Why are getters and setters preferred over public fields when the setter just assigns?
  • Future-proofing the ABI/API — you can later add validation, logging, lazy loading or a change notification without touching a single caller.
  • Read-only or write-only properties become expressible.
  • Representation independence — getFahrenheit() need not correspond to a stored field.
  • Framework contract — JavaBeans, JPA, Jackson and most reflection-based frameworks rely on accessor naming.

Honest caveat worth adding: for a genuinely dumb data carrier, modern Java prefers a record, and C++ prefers a plain struct. Boilerplate accessors on a value type are noise.

What is a defensive copy and when do you need one?

Returning (or storing) a copy of a mutable object rather than the reference itself. Needed whenever a getter would otherwise hand out a live reference to internal mutable state — arrays, collections, Date, or any mutable custom object. Without it a caller can mutate your object's internals behind its back and break the invariants the class was written to protect. The same applies on the way in: copy mutable constructor arguments before storing them.

Difference between class and struct in C++?

Exactly one difference in the language: default member access and default inheritance access — private for class, public for struct. Everything else (constructors, methods, inheritance, virtual functions, templates) is identical. By convention struct is used for passive aggregates with public data, class for types with invariants and behaviour. In C, a struct cannot have member functions at all.

Is Python's encapsulation real?

No — it is convention-based. A single underscore is a hint; a double underscore triggers name mangling to _Class__attr, which mainly prevents accidental overriding in subclasses, not deliberate access. Python's design stance is "we're all consenting adults here": the language provides signals rather than enforcement. You can add real enforcement with @property for validated access, and __slots__ to prevent arbitrary new attributes.

§04

Abstraction

Abstraction is deciding what to show. Everything else about it follows from that one sentence.

What it means

Abstraction is the process of exposing only the essential characteristics of an entity while suppressing the details that are irrelevant to the user of that entity. In code, it means a caller depends on a contract — a set of operations and their meanings — rather than on any particular implementation.

Everyday example that beats "car and steering wheel": a List. You call add() and get(i). Whether that's an ArrayList (contiguous array, O(1) random access) or a LinkedList (nodes, O(n) random access) is hidden. The abstraction is what lets you swap one for the other without editing your code — and it is also why you must understand the implementations anyway, because the complexity differs.

Two levels of abstraction

  • Data abstraction — hiding representation. You use a Stack; you don't know if it's array-backed or list-backed.
  • Control / process abstraction — hiding a sequence of steps behind a single named operation. connection.commit() hides flush, fsync, log write, lock release.

Adding a new payment method means writing one new class. No existing file changes. That is the Open/Closed principle (§16) and it is the concrete business value of abstraction — say it in exactly those terms.

Interview Q&A · §04

very commonWhat is abstraction? Give a real code example, not a car analogy.

Abstraction exposes only the essential operations of an entity and hides the implementation behind them, so callers program against a contract. Example: java.util.List declares add, get, size; ArrayList and LinkedList implement them completely differently. Code written against List works with either, so the implementation can be swapped without changing callers.

Achieved through abstract classes and interfaces in Java, pure virtual functions in C++, and ABCs or protocols in Python.

Can you achieve 100% abstraction? How?

Yes — with an interface in which every method is abstract. Before Java 8 that was automatic. From Java 8 an interface may also contain default and static methods with bodies, so an interface no longer guarantees 100% abstraction. In C++, an abstract class whose members are all pure virtual (and which has no data members) is the equivalent.

Why can't you instantiate an abstract class? Then why can it have a constructor?

You can't instantiate it because it is incomplete — at least one method has no body, so there would be no valid implementation to dispatch to.

It still needs a constructor because the abstract class contributes fields to every concrete subclass object, and those fields must be initialised. The subclass constructor implicitly calls super(), which runs the abstract class's constructor as part of building the single object. So the constructor is used during subclass construction — it just can't be invoked via new AbstractThing().

Abstraction vs encapsulation, one more time — with a code example.

In the payment example: the PaymentMethod interface is abstraction — it decides what the outside world sees. Inside CardPayment, the fields cardToken and retryCount being private, and the class validating amounts before charging, is encapsulation — it protects the internals it chose not to expose. Abstraction is the decision; encapsulation is the enforcement.

What is a leaky abstraction?

An abstraction whose hidden implementation details still force themselves on the user. Classic examples: List.get(i) is O(1) on ArrayList and O(n) on LinkedList, so performance leaks through the interface; an ORM hides SQL until you hit an N+1 query problem; network file systems hide remoteness until latency or partition makes it obvious. The point to make: abstractions reduce cognitive load, they do not eliminate the need to know what's underneath.

§05

Inheritance

Inheritance is a type relationship, not a code-reuse trick. Interviewers probe exactly that distinction.

Definition and terminology

Inheritance lets a class (derived / child / subclass) acquire the members of another class (base / parent / superclass) and then extend or specialise them. It establishes an IS-A relationship: a Car IS-A Vehicle, so a Car may be used anywhere a Vehicle is expected.

Java
class Vehicle {
    protected String reg;
    protected int wheels;

    Vehicle(String reg, int wheels) { this.reg = reg; this.wheels = wheels; }
    void start() { System.out.println(reg + " starting"); }
    String describe() { return wheels + "-wheeler " + reg; }
}

class Car extends Vehicle {
    private int seats;

    Car(String reg, int seats) {
        super(reg, 4);            // MUST be the first statement
        this.seats = seats;
    }

    @Override String describe() {                       // specialise
        return super.describe() + " with " + seats + " seats";
    }

    void openBoot() { System.out.println("boot open"); } // extend
}

The diamond problem

Diagram
        Device                 Device has field id and method info()
        /     \
   Sensor     Actuator         both inherit id, both may override info()
        \     /
      SmartValve                which id? whose info()?  ← ambiguity

What goes wrong: without special handling, SmartValve contains two copies of Device's state, and a call to info() is ambiguous.

  • C++ solution — virtual inheritance. Declare class Sensor : virtual public Device and class Actuator : virtual public Device. Then SmartValve holds exactly one shared Device sub-object. The most-derived class becomes responsible for calling Device's constructor. Ambiguous function calls must still be resolved explicitly with Sensor::info().
  • Java solution — forbid it. A class extends exactly one class, so state can never be duplicated. Multiple interfaces are allowed, because before Java 8 interfaces had no state and no bodies. Since Java 8, if two interfaces provide conflicting default methods, the compiler forces the implementing class to override and disambiguate with InterfaceName.super.method().
  • Python solution — the MRO. Python allows multiple inheritance and linearises the hierarchy using the C3 linearisation algorithm. ClassName.__mro__ shows the exact search order, and super() follows it cooperatively.

The IS-A test

Before writing extends, ask: can every instance of the child be substituted wherever the parent is expected, without surprising the caller? That's the Liskov Substitution Principle (§16). Interview Q&A · §05

very commonWhy doesn't Java support multiple inheritance of classes?

To avoid the diamond problem and the complexity it brings. If C extended both A and B, and both inherited state and behaviour from a common ancestor, then C would contain duplicated state and ambiguous method resolution, and constructor ordering would become ill-defined. C++ solves this with virtual inheritance, but at real cost in complexity and object layout.

Java's designers chose simplicity: single inheritance of state, multiple inheritance of type via interfaces. Since Java 8 interfaces can carry behaviour through default methods, so Java now has multiple inheritance of behaviour too — and it handles conflicts by refusing to compile until you disambiguate with A.super.m(). It still has no multiple inheritance of state, which is the part that causes the real trouble.

What is the diamond problem? How does each language handle it?

When class D inherits from B and C which both inherit from A, D may end up with two copies of A's members and an ambiguous path for calls inherited from A.

  • C++ — allowed; fixed with virtual inheritance so only one A sub-object exists. The most-derived class then constructs A directly.
  • Java — prevented for classes; for conflicting interface default methods the compiler forces an explicit override.
  • Python — allowed; resolved deterministically by the C3 MRO, so A appears exactly once in the linearisation.
Is inheritance always the right way to reuse code?

No — the default advice is favour composition over inheritance. Inheritance is the strongest coupling available: the subclass depends on the superclass's implementation, not just its interface, so a change in the parent can silently break children (the fragile base class problem). Use inheritance only when there's a genuine IS-A relationship that satisfies Liskov substitution. Otherwise hold an instance of the other class as a field and delegate. Details and code in §09.

Does the subclass object contain the private fields of the superclass?

Yes — physically present, but not accessible by name. There is exactly one object in memory, and it contains the layout of the entire chain, including the parent's private fields. They occupy space and are used by inherited public/protected methods of the parent; the subclass simply cannot refer to them directly. Saying "they're not inherited" is the common shorthand; saying "they exist in the object but are inaccessible" is the correct answer.

Constructor call order in an inheritance chain?

Top-down for constructors: the most-base constructor completes first. In Java, if you don't write super(...) explicitly, the compiler inserts an implicit no-arg super(), and it must be the first statement. Full ordering for new Child():

  1. Static blocks/fields of Parent, then Child — once ever, at class loading.
  2. Parent instance initialisers and field initialisers → Parent constructor body.
  3. Child instance initialisers and field initialisers → Child constructor body.

Destruction in C++ is the exact reverse: derived destructor first, then base.

Can you inherit from a final class? Why does String exist as final?

No — final on a class forbids subclassing (the C++11 equivalent is class X final). String is final for security and correctness: a mutable or overridable String subclass could be passed to a file-open or class-loading API, be validated, then change — a time-of-check/time-of-use attack. Finality also enables string pooling and caching of the hash code, and lets the JIT assume no override exists.

What is the fragile base class problem?

Where seemingly safe changes to a base class break derived classes, because subclasses depend on the base's implementation details, not just its contract. Classic case: a base Collection.addAll() that internally calls add() in a loop. A subclass that overrides both to count elements double-counts. Fix the base to stop calling add() internally, and subclasses break the other way. Mitigations: document self-use, mark methods final, or prefer composition.

What does super do, and can you use it in a static method?

Two uses: super(...) invokes a superclass constructor (first statement of a constructor only), and super.method() calls the superclass version of an overridden method, bypassing dynamic dispatch. Also super.field to access a shadowed field.

It cannot be used in a static context — super and this both require an instance. Also, this(...) and super(...) can't both appear in the same constructor, since both must be the first statement.

Compile-time polymorphism: overloading

Two or more methods in the same scope share a name but differ in parameter list. The compiler picks one from the static types of the arguments.

Java · overloading rules
class Printer {
    void print(int x)            { System.out.println("int"); }
    void print(long x)           { System.out.println("long"); }
    void print(Integer x)        { System.out.println("Integer"); }
    void print(int... x)         { System.out.println("varargs"); }
    void print(double x)         { System.out.println("double"); }
}

new Printer().print(5);      // "int"      — exact match wins
// If print(int) is removed  → "long"      — widening beats boxing
// If print(long) also gone  → "double"    — still widening
// If all primitives gone    → "Integer"   — boxing beats varargs
// If Integer gone too       → "varargs"   — varargs is the last resort

Resolution order the compiler uses: (1) exact match / widening primitive conversion, (2) autoboxing/unboxing, (3) varargs. Overloading is never resolved on return type alone — that would be ambiguous at a call site whose result is discarded.

The overloading trap they set

void f(Object o) and void f(String s); call f(null). Answer: f(String) — null matches both, and the compiler chooses the most specific applicable type. Add a third overload f(Integer) and the same call becomes a compile error: String and Integer are unrelated, so no most-specific type exists (ambiguous).

Run-time polymorphism: overriding

A subclass provides a new implementation of an inherited instance method with the same signature. The method invoked is chosen by the actual object type at run time, not the reference type.

Java
class Shape       { double area() { return 0; }  String name() { return "Shape"; } }
class Circle extends Shape {
    double r;
    Circle(double r) { this.r = r; }
    @Override double area() { return Math.PI * r * r; }
    @Override String name() { return "Circle"; }
}
class Square extends Shape {
    double s;
    Square(double s) { this.s = s; }
    @Override double area() { return s * s; }
    @Override String name() { return "Square"; }
}

Shape[] shapes = { new Circle(1), new Square(2) };   // reference type = Shape
for (Shape sh : shapes)
    System.out.printf("%s %.2f%n", sh.name(), sh.area());
// Circle 3.14 / Square 4.00 — dispatch on the runtime type

Rules for a valid override (Java)

  • Same name and same parameter list. Different parameters = overloading, not overriding.
  • Return type must be the same or a covariant (narrower) type.
  • Access may not be reduced. protected → public is fine; public → protected is a compile error.
  • Checked exceptions may be narrowed or dropped, never broadened. Unchecked exceptions are unrestricted.
  • final, static and private methods cannot be overridden. Constructors cannot be overridden.
  • Use @Override — it turns a silent typo into a compile error.
Hiding vs overriding — asked constantly

static methods are hidden, not overridden. A static method call is bound to the reference type at compile time. Same for fields — fields are never polymorphic; they are shadowed and resolved statically.

Java
class P { static String who(){return "P";}  String id = "P-field"; }
class C extends P { static String who(){return "C";}  String id = "C-field"; }

P ref = new C();
System.out.println(ref.who());   // "P"       ← static: reference type
System.out.println(ref.id);      // "P-field" ← field: reference type
// Only instance METHODS are dynamically dispatched.

How dynamic dispatch actually works: the vtable

Being able to explain this mechanically is what separates a memorised answer from an understood one.

C++ · object layout with virtual functions
class Shape  { public: virtual double area(); virtual ~Shape(); };
class Circle : public Shape { double r; public: double area() override; };

  Circle object                    Circle's vtable (one per CLASS)
  +----------------+               +-------------------------+
  | vptr  ---------+-------------->| [0] &Circle::area       |
  +----------------+               | [1] &Circle::~Circle    |
  | double r       |               +-------------------------+
  +----------------+

Call:  shape_ptr->area();
Becomes roughly:  (*(shape_ptr->vptr[0]))(shape_ptr);
  → one pointer load + one indexed load + one indirect call.
  • Each class with virtual functions gets one vtable; each object gets one vptr (hence sizeof grows by 8 bytes on 64-bit).
  • The vptr is set by the constructor — which is exactly why calling a virtual function from a base constructor does not dispatch to the derived override (see the trap below).
  • In C++ dispatch is virtual only if the function is declared virtual. In Java all instance methods are virtual by default, unless final, static or private. The JVM uses a vtable-like table plus aggressive JIT optimisations — inline caching and, when only one implementation has been loaded, full inlining with a guard.
Virtual call inside a constructor

C++: during the base constructor the object is still "a Base" — the vptr points at Base's vtable — so a virtual call resolves to the base version. If it's pure virtual, you get undefined behaviour.
Java: the opposite and arguably worse — dispatch does reach the subclass override, but it runs before the subclass's fields are initialised, so it sees 0/null. Rule for both languages: never call an overridable method from a constructor.

Java · the classic bug
class Base { Base() { init(); }  void init() {} }
class Derived extends Base {
    private int x = 5;
    @Override void init() { System.out.println("x = " + x); }
}
new Derived();   // prints "x = 0"  — not 5. Field initialisers run AFTER super().

Covariant return types

Java
class Animal { Animal reproduce() { return new Animal(); } }
class Dog extends Animal {
    @Override Dog reproduce() { return new Dog(); }   // legal since Java 5
}
Dog puppy = new Dog().reproduce();   // no cast needed — that's the payoff

Upcasting and downcasting

Java
Shape  s = new Circle(2);              // UPCAST — implicit, always safe
double a = s.area();                   // dispatches to Circle.area()
// s.getRadius();                      // compile error: not in Shape's contract

Circle c = (Circle) s;                 // DOWNCAST — explicit, checked at runtime
Square q = (Square) s;                 // compiles, throws ClassCastException

    System.out.println(c2.r);

C++ equivalent: dynamic_cast<Circle*>(p) returns nullptr on failure (and throws std::bad_cast for references); static_cast does no runtime check and is undefined behaviour if wrong.

Can you override a static method? What happens if you try?

No. Declaring a static method in a subclass with the same signature hides the parent's — this is method hiding. Calls bind at compile time to the reference type, so P ref = new C(); ref.who(); calls P.who(). Static methods belong to the class, and overriding is defined for instances, so there is nothing to dispatch on.

Extra rules: a static method cannot hide an instance method and vice versa — that's a compile error, not hiding.

Can you override a private method? A final method? A constructor?

Private: no. It isn't visible to the subclass, so a same-named method in the child is an entirely new, unrelated method — it does not override, and marking it @Override is a compile error.
Final: no, by definition — that's what final means on a method.
Constructor: no; constructors aren't inherited and aren't polymorphic. You can, however, overload constructors.

very commonWhy must a base class destructor be virtual in C++?

Because deleting a derived object through a base pointer with a non-virtual destructor is undefined behaviour — in practice only the base destructor runs, so the derived class's members are never destroyed and its resources leak.

C++
struct Base { ~Base() { }              };   // NOT virtual — bug
struct Derived : Base { std::string big; ~Derived() { } };

Base* p = new Derived();
delete p;      // only ~Base() runs → Derived::big never destroyed → leak

Rule: if a class is meant to be a polymorphic base, give it a virtual destructor (or a protected non-virtual one to forbid base-pointer deletion). Java doesn't have this issue because the GC tracks actual object types.

What is dynamic method dispatch / late binding? Explain the mechanism.

The process of selecting which overridden implementation to execute at run time based on the actual object type. Mechanically: each polymorphic class has a virtual method table (vtable) mapping method slots to function addresses; every object carries a hidden pointer (vptr) to its class's vtable, installed by the constructor. A virtual call compiles to "load vptr, index the fixed slot for that method, call through the pointer" — so the cost is roughly two loads and one indirect call, plus a lost inlining opportunity.

Java makes every instance method virtual by default; the JIT counteracts the cost with inline caches, and devirtualises entirely when only one implementation is loaded (guarded by a deoptimisation check).

Runtime polymorphism with data members — does it work?

No. Fields are not polymorphic in Java or C++. A field access is resolved at compile time from the reference type. If both parent and child declare int x, the object contains two separate x fields, and ((Parent)obj).x and ((Child)obj).x read different storage. This is field shadowing/hiding and it is a code smell — avoid same-named fields across a hierarchy.

What is the difference between final, finally and finalize()?
  • final — a modifier. On a variable: assign once. On a method: cannot be overridden. On a class: cannot be subclassed.
  • finally — a block after try/catch that runs whether or not an exception was thrown; used for cleanup. Skipped only on System.exit(), JVM crash, or infinite loop/thread kill in the try.
  • finalize() — a legacy Object method the GC could call before reclaiming an object. Unpredictable, could resurrect objects, hurt GC performance. Deprecated since Java 9 and removed in later versions; use try-with-resources and AutoCloseable, or java.lang.ref.Cleaner.
Can we achieve runtime polymorphism through overloading?

No. Overload resolution is entirely a compile-time decision made from the static types of the arguments. Even if you pass an object whose runtime type is a subclass, the overload chosen is the one matching the declared type.

Java
void f(Animal a) { System.out.println("Animal"); }
void f(Dog d)    { System.out.println("Dog"); }

Animal a = new Dog();
f(a);              // prints "Animal" — chosen from the STATIC type
// This limitation is why the Visitor pattern exists (double dispatch).
What is double dispatch?

Selecting a method based on the runtime types of two objects rather than one. Java and C++ only give you single dispatch (on the receiver), so double dispatch is simulated with the Visitor pattern: the element calls visitor.visit(this), and because this has a known static type inside each concrete element, the correct overload is selected — combining one virtual call with one overload resolution. Typical use: rendering or exporting a heterogeneous object tree without putting export logic in every node class.

Method overloading with autoboxing and varargs — what is the resolution order?

The compiler runs three phases and stops at the first that finds an applicable method:

  1. Match without boxing/unboxing and without varargs (allows widening primitive conversion and subtyping).
  2. Allow boxing/unboxing, still no varargs.
  3. Allow varargs.

So f(int) beats f(long) beats f(Integer) beats f(int...). Within a phase, the most specific applicable method wins; if two are equally specific and unrelated, it's an ambiguity compile error.

When to choose which

Choose an abstract class when…

  • Subclasses share state or common field-based logic.
  • You want a template method: a concrete algorithm with abstract hook steps.
  • The types form a genuine IS-A family (AbstractHttpServlet).
  • You need non-public members or a constructor.

  • Unrelated classes need the same capability (Comparable, Serializable, Runnable).
  • You want to allow multiple capabilities on one class.
  • You're defining an API boundary for dependency injection and testing.
  • You want maximum decoupling — depend on abstractions, not classes (§16, DIP).
Java · both together, the standard idiom
interface Exportable { String export(); }         // capability

abstract class Report implements Exportable {     // shared state + template
    protected final String title;                 // state → needs abstract class
    protected Report(String title) { this.title = title; }

    // TEMPLATE METHOD: fixed algorithm, variable steps
    public final String render() {                // final: subclasses can't reorder
        return header() + body() + footer();
    }
    protected String header() { return "== " + title + " ==\n"; }  // default hook
    protected abstract String body();                              // must implement
    protected String footer() { return "\n-- end --"; }
}

class SalesReport extends Report {
    SalesReport() { super("Sales"); }
    @Override protected String body()  { return "revenue: 42"; }
    @Override public    String export(){ return render(); }
}

Java 8+ changed the answer

  • default methods — a body inside an interface, so you can add methods to a published interface without breaking every implementer. This is exactly how Collection.stream() and forEach() were retrofitted onto the entire Java Collections API.
  • static methods in interfaces — factory helpers like List.of(), Comparator.comparing().
  • private methods (Java 9) — to share code between default methods without exposing it.
  • Functional interface — exactly one abstract method, so it's a lambda target. Marked @FunctionalInterface. Runnable, Comparator, Callable, Function.
  • Sealed interfaces/classes (Java 17) — sealed interface Shape permits Circle, Square restricts who may implement, enabling exhaustive pattern matching.
"So are interfaces just abstract classes now?"

No, and this is the follow-up. Interfaces still cannot hold instance state and have no constructors. That's the reason multiple interface inheritance stays safe while multiple class inheritance doesn't — the diamond problem is fundamentally about duplicated state, not duplicated method names.

Interview Q&A · §07

asked every timeAbstract class vs interface — when do you use each?

Use an abstract class when the subtypes are a family that shares state and partial implementation — you need fields, a constructor, or a template method with default behaviour. Use an interface when you're declaring a capability that unrelated classes might have, when a class needs several such capabilities, or when you want a dependency-injection seam.

Rule of thumb: abstract class = "is a kind of"; interface = "is able to". A Bird IS-A Animal (abstract class, shares state like age and weight) and CAN-DO Flyable (interface, shared with Aeroplane, which is not an Animal).

Since Java 8, interfaces can carry behaviour via default methods, so the practical distinguishing feature is state: only abstract classes can hold instance fields.

Can an interface extend another interface? Can it extend a class?

An interface can extends one or more interfaces (multiple inheritance of type is allowed here). It cannot extend a class. A class implements interfaces and extends at most one class. A class can do both at once — class X extends Y implements A, B.

Can an abstract class have no abstract methods? Can it be final?

Yes to the first — perfectly legal, and a valid technique when you want to prevent direct instantiation while providing a fully working base (Java's AbstractMap style, or a base with only a protected constructor).

No to the second: abstract final class is a contradiction and a compile error. Abstract means "must be subclassed"; final means "cannot be subclassed". For the same reason an abstract method cannot be final, static or private.

What is a marker interface? Are they still used?

An interface with no members, used purely to tag a class with metadata that the runtime or a library checks via instanceof. Examples: Serializable, Cloneable, RandomAccess. Cloneable is the notorious one — it doesn't declare clone(), it just flips Object.clone() from throwing CloneNotSupportedException to working.

Modern code prefers annotations for metadata, since they carry parameters and are more expressive. Marker interfaces retain one advantage: they're a real type, so the compiler can enforce them in method signatures.

What is a functional interface? Name four from the JDK.

An interface with exactly one abstract method (SAM — single abstract method), so it can be the target of a lambda or method reference. Default and static methods don't count toward the limit, and neither do public methods of Object such as equals. @FunctionalInterface makes the compiler enforce it.

Examples: Runnable (run), Comparator<T> (compare), Function<T,R> (apply), Predicate<T> (test), Supplier<T> (get), Consumer<T> (accept), Callable<V> (call).

Why were default methods added to Java 8?

Interface evolution. Adding an abstract method to a published interface breaks every existing implementation — and Java needed to add stream(), forEach(), removeIf() to Collection, which thousands of third-party classes implement. Default methods let the method arrive with an implementation, so old code keeps compiling. The secondary benefit is shared behaviour across implementers without an abstract base class.

Cost: they reintroduce a conflict case for multiple inheritance, which Java resolves by forcing an explicit override (§05).

What is duck typing and how does it change the answer in Python?

Duck typing means an object's suitability is determined by the presence of the methods it's asked for, not by its declared type. Python doesn't need a class to declare implements Drawable — if it has a draw() method, it works. So Python gets polymorphism without inheritance, and abstract base classes are used only when you want to enforce a contract or benefit from isinstance checks. typing.Protocol gives static structural typing to type-checkers while keeping runtime duck typing.

§08

Constructors and destructors

Constructors are where invariants are established. If the constructor completes, the object should be valid — no exceptions.

Constructor properties

  • Same name as the class; no return type, not even void (write void and it becomes an ordinary method that happens to share the class name — a classic trick question).
  • Invoked automatically on object creation; cannot be called directly on an existing object.
  • Not inherited, cannot be overridden, cannot be final/static/abstract/synchronized.
  • Can be overloaded, and can be private (singletons, static factories, utility classes).
  • If you write no constructor, the compiler supplies a no-arg default constructor. Write any constructor and that default disappears.

Types of constructor

Java
class Point {
    int x, y;

    Point()                { this(0, 0); }        // no-arg, delegates via this()
    Point(int x, int y)    { this.x = x; this.y = y; }   // parameterised
    Point(Point other)     { this(other.x, other.y); }   // copy constructor (manual)
}
C++ · the special member functions
class Buffer {
    char*  data;
    size_t n;
public:
    Buffer(size_t n) : data(new char[n]), n(n) {}          // 1. parameterised ctor
    Buffer() : Buffer(16) {}                               //    delegating (C++11)
    Buffer(const Buffer& o) : data(new char[o.n]), n(o.n){ // 2. COPY constructor
        std::copy(o.data, o.data + o.n, data);             //    deep copy
    }
    Buffer& operator=(const Buffer& o);                    // 3. copy assignment
    Buffer(Buffer&& o) noexcept                           // 4. MOVE constructor
        : data(o.data), n(o.n) { o.data = nullptr; o.n = 0; }
    Buffer& operator=(Buffer&& o) noexcept;               // 5. move assignment
    ~Buffer() { delete[] data; }                           // 6. destructor
};
Rule of Three / Five / Zero

Rule of Three: if you need a custom destructor, copy constructor, or copy assignment operator, you almost certainly need all three — because they all exist for the same reason: the class owns a resource.
Rule of Five: in C++11 add the move constructor and move assignment operator for efficiency.
Rule of Zero: best of all — own no raw resources. Use std::string, std::vector, std::unique_ptr, and write none of the six; the compiler-generated versions are correct.

Initialisation order in Java — memorise this list

For new Child(), where Child extends Parent:

  1. Class loading (once ever): Parent static fields & static blocks, in source order → then Child's.
  2. Allocation: memory zeroed — all fields get default values (0, false, null).
  3. Child constructor is entered, immediately delegates via super() (implicit if absent).
  4. Parent: instance initialiser blocks & instance field initialisers in source order → Parent constructor body.
  5. Child: instance initialiser blocks & field initialisers in source order → Child constructor body.
Java · trace this
class P {
    static { System.out.println("1 P static"); }
    { System.out.println("3 P instance block"); }
    P()  { System.out.println("4 P ctor"); }
}
class C extends P {
    static { System.out.println("2 C static"); }
    { System.out.println("5 C instance block"); }
    C()  { System.out.println("6 C ctor"); }
}

C++
class Widget {

Interview Q&A · §08

Can a constructor be private? Why would you do that?

Yes. Reasons:

  • Singleton — force all access through getInstance().
  • Static factory methods — LocalDate.of(...), Integer.valueOf(...): named, can return cached instances or subtypes.
  • Utility class — Math, Collections: prevent instantiation entirely.
  • Builder pattern — construction only through the builder, guaranteeing a valid object.

A private constructor also implicitly prevents subclassing, since the subclass could not call super().

What is a copy constructor? Does Java have one?

A constructor taking an object of the same class and initialising the new object from it. In C++ it's a compiler-generated special member (a memberwise, shallow copy by default) invoked on T b = a;, on pass-by-value, and on return-by-value. If your class owns raw memory, you must write a deep copy or the two objects share a pointer and both destructors free it — a double free.

Java has no built-in copy constructor; you can write one manually (public Point(Point o)), which is the recommended alternative to the broken Cloneable/clone() mechanism (§11). Java assignment b = a; copies only the reference, never the object.

Difference between copy constructor and assignment operator in C++?

The copy constructor creates a new object from an existing one, so the target has no prior state. The assignment operator overwrites an already-constructed object, so it must first release its existing resources and must guard against self-assignment.

C++
Buffer a(10);
Buffer b = a;    // COPY CONSTRUCTOR   (initialisation)
Buffer c(5);
c = a;           // COPY ASSIGNMENT    (c already exists)

The safe implementation of assignment is the copy-and-swap idiom: take the parameter by value, then swap with *this — that gives self-assignment safety and the strong exception guarantee for free.

What is a shallow copy vs a deep copy? Why does it matter here?

Shallow copy duplicates the top-level fields; reference/pointer fields end up pointing at the same underlying object. Deep copy recursively duplicates what those references point to, so the two objects are fully independent.

It matters in constructors because the compiler-generated C++ copy constructor and Java's Object.clone() both do shallow copies. Symptoms of getting it wrong: mutating one object visibly changes the "copy", and in C++, a double free at destruction. Full treatment in §11.

Can a constructor throw an exception? What happens to the object?

Yes, and it's the correct way to reject invalid arguments — an object that would violate its invariants should never exist. If the constructor throws, construction fails and no reference is returned; the partially built object becomes garbage.

C++ subtlety worth stating: if a constructor throws, the destructor of that object is not called (the object was never fully constructed), but destructors of fully-constructed members and base classes are called. This is exactly why raw new in a constructor leaks on a later throw, and why RAII members (unique_ptr, vector) are the fix.

What is constructor chaining?

One constructor calling another to avoid duplicated initialisation logic. Within the same class: this(args) in Java, delegating constructors in C++11. Up the hierarchy: super(args) in Java, the member-initialiser list in C++. In Java the call must be the very first statement, and this() and super() are mutually exclusive in one constructor. Recursive chaining (A() calls A(int) which calls A()) is a compile error in Java.

Why is finalize() discouraged, and what replaced it?

Because it offers no guarantee of when, or even whether, it runs; it can resurrect the object by storing this somewhere; it adds a second GC cycle for every finalizable object; and exceptions inside it are silently swallowed. Deprecated in Java 9 and since removed.

Replacements: AutoCloseable + try-with-resources for deterministic release (the correct answer in 95% of cases), and java.lang.ref.Cleaner or PhantomReference as a safety net for native resources.

What is the order of destructor calls in C++ multilevel inheritance?

Exactly the reverse of construction. Construction: base → derived → most-derived, with each class's members constructed before its own constructor body. Destruction: most-derived destructor body → its members in reverse declaration order → derived base → base. Objects on the stack are destroyed in reverse order of declaration when the scope exits.

Interview Q&A · §09

very commonComposition vs inheritance — which and why?

Prefer composition by default. Inheritance couples a subclass to the implementation of its parent, so a change in the parent can silently break children (fragile base class). It's also fixed at compile time, is limited to one superclass in Java, and exposes protected internals, weakening encapsulation. Composition depends only on an interface, can be swapped at run time, allows many collaborators, and makes unit testing trivial via injected fakes.

Use inheritance when there is a real IS-A relationship that satisfies the Liskov Substitution Principle and you actually want to inherit the parent's behaviour — typically when both classes are in the same package or module and evolve together.

Composition vs aggregation — give a precise distinction.

Both are HAS-A; the difference is ownership and lifetime. In composition the whole owns the part: the part is created by the whole and cannot exist meaningfully without it (House–Room, Order–OrderLine). In aggregation the whole merely holds a reference to a part that exists independently and may be shared (Department–Professor, Playlist–Song). In UML: filled diamond for composition, hollow for aggregation.

Model a car: which relationships appear?
  • Car IS-A Vehicle — inheritance.
  • Car HAS-A Engine — composition (a car's engine is built into it; scrap the car, scrap the engine as installed).
  • Car HAS-A Driver — aggregation (the driver exists independently and can drive another car).
  • Car USES FuelStation — association/dependency (passed to a refuel() method).

Being able to justify why the engine is composition and the driver is aggregation is the whole point of the question.

What is delegation?

An object forwarding a request to a held collaborator instead of handling it itself — the mechanism that makes composition work. It's how Decorator, Proxy, Adapter and Strategy are all implemented. Difference from inheritance: with delegation, this inside the delegate refers to the delegate, not the outer object, so there is no accidental self-call recursion (which is precisely what breaks the inherited CountingSet above).

Interview Q&A · §10

Why is main declared public static void main(String[] args)?
  • public — the JVM must call it from outside the class.
  • static — it must be callable without creating an instance; the JVM has no way to know which constructor to use.
  • void — the JVM ignores any return value; exit status is set via System.exit().
  • String[] args — command-line arguments. String... args is equivalent and also valid.

Follow-up: yes, main can be overloaded, but the JVM only invokes the exact String[] signature; other overloads must be called explicitly. It can also be final or synchronized.

Can a static method access instance variables? Can an instance method access static ones?

Static cannot access instance members directly — no this exists — but it can if given an object reference explicitly (obj.field). Instance methods can freely access static members, since the class is always available. Similarly, this and super are unavailable in static context, and an inner (non-static) class cannot be declared inside a static context without an enclosing instance.

When are static blocks executed?

During class initialisation, which happens at most once, on the first of: creating an instance, accessing a static field (that isn't a compile-time constant), calling a static method, or reflective initialisation via Class.forName. Multiple static blocks run in source order, interleaved with static field initialisers. This is exactly what old JDBC drivers used to register themselves.

Can we declare a class as static?

Only a nested class. A static nested class behaves like a top-level class that happens to be namespaced inside another; it has no implicit reference to an outer instance and can be instantiated as Outer.Inner x = new Outer.Inner();. A non-static inner class requires an outer instance: outer.new Inner(). Prefer static nested classes — the hidden outer reference in inner classes prevents the outer object from being garbage collected.

Difference between final, const and readonly semantics?

Java's final on a field = assign once, at declaration or in every constructor path (a "blank final"). It gives no transitive immutability. C++ const is transitive at the type level (const T* forbids modifying the pointee) and also applies to member functions, promising the function doesn't mutate the object. C++ constexpr goes further: evaluable at compile time. Java's nearest to compile-time constant is static final with a constant initialiser, which the compiler inlines into call sites — a real gotcha, since changing the constant requires recompiling dependent classes.

Why clone() is considered broken

Cloneable is a marker interface that doesn't declare clone(); Object.clone() is protected, throws a checked exception, creates the object without running any constructor (so invariants aren't re-established and final fields can't be reassigned), and is shallow by default. Java · the contract
class Point {
    final int x, y;
    Point(int x, int y) { this.x = x; this.y = y; }

    @Override public boolean equals(Object o) {
        if (this == o) return true;                       // fast path
        if (!(o instanceof Point p)) return false;        // type + null check
        return x == p.x && y == p.y;                      // value comparison
    }
    @Override public int hashCode() { return Objects.hash(x, y); }
}

The hashCode contract: equal objects must have equal hash codes. Unequal objects may collide. Break this and your object goes into a HashMap and can never be found again — it hashes to a different bucket than the lookup key.

Interview Q&A · §11

very commonDifference between == and equals()?

== compares values for primitives and references (identity) for objects. equals() is a method whose default implementation in Object is also reference comparison, but which classes override to compare logical content — String, the wrappers, and collections all do.

C++ contrast: == can be overloaded for a class, so it compares content if you say so; there is no separate equals. Python uses is for identity and == (which dispatches to __eq__) for equality.

very commonWhy must you override hashCode() whenever you override equals()?

Because hash-based collections rely on the contract "equal objects have equal hash codes". HashMap.get(key) first computes the bucket from hashCode(), then scans that bucket using equals(). If two logically equal objects produce different hash codes they land in different buckets, so a lookup with an equal key returns null and a HashSet happily stores duplicates.

Java
// equals overridden, hashCode NOT:
Set<Point> s = new HashSet<>();
s.add(new Point(1,1));
s.contains(new Point(1,1));   // false — different buckets
s.add(new Point(1,1));        // size becomes 2

The reverse is not required: equal hash codes do not imply equality (collisions are legal and expected).

How do you make a class immutable? Why is String immutable?

Make the class final, all fields private final, provide no setters, take defensive copies of mutable arguments in the constructor and of mutable state in getters, and never leak this during construction.

String is immutable for: security (a filename or class name validated then mutated would be a TOCTOU attack), the string pool (sharing one instance is only safe if nobody can change it), hash caching (a String caches its hash on first use, which is why it's the ideal HashMap key), and thread safety without synchronisation. The cost is garbage — hence StringBuilder for repeated concatenation.

What is the difference between deep copy and shallow copy? How do you implement each?

Shallow copies only the top-level fields, so reference fields are shared between the original and the copy; mutating a nested object through one is visible through the other. Deep copy recursively duplicates the entire reachable object graph, producing an independent object.

Implement shallow with Object.clone() or the default C++ copy constructor. Implement deep by writing a copy constructor that constructs new instances of each mutable member (recursively), by serialisation round-trip in Java, or with copy.deepcopy() in Python. Watch for cycles — a naive recursive deep copy on a cyclic graph loops forever; you need a visited map.

Why is StringBuffer/StringBuilder needed?

Because String is immutable, every concatenation creates a new object; concatenating in a loop is O(n²) in time and garbage. StringBuilder holds a mutable char array and appends in amortised O(1). StringBuffer is the same API with synchronized methods — thread-safe but slower, and almost never what you want, since builders are usually method-local. Note the compiler already rewrites simple a + b + c expressions into a builder; it's the loop case that needs manual work.

Can an immutable class have a mutable field?

Yes, as long as it is never exposed and never mutated after construction — for example a cached hash code (String.hash works exactly like this: a non-final int computed lazily). This is "observable immutability": the class appears immutable to every caller even though a field changes internally. It's safe only if the computation is idempotent and the field write is benign under concurrency.

Operator overloading

A C++ topic that Java candidates still get asked, because the interesting question is why Java refuses to have it.

C++
class Complex {
    double re, im;
public:
    Complex(double r = 0, double i = 0) : re(r), im(i) {}

    // Member: left operand is implicitly *this
    Complex operator+(const Complex& o) const { return {re + o.re, im + o.im}; }
    Complex& operator+=(const Complex& o) { re += o.re; im += o.im; return *this; }
    bool operator==(const Complex& o) const { return re == o.re && im == o.im; }

    // Prefix vs postfix ++: the int parameter is a dummy tag
    Complex& operator++()    { ++re; return *this; }          // ++c
    Complex  operator++(int) { Complex t = *this; ++re; return t; }  // c++

    // Non-member friend: needed when the LEFT operand isn't your class
    friend std::ostream& operator<<(std::ostream& os, const Complex& c) {
        return os << c.re << (c.im < 0 ? "" : "+") << c.im << "i";
    }
};

  • Cannot be overloaded: :: (scope), . (member access), .*, ?:, sizeof, typeid.
  • Must be a member function: =, [], (), ->, and conversion operators.
  • Should be non-member: symmetric binary operators like + and ==, and stream operators (because the left operand is ostream, not yours).
  • You cannot invent new operators or change arity, precedence or associativity.
  • At least one operand must be a user-defined type — you can't redefine int + int.

Interview Q&A · §12

commonWhy doesn't Java support operator overloading?

A deliberate design decision for readability and simplicity. James Gosling's stated reasoning: overloaded operators are frequently abused, making code where a + b could allocate, throw, or do I/O — so you can no longer read an expression and know roughly what it costs. It also complicates the language spec and the compiler.

Important nuance to add: Java isn't consistent about it — + is overloaded for String concatenation, which is a built-in special case, not something you can do for your own types. The idiomatic Java substitute is named methods: BigDecimal.add(), compareTo(), equals(). Kotlin and Scala, which run on the JVM, both support operator overloading.

Is method overloading the same as operator overloading?

Both are compile-time (ad-hoc) polymorphism, and an overloaded operator in C++ is literally a function named operator+, resolved by the same overload rules. The difference is only syntactic — operators are called through infix notation and inherit fixed precedence and arity, which functions do not.

How do you overload << for your class, and why must it be a friend/non-member?

Because the left operand is std::ostream, not your class. A member operator<< would require the left operand to be your type, giving the backwards syntax myObj << cout. So you write a free function std::ostream& operator<<(std::ostream&, const T&), and declare it friend if it needs access to private members. It returns the stream by reference to allow chaining.

How do you distinguish prefix and postfix ++?

By a dummy int parameter. T& operator++() is prefix and returns a reference to the modified object. T operator++(int) is postfix, saves a copy, increments, and returns the copy by value. That's also why postfix is slower for heavy types, and why ++it is preferred over it++ for iterators.

Overriding rules for exceptions

  • An overriding method may throw fewer or narrower checked exceptions than the parent, never broader or new ones.
  • It may throw any number of unchecked exceptions regardless of the parent's throws clause.
  • This is a direct application of the Liskov Substitution Principle: a caller holding a parent reference must not be surprised by a new checked failure mode.
Java

class Ok2 extends Parent { void read() throws FileNotFoundException {} } // narrower: legal

class Bad extends Parent { void read() throws Exception {} }         // BROADER: error
The finally + return trap
Java
int f() {
    try { return 1; }
    finally { return 2; }     // returns 2 — finally's return DISCARDS try's
}
int g() {
    int x = 1;
    try { return x; }         // return value (1) is COPIED before finally runs
    finally { x = 99; }       // returns 1, not 99
}

finally is skipped only by System.exit(), a JVM crash, or a thread that never leaves the try block. Never return or throw from finally — it swallows the original exception.

C++ and Python contrasts

  • C++ has no checked exceptions; noexcept declares a function won't throw (violating it calls std::terminate). Exceptions must be caught by const& to avoid slicing. Throwing from a destructor during stack unwinding terminates the program. RAII is what makes C++ exception-safe — there is no finally.
  • Python uses try/except/else/finally. All exceptions are unchecked. raise X from Y chains causes. The else block runs only if no exception occurred, and context managers (with) play the role of try-with-resources.

Interview Q&A · §13

Checked vs unchecked exceptions — and which should you create?

Checked exceptions are verified at compile time: the calling method must either catch them or declare throws. They model recoverable conditions caused by the environment. Unchecked exceptions (RuntimeException and subclasses) need no declaration and model programming errors.

Guidance: create a checked exception only when the caller can plausibly do something about it. Otherwise prefer unchecked — checked exceptions propagate up through every layer and pollute signatures, which is why most modern frameworks (Spring, Hibernate) wrap them into unchecked ones.

Can a try exist without catch? Without finally?

A try needs at least one of catch or finally — try {} alone won't compile. try/finally with no catch is a normal and useful pattern for guaranteed cleanup while letting the exception propagate. Since Java 7, try-with-resources may stand alone with neither, because the implicit finally that closes resources satisfies the rule.

What is exception chaining and why use it?

Wrapping a low-level exception in a higher-level one while preserving the original as the cause: throw new DataAccessException("load failed", sqlEx). It lets each layer expose an abstraction-appropriate exception (so callers don't depend on SQL details — that's the Dependency Inversion Principle) without losing the root-cause stack trace, which is printed as "Caused by:". Losing the cause is one of the most common real-world logging mistakes.

What is object slicing? (C++)

Assigning or passing a derived object by value to a base-type variable copies only the base sub-object — the derived parts are "sliced off", and the result is a plain Base with base behaviour, even for virtual functions.

C++
void f(Base b);          // by value → SLICES
void g(const Base& b);   // by reference → polymorphism works

Derived d;
f(d);   // only Base part copied; virtual calls dispatch to Base
g(d);   // correct: dispatches to Derived

This is the reason exceptions must be caught by reference (catch (const std::exception& e)) and why polymorphic parameters are passed by reference or pointer. Java cannot slice, because objects are always accessed via references.

Can constructors throw? Should destructors?

Constructors should throw on invalid input — that's how you guarantee no invalid object exists. Destructors should never throw: in C++ a destructor that throws while an exception is already unwinding the stack calls std::terminate. Since C++11 destructors are implicitly noexcept. If cleanup can fail, expose an explicit close() that can throw and let the destructor swallow errors as a last resort.

Interview Q&A · §14

Why were generics added to Java, and what is type erasure?

Before Java 5, collections held Object, so type errors surfaced as ClassCastException at runtime and every read needed a manual cast. Generics move that check to compile time and remove the casts from source.

Type erasure is how it was implemented while keeping binary compatibility with pre-generics code: the compiler checks types, then erases the parameters (replacing T with its bound, usually Object) and inserts the casts itself. So the bytecode looks essentially like the old pre-generics code, and old and new code interoperate.

What does PECS mean?

Producer Extends, Consumer Super. Use ? extends T when the structure only produces T values that you read out — you can read them as T but cannot add (except null), because the actual element type could be any subtype. Use ? super T when the structure consumes T values you write in — you can add T but reads come back as Object. Use an exact T when you both read and write.

Is List<String> a subtype of List<Object>?

No — Java generics are invariant. If it were allowed, you could write List<Object> o = stringList; o.add(42); and then a String read would fail. Arrays, by contrast, are covariant (String[] IS-A Object[]), which is a known design flaw — it defers the failure to runtime as an ArrayStoreException. Wildcards exist to recover the flexibility that invariance removes.

Templates vs generics — which is more powerful?

C++ templates are strictly more expressive: they support non-type parameters (array<int, 5>), full and partial specialisation, template metaprogramming, and they work with primitives without boxing, producing fully specialised machine code. Java generics are simpler, compile once, give clearer errors, and preserve backward compatibility — but they cost boxing, forbid new T(), and lose type information at runtime. Different goals: C++ optimises for zero-overhead abstraction, Java for safety and binary compatibility.

§15

Memory management: GC, RAII, smart pointers

Java: garbage collection

  • Reachability, not reference counting. An object is collectable when it is not reachable from any GC root (stack locals, static fields, JNI refs, active threads). This is why reference cycles are collected fine in Java but leak in a pure refcounting scheme.
  • Generational hypothesis — most objects die young. The heap is split into Young (Eden + two Survivor spaces) and Old. Minor GCs sweep Young frequently and cheaply; objects surviving enough cycles are promoted to Old, collected by rarer, costlier major GCs.
  • Collectors: Serial, Parallel (throughput), G1 (default since JDK 9, region-based, pause-target driven), ZGC and Shenandoah (sub-millisecond pauses on huge heaps).
  • System.gc() is only a request; the JVM may ignore it. Never rely on it.
Yes, Java can leak

A memory leak in Java means unintentional retention: objects still reachable but never used again. Common causes — a static Map cache with no eviction; unremoved listeners/observers; a non-static inner class or lambda capturing an outer object (Android Activity leaks); ThreadLocals not cleared in a thread pool; unclosed streams and connections. Fix with weak references (WeakHashMap), explicit removal, and bounded caches.

C++: RAII and smart pointers

RAII — Resource Acquisition Is Initialisation: tie a resource's lifetime to an object's lifetime. Acquire in the constructor, release in the destructor. Because destructors run deterministically when a scope exits — including during exception unwinding — resources cannot leak. This is C++'s answer to both GC and finally.

    mayThrow();
}   // scope exit: file closed, mutex released — even if mayThrow() threw

Interview Q&A · §15

How does garbage collection decide what to collect?

By reachability. The collector starts from GC roots — stack frames of live threads, static fields, JNI references — and marks everything transitively reachable. Whatever is unmarked is garbage. Then it either sweeps in place or copies survivors to a fresh region (compacting, which also fixes fragmentation).

Key consequence: an island of mutually referencing but unreachable objects is collected, so cycles are not a leak in Java — unlike naive reference counting.

Can you force GC in Java? Can memory leak in Java?

You can call System.gc()/Runtime.getRuntime().gc(), but it's advisory only and may be ignored entirely (it can even be disabled with -XX:+DisableExplicitGC). Relying on it is a code smell.

And yes, leaks happen — as unintentional retention. Static collections that only grow, forgotten listeners, ThreadLocals in pooled threads, and inner-class captures are the usual suspects. The tell is a heap that grows steadily across full GCs; diagnose with a heap dump and a dominator tree in a profiler.

RAII vs garbage collection — which is better?

They solve different problems. GC handles memory automatically and correctly, including cycles, at the cost of non-deterministic timing and pause latency. RAII handles all resources — memory, files, sockets, locks — deterministically at scope exit, which GC cannot do (a finalizer might run minutes later, or never, so file handles would be exhausted).

That's why Java added try-with-resources: it reintroduces deterministic release for non-memory resources on top of a GC'd heap. The honest summary: GC removes a class of bugs (use-after-free, double free) at the price of control; RAII gives control at the price of requiring discipline.

What is a dangling pointer, a double free, and a memory leak?
  • Dangling pointer — a pointer to memory that has already been freed; dereferencing it is undefined behaviour. Set pointers to nullptr after delete, or use smart pointers.
  • Double free — calling delete twice on the same address, corrupting the allocator. Almost always caused by a shallow copy of a pointer-owning class (§08).
  • Memory leak — allocated memory that is never freed and no longer reachable. In C++ from a missing delete; in Java from unintentional retention.

All three disappear if you follow the Rule of Zero and use unique_ptr/containers rather than raw new.

SOLID principles

Five design principles by Robert C. Martin. Expect "explain SOLID" as a single question, then a follow-up asking for a violation you've seen. Have a real example ready.

S — Single Responsibility Principle

A class should have one, and only one, reason to change. "Reason to change" means one stakeholder or one axis of change — not "does one thing".

Java
// VIOLATION: three reasons to change — business rules, DB schema, report format
class Employee {
    double calculatePay()  { }   // changes when finance policy changes
    void   save()          { }   // changes when the DB changes
    String toReport()      { }   // changes when the report format changes
}

// FIX: separate the axes
class Employee          { double calculatePay() { } }   // domain
class EmployeeRepository{ void save(Employee e) { } }   // persistence
class EmployeeReporter  { String render(Employee e) { } }  // presentation

O — Open/Closed Principle

Open for extension, closed for modification. Adding behaviour should mean adding code, not editing working code.

Java
// VIOLATION: every new shape edits this method — and risks breaking the others
double area(Object s) {
    if (s instanceof Circle c)   return Math.PI * c.r * c.r;
    else if (s instanceof Square q) return q.side * q.side;
    // add Triangle → edit here, retest everything
}

// FIX: polymorphism. New shape = new class, zero edits to existing files.
interface Shape { double area(); }
class Triangle implements Shape { public double area() { } }

L — Liskov Substitution Principle

Objects of a subtype must be usable anywhere the supertype is expected, without the caller needing to know. A subclass may weaken preconditions and strengthen postconditions, never the reverse.

Java · the canonical violation
class Rectangle {
    protected int w, h;
    void setWidth(int w)  { this.w = w; }
    void setHeight(int h) { this.h = h; }
    int area() { return w * h; }
}
class Square extends Rectangle {                 // "a square IS-A rectangle", right?
    @Override void setWidth(int w)  { this.w = this.h = w; }
    @Override void setHeight(int h) { this.w = this.h = h; }
}

void test(Rectangle r) {
    r.setWidth(5); r.setHeight(4);
    assert r.area() == 20;          // holds for Rectangle, FAILS for Square (16)
}
// Fix: don't inherit. Make Shape an interface; Square and Rectangle are siblings,
// or make both immutable so the mutating precondition never exists.

Other LSP violations to name: an override that throws UnsupportedOperationException (Arrays.asList().add()), an override that widens checked exceptions, or one that tightens an input precondition.

I — Interface Segregation Principle

No client should be forced to depend on methods it does not use. Prefer several small role interfaces to one fat one.

Java
// VIOLATION
interface Worker { void work(); void eat(); void attendStandup(); }
class Robot implements Worker {
    public void work() { }
    public void eat()  { throw new UnsupportedOperationException(); }  // smell
    public void attendStandup() { throw new UnsupportedOperationException(); }
}

// FIX
interface Workable { void work(); }
interface Feedable { void eat(); }
class Robot  implements Workable { public void work() { } }
class Human  implements Workable, Feedable { }

D — Dependency Inversion Principle

High-level modules should not depend on low-level modules; both should depend on abstractions. And abstractions should not depend on details — details depend on abstractions.

Java
// VIOLATION: the policy layer is welded to a specific database
class OrderService {
    private final MySqlOrderRepo repo = new MySqlOrderRepo();   // concrete + self-made
}

// FIX: depend on an interface, receive the implementation (dependency injection)
interface OrderRepo { void save(Order o); }

class OrderService {
    private final OrderRepo repo;
    OrderService(OrderRepo repo) { this.repo = repo; }   // constructor injection
}
new OrderService(new MySqlOrderRepo());     // production
new OrderService(new InMemoryOrderRepo());  // unit test — no DB needed
The three you should also be able to name

DRY — Don't Repeat Yourself: every piece of knowledge has one authoritative representation. KISS — keep it simple. YAGNI — You Aren't Gonna Need It: don't build for imagined future requirements. Add Law of Demeter ("talk to friends, not strangers" — avoid a.getB().getC().doThing()) if you want a fourth.

Interview Q&A · §16

very commonExplain SOLID in one line each.
  • Single Responsibility — one reason to change per class.
  • Open/Closed — extend behaviour by adding code, not editing existing code.
  • Liskov Substitution — a subtype must be usable wherever its supertype is, without surprises.
  • Interface Segregation — many small role interfaces beat one fat interface.
  • Dependency Inversion — depend on abstractions; inject the concrete implementation.

Then offer the payoff sentence: together they make code testable and changeable, and O and D are what let you add features without touching working code.

Give a real Liskov violation from a standard library.

java.util.Arrays.asList(arr) returns a fixed-size List whose add() throws UnsupportedOperationException. Any code written against the List contract can break when handed one. Same for Collections.unmodifiableList and List.of(). Also java.util.Stack extends Vector, so a Stack exposes insertElementAt(0, x) — you can insert at the bottom of a stack, which violates what a stack means. Properties extends Hashtable<Object,Object> is another: it's supposed to be String-to-String but inherits methods that accept anything.

How does SOLID relate to unit testing?

Directly — hard-to-test code almost always violates SRP or DIP. If a class news up its own database connection (DIP violation) you cannot test it without a database. If it does three unrelated things (SRP violation) every test needs the whole setup. Applying DIP with constructor injection is what makes mocking possible, and applying SRP is what keeps each test small. A good line for an interview: "I treat 'this is hard to unit test' as a design smell, not a testing problem."

Can you over-apply SOLID?

Yes, and saying so shows judgement. Taken to an extreme, SRP produces hundreds of one-method classes, DIP produces an interface per class with exactly one implementation, and the codebase becomes impossible to navigate — abstraction without a second implementation is speculative generality, which YAGNI warns against. The principles are heuristics for managing likely change, applied where change is actually likely.

Singleton

Exactly one instance, with a global access point. Also the most criticised pattern — it's global mutable state, it hides dependencies, and it makes unit testing painful.

Java · the three implementations to know
// 1. EAGER — simple, thread-safe by class-initialisation semantics
class EagerSingleton {
    private static final EagerSingleton INSTANCE = new EagerSingleton();
    private EagerSingleton() {}
    public static EagerSingleton getInstance() { return INSTANCE; }
}

// 2. LAZY, thread-safe: double-checked locking. `volatile` is MANDATORY.
class LazySingleton {
    private static volatile LazySingleton instance;   // volatile stops the
    private LazySingleton() {}                        // reordering bug below
    public static LazySingleton getInstance() {
        if (instance == null) {                       // 1st check: no lock
            synchronized (LazySingleton.class) {
                if (instance == null)                 // 2nd check: with lock
                    instance = new LazySingleton();
            }
        }
        return instance;
    }
}

// 3. ENUM — the recommended way (Effective Java). Serialization- and
//    reflection-safe for free, and lazy via class loading.
enum Config {
    INSTANCE;
    private final Properties props = load();
    public String get(String k) { return props.getProperty(k); }
}
Why volatile in double-checked locking

instance = new LazySingleton() is not atomic: allocate → construct → assign reference. The JIT or CPU may reorder assign before construct, so another thread can see a non-null but half-initialised object. volatile forbids that reordering and guarantees visibility. Without it, DCL is famously broken.

Interview Q&A · §17

very commonImplement a thread-safe Singleton and explain the trade-offs.

Best answer: an enum singleton, because the JVM guarantees a single instance even across serialisation and reflection attacks, and initialisation is lazy and thread-safe by the class-initialisation lock. Second best: the initialisation-on-demand holder idiom — a private static nested class holding the instance, loaded only on first access, thread-safe with no synchronisation cost. Third: double-checked locking with a volatile field.

Trade-offs to volunteer: a singleton is global mutable state, so it hides dependencies, complicates unit testing (you cannot inject a fake), can become a concurrency bottleneck, and misbehaves across multiple class loaders. In modern code the same "one instance" outcome is usually achieved by a DI container with singleton scope, which keeps the class itself an ordinary injectable object.

Difference between Factory and Abstract Factory?

Factory Method defines an interface for creating one product and lets subclasses (or a switch) decide the concrete class. Abstract Factory provides an interface for creating families of related products without specifying concrete classes, so the products are guaranteed to be compatible with each other. Structurally, an Abstract Factory is usually implemented as an object with several factory methods on it.

Over-application. A pattern is a response to a specific pressure; applying it before the pressure exists adds indirection with no benefit (speculative generality). Patterns can also become a substitute for thinking — "we need a factory" instead of "why is construction hard here?" Interview Q&A · §18

Why are Java methods virtual by default while C++ methods are not?

Different priorities. C++ follows "you don't pay for what you don't use": virtual dispatch costs a vptr per object and an indirect call, so it's opt-in. Java prioritises polymorphism as the default idiom and relies on the JIT to remove the cost — it can devirtualise and inline whenever the profile shows only one implementation is used, adding a cheap guard for correctness. A consequence: in C++, forgetting virtual silently breaks polymorphism; in Java, forgetting final silently permits it.

Java has no destructors — how do you release a file handle deterministically?

Implement AutoCloseable and use try-with-resources, which guarantees close() runs at the end of the block, before any catch or finally, and even if the body throws (suppressed exceptions are attached to the primary one). Cleaner or a phantom reference can act as a last-resort safety net for native resources, but they must not be the primary mechanism.

How does Python achieve polymorphism without interfaces?

Duck typing plus dynamic attribute lookup: a call obj.draw() is resolved at runtime by searching the instance dict, then the class, then the MRO. No declared relationship is needed — anything with a draw attribute works. ABCs add optional enforcement, and typing.Protocol adds static structural checking for tools like mypy without any runtime inheritance.

Predict the output

classicQ1 — Is Java pass-by-value or pass-by-reference?
Java
static void mutate(StringBuilder sb) { sb.append(" world"); }
static void reassign(StringBuilder sb) { sb = new StringBuilder("bye"); }

StringBuilder s = new StringBuilder("hello");
mutate(s);    System.out.println(s);
reassign(s);  System.out.println(s);

Output: hello world then hello world.

Java is always pass-by-value. The value passed is a copy of the reference. mutate follows that copy to the same heap object and changes it, so the caller sees the change. reassign rebinds only the local copy of the reference; the caller's variable still points at the original object. If Java were pass-by-reference, the second line would print "bye".

Java
class A { static void s(){System.out.println("A.s");}
          void i(){System.out.println("A.i");}
          String f = "A.f"; }

class Derived extends Base {
    int x = 10;
    Derived(){ System.out.println("ctor, x=" + x); }
    @Override void show(){ System.out.println("Derived.show, x=" + x); }
}
new Derived();

Output: Derived.show, x=0 then ctor, x=10

The Base constructor runs first and its call to show() dispatches to the override (Java methods are virtual immediately). But x = 10 is a field initialiser of Derived, which runs after super() returns, so x is still the default 0.

In C++ the same code prints Base.show, because the vptr still points at Base's vtable during Base's constructor. Both are reasons never to call an overridable method from a constructor.

Q4 — Overload resolution with null
Java
void f(Object o) { System.out.println("Object"); }
void f(String s) { System.out.println("String"); }
f(null);

Output: String

null is assignable to both, so the compiler picks the most specific applicable type, and String is a subtype of Object. Add void f(Integer i) and the same call becomes a compile error: String and Integer are unrelated, so there is no single most specific method. Cast explicitly — f((String) null) — to disambiguate.

Q5 — Integer caching
Java
Integer a = 127, b = 127;
Integer c = 128, d = 128;
System.out.println(a == b);
System.out.println(c == d);
System.out.println(c.equals(d));

Output: true / false / true

Integer.valueOf (which autoboxing calls) caches instances from −128 to 127 inclusive, so a and b are the same object. 128 is outside the cache, so two distinct objects are created and == compares different references. equals compares values and is always correct. Lesson: never use == on boxed types.

Q6 — equals without hashCode
Java
class P { int x;
  P(int x){this.x=x;}
  @Override public boolean equals(Object o){ return o instanceof P p && p.x==x; } }

Set<P> s = new HashSet<>();
s.add(new P(1)); s.add(new P(1));
System.out.println(s.size() + " " + s.contains(new P(1)));

Output: 2 false

hashCode() was not overridden, so it falls back to identity hashing — three logically equal objects land in three different buckets. The set never even reaches the equals comparison. Overriding equals without hashCode is one of the most common real bugs in Java code.

Q7 — C++ slicing
C++
struct Base    { virtual void who(){ std::cout << "Base\n"; } };
struct Derived : Base { void who() override { std::cout << "Derived\n"; } };

void byValue(Base b) { b.who(); }
void byRef(Base& b)  { b.who(); }

Derived d;  byValue(d);  byRef(d);

Output: Base then Derived

byValue copy-constructs a Base from the Derived, discarding the derived part — object slicing. The copy genuinely is a Base, so the virtual call resolves to Base::who. byRef binds a reference to the original object, so dispatch works. Rule: pass polymorphic types by reference or pointer, never by value.

Q8 — Python mutable default argument
Python
class Cart:
    def __init__(self, items=[]):    # ← the bug
        self.items = items
    def add(self, x):
        self.items.append(x); return self

a = Cart(); a.add("apple")
b = Cart()
print(b.items)

Output: ['apple']

Default arguments are evaluated once, when the function is defined — so every Cart() shares the same list object. Fix: def __init__(self, items=None): self.items = list(items) if items else []. This is the most-asked Python gotcha and it is an object-identity question at heart.

Q9 — Python MRO
Python
class A:
    def go(self): print("A")
class B(A):
    def go(self): print("B"); super().go()
class C(A):
    def go(self): print("C"); super().go()
class D(B, C): pass

D().go()

Output: B, C, A

The MRO is D → B → C → A → object. super() does not mean "my parent" — it means "the next class in the MRO of the actual instance's type". So inside B.go, super() resolves to C, not A. This cooperative behaviour is what makes A run exactly once despite being reachable by two paths.

Q10 — try/finally
Java
static int f() {
    try { return 1; }
    finally { System.out.println("finally"); }
}
static int g() {
    int x = 1;
    try { return x; } finally { x = 99; }
}
System.out.println(f()); System.out.println(g());

Output: finally / 1 / 1

finally always runs, but the return value is evaluated and stored before it executes, so mutating x afterwards has no effect. If finally itself contained return 99;, that would override — and would also silently discard any in-flight exception, which is why returning from finally is banned in every style guide.

Q11 — C++ non-virtual destructor
C++
struct Base    { ~Base()    { std::cout << "~Base\n"; } };
struct Derived : Base { ~Derived() { std::cout << "~Derived\n"; } };
Base* p = new Derived();
delete p;

Output: ~Base only — and formally, undefined behaviour.

~Derived never runs, so anything Derived owned leaks. Making ~Base virtual gives the correct ~Derived then ~Base. Rule: any class intended as a polymorphic base needs a public virtual destructor (or a protected non-virtual one, to forbid deletion through a base pointer).

Q12 — String immutability
Java
String s = "hello";
s.toUpperCase();
System.out.println(s);
String t = "a"; for (int i=0;i<3;i++) t += "b";
System.out.println(t);

Output: hello then abbb

toUpperCase() returns a new String and the result is discarded — String methods never mutate. The loop works, but each += builds a new StringBuilder, appends and calls toString(), allocating on every iteration. Use an explicit StringBuilder outside the loop.

§20

The "design a system" round

Low-level design questions — parking lot, library, ATM, elevator, splitwise, chess. They're all the same exercise: turn requirements into classes.

A method that works under pressure

  1. Clarify scope (60 seconds). Ask 2–3 questions and state your assumptions out loud. "Multiple floors? Do we handle payment? Single site or multi-site?" Never start coding immediately.
  2. Find the nouns. They become candidate classes. Parking lot → ParkingLot, Floor, Spot, Vehicle, Ticket, Payment, Gate.
  3. Find the verbs. They become methods: park(), unpark(), issueTicket(), calculateFee().
  4. Fix the relationships. Which are IS-A, which are HAS-A, which are aggregation? Draw it.
  5. Locate the variation points. Anything the requirements say "different kinds of" or "depends on" becomes an interface: fee strategies, spot types, payment methods.
  6. Sanity-check against SOLID. Does one class have three reasons to change? Would adding an EV charging spot require editing existing files?
Java · parking lot skeleton
enum VehicleType { BIKE, CAR, TRUCK, EV }

abstract class Vehicle {                       // IS-A hierarchy
    private final String plate;
    private final VehicleType type;
    protected Vehicle(String p, VehicleType t) { plate = p; type = t; }
    public VehicleType type() { return type; }
}
class Car extends Vehicle { Car(String p){ super(p, VehicleType.CAR); } }

class Spot {                                   // one physical space
    private final String id;
    private final VehicleType fits;
    private Vehicle occupant;                  // null = free
    boolean isFree() { return occupant == null; }
    boolean canFit(Vehicle v) { return isFree() && v.type() == fits; }
}

class Floor { private final List<Spot> spots; }        // COMPOSITION
class ParkingLot { private final List<Floor> floors; } // COMPOSITION

interface SpotAllocationStrategy {             // VARIATION POINT → Strategy
    Optional<Spot> allocate(List<Floor> floors, Vehicle v);
}
class NearestFirst implements SpotAllocationStrategy { }
class LowestFloorFirst implements SpotAllocationStrategy { }

interface FeeStrategy { double fee(Ticket t, Instant exit); }  // another one
class HourlyFee implements FeeStrategy { }
class DayPassFee implements FeeStrategy { }

class Ticket {                                 // the entity linking them
    private final String id; private final Spot spot;
    private final Vehicle vehicle; private final Instant entry;
}

class ParkingService {                         // orchestration; SRP-clean
    private final SpotAllocationStrategy allocator;   // injected → DIP
    private final FeeStrategy fees;
    Ticket park(Vehicle v)          { }
    double unpark(Ticket t)         { }
}
What earns marks
  • Naming the relationship out loud: "Floor to Spot is composition, because a spot has no identity outside its floor."
  • Introducing an interface at each variation point and saying why — "fee rules will change monthly, so I don't want that inside ParkingService."
  • Using an enum for closed sets and an interface for open ones.
  • Mentioning concurrency once: "two cars can't be allocated the same spot, so allocation must be atomic — a lock per floor or a CAS on the spot's state."
  • Saying what you'd defer: "I'd keep payment gateway integration behind a PaymentProcessor interface and not model it further today."
What loses marks

A god class (ParkingLot that parks, prices, prints and persists). Inheritance where composition belongs (class ElectricCarSpot extends Spot extends Floor). Booleans instead of types (isCar, isBike, isTruck as three flags). Beginning to code before asking a single clarifying question.

Rapid-fire cheat sheet

The last 20 minutes before the interview. One line each.

The pillars

Encapsulation → bind state + methods, protect invariants
Abstraction → expose what, hide how
Inheritance → IS-A, reuse + specialise
Polymorphism → one interface, many implementations

Overloading vs overriding

Overload = same name, different params, compile time, same class
Override = same signature, run time, parent→child
Static methods hide · fields shadow · only instance methods dispatch

Abstract class vs interface

Abstract = state + constructor + partial impl, one only
Interface = capability, many, no instance state
Since Java 8: default/static methods; Java 9: private methods

Cannot be overridden

final · static · private · constructors
Cannot be abstract: final, static, private, constructors

Override rules

Same signature · covariant return OK
Access can widen, never narrow
Checked exceptions can narrow, never widen

Diamond problem

C++ → virtual inheritance, one shared base
Java → banned for classes; explicit override for default methods
Python → C3 MRO, base appears once

equals / hashCode

Equal objects MUST have equal hash codes
Unequal objects MAY collide
Break it → object lost inside HashMap

Shallow vs deep

Shallow = references shared (Object.clone, C++ default copy ctor)
Deep = whole graph duplicated
Prefer a copy constructor over clone()

SOLID

S one reason to change · O extend don't modify
L substitutable subtypes · I small interfaces
D depend on abstractions, inject concretes

Patterns by intent

Decorator adds behaviour · Adapter changes interface
Proxy controls access · Facade hides complexity
Strategy chosen by client · State transitions itself

C++ specials

Rule of 0/3/5 · virtual destructor in every polymorphic base
Slicing on pass-by-value · catch by const reference
unique_ptr default, weak_ptr breaks cycles

Java memory

Objects on heap, references on stack
Pass-by-value always (the reference is the value)
GC by reachability, so cycles are collected

Twelve one-line answers

QuestionAnswer
Can a constructor be virtual?No — the object's type isn't established yet, so there's nothing to dispatch on. C++ simulates it with a virtual clone(): the Prototype pattern.
Can an interface have a constructor?No — it has no instance state to initialise and is never instantiated.
Can an abstract class be instantiated?Not directly; only via a concrete subclass, or an anonymous subclass (new Abstract(){ ... }), which is genuinely a new class.
Is Java pass-by-reference?No — pass-by-value, where the value copied is the reference.
Can you overload main?Yes, but the JVM only calls String[].
Multiple inheritance in Java?Of type, yes (interfaces). Of state, no.
Difference between throw and throws?throw raises an instance; throws declares what a method may propagate.
Is an empty class useful?Yes — marker interfaces, exception types that carry meaning by their name alone.
Can a class implement two interfaces with the same method?Yes if abstract (one implementation satisfies both). If both provide conflicting defaults, you must override.
Association vs dependency?Association is a stored structural link (a field); dependency is transient (a parameter or local).
Cohesion vs coupling?Cohesion = how focused one module is (want high). Coupling = how much modules depend on each other (want low).
What is object persistence?Storing object state beyond process lifetime — serialisation, ORM, or a database. Requires deciding identity and how references are represented.

When you don't know something, say so and then reason out loud toward an answer — interviewers score reasoning far above recall. And when you finish an answer, stop talking. Over-explaining a correct answer is the most common way strong candidates lose points.
