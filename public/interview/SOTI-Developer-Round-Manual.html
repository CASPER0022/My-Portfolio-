02 · Tier 1 · highest yield

DSA and the coding round

For a developer panel this is the block that decides most of your score, because it's the only part where they watch you actually build something. Reported SOTI fresher problems cluster around strings, arrays, recursion and hashing, with occasional dynamic programming and graphs.

The pattern map — if you know these eight, you can attempt almost anything they'll ask

1
Hashing / frequency counting

Anagrams, first unique character, two sum, duplicates, group anagrams. The moment you think "I need to look something up fast", reach for a map. Turns O(n²) into O(n).

2
Two pointers

Palindromes, reversing in place, pair sums in a sorted array, removing duplicates. One pointer from each end, or a slow and a fast one.

3
Sliding window

"Longest / maximum / smallest subarray or substring with property X." Expand the right edge, shrink the left when the property breaks.

4
Binary search

Any sorted input, or any "find the smallest value that works" question. Get the lo <= hi and mid update right — that's where people fail, not the concept.

5
Stack

Balanced brackets, next greater element, undo behaviour, expression evaluation. Anything with nesting.

6
Recursion & backtracking

Permutations, subsets, string generation, tree traversal. Always state the base case first, out loud, before writing anything.

7
BFS / DFS on graphs and trees

Shortest path in an unweighted graph is BFS with a queue. Reachability, connected components and cycle detection are DFS with a visited set.

8
Dynamic programming, the easy tier

Fibonacci, climbing stairs, house robber, coin change. The formula: define the state, write the recurrence, add memoisation, then convert to a loop if you want O(1) space.

Space complexity counts too: a hash map that stores every element is O(n) extra space, and "can you do it in O(1) space?" is the standard follow-up. Have an answer ready — usually two pointers, in-place swapping, or an arithmetic trick like the sum formula.

from collections import deque, defaultdict

def max_sum_window(nums, k):                 # sliding window — O(n), not O(n*k)
    if len(nums) < k: return None
    window = sum(nums[:k]); best = window
    for i in range(k, len(nums)):
        window += nums[i] - nums[i - k]          # add the new, drop the old
        best = max(best, window)
    return best

def longest_unique_substring(s):              # sliding window + hash map — O(n)
    last = {}; start = 0; best = 0
    for i, ch in enumerate(s):
        if ch in last and last[ch] >= start:
            start = last[ch] + 1                 # jump the window past the repeat
        last[ch] = i
        best = max(best, i - start + 1)
    return best

def binary_search(nums, target):              # O(log n) — sorted input required
    lo, hi = 0, len(nums) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if nums[mid] == target: return mid
        if nums[mid] < target: lo = mid + 1
        else: hi = mid - 1
    return -1

class Node:
    def __init__(self, val, nxt=None): self.val, self.next = val, nxt

def reverse_list(head):                       # O(n) time, O(1) space — three-pointer walk
    prev = None
    while head:
        head.next, prev, head = prev, head, head.next
    return prev

def to_list(head):
    out = []
    while head: out.append(head.val); head = head.next
    return out

def bfs(graph, start):                        # queue — level by level
    seen, order, q = {start}, [], deque([start])
    while q:
        node = q.popleft(); order.append(node)
        for nb in graph[node]:
            if nb not in seen:
                seen.add(nb); q.append(nb)
    return order

def dfs(graph, node, seen=None):             # recursion — go deep first
    if seen is None: seen = set()
    seen.add(node); order = [node]
    for nb in graph[node]:
        if nb not in seen: order += dfs(graph, nb, seen)
    return order

def climb_stairs(n):                          # DP in O(1) space — it's Fibonacci in disguise
    a, b = 1, 1
    for _ in range(n - 1): a, b = b, a + b
    return b

def group_anagrams(words):                    # hashing on a canonical key
    groups = defaultdict(list)
    for w in words: groups["".join(sorted(w))].append(w)
    return list(groups.values())

  • max window sum → 9. The best three consecutive values are 5+1+3. The point isn't the answer, it's that the window slides: each step adds one element and subtracts one, so you never re-add the middle. The naive version recomputes the whole window every time and is O(n·k).
  • longest unique → 3 then 1. In "abcabcbb" the answer is "abc". The subtle part is last[ch] >= start: a repeat that sits before the current window start must be ignored, otherwise the window jumps backwards. That one condition is the whole difficulty of the problem — mention it and you look like you've actually written this before. "bbbb" gives 1.
  • binary search → 3 and −1. Index 3 holds 7. The second call returns −1 because 4 isn't present, which is the case interviewers check for. Say lo + (hi - lo) // 2 if they ask about overflow in Java or C#, where lo + hi can exceed the integer range.
  • reversed list → [3, 2, 1]. The tuple assignment does the classic three-pointer dance in one line. On paper, write it as three separate statements with a next_node temporary — it's easier to explain and harder to get wrong under pressure.
  • bfs / dfs → different orders from the same graph. BFS visits A, then both its neighbours B and C, then D and E — level by level, using a queue. DFS dives A → B → D → E before backtracking to C, using recursion (the call stack). Being able to say "BFS uses a queue and gives shortest paths in an unweighted graph; DFS uses a stack or recursion" is the answer to a very common question.
  • climb stairs(5) → 8. Ways to reach step n = ways to reach n−1 plus ways to reach n−2, because your last move was either one step or two. That's Fibonacci, and the two-variable loop gives O(n) time in O(1) space. Name the state and the recurrence out loud — that's what DP interviews grade.
  • group anagrams. Sorting each word produces a canonical key, so all anagrams collide in the same bucket. O(n·k log k). The alternative key is a 26-length character count, which is O(n·k) and worth mentioning as the optimisation.

Ask me this

Which data structure would you use, and why?

Have the mapping instant: array for indexed access and cache locality; hash map for O(1) lookup by key, when order doesn't matter; set for membership and de-duplication; stack for nesting and undo; queue for FIFO and BFS; heap for "top k" and priority scheduling; balanced tree / sorted map when you need order and fast lookup; graph for relationships and reachability. Then justify with the operation you need to be fast.

Array vs linked list?

"Arrays give O(1) random access and better cache behaviour, but inserting or deleting in the middle is O(n) because everything shifts. Linked lists give O(1) insertion and deletion once you hold the node, but access is O(n) and every node costs a pointer plus poor locality. In practice I reach for a dynamic array almost always, and a linked list when I'm doing heavy insertion and deletion at known positions — an LRU cache being the classic example, where a hash map plus a doubly linked list gives O(1) for everything."

How does a hash map work internally?

"A hash function turns the key into an index into an array of buckets. Ideally that's O(1). Two keys can hash to the same bucket — a collision — which is handled either by chaining (a list or tree in each bucket) or by open addressing (probe for the next free slot). When the load factor gets too high the table resizes and everything is rehashed, which is why insertion is O(1) amortised rather than guaranteed. Worst case degrades to O(n) if every key collides, which is why keys need a good hash and why mutable objects make bad keys."

Recursion or iteration — which and why?

"Recursion when the problem is naturally self-similar — trees, backtracking, divide and conquer — because the code matches the structure and is far easier to get right. Iteration when depth could be large, because every recursive call consumes stack space and deep recursion means a stack overflow. Python caps recursion around a thousand frames by default, so anything linear over a big input I'd write as a loop."

Your solution works but is O(n²). Improve it.

Run through the standard escalation out loud: "Can I sort first and use two pointers — that's O(n log n)? Can I trade memory for time with a hash map, which usually gets me to O(n)? Is there a sliding window, since I'm looking at contiguous ranges? Can I avoid recomputing by caching sub-results?" Naming the ladder shows method even if you don't land the optimum immediately.

The four pillars — with examples from your own code

Follow-ups to have ready: overloading vs overriding (same name different parameters, resolved at compile time, vs same signature in a child, resolved at run time); abstract class vs interface (shared state and partial implementation, single inheritance, "is-a" vs pure contract, multiple implementation, "can-do"); composition vs inheritance ("has-a" beats "is-a" most of the time, because deep hierarchies become fragile).

SOLID, in plain language

S
Single responsibility

A class should have one reason to change. A route handler that validates input, computes prices, writes to the database and sends an email has four reasons to change — and four ways to break. Split it.

O
Open/closed

Open for extension, closed for modification. Adding a third payment gateway should mean writing a new class that implements the interface, not editing a growing if/else chain inside checkout.

L
Liskov substitution

Anywhere the parent type works, a child must work too, without surprises. If Square extends Rectangle but setting the width secretly changes the height, code written against Rectangle breaks. That's the classic example — use it.

I
Interface segregation

Many small interfaces beat one fat one. Don't force a class to implement methods it has no use for — a read-only report service shouldn't be made to implement delete().

D
Dependency inversion

Depend on abstractions, not concrete classes. Your order service should depend on a PaymentGateway interface, with the concrete Razorpay client injected in. This is the one that makes code testable — you can inject a fake gateway in a unit test. Say that; it connects both JDs in one sentence.

The honest, high-scoring version of the SOLID answer

Don't recite all five and stop. Name them, then say where you fell short: "In SpiceNest my payment route violates single responsibility badly — one handler verifies the signature, computes totals, creates the order, decrements stock and triggers an email. I'd extract a payment verifier, an order service and a notification service. Clean code — the rules they'll expect you to hold

  • Names carry meaning. parseWeightToKg tells you the input, the output and the unit. calc() tells you nothing.
  • Small functions that do one thing. If you need "and" to describe it, it's two functions.
  • No magic numbers. subtotal < 500 should be FREE_SHIPPING_THRESHOLD — one named constant, one place to change it, and the test reads the same word as the code.
  • Comments explain why, not what. The code already says what. A comment earns its place by recording a decision or a trap.
  • Handle errors deliberately. Never swallow an exception silently. Fail with a message someone can act on.
  • Don't repeat yourself — but don't over-abstract either. Two similar things aren't necessarily the same thing; premature abstraction is as expensive as duplication.
  • Consistent formatting, enforced by tooling rather than argued about in review — linters and formatters in the pipeline.

04 · Tier 1 · explicitly required

Data modelling and SQL

The JD asks for "good understanding of data modelling and storage with well-known relational database (preferably SQL)". You have a real eight-table schema you designed yourself, which is a far stronger answer than textbook normalisation. Lead with it.

Modelling — the questions to answer out loud

  1. What are the entities? Nouns in the problem: user, product, order, supplier.
  2. What are the relationships and their cardinality? One-to-many (a user has many orders), many-to-many (a product belongs to many categories — which needs a join table).
  3. What identifies each row? Primary key — surrogate (auto-increment or UUID) or natural (an email). Prefer surrogate: natural keys change.
  4. What must always be true? Constraints: not null, unique, foreign keys, check constraints. Enforce rules in the database, not only in application code — the database is the last line of defence.
  5. What happens on delete? Cascade, set null, or restrict. A deliberate choice, not a default.
  6. What will be queried most? That's where the indexes go.

Your schema as the worked example

Talk through the three decisions that show judgement rather than memorised rules:

  • Order items snapshot the product name and price. Deliberate denormalisation, because an order is a historical record — repricing a product must not rewrite old invoices.
  • The cart's composite unique key (userId, productId, weight) — the same spice in 100g and 250g is two distinct lines, and the database enforces that rather than trusting the application.
  • Soft delete via isArchived, and onDelete: SetNull on order items — a product referenced by past orders can't simply vanish.

Normalisation, quickly

1NF: atomic values, no repeating groups. 2NF: no partial dependency on part of a composite key. 3NF: no transitive dependency — non-key columns depend only on the key. Denormalise deliberately when reads dominate or history must be preserved, and be able to say which you did and why.

The SQL shapes to have in your hand

-- JOIN + aggregate: top customers by spend
SELECT u.name, COUNT(o.id) AS orders, SUM(o."totalAmount") AS spend
FROM "User" u
JOIN "Order" o ON o."userId" = u.id
GROUP BY u.id, u.name
HAVING SUM(o."totalAmount") > 5000
ORDER BY spend DESC;

-- LEFT JOIN + IS NULL: find the orphans (products never ordered)
SELECT p.id, p.name
FROM "Product" p
LEFT JOIN "OrderItem" oi ON oi."productId" = p.id
WHERE oi.id IS NULL;

-- Second highest — the interview classic, two ways
SELECT MAX(price) FROM "Product"
WHERE price < (SELECT MAX(price) FROM "Product");

SELECT DISTINCT price FROM "Product"
ORDER BY price DESC OFFSET 1 LIMIT 1;

-- Duplicates — a data-integrity check worth knowing by heart
SELECT email, COUNT(*) FROM "User"
GROUP BY email HAVING COUNT(*) > 1;

-- Transaction: the fix for SpiceNest's atomicity problem
BEGIN;
  UPDATE "Product" SET stock = stock - 0.25
   WHERE id = 7 AND stock >= 0.25;   -- 0 rows affected = out of stock, roll back
  INSERT INTO "Order" (...) VALUES (...);
COMMIT;

Reading the second-highest queries: the first asks for the largest price strictly below the maximum, and returns NULL instead of erroring when every price is identical — that's the edge case they're probing. The second sorts descending, skips one row and takes the next; the DISTINCT matters, because two products tied at the top would otherwise make the "second highest" the same number.

Reading the transaction: the AND stock >= 0.25 is the whole trick. It makes the check and the update a single atomic operation, so two concurrent buyers can't both pass the check — exactly the race condition in your own checkout flow. If the update affects zero rows, you roll back and tell the customer it's out of stock.

How would you handle a query that's suddenly slow?

"Measure before guessing — run EXPLAIN ANALYZE and look at the plan. A sequential scan on a large table usually means a missing index on the filter or join column. Then check whether the query is doing work it doesn't need: selecting every column, fetching every row instead of paginating, or an N+1 pattern where the application queries once per result. If the plan is fine and it's still slow, it's contention or data volume, and caching or denormalisation comes next."

  • A D C B — the event loop. Synchronous code runs first, so A then D. Then the microtask queue drains, which is where promise callbacks live, giving C. Only then does the event loop take from the macrotask queue, where setTimeout callbacks sit, giving B. setTimeout(fn, 0) does not mean "now" — it means "after the current synchronous work and all pending microtasks". React — the parts they'll probe

  • Why components and one-way data flow? State flows down through props, changes flow up through callbacks, so there's one direction to debug.

What makes an API RESTful

  • Resources, not actions, in the URL. /api/products/7, not /api/getProduct?id=7. The verb is the HTTP method.
  • Stateless. Every request carries what's needed to serve it — which is why the JWT travels in the Authorization header instead of a server-side session.
  • Correct methods and status codes. GET reads and never changes state; POST creates; PUT replaces; PATCH updates part; DELETE removes.
  • Consistent representation — JSON in, JSON out, with a predictable error shape.
  • Cacheable where it makes sense, and layered, so a proxy or load balancer can sit in front without the client knowing.

Authentication concepts

JWT: three base64url parts — header, payload, signature. The server signs it with a secret; anyone can read the payload, so never put secrets in it. The server verifies the signature rather than looking the session up, which makes it stateless and horizontally scalable. The cost is that you can't revoke a token before it expires — hence short-lived access tokens plus refresh tokens in real systems.

Sessions vs tokens: a session ID means server-side state and easy revocation; a token means no server state but harder revocation. Authentication vs authorisation: who you are vs what you're allowed to do — and both must be enforced, on every protected route, server-side.

Hashing passwords: bcrypt with a per-user salt, deliberately slow. Never a fast hash like SHA-256, and never encryption, because passwords should not be recoverable at all.

Idempotency, and why it matters

GET, PUT and DELETE are idempotent — repeating them has the same effect as doing them once. POST isn't, which is exactly why a retried checkout can create two orders. SpiceNest guards this with a unique razorpayOrderId plus an early return when the order already exists. That's a concrete, senior-sounding example of a real distributed-systems concern.

Then a small vertical slice — schema change and migration, API, then UI — behind a flag if it's risky, with tests written alongside rather than after. Small pull requests, reviewed early, instead of a two-week branch that nobody can review properly."

How do you approach debugging a production issue?

The JD says "detect, report, investigate and fix product defects", so have a real method. "Reproduce first, or get as close as I can — exact steps, environment, build, timestamp. Then narrow the layer: is the API response wrong, or is the UI rendering it wrong? If the API is wrong, is the database wrong or the read path — caching is a common culprit, and my own project serves stale stock from an in-process cache. Check logs around the timestamp, and check what changed recently, since most incidents follow a deploy. Fix the cause rather than the symptom, then add the test that would have caught it."

11 · The overlap

The testing a developer must know

Both descriptions ask for it — the developer JD says "automation, including writing unit and integration tests", the SDET JD asks for test design and BDD. If you only revise four things from volume I, make it these.

1 · The test pyramid and what each layer is for

Many unit tests (milliseconds, one function, mocked dependencies), fewer integration tests (real database, several units together), fewest end-to-end tests (slow, brittle, most realistic). The rule: push every check to the lowest level that can prove it. A suite built upside down takes an hour, fails randomly and gets ignored.

2 · What a unit test actually looks like

pricing.test.js — the shape they want to see you know 
import { getWeightAdjustedPrice, shippingFor } from "./pricing.js";

describe("weight-adjusted pricing", () => {
  test("100g is the base price", () => {
    expect(getWeightAdjustedPrice(100, "100g")).toBe(100);
  });

  test("250g is 2.5x with a 5% discount", () => {
    expect(getWeightAdjustedPrice(100, "250g")).toBe(237.5);
  });

  test("an unknown weight should be rejected, not silently priced as base", () => {
    expect(() => getWeightAdjustedPrice(100, "750g")).toThrow();
  });
});

describe("free shipping threshold", () => {
  // boundary value analysis: the bug lives at < versus <=
  test.each([
    [499, 100],
    [500, 0],
    [501, 0],
  ])("subtotal %i charges %i shipping", (subtotal, expected) => {
    expect(shippingFor(subtotal)).toBe(expected);
  });
});

What this demonstrates without you saying it: the arrange-act-assert shape, one behaviour per test, descriptive names that read as sentences, a parameterised table for boundary values, and — in the third test — asserting on a desired behaviour that the current code doesn't have, which is how you encode a bug you intend to fix. If they ask you to write a test on paper, write something with this shape.

3 · Mocking, stubbing and why dependency injection matters

A unit test shouldn't hit the network, the clock or a real database — those make it slow and non-deterministic. You replace them with a fake. That's only possible if the dependency comes in from outside rather than being constructed inside the function, which is the practical payoff of dependency inversion. Say both halves together and you've answered a SOLID question and a testing question at once.

Ask me this

Do you write tests for your own code?

Be honest, then show you know what good looks like: "Not systematically on SpiceNest, and that's a gap I can see clearly now — I tested by using the application rather than by writing tests. What I'd start with is the pure logic: the weight-to-kilogram conversion, the pricing tiers and the shipping threshold, because those are trivially unit-testable and they're where a silent arithmetic bug would cost real money. Then API-level tests on auth and checkout. In my internships I leaned more on evaluation harnesses, because for the AI work correctness was measured statistically rather than asserted exactly."

What's the difference between unit and integration testing?

"A unit test exercises one function or class in isolation with its dependencies replaced by fakes, so it's fast and deterministic and a failure points at one place. An integration test exercises several real components together — my cart route actually writing to and reading from Postgres — so it catches the wiring problems unit tests can't see, at the cost of speed and setup. You need both: unit tests tell you the logic is right, integration tests tell you the pieces actually fit."

How much test coverage is enough?

"Coverage is a useful signal and a terrible target. A hundred percent line coverage with no meaningful assertions proves nothing, and chasing a number produces tests written for the metric. What I'd actually want is that the critical paths — anything touching money, data or authentication — are covered including their failure cases, and that every fixed bug gets a regression test. If I had to name a number for general code I'd say around 70–80% as a health check, with the real judgement being about risk."

The morning checklist

In the room

  • Think out loud. Silence is the only unrecoverable mistake — they can't grade reasoning they can't hear.
  • Ask one clarifying question before starting any problem. It reads as competence, not confusion.
  • When stuck, say where. "I know this needs a hash map, I'm just not seeing how to handle duplicates yet." Interviewers help candidates who narrate.
  • Never bluff. A clean "I don't know, here's how I'd find out" costs one question. A bluff costs their trust in everything you've already said.
  • State complexity unprompted, and name the edge cases you'd test. That one habit satisfies both interviewers at once.
Last thing

You're not walking in as a student who has read about software. You've designed a schema, shipped an API, integrated payments, deployed to a real domain, and then gone back and found what's wrong with all of it. Whichever role they're screening for, that's the story — tell it plainly and let it do the work.
