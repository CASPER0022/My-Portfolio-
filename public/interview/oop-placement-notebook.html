01

Why OOP Exists

Before the four pillars, understand the problem they were invented to solve. Interviewers open here, and a candidate who answers with history instead of a definition immediately sounds different.

The problem: procedural code doesn't scale

In procedural programming (C, Pascal, plain scripts) a program is a list of functions operating on shared data. Data and the code that manipulates it live apart. For a 300-line program that's fine. For a 300,000-line banking system it collapses, because:

  • Any function can modify any data. If a balance goes negative, the culprit could be any of 400 functions. There is no boundary to search within.
  • Change ripples. Adding one field to a struct forces edits everywhere that struct is touched.
  • Nothing is reusable in a meaningful unit. You can copy a function, but a function without its data is half a feature.
  • The code doesn't resemble the problem. The real world has customers, accounts and transactions; the code has arrays and loops. The translation cost is paid on every single change.

The idea: bundle state with the behaviour that owns it

Object-Oriented Programming is a paradigm that organises software as a collection of objects — self-contained units that hold data (state / attributes) and the functions that operate on that data (behaviour / methods) together, and expose only a controlled interface to the outside world.

One sentence for the interview: “OOP models a program as interacting objects, where each object owns its data and is the only thing allowed to change it.” Everything else — encapsulation, inheritance, polymorphism, abstraction — is machinery that makes that idea practical.

OOP is not universally better. It adds indirection, object allocation cost and deep hierarchies that can obscure control flow. Interview questions — Section 01

Q1What is Object-Oriented Programming?

OOP is a programming paradigm that structures a program as a collection of objects. Each object bundles state (fields) with the behaviour that acts on that state (methods), and exposes only a controlled public interface. It rests on four pillars — abstraction, encapsulation, inheritance and polymorphism — which together give code that mirrors the real-world domain, resists accidental corruption, and can be extended by adding classes rather than editing existing ones.

Q2Why do we need OOP at all — what was wrong with procedural code?

Procedural code separates data from the functions that use it, so any function can mutate any data. In a large codebase this means no bug has a bounded search space, every schema change ripples across the program, and reuse is limited to isolated functions. OOP draws a boundary around each piece of state and makes exactly one class responsible for it. That gives us maintainability, safe reuse and a design that matches the problem domain — which is what actually reduces cost as a system grows.

Q3What are the four pillars of OOP? Define each in one line.
  • Encapsulation — binding data and methods into a single unit and restricting direct access to the data.
  • Abstraction — exposing only essential features and hiding implementation complexity.
  • Inheritance — deriving a new class from an existing one to reuse and extend its members.
  • Polymorphism — one interface taking many forms, so the same call behaves differently depending on the actual object.
Q4Is Java a pure object-oriented language?

No. A pure OO language would treat everything as an object. Java has eight primitive types (int, char, boolean, etc.) that are not objects, it has static members that belong to the class rather than an instance, and its operators are not defined on objects. Languages closer to “pure” are Smalltalk and Ruby, where even 3 is an object. C++ is even less pure — it permits fully procedural programs with free functions and a bare main.

Q5What is message passing in OOP?

Objects do not read each other's internals; they communicate by invoking each other's methods, which is conceptually sending a message that names an operation plus arguments. The receiving object decides how to respond. This is what makes polymorphism possible: the sender names what it wants (shape.draw()), and the receiver decides how. It also makes objects loosely coupled, since only the message signature is shared, not the implementation.

Q6When would you NOT use OOP?

When the problem has no meaningful long-lived entities with invariants to protect. Pure data transformation (ETL pipelines, numeric kernels, compilers' optimisation passes) is often cleaner in a functional or procedural style. Systems with hard memory or latency budgets — embedded firmware, OS kernels, game engine hot loops — avoid virtual dispatch and heap-allocated object graphs. A good answer names the cost: indirection, allocation, and hierarchies that hide control flow.

02

Classes & Objects

The atoms of the paradigm. Nearly every interview begins with class vs object, and a surprising number of candidates lose the plot on where objects actually live in memory.

Class = blueprint, object = instance

A class is a user-defined type: a template that declares what data an object of that type will hold and what operations it supports. It occupies no memory for instance data — it is a specification. An object is a concrete instance created from that class at runtime, with its own copy of the instance fields and its own identity.

The standard analogy: a class is the architectural plan of a house; an object is a house built from it. Ten houses can share one plan and still be painted different colours — that colour is instance state.

Where objects live: stack vs heap

This is the question that separates the memorisers from the rest.

  • In Java, new always allocates the object on the heap. The variable a is a reference stored on the stack (if it's a local variable) that points at the heap object. There is no way to place an object on the stack.
  • In C++ you choose. BankAccount a("Aswin", 5000); puts the object on the stack and destroys it automatically when scope ends. BankAccount* p = new BankAccount(...); puts it on the heap and you must delete it (or use a smart pointer).
  • In Python, everything is a heap object and variables are names bound to references; lifetime is managed by reference counting plus a cycle collector.

Interview questions — Section 02

Q1Difference between a class and an object.

A class is a blueprint / user-defined type declared once at compile time; it describes structure and behaviour but holds no instance data. An object is a runtime instance of that class with its own memory for instance fields and its own identity. One class produces many objects; changing one object's state does not affect another. Classes are declared, objects are constructed.

Q2Where are objects stored in memory in Java?

Every object created with new lives on the heap, which is shared across threads and managed by the garbage collector. The reference to it is stored wherever the variable is declared — on the thread's stack for a local variable, inside the enclosing object on the heap for a field. Class metadata, bytecode and static variables live in the method area / metaspace. In C++ you can additionally place an object directly on the stack, which is why C++ has destructors that fire deterministically at scope exit.

Q3What is the difference between a static and an instance variable?

A static variable has exactly one copy shared by every object of the class, is created when the class is loaded, and is accessed through the class name. An instance variable gets a fresh copy inside every object, is created when the object is constructed, and is accessed through a reference. Use static for data that belongs to the type — a counter of created objects, a configuration constant — and instance for data that describes one particular object.

Q4What does the this keyword do?

this is an implicit reference to the object on which the current instance method or constructor is executing. Three real uses: (1) disambiguating a field from a parameter of the same name (this.name = name); (2) calling another constructor of the same class as the first statement, this(...) — constructor chaining; (3) passing the current object to another method, or returning it to enable a fluent/builder API. It is unavailable in static context.

Q5Can a class exist without any object? Can an object exist without a class?

Yes to the first — a class is a type definition and is perfectly valid with zero instances; utility classes like java.lang.Math are designed never to be instantiated. No to the second in class-based languages: every object is an instance of some class, and even an anonymous class silently creates a class behind the scenes. (Prototype-based languages like JavaScript are the exception — objects there clone other objects and no class is required.)

Q6What is an anonymous / inner class and why use it?

An inner class is a class declared inside another class; a non-static inner class holds an implicit reference to its outer instance and can read its private fields, which is why it's used for tightly-coupled helpers such as a Node inside a LinkedList. An anonymous class is a one-off class defined and instantiated in a single expression, typically to supply an implementation of an interface at the point of use (a comparator, an event listener). It exists to avoid naming a class you will only ever use once. Lambdas replaced most anonymous-class use in modern Java.

Q7What is the difference between a class and a structure (C++)?

Technically the only difference in C++ is the default access level: members of a struct are public by default, members of a class are private; the same applies to default inheritance access. Everything else — constructors, methods, inheritance, polymorphism — works identically. By convention, struct is used for passive data aggregates and class for types with invariants and behaviour. In C, a struct cannot contain functions at all.

Q8What is an object's identity, state and behaviour?

Three properties every object has. Identity — what makes it distinguishable from every other object even if the contents match (in Java, its reference; compared with ==). State — the current values of its fields, which change over its lifetime. Behaviour — the operations it can perform, defined by its methods. Two accounts with identical balances have equal state but different identity.

03

Constructors & Object Lifecycle

Constructors are guaranteed-invoked initialisation code. Panels probe here because the rules are precise and easy to get half-right.

What a constructor is

A constructor is a special method invoked automatically when an object is created. Its job is to leave the object in a valid state — every invariant satisfied — before anyone can use it. Rules:

  • Its name is exactly the class name.
  • It has no return type, not even void. (Writing void turns it into an ordinary method — a favourite trick question.)
  • It is called once, at creation, and cannot be called again on an existing object.
  • It can be overloaded, and it can be private.
  • It is not inherited, so it cannot be overridden.

The rule to state out loud

Construction runs top-down: the base-class constructor completes before the derived constructor body begins, because a derived object physically contains a base sub-object that must be valid first. Destruction in C++ runs the reverse, bottom-up: derived destructor, then base.

Destruction: C++ vs Java

C++ has a destructor ~ClassName(): no arguments, no return type, cannot be overloaded, and called deterministically when a stack object leaves scope or delete is called. This underpins RAII (Resource Acquisition Is Initialization) — acquire a file handle or lock in the constructor, release it in the destructor, and it is impossible to leak even if an exception is thrown.

Java has no destructor. The garbage collector reclaims unreachable objects at an unpredictable time. finalize() existed for cleanup but is deprecated and must never be relied on. The correct Java idiom is try-with-resources over the AutoCloseable interface.

Interview questions — Section 03

Q1What is a constructor and how does it differ from a method?

A constructor initialises a newly created object and is invoked implicitly by new. Differences from a method: it must share the class's name, it has no return type, it cannot be inherited or overridden, and it can never be called explicitly on an existing object. A method has any name, must declare a return type, is called explicitly, and can be inherited and overridden.

Q2Can a constructor be private? Why would you do that?

Yes. A private constructor prevents outside code from instantiating the class, which is exactly what you want for: a Singleton (the class itself controls the single instance), a static utility class like Math that should never be instantiated, a Builder where objects are produced only through the builder, and static factory methods such as valueOf() that want to cache or return subtypes.

Q3Can a constructor be final, static or abstract?

No to all three, and each has a distinct reason. final prevents overriding, but constructors are never inherited so there is nothing to prevent. static means “no current object”, yet a constructor's entire purpose is to initialise the current object. abstract means “implemented by a subclass”, but a constructor is not inherited, so no subclass could ever supply the body.

Q4What is constructor chaining?

Calling one constructor from another so initialisation logic is written once. Within the same class you use this(args); to invoke the superclass constructor you use super(args). Either call must be the first statement in the constructor, and you cannot use both in the same constructor. If you write neither, the compiler silently inserts super() — which is why a parent with no no-arg constructor forces every child constructor to call super(...) explicitly.

Q5Default constructor vs no-argument constructor — are they the same?

Not quite. A no-argument constructor is any constructor you write that takes no parameters. A default constructor is one the compiler generates for you, and only when you have declared no constructor whatsoever; it is a no-arg constructor whose body just calls super(). The moment you write any constructor — even a parameterised one — the compiler stops generating it, so new MyClass() then fails to compile.

Q6What is a destructor? Does Java have one?

A destructor is a special member function called automatically when an object is destroyed, used to release resources. In C++ it is ~ClassName(), it takes no parameters, cannot be overloaded, and fires deterministically at scope exit or on delete. Java has no destructor — memory is reclaimed by the garbage collector at an unspecified time. finalize() was the nearest equivalent and is deprecated because it is unpredictable and can resurrect objects; the correct approach is AutoCloseable with try-with-resources, or an explicit close().

Q7Why must a base class destructor be virtual in C++?

If you delete a derived object through a base-class pointer and the base destructor is not virtual, the behaviour is undefined — in practice only the base destructor runs, so the derived class's members and resources are never released, leaking memory. Declaring the base destructor virtual makes the deletion dispatch through the vtable, so the derived destructor runs first, then the base's. Rule: any class intended as a polymorphic base needs a virtual destructor (or a protected non-virtual one, if deletion through the base is meant to be forbidden).

Q8What is RAII?

Resource Acquisition Is Initialization — a C++ idiom that ties a resource's lifetime to an object's lifetime. You acquire the resource (memory, file, mutex, socket) in the constructor and release it in the destructor. Because C++ guarantees destructors run on scope exit, including during exception unwinding, the resource cannot leak. std::unique_ptr, std::lock_guard and std::fstream are all RAII wrappers. Java's closest analogue is try-with-resources, and Python's is the with statement over a context manager.

Q9What happens if a constructor throws an exception?

The object is never fully created and the reference is never assigned. In C++, any fully-constructed member sub-objects and base sub-objects are destroyed in reverse order, but the object's own destructor does not run — which is why raw resources acquired in a constructor should be held by RAII members. In Java, the partially built object becomes unreachable and eligible for garbage collection. This is the reason validation belongs in the constructor: failing fast there guarantees no invalid object ever escapes.

Encapsulation

The pillar that protects data. Easy to define, easy to demonstrate badly — most candidates write a getter/setter pair and call it encapsulation, which is precisely what interviewers push back on.

Definition

Encapsulation is the bundling of data and the methods that operate on it into a single unit (the class), combined with restricting direct access to that data from outside. The outside world can only change state through methods that enforce the class's rules.

The mechanism is access modifiers. The payoff is that every invariant — “balance can never be negative”, “age is between 0 and 130” — has exactly one place to be enforced.

Python has no enforcement at all: a single underscore _x is a convention meaning “internal”, and a double underscore __x triggers name mangling to _ClassName__x, which discourages but does not prevent access.

The push-back you must survive

“If you add a public getter and setter for every private field, haven't you just made it public with extra steps?” Largely yes. That is called an anaemic model. Real encapsulation means (1) not every field gets an accessor, (2) setters validate rather than blindly assign, and (3) you prefer intent-revealing operations — giveRaise(10), withdraw(500) — over raw setters, because those express a rule the class owns. Saying this unprompted is a strong signal.

Immutability: encapsulation taken to its conclusion

An immutable object cannot change after construction, so there is no invalid state to defend against and it is automatically thread-safe. To make a class immutable in Java: declare the class final, make all fields private final, provide no setters, and defensively copy any mutable field on the way in and on the way out.

Interview questions — Section 04

Q1What is encapsulation? Give a real-world example.

Encapsulation binds data and the methods that act on it into one unit and restricts direct external access to that data, so all changes flow through methods that enforce the class's rules. Real-world example: an ATM. You press “withdraw”; you cannot open the machine and take cash directly. The machine validates your PIN, checks the balance, dispenses, and logs — the internal cash tray is private, the button panel is the public interface.

Q2How do you achieve encapsulation in Java?

Declare every instance field private, and expose controlled public methods for the operations the class legitimately supports. Getters return state (defensively copied if mutable); setters or, better, domain methods validate before mutating. Fields that shouldn't be readable get no getter at all; fields that shouldn't change after construction get no setter and are marked final.

Q3Encapsulation vs abstraction — both hide things, so what's the difference?

Abstraction hides complexity and is a design-level decision about what to expose — you use an interface so the caller sees behaviour without implementation. Encapsulation hides data and is an implementation-level mechanism about how access is restricted — you use access modifiers so state cannot be corrupted. A car gives you a steering wheel and hides the steering mechanism (abstraction); it also seals the engine so you can't reach in and change the fuel mixture (encapsulation).

Q4What is data hiding, and is it the same as encapsulation?

Data hiding is the specific act of making members inaccessible from outside — the private part. Encapsulation is the broader concept: hiding plus bundling the data with the methods that manage it. So data hiding is one component of encapsulation, not a synonym. A class with private fields and no methods hides data but doesn't encapsulate anything useful.

Q5Explain the four access modifiers in Java.

private — visible only inside the declaring class; the default choice for fields. default (write nothing) — visible within the same package; useful for package-internal collaboration. protected — same package plus subclasses in other packages; intended for members a subclass must extend. public — visible everywhere; reserve it for the deliberate API. The guiding rule is always use the most restrictive modifier that works, because anything public becomes a contract you cannot change later.

Q6Can a class be private in Java?

A top-level class can only be public or package-private (default) — private would make it unusable by anyone, which is meaningless. A nested/inner class can be private, and commonly is: a private static nested Node class inside a LinkedList is a real implementation detail that should be invisible outside.

Q7What is an immutable object and how do you create one?

An object whose state cannot change after construction. In Java: mark the class final so it can't be subclassed and weakened, make all fields private final, set them only in the constructor, provide no setters, and defensively copy mutable fields both when accepting them and when returning them. Benefits: inherently thread-safe, safe to use as a HashMap key, cacheable and freely shareable. String, the wrapper classes and LocalDate are the standard examples; Java records give you most of this automatically.

Q8Why is String immutable in Java?

Four reasons worth naming. String pool — identical literals share one object, which is only safe if nobody can mutate it. Security — file paths, URLs and credentials are passed as Strings; if a String could be mutated after a security check, it could be changed before use. Hashing — the hash code is cached, making Strings efficient and reliable as HashMap keys. Thread safety — immutable objects need no synchronisation.

Q9Are getters and setters always good practice?

No. Mechanically generating a getter and setter for every field defeats the purpose — the fields become effectively public and the class becomes a data bag with no behaviour (an “anaemic domain model”). Better practice: expose only the accessors the outside world genuinely needs, validate inside setters, and prefer methods that name a domain operation (account.withdraw(amount)) over setBalance(), so the rules governing the change live inside the class that owns the data.

Abstraction

Hiding how, exposing what. In code this becomes the abstract-class-versus-interface question, which appears in roughly every second OOP interview.

Definition

Abstraction is the process of exposing only the essential characteristics of an object while hiding the implementation details. You drive a car through a steering wheel, pedals and gear stick; you are not required to know about fuel injection to use it. The interface is small and stable, the implementation is large and free to change.

Two levels are worth distinguishing when you answer:

  • Data abstraction — a type exposes operations, not representation. A Stack guarantees push/pop/peek; whether it's an array or a linked list is invisible.
  • Control abstraction — a method hides a sequence of steps. Collections.sort(list) hides which algorithm runs.

Abstract classes

An abstract class is a class that cannot be instantiated and may declare abstract methods — methods with a signature but no body, which every concrete subclass must implement. It exists to define a partially-built template: shared state and shared implementation live in the parent, and the genuinely varying parts are left abstract.

Interfaces

An interface is a pure contract: a set of method signatures a class promises to provide. It describes a capability (“can be compared”, “can be serialised”, “can fly”) rather than an identity. A class can implement many interfaces but extend only one class, which is how Java gets the benefits of multiple inheritance without the diamond problem.

Modern Java interfaces have grown: since Java 8 they can have default methods (with a body, for backwards-compatible evolution) and static methods; since Java 9, private methods to share code between defaults. Fields in an interface are always public static final.

Interview questions — Section 05

Q1What is abstraction? How is it implemented in Java and C++?

Abstraction exposes only the essential behaviour of an object and hides its implementation, reducing what a user must understand and letting the implementation change freely. In Java it is implemented with abstract classes (partial abstraction — some methods implemented) and interfaces (near-total abstraction). In C++ it is implemented with pure virtual functions (virtual void draw() = 0;); a class with at least one pure virtual function is an abstract class, and one with only pure virtual functions and no data is the C++ equivalent of an interface.

Q2Abstract class vs interface — when do you choose each?

Choose an abstract class when the subtypes are closely related and share state or implementation, and when you want to evolve the base later without breaking subclasses — e.g. Payment with a shared amount field and a fixed processing skeleton. Choose an interface when unrelated classes need the same capability, when you need a class to take on multiple roles, or when you want callers decoupled from any implementation — e.g. Comparable, Runnable, a PaymentGateway port. Practical rule: interface for the contract, abstract class for shared code beneath it.

Q3Can an abstract class have a constructor? Can it have zero abstract methods?

Yes to both. An abstract class can — and usually should — have a constructor, because it holds fields that subclasses must initialise; it runs when a subclass constructor calls super(), even though the abstract class itself is never instantiated directly. An abstract class with no abstract methods is also legal; you'd declare it abstract purely to prevent direct instantiation while still providing shared behaviour.

Q4Can an abstract class be final? Can an abstract method be private or static?

No, in every case, and the reason is the same each time: abstract means “must be completed by a subclass”. final forbids subclassing, so abstract final is a contradiction. private hides the method from subclasses, so none could implement it. static binds the method to the class at compile time, which is incompatible with the runtime overriding an abstract method requires. Likewise abstract synchronized is illegal — there is no body to synchronise.

Q5What is a pure virtual function and an abstract class in C++?

A pure virtual function is a virtual function declared with = 0 and (usually) no body: virtual double area() const = 0;. Any class containing at least one becomes an abstract class and cannot be instantiated, though it can still have data members, constructors and implemented methods. Derived classes must override every pure virtual function or they remain abstract too. A class with only pure virtual functions and a virtual destructor is how C++ expresses an interface.

Q6Can an interface extend another interface? Can it extend a class?

An interface can extend one or more interfaces — interface A extends B, C {} is legal and is how Java composes contracts. An interface cannot extend a class, because a class carries implementation and state that an interface has no way to hold. Conversely a class implements interfaces and extends exactly one class.

Q7What is a functional interface and a marker interface?

A functional interface has exactly one abstract method, which makes it a valid target for a lambda expression or method reference — Runnable, Comparator, Predicate. The @FunctionalInterface annotation is optional but makes the compiler enforce the single-method rule. A marker interface has no methods at all and exists purely to tag a class with metadata the runtime or a library checks — Serializable, Cloneable. Annotations have largely replaced markers in modern code.

Q8Why were default methods added to interfaces in Java 8?

For backward-compatible interface evolution. Before Java 8, adding a method to an interface broke every existing implementation. Java 8 needed to add stream(), forEach() and others to Collection without breaking the millions of classes already implementing it, so default methods let an interface ship an implementation that existing classes inherit for free. The side effect is that interfaces now support a limited form of multiple inheritance of behaviour — which reintroduced a version of the diamond problem, resolved by an explicit compiler rule (see Section 06).

Q9Can you instantiate an interface or an abstract class?

Not directly — new Runnable() or new Payment(100) won't compile. But you can write new Runnable() { public void run() { ... } }, which looks like instantiating the interface and is actually creating an anonymous class that implements it and instantiating that. You can also hold a reference of an abstract or interface type pointing at a concrete object — Payment p = new UpiPayment(500); — which is the whole basis of polymorphism.

Inheritance

Reuse by specialisation — and the pillar most often misused. Expect questions on the types of inheritance, the diamond problem, and why Java refused multiple class inheritance.

Definition and vocabulary

Inheritance lets a new class (child / derived / subclass) acquire the fields and methods of an existing class (parent / base / superclass), then add to or specialise them. It models an IS-A relationship: a Car IS-A Vehicle, so anywhere a Vehicle is expected a Car can be used.

Two benefits: code reuse (write shared behaviour once) and, more importantly, subtype polymorphism (a base reference can hold any derived object). The second is what makes extensible design possible.

What is and isn't inherited (Java)

The diamond problem

If B and C both inherit from A and both override greet(), then a class D inheriting from both B and C creates an ambiguity: which greet() does d.greet() call? There is also a data problem — D would contain two copies of A's fields.

How each language answers:

  • C++ — permits it, and solves the data duplication with virtual inheritance (class B : virtual public A), which makes D share a single A sub-object. Method ambiguity must still be resolved explicitly (d.B::greet()).
  • Java — forbids multiple class inheritance entirely, so the problem cannot arise. A class may implement many interfaces because, pre-Java 8, interfaces carried no implementation and no state, so there was nothing to conflict.
  • Python — permits it and resolves order deterministically via the MRO (Method Resolution Order), computed by the C3 linearisation algorithm and visible through ClassName.__mro__.
Java 8 brought the diamond back — and fixed it by rule

Since interfaces can now have default methods, two interfaces can supply conflicting bodies. Java resolves it with three precedence rules: (1) a class's own method always wins over any inherited default; (2) a more specific sub-interface wins over a super-interface; (3) if still ambiguous, compilation fails and you must disambiguate explicitly with InterfaceName.super.method().

When inheritance is the wrong tool

Inheritance is the tightest coupling in OOP: the subclass depends on the parent's implementation, not just its interface, so a change in the parent can silently break every child (the fragile base class problem). Use it only when the IS-A relationship is genuinely true and permanent. Otherwise use composition — see Section 09.

The classic wrong hierarchy

class Square extends Rectangle. Mathematically a square is a rectangle, so it feels right. But Rectangle has setWidth and setHeight as independent operations, and Square must keep them equal — so code that sets width to 5 and height to 4 and then asserts area is 20 breaks for a Square. That is a Liskov Substitution violation (Section 12). IS-A must hold for behaviour, not just for nouns.

Interview questions — Section 06

Q1What is inheritance and what are its types?

Inheritance lets a derived class acquire the members of a base class, modelling an IS-A relationship and enabling reuse plus subtype polymorphism. Types: single (one parent), multilevel (a chain, A→B→C), hierarchical (several children of one parent), multiple (one child, several parents), and hybrid (a combination). Java supports the first three for classes and achieves multiple/hybrid through interfaces; C++ and Python support all five.

Q2Why doesn't Java support multiple inheritance of classes?

To avoid the diamond problem and the complexity it brings. If a class inherited from two parents that both define the same method, the compiler could not decide which to run, and the object would carry two copies of the shared grandparent's state. C++ solves this with virtual inheritance and explicit qualification, but at a real cost in language and compiler complexity. Java's designers chose simplicity: single class inheritance for state and implementation, multiple interface implementation for contracts — which gives most of the benefit with none of the ambiguity.

Q3Java 8 interfaces have default methods with bodies. Doesn't that bring the diamond problem back?

It brings back the method ambiguity, but not the state ambiguity — interfaces still cannot hold instance fields, so there is never duplicated data. The method conflict is resolved by explicit rules: the implementing class's own method wins; otherwise the most specific interface wins; otherwise the code does not compile until you override the method and disambiguate with Walker.super.move(). Java forces the ambiguity to be resolved by the programmer rather than resolving it silently.

Q4What does super do?

Three uses. super(args) invokes a superclass constructor and must be the first statement in the subclass constructor. super.method() invokes the parent's version of an overridden method — useful when you want to extend rather than replace behaviour. super.field accesses a parent field that the subclass has shadowed with a same-named field. Note that super is unavailable in a static context, for the same reason this is.

Q5Are private members inherited?

Strictly, no — a private member is not accessible in the subclass and is not part of its inherited API. But it is important to add that the private field still physically exists inside the subclass object, because the object contains a complete parent sub-object; the subclass simply cannot name it. It can be reached indirectly through a public or protected accessor the parent provides. Saying both halves shows you understand memory layout, not just the access rule.

Q6What is the diamond problem and how does C++ solve it?

When D inherits from B and C, which both inherit from A, D receives two copies of A's members and two candidate versions of any method A declared — so a call is ambiguous. C++ solves the duplicated-state half with virtual inheritance: declaring class B : virtual public A and class C : virtual public A makes both share a single A sub-object, so D contains exactly one A, and D becomes responsible for initialising it. Ambiguous method calls must still be qualified explicitly, e.g. d.B::greet().

Q7Can a constructor be inherited? What about static methods?

Constructors are not inherited — each class declares its own, and a subclass constructor invokes the parent's via super(). Static methods are inherited in the sense that a subclass can call them, but they are not overridden: declaring a static method with the same signature in the subclass hides the parent's. The distinction matters because hiding is resolved at compile time by the reference type, whereas overriding is resolved at runtime by the object type.

Q8What is the fragile base class problem?

Because a subclass depends on the parent's implementation and not only its interface, a seemingly safe change inside the parent can break subclasses that relied on the old internal behaviour. The canonical case: a collection's addAll() internally calls add(); a subclass that overrides both to count elements ends up double-counting, and a later refactor of the parent silently changes the count again. It is the strongest practical argument for favouring composition, and for designing base classes deliberately — documenting self-calls or making methods final.

Q9What is the purpose of the final keyword?

It means “cannot be changed”, with a different meaning per target. A final variable can be assigned once — a final reference can still have the object it points to mutated, only the binding is fixed. A final method cannot be overridden, which locks behaviour subclasses might otherwise break. A final class cannot be extended, used for security and immutability (String) and for value types. The C++ equivalents are const for variables and the final specifier on methods and classes since C++11.

Polymorphism

One interface, many forms. If you master only one section for the interview, make it this one — overloading vs overriding is the single most-asked OOP question.

Two kinds

Resolved at compile time

Static / compile-time polymorphism

Also called early binding. Achieved by method overloading and, in C++, operator overloading. The compiler picks the target from the argument types.

Resolved at run time

Dynamic / runtime polymorphism

Also called late binding or dynamic dispatch. Achieved by method overriding. The JVM/vtable picks the target from the actual object.

Overloading

Overloading means several methods in the same class share a name but differ in their parameter list — different count, different types, or different order. Return type alone is not enough to overload; the compiler cannot choose based on it.

Overriding

Overriding means a subclass supplies its own implementation of a method already defined in its superclass, with the same name, same parameter list and a compatible return type. The choice of which body runs is made at runtime from the object's actual class, not from the reference type.

Rules for a valid override (Java)

  1. Same method name and same parameter list.
  2. Return type identical, or a covariant subtype — if the parent returns Shape, the child may return Circle.
  3. Access may widen but never narrow: protected → public is fine, public → protected is a compile error.
  4. May throw fewer or narrower checked exceptions; may not add new or broader ones. Unchecked exceptions are unrestricted.
  5. final, static and private methods cannot be overridden. Constructors cannot be overridden.
  6. Use @Override — it costs nothing and turns a typo from a silent bug into a compile error.
The trap that catches almost everyone

In Java, fields are not polymorphic. Field access is resolved at compile time from the reference type; method calls are resolved at runtime from the object type. So with Parent p = new Child();, p.x gives the Parent's x, while p.show() runs the Child's show(). Static methods behave like fields here — they are hidden, not overridden.

Upcasting and downcasting

Upcasting (child reference → parent reference) is implicit and always safe: Shape s = new Circle(2);. Through s you can only call methods declared on Shape, but overridden ones dispatch to Circle.

Downcasting (parent reference → child reference) must be explicit and can fail at runtime with a ClassCastException. Guard it with instanceof, or better, use Java 16+ pattern matching: if (s instanceof Circle c) { c.radius(); }. Frequent downcasting is usually a smell that a method is missing from the base type.

Interview questions — Section 07

Q1What is polymorphism? Explain its types with examples.

Polymorphism — literally “many forms” — lets one interface serve many underlying types, so the same call produces different behaviour depending on the object. Compile-time polymorphism is achieved by method overloading (and operator overloading in C++); the compiler selects the method from the argument types, e.g. add(int,int) vs add(double,double). Runtime polymorphism is achieved by method overriding; the actual object determines the method, e.g. a Shape reference holding a Circle runs Circle.area(). The second is what makes code extensible — you add a new subclass without touching the calling code.

Q2Difference between method overloading and overriding.

Overloading is same name, different parameter list, same class, resolved by the compiler — it is a convenience for related operations and needs no inheritance. Overriding is same name, same parameter list, subclass replacing a parent method, resolved at runtime by the object's actual type — it requires inheritance and is what delivers runtime polymorphism. Return type alone cannot distinguish overloads; an override may return a covariant subtype, may not narrow access, and may not add broader checked exceptions.

Q3Can you override a static method? What happens if you try?

No. Declaring a static method in the subclass with the same signature performs method hiding, not overriding. The difference is observable: hiding is resolved at compile time from the reference type, so Parent p = new Child(); p.staticMethod(); runs the Parent's version. Overriding would run the Child's. Static methods belong to the class and are invoked without an object, so there is no object type to dispatch on. Adding @Override to a static method is a compile error — a useful way to prove the point.

Q4Can you override a private or final method?

Neither. A private method is invisible to the subclass, so defining a method with the same signature simply creates a brand-new unrelated method — no polymorphism, and @Override would fail to compile. A final method is explicitly sealed against overriding; the compiler rejects any attempt. Both are sometimes deliberate design choices: marking a method final protects an invariant that subclasses could otherwise break.

Q5What is dynamic method dispatch?

The mechanism by which a call to an overridden method is resolved at runtime rather than compile time. The compiler verifies that the method exists on the reference's declared type; the JVM then looks at the object actually referenced and invokes that class's implementation, using the object's method table. This is why Shape s = new Circle(2); s.area(); runs Circle.area(). It is the runtime foundation of the Open/Closed Principle.

Q6What is covariant return type?

A relaxation added in Java 5 that lets an overriding method return a subtype of the parent method's return type. If Animal reproduce() is declared in Animal, then Dog may override it as Dog reproduce(). This is type-safe because any caller expecting an Animal still receives one, and it removes the need for the caller to downcast. It is heavily used in clone() implementations and fluent builders.

Q7Is operator overloading supported in Java?

No — Java deliberately omits user-defined operator overloading. The single exception is + for String concatenation, which is built into the language rather than user-definable. C++ and Python support it fully (operator+, __add__). Java's designers left it out because overloaded operators frequently obscure meaning — a reader cannot tell whether a + b is arithmetic or an expensive network call — and they judged the readability cost higher than the expressive benefit.

Q8Explain upcasting and downcasting.

Upcasting converts a subclass reference to a superclass reference. It is implicit and always safe because the IS-A relationship guarantees the object supports the base type's interface; you lose access to subclass-specific methods but overridden methods still dispatch dynamically. Downcasting converts back to the subclass type; it must be written explicitly and throws ClassCastException if the object isn't actually of that type. Always guard with instanceof — and treat repeated downcasting as a design smell suggesting a missing abstraction.

Q9What is early binding vs late binding?

Early (static) binding resolves a call at compile time using the declared type — applies to overloaded methods, static methods, private methods, final methods and field accesses. It is faster because the target address is fixed and the call can be inlined. Late (dynamic) binding defers resolution to runtime using the object's actual type — applies to overridden instance methods (in C++, only those declared virtual). It costs one indirection through the method table, and buys extensibility.

Q10Why is polymorphism useful in practice? Give a concrete case.

It removes conditional chains and makes code extensible without modification. Without it, a payment processor has if (type == CARD) ... else if (type == UPI) ... else if (type == WALLET) ..., and every new payment method means editing and re-testing that method. With polymorphism you define a PaymentMethod interface and call method.pay(amount); adding wallet support means adding one class and zero edits to existing tested code. That is the Open/Closed Principle in action, and it's the answer that connects the pillar to real engineering value.

Under the Hood: vtable, vptr & Dispatch

How runtime polymorphism actually works in memory. Asked in C++-oriented interviews and in any round where the panel wants to separate depth from surface knowledge.

The mechanism

When a C++ class declares at least one virtual function, the compiler builds a vtable (virtual table) — a static, per-class array of function pointers, one slot per virtual function. Every object of such a class carries a hidden pointer, the vptr, set during construction to point at its class's vtable.

A call like shape->area() compiles not to a fixed address but to roughly: follow the object's vptr to the vtable, jump to slot 2, call it. The slot index is fixed at compile time; the table it lands in is decided at runtime by what the object actually is. That indirection is the entire cost of runtime polymorphism — one pointer dereference plus an indirect call, and it blocks inlining.

Java is different by default

C++ methods are non-virtual unless you say virtual; you opt in to polymorphism. Java instance methods are virtual by default; you opt out with final, private or static. The JVM uses an equivalent per-class method table, and the JIT often removes the indirection entirely when it proves only one implementation is loaded — a technique called monomorphic inline caching.

Interview questions — Section 08

Q1What is a virtual function?

A member function declared virtual in a base class, signalling that derived classes may override it and that calls through a base pointer or reference must be resolved by the actual object type at runtime rather than the pointer's declared type. Without virtual, C++ binds the call at compile time and the base version always runs, even for a derived object. In Java every non-static, non-final, non-private method is implicitly virtual.

Q2Explain vtable and vptr.

The vtable is a compiler-generated array of function pointers, created once per class that has virtual functions, with one slot per virtual function pointing at the most-derived implementation for that class. The vptr is a hidden pointer added to every object of such a class, initialised by the constructor to point at that class's vtable. A virtual call dereferences the vptr, indexes a fixed slot, and calls through that pointer — so the same compiled call site reaches different functions for different objects. Cost: one extra pointer per object, one table per class, and one indirection per call.

Q3What happens if you call a virtual function from inside a constructor?

In C++, the vptr is updated as each level of construction completes, so during the base constructor the object is still “a Base” and the base version runs — never the derived override. This is deliberate: the derived part isn't initialised yet, so calling into it would touch uninitialised members. In Java the opposite happens: the derived override is called, and it can observe the subclass's fields still at their default values — a genuine and well-known bug source. In both languages the rule is: never call an overridable method from a constructor.

Q4What is object slicing?

A C++-specific bug. Assigning a derived object to a base object by value — Shape s = circle; — copies only the base sub-object; the derived fields are “sliced off” and the vptr is reset to the base's vtable, so polymorphism is silently lost. It cannot happen in Java or Python, where variables are always references. The fix is to work through pointers or references (Shape& s = circle; or a std::unique_ptr<Shape>).

Q5What is a virtual base class?

A base class inherited with the virtual keyword (class B : virtual public A) so that, in a diamond hierarchy, the most-derived class contains only one shared copy of A rather than one per path. It solves the duplicated-state half of the diamond problem. The trade-off is that the most-derived class becomes responsible for initialising the virtual base directly, and object layout becomes more complex and slightly slower to traverse.

Q6Is there a performance cost to polymorphism?

Yes, though usually small. Each virtual call costs a pointer dereference plus an indirect jump, it prevents the compiler from inlining, and it can cause branch mispredictions and worse instruction-cache locality. Each polymorphic object also carries an extra pointer. In practice this matters only in tight loops; modern JVMs and C++ devirtualisation can eliminate it when only one implementation is in play. The right framing: polymorphism trades a small, predictable runtime cost for a large reduction in the cost of change — and you profile before optimising it away.

Composition over inheritance

This is the design principle interviewers most want to hear you defend. Inheritance is compile-time, permanent, single-parent, and exposes the parent's implementation to the child. Composition is runtime, swappable, unlimited, and exposes only the collaborator's interface.

Say this, and stop

“I use inheritance only when the IS-A relationship holds for behaviour and is permanent — when I'd be happy for every subclass to be substitutable for the parent anywhere. For sharing capability or reusing code, I compose, because it's swappable at runtime, avoids the fragile base class problem, and doesn't spend my one inheritance slot.”

Interview questions — Section 09

Q1Difference between association, aggregation and composition.

Association is the general “these two classes know each other” relationship, with no ownership — a Student and a Course. Aggregation is a specialised association meaning HAS-A with weak ownership: the part exists independently and survives the whole, e.g. a Department and its Professors. Composition is HAS-A with strong ownership: the part is created by and dies with the whole, e.g. a House and its Rooms. So composition ⊂ aggregation ⊂ association, in increasing order of looseness.

Q2What does “favour composition over inheritance” mean and why?

It means build functionality by holding references to collaborator objects (HAS-A) rather than by extending a base class (IS-A), unless a true IS-A relationship exists. Reasons: inheritance is fixed at compile time while composition can be reconfigured at runtime; a class can compose many collaborators but extend only one parent; composition depends only on the collaborator's interface, so it avoids the fragile base class problem; and it keeps hierarchies flat instead of producing deep trees that are hard to reason about. The classic illustration is the Strategy pattern — a Duck that has a fly behaviour instead of being a flying bird.

Q3When IS inheritance the right choice?

When three things all hold: the IS-A relationship is genuinely true for behaviour (every subclass is substitutable for the parent — Liskov), the relationship is permanent and won't need to change at runtime, and the subclass genuinely needs to be used polymorphically through the base type. Framework extension points, sealed type hierarchies (Shape → Circle/Rect), and template-method skeletons are legitimate uses. Reaching for extends purely to reuse a couple of methods is not.

Q4What is a dependency relationship?

The weakest relationship: class A uses class B momentarily without storing it — B appears as a method parameter, a local variable, or a return type. Nothing is retained after the call. It's usually drawn as a dashed arrow in UML. Keeping relationships at dependency level where possible minimises coupling, which is exactly what dependency injection exploits: pass the collaborator in rather than constructing it.

Q5What is delegation?

An object handling a request by forwarding it to a helper object it holds, rather than implementing the work itself. It is the mechanism that makes composition practical: Duck.performFly() delegates to flyBehaviour.fly(). Delegation gives you the reuse benefit of inheritance without the coupling, and it's the basis of the Strategy, Decorator, Proxy and Adapter patterns. The trade-off is a small amount of boilerplate forwarding code.

Q6Give a real example where inheritance was the wrong choice.

Java's own java.util.Stack extends Vector. Because it inherits from a list, a Stack exposes get(int), insertElementAt() and remove(int) — so a caller can insert into the middle of a stack, which destroys the LIFO invariant the type is supposed to guarantee. Composition (a Stack that has a list and exposes only push/pop/peek) would have preserved the invariant. Java effectively acknowledged the mistake by introducing Deque/ArrayDeque as the recommended replacement.

Copying & Object Identity

Shallow vs deep copy, copy constructors, and the equals/hashCode contract — where interviewers test whether you've actually debugged a HashMap.

Shallow vs deep copy

A shallow copy duplicates the object's fields as-is. For primitives that's a real copy; for reference fields it copies the reference, so the original and the copy point at the same nested object. Mutating that nested object through one is visible through the other.

A deep copy recursively duplicates the nested objects too, producing a fully independent object graph. It is more expensive, and must handle cycles.

Copy constructors and the Rule of Three/Five (C++)

A copy constructor creates a new object as a copy of an existing one of the same class: Person(const Person& other). C++ generates one automatically, but the generated version is a member-wise shallow copy — disastrous for a class holding a raw pointer, since both objects would delete the same memory (a double-free).

Hence the Rule of Three: if a class needs a custom destructor, copy constructor, or copy assignment operator, it almost certainly needs all three. C++11 extends it to the Rule of Five by adding the move constructor and move assignment operator. The modern preference is the Rule of Zero: use RAII types like std::unique_ptr and std::vector so you need none of them.

Java has no copy constructor built in. Your options are a hand-written copy constructor (preferred), a static factory copyOf(), or Cloneable + clone() — which is widely regarded as a broken design and generally avoided.

equals() and hashCode()

== compares references (identity); equals() compares state (equality), if the class overrides it. Default Object.equals() is just ==, which is why forgetting to override it makes two identical-looking objects unequal.

The contract you must recite

If two objects are equal by equals(), they must return the same hashCode(). The converse need not hold — unequal objects may collide. Override one without the other and hash-based collections break: you put an object into a HashMap and can never find it again, because lookup goes to a different bucket. equals() must also be reflexive, symmetric, transitive, consistent, and return false for null.

Interview questions — Section 10

Q1Shallow copy vs deep copy.

A shallow copy duplicates the top-level object but copies reference fields by reference, so both objects share the same nested objects — mutating a nested object through one is visible through the other. A deep copy recursively duplicates the nested objects too, giving two fully independent graphs. Shallow is fast and fine for immutable or primitive-only fields; deep is required whenever the nested objects are mutable and the copies must not interfere. In Java, Object.clone() is shallow by default; deep copying requires a hand-written copy constructor or serialisation round-trip.

Q2What is a copy constructor and when is it called in C++?

A constructor taking a reference to another object of the same class, T(const T& other), used to initialise a new object as a copy. It is invoked when an object is initialised from another (T b = a;), when an object is passed by value, and when one is returned by value (subject to copy elision). The parameter must be a reference — taking it by value would require a copy to make the copy, an infinite recursion. If you don't write one, the compiler generates a member-wise shallow copy.

Q3Explain the Rule of Three / Five / Zero.

Rule of Three: if a class defines any of destructor, copy constructor, or copy assignment operator, it manages a resource and almost certainly needs all three — otherwise the compiler-generated versions will shallow-copy and cause double-frees or leaks. Rule of Five (C++11) adds the move constructor and move assignment operator, so the class also benefits from efficient moves. Rule of Zero is the modern preference: hold resources in RAII types (unique_ptr, vector, string) so the class needs none of the five and the defaults are correct.

Q4Difference between == and equals() in Java.

== is an operator that compares values for primitives and reference identity for objects — are these two variables pointing at the same object? equals() is a method that compares logical equality, but only if the class overrides it; Object's default implementation just does ==. String, the wrappers and collections all override it. The classic gotcha: new String("a") == new String("a") is false while .equals() is true, whereas two identical string literals are == because of the string pool.

Q5Why must you override hashCode() whenever you override equals()?

Because hash-based collections depend on the contract that equal objects produce equal hash codes. HashMap finds an entry by first computing the hash to pick a bucket, then using equals() within that bucket. If you override equals() alone, two logically equal objects keep their distinct identity-based hash codes, land in different buckets, and map.get(key) returns null even though an equal key is in the map. Always derive both from the same set of fields — Objects.hash(...) and Objects.equals(...) make this easy, and records do it for you.

Q6Why is clone() considered problematic in Java?

Several reasons. Cloneable is a marker interface that doesn't declare clone(), so the contract isn't expressed in the type system. Object.clone() is protected, so every class must re-expose it. It performs a shallow copy that silently shares mutable state. It bypasses constructors, so invariants and final fields aren't handled normally. And it throws a checked CloneNotSupportedException for no useful reason. The recommended alternative is a copy constructor or a static copyOf() factory, which are explicit, type-safe and free to deep-copy.

Q7What is the purpose of toString()?

To return a human-readable representation of the object, used automatically by System.out.println(), string concatenation and most logging and debugging tools. The default from Object prints ClassName@hexHashCode, which is useless in a log. Overriding it to include the identifying fields makes debugging dramatically faster. Keep it free of side effects and avoid dumping sensitive data such as passwords or tokens.

Coupling & Cohesion

The two words that let you talk about design quality precisely instead of saying “clean code”. Short section, high return.

Coupling is the degree to which one module depends on another. Low coupling is the goal — a change in one class should not force changes in many others.

Cohesion is the degree to which the elements inside a single module belong together. High cohesion is the goal — a class should do one thing, and everything in it should serve that thing.

The pair is always quoted together: low coupling, high cohesion. They pull in the same direction — a class that does one job needs fewer collaborators.

Interview questions — Section 11

Q1What are coupling and cohesion? Which do you want high and which low?

Coupling measures inter-module dependency; cohesion measures intra-module focus. You want low coupling and high cohesion. Low coupling means a change in one class rarely ripples into others, so the system is safe to modify and each part is independently testable and reusable. High cohesion means a class has a single, clear responsibility, which makes it easy to name, understand and change. They reinforce each other: a class that does one thing needs fewer collaborators.

Q2How do you reduce coupling in practice?

Depend on interfaces rather than concrete classes; inject collaborators through the constructor instead of calling new inside; keep fields private so nobody depends on your internals; prefer composition to inheritance, since inheritance is the tightest coupling there is; use events or callbacks where two modules must not know each other directly; and avoid shared mutable global state. Dependency injection frameworks like Spring exist essentially to automate this.

Q3What is dependency injection and how does it relate to OOP?

Dependency injection means an object receives its collaborators from outside — via constructor, setter or method parameter — rather than constructing them itself. It's the practical implementation of the Dependency Inversion Principle: the class declares what it needs as an abstraction, and the caller (or a container) decides the concrete implementation. The payoff is testability, since you can pass a mock, and configurability, since you can swap implementations without touching the class. Constructor injection is preferred because it makes dependencies explicit and allows the field to be final.

Q4What is the Law of Demeter?

The “principle of least knowledge”: a method should only call methods on its own fields, its parameters, objects it creates, and itself — not on objects returned by other objects. Practically it forbids long chains like order.getCustomer().getAddress().getCity().getPin(), since that couples you to three classes you don't own and any of them can break you. The fix is to ask the immediate collaborator for what you need — order.getShippingPin() — which is often called “tell, don't ask”.

SOLID Principles

Five design principles that turn the four pillars into working guidance. Expect “explain SOLID” in almost every interview past the fresher screen, and a follow-up asking you to spot a violation.

S — Single Responsibility Principle

A class should have only one reason to change. “Reason to change” means one stakeholder or one axis of change — not literally “one method”. If the reporting team and the persistence team can both force you to edit the same class, it has two responsibilities.

O — Open/Closed Principle

Software entities should be open for extension but closed for modification. You should be able to add behaviour by adding new code, not by editing tested code. Polymorphism is the mechanism.

L — Liskov Substitution Principle

Objects of a subclass must be substitutable for objects of the base class without breaking the program. Inheritance must preserve behaviour, not just structure. Practical tests: a subclass must not strengthen preconditions, must not weaken postconditions, must not throw new exception types, and must not turn an inherited method into a no-op or an error.

I — Interface Segregation Principle

Clients should not be forced to depend on methods they do not use. Prefer several small, role-specific interfaces to one large one. The symptom of a violation is an implementation full of empty methods or throw new UnsupportedOperationException().

D — Dependency Inversion Principle

High-level modules should not depend on low-level modules; both should depend on abstractions. Abstractions should not depend on details; details should depend on abstractions. In practice: your business logic defines the interface it needs, and the database/email/SMS classes implement it — so the dependency arrow points into your domain, not out of it.

30-second SOLID summary for a screening round

S — one class, one reason to change. O — extend by adding classes, not editing them. L — a subclass must be usable anywhere its parent is. I — many small interfaces beat one fat one. D — depend on abstractions, inject the concrete. Together they aim at one outcome: changes stay local.

Interview questions — Section 12

Q1What are the SOLID principles and why do they matter?

Five design principles for maintainable OO code: Single Responsibility (one reason to change), Open/Closed (open for extension, closed for modification), Liskov Substitution (subtypes must be substitutable for their base type), Interface Segregation (no client forced to depend on unused methods) and Dependency Inversion (depend on abstractions, not concretions). They matter because software cost is dominated by change, and each principle localises the effect of a change — giving code that is easier to test, extend and reason about.

Q2Explain the Single Responsibility Principle with an example.

A class should have exactly one reason to change — one axis of responsibility. A class that computes an employee's pay, persists them to a database and formats their payslip email has three: a change in tax rules, a change in schema, or a change in email templating all force edits to the same file, and each edit risks the others. Splitting into Employee, PayCalculator, EmployeeRepository and PayslipMailer means each change touches exactly one class. The test I use: can I describe the class in one sentence without “and”?

Q3How do you achieve Open/Closed in practice?

Through abstraction and polymorphism. Identify the axis along which the code will vary, define an interface or abstract class over it, and let callers depend only on the abstraction. New behaviour then arrives as a new implementing class, with zero edits to code that is already tested and in production. The practical smell to hunt for is a growing if/else or switch on a type field — that chain is exactly what an interface plus a set of implementations replaces. The Strategy and Factory patterns are the standard tools.

Q4Give a real example of a Liskov Substitution violation.

The Rectangle/Square case: Square extends Rectangle must keep width and height equal, so overriding setWidth() also changes the height. Any client that sets width 5, sets height 4 and expects area 20 now gets 16 — the subclass broke a rule the base class promised. Another everyday example: a ReadOnlyList extending List and throwing UnsupportedOperationException from add(). The lesson is that IS-A must hold for behaviour and contracts, not just for the English noun; when it doesn't, use composition or a common abstraction instead.

Q5What's the difference between Dependency Inversion, Inversion of Control and Dependency Injection?

They are three levels of the same idea. Dependency Inversion is the principle: high-level modules and low-level modules should both depend on abstractions. Inversion of Control is the broader pattern: the framework calls your code rather than your code calling the framework — control of flow is inverted. Dependency Injection is a specific technique for achieving them: dependencies are supplied from outside via constructor, setter or parameter, instead of being constructed inside the class. Spring's container is a DI implementation serving the DIP.

Q6Can SOLID be overdone?

Yes, and saying so shows judgement. Applying SRP too literally produces dozens of one-method classes and a codebase where following a single request means opening fifteen files. Applying OCP speculatively creates interfaces with exactly one implementation that will never have a second — abstraction with no payoff. The sensible stance is to apply the principles when you have evidence of a real axis of change, and to accept a simple concrete class until that evidence appears. YAGNI is a legitimate counterweight to premature abstraction.

Singleton — exactly one instance

Guarantees a class has one instance and gives a global access point. Used for configuration, logging, connection pools, caches.

Have the criticism ready

Singleton is widely considered an anti-pattern when overused: it is global mutable state, it hides dependencies (a class using it doesn't declare it), it makes unit testing hard (you cannot substitute a fake), and it can become a bottleneck under concurrency. The modern alternative is a normal class with a single instance managed by a dependency injection container — same “one instance” guarantee, with the dependency made explicit and replaceable.

Interview questions — Section 13

Q1What is a design pattern and what are the three categories?

A design pattern is a proven, reusable solution to a problem that recurs in software design — not code you copy, but a structure you apply, plus a shared name that makes design discussions faster. The Gang of Four grouped 23 patterns into three categories: creational (object creation — Singleton, Factory, Builder, Prototype, Abstract Factory), structural (composing objects into larger structures — Adapter, Decorator, Facade, Proxy, Composite), and behavioural (communication and responsibility — Strategy, Observer, Command, Template Method, Iterator, State).

Q2How do you implement a thread-safe Singleton?

Three good options. Eager initialisation — a private static final instance created at class load; thread-safe by the JVM's class-initialisation guarantees, but built even if unused. Double-checked locking — a volatile field with a null check outside and inside a synchronized block; volatile is essential, because without it another thread can see a non-null reference to a partially constructed object due to instruction reordering. Enum singleton — recommended in Effective Java; it's concise, lazily initialised, and the only form immune to reflection and serialization attacks. The Bill Pugh static-holder idiom is a fourth clean option.

Q3Why is Singleton often called an anti-pattern?

Because it is global mutable state wearing a design-pattern badge. It hides dependencies — a class that calls Config.getInstance() doesn't declare that it needs Config, so you can't tell from its signature what it depends on. It makes unit testing hard, since you cannot inject a fake and state leaks between tests. It violates SRP by combining the object's real job with managing its own lifecycle, and it can serialise access under concurrency. The modern approach is one instance managed by a DI container and injected explicitly.

Q4Difference between Factory Method and Abstract Factory.

Factory Method defines an interface for creating one product and lets subclasses (or a switch) decide which concrete class to instantiate — one product hierarchy. Abstract Factory provides an interface for creating families of related products without specifying their concrete classes — several product hierarchies kept consistent with each other. Example: a Factory Method returns a Button; an Abstract Factory (WindowsUIFactory / MacUIFactory) returns a matching Button, Checkbox and Scrollbar so you can't accidentally mix a Windows button with a Mac scrollbar.

Q5When would you use the Strategy pattern?

When you have several interchangeable ways of doing the same job and want to choose or change one at runtime — sorting algorithms, discount rules, compression formats, payment methods, routing policies. It replaces a conditional chain with a set of classes behind one interface, which satisfies the Open/Closed Principle: adding a strategy means adding a class, not editing the context. The trade-off is more classes and the caller needing to know which strategy to pick.

Q6Explain the Observer pattern and give a real use.

Observer defines a one-to-many dependency: when the subject changes state, all registered observers are notified automatically. The subject knows only the observer interface, so it stays decoupled from what they do. Real uses: UI event listeners, a stock ticker pushing prices to multiple displays, a parking lot notifying availability boards when a spot frees, and reactive streams. Practical caution: forgetting to unsubscribe is a common memory-leak source, and notification order should not be relied upon.

Q7Difference between Adapter, Decorator, Facade and Proxy — they all wrap an object.

They differ by intent, not structure. Adapter converts an existing interface into the one a client expects — making an incompatible class usable. Decorator keeps the same interface and adds behaviour, and can be stacked — BufferedReader wrapping a FileReader. Facade provides a simplified interface over a complex subsystem — one entry point hiding many classes. Proxy keeps the same interface and controls access to the real object — lazy loading, caching, permission checks, remote calls. Same shape, four different reasons.

Q8What is the Builder pattern and when do you need it?

Builder constructs a complex object step by step, separating construction from representation. Use it when a class has many parameters, several of them optional — the alternative is telescoping constructors (five overloads that differ only in argument count) or a no-arg constructor plus setters, which forfeits immutability and lets objects exist in an invalid half-built state. A builder gives named, readable calls, validates everything in build(), and can return a fully immutable object. StringBuilder and Stream.Builder are JDK examples.

Exceptions, Generics & Object Class

The OOP features that surround the four pillars in real code — and that panels use to check whether you've written more than textbook examples.

Exceptions are objects too

An exception is an object representing an abnormal condition. Java's hierarchy is itself a lesson in inheritance:

  • Throwable — the root.
    • Error — serious JVM-level problems you should not catch (OutOfMemoryError, StackOverflowError).
    • Exception — conditions an application can reasonably handle.
      • Checked — everything except RuntimeException; the compiler forces you to catch or declare them (IOException, SQLException). Use for recoverable, expected failures.
      • Unchecked — RuntimeException and its subclasses; not enforced by the compiler (NullPointerException, IllegalArgumentException). Use for programming errors.

Overriding rule worth remembering: an overriding method may throw fewer or narrower checked exceptions than the method it overrides, never new or broader ones — otherwise a caller written against the base type would be blindsided, which is a Liskov violation.

Generics — parametric polymorphism

Generics let a class or method be written once and used with many types, with the compiler enforcing type safety. List<String> makes it impossible to insert an Integer, and removes the casts that pre-generics code needed.

Java implements generics with type erasure: the type parameter exists only at compile time and is erased to Object (or the bound) in the bytecode. That's why you cannot write new T[] or check list instanceof List<String>. C++ templates are entirely different — the compiler generates a separate class per type argument, giving more power and larger binaries.

Interview questions — Section 14

Q1Checked vs unchecked exceptions — when do you use each?

Checked exceptions extend Exception but not RuntimeException; the compiler forces the caller to catch or declare them. Use them for conditions the caller can reasonably anticipate and recover from — a missing file, a network timeout. Unchecked exceptions extend RuntimeException and carry no compiler obligation. Use them for programming errors that should be fixed in code, not handled at runtime — a null argument, an index out of range, an illegal state. The practical guide: if a well-written caller could do something useful about it, make it checked; otherwise unchecked.

Q2What is the difference between throw and throws, and between final, finally and finalize?

throw is a statement that actually raises an exception object, inside a method body; throws is a clause in the method signature declaring which checked exceptions the method may propagate. As for the trio: final is a modifier meaning “cannot be changed/overridden/extended”; finally is a block after try/catch that always executes, used for cleanup; finalize() was a deprecated Object method the GC could call before reclaiming an object, and must never be relied on. They are unrelated — the question exists purely to test precision.

Q3Can you override a method to throw a broader checked exception?

No. An overriding method may throw the same checked exceptions, narrower subtypes, fewer of them, or none at all — but never a new or broader checked exception. The reason is substitutability: a caller holding a base-type reference compiled against the base signature would have no handler for an exception the base never declared. Unchecked exceptions are unrestricted, since the compiler tracks no contract for them.

Q4Why do exception classes form an inheritance hierarchy?

So that catch can be polymorphic. Catching IOException also catches FileNotFoundException and every other subtype, letting a caller choose its level of granularity — handle a specific failure precisely, or handle a whole family generically. This is why catch blocks must be ordered most specific first: a broader type listed earlier would shadow the narrower one, and Java rejects that as unreachable code.

Q5What are generics and what problem do they solve?

Generics parameterise a class or method by type, so one implementation works for many types while the compiler still enforces type safety. Before generics, collections held Object, so any mistake surfaced as a ClassCastException at runtime and every read needed a cast. With List<String> the error is caught at compile time and the casts disappear. Generics are Java's form of parametric polymorphism, complementing the subtype polymorphism that inheritance provides.

Q6What is type erasure, and how do Java generics differ from C++ templates?

Type erasure means Java's type parameters exist only during compilation; the compiler checks types, inserts casts, and erases T to Object (or its bound) in the bytecode. So there is one List class at runtime, and you cannot instantiate new T(), create new T[], or test instanceof List<String>. It was chosen for backward compatibility with pre-generics bytecode. C++ templates work by instantiation: the compiler generates a distinct class for each type argument, so type information survives, specialisation and compile-time computation are possible, and the binary is larger.

Q7Why is every class in Java implicitly a subclass of Object?

So the language has a universal supertype. It guarantees every object supports a minimum protocol — equals, hashCode, toString, getClass and the monitor methods — which lets collections, serialisation and the pre-generics APIs accept any object with a single Object parameter. It is also what makes Object[] and erased generics workable. C++ has no such universal base, which is why its containers rely on templates rather than a common root type.

The LLD Round: Designing with Objects

Many placement processes end with “design a parking lot / elevator / BookMyShow”. This is where the previous fourteen sections get used at once.

A repeatable method

  1. Clarify requirements (3–5 min). Ask before designing. Scope, scale, and what's explicitly out of scope. Never start coding immediately — interviewers score this step.
  2. Identify entities. Underline the nouns in the requirements — those become your candidate classes. Verbs become methods.
  3. Define relationships. For each pair, decide IS-A, HAS-A (composition or aggregation), or uses. Draw it.
  4. Define interfaces before implementations. Where will this change? Put an abstraction there.
  5. Apply patterns where they earn their place. Name them out loud — “I'll use Strategy here so pricing rules can vary”.
  6. Write the core classes. Fields, key method signatures, and only the important method bodies. You will not finish a full implementation, and you are not expected to.
  7. Discuss trade-offs and extensions. Concurrency, persistence, and what you'd change to add a new feature.

Worked example: parking lot

Requirements gathered: multiple floors; spots sized for motorcycle / car / truck; vehicle gets a ticket on entry and pays on exit; fee depends on duration and vehicle type; display boards show free spots per floor; multiple entry and exit gates.

Nouns → classes: ParkingLot, Floor, Spot, Vehicle, Ticket, Gate, Payment, DisplayBoard.

Sentences that score in an LLD round

“I'm making pricing a Strategy so a new fee model is a new class, not an edit — that's Open/Closed.” · “Floors are composed into the lot because a floor has no meaning without it; vehicles are only associated, since they exist independently.” · “The assign method is synchronized because two gates can race for the last spot.” · “I'd avoid Singleton for ParkingLot and let the container own the single instance, so it stays testable.”

Interview questions — Section 15

Q1How do you approach an object-oriented design question?

Clarify requirements and constraints first, and state explicitly what's out of scope. Extract nouns from the requirements as candidate classes and verbs as behaviours. Decide the relationship between each pair — IS-A, composition, aggregation, or plain association. Identify the axes along which the system will vary and place an interface at each one. Then sketch the core classes with fields and key signatures, mention the patterns you're applying and why, and finish with trade-offs: concurrency, persistence, and how a specific new requirement would be absorbed.

Q2In your parking lot design, where did you use each OOP pillar?

Abstraction — Vehicle and PricingStrategy expose behaviour without implementation. Encapsulation — Spot keeps its occupant private and exposes only assign()/release(), so the occupancy invariant can't be corrupted from outside. Inheritance — Car, Motorcycle and Truck specialise Vehicle, sharing the plate and type. Polymorphism — the lot calls pricing.calculate() and observer.onAvailabilityChanged() without knowing the concrete class, so new pricing models and new display types plug in without edits.

Q3How would you handle two cars arriving at different gates competing for the last spot?

The check-and-assign must be atomic. In the design above, Spot.assign() is synchronized and re-verifies canFit() inside the lock, so exactly one thread succeeds and the other gets false and moves to the next spot — a compare-and-set on the spot itself. Locking the whole ParkingLot would also be correct but would serialise every gate, so per-spot locking scales better. At larger scale you'd move the allocation to a concurrent data structure or a database row lock, and make ticket issuance idempotent.

Q4How would you add electric-vehicle charging spots without breaking existing code?

Add ELECTRIC to VehicleType and an ElectricCar extends Vehicle; add a ChargingSpot extends Spot (or better, give Spot a composed Charger capability, since not all electric spots charge); add a pricing strategy that includes energy cost. Nothing in ParkingLot.park() changes, because it works against the abstractions. That is the Open/Closed Principle paying off, and demonstrating it concretely is exactly what the follow-up question is testing.

Interview questions — Section 16

Q1What are the main OOP differences between Java and C++?

Java allows multiple inheritance only through interfaces, C++ allows it fully with virtual base classes. Java methods are virtual by default, C++ requires the virtual keyword. Java is garbage collected with no destructors, C++ gives deterministic destructors that enable RAII. Java forbids operator overloading and pointer arithmetic; C++ has both. Java objects always live on the heap and variables are references, whereas C++ lets you place objects on the stack — which is why object slicing exists in C++ and not in Java. Java has a universal Object root; C++ has none.

Q2How does Python handle multiple inheritance?

Python permits it and resolves ambiguity with the Method Resolution Order, computed by the C3 linearisation algorithm. The MRO produces a deterministic, consistent ordering that preserves each class's local precedence and respects the inheritance graph; you can inspect it with ClassName.__mro__ or .mro(). super() follows the MRO rather than jumping directly to a named parent, which is what makes cooperative multiple inheritance work. If a consistent order cannot be computed, Python raises a TypeError at class-definition time rather than guessing.

Q3Does Python really support encapsulation if anything can be accessed?

Python supports encapsulation by convention rather than enforcement. A leading underscore (_balance) signals “internal, don't touch”; a double underscore (__balance) triggers name mangling to _ClassName__balance, which prevents accidental access and subclass collisions but is still reachable if you insist. The language's stance is “we're all consenting adults”. Real control over access is achieved with @property, which lets you expose an attribute-like interface while validating in the setter — the same goal as a Java getter/setter pair, with cleaner syntax.

Q4What is duck typing?

“If it walks like a duck and quacks like a duck, it's a duck.” In dynamically typed languages, an object's suitability is determined by whether it has the required methods at the moment of the call, not by which class or interface it declares. So any object with a fly() method works where flying is needed, with no implements Flyable. It gives polymorphism without an inheritance hierarchy — more flexible, but errors surface at runtime rather than compile time. Python's ABCs and type hints exist to reclaim some of that safety.

Final mixed set — the awkward ones

Q1Can you achieve polymorphism without inheritance?

Yes, in several ways. Interfaces give subtype polymorphism without class inheritance — unrelated classes implementing Comparable are used interchangeably. Overloading is compile-time polymorphism and needs no hierarchy at all. Generics provide parametric polymorphism. And duck typing in Python or JavaScript gives polymorphism with no declared relationship whatsoever. Inheritance is one route to polymorphism, not the definition of it.

Q2What is an anti-pattern? Name two.

A commonly used solution that looks reasonable but produces more problems than it solves. Two examples: the God Object — one class that knows and does everything, violating SRP and becoming a merge-conflict magnet; and the Anaemic Domain Model — classes reduced to fields with getters and setters while all logic sits in separate “service” classes, which throws away encapsulation entirely. Others worth knowing: Spaghetti Code, Golden Hammer, and overuse of Singleton.

Q3Is inheritance always about code reuse?

No — and treating it that way is the source of most bad hierarchies. Inheritance's more important purpose is establishing a subtype relationship so objects can be used polymorphically through the base type. If all you want is to reuse a few methods, composition does that with looser coupling and no constraint on your single inheritance slot. The right question before extends is never “do I want these methods?” but “is this genuinely substitutable for that, everywhere?”

Q4What is the difference between an interface and an abstract class in one sentence?

An interface defines what a class can do (a capability contract, multiply implementable, stateless), while an abstract class defines what a class is (a partial identity, singly inheritable, able to hold shared state and implementation).

Q5Which OOP concept do you find most misused in real code, and why?

Inheritance — used for code reuse rather than for genuine subtyping. It produces deep hierarchies where behaviour is scattered across five files, subclasses that override methods into no-ops (breaking Liskov), and the fragile base class problem where a safe-looking parent change breaks children silently. The discipline that fixes it is asking whether the subclass is truly substitutable everywhere the parent is used; if the honest answer is “mostly”, the right tool is composition. This is a good question to have a real opinion on — it's often asked to see whether you've maintained code, not just written it.

Q6How would you explain OOP to a non-technical person?

Think of a restaurant. Each role is an object: the chef, the waiter, the cashier. Each one keeps their own things and knows their own job — the chef owns the kitchen, and nobody else reaches into it. They work by making requests of each other: the waiter asks the chef for a dish, without needing to know how it's cooked. Replace the chef with a different one who cooks differently, and the waiter's job doesn't change at all. That's encapsulation, abstraction and polymorphism, and it's why the restaurant keeps running when one role changes.
