  • Second pass — the code walkthroughs. Sections 07, 11 and 12 go line by line. Open the actual repo files beside this page.

The 60-second pitch (memorise this)

Say this when they ask "tell me about your project"

"Casper 2.0 is an autonomous web research assistant. Instead of a normal chatbot that answers from memory, Casper is an agent — you give it a research question, and it decides on its own what to search for, runs the search, reads the results, decides whether it needs more information, and searches again. It keeps looping until it's satisfied, then writes a cited summary.

The agent brain is built with LangGraph, which models the agent as a state machine with a cycle: a chatbot node that reasons, and a tools node that executes DuckDuckGo searches, with a conditional edge between them. The LLM is Llama 3.1 8B running on Groq, chosen for its very low inference latency and reliable native tool-calling.

A key design decision was the search budget: agents can loop forever and burn tokens, so the user sets a limit of 1–8 searches and the graph state carries a loop_count. Once the budget is spent, the node stops binding tools to the model at all, which structurally forces it to summarise instead of merely asking it politely.

The whole run streams to the browser over Server-Sent Events from a FastAPI backend, so the React frontend shows the agent's reasoning live — every query it formulates and every source it reads — rather than a spinner. That transparency was the actual point of the project: making the agent's thought process visible."

That pitch deliberately front-loads the three things an interviewer will latch on to: cyclic graph budget control live streaming. Each one is a doorway into a deeper technical conversation you are prepared for.

Interview questions · Orientation

Why did you build this project?

Frame it as a problem, not a tutorial. "Language models have a training cutoff and can't see today's web, and single-shot search tools give you one round of results whether or not that's enough. I wanted to build something that behaves like a person doing research — search, read, notice a gap, search again. That naturally requires a loop, and once you need a loop with state, a linear chain isn't enough, which is what pushed me to LangGraph."

Then add the honest engineering motivation: "I also wanted the reasoning to be visible. Most agent demos are a black box with a spinner. Streaming the thought process was as much of a goal as the answer itself."

What was the hardest part?

A strong, specific answer: controlling the loop. "A cyclic agent has no natural stopping point. My first version just told the model in the system prompt to stop searching — and it ignored that instruction sometimes, because prompt instructions are suggestions, not constraints. The fix was structural: once loop_count reaches the budget, I stop calling bind_tools() entirely, so the model physically has no tool to call. That taught me that with LLMs you should prefer making bad behaviour impossible over asking for good behaviour."

Second candidate: the tool-call parsing fallback in agent.py — see section 07, it's a great story about models emitting tool calls as plain text.

What would you do differently if you rebuilt it today?

Have three ready: (1) add a checkpointer so conversations persist and can be resumed, instead of every request starting from an empty state; (2) make the searches within a single reasoning step parallel instead of strictly sequential; (3) tighten the security posture — the CORS policy is wide open and there's no rate limiting, which is fine for a local demo but not for deployment. Section 15 covers all of these in depth.

Interview questions · Project shape

Why is there no database in this project?

Because nothing needs to survive a server restart. Each research run is stateless on the server: the request creates a fresh graph state, streams results, and finishes. The only persistence is the history sidebar, and that's user-specific and small, so localStorage in the browser is the right tool — zero infrastructure, instant reads, and no privacy question about storing people's queries on a server.

Then show you know the limit: "That breaks the moment you want history across devices, shared runs, or resumable conversations. At that point you'd add Postgres plus a LangGraph checkpointer, keyed by a thread id."

Why keep the agent runnable as a CLI when there's a web UI?

It's a cheap, fast test harness. The __main__ block in agent.py lets you exercise the whole graph — model, tools, loop control — without starting a server, opening a browser, or worrying about CORS and SSE. When something breaks you immediately know which half it's in. It also proves the agent module has no web dependencies, which is the design property you actually want.

How would you deploy this?

Backend: containerise it, run uvicorn behind a reverse proxy, and set GROQ_API_KEY as a platform secret rather than a .env file. Frontend: npm run build produces static files that go to any CDN or static host. Two things must change from local: the hardcoded http://127.0.0.1:8000 in App.jsx becomes an environment variable (import.meta.env.VITE_API_URL), and CORS must be narrowed from ["*"] to the actual frontend origin.

Add the SSE caveat: many proxies buffer responses, which silently kills streaming. You need proxy_buffering off in nginx or the equivalent, and a read timeout longer than the longest research run.

Section 03

Foundations: LLMs, prompts and context

Before any framework, you need the mental model of what the model actually is. Interviewers routinely ask "what is an LLM, in your own words" and a vague answer undermines everything you say afterwards.

What a large language model actually does

An LLM is a next-token predictor. It has been trained on an enormous amount of text with one objective: given a sequence of tokens, predict a probability distribution over what the next token should be. That's the whole mechanism. Everything else — answering questions, writing code, calling tools — is that one capability, wrapped.

  • Token. Not a word, and not a character — a sub-word chunk. "unbelievable" might be un + believ + able. Roughly 4 characters or ¾ of an English word per token. You pay per token, and you're limited by tokens, so this matters practically.
  • Parameters. The learned weights. Llama 3.1 8B has 8 billion of them. More parameters generally means more capability but slower and costlier inference.
  • Context window. The maximum number of tokens the model can see at once — prompt plus generated output. Everything the model "knows" about your conversation must fit here, because the model has no memory between calls.
  • Knowledge cutoff. Training data stops at a date. Anything after it doesn't exist to the model. This is the single fact that justifies Casper's existence.
  • Hallucination. Because the model optimises for plausible-sounding text, not truth, it will confidently invent facts, citations and URLs. Grounding the model in real retrieved text — as Casper does — reduces this substantially.
The key consequence for agent design

The model is stateless. Every single call to the LLM sends the entire conversation again. There is no server-side memory of your last message. When you hear "the agent remembers what it searched", what's physically happening is that the previous messages are being re-sent in the next request. This is why LangGraph's state — a growing list of messages — is the whole ballgame, and why long agent loops get expensive: each loop re-sends everything before it.

Temperature and why Casper uses 0

After the model computes its probability distribution, temperature controls how that distribution is sampled. At temperature=0 the model always picks the highest probability token — deterministic and repeatable. At 0.7 it samples more freely, producing more varied, creative output.

Casper sets temperature=0. The reasoning is specific: the model's most important decisions here are whether to call a tool and what JSON arguments to pass. Those need to be exactly right, not creative. A randomly sampled token in the middle of a JSON argument produces a malformed tool call and a crashed loop. Determinism also makes debugging possible — you can re-run the same query and get the same behaviour.

Prompt engineering, in the two ways Casper uses it

Look closely at agent.py and you'll see the system prompt is not constant — it switches based on whether the search budget is exhausted. That's a real technique, sometimes called dynamic or conditional prompting:

Budget remaining

"Use the web_search tool to find real-time information… Do not perform redundant or repeated searches… cite URLs from search results." Encourages tool use, discourages waste, mandates citations.

Budget exhausted

"You have reached the maximum search limit (N searches). DO NOT search anymore or call any tools. Analyse the information you have already gathered and write the final summary." Redirects the model to synthesis.

The point interviewers love

That second prompt is a request, and LLMs sometimes ignore requests. That's why Casper also removes the tools from the model at the same moment — llm instead of llm.bind_tools(tools). The prompt explains the situation, the unbinding enforces it. Belt and braces: prompt for cooperation, architecture for guarantee.

Interview questions · LLM foundations

Explain a large language model to a non-technical interviewer.

"It's an extremely sophisticated autocomplete. It's read a huge portion of the public internet and learned the statistical patterns of language, so given some text it can predict what comes next, one chunk at a time. Because so much human knowledge is encoded in how we write about it, that prediction ability turns out to look like reasoning. But it has two hard limits: it only knows what was in its training data up to a cutoff date, and it has no memory between conversations. My project is built specifically to work around both."

What is a context window, and why does it matter for an agent?

It's the maximum number of tokens the model can process in one call — prompt plus response. For an agent it matters more than for a chatbot, because every loop adds to the conversation. Casper appends an AI message and a full search result (five titles, URLs and snippets) on every iteration. Eight loops of that can be tens of thousands of tokens.

Consequences: cost grows roughly quadratically with loop count (each loop re-sends everything before it), latency grows, and eventually you overflow the window and the call fails. Mitigations you can name: summarise older messages, truncate tool results before appending them, keep only the last N results, or store full results externally and pass only IDs. Casper's search budget is a crude but effective version of this control.

Why temperature 0 and not 0.7?

Because the critical outputs are structured, not prose. The model must emit a valid function name and valid JSON arguments; randomness there produces parse failures. Determinism also makes the system testable and debuggable — same input, same trace.

Good nuance to volunteer: "Ideally you'd want temperature 0 for the tool-calling decisions and something slightly higher for the final written summary, where a little variation reads better. Casper uses one model instance for both, so it takes the safe option. Splitting them would be a genuine improvement."

Is temperature 0 truly deterministic?

Practically yes, theoretically no. Floating-point non-associativity on GPUs, batching effects, and provider-side model updates mean identical inputs can occasionally produce different outputs. It's "as deterministic as you can get", not a mathematical guarantee. Mentioning this shows depth.

What is hallucination, and how does Casper reduce it?

Hallucination is the model producing confident, fluent, false output — invented facts, fake citations, non-existent URLs. It happens because the training objective rewards plausibility, not truth.

Casper reduces it by grounding: the final summary is written after real web snippets have been placed in the context, and the system prompt requires citing URLs from those results. The model is summarising provided text rather than recalling from weights. It doesn't eliminate the problem — the model can still misread a snippet or cite the wrong source — but it moves from "trust the model" to "trust, and the user can check the link".

Section 04

Tool calling & the ReAct pattern

This is the conceptual heart of the project. If you understand exactly what happens when an LLM "calls a tool", most agent questions become easy.

The critical misconception to avoid

Never say this in an interview

"The LLM calls the function." It does not. The model cannot execute code, make network requests, or touch your machine. All it can do is emit text. What actually happens is that the model emits a structured request — a function name and JSON arguments — and your code decides whether to honour it and runs the actual Python. In Casper, that executing code is LangGraph's ToolNode.

The six-step mechanics of tool calling

  • Describe. You define web_search(query: str) -> str with a docstring. LangChain converts it into a JSON schema: name, description, and a parameter object with types. The description comes from the docstring — which is why the docstring is functional code here, not a comment.
  • Bind. llm.bind_tools(tools) attaches that schema to every outgoing request. The model now sees, alongside your messages, a catalogue of what it can ask for.
  • Decide. The model reads the user's question and the tool descriptions and decides: answer directly, or request a tool. This decision is itself just token prediction, which is why good tool descriptions matter so much.
  • Emit. If it wants the tool, it returns an AIMessage whose content is typically empty and whose tool_calls list contains {"name": "web_search", "args": {"query": "..."}, "id": "call_abc123"}.
  • Execute. Your runtime matches the name to the real Python function, calls it with the arguments, and captures the return value. This is the only place real work happens.
  • Feed back. The result is wrapped in a ToolMessage carrying the matching tool_call_id and appended to the conversation. The model is called again with the extended history, and now it can see the search results.

Step 6 is why agents loop. One tool call requires two LLM calls minimum — one to request, one to interpret. Casper's four-search default therefore means roughly five LLM calls per run.

ReAct: Reason + Act

ReAct is the pattern Casper implements. It comes from a 2022 research paper and the idea is simple: instead of asking a model to reason in one shot, interleave reasoning with acting and observing, so each thought is informed by real evidence rather than by the model's imagination.

Casper's variation on standard ReAct

Classic ReAct terminates when the model emits a "Final Answer". Casper adds a second, external termination condition: the search budget. This is a meaningful engineering addition, because pure ReAct agents are notorious for looping until they hit a token limit or a bill. Frame it as "I don't fully trust the model to decide when it's done, so I gave the system an independent authority to stop it."

Agent vs. chatbot vs. workflow

Interviewers ask this constantly, and the distinguishing question is always: who decides the control flow?

Chatbot

One message in, one message out. No tools, no loop. The developer controls flow; there is barely any flow to control.

Chain / workflow

A fixed sequence: retrieve → prompt → generate. The developer decides the steps in advance; the LLM only fills in content. Predictable, cheap, testable.

Agent

The LLM decides the control flow. Whether to search, what to search for, how many times, when to stop. Flexible and powerful, but non-deterministic and harder to test — which is exactly why guardrails like the search budget exist.

How Casper relates to RAG

RAG (Retrieval-Augmented Generation) means fetching relevant documents and putting them in the prompt before generating. Casper is RAG-shaped, but with two differences worth naming:

Classic RAGCasper
Retrieval triggerAlways, once, before generationThe model decides whether and when
Retrieval countExactly one roundUp to N rounds, each informed by the last
QueryThe user's question, embedded as-isA query the model writes itself, refined across loops
SourceA vector database of your own documentsThe live public web via DuckDuckGo
MatchingSemantic — embeddings and cosine similarityKeyword/lexical — whatever the search engine does

The accurate label for Casper is agentic RAG: retrieval as a tool the agent chooses to use, iteratively, rather than a fixed pre-processing step.

Interview questions · Tools & ReAct

Walk me through what happens when the LLM "calls" your search tool.

Use the six steps: describe (docstring → JSON schema), bind (schema travels with the request), decide (model picks), emit (an AIMessage with a tool_calls array, content usually empty), execute (my code — LangGraph's ToolNode — runs the real Python function), feed back (result becomes a ToolMessage with the matching tool_call_id and the model is invoked again with the longer history).

Land the key point explicitly: "The model never executes anything. It produces a structured request; my runtime is the one that decides to honour it. That separation is also the security boundary — I could validate or refuse a tool call before running it."

Why does the docstring matter so much?

Because it is the tool description sent to the model, and the model's decision to use the tool is made purely from that text plus the parameter names. A vague docstring means the model uses the tool at the wrong time or not at all. Casper's — "Searches the web using DuckDuckGo to get real-time information and answer questions" — names the capability and, crucially, the trigger condition (real-time information).

Neat one-liner: "The docstring is a prompt, not a comment. Changing it changes runtime behaviour."

What is ReAct and why is it better than just asking the model?

ReAct interleaves reasoning with acting: Thought → Action → Observation → repeat. It's better for research tasks because each reasoning step is grounded in freshly retrieved evidence instead of recalled training data, which reduces hallucination and lets the model recover when a search returns something unexpected. It also produces a legible trace — which is literally what Casper's live log panel renders.

The cost: more LLM calls, more latency, more tokens, and less predictability.

How do you stop an agent from looping forever?

Four mechanisms, and Casper uses the first two:

  • A hard counter in state — loop_count vs max_searches.
  • Capability removal — once the budget is spent, don't bind the tools at all, so calling one is impossible rather than merely discouraged.
  • Graph recursion limit — LangGraph has a built-in recursion_limit (default 25 supersteps) that raises an error as a final safety net.
  • Wall-clock / token budget — abort past a time or cost ceiling.

Say why you chose the second: prompts are advisory, architecture is binding.

Is Casper a RAG system?

"It's agentic RAG. Classic RAG retrieves once, before generation, using the user's question against a vector store. Casper lets the model decide whether to retrieve, write its own search query, read the results, and retrieve again with a refined query. The retrieval source is the live web rather than an embedded corpus, so matching is lexical rather than semantic — which is a real trade-off: I get freshness and unlimited coverage, but I lose the precision of embedding-based retrieval over a curated corpus."

What happens if the model requests a tool that doesn't exist?

LangGraph's ToolNode looks the name up in the tools list; an unknown name produces an error which, by default, is returned to the model as a ToolMessage rather than crashing the graph — so the model gets a chance to correct itself. This is worth knowing because Casper's regex fallback (section 07) constructs tool calls from raw text, and a malformed model output could produce a bogus tool name there.

Section 05

LangChain building blocks

LangChain is the layer that makes models, tools and messages interchangeable. Casper uses a deliberately small slice of it — worth knowing precisely which parts, so you don't overclaim.

What LangChain is for

Every model provider has a different API shape. LangChain provides a common interface — a chat model takes a list of messages and returns a message — so swapping Groq for OpenAI or Gemini is a one-line change. Casper's dependency list still contains langchain-google-genai precisely because it was ported from Gemini to Groq, and that port was cheap for exactly this reason.

The four pieces Casper actually uses

1. ChatGroq — the model wrapper

agent.pypython
llm = ChatGroq(model="llama-3.1-8b-instant", temperature=0)

It reads GROQ_API_KEY from the environment automatically — which is why load_dotenv() must run first. It exposes .invoke(messages) for a single blocking call and .bind_tools(tools) to produce a tool-aware copy.

2. The @tool decorator

agent.pypython
@tool
def web_search(query: str) -> str:
    """Searches the web using DuckDuckGo to get real-time information and answer questions."""
    ...

This one decorator does three things: it reads the type hints to build a parameter schema (query is a required string), it reads the docstring as the tool description, and it wraps the function in a StructuredTool object with a .name, .description, .args_schema and an .invoke() method. That object is what gets serialised into the model request.

3. bind_tools

llm.bind_tools(tools) does not mutate llm. It returns a new runnable that carries the tool schemas as extra request parameters. That immutability is exactly what makes Casper's budget trick work — it can hold onto the plain llm and the bound version independently and choose between them per iteration.

4. Message classes

Covered in section 03. The one LangChain convenience worth knowing: you can pass a tuple like ("user", "hello") and LangChain coerces it into a HumanMessage. That's why the initial state in both agent.py and main.py is written as {"messages": [("user", query)]}.

LangChain vs. LangGraph — the boundary

LangChainLangGraph
ProvidesModel wrappers, tools, messages, prompt templates, output parsersState machines: nodes, edges, cycles, persistence
Control flowLinear — chains, "this then that" (LCEL pipes)Arbitrary graphs, including loops and branches
StatePassed through implicitlyAn explicit, typed, shared object with reducers
Best forFixed pipelines: summarise, classify, one-shot RAGAgents that iterate, branch, or need human approval

They aren't competitors — LangGraph is built on LangChain primitives. Casper uses LangChain for what the model and tools are, and LangGraph for how they're orchestrated.

Interview questions · LangChain

What does LangChain give you that calling the Groq API directly wouldn't?

Three concrete things: (1) a provider-agnostic interface, so switching models is one line — I actually did this, moving from Gemini to Groq; (2) automatic tool schema generation from Python type hints and docstrings, instead of hand-writing JSON schemas and keeping them in sync with the functions; (3) a standard message model that LangGraph's ToolNode and tools_condition can operate on generically.

Be balanced: "The cost is an abstraction layer that occasionally hides what's really being sent. For a production system I'd want to be comfortable reading the raw request."

Does bind_tools modify the LLM object?

No — it returns a new runnable with the tool schemas attached; the original is untouched. Casper depends on this: llm_to_call is either the bare llm or llm.bind_tools(tools) depending on the budget, and both come from the same underlying object. If bind_tools mutated in place, that budget logic would break after the first iteration.

How would you add a second tool, say a calculator?

Three steps and nothing else: write the function with type hints and a precise docstring, decorate it with @tool, and add it to the tools list. ToolNode(tools) and bind_tools(tools) both take the list, so the graph needs no changes at all.

The real work is the docstring — with two tools the model now has to choose, so the descriptions must be clearly distinguishable. Vague or overlapping descriptions are the usual cause of an agent picking the wrong tool.

Why is there a leftover langchain-google-genai dependency?

Answer honestly — it's a strength, not a weakness. "An earlier version used Gemini. I migrated to Groq for latency and more reliable tool-calling, and the dependency didn't get cleaned up. It's dead weight I'd remove — and it's a good argument for pinning versions and periodically auditing requirements.txt, since unused dependencies are also unnecessary supply-chain surface."

Section 06

LangGraph deep dive

LangGraph is the framework this project is really about. Expect the deepest questioning here. The core idea in one sentence: model your agent as a state machine — a graph of nodes that read and write a shared state object — so that loops, branches and interruptions become ordinary graph structure rather than tangled Python.

Why a graph instead of a chain

A LangChain chain is a directed acyclic pipeline: A → B → C. That's fine for "retrieve, then prompt, then generate". But a research agent needs to go backwards: after running a search, it must return to the reasoning step, possibly many times, and the number of times isn't known in advance. Expressing that with chains means writing a manual while loop and threading state by hand.

LangGraph gives you four things that loop specifically needs:

Cycles

An edge from tools back to chatbot is legal and normal. The loop is declared once, in the graph definition, not implemented imperatively.

Explicit typed state

State: TypedDict, Annotated and reducers

agent.pypython
class AgentState(TypedDict):
    messages:     Annotated[list, add_messages]
    loop_count:   int

Three things are happening in those four lines, and each is a likely question.

TypedDict

It's still a plain Python dict at runtime — no validation, no overhead. The typing is for your editor, for type checkers, and for LangGraph to know which keys exist. It's chosen over a Pydantic model because it's lightweight and dictionaries serialise trivially for checkpointing.

Annotated[list, add_messages] — the reducer

This is the single most important line in the state definition. A node returns a partial update, e.g. {"messages": [response]}. LangGraph must then decide how to merge that into the existing state. The default behaviour for a key is overwrite. If messages used the default, each node would replace the whole conversation with its one new message — and the agent would instantly forget everything.

add_messages is a reducer function that changes the merge rule to append. It also does real work beyond concatenation: it coerces tuples and dicts into proper Message objects, assigns IDs to messages that lack them, and — importantly — replaces rather than duplicates a message if an incoming message has the same ID as an existing one, which enables editing history.

The clean explanation to give

"A reducer answers the question: when a node returns a value for a key, what should happen to the value already in state? Overwrite is the default. For messages I want append, so I annotate the key with add_messages. For loop_count I actually want overwrite — the node computes the new count and replaces the old one — so it has no annotation. The state schema encodes merge semantics per field, which is much cleaner than handling it inside every node."

loop_count and max_searches

Both are plain int, so both overwrite. loop_count is written by the chatbot node each turn; max_searches is set once at the start from the request and then just carried along, read-only in practice. Putting the budget in the state rather than in a global is what allows two concurrent users to run different budgets against the same compiled graph.

Nodes

Casper has two nodes:

  • chatbot — a normal Python function you wrote. It builds the prompt, decides whether to bind tools, calls the LLM, applies the regex fallback, and updates the counter.
  • tools — ToolNode(tools), a prebuilt LangGraph component. It reads the last message, iterates its tool_calls, looks each name up in the tools list, executes it, and returns one ToolMessage per call with the matching tool_call_id. It also catches exceptions inside tools and returns them as tool messages so a failing tool doesn't kill the graph.

Edges: normal and conditional

agent.pypython
workflow.add_edge(START, "chatbot")          # unconditional
workflow.add_conditional_edges("chatbot", tools_condition)
workflow.add_edge("tools", "chatbot")        # the cycle
  • Normal edge — always go from A to B. Deterministic wiring.
  • Conditional edge — call a routing function with the state; the string it returns names the next node. This is where the LLM's decision becomes control flow.

tools_condition is a prebuilt router with a tiny job: look at the last message in state; if it has a non-empty tool_calls list, return "tools"; otherwise return END. Written by hand it would be about five lines:

what tools_condition does, conceptuallypython
def tools_condition(state):
    last = state["messages"][-1]
    if getattr(last, "tool_calls", None):
        return "tools"
    return END
Subtle but excellent point to raise unprompted

Notice that tools_condition knows nothing about the search budget. Casper does not enforce the limit in the router — it enforces it inside the chatbot node, by not giving the model any tools once the budget is spent. The model therefore produces a message with no tool calls, and tools_condition naturally routes to END. The budget is enforced by removing capability, not by intercepting the route. An alternative design would be a custom conditional edge that checks loop_count — mention that you considered it, and that the chosen approach is better because it also stops the model from wanting to search, avoiding a wasted LLM call that gets thrown away.

The graph, drawn

Two nodes, one cycle, one branch. Every research run of any length is a traversal of this graph.

Compilation and execution

workflow.compile() validates the graph (all referenced nodes exist, entry point is set, no dangling edges) and returns a Runnable — an executable object exposing .invoke(), .stream() and .astream(). The compiled object is stateless and reusable across requests; per-run state lives in the dict you pass in.

Execution proceeds in supersteps (a model borrowed from Google's Pregel graph-processing system). In each superstep, all currently-active nodes run, their state updates are merged through the reducers, and the outgoing edges determine which nodes are active next. A Casper run with two searches takes roughly six supersteps: chatbot → tools → chatbot → tools → chatbot → END.

Persistence: checkpointers (what Casper doesn't use, but you should know)

LangGraph can attach a checkpointer at compile time — workflow.compile(checkpointer=MemorySaver()) — which snapshots the full state after every superstep, keyed by a thread_id. That single addition unlocks: multi-turn conversations that remember previous runs, resuming after a crash, time-travel debugging (rewind to any earlier state), and human-in-the-loop approval via interrupt_before=["tools"], which pauses the graph before a tool executes so a person can approve it.

Casper compiles with no checkpointer, so every request is a fresh conversation. Knowing this gap and being able to describe exactly how you'd close it is one of the strongest things you can demonstrate about this project.

Interview questions · LangGraph

What is LangGraph and why did you use it instead of plain LangChain?

"LangGraph models an agent as a state machine — nodes are steps, edges are transitions, and there's one shared typed state object. I needed it because a research agent has to loop: reason, search, read, then reason again an unknown number of times. A LangChain chain is a directed acyclic pipeline, so implementing that would mean a manual while loop with state threaded by hand. LangGraph makes the cycle a declared edge from tools back to chatbot, and it gives me per-step streaming for free, which is what my live UI is built on."

Explain Annotated[list, add_messages].

"It attaches a reducer to the messages key. Nodes return partial updates, and LangGraph needs a merge rule. The default is overwrite — which for messages would mean every node wipes the conversation and replaces it with its single new message, so the agent would have no memory. add_messages changes the rule to append."

Then add the depth: "It does more than +=. It coerces tuples and dicts into Message objects, assigns IDs where missing, and if an incoming message has the same ID as an existing one it replaces it instead of duplicating — which is what allows editing or correcting history."

Why isn't loop_count annotated with a reducer?

Because overwrite is the correct semantics. The node reads the current count, computes count + 1 if a tool was called, and returns the new value to replace the old. If I'd annotated it with an adding reducer I'd have to return the delta instead of the total, which is easy to get wrong. Different fields want different merge rules, and that's exactly the flexibility the reducer system provides.

What does tools_condition do, and could you write it yourself?

"It's the routing function on the conditional edge out of the chatbot node. It inspects the last message: if it has tool calls, return the string 'tools'; otherwise return END. It's about five lines and I could absolutely write it by hand — I use the prebuilt one because it also handles the edge cases around message types consistently."

Where exactly is the search budget enforced, and why there?

"Inside the chatbot node, not in the router. When loop_count >= max_searches I call the LLM without binding tools, plus a system prompt telling it to summarise. With no tool schemas in the request the model literally cannot emit a tool call, so tools_condition sees a plain text message and routes to END naturally."

Why there rather than in the conditional edge: "Blocking it at the edge would mean the model still spends an LLM call requesting a search that I then discard. Removing the capability upstream means the same call becomes the summary — one call, not two, and the guarantee is structural rather than a prompt instruction the model might ignore."

What is a checkpointer and why doesn't Casper have one?

"A checkpointer persists the graph state after every superstep, keyed by a thread id. It gives you conversation memory across requests, crash recovery, time-travel debugging, and human-in-the-loop interrupts. Casper doesn't use one because each research query is self-contained — you ask a question, it researches, it's done — so every request starts from a fresh state."

Then the honest limitation: "That means you can't ask a follow-up question that builds on the previous run. Adding MemorySaver for development or a Postgres checkpointer for production, plus a thread_id from the frontend, is the first thing I'd add. It's a small change with a big behavioural payoff."

What are supersteps?

LangGraph borrows the Pregel/BSP execution model: in each superstep every active node runs, all their state updates are merged through the reducers, and the edges then determine which nodes are active in the next superstep. Because updates merge between supersteps rather than during, parallel nodes can't see each other's half-finished writes. The recursion_limit (default 25) counts supersteps, and is the framework-level backstop against an infinite loop.

What happens if a node raises an exception?

The exception propagates out of stream/astream and the run aborts. With no checkpointer, all progress is lost. Casper handles this at the API layer — main.py wraps the whole stream in try/except and emits an error SSE event so the frontend can show it rather than hanging. Exceptions inside a tool are different: ToolNode catches those and returns them to the model as a ToolMessage, giving the agent a chance to recover.

@tool
def web_search(query: str) -> str:
    """Searches the web using DuckDuckGo to get real-time information and answer questions."""
    from duckduckgo_search import DDGS
    try:
        with DDGS() as ddgs:
            results = list(ddgs.text(query, max_results=5))
            if not results:
                return f"No results found for query: {query}"

            formatted_results = []
            for r in results:
                title = r.get("title", "No Title")
                href  = r.get("href", "")
                body  = r.get("body", "")
                formatted_results.append(f"Title: {title}\nURL: {href}\nSnippet: {body}\n---")
            return "\n\n".join(formatted_results)
    except Exception as e:
        # Fallback to DuckDuckGoSearchRun if DDGS fails
        try:
            search = DuckDuckGoSearchRun()
            return search.run(query)
        except Exception as e2:
            return f"Search error: {str(e)}"

tools = [web_search]

Design points to be ready to discuss:

  • Returns a string, never raises. Every failure path returns text. That's deliberate — the return value goes into a ToolMessage and back to the model, so "No results found for query: X" is something the model can reason about and respond to by trying a different query. An exception would just kill the graph.
  • The Title: / URL: / Snippet: / --- format is a contract. It's readable by the LLM and parseable by the frontend's parseSearchResults(), which splits on --- and reads the prefixes. Same string, two consumers.
  • Local import. from duckduckgo_search import DDGS inside the function keeps module import fast and isolates a heavy/fragile dependency to the moment it's needed.
  • Two-tier fallback. The modern DDGS client first; if it fails (rate limiting is common with DuckDuckGo), LangChain's older DuckDuckGoSearchRun; if that also fails, an error string. Graceful degradation.
  • max_results=5. A deliberate context-budget choice — enough coverage without flooding the window, which matters because these results are re-sent on every subsequent loop.
A real bug — bring this up yourself

In the inner except, the message interpolates e (the first error), not e2 (the one that actually just happened). So when the fallback fails you are shown the primary failure reason, and the fallback's own error is silently swallowed. Volunteering this — "here's a bug I found in my own code and here's the one-word fix" — is one of the most credibility-building things you can do in a technical interview.

The chatbot node, part 1: choosing a model configuration

agent.pypython
def chatbot_node(state: AgentState):
    loop_count   = state.get("loop_count", 0)
    max_searches = state.get("max_searches", 4)

    llm = ChatGroq(model="llama-3.1-8b-instant", temperature=0)

    from langchain_core.messages import SystemMessage

    if loop_count >= max_searches:
        llm_to_call = llm                                   # NO tools bound
        system_prompt = SystemMessage(content=
            f"You are Casper... You have reached the maximum search limit "
            f"({max_searches} searches). DO NOT search anymore or call any tools. "
            f"Analyze the information you have already gathered and write the final summary.")
    else:
        llm_to_call = llm.bind_tools(tools)                  # tools available
        system_prompt = SystemMessage(content=
            "You are Casper, an autonomous web research assistant. "
            "Use the web_search tool to find real-time information... "
            "Do not perform redundant or repeated searches... "
            "When synthesizing findings, cite URLs from search results in your response.")

    messages = [system_prompt] + state["messages"]
    response = llm_to_call.invoke(messages)

The three decisions encoded here:

  • Budget check first. loop_count >= max_searches selects between two entirely different agent behaviours. This branch is the project's signature feature.
  • Capability removal, not instruction. In the exhausted branch, llm_to_call is the bare model. No tool schemas go over the wire, so a tool call is not just discouraged — it's impossible.
  • The system prompt is prepended, not stored. [system_prompt] + state["messages"] builds the request list without ever putting the system message into state. Consequence: it never accumulates (you don't end up with five system messages after five loops), and it can change between iterations — which is exactly what the budget branch needs.
Inefficiency worth naming before they do

ChatGroq(...) is constructed inside the node, so a new client object is built on every single loop iteration. It's cheap (no connection is opened at construction) but it's wasteful and it means the model can't be configured per-deployment without editing the function. Hoisting it to module scope, or reading the model name from an environment variable, is a clean improvement to propose.

The chatbot node, part 2: the tool-call rescue

This block is the most interesting code in the repository and makes a genuinely good interview story.

agent.pypython
    if not getattr(response, "tool_calls", None) and response.content:
        import re, json, uuid

        # Matches <tool_name>{...json...}</function>  or  <tool_name>{...}</tool_name>
        pattern = r"<(\w+)>(\{[\s\S]*?\})(?:</function>|</\1>)"
        matches = re.finditer(pattern, response.content)
        parsed_tool_calls = []
        for match in matches:
            tool_name = match.group(1)
            args_str  = match.group(2)
            try:
                args = json.loads(args_str)
                parsed_tool_calls.append({
                    "name": tool_name,
                    "args": args,
                    "id": f"call_{uuid.uuid4().hex[:8]}",
                    "type": "tool_call",
                })
            except Exception:
                pass

        if parsed_tool_calls:
            response.tool_calls = parsed_tool_calls
            response.content = ""   # hide the raw tags from the UI

What problem does this solve?

Native tool calling means the provider returns tool calls in a dedicated structured field. But open-weight models like Llama were trained to express tool use as text, and sometimes the model falls back to that habit — emitting something like <web_search>{"query": "AI regulation India"}</function> inside the message content instead of populating the structured field.

When that happens, tool_calls is empty, so tools_condition routes to END, and the user sees raw XML-ish garbage as their "answer". The agent silently fails.

This block is a repair layer: only when the structured field is empty and there is text content, it scans for that pattern, parses the JSON, synthesises properly-shaped tool call dicts (with a unique ID, since the model didn't provide one), assigns them to response.tool_calls, and blanks the content so the tags never reach the UI. From that point on, the rest of the graph can't tell the difference.

Decoding the regex, since you may be asked:

FragmentMeaning
<(\w+)>An opening tag; capture group 1 is the tool name (word characters).
(\{[\s\S]*?\})Capture group 2: a JSON object. [\s\S] matches any character including newlines; *? is lazy so it stops at the first closing brace rather than the last.
(?:...|...)A non-capturing group — grouping without creating a third capture.
</function>|</\1>Either a literal </function> or a backreference closing tag matching whatever group 1 captured.
Be ready for the pushback

A sharp interviewer will say: "parsing model output with a regex is fragile." Agree, and show you understand the trade-off. The honest answer: "It is. It's a defensive patch for a specific observed failure mode, and it's strictly additive — it only runs when the structured path already produced nothing, so it can't break the happy path. The proper fixes are to use a model with more reliable native tool-calling, or to add a retry that re-prompts the model for well-formed output. Given I was on a free tier with an 8B model, the patch was the pragmatic choice, but I'd treat it as technical debt." Also note the nested-JSON limitation: the lazy *? stops at the first }, so an argument object containing a nested object would be truncated and fail json.loads — at which point the except: pass quietly drops it.

Section 08

Groq, Llama 3.1 & model choice

Groq is not a model — it's an inference platform

The most common confusion. Groq doesn't train models; it runs open-weight models (Llama, Mixtral, Gemma) extremely fast on custom hardware it calls an LPU — a Language Processing Unit.

Why it's fast, at the level a non-hardware interview needs: GPUs are built for massively parallel throughput and were adapted for LLM inference, where token generation is inherently sequential — each token depends on the last — and performance is bound by how fast weights can be moved from memory. The LPU is a deterministic, sequentially-oriented architecture with a much tighter memory path, which removes that bottleneck. The practical result is dramatically higher tokens-per-second than typical GPU-served endpoints.

Why this matters specifically for Casper

An agent makes many sequential LLM calls — a four-search run is roughly five round-trips, each waiting on the previous one. Latency doesn't add, it compounds. If each call takes 8 seconds, the user waits 40 seconds and gives up. Cut it to 1.5 seconds and the same run feels instant. Groq wasn't chosen because it's trendy; it was chosen because agentic loops are latency-multiplying by nature. That's the answer that lands.

Why llama-3.1-8b-instant

ConsiderationReasoning
Native tool-callingLlama 3.1 was explicitly trained for function calling and Groq exposes it through the OpenAI-compatible tools API. Many small models can't do this reliably at all.
SpeedThe 8B variant is the fastest tier — the "instant" in the name. Critical for a multi-call loop.
CostGroq's free tier makes an 8B model effectively free for a portfolio project. A 70B model would be slower and costlier for a task that is mostly "decide to search" and "summarise text".

FastAPI, async & Server-Sent Events

Theory for the backend before the line-by-line. This section is pure computer science and comes up in interviews far beyond this project.

Synchronous vs. asynchronous, properly explained

A traditional synchronous server handles each request on a thread. When that request waits on the network — say, four seconds for an LLM response — the thread sits blocked doing nothing. Threads are expensive (memory, context switching), so throughput collapses under I/O-heavy load.

Async uses a single-threaded event loop. When a coroutine hits an await, it yields control back to the loop, which runs other work until the awaited operation completes. One thread interleaves thousands of waiting requests.

The one-line version

Async doesn't make anything faster — it stops you from wasting time while waiting. It's a win for I/O-bound work (network, disk, database) and no help at all for CPU-bound work, which just blocks the loop for everyone. Casper is almost entirely I/O-bound: waiting on Groq and waiting on DuckDuckGo. Async is exactly right here.

The trap that catches people

In an async def function, calling a blocking library freezes the entire event loop — not just that request. Every other user's stream stalls. This is why main.py uses app.astream(...) rather than app.stream(...): the synchronous version would block the loop for the whole multi-second research run. If you must call blocking code, you push it to a thread pool with await asyncio.to_thread(...) or run_in_executor.

Generators and async generators

A normal function returns once. A generator uses yield to produce a sequence of values lazily, pausing after each one and resuming where it left off. An async generator is the same idea in an async function: it can both yield values and await between them.

That's exactly the shape of an SSE endpoint: await the next graph event, then yield it to the client, repeat. Memory stays constant regardless of how long the run is, because nothing is accumulated — each event is emitted and forgotten.

ASGI vs. WSGI

WSGI (Flask, older Django) is the synchronous Python web standard: one request, one blocking call, one response. It has no vocabulary for long-lived connections or streaming. ASGI is the async successor, and it supports streaming responses and WebSockets natively. FastAPI is an ASGI framework; uvicorn is the ASGI server that runs it. This is why Casper's stack is FastAPI and not Flask — SSE with a slow, long-lived generator is exactly what ASGI exists for.

Server-Sent Events

SSE is a small W3C standard for server-to-client streaming over ordinary HTTP. The client opens a normal GET request with Accept: text/event-stream; the server keeps the connection open and writes text frames as things happen.

the SSE wire formattext/event-stream
event: message
data: {"type":"search_start","query":"India AI regulation 2026","loop_count":1}

event: message
data: {"type":"search_result","content":"Title: ...","loop_count":0}

event: message
data: {"type":"done"}

The rules are simple: fields are field: value lines, and a blank line terminates an event. data: is the payload — always a string, which is why Casper wraps everything in json.dumps() on the server and JSON.parse() in the browser. Optional id: and retry: fields support automatic reconnection.

Two SSE limitations to know

1. EventSource only issues GET requests and can't set custom headers — which is precisely why Casper's endpoint is GET /api/research?query=... with parameters in the query string rather than a POST body. That also means long queries can hit URL length limits, and it complicates Authorization headers (you'd need a cookie or a token in the query string).
2. Over HTTP/1.1 browsers allow only ~6 connections per origin, and an open SSE stream holds one for its whole lifetime. HTTP/2 multiplexing removes this.

CORS

Browsers enforce the same-origin policy: a page from http://localhost:5173 may not read a response from http://127.0.0.1:8000 unless the server opts in. Different port means different origin — origin is scheme + host + port. CORS is that opt-in, expressed as response headers.

For "non-simple" requests the browser first sends an OPTIONS preflight asking whether the real request is allowed. Casper's CORSMiddleware answers these. Note that an EventSource GET is a simple request, so it isn't preflighted — but the Access-Control-Allow-Origin header is still required on the response.

The security point to raise before they do

Casper sets allow_origins=["*"] together with allow_credentials=True. That combination is invalid per the CORS spec — browsers reject a wildcard origin when credentials are allowed — so it works only because nothing here actually sends credentials. In any real deployment you replace the wildcard with the specific frontend origin. Saying "my CORS config is wide open, that's a demo convenience and here's the exact fix" is a strong, security-aware answer.

Interview questions · Backend theory

Why FastAPI and not Flask or Django?

"Native async, which this workload genuinely needs. A research run holds a connection open for tens of seconds while doing almost nothing but waiting on the network. Use a concrete analogy: "One waiter serving twenty tables. Synchronous is taking an order, walking to the kitchen, and standing there until that dish is ready before speaking to anyone else. Async is placing the order and immediately serving the next table — the kitchen signals you when it's done. Same one waiter, far more tables served, because the time was spent waiting, not working."

Then translate: "await is where you hand control back to the event loop. It only helps for I/O-bound work — if the waiter has to personally chop vegetables for ten minutes, that's CPU-bound and nobody else gets served."

Why SSE instead of WebSockets?

"Because after the initial request the data flow is entirely one-directional. The client asks a question and then only listens — it never sends anything mid-run. SSE is designed for exactly that, and it's plain HTTP, so it passes through proxies and infrastructure without special handling and gets automatic browser reconnection for free. A WebSocket gives me a duplex channel I have no use for, plus manual reconnection logic. Choose the simpler protocol that fits the data flow."

If pushed: "If I added the ability to interrupt a running agent, or human-in-the-loop approval before a tool executes, the client would need to send messages mid-run and I'd switch to WebSockets."

Why is the endpoint a GET with query parameters instead of a POST?

"Because the browser's EventSource API only supports GET and doesn't allow custom headers — that's a hard constraint of the standard, not a design preference. So the query and the budget travel in the query string."

Show you know the costs: "That means long queries risk URL length limits, the query text ends up in server and proxy access logs which is a mild privacy concern, and adding an Authorization header isn't possible — I'd need a cookie or a token in the URL. If those mattered I'd use fetch with a ReadableStream and parse the SSE frames myself, which allows POST and headers, at the cost of losing free reconnection."

What is CORS and why did you need it?

"The browser's same-origin policy blocks a page on one origin from reading responses from another. My frontend runs on port 5173 and my API on 8000 — different port means different origin — so without CORS headers the browser refuses to hand the response to my JavaScript. CORSMiddleware adds Access-Control-Allow-Origin and answers preflight OPTIONS requests."

Add the critique unprompted: "Mine is allow_origins=['*'], which is a demo convenience. In production that becomes the specific frontend origin. It's also worth knowing CORS is enforced by the browser, not the server — it protects users, not the API. A permissive CORS policy isn't a server vulnerability by itself, but it removes a protection your users rely on."

What happens if the user closes the browser tab mid-run?

"The TCP connection drops. Starlette detects the client disconnect and cancels the generator, which raises inside it and stops iteration. But there's a real caveat: cancellation happens when the generator next tries to yield, so an LLM call already in flight will still complete and still be billed. With no checkpointer, partial work is simply discarded. Making this robust means checking await request.is_disconnected() and, ideally, running the agent as a background task writing to a queue so it can be cancelled or resumed independently of the connection."

The event generator

main.pypython
    async def event_generator():
        state = {"messages": [("user", query)],
                 "loop_count": 0,
                 "max_searches": max_searches}

        try:
            async for event in app.astream(state):
                for node_name, node_state in event.items():
                    latest_message = node_state['messages'][-1]
                    loop_count = node_state.get('loop_count', 0)

                    if node_name == "chatbot":
                        if latest_message.tool_calls:
                            for tool_call in latest_message.tool_calls:
                                yield {"event": "message", "data": json.dumps({
                                    "type": "search_start",
                                    "query": tool_call['args'].get('query'),
                                    "loop_count": loop_count})}
                        elif latest_message.content:
                            yield {"event": "message", "data": json.dumps({
                                "type": "chatbot_response",
                                "content": latest_message.content,
                                "loop_count": loop_count})}
                    elif node_name == "tools":
                        yield {"event": "message", "data": json.dumps({
                            "type": "search_result",
                            "content": latest_message.content,
                            "loop_count": loop_count})}

            yield {"event": "message", "data": json.dumps({"type": "done"})}

        except Exception as e:
            yield {"event": "message", "data": json.dumps({
                "type": "error", "message": str(e)})}

    return EventSourceResponse(event_generator())

What's happening, step by step

  • Fresh state per request. loop_count starts at 0 and max_searches comes from the URL. Because it's constructed inside the handler, two concurrent users never share state.
  • async for … in app.astream(state). The async iterator drives the graph. In the default "updates" mode, each yielded event is a dict shaped {node_name: partial_update} — the update that node just returned.
  • Translation, not forwarding. The handler doesn't dump LangGraph internals to the browser; it maps them onto a small, stable, UI-oriented vocabulary of four event types. This is a real API design decision — the frontend is decoupled from LangGraph's object model.
  • Branch on node. A chatbot update with tool calls becomes one search_start per call (carrying the query the model invented — this is what makes the reasoning visible). A chatbot update with content becomes chatbot_response. A tools update becomes search_result.
  • Sentinel events. done after the loop exits normally tells the client to close the connection and stop the spinner; error from the except does the same on failure. Without an explicit terminator the client can't distinguish "finished" from "still thinking".
  • EventSourceResponse. Takes the async generator, sets Content-Type: text/event-stream and the anti-buffering headers, and formats each yielded dict into the SSE wire frames.
The four event types — memorise this table

search_start the model decided to search, here's its query · search_result the search ran, here's the raw formatted text · chatbot_response the model wrote prose (interim or final) · done / error terminators.

Two subtleties in this file

1 · loop_count on tool events is always 0

With stream_mode="updates", node_state is the partial dict the node returned. ToolNode returns only {"messages": [...]} — it never touches loop_count — so node_state.get('loop_count', 0) falls back to 0 for every search_result event. The frontend then does if (data.loop_count !== undefined) setCurrentLoopCount(data.loop_count), so the progress counter momentarily drops back to 0 after each search before the next search_start corrects it. Fixes: read the counter only from search_start events, omit the field on tool events, or switch to stream_mode="values" where the full state is always present. Bringing this up unprompted is exactly the kind of detail that separates candidates.

2 · The final answer is identified by position, not by a flag

Every chatbot_response looks identical on the wire, so the frontend simply overwrites finalAnswer each time one arrives — the last one standing is the summary. It works because the summary is always last, but it's implicit. A cleaner protocol would put "is_final": true on the terminating message, or attach the summary to the done event.

Interview questions · main.py

Walk me through the API layer.

"One GET endpoint. It builds a fresh graph state from the query parameters, then iterates app.astream(state) asynchronously. Each iteration gives me the name of the node that just ran plus the update it produced, and I translate that into one of four simple event types — search_start, search_result, chatbot_response, and a done/error terminator — which I JSON-encode and yield. EventSourceResponse wraps the async generator into the SSE wire format. The whole thing is inside a try/except so a failure reaches the user as an event rather than a dropped connection."

Emphasise the translation: "I deliberately don't leak LangGraph's object model to the browser. The frontend codes against my four event types, so I could swap the agent framework entirely without touching the UI."

Why astream and not stream or invoke?

Three-part answer. Not invoke: it returns only the final state after everything finishes, so the user would stare at a spinner for 30 seconds and the entire "visible thought process" feature would be impossible. Not stream: it's synchronous, so inside an async def handler it would block the event loop for the whole run — every other user's request would freeze. astream yields each node's update as it happens and awaits properly, so one event loop serves many concurrent research runs.

Why send a done event? Doesn't the connection just close?

"Because EventSource treats a closed connection as a failure and automatically tries to reconnect — which would silently re-run the entire research query. An explicit done event lets the client call eventSource.close() deliberately, stop the loading state, and save the run to history. It's the difference between the client knowing it succeeded and the client guessing."

The try/except catches bare Exception and sends str(e) to the client. Any concerns?

Two, and naming them is the point of the question. Information disclosure — raw exception text can leak file paths, library versions, or fragments of an API key in a provider error message. Production should return a generic message plus a correlation ID and log the detail server-side. Over-broad catching — it swallows programming errors like KeyError exactly like it swallows network failures, so bugs get reported to the user as if they were transient. I'd catch specific exception types, log with a stack trace, and distinguish retryable from fatal.

How does the frontend know which response is the final answer?

"It doesn't, explicitly — it overwrites finalAnswer on every chatbot_response, so the last one wins. That's correct in practice because the summary is always the final message, but it's an implicit contract. I'd add an is_final flag or carry the summary on the done event so the client isn't inferring meaning from ordering."

The React frontend

React fundamentals you must be able to state

  • Declarative UI. You describe what the UI should look like for a given state; React works out the DOM changes. You never write document.createElement.
  • Virtual DOM & reconciliation. React keeps an in-memory tree, diffs the new tree against the old on each render, and applies the minimal set of real DOM mutations. Real DOM operations are expensive; diffing objects is cheap.
  • Components & props. Functions returning JSX; props flow one way, parent to child.
  • State triggers renders. Calling a setter schedules a re-render. Mutating a variable directly does not.
  • Keys. When rendering a list, key tells React which element is which across renders so it can move rather than rebuild. Casper uses the array index for logs (acceptable — logs are append-only and never reordered) and entry.id for history (correct — those get deleted).

Interview questions · React & frontend

Why setLogs(prev => [...prev, data]) instead of setLogs([...logs, data])?

"Because React state updates are asynchronous and batched, and the logs variable inside the callback is captured from the render in which the handler was created. Generalise it: "The rule is that whenever the next state depends on the previous state, use the updater function."

What is useRef and why not useState for the scroll anchor?

"useRef gives a mutable box that persists across renders and — crucially — changing .current does not trigger a re-render. Two uses: holding DOM nodes, and storing values you need to survive renders but don't want to render from."

"Here it holds the sentinel div at the bottom of the log list so I can call scrollIntoView on it. Using state would be wrong twice over: I'd trigger a re-render for something that has no visual output, and DOM nodes aren't values you render anyway."

Explain the dependency array in useEffect.

"It tells React when to re-run the effect. Omitted entirely: after every render. Empty array: once after mount — that's my theme and history loader. With values: whenever any of them changes by reference/value comparison — [logs] re-runs my auto-scroll each time a new log arrives."

What is the virtual DOM?

"A lightweight JavaScript representation of the UI tree. On a state change React builds a new tree and diffs it against the previous one, then applies only the minimal set of real DOM mutations. Real DOM operations trigger layout and paint and are expensive; comparing plain objects is cheap."

Show nuance: "It isn't magically fast — it's a trade that buys you a declarative programming model at an acceptable performance cost. Frameworks like Svelte and Solid get similar results by compiling away the diff instead."

Why is key needed in lists, and is the index acceptable?

"Keys let React identify which element is which between renders so it can move and reuse DOM nodes instead of rebuilding them, and so component state stays attached to the right item. The index is fine when the list is append-only and never reordered or filtered — which is true of my log list. It's not fine for the history sidebar, because entries get deleted from the middle, so I use entry.id there. Using the index on a mutable list causes state to attach to the wrong row."

Would you refactor this 600-line component?

Yes, and have a plan rather than a vague "split it up". Extract presentational components — <LogCard>, <SourceCard>, <HistorySidebar>, <SummaryPanel>. Extract a useResearchStream(query, budget) custom hook holding the EventSource lifecycle, so streaming logic is testable in isolation. Extract a useLocalStorageHistory() hook. Move the Markdown renderer and the search-result parser into pure utility modules with unit tests.

Then defend the current state: "For a single-screen app it's still navigable, and premature abstraction has its own cost — but it's past the size where I'd want it split."

How does the theme switch work without re-rendering every component?

"The colours are CSS custom properties declared on :root and redeclared under a [data-theme="light"] selector. Switching sets one attribute on <html>, and the browser recalculates styles — no React re-render of the tree is needed for the visual change. Only the toggle button's icon depends on React state. It's the CSS cascade doing the work instead of JavaScript."

What state management library did you use?

"None — plain useState. There's one screen and one component tree, so there's no prop-drilling problem and no cross-page shared state. Adding Redux or Zustand would be ceremony without benefit. If the app grew to multiple routes with a shared session, I'd reach for Context first and only add a library if I hit real performance or complexity problems."

Section 13

End-to-end data flow

If you can narrate this from the keystroke to the rendered summary, you can handle almost any "how does your project work" question. Practise saying it out loud.

The same journey in words

  • Submit. The user types a question and picks a budget. handleSearch resets state, sets searching = true, and opens an EventSource to the backend with the query URL-encoded.
  • Request. FastAPI validates the parameters, builds {messages: [("user", query)], loop_count: 0, max_searches: N} and begins iterating app.astream(state).
  • First reasoning turn. The chatbot node sees loop_count 0 < N, so it binds the tools and prepends the research system prompt, then calls Groq.
  • The decision. Llama returns an AIMessage with a web_search tool call and a query it wrote itself. The node bumps loop_count to 1 and returns the update.
  • First stream event. main.py sees a chatbot update carrying tool calls and emits search_start. The browser renders a "Reasoning Loop" card showing the query — the user is now watching the agent think.
  • Route. tools_condition finds tool calls and routes to the tools node.
  • Act. ToolNode executes web_search. DuckDuckGo returns five results, which are formatted into the Title/URL/Snippet string and appended as a ToolMessage.
  • Second stream event. search_result goes out; parseSearchResults splits it and renders collapsible source cards with favicons.
  • Loop back. The unconditional tools → chatbot edge returns control to the reasoning node — now with the search results in its context.
  • Decide again. Either the model requests another search (repeat from step 4), or it has enough and writes prose. If loop_count has reached the budget, the node silently switches to the unbound model and the summarise prompt, forcing prose.
  • Finish. A content-only AIMessage means no tool calls, so tools_condition routes to END. main.py emits chatbot_response then done.
  • Render. The frontend closes the stream, drops the spinner, renders the summary through renderMarkdown with clickable citations, and writes the whole run to localStorage.

Interview questions · Data flow

Trace what happens when I type a question and hit enter.

Narrate the twelve steps above, but compress to the five transitions that matter: browser opens an SSE connection → FastAPI builds fresh state and starts streaming the graph → chatbot node calls Groq with tools bound, model returns a tool call → ToolNode searches DuckDuckGo and the result is appended to state, then the graph loops back → once the model answers with prose instead of a tool call (or the budget forces it to), the graph ends and the summary streams out.

Mention the streaming at every stage: "each of those transitions emits an SSE event, so the UI is narrating the agent's reasoning in real time rather than showing a spinner."

Where does the state live at each point?

Three separate places, and being crisp about this shows architectural clarity: graph state — the messages list and counters, in memory inside a single astream call, discarded when the request ends; UI state — the React hooks, alive until page reload; persisted state — the history and theme in localStorage, surviving reloads. Nothing is stored server-side at all, which is exactly why there's no follow-up-question capability.

How long does a typical run take, and what dominates?

"A four-search run is five sequential LLM calls plus four searches. On Groq the LLM calls are fast — often under a second or two each — so the DuckDuckGo round-trips and the strictly sequential structure dominate. Roughly 10–25 seconds end to end."

The optimisation to name: "The searches are sequential because each reasoning step decides the next query based on the last result. If the model requested multiple queries in one turn, ToolNode could run them concurrently — that's the single biggest latency win available, and it's a change to how I prompt rather than to the graph."

Testing — the question that catches most candidates

There are no tests in this repo. Don't pretend otherwise; instead show that you know precisely what you'd test and how you'd make an LLM system testable at all.

Pure functions — easy

parseSearchResults, renderMarkdown, getDomain and the tool's result formatter are deterministic. Straight unit tests with Vitest and pytest, including malformed input.

The node — mock the LLM

Call chatbot_node with a fake model returning a canned AIMessage. Assert that loop_count increments only on tool calls, and that at loop_count == max_searches the response carries no tool calls.

The graph — fake tools

Replace web_search with a stub returning fixed text, then assert the traversal sequence and that the run terminates within the budget. Deterministic, no network, fast.

The API — TestClient

FastAPI's TestClient against a graph with a stubbed model: assert the exact sequence of SSE event types, and that done always arrives last.

Model quality — evals, not asserts

You can't assert on generated prose. Build a small eval set of questions with expected facts, run periodically, and score with an LLM-as-judge or keyword checks. Track it as a metric, not a pass/fail gate.

The lesson

The testable design principle: keep the non-deterministic part small and inject it. Everything around the LLM call can be deterministic if the model is a parameter rather than a hardcoded constructor call — which is another argument for hoisting ChatGroq out of the node.

Interview questions · Critique

What's the weakest part of your project?

Pick one real thing and go deep — vagueness reads as evasion. Strong choice: "The absence of tests, and the fact that the design makes testing harder than it needs to be. The ChatGroq instance is constructed inside the node, so I can't inject a fake model without patching. If I'd taken the model as a parameter, the entire node — budget logic, counter, regex fallback — would be deterministically testable. Alternative if they push on the agent itself: the coupling between the tool's text output format and the frontend parser.

If I gave you a week, what would you add?

Prioritise and justify, don't list. "Day 1–2: a checkpointer plus a thread id, so follow-up questions work — that's the biggest jump in perceived intelligence for the least code. Security checklist

  • Secrets. .env is gitignored — good. Production should use a platform secret manager, and the key should be rotatable. Never log the key, and be careful that provider error messages echoed to the client don't contain it.
  • CORS. Replace ["*"] with the exact frontend origin, and drop allow_credentials unless genuinely needed.
  • Input validation. Bound max_searches server-side and cap query length — both are DoS and cost-abuse vectors today.
  • Rate limiting & auth. The endpoint is unauthenticated, so anyone who finds the URL spends your API quota. At minimum, per-IP rate limiting; realistically, an API key or session.
  • Prompt injection. Web content enters the model's context. Delimit tool output and instruct the model to treat it as data; strip HTML and control characters; cap snippet length. The strongest structural defence is already in place — the only tool is read-only search, so a successful injection can't take a destructive action.
  • XSS. Already mitigated: the Markdown renderer builds React elements, so model output is escaped rather than injected. If a Markdown library is ever adopted, it must not use dangerouslySetInnerHTML without sanitisation.
  • Error disclosure. Stop sending str(e) to the browser.
  • Dependency hygiene. requirements.txt has no version pins and contains an unused package. Pin versions, remove dead dependencies, and scan for CVEs.

Feature roadmap, ranked by value per unit of effort

  • Checkpointer + thread id — unlocks follow-up questions. Biggest perceived intelligence gain for the smallest change.
  • Parallel tool execution — prompt the model to issue several queries at once; ToolNode can run them concurrently. Largest latency win.
  • Page fetching, not just snippets — a second tool that retrieves and extracts full article text so the model reasons over substance rather than two-line previews.
  • A reflection node — an explicit graph node that critiques the draft summary against the gathered sources and can route back for one more search. This is where the graph structure really pays off: a third node and one more conditional edge.
  • Streaming the final answer token by token — switch to stream_mode="messages" so the summary types out instead of appearing at once.
  • Human-in-the-loop — interrupt_before=["tools"] to let the user approve or edit a search query before it runs. Requires WebSockets for the reply channel.
  • Source deduplication and ranking — track seen URLs in state and prefer fresh domains, so repeated loops broaden coverage instead of re-reading the same page.

Interview questions · Production

How would you scale this to 10,000 concurrent users?

Structure the answer by bottleneck, not by technology. "The web tier isn't the problem — those connections are mostly idle waiting on I/O, and async handles that well with a few uvicorn workers behind a load balancer. The real ceilings are the LLM provider rate limit and cost."

"So: decouple the run from the connection — a background worker executes the graph and publishes events to Redis, and the SSE endpoint just subscribes, which also means a reconnecting user rejoins their run instead of restarting it. Add per-user rate limiting and a queue with backpressure so I degrade gracefully rather than getting 429s from Groq. Cache identical queries. And add tracing, because at that scale I need to see cost per run before the bill tells me."

What are the security risks in an LLM agent specifically?

Name the ones unique to LLMs, not just generic web security:

  • Prompt injection — untrusted retrieved content carrying instructions the model may follow. The core problem is that data and instructions share one channel.
  • Excessive agency — the more tools an agent has, the worse a successful injection is. Casper's blast radius is small because its only tool is read-only search; an agent with file or email access is a different risk class entirely.
  • Output handling — model output rendered as HTML or executed as code is an XSS or RCE path. Mine builds React elements, so it's escaped.
  • Denial of wallet — an unauthenticated agent endpoint costs real money per call, so abuse is a billing attack, not just a load attack.
  • Sensitive data leakage — anything in the context can appear in output; don't put secrets in prompts.
How would you add multi-turn conversation?

"Three changes. Compile with a checkpointer: workflow.compile(checkpointer=PostgresSaver(...)). Pass a config with a thread_id on every invocation: app.astream(state, config={'configurable': {'thread_id': tid}}). Have the frontend generate and store a thread id per conversation and send it with each request."

"Then the state key becomes important: on a follow-up I'd pass only the new user message, because add_messages appends it to the checkpointed history rather than replacing it. I'd also need to reset loop_count to 0 for each new turn while keeping the message history — otherwise the second question would start with the budget already spent. That's a nice illustration of why per-field reducer semantics matter."

How would you reduce cost per query?

Attack the token count, because that's what you pay for. "Truncate snippets before they enter context; cap results per search at five, which I already do; summarise or drop older tool messages after a few loops so the history stops growing linearly; cache identical search queries; and use a small model for the loop decisions with a larger one only for the final synthesis. The search budget itself is already the crudest and most effective control — it puts a hard ceiling on the worst case, which is what actually protects the bill."

Your agent uses one tool. How would the design change with twenty?

"The graph wouldn't change at all — ToolNode and bind_tools both take a list. What breaks is the model's ability to choose well: twenty tool descriptions is a lot of context and a lot of ambiguity, and small models start picking wrongly."

"So the changes are about selection, not plumbing: retrieve a relevant subset of tools per query rather than binding all twenty; or group them behind specialist sub-agents with a supervisor node routing between them — which is exactly the multi-agent pattern LangGraph is designed for, since each sub-agent is just another node. I'd also add per-tool permissioning, because with twenty tools some of them will have side effects."

Rapid-fire, HR answers & study plan

Rapid-fire technical

One-line answers — drill these

What is an agent, in one sentence?

An LLM that decides its own control flow — which tools to call, in what order, and when to stop — instead of following a sequence the developer fixed in advance.

What is a reducer in LangGraph?

A function that defines how a node's returned value merges into existing state for a given key. Default is overwrite; add_messages makes it append.

What does bind_tools actually send?

A JSON schema per tool — name, description from the docstring, and a parameter object derived from the type hints — attached to the model request.

Who executes the tool?

Your code — LangGraph's ToolNode. The model only emits a structured request; it cannot run anything.

Why temperature=0?

Deterministic tool selection and valid JSON arguments; randomness in a structured field produces malformed calls.

What terminates the graph?

tools_condition routes to END when the last message has no tool calls — which happens either because the model is satisfied, or because the budget removed its tools.

SSE in one sentence?

A one-way server-to-client stream over ordinary HTTP, where the server writes data: lines separated by blank lines and the browser's EventSource reconnects automatically.

Why is the endpoint GET?

EventSource only supports GET and can't set custom headers.

Why async on the backend?

The workload is I/O-bound — waiting on Groq and DuckDuckGo — so one event loop can interleave many concurrent runs instead of blocking a thread each.

Why the functional form of setState?

Because updates are batched and the closed-over variable can be stale; when new state depends on old state, always use the updater function.

What is useRef for?

A mutable value that survives renders without triggering one — here, a handle on the DOM node used for auto-scrolling.

What is CORS protecting?

The user, not the server. It's a browser-enforced rule stopping one origin's JavaScript from reading another origin's responses.

Difference between LangChain and LangGraph?

LangChain gives the components (models, tools, messages) and linear chains; LangGraph gives stateful orchestration with cycles, branches and persistence.

What is ReAct?

Interleaving Reasoning and Acting: Thought → Action → Observation → repeat, so each reasoning step is grounded in real retrieved evidence.

What's a superstep?

One round of graph execution: all active nodes run, updates merge through reducers, edges determine what's active next. The recursion_limit counts these.

Biggest risk in your project?

Prompt injection through untrusted web content — mitigated mainly by the fact that the only tool is read-only search, so the blast radius is small.
