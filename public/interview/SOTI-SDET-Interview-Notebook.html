03 · The core

Testing fundamentals

This is the section where developers usually lose the interview — not because the ideas are hard, but because they've never had to say them precisely. Learn these as vocabulary. Precision here signals "this person has thought about quality", vagueness signals "this person wants a dev job".

Verification vs validation

Verification: are we building the product right? Does it match the specification? Reviews, static analysis, unit tests. Validation: are we building the right product? Does it solve the user's actual problem? Functional and acceptance testing.

One-liner to remember: verification checks the blueprint, validation checks the building.

SDLC and STLC

SDLC is the software lifecycle: requirements → design → development → testing → deployment → maintenance. STLC is the testing lifecycle that runs alongside it:

  1. Requirement analysis — what's testable, what's ambiguous. A tester's most valuable hour is here: a bad requirement caught now costs nothing.
  2. Test planning — scope, strategy, resources, schedule, risk.
  3. Test case development — cases, scripts, test data.
  4. Environment setup — builds, devices, data, stubs.
  5. Test execution — run, log defects, retest.
  6. Test closure — reports, metrics, lessons.

Entry criteria = what must be true before a phase starts (build deployed, environment ready, cases reviewed). Exit criteria = what must be true to stop (all high-priority cases run, no open critical defects, coverage target met).

Box types

Black box

Test through the interface without seeing the code. You know inputs and expected outputs. Most functional, system and acceptance testing.

White box

Test with knowledge of the internals — statements, branches, paths. Unit tests, code coverage, security review.

Grey box

Partial knowledge. You can read the schema and the API contract, so you write smarter black-box tests. This is the SDET's natural habitat — say that.

Static vs dynamic

Static = examining without running (reviews, linting, SAST). Dynamic = running the software. The JD's "review code and identify gaps" is static testing.

Severity vs priority — they love this one

Severity = technical impact of the defect on the system. Set by the tester. Priority = how urgently the business wants it fixed. Set by the product owner/manager.

Defect lifecycle

New → Assigned → Open → Fixed → Retest → Verified → Closed. With two side branches: Rejected (not a defect / works as designed), Deferred (real, but not this release), and Duplicate. Reopened happens when retesting fails.

What a good bug report contains

Title (one line, specific), environment (build, OS, device, browser), preconditions, exact steps to reproduce, expected result, actual result, severity and priority, evidence (screenshot, video, logs), and frequency (always / 1 in 5).

The mistake freshers make

"Login not working" is not a bug report. "Login fails with 500 on Chrome 128 / Windows 11, build 4.2.1, when the email contains a trailing space — expected: trimmed and accepted, or a clear validation error; actual: server error, logs show Prisma unique constraint. Reproducible 5/5." That is. The difference is whether a developer can fix it without talking to you.

The testing pyramid

Draw this if asked about automation strategy
              /\            UI / E2E tests      few · slow · brittle · most realistic
             /  \           
            /----\          API / Integration    some · faster · stable
           /      \         
          /--------\        Unit tests           many · milliseconds · cheap to fix
         /__________\

Why the shape: a failing unit test points at one function; a failing UI test could be anything. UI tests are slow and flaky, so a suite built as an upside-down pyramid (the "ice-cream cone") takes an hour to run, fails randomly, and gets ignored — which is how teams stop trusting their tests altogether. Push every check to the lowest level that can prove it.

Shift left

Involve testing earlier: review requirements, write acceptance criteria with the team, unit tests during development, static analysis in the pipeline. A defect found in requirements costs almost nothing; the same defect found in production costs orders of magnitude more, plus a customer. BDD (section 05) is a shift-left practice — it drags the conversation about correctness to before the code is written.

Ask me this

Difference between smoke and sanity testing?

"Smoke is wide and shallow — a quick pass over the critical paths to decide whether the build is worth testing at all. It's usually scripted and automated on every build. Sanity is narrow and deep — after a specific fix or small change, you check that one area in detail, usually unscripted. Smoke is a gate on the build; sanity is a check on a change."

When would you stop testing?

Never say "when all bugs are found" — exhaustive testing is impossible. Say: "When the exit criteria in the test plan are met: all planned high-priority cases executed, no open critical or high-severity defects, coverage and pass-rate thresholds met, and the remaining known issues are documented and accepted by the product owner. In practice you also stop when the deadline arrives — and then the job is to state clearly what risk is being shipped."

Can you test a product completely?

"No. Exhaustive testing is impossible — the input space is effectively infinite. A login field alone accepts unbounded strings. So testing is risk management, not proof: you use techniques like equivalence partitioning and boundary analysis to get maximum coverage from minimum cases, and you spend your effort where failure is most likely and most expensive." This is one of the seven classic testing principles and interviewers like hearing it.

Give me a high severity, low priority bug.

Have a concrete one ready: "A crash on a deprecated OS version used by a tiny fraction of users, or a data-corrupting bug in an admin feature that is used once a year. Technically severe, but nobody is blocked today, so it gets scheduled rather than hot-fixed."

A developer says "it's not a bug, it works on my machine." What do you do?

"First, I make sure my report is airtight — exact build, environment, steps, evidence, and how often it reproduces. Nine times out of ten the difference is environment or data, and pinning that down is part of my job, not an argument to win. I'd reproduce it with them on a call or record it. If it genuinely doesn't reproduce, I document it as environment-specific rather than pushing. If it does reproduce and we still disagree on whether it matters, that's a product-owner decision about priority, not a fight between us."

The attitude they're testing for: evidence over ego.

What is a test plan vs a test strategy vs a test case?

"A test strategy is high level and usually organisation-wide: the approach, tooling, levels of testing, standards. A test plan is project-specific: scope, features in and out, resources, schedule, environment, risks, entry and exit criteria. A test case is a single verifiable check: ID, title, precondition, steps, test data, expected result."

How would you test a pen? (or a lift, a chair, an ATM)

They ask this to see whether you have a method. Never start listing random checks. Start by clarifying, then use categories:

1. Clarify: "What kind of pen, and who's the user — a ballpoint for an office, or a stylus?" 2. Functional: does it write, on paper, on the first stroke, after the cap is on for a week, until the ink is finished? 3. Non-functional: how long does the ink last, does it leak at altitude, does it survive a drop, is it comfortable for 30 minutes of writing? 4. Usability: left-handed users, grip, cap fits. 5. Compatibility: paper types, temperatures, surfaces. 6. Negative: writing on glass, pressing hard enough to snap the tip, storing it nib-up. 7. Security/compliance: is the ink non-toxic; does it meet packaging standards?

End with priority: "If I had one hour, I'd test the primary flow — does it write reliably — and leaking, because that's the failure that ruins a shirt and loses a customer."

04 · Highest value

Designing test cases

The JD's first responsibility is "designing and writing test cases". So there is a high chance someone says: "Here's a login page / a text field / this checkout — give me test cases." This is the question you can win outright, because most candidates answer it by listing whatever pops into their head. You will answer it with named techniques, and that immediately reads as trained.

Your opening move, every time

Before listing a single case, say this: "Let me clarify the requirement first, then I'll structure it — positive cases, negative cases, boundary values, and then non-functional and security." You've just told them you have a system. Then ask one or two real clarifying questions. Asking questions is not weakness here; a tester who doesn't question the spec is the one who ships the bug.

Technique 1 — Equivalence partitioning (EP)

Split the input space into groups where every value in a group should be treated identically by the system. Test one value per group, not a hundred.

Age field accepting 18–60: the partitions are below 18 (invalid), 18–60 (valid), above 60 (invalid), plus non-numeric input, empty, and negative. Six tests instead of thousands. The justification sentence: "Exhaustive testing is impossible, so I partition inputs into classes that the system should treat the same and sample one from each."

Technique 2 — Boundary value analysis (BVA)

Bugs cluster at edges, because edges are where humans write < instead of <=. For a valid range of 18–60 you test 17, 18, 19 and 59, 60, 61 (the three-value form), or at minimum 17, 18, 60, 61 (two-value form).

Functional: add one item, cart badge increments; add the same item twice, quantity becomes 2 rather than two lines; add the same product in two different weights (100g and 250g) — those are separate cart lines, which is exactly what the @@unique([userId, productId, weight]) constraint in my schema enforces; add an out-of-stock item → blocked; price shown in the cart matches the weight-adjusted price. State: add as a guest → cart persists in localStorage; log in → the guest cart merges into the database cart without duplicates or lost items. Boundary: quantity 0, 1, maximum allowed, maximum + 1, negative, decimal. Negative: add while the product is deleted or archived in another tab; add with an expired token; double-click the button rapidly — does it add two? Non-functional: latency, and that the cart survives refresh and a second device.

What is equivalence partitioning and boundary value analysis? Give an example.

"EP divides inputs into classes the system should treat identically, so I test one representative per class instead of every value. BVA then tests the edges of those classes, because that's where off-by-one errors live. For a field accepting 1–100: EP gives me classes of below-range, in-range, above-range, non-numeric and empty. BVA adds 0, 1, 2 and 99, 100, 101. They're used together — EP finds the classes, BVA picks the values."

How many test cases would you write for a field that accepts a 10-digit mobile number?

Don't answer with a number — answer with a method. Partitions: valid 10-digit, fewer than 10, more than 10, non-numeric, empty, special characters, leading zeros, country code prefix (+91), spaces or dashes inside. Boundaries: 9, 10, 11 digits. Plus: paste rather than type, autofill, and whether the field silently truncates a longer paste — truncation is a classic real defect. That's about 12 well-chosen cases, and I'd say why each exists.

Requirements are unclear and the deadline is tomorrow. What do you do?

"I'd write down my assumptions explicitly and get them confirmed by whoever owns the feature — usually a two-line message is enough, and it's faster than waiting for a meeting. Meanwhile I'd start with risk-based testing on what's unambiguous: the critical path and anything touching money, data or security. And I'd do time-boxed exploratory testing on the unclear parts, because unclear requirements are exactly where exploration finds things. At the end I report what was tested, what was assumed, and what risk remains — so the release decision is informed rather than blind."

You have 200 regression cases and two hours before release. Which do you run?

"Risk-based selection. First, anything in the blast radius of what actually changed — I'd look at the diff or ask the developer which modules were touched. Second, the revenue-critical path: login, cart, payment, order creation. Third, areas with a history of defects, because bugs cluster. I'd run those manually or via the automated smoke suite, and explicitly report which areas were not covered so the risk is visible rather than hidden."

BDD, Gherkin and feature files

The JD says it outright: "writing BDD/automation scripts for acceptance criteria" and "create feature files & develop test in BDD". If you learn one new thing for this interview, learn this. It is genuinely easy.

What BDD is, in plain terms

Behaviour Driven Development is a way of writing down what software should do in language a business person, a developer and a tester can all read — before the code is written — and then wiring that same text directly to automated tests. So the specification and the test suite are the same artefact and cannot drift apart.

The practice around it is often called the three amigos: a business analyst/product owner, a developer and a tester sit together over a user story and agree the examples of correct behaviour. The tester's questions in that meeting ("what happens if the payment succeeds but the stock ran out?") are where most bugs get prevented rather than found.

Feature: Shipping charges at checkout

  I want free shipping on larger orders
  So that I am rewarded for buying more

    And the product "Black Pepper" is in stock

    Given my cart subtotal is 499 rupees

    Then a shipping charge of 100 rupees is added

    When I proceed to checkout

How a feature file becomes a running test

Each Gherkin step is matched by a regular expression to a step definition — an ordinary method in code that does the work. The feature file is the readable layer; the step definitions are the automation layer.

CheckoutSteps.cs — SpecFlow style (C#) 
[Binding]
public class CheckoutSteps
{
    private readonly CartContext _cart;

    [Given(@"my cart subtotal is (.*) rupees")]
    public void GivenMyCartSubtotalIs(decimal subtotal)
        => _cart.SetSubtotal(subtotal);

    [When(@"I proceed to checkout")]
    public void WhenIProceedToCheckout()
        => _cart.Checkout();

    [Then(@"the shipping charge is (.*) rupees")]
    public void ThenTheShippingChargeIs(decimal expected)
        => Assert.AreEqual(expected, _cart.ShippingCharge);
}
steps/checkout_steps.py — behave, Python, same idea 
from behave import given, when, then

@given('my cart subtotal is {subtotal:d} rupees')
def step_set_subtotal(context, subtotal):
    context.cart = Cart(subtotal=subtotal)

@when('I proceed to checkout')
def step_checkout(context):
    context.result = context.cart.checkout()

@then('the shipping charge is {expected:d} rupees')
def step_check_shipping(context, expected):
    assert context.result.shipping == expected, \
        f"expected {expected}, got {context.result.shipping}"

Expected output when you run this: the runner prints each scenario with its steps, each coloured green as it passes and the run summarised as something like 3 scenarios passed, 0 failed. If the shipping rule were wrong — say someone wrote <= — the 500-rupee row of the Examples table fails and the report shows exactly that row with expected 0 and actual 100. That precision is the whole point: the failure message names the business rule, not a line number.

Hooks

Setup and teardown that runs around scenarios: @Before/@After in Cucumber, [BeforeScenario]/[AfterScenario] in SpecFlow. Use them to launch and quit the browser, seed and clean test data, and take a screenshot on failure.

Good Gherkin vs bad Gherkin

Bad — imperative, UI-coupled

When I open "https://site/login"
And I type "albin" into field id="u"
And I type "pass" into field id="p"
And I click the button with class "btn-primary"

Reads like a script, breaks when a CSS class changes, and a business person can't check it.

Good — declarative, behaviour-focused

When I sign in as a registered customer
Then I see my account dashboard

Describes intent. The selector lives in the step definition, where it belongs. One place to fix when the UI changes.

The anti-patterns to name if asked

Steps that assert nothing; one giant scenario testing five things; scenarios that depend on the order of earlier scenarios; hard-coded test data that only works on one environment; and duplicated step definitions with slightly different wording, which makes the step library unmaintainable. Every scenario should be independent and test one behaviour.

Ask me this

What is BDD and how does it differ from TDD?

"TDD is a developer discipline: write a failing unit test, write the minimum code to pass it, refactor. The audience is the developer and the unit is a function or class. BDD raises that to behaviour: you describe what the system should do from the user's point of view, in Given-When-Then, in language the whole team shares, and that description drives the automation. ATDD is the closely related idea of agreeing acceptance criteria up front. In practice BDD's biggest value isn't the tooling — it's forcing the conversation about edge cases before anyone writes code."

Write a feature file for the login functionality.

What goes in Given vs When vs Then?

"Given is context that already exists — I don't test it, I assume it. When is the single action under test; if I need two Whens, I probably have two scenarios. Then is an observable outcome, from the user's perspective, never an internal implementation detail. A common mistake is putting the action in Given, or putting an assertion in When."

How do you avoid duplicate step definitions across many feature files?

"Keep a shared, reviewed step library organised by domain rather than by feature file — cart steps, auth steps, order steps — and parameterise steps instead of writing near-duplicates. If two people write 'I log in' and 'I sign in' they're the same step and one should go. It's ordinary code hygiene: the step definitions are production code for the test suite and deserve review and refactoring."

Frameworks, Selenium, Appium and flakiness

What a test automation framework actually is

Not a tool. A framework is the structure that makes tests readable, reusable and maintainable: layers, conventions, shared utilities, data handling, reporting and CI hooks. The common types: data-driven (same script, many data sets), keyword-driven (tests written as keyword tables), hybrid, and BDD (behaviour as the entry point). Most real frameworks are hybrid with a BDD front end.

Page Object Model, the pattern they will ask about

Every page (or component) gets a class. The class holds the locators and exposes intention-revealing methods. Tests then read like sentences and contain no selectors.

# pages/login_page.py
class LoginPage:
    EMAIL    = (By.ID, "email")
    PASSWORD = (By.ID, "password")
    SUBMIT   = (By.CSS_SELECTOR, "[data-testid='login-submit']")

    def __init__(self, driver):
        self.driver = driver
        self.wait = WebDriverWait(driver, 10)

    def login_as(self, email, password):
        self.wait.until(EC.visibility_of_element_located(self.EMAIL)).send_keys(email)
        self.driver.find_element(*self.PASSWORD).send_keys(password)
        self.driver.find_element(*self.SUBMIT).click()
        return DashboardPage(self.driver)   # chaining: returns the next page

# the test — no selectors anywhere
def test_valid_login(driver):
    dashboard = LoginPage(driver).login_as("albin@x.com", "Valid@123")
    assert dashboard.username() == "Albin"

Why it matters: when the login button's markup changes, you edit one line in one class instead of hunting through 200 tests. That sentence is the whole answer to "why POM?".

Locators, best to worst

  1. A dedicated test attribute — data-testid. Stable because it exists only for tests; nobody restyles it away. Recommend this as something you'd ask developers to add — the JD says you review their code, and this is a great example of a testability gap to raise.
  2. ID — fast and unique, if the app actually has them.
  3. Name, link text — fine for forms and links.
  4. CSS selector — concise, fast.
  5. XPath — most powerful (can traverse upward, match text), slowest and most brittle. Avoid absolute XPath like /html/body/div[3]/div[2]/… — it breaks the moment anyone adds a div.

Waits — the single biggest cause of flaky UI tests

Flaky tests — have a real answer ready

A flaky test passes and fails without the code changing. It is worse than no test, because it trains the team to ignore red builds. The causes, in the order you should list them:

  1. Timing — implicit assumptions about how fast something renders. Fix with explicit waits on conditions, never sleeps.
  2. Test data and shared state — a test that assumes a user exists, or two tests fighting over the same record. Fix by creating fresh data per test and cleaning up.
  3. Test order dependency — test B only passes if test A ran first. Fix by making every test independent and running the suite in random order to prove it.
  4. Environment — a slow or shared test environment, a third-party sandbox that's down. Fix by mocking or stubbing external services.
  5. Animation and async UI — clicking an element mid-transition.

Then the process answer: "Quarantine the flaky test out of the blocking suite immediately so the build stays trustworthy, raise a ticket, and fix the root cause. Blind retries hide real race conditions — I'd only use a retry as a temporary measure with a ticket attached."

Ask me this

What would you automate and what would you leave manual?

"Automate what is repetitive, stable, high-risk and objectively verifiable: regression suites, smoke tests, API contract tests, data-driven permutations, cross-browser and cross-device runs. "First measure — find which tests eat the time; usually a small number dominate. What to test in an API

  1. Status code and response time for each path.
  2. Schema / contract — every expected field present, correct types, no unexpected nulls, no fields that shouldn't be there. Critically: does the user object come back with the password hash in it? Check response bodies for leaked internals.
  3. Business rules — correct totals, correct stock after an order, correct discount application.
  4. Authentication and authorisation — no token, wrong token, expired token, another user's token, a normal user hitting admin routes. Try to read someone else's order by changing an ID in the URL (that's IDOR — insecure direct object reference — and it's the single most common real-world API vulnerability).
  5. Negative and boundary input — missing fields, wrong types, huge payloads, negative quantities, SQL and script payloads.
  6. Idempotency and concurrency — same request twice, two requests at once.
  7. Headers — content type, CORS, caching, security headers.

SQL for testers

Expect two or three queries. They are almost always: a join, a group-by with having, and "second highest". Learn these three shapes and you're covered.

Run these against any Postgres/MySQL — shapes you must know cold 
-- 1. JOIN: every order with the customer who placed it
SELECT o.id, u.name, o."totalAmount", o."createdAt"
FROM "Order" o
JOIN "User" u ON u.id = o."userId"
ORDER BY o."createdAt" DESC;

-- 2. LEFT JOIN + IS NULL: products that have never been ordered
SELECT p.id, p.name
FROM "Product" p
LEFT JOIN "OrderItem" oi ON oi."productId" = p.id
WHERE oi.id IS NULL;

-- 3. GROUP BY + HAVING: customers who placed more than 3 orders
SELECT u.name, COUNT(o.id) AS order_count
FROM "User" u
JOIN "Order" o ON o."userId" = u.id
GROUP BY u.id, u.name
HAVING COUNT(o.id) > 3;

-- 4. THE CLASSIC: second highest value (two ways)
SELECT MAX(price) FROM "Product"
WHERE price < (SELECT MAX(price) FROM "Product");

SELECT DISTINCT price FROM "Product"
ORDER BY price DESC OFFSET 1 LIMIT 1;

-- 5. Find duplicates — a tester's favourite data-integrity check
SELECT email, COUNT(*) FROM "User"
GROUP BY email HAVING COUNT(*) > 1;

-- 6. Data check after an order: did stock actually decrement correctly?
SELECT oi."productName", oi."initialStock", oi."finalStock", p.stock AS current_stock
FROM "OrderItem" oi
JOIN "Product" p ON p.id = oi."productId"
WHERE oi."orderId" = 42;

Reading query 4: the first version asks "of all prices strictly below the maximum, what's the largest" — that's the second highest, and it returns NULL rather than erroring if every product has the same price, which is the edge case an interviewer probes for. The second version sorts descending, skips one row and takes the next; DISTINCT matters, otherwise two products priced identically at the top would make the "second highest" the same number. Say that distinction out loud — it's exactly the boundary thinking they're testing for.

Also know: WHERE filters rows before grouping, HAVING filters groups after. DELETE removes rows and can be rolled back; TRUNCATE empties a table fast without row-level logging; DROP removes the table itself.

Ask me this

What is API testing and why would you prefer it over UI testing?

"API testing exercises the business logic directly at the service layer, without a browser. I prefer it where I can because it's an order of magnitude faster, far less flaky, available before the UI exists, and it can reach states the UI won't let you construct — sending a negative quantity, or an order for a product that was deleted a millisecond ago. The UI layer then only needs to test what's genuinely UI: rendering, navigation and user flow."

Difference between 401 and 403?

"401 Unauthorized is really unauthenticated — the server doesn't know who you are, so send credentials. 403 Forbidden means you're authenticated but not permitted; re-sending credentials won't help. In an admin route, a missing token should give 401 and a valid non-admin token should give 403."

How would you test that a user can't see another user's data?

"Create two users, A and B, each with an order. Log in as A, take A's token, then call B's order endpoint with A's token and B's order ID. The expected result is 403 or 404 — never B's data. I'd repeat that for every endpoint that takes an ID, because it's the most common real vulnerability, and I'd automate it as a standing security regression test rather than doing it once by hand."

What's the difference between joins?

"INNER JOIN returns rows matching in both tables. LEFT JOIN returns everything from the left table, with NULLs where the right has no match — which is how you find orphans, like products that were never ordered. RIGHT JOIN is the mirror. FULL OUTER returns both sides with NULLs where either is missing. CROSS JOIN is every combination, which is occasionally useful for generating test data permutations."

You found a data mismatch between the UI and the database. How do you investigate?

"Work down the stack. First reproduce and note the exact time. Then check the API response in devtools — if the API is right and the screen is wrong, it's frontend rendering or state. If the API is also wrong, query the database directly — if the database is correct, it's the read path, likely caching. SpiceNest has an in-memory cache with a 5-minute TTL, so a stale product price or stock count after an update is a bug I'd suspect immediately. If the database itself is wrong, it's the write path, and I'd check logs around that timestamp."

That is a genuinely excellent answer because it's a real debugging method with a real example attached.

Normalisation

Organising tables to remove redundancy and update anomalies. 1NF: atomic values, no repeating groups. 2NF: 1NF plus no partial dependency on part of a composite key. 3NF: 2NF plus no transitive dependency — non-key attributes depend only on the key. Denormalisation deliberately reintroduces redundancy for read speed.

Keys and indexes

The TCP three-way handshake

Easy to draw, often asked
  Client                                Server
    |  ---------- SYN (seq=x) --------->  |    "I want to talk, my sequence starts at x"

Teardown is a four-way exchange of FIN and ACK in both directions. If asked why three and not two: both sides must confirm their own sequence numbers were received, otherwise ordering and retransmission can't work.

DNS — very likely asked

DNS translates a human name like idukkiorigins.com into an IP address. The resolution walk: your machine checks its local cache, then the recursive resolver (usually your ISP or 8.8.8.8), which asks a root server, which points to the TLD server for .com, which points to the domain's authoritative nameserver, which returns the record. Results are cached according to their TTL.

Record types worth knowing: A (name → IPv4), AAAA (IPv6), CNAME (alias to another name), MX (mail), TXT (verification, SPF), NS (nameservers). DNS normally runs over UDP port 53, falling back to TCP for large responses.

You have first-hand experience here — you pointed a real domain at a deployment. Say so: "When I put SpiceNest on its domain I configured the A and CNAME records, and the thing that surprised me was TTL-driven propagation delay — the old IP kept being served from caches for a while. That's also a testing lesson: after a DNS change, some users are on the old target for hours."

DHCP

Assigns IP configuration to devices automatically so nobody configures them by hand. The four-step exchange, remembered as DORA: Discover (client broadcasts "is there a DHCP server?"), Offer (server offers an address), Request (client asks for that one), Acknowledge (server confirms and leases it). The lease has a duration and is renewed. It also hands out the subnet mask, default gateway and DNS servers. This is directly relevant to SOTI: thousands of devices joining and leaving warehouse networks all day.

HTTP vs HTTPS and the TLS handshake

HTTPS is HTTP inside a TLS tunnel on port 443. It gives three things: confidentiality (encryption), integrity (tampering is detected), and authentication (the certificate proves you're talking to the real server). Simplified handshake: client hello with supported ciphers → server hello with its certificate → client verifies the certificate chain against trusted CAs → they agree a shared symmetric session key via asymmetric cryptography → all further traffic uses fast symmetric encryption.

Say why the switch to symmetric keys happens: asymmetric crypto is slow, so it's used only to establish the session key. That detail separates "I memorised the steps" from "I understand it".

"What happens when you type a URL and press Enter?"

The universal networking question. Answer it as a chain and don't skip steps:

  1. Browser parses the URL and checks its cache (and HSTS list).
  2. DNS resolution — local cache, resolver, root, TLD, authoritative → IP.
  3. ARP if needed to find the gateway's MAC, then routing across the internet.
  4. TCP three-way handshake with the server on port 443.
  5. TLS handshake — certificate validation, session key agreement.
  6. Browser sends the HTTP request; server (often via a reverse proxy/load balancer) handles it, possibly hitting a cache, an application server, and a database.
  7. Response comes back — status code, headers, HTML. Browser parses HTML, builds the DOM, fetches CSS/JS/images (more requests), builds the render tree, lays out and paints.
  8. JavaScript runs, may fire further API calls, page becomes interactive.

Then add the tester's coda: "Each of those steps is a place to test or a place to fail — DNS misconfiguration, expired certificate, CORS rejection, slow database, render-blocking scripts."

from collections import Counter

def is_palindrome(s):                         # O(n) time, O(n) space
    cleaned = [c.lower() for c in s if c.isalnum()]
    left, right = 0, len(cleaned) - 1
    while left < right:
        if cleaned[left] != cleaned[right]:
            return False
        left += 1; right -= 1
    return True

def reverse_words(sentence):                   # O(n)
    return " ".join(sentence.split()[::-1])

def first_non_repeating(s):                    # O(n) — two passes
    counts = Counter(s)
    for ch in s:
        if counts[ch] == 1:
            return ch
    return None

def two_sum(nums, target):                     # O(n) with a hash map, vs O(n²) brute force
    seen = {}
    for i, n in enumerate(nums):
        if target - n in seen:
            return [seen[target - n], i]
        seen[n] = i
    return []

def is_anagram(a, b):                          # O(n) counting; sorting would be O(n log n)
    return Counter(a.replace(" ", "").lower()) == Counter(b.replace(" ", "").lower())

def second_largest(nums):                      # O(n), single pass, handles duplicates
    first = second = float("-inf")
    for n in nums:
        if n > first:
            first, second = n, first
        elif first > n > second:
            second = n
    return second if second != float("-inf") else None

def is_substring(haystack, needle):            # O(n*m) naive — say KMP is O(n+m)
    if not needle:
        return True
    n, m = len(haystack), len(needle)
    for i in range(n - m + 1):
        if haystack[i:i + m] == needle:
            return True
    return False

def missing_number(nums, n):                   # O(n) time, O(1) space — sum formula
    return n * (n + 1) // 2 - sum(nums)

def is_balanced(s):                            # O(n) with a stack
    pairs = {")": "(", "]": "[", "}": "{"}
    stack = []
    for ch in s:
        if ch in "([{":
            stack.append(ch)
        elif ch in pairs:
            if not stack or stack.pop() != pairs[ch]:
                return False
    return not stack

def fib_memo(n, memo=None):                    # O(n) vs O(2^n) for naive recursion
    if memo is None: memo = {}
    if n <= 1: return n
    if n in memo: return memo[n]
    memo[n] = fib_memo(n - 1, memo) + fib_memo(n - 2, memo)
    return memo[n]

Switch fall-through

int day = 2;

    case 1: System.out.println("Mon");
    case 2: System.out.println("Tue");

    default: System.out.println("Other");
}

Prints Tue and then Wed. Without a break, execution falls through into the following cases until it hits one. It stops after Wed because that case breaks. Missing break is a classic real bug, and C# actually forbids implicit fall-through for this reason — a nice thing to mention in a .NET shop.

The four flows they'll probe

1. Registration and login

Register: lowercase the email → check it's not taken → bcrypt.genSalt(10) and hash → create the user → also link any guest orders whose stored address email matches. Login: find by lowercased email → bcrypt.compare → sign a JWT containing only the user id, expiring in 7 days → return the token and a safe user object. The frontend stores both in localStorage, and on every page load calls /api/auth/me to re-validate the token against the database rather than trusting the cached copy.

Why bcrypt and not SHA-256: bcrypt is deliberately slow and salted per user, so identical passwords produce different hashes and brute-forcing is expensive. A fast hash like SHA-256 is wrong for passwords precisely because it's fast. Say this if password storage comes up — it's a genuinely good answer.

2. Cart, including the guest merge

A logged-out user's cart lives in localStorage under cart_guest. On login, the frontend posts those items to /api/cart/sync, the server merges them into the database cart, and the guest copy is cleared — with a fallback to a plain fetch if the sync call fails. Price is recalculated on the server per weight tier, never trusted from the client for the cart display.

The weight tiers, which are a nice concrete detail: 100g is the base price; 250g is 2.5× base with 5% off; 500g is 5× with 10% off; 1kg is 10× with 15% off. That function is a perfect test-case exercise and section 12 uses it.

The defect register — six real findings in your own repository

1 · Prices and discounts are taken from the client  — Critical

Both create-razorpay-order and confirm-razorpay-order compute the subtotal from the items array in the request body, using item.price, and accept a discount value the client sends. Nothing re-reads the price from the database.

The attack: intercept the request, change every price to 1 and the discount to whatever you like, and buy the whole catalogue for a few rupees. The test: send a checkout request with a tampered price and assert the order total matches the database price, not the submitted one. The fix: the client sends only product IDs, weights and quantities; the server looks up every price and recomputes the total, and validates coupons server-side.

Lead with this one

"Never trust the client" is the first law of application security, and you caught yourself breaking it. A candidate who says that about their own live project is doing, unprompted, exactly what the JD means by reviewing code and identifying gaps.

2 · Time-of-check to time-of-use race on stock  — High

Stock is verified when the payment order is created, then decremented later, in a separate request, with a plain decrement. There is no transaction and no conditional update.

Draw this if they ask about concurrency — it explains itself
  Only 0.1 kg of pepper left.  Two customers, same instant.

  Customer A                          Customer B
  ──────────                          ──────────
  check stock: 0.1 >= 0.1  OK
                                      check stock: 0.1 >= 0.1  OK      ← both passed
  pays                                pays
  decrement 0.1 → 0.0                 decrement 0.1 → -0.1             ← negative stock
  order created                       order created                    ← one can't be shipped

The test: fire N concurrent checkout requests for the last unit and assert that exactly one succeeds and stock never goes below zero. This is a proper SDET test and you can describe it precisely: "a load-test script with 50 virtual users hitting the endpoint simultaneously, asserting on the final database state, not on the responses." The fix: one transaction containing a conditional update — decrement only where stock is still sufficient — and treat "zero rows affected" as out of stock.

3 · Order creation and stock decrement are not atomic  — High

The order is created, then a loop updates each product's stock. If the process dies or a single update fails midway, you get an order whose stock was never deducted, or partially deducted. That's a textbook atomicity violation. The fix: prisma.$transaction wrapping both. The test: force the second update to fail and assert the order does not exist afterwards.

4 · The cache serves stale stock after a purchase  — Medium

The product cache is invalidated when an admin edits a product, but not when an order decrements stock. So for up to five minutes after the last unit is sold, the shop still advertises it as in stock. Customers reach checkout and get rejected. The test: read the product list, place an order, immediately read the list again and assert stock reflects the sale. The fix: invalidate on stock change too — and note that the cache is per-process, so it's wrong the moment you run two instances behind a load balancer.

5 · Cart weight and quantity are unvalidated  — High

POST /api/cart accepts any weight string and any quantity the client sends. An unrecognised weight falls through to the base price in getWeightAdjustedPrice, while parseWeightToKg happily converts it for stock deduction. So a crafted request with weight "10kg" prices at the 100g rate while deducting ten kilograms. Quantity has no upper bound and no positivity check either.

The test: an API test that posts each invalid weight — "750g", "10kg", "abc", "", null — and asserts a 400 rather than a silent default. Same for quantity 0, −5, 1e9 and a decimal. The fix: validate against an allow-list of the four real tiers, server-side, and bound the quantity.

6 · Identity is asserted, never verified  — High

Three related findings, all stemming from there being no email verification step:

  • Admin by email string. The role is granted by matching the registration email against a hard-coded list, with an auto-upgrade on login. Since nobody proves they own an email address, the admin role rests on an unverified claim rather than on possession of the inbox.
  • Guest order claiming. On registration, the server scans guest orders and attaches any whose stored address email matches the new account — so registering with someone else's email address hands you their order history, including addresses and phone numbers.
  • User enumeration. Login returns "No registered user found with this email" versus "Incorrect password", which tells an attacker which addresses are registered. Interestingly, the forgot-password route gets this right with a deliberately generic message — so the codebase already knows the rule and applies it inconsistently.

The fix: email verification before either privilege or history is granted, role management in the database rather than in source, and one generic authentication failure message everywhere.

Also worth naming quickly

  • Money as floating point. Prices and stock are Float. Currency in binary floating point accumulates rounding error; the industry answer is integer paise, or a decimal type. Razorpay itself takes paise as an integer, which is the hint.
  • 401 versus 400 on an invalid token (section 07).
  • The cache never evicts. Expired entries are only removed when someone reads them, so write-only keys accumulate — a slow leak in a long-running process.
  • Stripe discount handling. The coupon is applied by shaving the first line item's unit price, floored at ₹1, so a large discount against a cheap first item is silently swallowed rather than applied.

Designing on paper

You won't be asked to design Instagram. For a fresher SDET the design question is a thinking test: can you take a vague prompt, ask the right questions, and produce a structure that isn't a mess? Follow the same six steps every time and the content almost writes itself.

The six-step method

  1. Clarify and scope. Who uses it, what are the two or three core use cases, what's explicitly out of scope. Say "I'll assume X, tell me if that's wrong."
  2. Rough numbers. Users, requests per day, read-versus-write ratio. Even crude estimates show you think about load.
  3. Draw the boxes. Client → API → service → database, plus cache, queue and third parties. Left to right, arrows labelled.
  4. Data model. The three or four core entities and their relationships. Never skip this — it's where most of the real thinking is.
  5. Walk one flow end to end with your finger on the diagram.
  6. Trade-offs and failure modes. What breaks first, what you'd monitor, what you'd do differently at 100× scale. And, since you're the test candidate: how you'd test it.

Then the tester's coda: "The hardest thing to test here is the offline-to-online transition — a device that misses three policy updates and then reconnects must converge to the right state. I'd build a device simulator to generate those scenarios at scale rather than testing by hand."

That "build a simulator" line is exactly the JD's "building enterprise utilities to reduce the time of testing". Use it.

Prompt 3 — "Design an e-commerce checkout"

You have already built one. Draw SpiceNest, then improve it out loud: idempotency keys, webhook as the source of truth, stock reservation with a timeout instead of a check-then-decrement, and an outbox for the confirmation email so it can't be lost. That is a senior-sounding answer and every piece of it is something you genuinely understand.

Prompt 4 — "Design a URL shortener"

The classic. Requirements: shorten, redirect, optionally track clicks. Core table: id, short code, long URL, owner, created, expiry. Generation: base-62 encode an auto-increment id, or hash and handle collisions. Read-heavy by a huge ratio, so cache aggressively; redirect with a 301 if permanent or a 302 if you want to keep counting clicks. Test cases: duplicate long URLs, expired links, invalid codes, very long input, and a redirect loop where someone shortens a short URL.

Ask me this

How would you test a feature that isn't built yet?

"That's the best time to test it, and it's the whole idea behind shift-left. I'd review the requirements and acceptance criteria for ambiguity, gaps and contradictions, and write the test cases and feature files from them — those questions almost always find missing rules before a line of code exists. I'd agree the API contract with the developer so I can build API tests against a mock while the implementation is in progress, and identify test data and environment needs early rather than being blocked on day one of testing."

You have a legacy module with no tests and no documentation. Where do you start?

"Not by writing tests. First I'd map what it does — read the code, talk to whoever owns it, watch it run, and check production logs and the support-ticket history to find out what actually breaks and what customers actually use. Then I'd write characterisation tests around the current behaviour of the highest-risk paths, so I have a safety net before anything changes. From there, coverage follows risk, not alphabetical order."

How do you decide what to test when everything is a priority?

"Risk equals likelihood times impact. Impact is business impact — money, data loss, security, anything customer-facing and hard to reverse. Likelihood comes from complexity, how recently the code changed, and defect history, since bugs cluster. I'd rank features on that grid with the product owner in the room, so priority is a shared decision rather than my private guess."

Agile, code review and CI/CD

Vocabulary check

  • User story — "As a <role>, I want <goal>, so that <benefit>." Its acceptance criteria are the conditions that make it done, and they map directly onto Gherkin scenarios.
  • Definition of Done — the team's shared bar: code reviewed, unit tested, automated acceptance tests passing, documentation updated, deployed to staging. If testing isn't in the DoD, testing becomes optional.
  • Story points — relative effort and complexity, not hours. Fibonacci-ish. Velocity is points completed per sprint, used for forecasting, not for judging people.
  • Scrum vs Kanban — Scrum is time-boxed sprints with fixed commitments; Kanban is continuous flow with work-in-progress limits. Scrum suits feature delivery, Kanban suits support and maintenance.
  • Sprint zero, spike, tech debt — setup, an exploratory time-box to reduce uncertainty, and the accumulated cost of earlier shortcuts.

Code review — "review code written by development and identify gaps"

This is an actual JD bullet, so have a structured answer. When you review a change, you look for:

  1. Correctness — does it do what the story says, including the edge cases nobody mentioned?
  2. Missing tests — is there a test for the failure paths, or only the happy one? This is the "gap" the JD means.
  3. Trust boundaries — is anything believed that came from the client? Are both authentication and authorisation enforced?
  4. Error handling — what does the user see when the dependency is down? Are exceptions swallowed silently?
  5. Concurrency and atomicity — check-then-act patterns, missing transactions.
  6. Testability — are there stable IDs or test attributes on new UI? Can this be driven through an API, or only by clicking? Is it a 200-line function that can't be unit tested?
  7. Observability — will there be enough in the logs to diagnose this at 2am, with nothing sensitive in them?

Then the human part, which matters more than the list: "I comment on the code, not the person, I distinguish blocking issues from suggestions, and I ask rather than assert when I might be missing context — 'what happens here if the token expires mid-request?' gets a better outcome than 'this is wrong.'"

CI/CD

Continuous integration: every push merges to the mainline and triggers an automated build plus tests, so integration problems surface in minutes rather than at the end of a release. Continuous delivery: every passing build is deployable, with the deployment itself a button. Continuous deployment: it goes out automatically.

Where tests sit in the pipeline: lint and unit tests on every commit (seconds), API and integration tests on merge (minutes), UI smoke on deploy to staging, full regression nightly, and a security scan on a schedule. The rule to state: the fast, deterministic tests gate the merge; the slow, broad ones run behind it. Anything flaky comes out of the gating suite immediately, because a suite people ignore is worse than no suite.

Deployment strategies worth naming: blue-green (two environments, switch traffic, instant rollback), canary (release to a small percentage first and watch metrics), and feature flags (ship the code dark, enable it separately — which also lets you test in production safely).

Ask me this

What is Agile and have you worked in it?

Define it briefly — iterative delivery in short cycles, working software over documentation, responding to change — then be honest about scale: "In my internships we worked in short cycles with stand-ups and demos rather than a formal Scrum with story points. So I know the rhythm, and I'd expect the formal ceremonies and tooling to be new to me." Claiming five years of Scrum as a student fools nobody.

A story is marked done but has no automated tests. What do you do?

"Then it isn't done, if our Definition of Done says tests are included — and that's a team agreement, not my personal preference, which is why it's worth having written down. Practically I'd raise it in the pull request rather than escalating: point at what's missing, and if the sprint is genuinely ending, agree an explicit tech-debt ticket rather than silently letting it through. What I wouldn't do is quietly write the missing tests myself and let the pattern repeat."

The release is tomorrow and you've found a critical bug. What do you do?

"Report it immediately with full evidence — the worst outcome is a decision-maker finding out late. Then give them what they need to decide: what breaks, how many customers it affects, whether there's a workaround, and how risky the fix is. The go/no-go call belongs to the product owner and release manager, not to me; my job is to make sure that call is fully informed and that the risk we're accepting is written down rather than assumed away."

A build fails in CI. Walk me through what you do.

"Read the failure before touching anything — which test, which assertion, what the actual versus expected values were. Then triage: is it a genuine regression, a flaky test, an environment problem, or a bad test? Check whether it fails locally and whether it fails consistently. If it's a real regression, I identify the offending commit and get it reverted or fixed fast, because a red mainline blocks everyone. If it's flaky, I quarantine it with a ticket rather than rerunning until it goes green — rerunning until green is how teams learn to ignore their tests."

16 · The human round

Behavioural, and closing well

The last stretch is usually managerial: why this role, how you handle pressure, how you work with people. Reported SOTI questions include the project discussion, why SOTI, how you manage deadlines and stress, and location preference. Freshers lose offers here more often than on technical content.

Use STAR, and keep it to 90 seconds

Situation (one sentence of context) → Task (what was yours to solve) → Action (what you specifically did) → Result (the outcome, with a number if you have one). Most of the time should be in Action. If you find yourself two minutes in and still describing the situation, stop and skip to what you did.

The answers that need exact words

"Why should we hire you?"

"Three reasons. I can read and write production code, so I can review developers' work and find gaps rather than only testing through a UI. I've already done the thing this job asks for — I went back through my own e-commerce project and found six defects in it, including a price-tampering hole and a race condition on stock. And I learn stacks fast; I picked up Prisma and a payment integration from nothing for that project. The gap is C# and enterprise tooling, and I'd rather be straight about that than pretend."

"What's your biggest weakness?"

Pick something real, specific and already being worked on. "I over-build before validating. On SpiceNest I wrote a lot of frontend before confirming the flows with the person who'd actually run the shop, and some of it was wasted. I've started sketching the flow and confirming it first — which is, incidentally, the same habit that makes acceptance criteria useful." Never say "I'm a perfectionist" or "I work too hard."

"Where do you see yourself in five years?"

"Technically deep rather than away from the technology. In five years I'd want to own the test architecture for a product area — the framework, the tooling, the quality signals a release decision rests on — and to have mentored people into it. I'm not looking to move off engineering."

"How do you handle pressure and deadlines?"

"I get concrete early. When the sports meet and end-semester exams collided, the thing that saved it was writing down what actually had to happen versus what I'd like to happen, and delegating the second list. Same with code — under a deadline I identify the highest-risk paths, cover those properly, and say clearly what isn't covered, rather than testing everything shallowly and pretending it's fine."

Questions to ask them

Have four ready; you'll get to ask two. Never say "no, I'm good" — it reads as indifference.

  • "What does the testing stack look like day to day — SpecFlow and Selenium, Appium for devices, how much is real hardware versus emulators?"
  • "How much of an Associate SDET's time is writing automation versus designing test scenarios versus exploratory work?"
  • "The JD mentions building utilities to reduce testing time — what's an example of one your team built recently?"
  • "What does a good first six months look like in this role?"

Avoid, in the technical round: salary, hours, leave policy, work from home. Those belong to HR.

How to close

When they ask if you have anything to add, take it. Short and specific: "Just that I know I'm coming from a development and AI background rather than a testing one. What I'd want you to take away is that I already work the way this job needs — I found and ranked six defects in my own production project, including a security hole in how I handled prices. I'd rather do that deliberately, with proper tooling, than by accident."

Ask me this

Do you have any offers / are you interviewing elsewhere?

Be honest without oversharing. "I'm in a couple of processes, but this is the one I've prepared most seriously for, because the role matches how I already work." Don't invent competing offers as leverage — at campus-hire level it reads badly and is easy to check.

You'd be testing other people's code all day. Won't you get bored?

Don't get defensive. "If the job were clicking through the same script every sprint, yes. But this one is described as writing automation, building utilities and running POCs on tooling — that's building, with a different definition of done. And honestly, the part of my own project I found most interesting was the part where I tried to break it."

Tell me about a time you disagreed with a teammate.

Use STAR, keep the other person's dignity intact, and make the resolution evidence-based rather than hierarchical. The outcome matters less than showing you can disagree without it becoming personal — which is exactly the skill needed when you tell a developer their code has a gap.

What if you're asked something you've never heard of?

Say so, then show how you'd approach it. "I haven't come across that. From the name I'd guess it's X — is that roughly the area? If I hit this on the job I'd read the documentation and try the smallest possible example first." Interviewers are, in part, testing whether you can be honest under pressure. Almost nobody gets full marks on every question; the ones who bluff get marked down twice.

The morning checklist

In the room

  • Think out loud. Silence is the only unrecoverable mistake. They are grading your reasoning, and they can't grade what they can't hear.
  • Ask before assuming. One clarifying question at the start of a problem is a signal of competence, not confusion.
  • When you're stuck, say where. "I know this needs a hash map but I'm not seeing how to handle duplicates — let me think about that case." Interviewers help candidates who narrate; they can't help a silent one.
  • Never bluff. A clean "I don't know, here's how I'd find out" costs you one question. A bluff costs you the panel's trust in every answer you've already given.
  • Bring it back to testing. Whatever they ask — a coding problem, a design, a project — the last sentence can always be "and here's how I'd test it." That's the job you're applying for.
Last thing

You are not walking in as someone who wants a job in testing. You are walking in as someone who has already built a production system, taken it apart, found six real defects in it and knows how to fix each one. That is a stronger position than most candidates for this role will have. Say it plainly and let it do the work.
