Databases, DBMS and the relational model

The vocabulary round. Short questions, but a fumbled answer here colours the whole interview.

What a database actually is

A database is an organised collection of related data stored so it can be retrieved and modified efficiently. A DBMS (Database Management System) is the software layer sitting between users and that stored data — it handles storage, retrieval, concurrency, security and recovery so applications don't have to.

Before DBMSs, applications used plain files. The file system approach fails on five counts that every DBMS is designed to fix:

Problem with filesWhat it looks likeHow a DBMS solves it
RedundancySame customer address copied in three filesNormalised tables, stored once
InconsistencyOne copy updated, two go staleSingle source of truth + constraints
No concurrency controlTwo clerks overwrite each otherTransactions, locks, isolation levels
Weak securityWhole file readable or notRow/column-level GRANT privileges
No recoveryCrash mid-write corrupts dataWrite-ahead log, commit/rollback

RDBMS and the relational model

An RDBMS is a DBMS built on E. F. Codd's relational model (1970): all data is presented as relations — mathematical sets of tuples — which we see as tables of rows and columns. Its power is that the model is grounded in set theory and predicate logic, so a small declarative language (SQL) can express any query, and the engine is free to choose how to execute it.

Codd's rules you should be able to name

There are twelve (thirteen, counting rule 0). Nobody expects all of them; know these four and say so honestly:

  • Information rule — all data, including metadata, is represented as values in tables.
  • Guaranteed access rule — every single value is reachable by table name + primary key + column name.
  • Systematic NULL treatment — NULL means "missing/unknown", handled uniformly and independent of data type.
  • Physical data independence — changing how data is stored (adding an index, moving files) must not break applications.

The three-schema architecture

ANSI/SPARC splits a database into three levels, and the point of the split is data independence:

External / View level

What each user group sees — views tailored per role. HR sees salaries, the intern sees names only.

Conceptual / Logical level

The whole database's logical design: tables, columns, relationships, constraints. The DBA's picture.

Internal / Physical level

How bytes are actually stored: files, pages, B-tree indexes, compression.

Logical data independence = changing the conceptual schema (splitting a table) without changing external views. Physical data independence = changing storage without touching the logical schema. Physical independence is easy and universal; logical independence is harder and only partial in real systems — say that and you sound like you have used a database, not just read about one.

Interview questions · Module 01
What is the difference between DBMS and RDBMS?

A DBMS stores and manages data but does not require the relational model — early ones used hierarchical or network models, data may be stored as files, and relationships between data are not enforced by the system. An RDBMS is a DBMS that stores data as tables of rows and columns, supports keys and referential integrity between tables, enforces normalization-friendly design, and guarantees ACID transactions.

  • DBMS: single-user oriented, low overhead, no relationship enforcement. Examples: file-based systems, MS Access (loosely), older IMS.
  • RDBMS: multi-user, constraint-driven, supports SQL, distributed capable. Examples: MySQL, PostgreSQL, Oracle, SQL Server.

Every RDBMS is a DBMS; the reverse is not true.

Say it like thisAn RDBMS is a DBMS that adds the relational model on top — tables, keys and enforced relationships — so integrity is the database's job rather than the application's.
What is SQL, and is it a programming language?

SQL (Structured Query Language) is the standard declarative language for relational databases: you state what result you want, not how to compute it — the query optimizer decides the execution plan. It was standardised by ANSI in 1986 and ISO in 1987.

Plain SQL is not Turing-complete in the way C or Python is; it is a special-purpose (domain-specific) language. But vendor procedural extensions — PL/SQL (Oracle), T-SQL (SQL Server), PL/pgSQL (PostgreSQL) — add variables, loops and conditionals, making those dialects fully procedural.

Explain degree, cardinality, schema and instance with an example.

Using our departments table with columns (dept_id, dept_name, location) and 4 rows:

  • Degree = number of attributes = 3.
  • Cardinality = number of tuples = 4.
  • Schema = the definition: departments(dept_id INT PK, dept_name VARCHAR(50), location VARCHAR(50)). Called the intension; it is time-invariant.
  • Instance = the actual 4 rows sitting in it right now. Called the extension; it changes with every INSERT.

Careful: in ER diagrams, "cardinality" is also used loosely for relationship ratios (1:1, 1:N, M:N). Clarify which sense the interviewer means if it is ambiguous.

What is data independence and why does it matter?

Data independence is the ability to change one level of the schema without disturbing the level above it.

  • Physical — adding an index, switching storage engines or partitioning a table must not change query results or force an application rewrite. Universally achieved.
  • Logical — splitting employees into employees + employee_contacts should not break code, provided a view named employees reconstructs the old shape. Harder to achieve; views are the main tool.

It matters because it decouples application code from storage decisions, which is what lets DBAs tune a live system.

How do you convert an ER diagram into relational tables?
  1. Each strong entity → one table; its key attribute → primary key.
  2. Each weak entity → one table containing the owner's PK as part of a composite key, with ON DELETE CASCADE.
  3. 1:N → put the foreign key on the "many" side. Never create a third table for this.
  4. 1:1 → foreign key on either side, marked UNIQUE; prefer the side with total participation.
  5. M:N → a new junction table with a composite primary key of both foreign keys, plus any relationship attributes.
  6. Multivalued attribute → its own table keyed by (owner PK, value).
  7. Composite attribute → flatten into its atomic parts as separate columns (required for 1NF).
  8. Generalisation/specialisation → either one table with a type discriminator, or a parent table plus child tables sharing the parent's PK.
When would you choose NoSQL over a relational database?

When at least one of these dominates: the schema genuinely varies per record (product catalogues, event payloads); write volume needs horizontal scale across many nodes; the access pattern is a single-key lookup with no joins; or the data is naturally a graph or time series. Also when eventual consistency is acceptable — a like count can be a second stale.

Stay relational when correctness of multi-row updates matters (money, inventory, bookings), when the query patterns are unknown up front (ad-hoc analytics need joins), or when integrity must be enforced centrally rather than by every client.

Say it like thisI pick by consistency need and access pattern, not by scale alone — modern Postgres scales far enough for most workloads, so I only leave it when the data model or write distribution genuinely fights the relational shape.

Classic trap

"Every super key is a candidate key" — false. Every candidate key is a super key; only the minimal super keys are candidate keys. If (emp_id, name) identifies a row, so does emp_id alone, so the pair is a super key but not minimal, hence not a candidate key.

Referential integrity, in one sentence

Every non-NULL foreign key value must match an existing primary/unique key value in the referenced table. That is the whole rule. A NULL foreign key is permitted and means "no relationship yet" — which is exactly Gita's dept_id in our data.

Interview questions · Module 02
Difference between primary key and unique key?

Both enforce uniqueness. The differences: a primary key rejects NULLs and there is exactly one per table, and it is the default target for foreign keys and usually the clustering index. A unique key permits NULLs and you may have several per table.

Design-wise: primary key answers "which row is this?"; unique key answers "this business value must not repeat".

Can a primary key be composite? Can a foreign key be NULL?

Yes to both. A composite primary key spans several columns — assignments(emp_id, proj_id) — and uniqueness applies to the combination, not to each column. A foreign key can be NULL, which simply means the row has no related parent yet; referential integrity only constrains non-NULL values. A foreign key can also be non-unique — many employees share one dept_id, which is exactly how 1:N works.

Surrogate key or natural key — which do you prefer and why?

I default to a surrogate key (auto-increment integer or UUID) because business values change: emails get updated, PAN formats get revised, and a changing key means cascading updates across every child table. Surrogates are also narrow, which keeps indexes and foreign keys small.

I still put a UNIQUE constraint on the natural key so the business rule is enforced. The natural key is worth using directly only when it is genuinely immutable and externally standardised — a country ISO code, for instance.

Trade-off worth naming: UUIDs as clustered primary keys cause random insert order and page splits in B-trees; prefer ordered UUIDs (v7) or a bigint identity if write throughput matters.

What is the difference between a CHECK constraint and a trigger for validation?

A CHECK is declarative, evaluated by the engine per row, cheap, and visible in the schema — but it can only reference columns of that row (portably). A trigger is procedural code that can look at other tables, other rows, and the before/after images, so it handles cross-row rules like "an employee's salary must not exceed their manager's". The cost is that triggers hide logic, run per statement or per row, and complicate debugging and bulk loads.

Rule of thumb: express it as a CHECK if you can, a trigger only if you must, and prefer application-layer validation for anything involving external state.

Why does UNIQUE allow multiple NULLs?

Because comparison with NULL yields unknown. To reject a duplicate the engine must prove two values are equal; NULL = NULL is unknown, never true, so it cannot prove a violation. SQL Server is the notable exception in practice — it treats NULLs as equal for uniqueness and allows only one; use a filtered index (WHERE col IS NOT NULL) to get the standard behaviour there.

Normalization, dependencies and denormalization

Asked in almost every DBMS round. Learn it as a story about one bad table getting fixed, not as five definitions.

Why normalize: the three anomalies

Start from a deliberately bad table that stores everything at once:

emp_bad — unnormalized
emp_idnameskillsdept_iddept_namedept_location
2BharatJava, SQL10EngineeringKochi
3ChitraSales, CRM20SalesPune

  • Insertion anomaly — you cannot record the new "Legal, Delhi" department until someone is hired into it, because emp_id is the key and cannot be NULL.
  • Update anomaly — Sales moves to Mumbai; you must update every Sales row. Miss one and the database now holds two truths.
  • Deletion anomaly — Chitra and Dev leave; deleting their rows erases the fact that a Sales department in Pune ever existed.

All three have one root cause: the table stores facts about two different things (an employee and a department). Normalization is the discipline of splitting tables so each table describes exactly one thing.

Functional dependency — the underlying idea

Written X → Y, "X functionally determines Y": if two rows agree on X they must agree on Y. In emp_bad: emp_id → name, and also dept_id → dept_name, dept_location.

Full FD
Y depends on the whole of a composite X, not part of it.
Partial FD
Y depends on only part of a composite key. Kills 2NF.
Transitive FD
X → Y and Y → Z, so X → Z indirectly. Kills 3NF.
Trivial FD
Y ⊆ X, e.g. (emp_id, name) → name. Always true, never a problem.
Prime attribute
An attribute that is part of some candidate key. Everything else is non-prime.

Armstrong's axioms (name them if asked to reason formally): reflexivity (if Y ⊆ X then X → Y), augmentation (X → Y implies XZ → YZ), transitivity (X → Y and Y → Z implies X → Z). Derived rules: union, decomposition, pseudo-transitivity.

The normal forms, in order

1NF — atomic values

Every cell holds a single, indivisible value; no repeating groups, no arrays, no comma-separated lists; each row is unique. Our skills column ("Java, SQL") breaks 1NF.

fix1NF
-- move the multivalued attribute into its own table
CREATE TABLE emp_skills (
    emp_id  INT,
    skill   VARCHAR(40),
    PRIMARY KEY (emp_id, skill),
    FOREIGN KEY (emp_id) REFERENCES employees(emp_id)
);
Do not say this

"1NF means adding skill1, skill2, skill3 columns." That is a repeating group and still violates 1NF — plus it breaks the moment someone has four skills.

2NF — no partial dependency

In 1NF and every non-prime attribute depends on the whole primary key. Only relevant when the key is composite.

Example: assignments(emp_id, proj_id, hours, proj_name). The key is (emp_id, proj_id), but proj_name depends on proj_id alone — a partial dependency. Fix by moving proj_name to the projects table.

3NF — no transitive dependency

In 2NF and no non-prime attribute depends on another non-prime attribute. In emp_bad: emp_id → dept_id → dept_name. Fix by splitting out departments. This is exactly the schema in Module 00 — real designs usually stop here.

Formal version worth quoting: for every FD X → Y, either X is a super key, or Y is a prime attribute.

BCNF — the stricter 3NF

For every non-trivial FD X → Y, X must be a super key. No exception for prime attributes. BCNF differs from 3NF only when a table has overlapping composite candidate keys.

The classic BCNF counter-example
studentsubjectteacher
AshaDBMSNair

Rules: each teacher teaches exactly one subject (teacher → subject), and a student takes a subject from one teacher. Candidate keys are (student, subject) and (student, teacher). teacher → subject holds, but teacher alone is not a super key — so this is 3NF (subject is prime) yet not BCNF. Decompose into (teacher, subject) and (student, teacher).

Worth one extra sentence

3NF decomposition is always both lossless and dependency-preserving. BCNF decomposition is always lossless but may lose a functional dependency — in the example above, the rule "a student takes a subject from only one teacher" can no longer be enforced by a key. That trade-off is precisely why production schemas often stop at 3NF.

4NF and 5NF — say the one-liners

  • 4NF: in BCNF and no non-trivial multivalued dependency. If an employee has independent sets of skills and of languages, storing both in one table produces a cartesian explosion of rows — split them.
  • 5NF (PJNF): cannot be decomposed further without losing information; deals with join dependencies. Rare in practice.
  • 6NF: irreducible; used in temporal data warehousing. Mentioning it is enough.

Lossless join and dependency preservation

Two properties any decomposition must be judged against:

  • Lossless (non-additive) join: rejoining the pieces gives back exactly the original rows — no spurious tuples. Guaranteed if the common attribute of the two tables is a super key of at least one of them. This is non-negotiable.
  • Dependency preservation: every original FD can still be checked on a single table without a join. Desirable, sometimes sacrificed for BCNF.

Denormalization

Deliberately reintroducing redundancy to speed up reads: storing dept_name on the employee row, keeping a total_amount on orders instead of summing line items, or maintaining a comment_count counter.

Gain
  • Fewer joins per query
  • Faster reads & simpler reporting
  • Good for read-heavy analytics, dashboards, star schemas
Cost
  • Update anomalies return — now your problem
  • More storage, wider rows
  • Writes must maintain duplicates (triggers, jobs, app code)

The professional line: normalize until it hurts, denormalize until it works — and only after measuring.

Interview questions · Module 03
What is normalization and why do we do it?

Normalization is the process of organising columns and tables to reduce redundancy and eliminate insertion, update and deletion anomalies, by decomposing tables so each one represents a single subject and every fact is stored once. It is driven by functional dependencies, and each normal form removes a specific class of dependency: 1NF removes non-atomic values, 2NF removes partial dependencies, 3NF removes transitive dependencies, BCNF requires every determinant to be a super key.

Benefits: consistency, smaller storage, cleaner enforcement of integrity. Cost: more tables and therefore more joins on read.

Explain 1NF, 2NF, 3NF with one example that carries through all three.

Start with orders(order_id, product_ids, cust_id, cust_city, qty, unit_price) where product_ids is a list.

  1. 1NF: product_ids is not atomic. Split into order_items(order_id, product_id, qty, unit_price).
  2. 2NF: in order_items the key is (order_id, product_id) but unit_price depends on product_id alone — a partial dependency. Move it to products(product_id, unit_price).
  3. 3NF: in orders, order_id → cust_id → cust_city is transitive. Move city to customers(cust_id, cust_city).

Final: orders, order_items, products, customers — each describing one thing.

Difference between 3NF and BCNF?

3NF allows a dependency X → Y where X is not a super key, provided Y is a prime attribute (part of some candidate key). BCNF removes that exception: every determinant must be a super key. So BCNF is strictly stronger, and the two differ only when a relation has multiple overlapping composite candidate keys.

The practical consequence: 3NF decomposition is always dependency-preserving; BCNF decomposition may not be, so a business rule can drop out of the schema and need a trigger or application check instead.

What is a transitive dependency? Give a real example.

When a non-key attribute determines another non-key attribute, so the key determines the second one only indirectly. In employees(emp_id, name, dept_id, dept_name): emp_id → dept_id and dept_id → dept_name, therefore emp_id → dept_name transitively. Because dept_name is stored once per employee rather than once per department, renaming a department requires touching many rows — the update anomaly. Removing it is exactly what 3NF requires.

When would you deliberately denormalize?

When profiling shows a read path is join-bound and the redundancy can be maintained safely. Typical cases: a reporting or OLAP star schema where dimensions are flattened; a feed that needs author_name alongside each post to avoid a join per row; precomputed aggregates like order.total or post.like_count that would otherwise require scanning child tables.

I would pair it with a maintenance strategy — a trigger, a materialized view refresh, or an idempotent background job — and I would treat the normalized tables as the source of truth so the derived copy can always be rebuilt.

Is a table in 3NF always in 2NF? Is every table automatically in 1NF?

Yes to the first — the normal forms are cumulative, so 3NF implies 2NF implies 1NF, and BCNF implies 3NF. No to the second: a table is only in 1NF if all values are atomic and there are no repeating groups. A column storing JSON blobs or comma-separated ids violates 1NF conceptually, even though the engine happily stores it.

Interview questions · Module 04
Difference between DELETE, TRUNCATE and DROP?

DELETE is DML: it removes rows one at a time, accepts a WHERE clause, writes each removal to the transaction log so it can be rolled back, fires row triggers, and leaves identity counters untouched.

TRUNCATE is DDL: it removes all rows by deallocating data pages, so it is much faster, takes no WHERE clause, does not fire triggers, resets identity/auto-increment, and is generally not rollback-able (SQL Server and PostgreSQL are exceptions inside an explicit transaction). It also fails while a foreign key references the table.

DROP is DDL: it removes the table definition, data, indexes, constraints, triggers and permissions entirely.

Say it like thisDELETE is a logged, filterable row operation; TRUNCATE is a structural reset; DROP removes the object itself.
Why should money never be stored as FLOAT?

FLOAT and DOUBLE are binary floating point: most decimal fractions have no exact binary representation, so values drift. 0.1 + 0.2 stores as 0.30000000000000004, sums over millions of rows accumulate error, and equality comparisons fail unpredictably. DECIMAL(p,s) stores digits exactly with a fixed scale, so arithmetic and rounding are deterministic — which is what auditing requires. The usual choice is DECIMAL(19,4), or storing integer paise/cents.

CHAR vs VARCHAR — when is CHAR still the right choice?

CHAR(n) always occupies n characters and pads with spaces; VARCHAR(n) stores the actual length plus 1–2 bytes of overhead. CHAR is marginally faster for fixed-width values because rows stay a predictable size and no length decoding is needed, so it fits genuinely fixed data: country codes CHAR(2), a Y/N flag CHAR(1), a fixed-format hash. For anything variable — names, emails, addresses — VARCHAR wins on space and avoids trailing-space comparison surprises.

Is TRUNCATE DDL or DML, and why does that matter?

DDL. It matters because DDL causes an implicit commit in MySQL and Oracle — so any open transaction is committed before the truncate runs and you cannot roll it back. It also explains why triggers do not fire (no per-row DML events are generated) and why permissions differ: TRUNCATE typically requires ALTER/DROP rights on the table, while DELETE only needs DELETE rights.

Interview questions · Module 05
What is NULL in SQL? Is it the same as 0 or an empty string?

NULL is a marker for a missing or unknown value — it is not a value itself. Zero is a known quantity and '' is a known string of length zero; both occupy the column meaningfully. NULL means "we do not know", which is why SQL uses three-valued logic: every comparison with NULL evaluates to UNKNOWN rather than TRUE or FALSE, and WHERE keeps only TRUE rows.

Practical consequences: test with IS NULL, never = NULL; aggregates other than COUNT(*) skip NULLs; UNIQUE permits repeated NULLs; and NOT IN against a NULL-bearing list returns nothing.

Oracle caveat worth mentioning: Oracle treats an empty string as NULL, unlike every other major engine.

Why does SELECT * FROM employees WHERE city != 'Kochi' miss Farhan?

Farhan's city is NULL. The predicate NULL != 'Kochi' evaluates to UNKNOWN, not TRUE, so the row is filtered out. If you want NULL rows included you must ask explicitly:

fix
WHERE city <> 'Kochi' OR city IS NULL;
-- or
WHERE COALESCE(city, '') <> 'Kochi';

This is the single most common cause of "rows went missing" bugs in reports.

Difference between COALESCE, ISNULL/IFNULL and NULLIF?
  • COALESCE(a, b, c, …) — ANSI standard, takes any number of arguments and returns the first non-NULL. Portable.
  • IFNULL(a,b) (MySQL) / ISNULL(a,b) (SQL Server) / NVL(a,b) (Oracle) — two-argument, vendor-specific equivalents. SQL Server's ISNULL also truncates the result to the first argument's type, which can surprise you.
  • NULLIF(a,b) is the inverse idea: it produces a NULL when the two arguments are equal, most often used as x / NULLIF(y,0) to avoid divide-by-zero.

Prefer COALESCE unless you need the vendor behaviour.

BETWEEN 10 AND 20 — inclusive or exclusive? And with dates?

Inclusive of both endpoints; it is shorthand for >= 10 AND <= 20. With dates there is a real trap: if the column is a DATETIME, BETWEEN '2024-01-01' AND '2024-01-31' excludes almost all of 31 January, because the literal is interpreted as midnight. Use a half-open range instead: >= '2024-01-01' AND < '2024-02-01'. That is also index-friendly, unlike wrapping the column in a function.

What does SELECT * cost you in production code?

It fetches columns nobody needs (extra I/O and network), prevents index-only scans because the index rarely covers every column, breaks application code silently when a column is added or reordered, and makes views and CTAS statements fragile. It is fine for exploration; in shipped code name your columns.

Interview questions · Module 06
Difference between DISTINCT and GROUP BY?

For simply removing duplicates from a column list they are equivalent, and most optimizers produce the same plan. The difference is intent and capability: DISTINCT only deduplicates the projected rows, whereas GROUP BY creates groups you can then aggregate over and filter with HAVING.

So: use DISTINCT when you want unique rows; use GROUP BY when you want one row per group with a computed value. If you find yourself writing SELECT DISTINCT with an aggregate, you wanted GROUP BY.

Can you use a column alias in the WHERE clause? Why or why not?

No, not portably. SQL's logical processing order evaluates FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY. Since the alias is created in SELECT, it does not exist yet when WHERE runs. ORDER BY runs after SELECT, so aliases work there.

Workarounds: repeat the expression in WHERE, or wrap the query in a subquery/CTE and filter on the outer level.

Two points to add: pagination without a deterministic ORDER BY can return the same row on two pages, so always include a tie-breaking unique column; and for deep pages, keyset pagination beats OFFSET.

Where do NULLs sort — first or last?

It is engine-defined. MySQL and SQL Server place NULLs first in ascending order; PostgreSQL and Oracle place them last (they treat NULL as the largest value). If it matters, be explicit: ORDER BY city NULLS LAST in Postgres/Oracle, or ORDER BY city IS NULL, city in MySQL.

Interview questions · Module 08
Difference between WHERE and HAVING?

WHERE filters individual rows before grouping and cannot reference aggregate functions. HAVING filters groups after GROUP BY has run and is the only place aggregates can be used as conditions.

Example: WHERE salary > 50000 keeps well-paid employees; HAVING AVG(salary) > 50000 keeps departments whose average is high — an entirely different question. You can use both in one query, and you should, because filtering rows early is cheaper than aggregating and discarding.

One nuance: HAVING without GROUP BY is legal — the entire result becomes a single group, so SELECT COUNT(*) FROM t HAVING COUNT(*) > 10 works.

Difference between COUNT(*), COUNT(1) and COUNT(column)?

COUNT(*) counts rows, including rows that are entirely NULL. COUNT(1) counts rows too — the constant is never NULL — and every modern optimizer treats it identically to COUNT(*), so the "COUNT(1) is faster" claim is a myth. COUNT(column) counts only rows where that column is non-NULL, so it can legitimately return a smaller number.

In our data: COUNT(*) = 7, COUNT(city) = 6 (Farhan's city is NULL), COUNT(DISTINCT dept_id) = 3 (Gita's NULL is excluded).

Can you use an aggregate function in the WHERE clause?

No. WHERE is evaluated before rows are grouped, so no aggregate exists yet — WHERE COUNT(*) > 1 is a syntax error. Put it in HAVING. If you need to filter rows by a whole-table aggregate, use a subquery: WHERE salary > (SELECT AVG(salary) FROM employees) is legal because the subquery is computed independently.

What happens to NULLs in GROUP BY?

All NULLs are collected into a single group. This is deliberate and differs from the usual "NULL is never equal to NULL" rule — GROUP BY, DISTINCT and UNION all treat NULLs as identical for the purpose of grouping. So a NULL department yields one row in the output, not zero and not one per NULL.

The logical order of execution

One diagram that explains half the "why doesn't this work?" questions in SQL. Learn it and you can reason about any query.

You write a query starting with SELECT. The database evaluates it in a completely different order. Every alias-scope rule, every WHERE-vs-HAVING question and every DISTINCT-with-ORDER-BY error follows from this sequence:

execution ordermemorise
1.  FROM        -- pick the base table(s)
2.  JOIN / ON   -- combine them, produce the working set
3.  WHERE       -- discard rows          (no aliases, no aggregates)
4.  GROUP BY    -- collapse rows into groups
5.  HAVING      -- discard groups        (aggregates allowed)
6.  SELECT      -- evaluate expressions, create column aliases
7.  DISTINCT    -- remove duplicate result rows
8.  ORDER BY    -- sort                  (aliases ARE visible here)
9.  LIMIT/OFFSET-- take a slice

Window functions (Module 14) are evaluated at step 6, with SELECT — after HAVING, before DISTINCT and ORDER BY. That single fact explains why you cannot filter on ROW_NUMBER() in a WHERE clause and must wrap the query in a CTE or subquery instead.

Logical order ≠ physical order

This is the logical order the standard defines, and it is what determines correctness. The optimizer is free to execute differently — pushing a predicate below a join, streaming an aggregate, stopping early for a LIMIT — as long as the result matches. If an interviewer asks "does the database really do it in that order?", that distinction is the answer they are hoping for.

Interview questions · Module 09
What is the order of execution of an SQL query?

FROM and JOIN first, then WHERE, GROUP BY, HAVING, then SELECT (including window functions), then DISTINCT, ORDER BY, and finally LIMIT/OFFSET. It differs from the writing order, which starts at SELECT.

The practical value: it tells you where aliases are visible, why aggregates cannot appear in WHERE, why row filters belong in WHERE rather than HAVING, and why window functions have to be filtered in an outer query.

Say it like thisSQL is written SELECT-first but executed FROM-first — that inversion explains almost every scope rule in the language.
Where do window functions fit in that order?

They are evaluated as part of the SELECT step, after GROUP BY and HAVING and before DISTINCT and ORDER BY. So a window function sees the post-aggregation result set — which is why you can legally write RANK() OVER (ORDER BY SUM(salary) DESC) in a grouped query — but you cannot reference the window result in WHERE or HAVING. To filter on it, wrap the query:

pattern
WITH ranked AS (
  SELECT name, salary,
         ROW_NUMBER() OVER (ORDER BY salary DESC) AS rn
  FROM   employees
)
SELECT * FROM ranked WHERE rn <= 3;
Is the physical execution the same as the logical order?

No. The logical order defines the meaning of the query; the optimizer chooses the physical plan. It routinely reorders joins, pushes WHERE predicates down below joins to cut rows early, converts a subquery into a join, uses an index to satisfy ORDER BY without sorting, and stops reading once LIMIT is satisfied. The guarantee is only that the result is identical to what the logical order would produce.

A join combines rows from two tables based on a predicate. Explain all types of joins with examples.

Given employees and departments:

  • INNER JOIN — only rows that match on both sides. Employees with a valid department.
  • LEFT OUTER JOIN — all rows from the left table plus matches; unmatched right columns are NULL. All employees, even the unassigned one.
  • RIGHT OUTER JOIN — mirror image. All departments, even empty ones.
  • FULL OUTER JOIN — union of both outer joins; everything, matched or not.
  • CROSS JOIN — Cartesian product, no ON clause. m × n rows.
  • SELF JOIN — not a separate type, just a table joined to itself with two aliases; used for hierarchies like employee→manager.

The useful add-on is the anti-join: a LEFT JOIN with WHERE right.key IS NULL, which returns exactly the rows that have no partner.

Difference between a condition in ON and a condition in WHERE for an outer join?

For an INNER JOIN there is no difference — the optimizer treats them identically. For an OUTER JOIN they mean different things:

  • ON is applied while matching. A row that fails it still survives, padded with NULLs.
  • WHERE is applied after the join. NULL-padded rows fail almost any condition, so the outer join collapses into an inner join.
compare
-- all employees; department shown only if it is in Kochi
LEFT JOIN departments d ON e.dept_id = d.dept_id AND d.location = 'Kochi';

-- effectively an INNER JOIN: only Kochi employees survive
LEFT JOIN departments d ON e.dept_id = d.dept_id
WHERE d.location = 'Kochi';

Exception worth naming: WHERE d.dept_id IS NULL is intentional — that is the anti-join idiom.

What is a self join and when have you needed one?

A self join is a join of a table to itself using two different aliases, so each alias plays a different role. It is required whenever a relationship exists within one table: an employee's manager, a category's parent category, a reply's parent comment, or comparing two rows of the same entity (same city, consecutive dates, duplicate detection).

Practical detail: use LEFT JOIN when the relationship is optional (the top of a hierarchy has no parent), and add an inequality such as a.id < b.id when producing pairs, otherwise you get each pair twice plus every row matched to itself.

If table A has 10 rows and table B has 5 rows, how many rows does each join return?
  • CROSS JOIN: exactly 50.
  • INNER JOIN: between 0 and 50 — it depends entirely on the data. If the join column is unique in B and every A row matches, exactly 10.
  • LEFT JOIN: at least 10 (every A row appears at least once), possibly more if an A row matches several B rows.
  • RIGHT JOIN: at least 5.
  • FULL OUTER: at least max(10, 5) = 10.

The point of the question is the "at least" reasoning: a LEFT JOIN can increase row count, which is how a careless join inflates aggregates. That is why SUM after a one-to-many join is a classic bug.

How do you find records present in one table but not another?
three ways
-- 1. anti-join
SELECT a.* FROM a LEFT JOIN b ON a.id = b.a_id WHERE b.a_id IS NULL;

-- 2. NOT EXISTS  (preferred: NULL-safe and usually best plan)
SELECT a.* FROM a WHERE NOT EXISTS (SELECT 1 FROM b WHERE b.a_id = a.id);

-- 3. set operator (compares whole rows, removes duplicates)
SELECT id FROM a EXCEPT SELECT a_id FROM b;   -- Oracle: MINUS

I default to NOT EXISTS: it short-circuits on the first match, it is immune to the NULL problem that breaks NOT IN, and it does not require the column lists to line up the way EXCEPT does.

Why avoid NATURAL JOIN and the old comma-join syntax?

NATURAL JOIN infers the join condition from every identically-named column. Add a created_at or status column to both tables and the join silently changes meaning — a bug with no error message. Always state the condition explicitly.

The comma syntax FROM a, b WHERE a.id = b.a_id is valid but mixes join conditions with filters, offers no outer-join form, and turns into an accidental Cartesian product the moment someone forgets the WHERE. Explicit JOIN … ON is the ANSI-92 style and is what reviewers expect.

Set operators treat NULLs as equal

For deduplication and matching purposes, two NULLs are considered the same value — the same exception that applies to DISTINCT and GROUP BY. So INTERSECT will match a NULL to a NULL, whereas a join on the same columns would not. That contrast is a good answer to have ready.

UNION vs JOIN

Say it geometrically: a JOIN adds columns (combines tables side by side, matching on a key); a UNION adds rows (stacks result sets that share a shape). If you need fields from two tables in one row, join. If you need records from two sources in one list — this year's orders plus last year's archive — union.

Interview questions · Module 11
Difference between UNION and UNION ALL? Which is faster?

UNION removes duplicate rows from the combined result; UNION ALL keeps everything. UNION ALL is faster because deduplication requires the engine to sort or hash the entire result set — an O(n log n) step plus memory, potentially spilling to disk.

So use UNION ALL by default and reach for UNION only when duplicates are genuinely possible and unwanted. If the two branches are mutually exclusive by construction (different date ranges, different status values), duplicates cannot occur and UNION is pure waste.

Difference between UNION and JOIN?

They combine data along different axes. A JOIN is horizontal: it matches rows from two tables on a condition and produces wider rows containing columns from both. A UNION is vertical: it appends the rows of one result set to another, requiring identical column counts and compatible types, producing more rows of the same width.

Concretely: "show each employee with their department name" is a join; "show all current and archived employees in one list" is a union.

Does EXCEPT/MINUS exist in MySQL, and what do you use instead?

MySQL added INTERSECT and EXCEPT only in version 8.0.31; older versions have neither, and MySQL has never supported Oracle's MINUS keyword. The portable substitutes are the anti-join and the semi-join:

equivalents
-- EXCEPT
SELECT a.id FROM a WHERE NOT EXISTS (SELECT 1 FROM b WHERE b.id = a.id);

-- INTERSECT
SELECT DISTINCT a.id FROM a WHERE EXISTS (SELECT 1 FROM b WHERE b.id = a.id);

One behavioural difference to note: EXCEPT compares entire rows and removes duplicates; the NOT EXISTS version compares only the columns you name and preserves duplicates unless you add DISTINCT.

Interview questions · Module 12
Difference between IN and EXISTS — and which is faster?

Semantics. IN compares a value against a list of returned values. EXISTS checks only whether the subquery produces at least one row, so it stops at the first match and ignores what is selected.

NULL handling. This is the real difference. If the IN list contains a NULL, NOT IN returns no rows at all, because x <> NULL is UNKNOWN. NOT EXISTS is unaffected. So for anti-joins, NOT EXISTS is the safe choice.

Performance. The old rule of thumb was "IN for a small subquery result, EXISTS for a large one, because EXISTS short-circuits and IN materialises the list". On modern optimizers — Postgres, SQL Server, MySQL 8, Oracle — both are usually rewritten into the same semi-join, so plans are often identical. I would say the correctness difference is the reason to choose, and then check the execution plan if it is hot.

Say it like thisThey usually plan the same; I pick EXISTS by default because it is NULL-safe and expresses intent — "does a related row exist" — more directly.
What is a correlated subquery? Give an example and its cost.

A subquery that references a column from the outer query, so it cannot run standalone — conceptually it is evaluated once per outer row. The classic example is "employees earning above their own department's average".

Cost: naively it is O(n) executions of the inner query, so on large tables it can be far slower than an equivalent join or window function. Optimizers frequently decorrelate it into a join or a hash semi-join, but not always — especially when the correlation sits inside an OR or a scalar SELECT.

The modern rewrite is usually a window function or a join to a pre-aggregated derived table:

rewrite
SELECT name, dept_id, salary
FROM (SELECT name, dept_id, salary,
             AVG(salary) OVER (PARTITION BY dept_id) AS dept_avg
      FROM employees) t
WHERE salary > dept_avg;
Find the second highest salary — give at least three approaches.
answerknow all of these
-- 1. Subquery on MAX: the "no window functions allowed" answer
SELECT MAX(salary) FROM employees
WHERE  salary < (SELECT MAX(salary) FROM employees);

-- 2. DISTINCT + LIMIT/OFFSET  (MySQL, Postgres)
SELECT DISTINCT salary FROM employees ORDER BY salary DESC LIMIT 1 OFFSET 1;

-- 3. DENSE_RANK — generalises to the Nth and handles ties correctly
SELECT DISTINCT salary FROM (
   SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk
   FROM   employees) t
WHERE rnk = 2;

-- 4. Correlated count: "exactly one distinct salary is higher"
SELECT DISTINCT e.salary FROM employees e
WHERE 1 = (SELECT COUNT(DISTINCT e2.salary) FROM employees e2
           WHERE e2.salary > e.salary);

Two points that turn a correct answer into a strong one: approach 1 returns NULL rather than erroring when there is no second salary, which is often the desired behaviour; and DENSE_RANK is right when ties should share a rank — with two employees on 90000, the "second highest salary" is 90000, and the second-highest distinct salary is 72000. Ask the interviewer which they mean.

Difference between a subquery and a join — when do you pick each?

A join combines columns from multiple tables into one result and can return columns from both sides. A subquery computes an intermediate value or a filtering set and, except for derived tables, returns nothing to the output.

I use a join when I need data from both tables. I use a subquery when I need a single computed threshold (the company average), an existence test, or a filter set — because it reads closer to the requirement. Historically joins outperformed subqueries; today optimizers usually converge, so I write for clarity first and check the plan if it matters.

One case where the join is clearly better: a subquery in the SELECT list executed per output row is a hidden loop — replacing it with a join to a pre-aggregated set is a real win.

What is a derived table and why must it be aliased?

A derived table is a subquery in the FROM clause — it produces an intermediate result set that the outer query treats as a table. It must have an alias because SQL requires every table expression in FROM to be nameable so its columns can be referenced unambiguously; MySQL and SQL Server raise an error without it (Postgres and Oracle are more lenient).

Derived tables are the pre-CTE way of staging a computation — WITH clauses (Module 13) do the same thing with better readability and reuse.

The WITH clause: named building blocks that make complex queries readable — and the only clean way to walk a hierarchy.

Common Table Expressions

A CTE is a named temporary result set that exists only for the duration of one statement. It does the job of a derived table but sits at the top, is named, and can be referenced more than once.

Why CTEs win
  • Read top-to-bottom instead of inside-out
  • Named steps document intent
  • Referenced multiple times in one query
  • The only way to write recursion in SQL
What they are not
  • Not stored — they vanish after the statement
  • Not always faster than a subquery
  • Not indexable, unlike a temp table
  • Not necessarily materialised — see below
The nuance that impresses

Whether a CTE is materialised (computed once into a work table) or inlined (folded into the outer query) is engine-dependent. PostgreSQL materialised every CTE before v12 — an optimization fence — and since v12 inlines non-recursive, single-reference CTEs unless you write WITH … AS MATERIALIZED. SQL Server and MySQL 8 generally inline. So "a CTE is slower/faster than a subquery" is not universally true; know your engine.

Recursive CTEs

The tool for hierarchies: org charts, category trees, bill-of-materials, graph paths, and generating number or date sequences. Every recursive CTE has exactly two parts joined by UNION ALL:

    UNION ALL
    <recursive member>              -- 2. references cte_name; runs until it returns 0 rows
)
SELECT * FROM cte_name;

Interview questions · Module 13
What is a CTE and how is it different from a subquery?

A CTE is a named temporary result set defined with WITH that exists for the duration of a single statement. Functionally it overlaps with a derived table, but it differs in three ways: it is named and defined before use, so the query reads top-to-bottom instead of inside-out; it can be referenced multiple times in the same statement without repeating the code; and it is the only construct that supports recursion.

It is not a performance feature by itself — depending on the engine it may be inlined into the outer query or materialised once.

Explain a recursive CTE. Where have you used one?

A recursive CTE has an anchor member that produces the starting rows and a recursive member that joins back to the CTE itself, combined with UNION ALL. The engine runs the anchor once, then repeatedly runs the recursive member against the rows produced by the previous iteration, until an iteration returns no rows; the union of all iterations is the result.

Uses: walking an employee-manager hierarchy and computing each person's level or full reporting path; expanding a category tree; exploding a bill of materials; finding connected nodes in a graph; and generating contiguous date or number series to fill gaps in reports.

I always add a termination guard — a depth cap or a visited-path check — because cyclic data would otherwise loop until the engine's recursion limit aborts it.

CTE or temporary table — how do you choose?

CTE when the intermediate result is used once or twice within a single statement and readability is the goal. Temp table when the intermediate is large, reused across several statements, or would benefit from an index or statistics — because a CTE can be recomputed on every reference, while a temp table is materialised once and can be indexed.

A concrete signal: if I reference the same CTE three times and the plan shows the same expensive scan three times, I move it to a temp table.

The topic that separates candidates. Every "Nth highest", "top per group", "running total" and "compare to previous row" question is a window function question.

The core idea

An aggregate function collapses rows: ten employees become one average. A window function computes across a set of related rows while keeping every row. You get the group's answer attached to each individual row — which is exactly what GROUP BY cannot do.

Interview questions · Module 14
Difference between RANK, DENSE_RANK and ROW_NUMBER?

All three assign a number to each row within a window ordered by some expression; they differ in how they treat ties.

  • ROW_NUMBER() gives a unique sequential number, breaking ties arbitrarily: 1, 2, 3, 4.
  • RANK() gives tied rows the same rank and then skips: 1, 2, 2, 4.
  • DENSE_RANK() gives tied rows the same rank without gaps: 1, 2, 2, 3.

Choose ROW_NUMBER for deduplication or picking exactly one row per group, RANK for leaderboard-style positions, DENSE_RANK for "Nth distinct value" questions like the Nth highest salary.

Difference between GROUP BY and a window function?

GROUP BY collapses each group into a single output row — detail is lost, and you can only select grouped columns or aggregates. A window function computes over a set of related rows but returns a value for every input row, so detail and aggregate coexist.

"Show each employee alongside their department's average salary" is impossible with GROUP BY alone (you would need a self-join to the aggregate); with AVG(salary) OVER (PARTITION BY dept_id) it is one pass and one line. You can also combine them: window functions are evaluated after GROUP BY, so RANK() OVER (ORDER BY SUM(sales) DESC) ranks aggregated groups.

Write a query for the top 3 earners in each department.
answer
WITH ranked AS (
    SELECT e.name, d.dept_name, e.salary,
           DENSE_RANK() OVER (PARTITION BY e.dept_id
                              ORDER BY e.salary DESC) AS rnk
    FROM   employees e
    JOIN   departments d ON d.dept_id = e.dept_id
)
SELECT dept_name, name, salary
FROM   ranked
WHERE  rnk <= 3
ORDER BY dept_name, salary DESC;

Points to mention while writing it: DENSE_RANK rather than ROW_NUMBER so that genuine ties are all returned; the CTE exists because you cannot filter a window result in WHERE; and if the interviewer bans window functions, the fallback is a correlated count — WHERE (SELECT COUNT(DISTINCT salary) FROM employees e2 WHERE e2.dept_id = e.dept_id AND e2.salary > e.salary) < 3.

How do you compute a running total and a month-over-month change?
answer
SELECT month,
       revenue,
       SUM(revenue) OVER (ORDER BY month
                          ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_total,
       LAG(revenue)  OVER (ORDER BY month)                                  AS prev_month,
       ROUND(100.0 * (revenue - LAG(revenue) OVER (ORDER BY month))
             / NULLIF(LAG(revenue) OVER (ORDER BY month), 0), 2)            AS mom_pct
FROM   monthly_sales;

Two details that matter: NULLIF(..., 0) guards against divide-by-zero when the previous month was zero, and multiplying by 100.0 rather than 100 avoids integer division.

Why can't you use a window function in the WHERE clause?

Because of the logical processing order: WHERE is evaluated at step 3, but window functions are computed at step 6 as part of SELECT, after grouping. At the time WHERE runs, the window result does not exist yet. The standard fix is to compute it in a CTE or derived table and filter in the outer query. PostgreSQL offers QUALIFY-like filtering only via subqueries; Snowflake and Teradata have a dedicated QUALIFY clause, which is worth naming if the interviewer works with those.

What is the default window frame, and why does it matter?

If you write OVER (ORDER BY x) with no frame clause, the default is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW. If you omit ORDER BY entirely, the frame is the whole partition.

It matters in two ways. First, LAST_VALUE() with the default frame returns the current row rather than the partition's final row — you must widen the frame explicitly. Second, RANGE lumps rows with equal ORDER BY values into the same boundary, so a running total over duplicate dates jumps in blocks; if you want strict row-by-row accumulation, write ROWS instead.

A view is a stored query that behaves like a table. It stores no data (unless materialized) — the query runs each time the view is referenced.

Why views exist
  • Security — expose columns/rows a role may see, hide salary
  • Simplicity — hide a five-table join behind one name

  • Logical independence — restructure tables, keep the view's shape
Limits
  • No performance gain — it is just the query, re-run

When is a view updatable?

Broadly: it must map to exactly one base table and each result row must correspond to one base row. So no DISTINCT, GROUP BY, HAVING, aggregate functions, UNION, or (usually) joins, and every NOT NULL column of the base table without a default must be present. WITH CHECK OPTION additionally prevents inserting or updating a row that would fall outside the view's WHERE condition. For anything more complex, use an INSTEAD OF trigger.

Cursors

A cursor processes a result set one row at a time, which is the opposite of how SQL is meant to work.

OPEN cur;                        -- 1. declare  2. open

Interview questions · Module 15
What is a view? Does it store data? Can you update through it?

A view is a named stored SELECT statement, a virtual table. A standard view stores no data — the underlying query executes whenever the view is referenced, so results are always current. A materialized view is the exception: it physically stores the result and must be refreshed, trading staleness for speed.

You can update through a simple view that maps one-to-one to a single base table with no DISTINCT, GROUP BY, aggregate, UNION or (typically) join. Add WITH CHECK OPTION to stop rows being written that the view itself could not see. For complex views, an INSTEAD OF trigger implements the write path explicitly.

Main reasons to use views: restricting column/row access for security, encapsulating complicated joins, and giving applications a stable interface while the underlying tables change.

Difference between a stored procedure and a function?

A function must return a value and is designed to be used inside expressions — you can call it in a SELECT list or a WHERE clause. It should be free of side effects, so DML and transaction control are generally forbidden.

A stored procedure is invoked as a standalone statement with CALL or EXEC, may return zero, one or many values through OUT parameters or result sets, and may perform DML, manage transactions and handle exceptions.

Rule of thumb: computation → function; operation → procedure.

What is a trigger, and when would you avoid one?

A trigger is procedural code the database executes automatically in response to an INSERT, UPDATE or DELETE — before, after, or instead of the event, at row or statement level. Typical uses are audit logging, enforcing rules across tables, and maintaining derived values.

I avoid them when the logic belongs to the application and would be invisible to whoever debugs it later, when the table takes bulk loads (row triggers multiply the cost), and when triggers would chain into other triggers, which makes ordering and deadlocks hard to reason about. I also note they do not fire on TRUNCATE, so an audit trail based purely on triggers can be bypassed.

What is a cursor and why is it discouraged?

A cursor is a database object that lets procedural code traverse a result set one row at a time: declare, open, fetch in a loop, close, deallocate. It is discouraged because SQL engines are optimized for set-based work — a single UPDATE touching a million rows is planned once and executed efficiently, while a cursor issues a million individual operations, keeps a result set and locks alive throughout, and cannot be parallelised.

Most cursor code can be rewritten as a single statement using joins, CASE or window functions. I would keep a cursor only for genuinely row-by-row external work.

What a transaction is

A transaction is a single logical unit of work — a sequence of operations that must either all succeed or all fail. The canonical example is a money transfer: debit one account, credit another. A crash between the two must not leave money destroyed.

Deadlocks

Two transactions each hold a lock the other needs, so neither can proceed:

scenariothe cycle
T1: UPDATE accounts SET … WHERE acc_id = 101;   -- holds X lock on 101
T2: UPDATE accounts SET … WHERE acc_id = 202;   -- holds X lock on 202
T1: UPDATE accounts SET … WHERE acc_id = 202;   -- waits for T2
T2: UPDATE accounts SET … WHERE acc_id = 101;   -- waits for T1   -> deadlock

The engine detects the cycle in its wait-for graph and kills one transaction (the "victim"), which then gets a deadlock error and must retry. Prevention: always acquire locks in a consistent order (e.g. ascending account id); keep transactions short; use the lowest workable isolation level; add indexes so updates lock few rows; and write applications that retry on deadlock rather than crashing.

Interview questions · Module 16
Explain ACID properties with an example.

Take transferring ₹5,000 from account A to B — two updates in one transaction.

  • Atomicity: both updates commit or neither does. If the server dies after the debit, the undo log rolls it back on restart, so money is never destroyed.
  • Consistency: the invariant "total money is unchanged" and every constraint (balance ≥ 0, valid foreign keys) holds before and after.
  • Isolation: a concurrent balance report must not see the debit without the credit. Isolation levels control how strictly this is enforced.
  • Durability: once COMMIT returns, the change survives a power cut, because the write-ahead log was flushed to durable storage before the commit was acknowledged.
What are the isolation levels and which anomaly does each prevent?

Four standard levels, ordered by strictness:

  1. READ UNCOMMITTED — allows dirty reads. Rarely used; acceptable only for approximate reporting.
  2. READ COMMITTED — you only see committed data, so no dirty reads, but the same row can change between two reads. Default in PostgreSQL, Oracle and SQL Server.
  3. REPEATABLE READ — a row you have read will not change for the rest of the transaction; phantoms may still appear in the standard, though InnoDB prevents them with gap locks. MySQL's default.
  4. SERIALIZABLE — the result is equivalent to running the transactions one at a time; prevents all three anomalies at the cost of concurrency and more rollbacks.

The trade-off to state explicitly: higher isolation means more locking or more aborts, so you choose the weakest level that keeps your invariants true.

Difference between a dirty read, a non-repeatable read and a phantom read?

A dirty read sees uncommitted data that may later be rolled back — the value read never legitimately existed. A non-repeatable read sees committed data, but a row's value changes between two reads inside the same transaction. A phantom read also involves committed data, but the change is a new or removed row matching your search condition, so re-running the same query returns a different set.

The shorthand: dirty = uncommitted data; non-repeatable = same row, different value; phantom = same query, different rows.

What is a deadlock and how do you prevent it?

A deadlock is a circular wait: T1 holds a lock T2 wants while T2 holds a lock T1 wants, so neither can progress. Databases detect the cycle and abort one transaction as the victim rather than waiting forever.

Prevention in order of usefulness: access resources in a consistent order across all code paths; keep transactions short and do not wait on user input inside one; use the lowest sufficient isolation level; index the columns used in WHERE clauses of updates so fewer rows are locked; and make the application retry the aborted transaction, since deadlocks cannot be eliminated entirely.

What is MVCC?

Multi-Version Concurrency Control. Instead of readers taking locks, each write creates a new version of the row tagged with a transaction id, and every transaction reads the snapshot consistent with its own start point. The consequence is that readers never block writers and writers never block readers, which dramatically improves concurrency for read-heavy workloads.

The costs: old versions accumulate and need cleanup (Postgres VACUUM, InnoDB's purge thread and undo tablespace), and write-write conflicts still need locking or abort-and-retry. PostgreSQL, Oracle and MySQL InnoDB all use MVCC.

What is a savepoint?

A named marker inside a transaction. ROLLBACK TO SAVEPOINT x undoes everything after that point while keeping the earlier work and the transaction itself alive — useful for long multi-step procedures where one optional step may fail. The transaction still must be committed or rolled back as a whole afterwards.

Indexes and query optimization

"How would you make this query faster?" is the most common senior-flavoured question asked of freshers. This module is the answer.

What an index is

An index is a separate data structure — almost always a B+ tree — that stores the indexed column's values in sorted order together with pointers to the rows. It converts a full table scan, O(n), into a tree descent, O(log n). The textbook analogy is the index at the back of a book: rather than reading every page to find "normalization", you look up the term and jump to page 214.

The trade-off is not subtle: reads get faster, writes get slower, because every INSERT, UPDATE or DELETE must also maintain every affected index, and each index consumes disk space.

  1. Measure first — read the execution plan; never guess.
  2. Index the WHERE, JOIN and ORDER BY columns, respecting the leftmost-prefix rule.
  3. Select only the columns you need — enables covering indexes, cuts I/O.
  4. Make predicates sargable — no functions on indexed columns.
  5. Filter early — WHERE before HAVING, reduce rows before joining.
  6. Prefer joins/EXISTS to correlated subqueries in the SELECT list.
  7. UNION ALL instead of UNION when duplicates are impossible.
  8. Avoid SELECT DISTINCT used to paper over a bad join — fix the join instead.

Interview questions · Module 17
What is an index? What are its disadvantages?

An index is an auxiliary B+ tree structure that keeps a column's values sorted with pointers to the corresponding rows, letting the engine locate matching rows in logarithmic time instead of scanning the whole table. It also lets the engine satisfy ORDER BY and range queries without sorting.

Disadvantages: every write must update every affected index, so INSERT/UPDATE/DELETE get slower; indexes consume significant disk and memory; too many indexes confuse the optimizer and inflate maintenance; and an index on a low-selectivity column may be ignored entirely, costing space for nothing.

Say it like thisAn index trades write throughput and storage for read speed — so I index what the workload actually filters, joins and sorts on, then verify with the execution plan.
Difference between a clustered and a non-clustered index?

A clustered index defines the physical order in which rows are stored — the leaf level of the index is the table data. There can be only one per table, and lookups through it need no extra step. In InnoDB the primary key is automatically the clustered index; if you do not define one, a hidden row id is used.

A non-clustered index is a separate structure holding the indexed key plus a pointer back to the row (in InnoDB, the primary key value). You can have many. A lookup may require a second read to fetch the remaining columns — a "bookmark lookup" or "key lookup" — unless the index covers the query.

Consequence worth adding: with InnoDB, a wide primary key makes every secondary index bigger, since each entry stores the PK value.

How would you optimize a slow query?

I would work in this order:

  1. Reproduce and measure — get the actual execution plan and the row counts, so I am tuning the real bottleneck rather than a guess.
  2. Look for scans that should be seeks — is there an index on the WHERE/JOIN columns? Is a predicate non-sargable because a function wraps the column?
  3. Check row estimates against actuals — a large gap means stale statistics or a bad join order.
  4. Reduce the data touched — select fewer columns, filter earlier, avoid SELECT *, replace UNION with UNION ALL, remove needless DISTINCT.
  5. Rewrite the shape — decorrelate subqueries, replace a per-row scalar subquery with a join to a pre-aggregate, use a window function instead of a self-join.
  6. Consider structure — a covering or composite index, partitioning by date, or a materialized view for an expensive repeated aggregate.
  7. Re-measure and confirm the write path did not regress from the new index.
Should you index every column?

No. Each index adds write cost and storage, and indexes on low-selectivity columns (a boolean, a status with three values) are usually ignored because a scan is cheaper than random I/O for a large fraction of the table. Redundant indexes are also common: given (dept_id, salary), a separate index on (dept_id) is unnecessary because of the leftmost-prefix rule.

I index primary and foreign keys, the columns that appear in high-frequency WHERE and JOIN clauses, and columns used for sorting — and I periodically check for unused indexes and drop them.

What is a covering index?

An index that contains every column a query references, so the engine can answer entirely from the index without reading the table — an index-only scan. For SELECT name FROM employees WHERE dept_id = 10, an index on (dept_id, name) is covering. Postgres and SQL Server let you add non-key payload columns with INCLUDE (…), which keeps the tree narrow while still covering.

Why is a B+ tree used rather than a hash index or a binary tree?

B+ trees are shallow and wide — each node is a disk page holding hundreds of keys — so finding any row takes only three or four page reads even in a huge table, which matters because disk I/O dominates. All values sit in the leaf level, which is a linked list, making range scans and ORDER BY efficient. They also stay balanced under inserts and deletes.

Hash indexes give O(1) equality lookups but cannot serve ranges, prefix matches, or sorted output. A binary tree would be far too deep for disk-resident data, costing one I/O per level.

Security, integrity and scaling

SQL injection, privileges, and the distributed-systems vocabulary that shows up in the last five minutes of an interview.

SQL injection

An attack where user input is concatenated into a query and reinterpreted as code. The classic:

vulnerablenever do this
-- application builds:  "SELECT * FROM users WHERE email = '" + input + "'"
-- attacker types:      ' OR '1'='1
SELECT * FROM users WHERE email = '' OR '1'='1';    -- returns every user
defenceparameterized query
-- the input is sent separately from the SQL text and can never become code
PREPARE stmt FROM 'SELECT * FROM users WHERE email = ?';
SET @e = ''' OR ''1''=''1';
EXECUTE stmt USING @e;                 -- searches for that literal string. 0 rows.

Defences, in priority order:

  1. Parameterized queries / prepared statements — the only real fix. Data never becomes code.
  2. Stored procedures with parameters (but not if they concatenate strings internally).
  3. Input validation and allow-lists — especially for things that cannot be parameterized, like a column name in an ORDER BY.
  4. Least privilege — the app account should not own the schema or hold DROP rights.
  5. Escaping — a last resort, easy to get wrong.
  6. Generic error messages — do not leak the query or schema in stack traces.

Interview questions · Module 18
What is SQL injection and how do you prevent it?

SQL injection is an attack where untrusted input is concatenated into a SQL statement so that the input is parsed as SQL rather than as data. A login form that builds WHERE email = 'input' can be given ' OR '1'='1, turning the predicate into something always true and returning every row; worse payloads can drop tables or exfiltrate data via UNION.

The definitive prevention is parameterized queries: the SQL text is compiled first, and parameter values are bound separately, so they can never change the statement's structure. Around that I would add least-privilege database accounts, allow-list validation for identifiers that cannot be parameterized (like a sort column), and generic error messages so the schema is not disclosed. ORMs help but only if you avoid their raw-SQL escape hatches.

Difference between GRANT and REVOKE? What is DCL?

DCL is Data Control Language, the part of SQL that manages permissions. GRANT gives a user or role a privilege on an object — SELECT, INSERT, UPDATE, DELETE, EXECUTE, and so on. REVOKE takes it away. WITH GRANT OPTION additionally lets the recipient pass the privilege on, which is worth flagging as a governance risk.

Good practice: grant to roles rather than individuals, grant on views to restrict columns, and give application accounts only the DML they need — never DDL.

OLTP vs OLAP?

OLTP (Online Transaction Processing) handles day-to-day operations: many short read-write transactions, high concurrency, normalized schemas, indexes tuned for point lookups, and correctness guaranteed by ACID. Think an order being placed.

OLAP (Online Analytical Processing) handles analysis: relatively few queries, each scanning huge volumes, aggregating and grouping. Schemas are denormalized into star or snowflake shapes, storage is often columnar, and data arrives in batches through ETL. Think "revenue by region by quarter for three years".

They are usually separated so heavy analytics do not compete with transactional latency.

What is sharding, and what does it cost you?

Sharding is horizontal partitioning across machines: rows are distributed by a shard key so each server holds a subset of the data, which lets write throughput and storage scale beyond one machine.

The costs are real: cross-shard joins and aggregations become application-level work; transactions spanning shards need two-phase commit or must be avoided; a badly chosen shard key creates hot spots; and resharding a live system is genuinely difficult. So the honest answer is that I would exhaust read replicas, caching, partitioning and vertical scaling first.

solution
-- counting approach: they bought as many distinct products as exist
SELECT o.cust_id
FROM   orders o
GROUP BY o.cust_id
HAVING COUNT(DISTINCT o.product_id) = (SELECT COUNT(*) FROM products);

-- double NOT EXISTS: "no product exists that this customer did not buy"
SELECT c.cust_id FROM customers c
WHERE NOT EXISTS (
    SELECT 1 FROM products p
    WHERE NOT EXISTS (SELECT 1 FROM orders o
                      WHERE o.cust_id = c.cust_id AND o.product_id = p.product_id));

The double-negation form is relational division. If you can explain why two NOT EXISTS mean "for all", you have answered a question most candidates cannot.

solution

Concepts and design

What is a relation?

A table — a set of tuples over a fixed set of attributes. Because it is a set, the relational model says row order carries no meaning and duplicate rows should not exist (SQL relaxes both).

What is a tuple?

A single row of a relation: one complete real-world fact, with one value per attribute.

What is a composite key?

A primary key made of two or more columns, where uniqueness holds for the combination rather than for any single column. assignments(emp_id, proj_id) is one.

Can a table have no primary key?

Technically yes — SQL permits it — but it is a design flaw: rows become indistinguishable, replication and updates get unsafe, and InnoDB silently creates a hidden key anyway. Always declare one.

What is referential integrity?

The guarantee that every non-NULL foreign key value matches an existing key in the referenced table, so there are no orphan rows. Enforced by FOREIGN KEY constraints and referential actions.

What is an entity-relationship diagram used for?

To model the data before writing DDL: it captures entities, their attributes, and the cardinality and participation of relationships, which then map mechanically to tables and foreign keys.

What is a weak entity?

An entity that cannot be identified by its own attributes alone and depends on an owner entity — its key includes the owner's key. An order line item is the standard example.

What is a schema vs a database?

A schema is a namespace grouping tables, views and other objects and defining their structure; a database is the container of one or more schemas plus the storage and configuration behind them. In MySQL the two words are effectively synonymous; in Postgres and SQL Server they are distinct levels.

What is a catalog / data dictionary?

The system tables where the DBMS stores metadata about itself — table definitions, columns, indexes, constraints, privileges. Queried through INFORMATION_SCHEMA or engine-specific views.

What is the difference between a primary key and a super key?

A super key is any column set that uniquely identifies rows, possibly with redundant columns. The primary key is one chosen minimal super key (candidate key), additionally required to be NOT NULL.

Language and syntax

Difference between DDL and DML?

DDL defines structure (CREATE, ALTER, DROP, TRUNCATE) and generally auto-commits; DML manipulates the rows inside that structure (INSERT, UPDATE, DELETE) and participates in transactions.

Is SELECT DDL or DML?

Neither, strictly — it is DQL (Data Query Language). Many textbooks lump it into DML since it operates on data; say DQL and note the alternative.

What does DISTINCT apply to?

The entire select list, not an individual column. SELECT DISTINCT a, b removes duplicate (a,b) pairs.

Can WHERE and HAVING appear in the same query?

Yes, and they should when both row-level and group-level filters are needed. WHERE runs first and reduces the rows fed into grouping.

What does LIMIT do without ORDER BY?

Returns an arbitrary subset — the engine may return any rows it happens to produce first. Without ORDER BY there is no defined row order, so "top 5" is meaningless.

How do you rename a column in the result?

With a column alias: SELECT salary AS monthly_pay. Use double quotes (or backticks in MySQL) if the alias has spaces or must preserve case.

What is the difference between <> and !=?

None functionally; <> is the ANSI standard operator and != is a widely supported synonym. Both return UNKNOWN when either side is NULL.

What does the wildcard _ mean in LIKE?

Exactly one character, whereas % matches zero or more. '_a%' means "second character is a".

How do you search for a literal %?

Escape it: LIKE '50\%' ESCAPE '\', or choose another escape character with the ESCAPE clause.

What is the difference between CAST and CONVERT?

CAST is ANSI standard and portable; CONVERT is vendor-specific and, in SQL Server, additionally accepts a style code for date and number formatting.

How do you concatenate strings portably?

There is no single portable operator: || in Postgres/Oracle/SQLite, CONCAT() in MySQL, + in SQL Server. CONCAT() is the closest to universal on modern versions.

What is an alias, and where can it be used?

A temporary name for a column or table within a query. Column aliases are visible in ORDER BY (and, in some engines, GROUP BY/HAVING) but not in WHERE, because WHERE is evaluated before SELECT.

Joins, subqueries, aggregation

What is the default join type?

JOIN alone means INNER JOIN. Similarly LEFT JOIN means LEFT OUTER JOIN.

What is an equi join vs a non-equi join?

An equi join uses only equality in the ON clause; a non-equi join uses another operator — for example joining a salary to a band table with ON s.salary BETWEEN b.low AND b.high.

What is a semi join?

A join that returns rows from the left table that have a match, without duplicating them or returning right-side columns — what EXISTS and IN express. Its complement is the anti join (NOT EXISTS).

Can you join on more than one column?

Yes: ON a.x = b.x AND a.y = b.y. Required whenever the relationship key is composite.

Can you join more than two tables?

Yes; joins are applied left to right, each producing an intermediate result that the next join uses. The optimizer may reorder them freely for inner joins.

Why did my LEFT JOIN behave like an INNER JOIN?

Because a condition on the right table was placed in WHERE instead of ON. The NULL-padded rows fail that condition and get filtered out.

Why did my SUM double after adding a join?

The join was one-to-many, so each left row was duplicated once per matching right row, and the aggregate counted it multiple times. Aggregate the child table in a subquery first, then join.

Does COUNT(*) count NULL rows?

Yes — it counts rows, regardless of content. COUNT(column) counts only non-NULL values of that column.

What does SUM return over an empty set?

NULL, not 0. Wrap it: COALESCE(SUM(x), 0). COUNT, by contrast, returns 0.

Can you nest aggregate functions?

Not directly — MAX(AVG(x)) is invalid without a GROUP BY that makes the inner aggregate meaningful. Compute the inner aggregate in a subquery or CTE, then aggregate that.

What is a scalar subquery?

A subquery returning exactly one row and one column, usable anywhere a single value is expected. If it returns more than one row, the query errors at runtime.

Does the SELECT list inside EXISTS matter?

No. EXISTS only checks whether rows are produced, so SELECT 1, SELECT * and SELECT NULL behave identically. SELECT 1 is the convention.

Difference between ANY and ALL?

> ANY is true if the value beats at least one of the subquery's values (equivalent to beating the minimum); > ALL requires beating every value (the maximum).

Windows, CTEs and views

What does PARTITION BY do?

Divides the result into independent windows; the function restarts for each partition. It is the window-function analogue of GROUP BY, except rows are not collapsed.

Is PARTITION BY mandatory?

No. Without it the whole result set is a single window, so AVG(salary) OVER () gives the overall average on every row.

Which window functions require ORDER BY?

The ranking family (ROW_NUMBER, RANK, DENSE_RANK, NTILE, PERCENT_RANK) and the offset family (LAG, LEAD, FIRST_VALUE, LAST_VALUE, NTH_VALUE) — anything whose meaning depends on sequence.

What does NTILE(4) produce?

Quartiles: it assigns each row a bucket number from 1 to 4, distributing rows as evenly as possible with earlier buckets taking the extra rows.

Difference between LAG and LEAD?

LAG looks backwards to a previous row in the window's order; LEAD looks forwards. Both accept an offset and a default value for when no such row exists.

Can a CTE be recursive without the RECURSIVE keyword?

In SQL Server, yes — it infers recursion. MySQL and PostgreSQL require WITH RECURSIVE explicitly.

Can you use multiple CTEs in one query?

Yes — separate them with commas after a single WITH, and a later CTE may reference an earlier one.

Can a CTE be used in an UPDATE or DELETE?

Yes in PostgreSQL, SQL Server and MySQL 8: define the CTE, then reference it in the DML statement — the standard way to delete duplicates by ROW_NUMBER.

Difference between a view and a materialized view?

A view stores only the query and re-executes it every time; a materialized view stores the computed result on disk and must be refreshed, trading freshness for speed. MySQL has no materialized views — you emulate them with a summary table.

Does creating a view improve performance?

No, by itself. It is expanded into the referencing query at execution time. Only a materialized or indexed view actually stores results.

Transactions, indexes, engine

What does COMMIT do?

Makes all changes in the transaction permanent and visible to other transactions, releases locks, and guarantees durability by ensuring the log is flushed to stable storage.

Can you roll back a COMMIT?

No. Once committed, the only way back is point-in-time recovery from a backup plus log replay, or a compensating transaction.

What is autocommit?

A session mode where every individual statement is wrapped in its own transaction and committed immediately. It is on by default in MySQL and SQL Server, which is why an accidental UPDATE without WHERE is unrecoverable.

What is a write-ahead log?

The rule that a change is written to the log on durable storage before the corresponding data page is written. It is what makes atomicity and durability possible after a crash.

What is two-phase commit?

A protocol for committing a transaction spanning multiple databases: a coordinator asks every participant to prepare, and only if all vote yes does it tell them to commit. It guarantees atomicity across nodes but blocks if the coordinator fails.

How many clustered indexes can a table have?

One, because it defines the physical row order. You can have many non-clustered indexes.

Does a primary key automatically create an index?

Yes — every major engine creates a unique index to enforce it, clustered by default in InnoDB and SQL Server.

Should you index a foreign key column?

Usually yes. Joins and cascading operations use it constantly, and without an index the parent-side delete must scan the child table. MySQL InnoDB creates one automatically; Postgres and SQL Server do not.

What is index selectivity?

The ratio of distinct values to total rows. High selectivity (an email column) makes an index very effective; low selectivity (a gender column) usually makes the optimizer prefer a scan.

What is a composite index's column order rule?

Leftmost prefix: an index on (a, b, c) serves predicates on a, on (a,b), and on (a,b,c) — but not on b or c alone. Put the most-filtered, equality-tested column first.

What is query optimizer statistics?

Summaries of data distribution (row counts, histograms, distinct values) that the optimizer uses to estimate costs. Stale statistics cause bad plans; refresh with ANALYZE or UPDATE STATISTICS.

What is a temporary table?

A table visible only to the session (or transaction) that created it, dropped automatically at the end. Unlike a CTE it is materialized and can be indexed, so it suits large reused intermediates.

Difference between a heap and a clustered table?

A heap stores rows in no particular order with a row identifier; a clustered table stores rows physically ordered by the clustering key. Heaps make inserts cheap but every lookup needs an index or a scan.

What is normalization's effect on query performance?

It reduces redundancy and speeds writes, but increases the number of joins on read. That trade-off is the reason analytical schemas are deliberately denormalized.

What is a stored procedure's main performance benefit?

The plan is compiled and cached, and multiple statements execute in one round trip instead of many — significant when network latency dominates.

What is the difference between DROP and DELETE of a database object?

DELETE removes rows and is DML; DROP removes the object itself — table, view, index or database — along with its data, constraints and privileges.

What does ON DELETE CASCADE do?

Automatically deletes child rows when the referenced parent row is deleted. Powerful and dangerous — it chains through further cascades without warning.

What is a covering index in one sentence?

An index that includes every column the query needs, so the engine answers entirely from the index without reading the table.

How to behave in the SQL round

  1. Restate the question and confirm the schema before writing. "So — employees table with dept_id and salary; you want one row per department?"
  2. Ask about ties and NULLs. Every ranking question has a tie policy and every join has a NULL story. Asking marks you as someone who has been burned by real data.
  3. Write in execution order, not left to right: FROM first, then filters, then the select list. It reduces mistakes and shows your model of the engine.
  4. Say what you are doing as you type. A silent correct answer scores lower than a narrated one.
  5. Trace your query on two or three sample rows aloud when you finish. You will catch your own bug more often than not.
  6. Offer the alternative. "This uses a window function; without them I'd use a correlated count — do you want that version?"
  7. If you blank, describe the shape. "I need one row per group with the max, so this is a top-N-per-group — CTE plus DENSE_RANK." Partial credit is real.
