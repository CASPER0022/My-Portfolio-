§ 00Orientation

How to use this, and the pitch you memorise

The whole project in one sentence

LegalEase turns a pile of Indian statute PDFs into a searchable knowledge base, finds the handful of passages that actually answer your legal question, and forces a large language model to write advice using only those passages — so every claim can be traced back to a real section number.

How to study this notebook

Every section follows the same three-beat rhythm, because that is exactly the rhythm an interviewer expects from you:

  1. The theory, from zero. What the concept is, why it exists, what the alternatives are. No assumed knowledge.
  2. In LegalEase. The real code from your repository, with the specific numbers you chose and why they are defensible.
  3. Cross-examination. The questions an interviewer will actually fire at you, with model answers. Click a question to reveal the answer — try to answer aloud first, then check. Reading answers passively will not survive a panel.
The single biggest scoring rule

Interviewers do not grade you on whether the project is impressive. They grade you on whether you made decisions and can justify them. Every time you say a number — 1200, 200, 25, 8, 384 — follow it immediately with "because". A candidate who says "chunk size 1200 because a statute section is usually 800–1500 characters and I did not want to split a section across chunks" beats a candidate with a fancier project every single time.

Your 60-second pitch (learn this word for word)

"LegalEase is a full-stack RAG system that answers legal questions from Indian criminal statutes. The problem it solves is that a general LLM will confidently invent section numbers — which is dangerous in law. So instead of trusting the model's memory, I built a retrieval layer: I parse the statute PDFs, split them into 1200-character overlapping chunks, embed each chunk with a MiniLM sentence transformer, and store the 384-dimensional vectors in ChromaDB. At query time I do a two-stage retrieval — a fast vector search for the top 25 candidates, then a cross-encoder reranker that reads the query and each candidate together and keeps the best 8. Those 8 chunks are injected into a strict prompt that tells the model to cite only what is in the context and return structured JSON. The backend is FastAPI, the frontend is React with Vite and Tailwind, and I evaluate retrieval and answer quality with Ragas. The interesting engineering problem was latency versus accuracy — that's what the two-stage retrieval is for."
Domain Indian criminal law (BNS / BNSS) Pattern Two-stage retrieve-then-rerank Output Structured JSON, not free text Guardrail Empty retrieval → refuse to answer

Cross-examination

Tell me about a project you're proud of.

Give the 60-second pitch above, then stop talking. Do not ramble into the tech stack list — let them pull. The pitch already contains four hooks they can grab (hallucination, two-stage retrieval, structured output, evaluation); whichever one they pick is a question you have already prepared.

Say it like this
"The problem, the approach, the interesting trade-off — happy to go deeper on any of those."
Why did you build this? What was the actual motivation?

Have a human reason, not a resume reason. A good honest framing:

"Legal text is the worst-case scenario for a language model — the answers depend on exact section numbers, and a wrong number is worse than no answer. That made it a good stress test for grounding. It also mapped to a real problem: an ordinary person cannot read the Bharatiya Nyaya Sanhita to find out what to do about a neighbour dumping waste on their land."

Then add the engineering motivation: "I wanted to build the whole loop myself — ingestion, retrieval, reranking, serving, evaluation — rather than calling a single hosted RAG API, so I would understand where quality actually comes from."

What was the hardest part?

Pick one, be specific, and describe the fix. Strongest option:

"Retrieval quality. Pure vector search kept returning chunks that were topically similar but legally wrong — for a question about waste dumping it would surface any section that mentioned 'property' or 'nuisance'. Vector similarity is a blunt instrument; it compresses a whole chunk into one 384-dimensional point, so fine distinctions get lost. I fixed it by adding a second stage: retrieve 25 candidates cheaply, then run a cross-encoder that reads the question and each candidate together and scores them properly, and keep only the top 8. Precision went up a lot and I only pay the expensive model on 25 items instead of the whole corpus."

Second option, if they seem more systems-oriented: memory. The reranker plus the embedding model plus ChromaDB did not fit in a free-tier 512 MB container, so you added torch.set_num_threads(1) and a DISABLE_RERANKER environment flag that degrades gracefully to single-stage retrieval instead of crashing.

What would you do differently if you rebuilt it?

Never say "nothing." Have three ready — full detail is in §15:

  1. Fix the shared conversation state. Chat history is a module-level global, so all users share one history. Correct design: a session ID per client, history in Redis with a TTL.
  2. Chunk on statute structure, not character count. Split on "Section N." boundaries so a chunk is always exactly one legal provision, and attach the section number as metadata.
  3. Add sparse retrieval. rank_bm25 is already in requirements. Exact-match queries like "Section 152 BNSS" are where dense embeddings are weakest and keyword search is strongest.
Is this production-ready?

Say no, then show you know precisely why. That answer scores higher than a defensive yes.

"No — it is a working prototype with a production-shaped architecture. To ship it I would need per-user session isolation, a locked-down CORS policy, authentication and rate limiting on the chat endpoint, structured logging and tracing on the retrieval stage, a real evaluation set of a few hundred legal questions rather than three, and a clear disclaimer that it is not a substitute for a lawyer."
§ 01Foundations

Why RAG exists at all

The idea in one line

A language model is a brilliant writer with a frozen, blurry memory — RAG is the act of handing it the right page of the right book at the exact moment it needs to write.

What a large language model actually is

Strip away the mystique and an LLM is a next-token predictor. It has seen an enormous amount of text and learned the statistical shape of language: given everything so far, what word comes next? All of that learning is compressed into billions of numbers called weights. Those weights are fixed after training.

This produces four hard limitations, and every one of them is a reason RAG exists.

1. Knowledge cutoff

The weights only encode text seen during training. A model trained before the Bharatiya Nyaya Sanhita replaced the Indian Penal Code in July 2024 will keep quoting IPC sections, because that is what its weights know. It has no mechanism to notice it is out of date.

2. No private knowledge

Your company's contracts, your college's regulations, a specific state amendment — none of that was in the training data. The model cannot know what it never read.

3. Hallucination

This is the important one. Because the model is optimised to produce plausible text, not true text, when it does not know something it does not stop — it generates the most statistically likely continuation. Ask it for a legal citation and it will produce something that looks exactly like a citation: "Section 294 of the BNS, punishable with up to two years." Correct format, correct tone, possibly a completely invented number. In law, that is not a small error; it is malpractice.

4. No traceability

Even when a plain LLM is right, it cannot show you where the answer came from. You cannot verify it. For any serious domain — law, medicine, finance, compliance — an unverifiable answer is an unusable answer.

Say this in the interview

"The core insight of RAG is that we separate knowledge from reasoning and language. Knowledge lives outside the model in a searchable store where I can update it, audit it, and cite it. The model is used only for what it is genuinely good at: reading the passages I give it and writing a clear answer. That turns an unverifiable claim into a verifiable one."

The killer line

"Fine-tuning changes how a model speaks. RAG changes what it knows. Legal statutes get amended, so the knowledge must be swappable without retraining — that is why LegalEase is RAG and not a fine-tune. If I wanted the trial-advocate tone to be reliable without a long prompt, that would be the fine-tuning use case."

Where the term comes from

"Retrieval-Augmented Generation" was named in a 2020 paper from Facebook AI Research (Lewis et al.). The original version trained the retriever and generator jointly. What almost everyone builds today — including LegalEase — is the simpler, more practical descendant: a frozen off-the-shelf retriever, a frozen off-the-shelf generator, and clever plumbing in between. Knowing that distinction is a nice signal of depth.

Cross-examination

What is RAG? Explain it to someone non-technical.

Use an analogy, then the technical version. Analogy:

"Imagine a very well-read lawyer with a brilliant way with words but a poor memory for exact numbers. Instead of asking her to recall the statute, you first run to the library, pull the three relevant pages, put them on her desk, and say 'answer using only these'. RAG is the librarian step."

Technical version: "RAG is a two-phase system. Offline, I index a corpus by splitting it into chunks and storing vector representations of each chunk. Online, I embed the user's query, find the nearest chunks in that vector space, and inject them into the LLM's prompt as context with an instruction to answer only from that context."

Why not just fine-tune the model on the legal documents?

Four reasons, delivered crisply:

  • Updatability. Statutes change. RAG needs one re-ingest; fine-tuning needs a retraining run.
  • Citations. Fine-tuning smears knowledge across weights, so you can never point at a source. RAG hands you the source chunk for free — LegalEase attaches [Source: filename] to every passage.
  • Hallucination. Fine-tuning does not remove it; it can make the model more confidently wrong in-domain.
  • Cost and data. Fine-tuning needs GPUs and thousands of curated examples. I had statute PDFs, not a labelled instruction dataset.

Then show balance: "Fine-tuning is the right tool for behaviour and format. If I wanted a smaller local model to reliably emit my exact JSON schema, I'd fine-tune for that and keep RAG for the facts."

Models now have 1M-token context windows. Isn't RAG obsolete?

This is a current, deliberately provocative question. Answer with cost, latency, accuracy, and scale:

  • Cost. You pay per input token on every request. Sending 500k tokens for a one-line question is enormously wasteful compared to sending 8 chunks.
  • Latency. Attention cost grows steeply with sequence length. Long prompts mean slow first tokens.
  • Accuracy. The "lost in the middle" effect: models attend well to the start and end of a long context and reliably miss things buried in the middle. Retrieval puts the relevant passage first.
  • Scale. The full Indian statute corpus plus case law is far beyond any context window. Retrieval is not a workaround for small windows; it is how you search a corpus.

Close with nuance: "Bigger windows do change the design though — they make chunks less precious, so you can afford to pass more and larger chunks. It shifts the trade-off, it doesn't delete the problem."

Give me a concrete example of a hallucination your system prevents.

"Ask a plain LLM 'what's the punishment for public nuisance in India' and it will very likely answer with IPC Section 268 or 290 — because the Indian Penal Code dominates its training data. But the IPC was replaced by the Bharatiya Nyaya Sanhita in July 2024. My knowledge base contains BNS text, so retrieval surfaces the BNS provision and the prompt explicitly says: if a section number or penalty is not in the provided context, do not invent it. The model is anchored to the current law rather than to its stale memory."

Bonus point: "That is also exactly why RAG matters more, not less, as models improve — model memory ages, the knowledge base does not."

What are the failure modes of RAG itself?

Show you know RAG is not magic. Name them by stage:

  • Retrieval miss. The right chunk exists but ranks below the cutoff. Fixes: reranking, hybrid search, query rewriting.
  • Chunking damage. The answer is split across a chunk boundary, so no single chunk contains it. Fixes: overlap, structure-aware splitting.
  • Not in the corpus. The question simply cannot be answered. Fix: detect and refuse — LegalEase returns a "no relevant documents" response instead of calling the model.
  • Ignoring the context. The model overrides good context with its own priors. Fixes: temperature 0, strict prompt, faithfulness evaluation.
  • Distraction. Irrelevant retrieved chunks actively degrade the answer. Fix: reranking to raise precision — you want few, correct chunks, not many, plausible ones.

Why the split matters

The offline pipeline is expensive but rare. Embedding a thousand chunks takes seconds to minutes on CPU, but you only do it when documents change. The online pipeline is cheap but constant — it runs on every keystroke-triggered question, so every millisecond counts.

This is why the design choices differ so sharply between them. Offline you can afford a slow, high-quality model. Online you cannot — which is exactly the reason the reranker only sees 25 candidates instead of the whole database.

The retrieval logic lives in retriever.py, entirely separate from the LLM logic in output.py, which is entirely separate from the HTTP layer in api.py. Cross-examination

Walk me through what happens when a user types a question and hits enter.

This is the single most likely question in the entire interview. Rehearse it as a numbered sequence:

  1. React's handleSubmit appends the user message to local state, clears the input, sets isLoading true.
  2. axios.post sends { query } as JSON to POST /api/chat.
  3. FastAPI validates the body against the ChatRequest Pydantic model. A missing or wrongly-typed query is rejected with a 422 before my code runs.
  4. The endpoint calls generate_answer(query), which calls retrieve(query).
  5. retrieve encodes the query with MiniLM into a normalised 384-dim vector and asks ChromaDB for the 25 nearest chunks.
  6. Those 25 go to FlashRank's cross-encoder, which scores each (query, chunk) pair jointly and returns the top 8.
  7. If zero chunks came back, I short-circuit and return a "no relevant documents" answer without calling the LLM — no context means no grounded answer, so calling the model would only invite hallucination.
  8. Otherwise I stitch the 8 chunks into a context block, each prefixed with its source filename, prepend up to 3 previous exchanges, and drop that into a strict prompt with a JSON schema.
  9. I POST to the Ollama API with temperature 0.0, format: "json", stream: false, 60-second timeout.
  10. I parse the response with json.loads; on failure I regex out the first {...} block; on failure again I regex out just the answer field. Three layers, because LLM JSON is not guaranteed.
  11. I append the exchange to session history, persist it to chat_history.json, and return the parsed dict.
  12. FastAPI serialises it; React stores it as message.raw and renders answer through react-markdown, plus expandable cards for legal_terms and relevant_articles.
Why separate ingestion from serving? Why not index on startup?
  • Startup time. Re-embedding the whole corpus on every boot would make cold starts unbearable and would burn CPU repeatedly for an identical result.
  • Idempotence. Ingestion uses upsert with deterministic IDs ({source}-{chunk_id}), so re-running it updates in place instead of duplicating. That only works if it is a deliberate, separate action.
  • Different scaling. Ingestion is CPU-and-memory heavy and runs rarely; serving is latency-sensitive and runs constantly. In a real deployment they would be separate jobs entirely.

Then be honest about the current compromise: "In my Dockerfile I run python ingest.py at build time, so the vector store is baked into the image. That gives instant, dependency-free startup, but it means adding a document requires rebuilding the image. For a static statute corpus that is a fine trade; for user-uploaded documents it would be wrong, and I'd move ChromaDB to a mounted volume or a hosted vector service."

Where is the bottleneck?

"Overwhelmingly the LLM generation call — it is a remote request to a 120-billion-parameter model producing up to 2048 tokens, so it dominates everything else. Roughly: query embedding is single-digit milliseconds, ChromaDB search over a small corpus is a few milliseconds, the cross-encoder on 25 passages is on the order of tens to low hundreds of milliseconds on CPU, and generation is seconds."

Then the improvements: "The highest-impact fix is streaming — Ollama supports stream: true, and I set it to false for simplicity. Streaming wouldn't reduce total time but would cut perceived latency enormously because tokens appear immediately. After that: cache embeddings for repeated queries, and cache whole answers for common questions."

How would you scale this to 10,000 concurrent users?

Go layer by layer — this shows systems thinking, not just ML knowledge.

  • Statelessness first. The current global SESSION_HISTORY makes horizontal scaling impossible. Move history to Redis keyed by session ID; then any replica can serve any request.
  • API layer. Multiple Uvicorn workers behind a load balancer; scale replicas horizontally.
  • Vector store. ChromaDB's persistent local client is single-node. Move to a server-mode vector DB (Chroma server, Qdrant, or pgvector) so replicas share one index.
  • Models. Serve the embedding model and reranker as separate inference services so they load once, not once per API replica. Batch requests.
  • LLM. This is the real cost and rate-limit ceiling. Queue requests, cache aggressively, and consider a smaller model for simple queries with escalation for complex ones.
  • Protection. Rate limiting per user, timeouts, and circuit breakers so a slow LLM does not exhaust the thread pool.
§ 03Indexing pipeline

Loading and parsing the documents

The idea in one line

Garbage in, garbage out — retrieval quality is capped by how cleanly you got text out of the PDF in the first place, and PDFs are a printing format, not a text format.

Why PDF extraction is genuinely hard

A PDF does not store "paragraphs" or "sections". It stores instructions like "draw glyph 'S' at coordinates (72, 640) in font F1 at size 11". There is no notion of reading order, no notion of a heading, often no notion of a word boundary. A text extractor has to reconstruct all of that from positions.

Consequences you should be able to name:

  • Multi-column layouts get read straight across, interleaving two columns into nonsense.
  • Tables collapse into a run of numbers with no structure.
  • Headers, footers and page numbers get pulled into the body text on every page.
  • Ligatures and special characters (fi, ffi, §) can come out mangled or missing.
  • Scanned PDFs are just images — extraction returns an empty string, and you need OCR (Tesseract, or a vision model).
  • Hyphenated line breaks split words across lines: "punish-\nment".

In LegalEase

backend/ingest.pydocument loading
def load_documents(p):
    documents = []
    for fp in Path(p).glob("**/*"):
        if fp.suffix.lower() in [".txt", ".md", ".pdf"]:
            try:
                content = ""
                if fp.suffix.lower() in [".txt", ".md"]:
                    content = fp.read_text(encoding="utf-8", errors="ignore")
                elif fp.suffix.lower() == ".pdf":
                    import PyPDF2
                    with open(fp, "rb") as f:
                        reader = PyPDF2.PdfReader(f)
                        pages = [pg.extract_text() or "" for pg in reader.pages]
                        content = "\n".join(pages)

                if content.strip():
                    documents.append({
                        "content": content,
                        "metadata": {"source": fp.name, "path": str(fp)}
                    })
            except Exception as e:
                print(f"failed to read {fp}: {e}")
    return documents

Decisions in this small function you can actually defend:

  • Path(p).glob("**/*") — recursive, so nested folders inside kb/text work without extra code.
  • errors="ignore" on text files — a single bad byte in a statute dump should not kill the entire ingest run.
  • pg.extract_text() or "" — extract_text() returns None on a page with no extractable text (a scan or a blank page). Without the or "", "\n".join(...) raises a TypeError and the whole document is lost.
  • if content.strip() — skips files that produced no usable text, so you never embed empty strings.
  • Per-file try/except — one corrupt PDF degrades the corpus by one file instead of aborting the run.
  • Metadata captured at load time — source and path travel with every chunk, which is what makes citation possible later.
Known limitation — raise it yourself

Page boundaries are joined with a plain newline, so the page number and any running header land in the middle of the text stream. Worse, the page number is lost — the metadata records only the filename. A legal citation ideally says "BNS, Section 152, page 41". The fix is to build the document as a list of (page_number, text) pairs and carry page into chunk metadata. Volunteering this before they find it makes you look like an engineer, not a student.

Watch out

The kb/text folder in the repository contains a CV PDF alongside the statute files. Everything in that folder gets embedded, so a query can retrieve CV content as "legal context". Clean the corpus before any demo — and if an interviewer spots it, the right answer is "that is exactly why production ingestion needs an allow-list and a validation step, not a glob."

Cross-examination

Why is extracting text from a PDF harder than from a text file?

"A PDF is a page-description format — it stores glyphs and coordinates, not sentences. Reading order, paragraph boundaries and even word spacing have to be inferred from positions. So a two-column statute page can come out interleaved, a table becomes a flat number soup, and a scanned page returns nothing at all because it is just an image. I used PyPDF2 because my sources are single-column, digitally generated statute PDFs, which is its best case. For scanned judgments I'd need OCR, and for anything with tables I'd move to pdfplumber."

What happens if one PDF in the folder is corrupt?

"Nothing catastrophic — each file is wrapped in its own try/except, so a failure prints a message and the loop continues. That was deliberate: ingestion is a batch job over untrusted inputs, and one bad file should not cost you the other ninety-nine. The improvement I'd make is to collect failures into a list and report a summary at the end, plus a non-zero exit code if the failure rate crosses a threshold, so a CI job would actually catch it."

How do you handle scanned documents?

"Currently I don't — extract_text() returns empty, content.strip() is falsy, and the file is silently skipped. To support them I'd detect the empty-extraction case and route to OCR: render each page to an image with PyMuPDF and run Tesseract, or use a vision-language model for better accuracy on legal typography. I'd also store an extraction_method flag in metadata, because OCR text is noisier and I'd want to weight or flag it differently at retrieval."

What metadata do you store with each chunk and why?

"source (the filename), path, and chunk_id (the chunk's index within its document). source is what makes citation possible — at generation time I prefix every retrieved chunk with [Source: filename] so the model can attribute claims. chunk_id plus source forms the deterministic Chroma ID {source}-{chunk_id}, which is what makes re-ingestion idempotent rather than duplicating."

Then extend: "What I'd add is page, section_number, and an ingested_at timestamp. section_number especially — it would let me do metadata-filtered retrieval, so a query mentioning 'Section 152' could filter to that section instead of relying purely on semantic similarity."

§ 04Indexing pipeline

Chunking, and the 1200/200 decision

The idea in one line

A chunk is the smallest unit your system can ever retrieve, so chunking decides the ceiling on your accuracy before any model is involved.

Why chunk at all? Three independent reasons

  1. The embedding model has a hard input limit. all-MiniLM-L6-v2 truncates at 256 word-piece tokens. Feed it a 50-page statute and it silently embeds only the first paragraph and throws the rest away.
  2. Precision. One vector must represent one idea. Average a whole document into 384 numbers and you get a vector that means "law, generally" — close to every query and useful for none. This is dilution, and it is the main reason huge chunks fail.
  3. Context budget. Whatever you retrieve gets pasted into the LLM prompt. Smaller units mean you can fit several relevant passages instead of one bloated one.

The fundamental trade-off

Chunking strategies, from crudest to smartest

Fixed-size

Cut every N characters. Trivially simple and brutally destructive — it will happily cut "punishable with imprisonment of either description for a term which may extend to" in half.

Recursive character splitting (what LegalEase uses)

Try to split on the most meaningful separator first; only fall back to a cruder one when a piece is still too big. Given ["\n\n", "\n", " ", ""] the algorithm is:

  1. Split the text on "\n\n" (paragraph breaks).
  2. Any resulting piece that still exceeds chunk_size gets split again on "\n" (line breaks).
  3. Still too big? Split on " " (word boundaries).
  4. Still too big — a single enormous word or an unbroken run of text? Split on "", i.e. raw characters. This is the guarantee that the algorithm always terminates.
  5. Finally, merge adjacent small pieces back together up to chunk_size, carrying chunk_overlap characters from the end of each chunk into the start of the next.

The elegance is that it prefers natural boundaries but never fails on pathological input.

Document-structure splitting

Split on the document's own headings — Markdown ##, HTML tags, or in this domain, a regex on "Section 152." Best possible option for statutes, and the top item on your improvement list.

Semantic splitting

Embed each sentence, and start a new chunk where the similarity between consecutive sentences drops below a threshold — i.e. where the topic changes. Elegant, but slow (you embed everything twice) and threshold-sensitive.

Precision point that impresses

The README calls the strategy "semantic chunking". It is not — RecursiveCharacterTextSplitter is structure-aware character splitting. Semantic chunking specifically means using embedding similarity to find topic boundaries. If an interviewer picks up on the README wording, correcting it yourself is a strong move: "That's loose wording in my README — it's recursive character splitting that respects paragraph structure. True semantic chunking would embed sentence-by-sentence and cut at similarity troughs, which I considered but rejected on ingestion cost."

Defending 1200

"Legal text is unusually unforgiving about splitting. A single provision typically runs 800 to 1500 characters — the offence, the qualifiers, the exceptions and the punishment all belong together, and the punishment clause at the end is usually what the user actually needs. A 400-character chunk would routinely separate 'whoever does X' from 'shall be punished with Y', which makes the retrieved chunk technically relevant and practically useless. 1200 characters keeps a typical section whole."

Defending 200 overlap

"Overlap is insurance against boundary damage. Roughly 17% of each chunk is repeated from the previous one, so a sentence that straddles a cut still appears complete in at least one chunk. The cost is about 17% more vectors and storage, and some near-duplicate results at retrieval — which the reranker then filters. I judged that cheap relative to losing an answer entirely."

The flaw you must know about — this is the sharpest question available

all-MiniLM-L6-v2 has a maximum sequence length of 256 word-piece tokens. English averages roughly 4 characters per token, so 256 tokens is about 1000–1100 characters. A 1200-character chunk therefore sits right at, or just past, the truncation boundary — and legal English is denser than average, with long words and many rare tokens, which pushes it further over. The tail end of the longest chunks is silently dropped from the embedding.

Note precisely what this does and does not break: the full 1200 characters are still stored in Chroma and still reach the LLM, and FlashRank's L-12 model reads the whole passage. Only the vector is computed from a truncated view. So the failure mode is narrow but real: a chunk whose distinguishing content lives in its last 15% may not be found by vector search at all.

Answer if asked: "You're right, and it's the flaw I'd fix first. Three options: reduce chunk_size to about 900 so it fits inside 256 tokens; switch to a longer-context embedding model like BGE or E5 with a 512-token limit; or split on statute structure so chunk length follows the provision rather than a fixed number. I'd do the third, with the second as a fallback — measuring both against a Ragas context-recall baseline rather than guessing."

Subtle Python detail worth mentioning

doc["metadata"].copy() inside the loop is not cosmetic. Without it, every chunk from a document would hold a reference to the same dictionary, so the last chunk_id written would overwrite all of them and every chunk would report the same ID. It is a classic mutable-default-style aliasing bug, and pointing at it shows you read your own code carefully.

§ 05Indexing pipeline

Embeddings, built up from scratch

The idea in one line

An embedding is a list of numbers positioned so that closeness in the list means closeness in meaning — which converts "find text that means the same thing" into "find nearby points", a problem computers are extremely good at.

Step 1 — Why we needed vectors in the first place

Traditional search matches characters. Search "car" and you will not find "automobile"; search "penalty for dumping garbage" and you will not find a statute that says "whoever causes any obstruction or nuisance by depositing refuse". The words do not overlap. Meaning does.

Step 2 — One-hot vectors and why they fail

The naive encoding: give every word in the vocabulary a slot, set that slot to 1, everything else to 0. With 50,000 words you get 50,000-dimensional vectors that are almost entirely zeros. Worse, every pair of distinct words is exactly equally far apart. "king" and "queen" are as unrelated as "king" and "toaster". The representation carries no meaning at all.

Step 3 — Word2Vec and the distributional insight

The breakthrough (2013) came from an old linguistic idea: you shall know a word by the company it keeps. Train a small network to predict a word from its neighbours, and the hidden layer that emerges is a dense vector — a few hundred numbers — where words used in similar contexts land near each other. Suddenly the geometry means something. The famous demonstration: king − man + woman ≈ queen. Relationships became arithmetic.

The remaining problem: one vector per word

Word2Vec gives "bank" a single vector, averaging the riverbank and the financial institution into one confused point. Context is invisible.

Step 4 — Transformers and contextual embeddings

BERT (2018) fixed this with self-attention. Intuitively: for each word, the model computes how much every other word in the sentence should influence its representation, then builds a weighted blend. So in "I sat on the river bank", the word river pulls bank's representation toward geography; in "I deposited cash at the bank", cash pulls it toward finance. Same word, different vectors, because context now participates.

You do not need the matrix algebra in an interview, but you do need this sentence: "Attention lets every token look at every other token and decide how much each one matters for its own representation."

Step 5 — From word vectors to sentence vectors

BERT gives you one vector per token. For search you need one vector per chunk. Two things are needed:

Pooling

Collapse N token vectors into one. Options: take the special [CLS] token's vector, take the maximum per dimension, or take the mean of all token vectors. Mean pooling wins in practice for retrieval and is what sentence-transformers uses by default.

The right training objective

Vanilla BERT was never trained so that "similar sentences have similar mean-pooled vectors" — and empirically its raw vectors are poor at that. Sentence-BERT fixed it by training with a contrastive objective: show the model pairs of sentences that mean the same thing and pairs that do not, and adjust the weights to pull matching pairs together in vector space and push non-matching pairs apart. all-MiniLM-L6-v2 was trained this way on over a billion sentence pairs.

The one-line version of §05

"Embeddings turn semantic similarity into geometric proximity. Contrastive training is what forces that property — you explicitly optimise for 'sentences that mean the same thing land close together'."

The model LegalEase uses: all-MiniLM-L6-v2

Layers 6 transformer blocks Output 384 dimensions Params ~22M Max input 256 word-piece tokens Pooling mean Size on disk ~90 MB

MiniLM means it is a distilled model: a large teacher model was trained first, then a small student was trained to imitate the teacher's internal behaviour. You get most of the quality at a fraction of the size and latency. L6 is the six layers. 384 is the embedding width.

Why it is the right choice here: it runs comfortably on CPU, loads fast in a small container, and is strong on general semantic similarity. Why it is not perfect: 256-token limit (see §04), and it is a general-purpose model with no legal-domain training — it does not know that "cognizable" and "non-bailable" are terms of art.

Measuring similarity

Cosine similarity measures the angle between two vectors, ignoring their length: it asks "do these point the same way?" — which is what we want, since a long document and a short query can express the same idea. It ranges from −1 (opposite) through 0 (unrelated) to 1 (identical direction).

Euclidean (L2) distance measures straight-line distance, so it is sensitive to magnitude.

The connection you should know cold: for unit-length vectors, ranking by cosine similarity and ranking by Euclidean distance give the identical ordering, because ‖a−b‖² = 2 − 2·cos(a,b). Once both vectors are normalised, minimising distance is maximising cosine.

What is an embedding? Explain like I know nothing.

"It's a way of turning text into coordinates. "384 is the architecture of MiniLM-L6, not a knob I turned. "Cosine, conceptually — it compares direction, so a two-word query and a 1200-character chunk can be compared fairly without magnitude skewing the result. "Raw BERT wasn't trained to produce comparable sentence-level vectors. "Very likely yes, and it's on my roadmap. § 06Indexing pipeline

Vector databases, ChromaDB and HNSW

The idea in one line

A vector database trades a guarantee of exactness for orders of magnitude of speed — it finds almost certainly the nearest neighbours in logarithmic-ish time instead of definitely the nearest in linear time.

The problem it solves

Given a query vector, find the k closest of N stored vectors. The exact method — compute the distance to all N and sort — is called flat or brute-force search. It is perfectly accurate and perfectly fine up to maybe a hundred thousand vectors. At ten million it is hopeless, because every single query touches every single vector.

So we use Approximate Nearest Neighbour (ANN) search: accept ~95–99% recall in exchange for searching a tiny fraction of the data.

HNSW — the algorithm under almost every modern vector DB

Hierarchical Navigable Small World graphs. The intuition is a transport network:

  • Build a graph where each vector is a node connected to its nearby vectors.
  • Stack that graph into layers. The top layer is sparse — few nodes, very long-range links, like intercontinental flights. Each layer down is denser with shorter links, like national trains, then local buses, then walking.
  • To search: enter at the top layer, greedily walk to the neighbour closest to the query, and when you cannot improve, drop a layer and repeat. Long hops get you to the right region fast; short hops refine.
  • Finish at the bottom layer, which contains every vector, and return the k best found.

Two knobs to name if asked: M (links per node — higher means better recall, more memory) and ef_search (how wide the candidate list is kept during search — higher means better recall, slower query). Both trade recall against cost, and neither changes correctness, only probability.

The path is already in metadata — using it in the ID, or hashing the chunk content, would fix it. Volunteering this is a strong signal; so is knowing that a content hash ID also gives you free deduplication.

  • Ingestion. A distributed batch job — Spark or Ray — rather than a single-process script, with checkpointing so a failure doesn't restart from zero.

§ 07Query pipeline

Retrieval: dense, sparse and hybrid

The idea in one line

Dense search finds things that mean the same; sparse search finds things that say the same — and legal queries need both, because "Section 152" is a keyword and "my neighbour is dumping waste" is a meaning.

Sparse retrieval — the classical approach

Represent a document as a vector over the whole vocabulary, where most entries are zero (hence "sparse"). Score by word overlap, weighted so that rare, informative words count more than common ones.

TF-IDF

Two intuitions multiplied together:

  • Term Frequency — a word appearing often in this document suggests the document is about it.
  • Inverse Document Frequency — a word appearing in every document ("the", "shall", "section") carries almost no information, so weight it down. A word appearing in three documents out of a thousand is highly discriminative.

BM25 — the refinement everyone actually uses

BM25 keeps the TF-IDF idea but fixes two flaws:

  • Term-frequency saturation. A word appearing 100 times is not 10× more relevant than one appearing 10 times. BM25 applies diminishing returns via a parameter k1.
  • Length normalisation. Long documents naturally contain more of every word. BM25 discounts for length via parameter b.

BM25 has been the strong baseline in information retrieval for three decades, and it still beats naive dense retrieval on exact-match and rare-term queries.

Dense retrieval — what LegalEase does

Everything from §05 and §06: embed the query, find nearest vectors. Strong on paraphrase, synonymy and colloquial phrasing. Weak on exact identifiers, rare proper nouns and out-of-domain jargon, because those get compressed away in a 384-dimensional average.

Run both retrievers, then merge their ranked lists. The problem is that their scores are on incomparable scales — a cosine of 0.83 and a BM25 score of 14.2 cannot be added. Reciprocal Rank Fusion sidesteps this entirely by throwing away the scores and using only the ranks:

# k is a smoothing constant, commonly 60
score(doc) = sum over each retriever of  1 / (k + rank_of_doc_in_that_retriever)

# a doc ranked 1st by dense and 3rd by sparse:
#   1/(60+1) + 1/(60+3) = 0.0164 + 0.0159 = 0.0323
# a doc ranked 1st by dense only:
#   1/(60+1)            = 0.0164

Documents that both retrievers like float to the top; documents only one likes still get partial credit. Elegant, parameter-light, and it is what most production hybrid systems use.

Cross-examination

What's the difference between sparse and dense retrieval?

"Sparse retrieval represents text as a very high-dimensional, mostly-zero vector over the vocabulary and scores by weighted term overlap — TF-IDF and BM25. It matches words. Dense retrieval represents text as a small, fully populated vector learned by a neural model and scores by geometric closeness. It matches meaning."

Then the practical framing, which is what they want: "They fail in opposite directions. Dense handles paraphrase — a user writing 'my neighbour dumps garbage' finds a provision about 'depositing refuse' with zero word overlap. Sparse handles exact identifiers — 'Section 152 BNSS' is a rare token that BM25 nails and a 384-dimensional average tends to smear away. My system is dense-only, which means it's strong on colloquial user questions and weak on citation lookups. That's the specific gap hybrid search would close."

Explain BM25.

"It's TF-IDF with two corrections. The base idea is that a term matters more if it appears often in this document (term frequency) and less if it appears in many documents (inverse document frequency) — so 'shall' contributes nothing and 'nuisance' contributes a lot."

"BM25 adds saturation: the tenth occurrence of a word adds much less than the second, controlled by k1. And it adds length normalisation: long documents contain more of everything, so their scores are discounted, controlled by b. Typical defaults are k1 around 1.2–2.0 and b around 0.75. It's been the standard IR baseline since the 1990s and still beats out-of-the-box dense retrieval on keyword-heavy queries."

How would you combine dense and sparse results? Their scores aren't comparable.

"Right — cosine similarity lives in [0,1] and BM25 is unbounded, so you cannot add them directly. Three options:"

  1. Normalise then weight — min-max scale each list and take α·dense + (1−α)·sparse. Simple, but α needs tuning and normalisation is unstable when one list is uniformly scored.
  2. Reciprocal Rank Fusion — discard scores, use ranks: Σ 1/(k + rank) with k typically 60. Robust, no tuning, no scale problem. This is what I'd use.
  3. Let the reranker decide — union both candidate lists and let the cross-encoder score everything on one scale. Since I already have a reranker, this is almost free, and arguably the cleanest: fusion becomes "put both lists in the bucket" and precision is handled by a model that actually reads the text.
Why did you choose k=25 candidates?

"It's the recall-versus-cost dial for the first stage. The only job of stage one is to make sure the right chunk is somewhere in the candidate set — precision doesn't matter yet, because stage two fixes ordering. Too small and a correct chunk ranked 30th is lost forever, since the reranker can only reorder what it's given. Too large and cross-encoder latency grows roughly linearly, since it's one forward pass per candidate."

"25 into 8 is about a 3:1 funnel, which is a common ratio in practice. What I'd do properly is measure recall@k on a labelled question set — find the k where recall plateaus and stop there, rather than picking a round number. That's the experiment I'd run with more time."

Your docstring says "hybrid-ready" but I don't see BM25 anywhere.

Do not dodge. "Correct — that's aspirational naming and the sparse path isn't implemented. rank_bm25 is in requirements because it was the next thing on my list. What's actually there is dense retrieval plus cross-encoder reranking."

Then convert it into a design answer: "The reason it's the next thing is a specific failure I saw — queries that name a section number directly retrieve poorly, because the number is a rare token that contributes little to a 384-dimensional average. BM25 is exactly the right tool for that. The implementation would be: build a BM25Okapi index over the same chunk list at startup, run both retrievers to 25 each, fuse with RRF, and hand the fused list to FlashRank unchanged. The second stage doesn't need to know where candidates came from, which is why the architecture already supports it."

What is query expansion / rewriting, and would it help here?

"Query rewriting means transforming the user's question before retrieval. Several variants: multi-query — ask an LLM to generate three paraphrases and retrieve for each, then fuse; HyDE — ask an LLM to hallucinate a hypothetical answer and embed that instead of the question, since an answer is lexically closer to the source document than a question is; contextual rewriting — resolve pronouns using chat history, turning 'what's the punishment for that?' into a standalone query."

"The third would help my system most and is nearly free. Right now the retriever only sees the latest message — history is added to the prompt but not to the query — so a follow-up like 'and what compensation can I claim?' retrieves on those words alone, with no idea we were discussing waste dumping. That's a concrete, identifiable bug in my current design and rewriting is the fix."

§ 08Query pipeline

Reranking and cross-encoders

The idea in one line

A bi-encoder judges the query and the document separately and compares summaries; a cross-encoder reads them together and judges the pair — far more accurate, far too slow to run on a whole database, which is precisely why it goes second.

Bi-encoder versus cross-encoder — the central distinction

BI-ENCODER  (the embedding model, §05)
   query ──▶ [encoder] ──▶ vector_q  ┐
                                     ├─▶ cosine similarity ──▶ score
   doc   ──▶ [encoder] ──▶ vector_d  ┘
   ▸ doc vectors precomputed once, offline
   ▸ query cost = 1 forward pass, then pure arithmetic
   ▸ query and doc NEVER see each other

CROSS-ENCODER  (the reranker)
   [query  [SEP]  doc] ──▶ [encoder] ──▶ single relevance score
   ▸ nothing can be precomputed — the input contains both
   ▸ cost = 1 forward pass PER (query, doc) PAIR
   ▸ attention runs across query and doc tokens jointly

The reason for the accuracy gap is mechanical, not mystical. In a bi-encoder, the document is compressed into 384 numbers before the query is known — so the compression cannot know what to preserve. In a cross-encoder, every token of the query can attend to every token of the document. It can notice that the query says "minor" and the document says "person under eighteen years", that the query asks about punishment while the passage only defines the offence, or that a numeric section reference matches exactly.

The line that lands

"A bi-encoder asks 'are these two summaries similar?'. A cross-encoder asks 'does this passage actually answer this question?'. Those are different questions, and the second is the one I care about — but I can only afford to ask it 25 times, not a million times."

Why two stages instead of one

Suppose you have 100,000 chunks and a cross-encoder pass costs 10 ms.

DesignCost per queryQuality
Cross-encoder over everything100,000 × 10 ms ≈ 17 minutesBest possible
Bi-encoder only~5 msGood recall, mediocre precision
Bi-encoder → cross-encoder on top 25~5 ms + 25 × 10 ms ≈ 255 msNear-best precision

That table is the argument. Stage one buys recall cheaply; stage two buys precision on a tiny candidate set. This pattern — cheap-and-broad then expensive-and-narrow — is called cascade ranking, and it is how every large search engine works.

FlashRank and ms-marco-MiniLM-L-12-v2

FlashRank is a lightweight reranking library: small ONNX-exported cross-encoders that run fast on CPU with no PyTorch inference dependency and no GPU. That matters enormously for a free-tier deployment.

ms-marco-MiniLM-L-12-v2 is a 12-layer distilled cross-encoder trained on MS MARCO — a Microsoft dataset of about a million real Bing queries paired with human-judged relevant passages. Because it is trained on real user questions against real web passages, it generalises well to "does this passage answer this question?" across domains.

Note the asymmetry worth mentioning: the retriever is L6, the reranker is L12. The second stage deliberately uses a bigger, slower model — that is the entire point of putting it second.

Three engineering decisions to point at

Graceful degradation. The DISABLE_RERANKER flag plus the ImportError fallback means the service still answers questions — slightly worse — instead of crashing when the reranker cannot be loaded. Say: "I'd rather ship a degraded feature than a 500."

Configuration by environment, not by code. The same image runs with the reranker locally and without it on a memory-limited host, no rebuild needed. That is the twelve-factor principle.

The candidate pool follows the flag. search_k = rerank_k if DISABLE_RERANKER else k — retrieving 25 with nothing to filter them would only add noise.

Detail worth knowing

The scores returned by the reranker are relevance scores from a different model on a different scale than the cosine similarities from the vector search — they are not comparable and are not meant to be. They are also currently only returned, never used: nothing thresholds on them. A simple, high-value improvement is to drop chunks below a minimum score, so that a weak-but-top-8 chunk does not get promoted into the context just because eight slots exist.

Cross-examination

What is a reranker and why do you need one if you already have vector search?

"Vector search optimises recall cheaply, but it's structurally imprecise: the document vector is computed before the query exists, so the compression can't know what's relevant. That produces chunks that are topically near but don't answer the question — for a query about waste dumping, anything mentioning property or nuisance."

"A reranker is a cross-encoder: it takes the query and one passage together as a single input and outputs a relevance score, so attention runs across both. It can tell that the query asks for punishment while the passage only defines the offence. I retrieve 25 candidates by vector search, rerank all 25, and keep the best 8. The result is that the LLM's context contains fewer, better chunks — and fewer-and-better beats more-and-plausible, because irrelevant context actively degrades generation."

Why not just use the cross-encoder for everything?

"Because it can't be indexed. A bi-encoder's document vectors are computed offline once and reused for every query forever. A cross-encoder's input contains the query, so nothing can be precomputed — scoring N documents means N forward passes at query time. Over a 100,000-chunk corpus at roughly 10 ms per pass, that's about 17 minutes per query."

"So the two models aren't competing; they're a cascade. The cheap model reduces a million candidates to 25 with high recall, and the expensive model turns those 25 into a precisely ordered 8. Every large-scale search system is built this way."

What is MS MARCO and why does it matter that the reranker was trained on it?

"MS MARCO is a Microsoft dataset of roughly a million anonymised real Bing queries, each paired with passages that human annotators judged relevant. It's the standard training and benchmark set for passage ranking."

"It matters because the model learned the general skill 'does this passage answer this question?' from genuine user phrasing rather than clean, well-formed queries. That transfers well to my users, who type things like 'my neighbour is throwing waste in my area, what should I do?'. What it did not learn is legal domain specifics — it has no notion that bailable and non-bailable are opposites of great practical importance. If I had a few thousand labelled (legal question, correct section) pairs, fine-tuning this cross-encoder on them would be the single highest-return improvement to retrieval quality, because rerankers fine-tune well on small datasets."

Why keep 8 chunks and not 3 or 20?

"It's a context-budget decision. Eight chunks at up to 1200 characters is roughly 9,600 characters, call it 2,500 tokens, plus the prompt and history — comfortably inside the model's window with room for a 2048-token answer."

"Too few and I risk missing a cross-reference — legal answers often need the offence in one section and the procedure in another, so 3 is genuinely risky here. Too many and two things go wrong: cost and latency grow, and precision drops because irrelevant chunks distract the model. There's published evidence that adding irrelevant context measurably degrades answer quality, so more retrieved context is not monotonically better."

Then the improvement: "What I'd add is a score threshold rather than a fixed count — take up to 8, but only those above a relevance floor. Right now a weak chunk gets promoted simply because there's a slot open."

What happens if the reranker fails to load in production?

"The system degrades instead of failing. There's an ImportError fallback that sets DISABLE_RERANKER = True and ranker = None, and the retrieval path checks that flag and returns the raw vector-search results directly. There's also an explicit environment variable so I can turn it off deliberately — which is what I did on a 512 MB free-tier host where the reranker plus the embedding model plus ChromaDB wouldn't fit."

"There's a subtlety I'm proud of: when the reranker is off, I also reduce the candidate count from 25 to 8, because retrieving 17 extra candidates with nothing to filter them would just pollute the LLM context. The pool size is a function of whether a second stage exists."

Honest caveat if they push: "What I don't currently do is log the degradation or expose it in a health endpoint, so silently running without the reranker is possible. That's a real observability gap."

Are there alternatives to a cross-encoder reranker?
  • LLM-as-reranker — prompt a language model to score or order passages. Highest quality, highest cost and latency; sometimes used for the final top 5.
  • ColBERT / late interaction — keep one vector per token instead of one per document and compute fine-grained token-level matching at query time. A genuine middle ground: much better than a bi-encoder, much cheaper than a cross-encoder, but the index is far larger.
  • Hosted rerank APIs — Cohere Rerank and similar. Strong quality, no infrastructure, but a network hop and a per-call cost.
  • Metadata and rule-based boosting — in legal search, boost chunks whose extracted section number appears literally in the query. Cheap, deterministic, and surprisingly effective in this domain.

"I chose FlashRank because it runs on CPU with no GPU and no PyTorch inference path, which was the binding constraint for free-tier deployment."

Prompting, grounding and generation

The idea in one line

Retrieval decides what the model can know; the prompt decides what it is allowed to do with it — and in a legal system the second constraint matters as much as the first.

The guardrail is the most important five lines in the file

If retrieval returns nothing, the code does not call the LLM at all. It returns a fixed refusal with confidence: "low". This is the difference between a demo and a system: an empty context handed to a language model does not produce "I don't know" — it produces a beautifully written, entirely invented legal opinion. Refusing to generate is the correct engineering answer, and it costs nothing. Lead with this when asked "how do you prevent hallucination?".

Source attribution

Every chunk is prefixed with [Source: filename] before entering the prompt. This is what lets the model populate the source field in its structured output — the citation chain runs unbroken from ingestion metadata, through retrieval, into the prompt, into the JSON, into the UI.

A real bug in the ordering — spot it before they do

Look carefully at the last three lines. The variable is named prev_context, and it is placed before the string "Previous conversation history:". So the layout is: [the actual history] → the label "Previous conversation history:" → [the retrieved statute chunks]. The label sits above the wrong block, meaning the retrieved legal text is announced as if it were chat history.

The model usually recovers, because the chunks are visibly statute text. But it is a genuine defect, and catching your own bug in front of an interviewer is worth more than the bug costs. The fix is one line: context = "Previous conversation history:\n" + prev_context + "\n\nRetrieved legal context:\n" + context.

The prompt, dissected

The prompt does six distinct jobs. Being able to name them is what separates "I wrote a prompt" from "I engineered a prompt".

  1. Role assignment — "an elite, highly experienced Trial Advocate and Legal Counsel". Conditions vocabulary and register.
  2. Conditional clarification — if the user's facts are vague, output only 1–3 clarifying questions and stop. This is a genuine agentic behaviour encoded in a prompt: the model decides whether it has enough information to act.
  3. Escape hatch — if the user refuses to answer or asks directly for the strategy, stop asking and answer with what you have. Without this the model would interrogate forever; it is a state machine expressed in natural language.
  4. Citation requirement — weave exact section numbers into headers and steps.
  5. Format specification — Markdown, structured, never a wall of text.
  6. The anti-hallucination clause — "If an article number, section number, or penalty is not present in the provided context, do NOT invent or hallucinate it." Placed at the very end, after the context and the question, which is deliberate: instructions near the end of a prompt are attended to more reliably.

Where you'd improve it

The layered regex parsing is reactive. Conversation memory

The idea in one line

HTTP is stateless and LLMs have no memory between calls, so "remembering the conversation" is entirely an application-layer illusion you build by replaying past turns into every prompt.

Why memory is needed here specifically

The prompt asks clarifying questions. That behaviour is useless without memory — the model asks "where did this happen?", the user answers "in my apartment building", and if the next request carries no history, the model has no idea what incident is being discussed. Memory is not a nice-to-have in this design; it is load-bearing.

In LegalEase

backend/output.pyhistory
HISTORY_PATH = "chat_history.json"
HISTORY_MAX_EXCHANGES = 3

SESSION_HISTORY: List[Dict[str, str]] = load_history()   # module-level global

def get_recent_context(history, n=HISTORY_MAX_EXCHANGES) -> str:
    recent = history[-n:]                    # sliding window: last 3 only
    parts = [f"User: {ex.get('user','')}\nAssistant: {ex.get('assistant','')}"
             for ex in recent]
    return "\n\n".join(parts)

# after each generation
SESSION_HISTORY.append({"user": query, "assistant": answer_text})
if len(SESSION_HISTORY) > 50:
    SESSION_HISTORY[:] = SESSION_HISTORY[-50:]   # in-place slice assignment
save_history(SESSION_HISTORY)

Two windows, not one

  • Prompt window: 3 exchanges. What actually gets sent to the model. Bounded because every exchange consumes context tokens that would otherwise hold retrieved statute text — and statute text is what grounds the answer.
  • Storage window: 50 exchanges. What is kept on disk. Bounded so the file cannot grow without limit.

The SESSION_HISTORY[:] = ... syntax is worth a sentence: slice assignment mutates the list in place rather than rebinding the name, so any other module holding a reference to the same list sees the trim. Rebinding with SESSION_HISTORY = ... inside a function without global would create a local variable and silently do nothing.

Entity / scratchpad memoryExtract structured facts ("location: apartment", "injury: none")Best fit for this domain — but needs an extraction step
The defect you must be ready for — this is the most likely "gotcha" in the whole codebase

SESSION_HISTORY is a module-level global. FastAPI serves all requests from one process, so every user shares one conversation history. User A's questions about a property dispute become context in User B's assault query. It is simultaneously a correctness bug, a privacy leak, and a hard blocker on horizontal scaling — with two replicas, the same user would get different histories depending on which one they hit.

There is a second issue: save_history writes the whole file on every request with no locking, so concurrent requests can interleave writes and corrupt the JSON.

The fix, in order of increasing correctness: (1) accept a session_id in the request and key an in-memory dict by it — correct for one process; (2) move that dict to Redis with a TTL, so it works across replicas and expires automatically; (3) for real accounts, persist to Postgres with a user ID and proper access control. Say the word stateless: "the API should be stateless so any replica can serve any request; state belongs in a store, not in a module global."

Also worth noticing

init_session() calls input() — it prompts on the terminal. That is fine for the CLI mode at the bottom of output.py, but it would block a web server forever if it were ever called from the API path. It is not, but it shows the file grew from a CLI script into a web backend without a full clean-up. Noticing this in your own code reads as maturity.

Also: the history stores the raw JSON string the model returned, not the parsed answer field. So replayed history contains schema noise and burns tokens on braces and field names. Storing the parsed answer text would be strictly better.

Cross-examination

How does your chatbot remember previous messages?

"It doesn't, in any real sense — the model is stateless and HTTP is stateless, so memory is something I construct. After each turn I append {user, assistant} to a history list and persist it to JSON. On the next request I take the last three exchanges, format them as alternating User/Assistant lines, and prepend them to the context I send."

"Three is a deliberate bound: every exchange I include costs context tokens that would otherwise carry retrieved statute text, and the statute text is what grounds the answer. Memory competes with grounding for the same budget."

What happens if two users use the app at the same time?

Do not defend it. "They'd share a conversation history — SESSION_HISTORY is a module-level global in a single-process server, so there's exactly one history for the whole application. That's a correctness bug and a privacy problem: one user's case details would appear as context in another user's query."

"The fix is to make the API stateless. Accept a session ID from the client, key the history by it, and store it in Redis with a TTL so it works across multiple replicas and cleans itself up. There's also a concurrency issue with the file write — save_history rewrites the whole JSON with no locking, so simultaneous requests can corrupt it. Moving to Redis solves both at once."

Why it happened: "It's an artefact of the file starting life as a single-user CLI script and being wrapped in FastAPI later. The lesson I took is that global mutable state is the first thing to audit when a script becomes a service."

Why only 3 exchanges? Why not the whole conversation?
  • Context budget. The window is shared between history, eight retrieved chunks, the instructions and the answer. History that grows unbounded eventually crowds out the statute text — and the statute text is the entire point.
  • Cost and latency scale with input tokens on every single request, forever.
  • Attention dilution. Long contexts suffer from the lost-in-the-middle effect; older, less relevant turns can distract from the current question.

"Three fits the interaction pattern: the prompt asks 1–3 clarifying questions, so three exchanges is roughly one complete clarification cycle. If I needed longer memory I'd use summary memory — an LLM compresses older turns into a running summary — or better for this domain, entity memory that extracts the specific facts the prompt keeps asking for: location, injury, intent. Those are what actually need to persist, not the prose."

Does the conversation history affect retrieval?

This is a sharp question and the answer is a real design flaw — take it head on. "No, and it should. History is added to the prompt, but retrieve() only ever sees the raw latest message. So if a user asks 'what's the punishment for that?', retrieval runs on those five words alone with no idea what 'that' refers to, and returns near-random chunks."

"The fix is query rewriting: before retrieval, use a cheap LLM call to rewrite the follow-up into a standalone question using the history — 'what's the punishment for that?' becomes 'what is the punishment for dumping waste on a neighbour's property?'. That's a standard component in production conversational RAG and it's the most valuable single thing missing from my pipeline."

What does /api/clear actually do?

"It calls reset_session(), which empties the in-memory list and writes an empty array to chat_history.json. The frontend calls it from the 'New Session' button and simultaneously clears its own message array, so the UI and the server both reset."

Then the honest bit: "Because the history is global, that endpoint clears history for everyone. With per-session storage it would take a session ID and clear only that key — which is another way of saying the same architectural fix. It's also worth noting the two states can drift: the client keeps its own copy of the messages, so a browser refresh empties the UI while the server history survives."

WSGI, ASGI and where Uvicorn fits

A Python web app needs a standard way to talk to a server. WSGI was that standard for a decade — synchronous, one request per worker at a time, the basis of Flask and Django's classic stack. ASGI is its asynchronous successor: it supports concurrent request handling on a single thread via an event loop, plus WebSockets and long-lived connections, which WSGI cannot express at all.

Uvicorn is the ASGI server — it owns the socket, parses HTTP, and runs the event loop. FastAPI is the framework — routing, validation, serialisation. Starlette sits underneath FastAPI providing the ASGI plumbing, and Pydantic provides the typed models. Naming that stack correctly is a quick credibility win.

The sync-versus-async question — get this right and you look senior

chat_endpoint is declared with def, not async def. That is correct, and here is why.

Inside it, generate_answer does two blocking things: a CPU-bound cross-encoder forward pass, and a synchronous requests.post that can take tens of seconds. If the endpoint were async def, that blocking work would run on the event loop and freeze the entire server — no other request could be processed until it finished.

Because it is a plain def, FastAPI automatically runs it in an external thread pool, leaving the event loop free. So concurrency is preserved without any async code.

The rule: use async def only if everything inside is awaited and non-blocking. If you call a synchronous library — requests, most ORMs, any ML model — use def and let FastAPI handle the threading. The genuinely wrong choice is async def with blocking code inside, which is the most common FastAPI mistake there is.

The fully async version would be async def plus httpx.AsyncClient for the LLM call and run_in_threadpool for the CPU-bound reranking.

Pydantic and automatic validation

class ChatRequest(BaseModel): query: str is doing more than it looks:

  • The request body is parsed and validated against the type. A missing query, or an integer where a string belongs, is rejected with a 422 Unprocessable Entity and a precise error message — before a single line of your code runs.
  • The same model generates the OpenAPI schema, so /docs gives you a live, interactive Swagger UI for free, and /redoc gives you formatted documentation.
  • Editors get autocomplete on request.query because it is a real typed attribute, not a dictionary lookup.

The principle is worth naming: the type hint is the validator. You do not write validation code that can drift from the documentation, because they are generated from the same declaration.

CORS — what it is and why it is here

Browsers enforce the same-origin policy: JavaScript loaded from localhost:5173 may not read a response from localhost:8000, because a different port means a different origin. Without an explicit opt-in, the browser blocks the response — the request may even reach your server, but the JavaScript never sees the reply. This is a browser-side protection, not a server-side one.

CORS is the mechanism by which a server says "these origins are allowed". For non-simple requests the browser first sends an OPTIONS preflight asking permission; the middleware answers it automatically.

A real security bug in these four lines

allow_origins=["*"] combined with allow_credentials=True is invalid per the CORS specification. Browsers refuse to honour a wildcard origin when credentials are permitted — so the combination is both insecure in intent and non-functional in effect.

Correct version: list explicit origins, driven by environment variable.

fixed
allow_origins=[os.getenv("FRONTEND_URL", "http://localhost:5173")],
allow_credentials=True,
allow_methods=["POST"],
allow_headers=["Content-Type"],

Say: "Wildcard CORS was a development convenience I never tightened. It's not the disaster it looks like — the API has no authentication and no cookies, so there's nothing to steal cross-origin — but it's wrong, it's spec-invalid alongside allow_credentials, and it's the first thing I'd fix before deploying publicly. Restricting methods and headers as well follows least privilege."

Cross-examination

Why FastAPI and not Flask or Django?
  • Async support. FastAPI is ASGI-native. My workload is I/O-bound — waiting on an LLM for seconds — which is exactly where async concurrency pays. Flask is WSGI and would need extra machinery.
  • Validation from types. Pydantic models mean the type hint is the validator, and malformed requests are rejected with a precise 422 before my code runs. In Flask I'd write that by hand or add a library.
  • Free documentation. The same models generate OpenAPI, so /docs is a live Swagger UI. That was genuinely useful for testing the backend before the React app existed.
  • Right size. Django brings an ORM, admin and templating — I have no relational data and no server-rendered pages. That's weight without benefit.

"Flask would have worked. FastAPI meant less code and better ergonomics for an API-only, I/O-bound service."

Confident no — this is a trap question and the correct answer is impressive. "No, it's deliberate and it's correct. Inside that endpoint I do genuinely blocking work: a synchronous requests.post to the LLM that can take tens of seconds, and a CPU-bound cross-encoder forward pass. "Because it's a plain def, FastAPI runs it in a thread pool automatically, so the event loop stays free and concurrency is preserved. The rule is: async def only when everything inside is awaited. async def wrapped around blocking calls is the single most common FastAPI performance bug."

What is CORS and why did you need it?

"Browsers enforce the same-origin policy: script from one origin can't read a response from another, and origin includes the port. My React dev server runs on 5173 and the API on 8000, so by default the browser blocks the response — the request may even hit the server, but the JavaScript never sees the reply."

"CORS is the server's way of declaring which origins may read its responses. For non-simple requests the browser first sends an OPTIONS preflight, and FastAPI's CORSMiddleware answers it. Critically it's a browser protection — curl and Postman ignore it entirely, so CORS is not a security boundary for the API itself."

It should be an explicit origin from an environment variable, with methods and headers restricted too."

What happens if generate_answer throws an exception?

"Most failures are already caught — the Ollama call is wrapped in try/except and returns a structured error dict with confidence: 'low', and the JSON parsing has layered fallbacks. So the common failure paths return a valid response shape rather than crashing."

"But an unhandled exception outside those blocks — say ChromaDB failing to open, or the embedding model failing to load — would propagate to FastAPI and become a bare 500 with a stack trace in the logs, and a client that can't distinguish 'server broken' from 'no results'."

"What I'd add: a global exception handler returning a consistent error envelope, explicit HTTPException with meaningful status codes — 503 when the LLM upstream is down, 504 on timeout — and structured logging with a request ID so I can trace a specific bad answer back through retrieval. Right now debugging a bad answer means re-running it by hand."

How would you add authentication?
  • Scheme. JWT bearer tokens. Login issues a short-lived access token plus a refresh token; the client sends Authorization: Bearer <token>.
  • Mechanism. A FastAPI dependency — Depends(get_current_user) — that verifies the signature and expiry and returns the user, or raises 401. Dependencies are the idiomatic place for this because they compose and are testable in isolation.
  • Passwords. Never stored — hashed with bcrypt or argon2.
  • Payoff beyond auth. A user ID immediately fixes the session problem from §10: history keyed by user rather than a global, and rate limits enforceable per account rather than per IP.
  • CORS interaction. With real credentials, the wildcard origin must go — the spec forbids it and browsers enforce that.
How would you test this backend?

Answer in layers, because that structure is what they're checking for:

  • Unit. Pure functions in isolation — get_recent_context with 0, 1 and 5 exchanges; the JSON repair cascade against deliberately malformed strings; the chunk-metadata loop for the aliasing bug.
  • Integration with mocks. FastAPI's TestClient against /api/chat, with retrieve and the Ollama call mocked. That tests routing, validation and the empty-retrieval guardrail without network or GPU.
  • Contract. Assert the response always has answer, legal_terms, relevant_articles, confidence — including on every failure path. That's the invariant the frontend depends on.
  • Retrieval quality. A labelled set of (question → expected section) pairs, measured with recall@k and MRR. This is the test that actually catches regressions from changing chunk size or the embedding model.
  • End-to-end. Ragas over a golden set, run in CI on a schedule, failing if faithfulness drops below a threshold.

Be honest: "The repository has no test suite — there's a retriever_test.py that's really a manual smoke script. That's the biggest engineering gap, and the first three layers above are cheap to add."

The React frontend

The idea in one line

The UI holds exactly one source of truth — an array of messages — and everything on screen is a pure function of that array plus a loading flag.

State

frontend/src/App.jsxstate and submit
const [messages, setMessages]   = useState([]);
const [input, setInput]         = useState('');
const [isLoading, setIsLoading] = useState(false);
const messagesEndRef            = useRef(null);

const handleSubmit = async (e) => {
  e.preventDefault();
  if (!input.trim() || isLoading) return;      // guard: no empty, no double-submit

  const userMessage = { role: 'user', content: input };
  setMessages((prev) => [...prev, userMessage]);  // functional update
  setInput('');
  setIsLoading(true);

  try {
    const response = await axios.post(API_URL, { query: input });
    setMessages((prev) => [...prev, { role: 'assistant', raw: response.data }]);
  } catch (error) {
    setMessages((prev) => [...prev, {
      role: 'assistant',
      content: "Sorry, I encountered an error connecting to the server..."
    }]);
  } finally {
    setIsLoading(false);      // finally: runs on success AND failure
  }
};

Four things to point at

  • Functional updates. setMessages(prev => [...prev, msg]) rather than setMessages([...messages, msg]). React batches state updates, and the closed-over messages may be stale; the functional form always receives the latest value. This is the classic React state bug and knowing it signals real experience.
  • Immutability. The spread creates a new array. React detects change by reference identity — messages.push(...) mutates in place, the reference is unchanged, and the component never re-renders.
  • The double-submit guard. if (!input.trim() || isLoading) return; — with a generation taking several seconds, an impatient user hitting Enter twice would otherwise fire two expensive LLM calls.
  • finally. setIsLoading(false) runs whether the request succeeded or threw. Put it only in try and a network error leaves the spinner running forever.

Effects and refs

frontend/src/App.jsxauto-scroll
const scrollToBottom = () => {
  messagesEndRef.current?.scrollIntoView({ behavior: "smooth" });
};

useEffect(() => { scrollToBottom(); }, [messages]);

Why a ref, not state. A ref is a mutable box that persists across renders and — crucially — changing it does not trigger a re-render. It is the right tool for reaching into a real DOM node. Storing a DOM node in state would cause an infinite render loop.

Why an effect. Scrolling is a side effect on the DOM, and it must happen after React has painted the new message. useEffect with [messages] as the dependency array runs exactly when the message list changes, and not on unrelated re-renders such as typing in the input.

The optional chaining ?. matters because ref.current is null on the very first render, before the element exists.

Rendering the structured response

The assistant message stores the whole backend payload as raw. The renderer then:

  • passes raw.answer through react-markdown, so the model's headers, bold text and numbered lists render properly — this is why the prompt insists on Markdown and forbids a wall of text;
  • renders raw.legal_terms and raw.relevant_articles as collapsible cards, which is the payoff for demanding structured JSON in §09;
  • shows raw.confidence as a badge.
Security note you should raise unprompted

Rendering model output as Markdown means rendering untrusted content. react-markdown is safe by default — it does not execute embedded HTML unless you explicitly add rehype-raw. Worth saying: "I'm rendering LLM output, so I deliberately rely on react-markdown's default HTML escaping rather than dangerouslySetInnerHTML. If I ever needed raw HTML I'd sanitise with DOMPurify first." Interviewers rarely expect a candidate to volunteer XSS awareness in an AI project.

Vite, Tailwind and the build

Vite serves your source as native ES modules during development, so there is no bundling step and startup is near-instant regardless of project size; for production it bundles with Rollup. That is the whole reason it displaced Create React App.

Tailwind is utility-first CSS: you compose styles from small classes in the markup rather than naming components in a stylesheet. The real win on a solo project is that there is no naming to invent and no dead CSS — the build scans your files and emits only the classes you actually used.

import.meta.env.VITE_BACKEND_URL — Vite exposes only variables prefixed VITE_ to client code. That prefix rule is a safety feature: it prevents server secrets in your environment from being accidentally compiled into a public bundle. Anything reaching the browser is public, which is exactly why the Ollama API key lives only in the backend.

vercel.json rewrites all paths to index.html. Necessary for any single-page app: the client owns routing, so a direct request for a sub-path must still be served the app shell rather than a 404.

Explain useState and useEffect.

"useState gives a function component memory across renders. It returns the current value and a setter; calling the setter schedules a re-render with the new value. In my app messages, input and isLoading are all state, because the UI must redraw when any of them changes."

"useEffect runs side effects after render — things that touch the world outside React. "Two reasons, and both are real bugs avoided."

Staleness. "messages is captured by the closure at render time. React batches updates, so if two updates happen before a re-render, the second reads a stale array and silently drops the first message. The functional form receives the latest value from React itself, so it can't be stale."

Immutability. "The spread creates a new array. React decides whether to re-render by comparing references, so mutating with push would leave the reference identical and the UI would never update — the data would be right and the screen would be wrong, which is the worst kind of bug."

"A ref is a persistent mutable container whose changes do not trigger a re-render. That's exactly what you want for a handle to a DOM node — I need to call scrollIntoView on it, not display it."

The idea in one line

A container is not a lightweight virtual machine — it is your process running on the host kernel inside isolated namespaces, which is why it starts in milliseconds and why the image contents are the whole contract.

The Dockerfile

Layer caching — the reason for the odd COPY order

Each instruction creates a layer. Docker reuses a cached layer if that instruction and everything before it are unchanged; once one layer misses, every layer after it rebuilds.

So copying requirements.txt alone and installing before copying the source is deliberate. Changing a line in api.py invalidates only the COPY . . layer onwards, and the expensive pip install — minutes, because of torch — stays cached. Reverse the order and every source edit reinstalls everything.

The other choices

  • python:3.10-slim — a much smaller base than the full image. Smaller means faster pulls, less disk, and a smaller attack surface.
  • rm -rf /var/lib/apt/lists/* in the same RUN — this matters. Layers are immutable and additive: deleting files in a later layer does not shrink the image, because the earlier layer still contains them. Cleaning in the same instruction is what actually reduces size.
  • --no-cache-dir — stops pip keeping downloaded wheels inside the image.
  • --host 0.0.0.0 — essential. Binding to 127.0.0.1 would make the server reachable only from inside the container, so port mapping would appear broken. This is one of the most common Docker mistakes and a very common interview question.
  • EXPOSE 8000 — documentation and metadata; it does not itself publish the port. You still need -p 8000:8000.
The interesting decision: ingesting at build time

RUN python ingest.py means the ChromaDB index is baked into the image.

Pros: startup is instant — no embedding work at boot; the container is fully self-contained with no volume or external DB; the image is reproducible, so the exact same index runs in every environment; and the knowledge base is versioned with the code.

Cons: adding a document requires a rebuild and redeploy; the image is larger (index plus the downloaded MiniLM weights); and it is completely unsuitable for user-uploaded documents.

The judgement: "For a fixed statute corpus that changes when Parliament amends the law, baking it in is the right trade — I get immutable, reproducible deployments. The moment users can upload documents, the index has to move to a mounted volume or a hosted vector service, because you can't rebuild an image per upload."

What is missing
  • No multi-stage build. build-essential is needed to compile some wheels but is dead weight at runtime. A builder stage plus a slim runtime stage would cut hundreds of megabytes.
  • Runs as root. Should useradd and USER appuser — a container escape as root is far worse than as an unprivileged user.
  • No .dockerignore. Without one, COPY . . pulls in .git, virtualenvs and any local .env — bloat and a real secret-leak risk.
  • No HEALTHCHECK, so an orchestrator cannot tell a hung process from a healthy one.
  • Unpinned dependencies. requirements.txt has no version constraints, so two builds a month apart can produce different behaviour. Pin them, or use a lockfile.

That's why it starts in milliseconds and uses a fraction of the memory, and also why the kernel is shared, which is the security trade-off."

Why copy requirements.txt separately before the rest of the code?

"Layer caching. Docker caches each instruction's layer and reuses it while that instruction and everything before it are unchanged. pip install with torch takes minutes. If I copied all the source first, editing one line in api.py would invalidate the copy layer and force a full reinstall on every build."

"By copying only requirements.txt, installing, and copying the source afterwards, a source change invalidates only the last layers. The install layer stays cached until the dependency list itself changes. It's a one-line reordering that turns a five-minute rebuild into a five-second one."

You run ingest.py during the build. Is that a good idea?

"It's a deliberate trade, and it depends entirely on whether the corpus is static."

"For mine it is — statutes change when Parliament amends them, not when users act. Baking the index in gives instant startup with no embedding at boot, a fully self-contained container with no volume or external database, and reproducible deployments where the same image always has the same index. It also versions the knowledge base with the code, so I can roll back both together."

"It's wrong the moment documents become dynamic. You can't rebuild an image per upload. Then the index moves to a mounted volume, or better, a hosted vector service, and ingestion becomes a separate job or an API endpoint. It also makes the image larger, since it carries both the index and the downloaded model weights."

Why --host 0.0.0.0?

"Because inside a container, 127.0.0.1 means the container's own loopback interface, not the host's. Binding there makes the server unreachable from outside the container even with correct port mapping — the connection is refused and it looks like Docker networking is broken."

"0.0.0.0 binds to all interfaces, including the one Docker attaches to the container network, so -p 8000:8000 works. It's the single most common Docker networking mistake."

How do you handle secrets like the Ollama API key?

"Environment variables loaded with python-dotenv, never committed — .env is gitignored and the README documents which variables are needed. On the host they're set as environment config in the platform's secret store, not in the image."

"Two principles I'd emphasise. First, secrets must never be baked into an image, because anyone who can pull the image can read every layer — docker history exposes build arguments too. Second, anything reaching the browser is public: Vite only exposes VITE_-prefixed variables to client code precisely to prevent accidental leaks, which is why the LLM key lives only on the backend and the frontend never calls the model directly."

Improvement: "The gap is that I have no .dockerignore, so a local .env would be copied into the image by COPY . .. That's a real leak path and it's a two-line fix."

Your app ran out of memory on a free tier. Walk me through what you did.

Tell it as a debugging story — those land far better than a list.

"Symptom: the container was killed on startup on a 512 MB instance. Cause: three things load into memory at import — the MiniLM embedding model, the FlashRank cross-encoder, and ChromaDB's HNSW index — and PyTorch allocates a per-thread workspace on top."

"Two fixes. torch.set_num_threads(1) cut the per-thread allocations substantially at a small throughput cost, which was acceptable because the LLM call dominates latency anyway. Then I made the reranker optional through a DISABLE_RERANKER environment variable, with an ImportError fallback so it also degrades safely if the library simply isn't installed."

"The part I'm happiest with is that disabling the reranker also reduces the candidate pool from 25 to 8 — retrieving extras with nothing to filter them would only add noise to the LLM context. The degradation is coherent rather than partial."

"Proper fix at scale: run the embedding model and reranker as a separate inference service so they load once and are shared, rather than co-locating everything in the API process."

§ 14Engineering

Evaluating a RAG system

The idea in one line

You cannot improve what you cannot measure, and RAG has two separately measurable halves — did you find the right passages, and did the model faithfully use them?

Why this is harder than normal ML evaluation

There is no single correct string. Two answers can be worded completely differently and both be right; one can be fluent and wrong; one can be accurate but omit the crucial penalty clause. Exact-match accuracy is meaningless. So evaluation splits into components, and each component gets its own metric.

Retrieval metrics — classical IR

MetricQuestion it answersNote
Recall@kIs the correct chunk in the top k at all?The most important stage-one metric — retrieval sets the ceiling for everything downstream
Precision@kWhat fraction of the top k are relevant?What reranking improves
MRRHow high up is the first correct result?Mean of 1/rank; good when one right answer exists
NDCG@kAre results ordered well, with graded relevance?The standard when relevance is not binary

Ragas — the four RAG-specific metrics

Ragas uses an LLM as a judge to score things classical metrics cannot. The elegant part of its design is the 2×2: two metrics need no ground truth, two do.

MetricComparesCatchesNeeds labels?
Faithfulnessanswer ↔ retrieved contextHallucination. Breaks the answer into claims and checks each is supported by the context.No
Answer relevancyanswer ↔ questionEvasive or off-topic answers. Generates questions from the answer and measures similarity to the original.No
Context precisioncontext ↔ ground truthNoisy retrieval — are relevant chunks ranked at the top?Yes
Context recallcontext ↔ ground truthMissed retrieval — did you fetch everything needed?Yes
The diagnostic that makes you sound experienced

Reading two metrics together tells you where to fix:

  • Low context recall, high faithfulness → retrieval is failing. Fix chunking, the embedding model, or add hybrid search. The generator is behaving.
  • High context recall, low faithfulness → retrieval is fine, the model is ignoring the context. Fix the prompt, lower the temperature, or change model.
  • Both high, users still unhappy → your metrics are fine and your questions are unrepresentative. Fix the evaluation set.

Say: "Faithfulness and context recall together tell you whether to fix the retriever or the generator — that's the main reason to measure both rather than a single end-to-end score."

Three honest problems — know them before they are found
  1. Three examples is not an evaluation. The file's own comment admits it. Three questions gives a number with no statistical meaning; a single unlucky retrieval swings the score by 33%. A usable set is 50–200 questions covering common queries, edge cases and out-of-scope questions that should be refused.
  2. The ground truths are generic, not from the corpus. "The penalty for theft varies by jurisdiction" is a plausible sentence about law in general, not a statement grounded in the BNS text that was actually ingested. Context recall compares retrieved context against ground truth, so vague ground truth produces a meaningless score. Real ground truths should be written from the statute, ideally naming the exact section.
  3. A likely import bug. The file imports answer_relevance; the Ragas metric is answer_relevancy. Also, datasets is imported but is not in requirements.txt. Both suggest this harness was written but not run to completion — worth checking and fixing before any interview, because "I built an evaluation pipeline" invites "show me the numbers".
How to talk about it honestly and still score

Do not claim results you do not have. The strong framing is:

"I built the evaluation harness and wired up all four Ragas metrics, but I'll be straight with you — I ran it on three questions, which is a smoke test, not an evaluation. What I have is the infrastructure and a clear plan: 50–100 legal questions with ground truths written from the actual statute text, run in CI, tracking faithfulness and context recall over time so I can tell whether a chunking change helped or hurt. Right now I'd be guessing, and I'd rather say that than quote a number from three samples."

That answer is better than a fabricated 0.87 faithfulness score, because it shows you know what evaluation is for.

Cross-examination

How do you know your RAG system is any good?

"You measure the two halves separately, because they fail for different reasons and have different fixes."

Retrieval: "Classical IR metrics against a labelled set — recall@k tells me whether the right chunk was fetched at all, which is the hard ceiling on everything downstream, and MRR or NDCG tells me whether it was ranked high enough to survive the top-8 cut."

Generation: "Ragas faithfulness — does every claim in the answer trace to the retrieved context — and answer relevancy — does it actually address the question rather than dodging."

"Plus context precision and recall, which bridge the two by comparing retrieved context against ground truth. And for a legal system specifically I'd add a domain metric: citation accuracy — does every section number in the answer literally appear in the retrieved chunks? That's cheap, deterministic, needs no LLM judge, and it's the failure mode that actually matters here."

Explain faithfulness versus answer relevancy.

"They measure different failures and you need both."

Faithfulness — "answer against context. Ragas decomposes the answer into individual claims and checks whether each is supported by the retrieved text. It catches hallucination. A perfectly on-topic answer citing an invented section scores low."

Answer relevancy — "answer against question. It generates questions that the answer would be a good response to, and measures their similarity to the actual question. It catches evasion and rambling. An answer that faithfully quotes irrelevant statute text scores low here but high on faithfulness."

The insight: "You can score perfectly on one and terribly on the other, which is exactly why a single end-to-end score is misleading. Faithfulness without relevancy is a correct answer to a different question."

Which of your metrics need ground-truth labels?

"Faithfulness and answer relevancy don't — they only compare the answer against the context and the question, both of which I already have at runtime. That's practically important: they can run on production traffic as monitoring, not just on a curated test set."

"Context precision and context recall do need ground truth, because 'was the right thing retrieved' is undefined without knowing what the right thing is. That's the labelling effort — and it's where most of my remaining work is."

Your eval set has three questions. Isn't that meaningless?

Agree immediately and completely; defending it is the only wrong answer.

"Yes. Three samples is a smoke test that proves the pipeline runs end to end — it is not an evaluation, and a single unlucky retrieval moves the score by a third. There's a second problem I'd flag too: my ground truths are generic statements about law rather than sentences grounded in the BNS text I actually ingested, so context recall is comparing against the wrong reference and the number wouldn't mean what it claims."

"What a real set looks like: 50–100 questions minimum, stratified across common queries, edge cases, multi-section questions, and out-of-scope questions that should be refused — that last category is important and easy to forget. Ground truths written from the statute with exact section numbers. Then run it in CI on every change to chunking or retrieval, and treat a drop in faithfulness or context recall as a build failure."

Using an LLM to judge an LLM — isn't that circular?

Excellent question to get; treat it as a genuine limitation, not an attack.

"There's real risk. Known problems: judges show self-preference, favouring outputs from the same model family; they're sensitive to position and to verbosity, rewarding longer answers; and they can be inconsistent across runs."

"Why it's still used: the task is much easier than generation. 'Is this claim supported by this passage?' is close to natural-language inference — a verification task with the evidence supplied — whereas generating correct legal advice is open-ended. Judges correlate reasonably well with human ratings on that narrower job."

"Mitigations: use a different, ideally stronger model as judge than as generator; set temperature 0 for reproducibility; validate the judge against a few hundred human labels once to establish correlation; and pair LLM judgement with deterministic checks. For my system the deterministic check is the strongest one available — every cited section number must literally appear in the retrieved context. No judge needed, no ambiguity."

Honest weaknesses and the roadmap

The candidate who finds the flaws in their own project before the interviewer does has already won the round — because that is literally the job.

The roadmap, in the order you would actually do it

  1. Make the API stateless. Nothing else can be scaled or trusted until this is fixed, and it unblocks auth, per-user rate limits and multi-replica deployment simultaneously.
  2. Build a real evaluation set. Do this before any retrieval change, or every subsequent improvement is guesswork. This is the step most candidates skip, so saying it second is a strong signal.
  3. Fix retrieval: structure-based chunking + hybrid + query rewriting. Measured against step 2, one change at a time.
  4. Harden the service. CORS, error handling, health endpoint, logging, tests in CI.
  5. Improve the experience. Streaming, inline citation links back to the source passage, a confidence-aware UI that visibly declines when nothing clears the score floor.
  6. Then, if it earns its place: fine-tune the cross-encoder on labelled legal pairs, and evaluate a legal-domain embedding model.
Order is the answer

Notice that "fine-tune a domain model" is last and "build an eval set" is second. That ordering is the interview answer. Juniors reach for the most exciting ML change first; engineers fix the measurement, then the correctness, then the quality. If you only remember one thing from §15, remember to say: "I'd build the evaluation set before touching retrieval, because otherwise I can't tell whether a change helped."

What the project genuinely does well

Do not only self-criticise — you need the counterweight ready, because "what are you proud of?" always follows "what's wrong with it?".

  • Two-stage retrieval. Most student RAG projects stop at vector search. Cascade ranking is the correct production pattern and you implemented it.
  • The refusal guardrail. Not calling the LLM when retrieval is empty is a small piece of code with outsized judgement behind it.
  • Structured, verifiable output. Demanding an exact supporting quote per legal term makes fabrication mechanically checkable rather than a matter of trust.
  • Graceful degradation. The reranker is optional at runtime and the candidate pool adapts coherently — a deliberate response to a real constraint.
  • Clean seams. Retrieval, generation and HTTP are three files with one responsibility each, so swapping the vector store or the LLM touches one file.
  • Layered failure handling. Three-tier JSON repair means a malformed model response still delivers the answer the user needs.

Cross-examination

"The conversation history is a module-level global, so every user of the deployed app shares one history.   • Constraints produce better designs. "The 512 MB limit forced the reranker to be optional at runtime — and that turned out to be a better architecture than hardcoding it, because now the same image runs in both environments."
  • Global state is the thing that breaks when a script becomes a service. "That's the specific lesson I'll carry forward: the moment something moves from one user to many, audit every module-level variable."
